# Quant Lab — Architecture

**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
`data` is the Python library that owns the dataset: it downloads raw snapshots, builds and validates immutable dataset versions, writes exploratory reports, and serves point-in-time data through its loader and command line. `server` is a local Python backend over `data`: HTTP for queries, WebSocket for live run progress. `web` is the TypeScript + React browser app, which talks only to `server`, through one generated contract.

```mermaid
flowchart LR

  server -- "Python calls (data contract)" --> data
  cli["command line"] --> data
  data -- "download" --> sources["Sharadar · EODHD"]
  data -- "read/write" --> home[("Data home: snapshots, dataset versions, run log")]
```

## Dependency rules
- `data` imports nothing internal. It never imports `server`; research code in later stages depends on `data` alone.
- `server` imports `data` only through the symbols in [data's contract](packages/data/contract.md).
- `web` reaches `server` only over HTTP and WebSocket, through the types generated from the server contract (AD-12). It imports no Python and no hand-written copies of server types.
- Only `data` writes to the data home. `server` reads datasets through `data` and starts and cancels runs through `data`.
- Enforced by an import-linter contract in the project checks (Python) and an ESLint import boundary plus a contract drift check (web) (AD-01, AD-12).

## Cross-package contracts

## Cross-cutting concerns
- **Point in time:** every stored fact has a known-date; the loader filters on it (AD-05). This is the rule behind LOAD-01 and the only path research code gets data through.
- **Reproducibility:** datasets are a pure function of saved snapshots, the `reference/` lists and code; fingerprints hash canonical content (AD-09).
- **Errors:** `data` raises typed errors from one hierarchy (`data.DataError`); `server` maps each to an HTTP problem response with a stable `code` that `web` shows in plain English.
- **Configuration:** `QLAB_HOME` (data home, default `~/QuantLabData`) and the two API keys come from environment variables or an uncommitted `.env`; keys are never logged or sent to `web`.
- **Security (QR-05):** `server` binds 127.0.0.1 only and rejects requests whose Host or Origin isn't the local app (AD-11).
- **Performance:** QR-01 by columnar Parquet scans with predicate pushdown; QR-02 by `server` holding the current version's tables in memory; QR-03 by tailing the run log every 250 ms (AD-10).

## Decisions

### AD-01: Three-package monorepo with enforced direction
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** Two runtimes (Python, browser) and a one-way dependency worth enforcing: research code must get data without the web backend, and the dataset library must never depend on the server. QR-06 needs both sides checked together.
- **Decision:** One repo; a uv workspace holds `data` and `server`, pnpm holds `web`. import-linter forbids `qlab_data` importing `qlab_server`; ESLint forbids `web` importing outside its own source and the generated client.
- **Alternatives:** One Python package plus the app — backend and research library tangle, and later stages inherit web dependencies. Separate repos — the contract drift check (AD-12) would cross repos for no benefit.
- **Consequences:** One checkout and one check command cover everything. A later stage's research package joins the workspace depending on `data` only.

### AD-02: Languages and frontend base
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The brief fixes Python for the backend and TypeScript + React for the app.
- **Decision:** Python 3.12; TypeScript 5.6 (strict) on Node 22 LTS; React 18.3 with Vite 5; TanStack Query for server state.
- **Alternatives:** Next.js — server rendering and routing conventions add nothing for a single local user. Plain fetch state — reinvents caching and refetching for every view.

### AD-03: Primary data source — Sharadar
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** Checked against DATA-01 (from 2006), DATA-02 (delisted S&P 500 members), DATA-03 (membership dates), DATA-04 (actions, delistings), DATA-05 (permanent ID, ticker history) and DATA-08 (≤ $50/month total, local storage).
- **Decision:** Sharadar's personal plan, paid annually (about $25/month): daily prices with raw and adjusted closes from 1998, the actions table (splits, dividends, delistings with reasons, acquirer), the tickers table (`permaticker`, ticker history) and the S&P 500 membership table (effective dates). ### AD-04: Cross-check source — EODHD Historian
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** VAL-06 and DATA-06 need an independent source of raw closes covering ≥ 80% of member-days since 2011, within the remaining budget.
- **Decision:** EODHD's end-of-day plan, paid annually (about $17/month; about $42/month with AD-03). Raw `close` per ticker since 2011 for every security that was ever a member, mapped to `permaticker` through Sharadar's dated ticker history.
- **Alternatives:** Tiingo (free or $30/month) — delisted coverage unverified, and the free tier's 500 symbols/month would take months to cover about 1,000 tickers. Stooq or Yahoo — current tickers only.
- **Consequences:** EODHD has no permanent ID, so a ticker is matched only within the date range Sharadar says it held it; unmatched tickers are reported as "not cross-checked". Coverage is measured on the first build; below 80% raises the open question in the spec.

### AD-05: Point-in-time rules
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** LOAD-01 forbids any value known after the requested date; UNIV-03 requires each membership record to say which date it carries. Sharadar gives effective dates only.
- **Decision:** Every stored fact carries a `known_date`. A day's prices: that day. A membership change: its announcement date if a source has one, else its effective date, with `date_kind` recorded. Corporate actions: their ex-date. Adjusted prices are never stored back-adjusted to today: the loader adjusts as of the request's end date, applying only actions with ex-date ≤ that date. Returns use same-day split bases, so they carry no future information.
- **Alternatives:** Store vendor back-adjusted prices — their level on any past date encodes splits and dividends that happened later. Treat membership as known before its effective date — no source gives the date, so it would be a guess.
- **Consequences:** Using effective dates is conservative: a strategy can't act on an index addition before it takes effect, which costs some realism but never leaks. A future source with announcement dates fills them without a design change.

### AD-06: Own adjustments and returns from raw prices
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** PRICE-04 and PRICE-05 require adjusted prices derived from raw prices and recorded actions, traceable factor by factor; RET-01–RET-05 define returns.
- **Decision:** `data` computes cumulative split and dividend factors itself from raw closes and the cleaned actions, and keeps the per-action factors so a trace can be shown. The vendor's adjusted close is not used.
- **Alternatives:** Use the vendor's adjusted close — untraceable, and back-adjusted to today (AD-05).
- **Consequences:** Adjustment bugs are ours, so golden cases (known splits and dividends) are the main test. Action types we can't adjust for are flagged (PRICE edge cases).

### AD-07: Delisting payouts — unknown unless entered by hand
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** RET-04 needs delisting payouts when known; no source within budget has them (AD-03).
- **Decision:** A delisted stock's final return is marked "delisting return unknown" by default. The researcher may add rows to `reference/delisting_payouts.csv` (permanent ID, payout per share, source note), which the build applies as corrections with that source as the reason.
- **Alternatives:** Estimate payouts from the last close — silently fills a value the spec forbids filling. Buy CRSP-grade data — far over budget.
- **Consequences:** Many acquisitions will show "unknown" until entered. The file is part of the build inputs, so editing it changes the fingerprint.

### AD-08: Storage — immutable snapshots and Parquet dataset versions
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** BUILD-04–BUILD-06 need untouched raw inputs and atomic publishing; LOAD-04 needs fixed versions; QR-01 needs fast column scans; QR-04 caps disk at 20 GB.
- **Decision:** Each download is a snapshot folder under `QLAB_HOME/snapshots/` with a manifest of SHA-256 hashes, made read-only on save. A build writes its tables (securities, tickers, membership, prices, actions, factors, returns, flags) as Parquet into a staging folder, then renames it to `QLAB_HOME/datasets/<fingerprint>/` and updates the version registry last. Polars reads and writes them. Updates download prices for the last 30 trading days plus the full actions, tickers and membership tables; a full refresh re-downloads everything.
- **Alternatives:** A database file (DuckDB or SQLite) for the dataset — harder to make immutable per version and to hash. pandas — slower scans and no lazy pushdown.
- **Consequences:** Old versions stay loadable as long as their folders exist. Revisions older than 30 trading days surface only on a full refresh.

### AD-09: Content fingerprint
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** BUILD-04 requires identical fingerprints from identical snapshots, on any day; Parquet bytes can differ between writes of the same data.
- **Decision:** The fingerprint is SHA-256 over each table, in fixed order, sorted by its key and serialised as Arrow IPC with a fixed schema; floats are rounded (prices 1e-6, factors and returns 1e-12) before hashing and storing. No timestamps or run IDs in table contents; build metadata lives in the version record, outside the hash.
- **Alternatives:** Hash Parquet files — breaks on writer or library changes. Hash the inputs only — misses nondeterminism in the build itself.
- **Consequences:** Parallel float reductions must be avoided or rounded away; a test rebuilds twice and compares.

### AD-10: Runs as subprocesses with a shared run log
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** BUILD-07 (one run at a time), BUILD-09 (app and command line run the same thing), RUN-03 (command-line runs visible live), RUN-04 (cancel), RUN-06 (reload mid-run), QR-03 (≤ 2 s).
- **Decision:** Every run is the `qlab` command-line process. `server` starts app runs by spawning it. Runs write progress as `RunEvent` rows to `QLAB_HOME/runs.sqlite` (WAL mode), which also holds the run lock (run ID, PID, start time; a lock whose PID is dead is reclaimed). `server` tails the log every 250 ms. Cancel sends SIGTERM to the run's PID; the run discards its staging folder and records the cancellation.
- **Alternatives:** Run builds inside the server process — command-line runs wouldn't appear, and a crash takes the server down. A message broker — needless for one machine.
- **Consequences:** The server can restart without affecting a run. The lock and log are the only shared state between processes.

### AD-11: Local-only backend
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `server`
- **Context:** QR-02, QR-03, QR-05; one local user, no login.
- **Decision:** FastAPI on uvicorn, bound to 127.0.0.1. Middleware rejects any request whose Host isn't `127.0.0.1` or `localhost` on the configured port, and any WebSocket or state-changing request whose Origin isn't the app's, to block DNS rebinding and cross-site requests from other pages.
- **Alternatives:** Flask plus a separate WebSocket server — two servers for one job. Litestar — fine, but smaller ecosystem for the generated OpenAPI step.
- **Consequences:** No authentication code. A future remote use would need a new decision.

### AD-12: One generated app↔backend contract
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** QR-06: one contract definition shared by app and backend; a mismatch fails before either runs.
- **Decision:** `server`'s Pydantic models are the single definition, covering HTTP bodies and WebSocket messages. A script exports them as OpenAPI with JSON Schema; openapi-typescript generates `web`'s types into a checked-in file. The project checks regenerate it and fail on any diff, and `tsc` fails on any use that no longer matches.
- **Alternatives:** Hand-written TypeScript types — drift silently. A schema-first IDL (protobuf) — another language to maintain for one consumer.
- **Consequences:** Every server change that touches a response regenerates the client in the same commit. Contract fixtures (JSON samples) are validated against the exported schema on both sides.

### AD-13: Exploratory reports as structured data
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** EDA-01–EDA-03 need a report per dataset version, tied to its fingerprint and shown in the app (APP-06). The `data-analysis` skill defines what the analysis covers.
- **Decision:** `data`'s `eda` component computes the report at the end of each build, following the `data-analysis` skill's method, and writes it as one JSON document (sections, tables, chart series, findings naming stocks and dates) inside the dataset version. `web` renders it with the same charts as every other view.
- **Alternatives:** Notebooks or static HTML — can't share the app's charts and design, and are harder to tie to a version.
- **Consequences:** The report schema is part of the data and server contracts. Narrative interpretation stays with the researcher; the report lists findings by rule (thresholds), not prose.

## Risks and open questions
- Sharadar's full price export may be several GB per snapshot; with monthly full refreshes QR-04 could fail — mitigation: incremental updates (AD-08), compressed snapshots, and measuring size on the first build.
- EODHD may cover under 80% of member-days (DATA-06), mostly delisted names with reused tickers — measured on the first build; if short, the researcher decides between lowering the threshold or adding a source.
- Sharadar's delisting-reason codes and action `value` meanings need confirming with a sample before the cleaning map is written.
- exchange_calendars must list every closure DATA-07 names (including 2025-01-09); a golden case checks it.
- Does affordable data cover all US stocks, not only the S&P 500? Sharadar does; widening the universe is a later idea, not S1.

# data — Architecture

**Package:** data · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`data` (Python package `qlab_data`, command `qlab`) turns vendor downloads into immutable, validated, point-in-time dataset versions and serves them. A run downloads into a read-only snapshot, cleans the raw tables into canonical ones keyed by permanent ID, derives adjustment factors and returns, validates every row, writes the exploratory report, and publishes the version atomically. The loader is the only read path, for `server` and research code alike.

| `cli` | `qlab build`, `qlab update`, `qlab rebuild`, `qlab versions`, `qlab diff` | BUILD-09 | `runs`, `store` |

**Skill routing:** `eda` runs the `data-analysis` skill's method (summary statistics, distributions and tails, missingness, correlation structure over rolling windows, stability over time) on each version's returns, prices and membership; the tasks that build it load that skill. No S1 component makes a beat-chance claim, so `null-hypothesis-testing` has no home here yet.

## Interfaces
See [contract.md](contract.md).

## Data
- **Sources:** Sharadar (AD-03) for prices, actions, tickers and S&P 500 membership; EODHD (AD-04) for cross-check closes since 2011. Hand-checked inputs live in the repo's `reference/`: known corporate actions (VAL-07), known delisted members (DATA-02), delisting payouts (AD-07).
- **Data home (`QLAB_HOME`):**
  ```
  snapshots/<source>/<UTC timestamp>-<hash8>/   → raw vendor files + manifest.json, read-only
  datasets/staging/<run-id>/                     → in-progress build, deleted on failure or cancel
  datasets/<fingerprint>/                        → published version: *.parquet, validation/, eda/report.json, version.json
  registry.json                                  → versions, inputs (snapshot IDs, reference hashes, code version), pass/fail, current
  runs.sqlite                                    → run lock, runs, RunEvent log
  ```
- **Canonical tables** (all keyed by `permaticker`, the permanent ID): `securities`, `tickers` (ticker, from, to), `membership` (effective date, known date, date kind, add/remove), `prices_raw`, `actions`, `delistings`, `factors`, `returns`, `flags`. Every row has a `known_date` (AD-05).
- **Flow:** sources → snapshots → clean → derive → validate → eda → store. `validate` marks rows rejected, corrected or flagged; rejected rows stay in `flags` only, never in the served tables.
- **Updates:** last 30 trading days of prices plus full small tables; a full refresh re-downloads everything (AD-08). The change list compares the new version with the previous one table by table.

## Cross-cutting concerns
- **Determinism:** no wall-clock time or randomness inside tables; stable sorts; rounded floats (AD-09). A test rebuilds from the same snapshots twice and compares fingerprints.
- **Progress:** each stage emits `RunEvent`s (stage, percent, current item, counts) through `runs`; components take a progress callback rather than importing `runs`.
- **Performance:** the loader scans Parquet lazily with date and ID predicates; QR-01 is timed on the full dataset in the test suite's slow tier.
- **Failure:** a stage error aborts the run, deletes staging and leaves the registry untouched (BUILD-06).

## Overview
`server` (Python package `qlab_server`, command `qlab-server`) is the local backend the app talks to. It answers queries by calling `data`'s loader and report functions, starts and cancels runs through `data`, and pushes live run progress over a WebSocket by tailing `data`'s run log. Its Pydantic models are the one definition of the app↔backend contract (AD-12). It also serves the built `web` bundle on the same origin.

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `models` | Pydantic request, response and message models: the app↔backend contract | QR-06 | — |

| `guard` | 127.0.0.1 binding, Host and Origin checks | QR-05 | — |
| `cache` | Holds the open `data.Loader` and hot tables for the selected version | QR-02, APP-07 | `data` |

| `live` | Run WebSocket: tails `data.read_events` every 250 ms and pushes messages; sends current state on connect | RUN-02, RUN-03, RUN-06, QR-03 | `models`, `data` |
| `app` | Assembles the FastAPI app, error mapping, static bundle | APP edge cases (backend not running is detected by `web`) | all above |

## Interfaces
See [contract.md](contract.md). Consumes [data's contract](../data/contract.md).

## Data
No storage of its own. Reads dataset versions and the run log only through `data`. The selected version is per server process, chosen by the app (APP-07); the default is `data.open_loader()`'s choice.

## Cross-cutting concerns
- **Errors:** each `data.DataError` maps to an RFC 9457 problem response carrying its `code`; unexpected errors return `internal_error` without stack traces.
- **Performance:** `cache` loads the selected version's prices, returns and flags into memory on first use; QR-02 is timed per endpoint on the full dataset.
- **Security:** see AD-11; no endpoint accepts file paths or shell input; run kinds are a closed enum.
- **Contract drift:** the project checks run `contract_export`, regenerate `web`'s types and fail on any diff (AD-12).

The loader adjusts them only up to the end date you ask for, because the usual approach (vendor prices adjusted to today) quietly leaks later splits and dividends into past prices.
- **AD-07, payouts when a stock is delisted.** They're marked "unknown" unless you add them by hand to a reference file. Expect many "unknown" acquisitions at first.
- **AD-08, updates.** An update re-downloads only the last 30 trading days of prices, to stay under the 20 GB disk limit. Revisions to older data show up only on a full refresh.
- **AD-10, how runs work.** Every run is a separate command-line process. Progress goes into a small local database that the server reads every 250 ms. That's how runs started from the command line show up live in the app.
- **AD-12, the shared contract.** The server's request and response models are the single definition. The TypeScript types are generated from them and checked in, and the checks fail if the two drift apart.

**Assumptions**
- **Names:** Python packages `qlab_data` and `qlab_server`, and commands `qlab` and `qlab-server`.
- **Data location:** data lives under `QLAB_HOME` (default `~/QuantLabData`). The hand-checked lists live in the repo's `reference/` folder.
- **Data handling:** dataframes use Polars, validated against fixed schemas. Each dataset version is identified by a fingerprint (a hash of its content), and stocks are identified by Sharadar's permanent ID.
- **Server:** it serves the built app on the same origin and remembers one selected dataset version for all views.
- **Exploratory report:** it's a JSON document stored inside each dataset version, with findings picked out by threshold rules rather than written-up prose. It's computed following the `data-analysis` skill's method.
- **Skills:** `frontend-design` is used for the `web` design module and `dataviz` for its charts. `null-hypothesis-testing` isn't used yet because no S1 module makes a beat-chance claim.
