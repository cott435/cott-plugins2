# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. # Contracts

Read when writing or changing a `contract.md`.

Write `docs/packages/<pkg>/contract.md`: the provider's promise to its consumers. Consumers read only this page, so it stands alone.

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). The ID survives Grow, because the component id becomes the package id.
- **One symbol per heading.** Never `### train.train / train.train_seeds: …` or `### baselines.MajorityClass / LogisticBaseline: …`, however alike the symbols are: dt resolves `Read:` IDs and `dt context` packets only from a symbol's own heading. `dt lint` errors on these (`contract-heading`).
- **Function sections:** the signature in the project's language, then **Invariants** (shapes, ranges, guarantees), **Errors** (what fails and how it's reported), and **Used by** (consuming components or packages, plus `PL-NN` IDs once those pipelines exist).

## When it touches older decisions

Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. Delete its Context, Decision, Alternatives and Consequences. The new decision's Context says what the old one chose and why that no longer holds. Then update every section that cited the old decision (tech stack, contracts, code comments, layout, risks) so that only the superseded line, the new decision and the Changelog mention it.

# Quant Research Platform — Architecture

**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
Two packages in one repo, split by runtime. `qdata` (Python) downloads Sharadar prices, corporate actions, tickers and S&P 500 membership into an append-only local store where every record carries its first-known date. Each completed run commits a read-only data version. It runs the validation checks and the Yahoo cross-check, and serves a point-in-time reader to research code and an HTTP + Server-Sent Events API, bound to localhost, to the app. `explorer` (TypeScript + React) is the browser app. It talks to `qdata` only through that API, with types generated from `qdata`'s OpenAPI schema.

```mermaid
flowchart LR
  SH[(Sharadar)] --> qdata
  YH[(Yahoo)] --> qdata
  research[research code, later stages] -->|query.PitReader| qdata
  explorer -->|HTTP + SSE, generated types| qdata
  qdata --> disk[(local store: Parquet + SQLite)]
```

## Dependency rules
- `explorer` never reads `qdata`'s files or store. It calls the HTTP API through the client generated from `contracts/openapi.json` (AD-08).

- Later research stages are new Python packages. They import only `qdata.query` and `qdata.core`, never `load`, `runs` or `api`.

## Cross-cutting concerns
- **Point in time (QUERY-01, CHECK-07, DATA-05):** every stored record has a `first_known` date and the run that added it. Every read filters on both (AD-04, AD-05). Returns and adjusted prices are derived at read time, never stored (AD-06).
- **Local only (QR-04, QR-06):** uvicorn binds 127.0.0.1, and the app rejects requests whose `Host` is not a loopback name. The only outgoing connections are `sources`' two clients. No endpoint exports data in bulk.
- **Performance (QR-02, QR-03):** DuckDB scans Parquet partitioned by dataset and run. Refreshes filter Sharadar on `lastupdated` (PB-02). Checks run as set-based DuckDB queries, not per-row Python. Timings are measured against the full version once it exists.
- **Errors:** refusals (`QUERY-05`, no data loaded, run already active) are `core.QueryRefused` and `runs.RunRefused` in Python, and HTTP 409/422 with a typed body in the API.
- **Skills:** `data-analysis` runs `checks`' threshold calibration (CHECK-12); `frontend-design` sets `explorer`'s visual direction before any page is built (QR-07).

## Decisions
### AD-01: Two packages split by runtime, one repo
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The brief fixes a TypeScript + React browser app over a Python backend. The two have different runtimes, toolchains and package managers. QR-08 asks that their messages be checked at build time.
- **Decision:** `qdata` (Python 3.12, uv) and `explorer` (TypeScript, pnpm) live in one repo, joined only by the committed OpenAPI schema. Everything Python is one package. `query` is the seam that becomes its own package if later stages shouldn't carry FastAPI.
- **Alternatives:** One Python package with the app as a static folder — hides a real runtime boundary and its build. Splitting `qdata` into store, checks and server packages now — no separate install or deployment justifies it yet.
- **Consequences:** CI runs two toolchains. A message change touches both packages in one commit, enforced by AD-08.

### AD-02: Sharadar via Nasdaq Data Link as the primary source
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** The brief says Sharadar is already paid for. Checked against DATA-01 (delisted members included), DATA-02 (unadjusted OHLCV), DATA-03 (splits, dividends, ticker changes, delistings with exit type), DATA-04 (membership by effective date), DATA-06 (permanent id) and QR-01. The Sharadar documentation pages (data.nasdaq.com/databases/SFA/documentation and /databases/SEP/documentation) are rendered by JavaScript and returned no content when read on 2026-10-17. So the table shapes this decision relies on come from prior knowledge and must be proven by the probe: `SEP` (daily prices, split-adjusted, with `closeunadj`), `ACTIONS` (dividend, split, tickerchange, acquisitionby, bankruptcyliquidation, delisted and others), `TICKERS` (`permaticker`, first and last price dates), `SP500` (added and removed events by date and ticker).
- **Decision:** `sources.SharadarSource` reads those four tables through the `nasdaq-data-link` client. The company id is `permaticker`. Unadjusted open, high and low are rebuilt as each split-adjusted value × `closeunadj / close` for that day. `SP500` events are resolved to `permaticker` by the ticker held on the event date. Exit types map from `ACTIONS` to the spec's four categories, in one table in `load`.
- **Alternatives:** Another vendor for membership — only if the probe finds `SP500` missing from the plan, within QR-01. Building membership from public index-change lists — unreliable before about 2010, and no permanent ids.
- **Consequences:** Every Sharadar-specific field stays inside `sources` and `load`. A switch touches those two modules.
- **Probe:** PB-01 — does the user's Nasdaq Data Link key return `SEP`, `ACTIONS`, `TICKERS` and `SP500` for current and delisted former S&P 500 members since 2000, with `permaticker`, `closeunadj`, and the action types and exit categories above?

### AD-03: Yahoo via yfinance as the cross-check source
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** The brief names Yahoo through an unofficial free client. Checked against DATA-07 (split- and dividend-adjusted closes fetched independently), XCHK-04 (≥ 95% of current members covered) and QR-05 (≤ 1 request per second). The yfinance docs (ranaroussi.github.io/yfinance, read 2026-10-17) say it is "not affiliated, endorsed, or vetted by Yahoo" and that "the Yahoo! finance API is intended for personal use only". They don't describe `history`'s adjustment parameters, rate limits or delisted coverage.
- **Decision:** `sources.YahooSource` calls `Ticker.history` with full adjustment, one ticker per request, behind a 1-per-second limiter and a per-day cache of fetched companies (QR-05). Tickers are mapped by the dates each one belonged to the company (XCHK edge case).
- **Alternatives:** Stooq or Tiingo free tier — not what the brief chose; kept as fallbacks behind `SecondarySource` if Yahoo coverage falls short.
- **Consequences:** The client can break without notice. The cross-check then reports "not run", and the other checks still complete.
- **Probe:** PB-03 — for the current S&P 500 members and the user's 10 delisted names, what share does `yfinance` return, are its closes split- and dividend-adjusted, and does it hold up at 1 request per second over 500+ tickers?

### AD-04: Append-only Parquet records, versions as committed manifests, SQLite catalog
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** LOAD-02 keeps revised records beside earlier ones. LOAD-03 needs earlier versions to stay byte-identical, LOAD-04 needs atomic commits and resumable runs, and LOAD-05 asks for every raw response. QUERY-01 and QUERY-02 filter by as-of date and version. Explanations and run progress are small mutable records, written by the worker and the API at the same time.
- **Decision:** Each dataset (bars, actions, membership, tickers) is append-only Parquet under `records/<dataset>/run=<run_id>/`. Each row carries `first_known`, `run_id` and `raw_ref`. A run writes raw responses to `raw/<run_id>/` and records to its partition. It commits by atomically renaming `versions/v<N>.json` into place, listing every run in the version. Partitions of runs that never committed are invisible, and a resumed run reuses their raw responses. Reads go through DuckDB views over a version's partitions, taking the latest row per key with `first_known` ≤ as-of. Runs, progress events, check results and explanations live in a SQLite catalog in WAL mode.
- **Alternatives:** A single DuckDB database file — one writer at a time, and versions would need copy-on-write tables. Postgres — a server to run for one user. Overwriting Parquet per version — loses the earlier values LOAD-02 keeps.
- **Consequences:** The store only grows. Compaction is a later concern. Every reader must go through `query` or `store`, never raw Parquet paths.

### AD-05: First-known date is the first download date unless the source evidences an earlier one
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** DATA-05, QUERY-01 and CHECK-07. Sharadar is believed to give only a `lastupdated` date per row, not a first-published date. That is open in the docs (AD-02).
- **Decision:** `first_known` = the run's download date for every record. The first full download is the one exception: all its records are stamped with their own dates (bar date, action ex-date, membership effective date), since Sharadar is treated as published by then. A revision is a key whose source values changed; it gets the date it was first seen. Unadjusted values are compared, so a split restating `SEP`'s adjusted history is not a revision.
- **Alternatives:** Stamp the first full download with its download date — every as-of read before 2026 would be empty, which defeats research use. Use `lastupdated` as first-known — it is a last-change date, so it moves later and would hide records that were known.
- **Consequences:** History before the first download is point-in-time only to the extent Sharadar did not revise it. That limit is recorded in Risks. Refreshes filter on `lastupdated` to find changed rows.
- **Probe:** PB-02 — does Sharadar expose any first-published date, and does `lastupdated` change on every revision (late dividend, corrected bar) so a refresh filtered on it misses nothing?

### AD-06: Returns and adjusted prices derived at read time
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** PRICE-02 and PRICE-03. Adjustments may use only actions known as of the read date (QUERY-01), and anchors are the caller's choice.
- **Decision:** `query` computes the total return r_t = (C_t + d_t) · s_t / C_{t−1} − 1 from unadjusted closes, cash dividends d_t and split ratios s_t (new shares per old share) by ex-date. It uses only actions with `first_known` ≤ as-of. Adjusted prices are the anchor's unadjusted close compounded through those returns.
- **Alternatives:** Store adjusted series per version — wrong for any as-of date before a later action is known, and one series per anchor.
- **Consequences:** Every read pays for the computation. That costs about 6,500 rows per company and 130,000 per universe-year, well within QR-02 in DuckDB. Checks and the cross-check use the same functions.

### AD-07: FastAPI on localhost with Server-Sent Events
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** RUN-03 asks for updates at least every 2 seconds, RUN-06 for runs that survive app reloads, QR-04 for local-only access, and QR-08 for typed messages.
- **Decision:** `qdata.api` is a FastAPI app served by uvicorn on 127.0.0.1, with a loopback `Host` check. Progress streams over SSE from the catalog's event table, with `Last-Event-ID` resume. It also serves `explorer`'s production build as static files, so one process is all the user starts.
- **Alternatives:** WebSockets — two-way messaging isn't needed, and reconnects are harder. Polling — works, but more requests and less live.
- **Consequences:** Pydantic models are the single definition of every message (AD-08).

### AD-08: Messages defined once in Pydantic, generated into TypeScript
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** QR-08 asks that a message-shape change on one side fail the other side's build.
- **Decision:** `qdata.api` Pydantic models export to `contracts/openapi.json`, committed. `explorer` generates `src/api/schema.ts` from it with `openapi-typescript`. CI fails if the export or the generated file differs from what is committed, and `tsc` fails where the app uses a changed field. SSE event payloads are schema components too.
- **Alternatives:** Hand-written TypeScript types — drift unseen. JSON Schema files as the source — a second definition beside the Pydantic models.
- **Consequences:** Every API change is a three-file commit: models, schema, generated types.

### AD-09: Each run in its own worker subprocess
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** RUN-02 allows one download or refresh at a time, and RUN-04 a cancel within 10 seconds. The backend-stop edge case marks runs "interrupted". QR-02 keeps the app responsive while checks are CPU-heavy.
- **Decision:** `runs` starts `python -m qdata.runs.worker <run_id>` for each run. The worker writes progress events to the catalog at least every second and checks a cancel flag between units of work, each under 10 seconds. A partial unique index allows only one active download or refresh. When the API starts, any run still marked running whose PID is gone becomes failed with "interrupted".
- **Alternatives:** A thread in the API process — a crash or a heavy check takes the API down with it. A task queue (Celery, RQ) — a broker for one user.
- **Consequences:** The worker and the API share state only through the catalog and the store.

### AD-10: React, Vite, TanStack Query and ECharts for the app
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `explorer`
- **Context:** The brief fixes TypeScript + React. EXPL-02 and EXPL-03 need a chart of about 6,500 days with markers and shaded intervals, interactive within 2 seconds (QR-02).
- **Decision:** React 18.3 with Vite 5, React Router 6 and TanStack Query 5 for server state. Charts use Apache ECharts 5 on canvas: `markArea` shades membership periods, and `markPoint`/`markLine` mark actions and the last trading date.
- **Alternatives:** TradingView Lightweight Charts — fast, but no native shaded vertical bands. uPlot — fastest, but every marker and band is custom drawing.
- **Consequences:** ECharts adds about 1 MB to the bundle; fine for a local app. The visual direction comes from `frontend-design`, not chart defaults (QR-07).

### AD-11: Failures keyed by check and subject, explained by fingerprint
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `qdata`
- **Context:** CHECK-10 keeps an explanation while the failure's found values are unchanged. It shows "failed again" with the old note when they change, and "resolved" when the failure disappears. XCHK-05 treats cross-check failures the same way.
- **Decision:** A failure's key is (check id, subject), where the subject is a company and day, an action, a day, or a company. Its fingerprint is a hash of the key plus its canonical found values. An explanation is stored against the key with the fingerprint it was written for. A matching fingerprint means explained; a different one means failed again, with the note shown. An explained key absent from a run counts as resolved.
- **Alternatives:** Match on key only — a changed value would stay silently explained.
- **Consequences:** Found values must be canonical (fixed rounding, sorted fields), or failures would flicker between runs.

# qdata — Architecture

**Package:** qdata · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`load` fetches from Sharadar through `sources`, normalises the rows into companies, bars, actions and membership intervals, and stages them in `store`. The run then commits a new data version. `query` answers every point-in-time read. `checks` and `xcheck` run over a version through `query` and record failures in the catalog. `runs` starts each run in a worker subprocess and records its progress. `api` exposes all of it to `explorer`.

```mermaid
flowchart LR
  api --> runs & query & checks & xcheck
  runs --> load & checks & xcheck
  xcheck --> sources & query & checks
  checks --> query & store
  load --> sources & store
  query --> store
  sources & store --> core
```

A single-page React app, served by `qdata.api` in normal use and by the Vite dev server (proxying to the API) in development.
