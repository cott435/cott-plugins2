# Extend mode: an idea file

`docs/brief.md` exists, so the new idea gets its own file and must earn its place in the project. Examples: `examples-extend.md`, `examples-ml.md`, `examples-data.md` (stage skills and references).

**Read before asking anything:** `docs/brief.md`, `docs/spec.md`, `docs/roadmap.md` and open ideas in `docs/ideas/`. Their problem, goals, constraints, Not Doing list and requirements constrain the new idea. `Specced` ideas are frozen records; where one disagrees with the spec, the spec is current.

- A `Draft` brief: ask whether to finish reviewing it first.
- A `Draft`, `Accepted` or `Parked` idea covering the same ground: offer to refine it instead. A `Specced` one is frozen; a change starts a new file.

**Phases 1-2** per `ideation.md`. Before Phase 1, restate the new idea in terms of the existing project: "This adds [X] so that [existing user] can [outcome]." Note which existing features and requirement IDs it touches.

**Fit check (during Phase 2) — answer one of these out loud. It decides whether the brief changes:**

| Finding | Idea file | Brief |
|---|---|---|
| Serves an existing goal. Every new stage of the same project does | Write it | **No change.** This is the common case. A new stage never adds a goal, even when the user asks for one: the stage is its roadmap row and the idea's *Serves* line. |
| Needs a new goal: the project's outcome itself widens, same problem and user | Write it | Add the goal with the next number. If that makes more than five, merge before writing: propose which goals fold together, your merge as the default, and write the merged set. Never write a sixth goal. |
| Changes a constraint (deadline, budget, a rule) | Write it | Update Constraints. |
| Contradicts the Not Doing list | Write it only if the user reverses that decision | Remove the item, with the user's agreement. Otherwise park the idea. |
| Different problem or different user | Don't write it | Push back: this may be a separate project with its own brief. |

**Phase 3: write `docs/ideas/<idea-slug>.md`** (kebab-case slug, e.g. `shared-editing.md`):

```markdown

**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [../brief.md](../brief.md)

## In one sentence
[This adds X so that Y can Z.]

[The specific pain this solves. Who hit it, how often, and evidence — customer requests, support tickets, lost deals.]

- **Touches:** [existing features and spec IDs this changes or depends on, e.g. EDIT-03]
- **Brief changes:** [None — or the sections edited, in one line: "Goal 4 added; Not doing narrowed"]
- **Stage:** [New S3 (roadmap stage on acceptance) — or "joins S2", when the user puts it in a stage not yet being built]

## Recommended direction
[1-3 paragraphs on how it should work from the user's point of view, and why this direction over the others.]

## Data
[ML and data ideas only — omit otherwise. What data it needs, where it lives or could come from, how much history and labels exist, and how results will be evaluated (held-out data, baseline). If an installed skill owns the evaluation step, such as a hypothesis-testing skill, name it here.]

## Alternatives considered
- [Direction] — [why not, in one line]

## What success looks like
- [Observable signs it worked]

## What we're betting on
- [Assumptions specific to this idea]

## Not doing
- [Tempting part of this idea we're leaving out] — [reason]

- [Questions spec-writing must resolve or ask about]
```

**Writing rules for idea files:**

- **Plain English, still no requirements.** Describe what the user experiences and why; `spec-writing` turns that into requirement IDs and acceptance criteria.
- **More room than the brief, not unlimited.** Aim for 300-700 words. The extra space goes to *How it fits*, *Alternatives considered*, and *Open questions* — the context the spec needs.
- **One idea per file.** If the conversation produced two separable ideas, write two files (ask the user which to do first).
- **Write it as a record, in the brief's voice.** The file outlives the review. Notes to the user ("my proposed limit, for you to check") belong in the conversation. Questions belong under *Open questions*.
- **Tool preferences live here, not in the spec.** If the user names a library, dataset or service ("hand-write the CNN, then compare with a torchvision model"), record it under *Recommended direction* or *Data*. `spec-writing` writes the behavior without the name, and `architecture-design` reads the name from here.
- **Never paste the idea into the brief.** Brief edits are limited to the fit-check table above. Goal numbers stay stable; new goals take the next number, and a merged goal keeps the lower one. If a goal is dropped or merged away, tell the user which spec requirements referenced it.

**Review Gate** (`../SKILL.md`): also say whether the brief changed and which sections.

**Stage** per `roadmap.md`: one stage for the idea, Source `ideas/<slug>.md`. Skip it only when the idea's *Stage* line says it joins a stage not yet being built.

**Idea status lifecycle:** `Draft` → `Accepted` (user approved here) → `Specced` (set by `spec-writing` once the spec is approved). Parked ideas get `Parked` with a one-line reason, so they aren't re-proposed blindly. **A `Specced` idea is frozen.** It records why the feature was added, as it stood that day. `spec-writing` adds a one-line banner saying so, and nobody edits the file afterwards. The spec is the current description. When a new idea changes what a `Specced` one describes, such as a narrowed holdout or a merged stage, the new idea gets its own file and names the old one under *Touches*. The old file is not edited.

# RL Lab

**Status:** Accepted · **Last updated:** 2026-10-18

## The problem
Reading about reinforcement learning (agents that learn by trial, error and reward) doesn't teach you why it works or why it fails. Library algorithms hide the parts that matter. The fastest way to understand it is to build agents yourself, in small 2D worlds where every result can be watched and explained.

## Who it's for
One learner: comfortable with Python and PyTorch basics, knows some reinforcement learning theory (Q-learning, the Bellman equation), still learning.

## Goals
1. Learn reinforcement learning by writing the learning algorithms yourself, one piece at a time.
2. Every trained agent is measured against a random player and a simple scripted bot, so "it learned" means something.
3. Every result can be explained, with the saved evidence from each run to back it up.
4. Any trained agent can be watched playing, as a replay.
5. A shared core (environment interface, training loop, logging, replay viewer) makes each new environment cheaper than the last.

## Constraints
- One person, evenings and weekends; a few weeks per environment.
- A MacBook Pro with Apple Silicon and no NVIDIA GPU.
- A training run must finish in under about an hour on the laptop's processor.
- No outside data: agents create their own experience by playing.

## What success looks like
- For each environment, the agent's learning curve beats a random player and a simple scripted bot. If it only ties the bot, that still counts as long as the tie is explained.
- A replay of each trained agent can be watched.
- Each piece added to an algorithm comes with a before-and-after comparison that shows what it changed.
- The first environment is classic Snake, learned by table-based Q-learning first, then by a deep Q-network (a neural network that scores each move) built step by step.

## What we're betting on
- Small 2D worlds with compact, hand-made views are enough to learn the core ideas.
- Writing the algorithms yourself teaches more than tuning a library's.
- A core shaped by one environment can be adapted to the next one without a rewrite.

## Not doing
- 3D worlds.
- Learning from pixels, or Atari games — too slow on a laptop, and the lesson is mostly computing power.
- Reproducing research papers — the aim is understanding, not benchmark scores.
- Web deployment.
- Library algorithms, for now — a comparison against them comes later.
- A general framework built before any environment needs it — the core grows from real use.
- Growing the board size during training — one fixed board keeps results comparable.
# Ideation: understand, expand, converge

Phases 1 and 2 of every run, New and Extend alike. The mode file says what to read before Phase 1 and what Phase 2 must also settle. Throughout, record the user's words as `requests.md` says: their first message, each answer, each direction they pick.

## Phase 1: Understand & expand

1. **Restate the idea** as a "How Might We" problem statement.
2. **Ask 3-5 sharpening questions**, no more, with `AskUserQuestion`: who it's for, what success looks like, real constraints, what's been tried, why now. Don't proceed until you know who it's for and what success looks like.
3. **Generate 5-8 variations**, each with a one-line reason it exists. Lenses: inversion, constraint removal, audience shift, combination, simplification, 10x version, expert lens. `frameworks.md` has more; pick what fits.

In a codebase, ground variations in what exists and cite files. Read `docs/references.md` too; an idea cites a reference as prior art by `RF-NN`, never its path.

## Phase 2: Evaluate & converge

1. **Cluster** what resonated into 2-3 meaningfully different directions.
2. **Stress-test** each: user value (painkiller or vitamin?), feasibility (cost, hardest part), differentiation (would someone switch?), and for ML and data projects, data: does usable data exist, can we use it, what's the non-ML baseline? "No usable data" is a feasibility failure, not an open question. Rubric: `refinement-criteria.md`.
3. **Surface hidden assumptions:** what you're betting is true, what could kill it, what you're ignoring for now.
4. **Get a decision** on a direction before writing anything.
# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.
# Roadmap stages

Read when proposing stages at the Review Gate and when adding them on acceptance; the mode file says which stages to propose. An example: `examples-data.md`.

Stages live in `docs/roadmap.md`. A stage is an outcome the user agreed: what they can do when it's done, such as "Data + stats" or "See my spending". It is coarse and unsized. **Don't size it:** no task estimates, no pipeline counts, no splitting a stage because it looks big. Two stages differ by outcome, never by size. Once a stage's pipelines are approved, `build-planning` cuts it into build-sized milestones (`M<n>`), each a vertical slice it can run end to end, and owns those rows.

## Features

### Snake environment (`SNAKE`)
**Serves:** Goal 1, Goal 5
**Stage:** S1
**Behavior:** Classic Snake on a grid. The snake moves one cell per move, turning left, turning right or going straight. Eating food makes it longer; hitting a wall or itself ends the game. The game hands the agent a short list of yes/no facts about its surroundings, and the reward for each move.

**Requirements**
- **SNAKE-01** The game is played on a fixed 10×10 board of open cells surrounded by walls.
  - Given any game, when it starts, then the board has 10×10 open cells, walls on all four sides, a snake of length 3 in the middle row heading right, and exactly one food on an empty cell.
  - Given any training run or test game, when the board size is read, then it is 10×10.
- **SNAKE-02** On each move the agent chooses one of 3 moves relative to its heading: straight, turn left, turn right.
  - Given a snake heading right, when it turns left, then its head moves up one cell and its heading becomes up.
  - Given any heading, when any of the 3 moves is chosen, then the snake never reverses into its own neck.
- **SNAKE-03** Eating food makes the snake 1 cell longer, gives a reward of +1, and places a new food on an empty cell.
  - Given food directly ahead, when the snake moves straight, then its length goes up by 1, the move's plain reward is +1, and one new food appears on a cell not covered by the snake.
- **SNAKE-04** Moving into a wall or into the snake's own body ends the game with a reward of −1.
  - Given the head next to a wall, when the snake moves into the wall, then the game ends and the move's reward is −1.
  - Given the head next to a body cell that will still be occupied after the move, when the snake moves into it, then the game ends and the move's reward is −1.
- **SNAKE-05** Every move that neither eats nor kills has a plain reward of 0.
  - Given a move into an empty cell, when it is made, then its plain reward is 0.
- **SNAKE-06** At every move the agent sees exactly 11 yes/no facts: danger straight, danger left, danger right; heading up, down, left, right; food is up, down, left, right of the head.
  - Given the head next to the top wall while heading up, when the facts are read, then "danger straight" is yes and "heading up" is yes.
  - Given food above and to the left of the head, when the facts are read, then "food is up" and "food is left" are yes and "food is down" and "food is right" are no.
  - Given a cell occupied by the body or a wall next to the head on its left, when the facts are read, then "danger left" is yes.
- **SNAKE-07** A game ends after 100 moves in a row without eating.
  - Given a snake that has gone 100 moves since its last food (or since the start), when the 100th move is made without eating, then the game ends and that move's plain reward is 0.
- **SNAKE-08** The same game seed and the same moves always give the same game.
  - Given a game seed and a list of moves, when the game is played twice, then every board, food position, reward and ending is identical.

**Edge cases & errors**
- The head moves into the cell the tail is leaving on that move → allowed; the game goes on.
- The snake fills every cell, so no food can be placed → the game ends as a full-board finish, with no −1.
- The food appears directly ahead of a turning snake → nothing special; food is only eaten when the head enters its cell.

### Baselines (`BASE`)
**Serves:** Goal 2
**Stage:** S1
**Behavior:** Two non-learning players set the bar every learner must clear: one picks moves at random, the other follows a simple rule. Both play the same test games as the learners.

**Requirements**
- **BASE-01** The random player picks each move uniformly at random from the 3 moves.
  - Given 30,000 random-player moves, when the share of each move is counted, then each is between 32% and 35%.
- **BASE-02** The scripted bot moves toward the food, never making a move that kills it immediately when a safe move exists.
  - Given food to the left and the left cell free, when the bot moves, then it turns left.
  - Given food straight ahead and a wall straight ahead with the right cell free, when the bot moves, then it turns right.
  - Given several safe moves equally close to the food, when the bot moves, then it prefers straight, then left, then right.
- **BASE-03** When every move kills it, the scripted bot goes straight.
  - Given danger straight, left and right, when the bot moves, then it goes straight and the game ends.

**Edge cases & errors**
- No safe move gets closer to the food → the bot takes the safe move that leaves it closest to the food, using the same preference order on ties.

### Table-based Q-learning (`TAB`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** The first learner keeps a table with a score for each of the 3 moves in every combination of the 11 facts, and improves the table after every move from the reward and the best score of the next situation.

**Requirements**
- **TAB-01** The table learner updates the score of the move it just made from the reward plus the discounted best score of the situation it reached (a one-step Q-learning update), after every move.
  - Given a known table, situation, move, reward and next situation, when one update is applied, then the new score equals the hand-computed Q-learning update for the run's learning rate and discount.
  - Given a move that ended the game, when the update is applied, then the next situation contributes nothing.
- **TAB-02** While training, the table learner sometimes picks a random move instead of its best one, at a rate that falls over the run from a starting rate to a floor saved with the run's settings.
  - Given a run's exploration settings, when the rate is read at the start, the middle and the end of training, then it matches the saved schedule at each point.
- **TAB-03** During test games the table learner always picks its highest-scored move.
  - Given a trained table, when a test game is played twice from the same seed, then both games are identical.
- **TAB-04** The learning update is written in the project; no ready-made learning algorithm is used.
  - Given the trained table learner, when its learning steps are traced, then each one is code written in the project.

**Edge cases & errors**
- A situation never seen in training comes up in a test game → all 3 moves score equal and the learner picks by the order straight, left, right.

### DQN ladder (`DQN`)
**Serves:** Goal 1, Goal 3
**Stage:** S1
**Behavior:** The second learner replaces the table with a small learned function that scores the 3 moves from the 11 facts. It is built in four rungs, each adding one piece to the one before, so each piece's effect can be measured on its own:
1. Plain: learns from each move as it happens.
2. + Replay buffer: learns from random samples of stored past moves.
3. + Target network: its learning targets come from a frozen copy of itself, refreshed at a fixed interval.
4. + Double DQN: the learner picks the best next move, and the frozen copy scores it.

**Requirements**
- **DQN-01** The plain rung learns from each move right after it is made, using that move's reward plus the discounted best score of the next situation as its target.
  - Given a known function, move, reward and next situation, when one update is applied, then the target equals the hand-computed value and the function's score for that move moves toward it.
- **DQN-02** The replay-buffer rung stores past moves and learns from batches drawn at random from that store.
  - Given a store of past moves and a seed, when a batch is drawn, then every move in it comes from the store and the same seed draws the same batch.
  - Given a store at its saved capacity, when a new move is added, then the oldest move is dropped.
- **DQN-03** The target-network rung computes its targets from a frozen copy of the learner, refreshed every fixed number of updates saved with the run's settings.
  - Given the refresh interval, when updates run between two refreshes, then the copy does not change; when the interval is reached, the copy equals the learner.
- **DQN-04** The Double DQN rung chooses the next situation's best move with the learner, and scores that move with the frozen copy.
  - Given a learner and a copy that disagree on the next situation's best move, when the target is computed, then it uses the copy's score for the learner's chosen move.
- **DQN-05** Each rung differs from the rung before only by the piece it adds; every other setting is the same.
  - Given the saved settings of two neighbouring rungs, when they are compared, then the only differences are the added piece and its own settings.
- **DQN-06** While training, each rung explores with the same falling random-move rate as TAB-02; during test games it always picks its highest-scored move.
  - Given a trained rung, when a test game is played twice from the same seed, then both games are identical.
- **DQN-07** The learning updates of every rung are written in the project; no ready-made learning algorithm is used.
  - Given any trained rung, when its learning steps are traced, then each one is code written in the project.

**Edge cases & errors**
- A move that ended the game is learned from → the next situation contributes nothing to its target.
- The replay-buffer store holds fewer moves than one batch → learning waits until it holds a full batch.
- Scores grow without bound (training diverges) → the run keeps going and saves its curve; the comparison reports the result, and the divergence is visible in the curve.

### Reward shaping (`SHAPE`)
**Serves:** Goal 1, Goal 3
**Stage:** S1
**Behavior:** A second reward adds a small nudge toward the food on top of the plain reward, so the learner can be trained on either and the two compared.

**Requirements**
- **SHAPE-01** The shaped reward is the plain reward plus 0.1 for a move that brings the head closer to the food and minus 0.1 for a move that takes it further away, measured in grid steps to the food that was on the board before the move.
  - Given a move that cuts the distance to the food from 5 to 4, when it is made, then the shaped reward is +0.1.
  - Given a move that raises the distance from 4 to 5, when it is made, then the shaped reward is −0.1.
  - Given a move that eats the food, when it is made, then the shaped reward is +1.1.
- **SHAPE-02** A move that ends the game by collision has a shaped reward of −1, with no nudge.
  - Given a move into a wall, when it is made, then the shaped reward is −1.
- **SHAPE-03** Every run uses either the plain or the shaped reward for training, and saves which.
  - Given a finished run, when its saved settings are read, then they name its reward.
- **SHAPE-04** Test scores never use the shaped reward; they always count food eaten.
  - Given the same agent tested once after plain training and once after shaped training, when the scores are read, then both are food eaten per game.
- **SHAPE-05** The plain-versus-shaped comparison trains the Double DQN rung on each reward, with every other setting the same.
  - Given the plain and shaped runs of that comparison, when their saved settings are compared, then the only difference is the reward.

### Training runs (`RUN`)
**Serves:** Goal 3, Goal 5
**Stage:** S1
**Behavior:** One training run trains one learner, with one reward, from one seed. The learner starts the run with one action, watches its progress, and afterwards finds everything the run produced saved together, enough to recreate it.

**Requirements**
- **RUN-01** A training run trains one learner (the table learner or one DQN rung) with one reward from one training seed.
  - Given a learner, a reward and a seed, when a run is started with one action, then it trains that learner with that reward and seed and nothing else.
- **RUN-02** Each run saves its settings, seed, learning curve, final agent and test games.
  - Given a finished run, when its saved evidence is opened, then all five are there.
- **RUN-03** Rerunning from a run's saved settings and seed gives the same result.
  - Given a finished run, when it is run again on the same laptop from its saved settings and seed, then the test score at every curve point is identical.
- **RUN-04** While a run trains, it shows the moves trained so far, the latest test score and the time elapsed.
  - Given a run in progress, when a curve point is reached, then the display updates all three.
- **RUN-05** A run never overwrites another run's evidence.
  - Given two runs with the same learner, reward and seed, when both finish, then both sets of evidence are kept.
- **RUN-06** A run that stops before it finishes is marked incomplete and is left out of every comparison.
  - Given a run stopped by hand partway through, when comparisons are made, then it is listed as incomplete and its numbers are not used.
- **RUN-07** A run still training at 60 minutes stops, saves what it has, and is marked over the time limit.
  - Given a run that reaches 60 minutes, when the limit passes, then training stops, its evidence so far is saved, it is marked over the time limit, and it is left out of every comparison.
- **RUN-08** Training, testing, saving evidence and replay work for a second environment without changes to them.
  - Given a minimal second environment used only for this check, when it is trained, tested and replayed, then none of the training, testing, saving or replay behavior had to change.

**Edge cases & errors**
- A run is started with a learner or reward that doesn't exist → it does not start, and the message lists the valid choices.
- The disk fills while saving → the run is marked incomplete and says which evidence is missing.

### Evaluation & comparison (`EVAL`)
**Serves:** Goal 2, Goal 3
**Stage:** S1
**Behavior:** Every learner and baseline is scored on the same 100 held-out test games. Learning curves show progress against the baselines. Comparison reports say, from 5 training seeds per learner, whether each learner beats the baselines, and what each added piece changed. Each result carries a written explanation, so a tie counts.

**Requirements**
- **EVAL-01** Every agent is scored on the same 100 test games, each started from a fixed test seed that is never used in training.
  - Given any two agents, when they are tested, then they play games from the same 100 test seeds.
  - Given any training run, when its game seeds are compared with the test seeds, then none match.
- **EVAL-02** An agent's test score is the mean food eaten per game over the 100 test games.
  - Given 100 test games with known food eaten, when the score is computed, then it equals their mean.
- **EVAL-03** Each run's learning curve is its test score against moves trained, at 20 evenly spaced points, with the random player's and the scripted bot's scores drawn as lines on the same chart; the chart follows the `dataviz` skill.
  - Given a finished run, when its curve is opened, then it shows 20 test scores in order of moves trained, plus both baseline lines.
  - Given the 5 seeds of one learner, when their combined curve is opened, then it shows the mean across seeds at each point with the spread across seeds.
- **EVAL-04** Each learner's final agent is compared with each baseline using the `null-hypothesis-testing` skill. It is given the 100 test-game scores of each of the learner's 5 seed runs, and the baseline's scores on the same 100 games. The learner beats the baseline when its score is higher and the difference is significant at 5% after correcting for the number of comparisons in the report; it ties when the difference is not significant; otherwise it loses.
  - Given 5 complete seed runs of a learner, when the comparison is made, then the report states beats, ties or loses against each baseline, with the test's result.
  - Given fewer than 5 complete seed runs, when the comparison is requested, then it is not made, and the report lists the missing seeds.
- **EVAL-05** Each added piece gets a before-and-after comparison with the rung below it, made the same way as EVAL-04: table learner → plain DQN, plain → + replay buffer, + replay buffer → + target network, + target network → + Double DQN, and plain reward → shaped reward. Every outcome counts: better, worse, or no difference.
  - Given 5 complete seed runs of both rungs, when the comparison is made, then the report states better, worse or no difference, with the test's result and both rungs' combined curves on one chart.
- **EVAL-06** Every comparison result holds a written explanation; a result with no explanation is shown as unexplained.
  - Given a comparison result with an empty explanation, when the report is opened, then that result is marked unexplained.
  - Given a tie or a no-difference result with an explanation, when the report is opened, then it is marked explained.
- **EVAL-07** Snake is done when the Double DQN agent beats the random player, beats or ties the scripted bot, every comparison in EVAL-04 and EVAL-05 has a result, and every tie and no-difference result is explained.
  - Given a Double DQN agent that beats both baselines and all comparisons made and explained, when the done check runs, then it reports done.
  - Given a Double DQN agent that ties the scripted bot with the tie explained, when the done check runs, then it reports done.
  - Given a tie with the scripted bot left unexplained, when the done check runs, then it reports not done and names the missing explanation.
  - Given a Double DQN agent that ties or loses to the random player, when the done check runs, then it reports not done.

**Edge cases & errors**
- Every seed of a learner scores exactly the same as a baseline → the result is a tie.
- A run marked incomplete or over the time limit is among a learner's runs → it is left out, and the comparison waits for 5 complete runs.

### Replay viewer (`REPLAY`)
**Serves:** Goal 3, Goal 4, Goal 5
**Stage:** S1
**Behavior:** The learner picks a saved agent and one of its test games, or a fresh game seed, and watches it play move by move. Next to the board, the viewer shows how the agent scored each of its 3 moves, so its choices can be explained.

**Requirements**
- **REPLAY-01** Any saved test game of any saved agent, the baselines included, can be watched as a replay.
  - Given a finished run, when one of its test games is chosen, then the replay plays it from the first move to the end.
- **REPLAY-02** The replay shows the board, the snake, the food, the move number, the food eaten so far, and how the game ended.
  - Given a replay at any move, when it is shown, then all of these are visible; at the end, the ending (wall, body, 100 moves without food, full board) is shown.
- **REPLAY-03** At every move of a learner's game, the replay shows the agent's score for each of the 3 moves, with the chosen move marked.
  - Given a table learner or DQN replay at any move, when it is shown, then 3 scores are visible and the chosen one is marked.
  - Given a baseline replay, when it is shown, then the move scores are shown as not applicable.
- **REPLAY-04** The replay can be paused, resumed, and stepped forward one move at a time.
  - Given a paused replay, when "step" is chosen, then it advances exactly one move and stays paused.
- **REPLAY-05** The replay speed can be set from 1 to 30 moves per second.
  - Given a speed of 5 moves per second, when it plays for 10 seconds, then it advances 50 moves (±2).
- **REPLAY-06** A replay of a saved test game is identical to the game that was scored.
  - Given a saved test game, when it is replayed, then every board, move and food count matches the saved game.
- **REPLAY-07** A saved agent can play and be watched on a fresh game from any seed chosen at the time.
  - Given a saved agent and a new seed, when the game is watched twice, then both games are identical.

**Edge cases & errors**
- The chosen agent or game can't be found or read → the viewer opens nothing and names the missing item.
- A game ends on its first move → the replay shows that one move and the ending.

## Data requirements
- **DATA-01** All training and test experience comes from the agents playing Snake; no outside data is used.
  - Given any run, when its inputs are listed, then the only source of games is the Snake environment, started from the run's own seeds.

## Quality requirements
- **QR-01** Each training run, including its test games, finishes in under 1 hour (60 minutes) on the laptop's processor.
  - Checked by the elapsed time saved with each run; RUN-07 stops any run that reaches 60 minutes.
- **QR-02** Training, testing and replay run on the Apple Silicon laptop with no NVIDIA graphics card.
  - Checked by running every learner's training, a comparison and a replay on that laptop.

## Assumptions
- One learner uses the lab on one Apple Silicon laptop, evenings and weekends.
- The full ladder (6 learner setups: the table learner, 4 DQN rungs and the shaped-reward Double DQN, × 5 seeds = 30 runs) takes many hours in total; only each single run has the 1-hour limit.
- The done check in EVAL-07 judges the Double DQN agent, the top of the ladder; the table learner and other rungs are reported but don't gate it.
- The table learner's and DQN rungs' tuning settings (learning rate, discount, exploration schedule, store size, refresh interval) are saved per run but not fixed by the spec; they are found during the build within the one-hour limit.

# Example: an ML feature in an existing product

Extend mode for an ML idea: the Data section and a baseline.

## ML Feature in an Existing Product (Extend Mode)

**User invokes:** `/ideate use ML to flag bad assay plates automatically in our lab results app`

The app already has `docs/brief.md` (Goal 2: *Bad data is caught before it reaches analysis*) and `docs/spec.md`, so this is **extend mode**. The skill reads both, plus the `qc` module in the codebase.

### Phase 1: Understand & Expand

> **How might we** catch failed plates before they reach analysis, without scientists reviewing every plate by hand?

Questions:

1. **How are plates checked today, and how long does it take?**
2. **What history exists?** How many plates, and is there a record of which ones were failed and why?
3. **What's worse: a bad plate getting through, or a good plate being re-run?**

**User responds:** "Scientists eyeball every plate — about 6 hours a week. We have 3 years of plate reads, roughly 40,000 plates, and about 2% were marked failed in the app. Missing a bad plate is much worse; a re-run costs a day."

**Skill continues:**

Before any ML: assay QC already has a standard rule, the **Z′-factor** (plates under 0.5 are suspect). Your `qc` module computes it but nobody acts on it. That's the baseline any model has to beat. If the rule alone catches most failures, you may not need ML at all.

Variations:

1. **Simplification — Just Use the Rule:** Auto-flag plates with Z′ < 0.5 and stop there. Zero ML.
2. **Ranked Review Queue:** A model scores every plate. Scientists review the riskiest first and stop when the scores get low. Humans still decide.
3. **Inversion — Auto-Pass the Obvious:** Instead of finding bad plates, confidently clear the clearly-good ones, and scientists review the rest.
4. **Anomaly Detection:** No labels needed. Flag plates that look unlike typical ones. Useful if past "failed" labels turn out to be unreliable.
5. **Expert Lens — Layout Patterns:** Many failures show up as spatial patterns (edge effects, a dead column). Features built from plate layout may beat a generic model.

### Phase 2: Evaluate & Converge (summary)

**Data check:** 40,000 plates with 800 failures is enough to try a supervised model, *if* the labels are consistent. That's the biggest bet. Different scientists may fail plates for different reasons. **Baseline:** the Z′ rule. **Cost asymmetry:** missing a bad plate is far worse, so measure recall at a fixed review budget, not accuracy (98% accuracy is free by passing everything).

The user picks **2 (ranked queue), with 1 as the baseline it must beat**. **Fit check:** it serves existing Goal 2 and the same users, so **the brief does not change.**

### Phase 3: Write the Idea File

`docs/ideas/plate-qc-ranking.md`:

```markdown
# Idea: Plate QC Ranking

**Status:** Draft · **Last updated:** 2026-10-14 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This ranks every new assay plate by how likely it is to fail QC, so scientists review the riskiest plates first instead of checking all of them.

## The problem
Scientists check every plate by eye, about 6 hours a week. Failures are rare (about 2%) but costly: a bad plate that slips through corrupts downstream analysis. A good plate failed by mistake costs a day to re-run. The app already computes a standard quality score (Z′) but nothing acts on it.

## Who it's for
Lab scientists doing plate QC, during their weekly review.

## How it fits
- **Serves:** Goal 2 (bad data caught before analysis)
- **Touches:** QC-01 (Z′ is calculated per plate), QC-03 (scientist marks pass/fail)
- **Brief changes:** None
- **Stage:** New S3 (roadmap stage on acceptance)

## Recommended direction
Each new plate gets a risk score from a model trained on three years of past pass/fail decisions. The review screen sorts plates riskiest first. Scientists still make every pass/fail call; the model only sets the order.

The Z′ rule is the baseline. If the model doesn't clearly beat "sort by Z′", we ship the rule alone and stop.

## Data
- About 40,000 plates over 3 years, with raw reads, Z′, and the scientist's pass/fail decision (about 800 failures).
- All in our own database. No outside data needed.
- Evaluate on the most recent 6 months, never trained on, to mimic real use.

## Alternatives considered
- Rule only (Z′ < 0.5) — kept as the baseline, and the fallback if the model doesn't beat it.
- Anomaly detection — only if past labels turn out to be unreliable.
- Auto-passing obvious plates — revisit once the ranking has earned trust.

## Questions (my guess in brackets; say "defaults" to take them all)

## Variations
1. **Policy-gradient ladder, one piece at a time** (mirrors the DQN rungs): REINFORCE → + a learned baseline → actor-critic → PPO's clipped update. Each rung gets a before-and-after comparison.
2. **One fish first, then several**: a single-fish tank rung before the multi-fish one, so you can tell difficulty from the algorithm apart from difficulty from crowding.
3. **Shared policy vs independent learners**: a comparison rung in its own right, a first real taste of multi-agent RL.
4. **Wide view vs short view**: train once seeing the whole tank and once with the short radius, and measure what limited sight costs.
5. **Survival vs plain staying-alive reward**: +1 per moment alive vs that plus a nudge for distance from the ball, the fish-tank version of Snake's shaped reward.
6. **Ball speeds up over time** (the 10x version): harder late game, which makes long survival mean more.
7. **The ball becomes a learning hunter** (inversion): two learners against each other. It's tempting, but I'd leave it out. It's a different lesson, and it doubles what can go wrong.
