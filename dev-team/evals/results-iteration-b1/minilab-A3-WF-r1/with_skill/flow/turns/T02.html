# Run

Read when `dt build status` shows no build for the active milestone. It starts one and drives it
until a stop or the milestone exit. The loop is `loop.md`; stops are `escalation.md`.

```
CHECK → [the user's go] → dt build start M<n> → loop.md → stop (escalation.md) or Exit
```

## Steps

**1. Check, then ask.** `dt status` shows the plan `Approved` with its `**Base:**` set, and
`dt status --skill build-setup` says `current`; the working tree is clean. Then ask for the go in
one message: the milestone, its task and half counts, the critical path and widest wave from
`dt status`, the concurrency cap (default 6), each `**Risk:** external` task (it waits for its own
yes), and that the build runs on its own from here until a stop or the exit. **Stop the turn.**

| The user says | Do |
|---|---|
| An unambiguous yes ("go", "build it") | Step 2 |
| A yes with a change (another cap, a task held back) | Make it, say so, step 2 |
| A hedge, or anything else | Not a go. Answer, ask again |

No live user: there is no go. Report what is ready and stop.

**2. Start.** `dt build start M<n>`. It refuses on a dirty tree; otherwise it creates and
switches to `build/M<n>`, the branch every worktree starts from and every landing commits to, and
commits the go there as `**Build:**` in `tasks/plan.md`. A refusal is reported as it stands; fix nothing yourself.

**3. Interface first.** The first `dt ready` lists only the interface task(s). After they land,
the interface review runs as a barrier: `dt ready` releases nothing else until it is recorded as
passed. A Critical there is a stop like any other.

**4. Loop** (`loop.md`) until it ends: Exit when every task has landed and the exit review is
recorded, otherwise a stop reported per `escalation.md`.

## Example: gridload M1

```
Ready to build M1 Ingest & clean: 14 tasks, 19 halves (5 split), critical path 4, widest wave 11.
Cap 6 agents at a time. No task needs credentials. From your go it runs on its own until a stop
or the exit review, and the merge waits for you. Build M1?
```

User: "Go." Then:

```
$ dt build start M1
$ dt ready --reserve --cap 6 --json      → M1-T01 solo (implementer)
  spawn 1 agent
  … DONE M1-T01 solo → dt land → landed
$ dt ready --reserve --cap 6 --json      → M1-T01.gridload reviewer (barrier, lead)
  … REVIEW M1-T01 gridload: 2 findings, 0 Critical → dt finding --from …/reviews/M1-T01.gridload.md
$ dt ready --reserve --cap 6 --json      → 6 rows: T05 solo, T02 solo, T11 tester, T12 tester, …
```

Each later turn is one completion and one landing, a few lines each.
# The dispatch loop

Read with Run, Resume and Exit. Stops go to `escalation.md`.

Work is dataflow, not waves: a task half starts the moment what it needs has landed, and `dt`
decides what that is. The driver only spawns what `dt ready` lists and lands what finishes.

## Dispatch

```
python3 ../../scripts/dt.py ready --reserve --cap 6 --json
```

It prints one object: `rows` to spawn, `held` (halves waiting, each with its `why`), `holds`
(why nothing is released: a Critical or an escalation, `escalation.md`) and `all_landed`. Each row
is `{id, role, agent_type, title, kind, pkg, remaining_cp, prompt}`, already reserved and ordered
by remaining critical path. The cap counts reservations and live claims, so asking again
after every completion fills only the free slots. The user may set another cap; keep it for the run.

Spawn every row in **one message**, one Agent call each:

| Agent field | Value |
|---|---|
| `subagent_type` | the row's `agent_type` (`tester`, `implementer`, `reviewer`) |
| `isolation` | `worktree` |
| `run_in_background` | `true` |
| `description` | `<id> <role>` |
| `prompt` | the row's `prompt`, verbatim: one line naming the task, the role and the `dt` path |

Rows with `agent_type` `reviewer` are checkpoint reviews: `dt` lists them once a checkpoint's
tasks have all landed (each package with changes, one marked lead). Spawn them the same way; their
worktrees keep their mutations out of the main checkout.

Before spawning, nothing else: no reading the task, the packet or the plan. The agent runs
`dt claim`, which writes its packet, its edit list and its base in its own worktree.

## Landing

Each completion arrives on its own, as the agent's last message. Act on its status line
(`../SKILL.md`, Status lines), one landing at a time, in completion order:

| Line | Run | Then |
|---|---|---|
| `DONE <task> <role>` or `STOPPED <task> <role>: …` | `dt land <task> --role <role>` | branch on the JSON below |
| `REVIEW <checkpoint> <pkg>: …` | `dt finding --from <reviews>/<checkpoint>.<pkg>.md --checkpoint <checkpoint> --pkg <pkg>`, where `<reviews>` is `$(git rev-parse --git-common-dir)/dt-build/reviews` | a Critical count above 0 → `escalation.md`, Critical. No findings file (the reviewer couldn't write it) → `dt build release <checkpoint>.<pkg> reviewer` and dispatch again; a second time is a stop (`escalation.md`, harness) |
| anything else | `dt land <task> --role <role> --harness` | the half goes back to `dt ready` |

`dt land` prints `{landed, reject, kind, detail_file}`:

| Result | Do |
|---|---|
| `landed: true` | dispatch again |
| `reject` `gate`, `writes`, `conflict`, `integration` | dispatch again: a first rejection comes back as a ready half whose claim prints it to the new agent; a second one blocks the half (`escalation.md`) |
| `reject` `escalated` | `escalation.md`, by `kind` |
| `reject` `harness` | dispatch again; the third in a row on one half blocks it |

Never re-read the agent's message for more, never fix anything yourself, never retry a land by hand.

## Draining and stopping

A stop never interrupts an agent mid-task. While a stop is pending, keep landing the agents still
running and keep dispatching whatever `dt ready` still lists (it holds back what the stop
affects). When nothing is ready and nothing is running:
- **every task landed** and the exit review recorded → Exit (`exit.md`);
- otherwise, report the stop (`escalation.md`) and end the turn.

After a compaction in the same session, run `dt build status`: a claim not yet finished belongs
to a running agent; leave it and wait for its completion. A finished claim nobody landed gets
`dt land` now.

## The task list

Keep one item per running half (`<id> <role>`), ticked when it lands or blocks, so the user sees
the build move without reading the transcript.
# Stops and escalations

Read with every mode that drives the loop. A stop drains, never interrupts: in-flight agents
finish and land, `dt ready` holds back what the stop affects, and the driver reports once nothing
is ready or running (`loop.md`, Draining and stopping). Every user decision is recorded with
`dt build resolve <finding|task> --note "<the user's words>"`; a decision said in chat and not
recorded doesn't exist for a resumed build.

## By condition

| Condition | Arrives as | Do |
|---|---|---|
| A test can't pass, or the build breaks | `reject` `gate` or `integration` a second time on one half | Blocked. Report the task, its dependents held back and the `detail_file` (both outputs). The user decides: a Replan, a bar change through `build-setup` Revise, or a retry (`dt build resolve <task>`) |
| Writes outside the task, or a merge conflict | `reject` `writes` or `conflict` a second time | Blocked, as above. A `conflict` means two tasks claim one path: a plan gap for `build-planning` Replan, whatever the user decides |
| An intent test is wrong | `escalated`, `kind` `TEST-WRONG` | Blocked. Give the user the implementer's one-line reason from `dt build status` and the `detail_file` path; never judge it yourself. On their yes, `dt build resolve <task>` reopens the tester half and a fresh tester rewrites the test, never a fixture or expected value (oracle changes go through `test-planning` and `dt guard`). A no means the test stands: `dt build resolve <task> --test-stands --note "<their words>"` keeps the tests and retries the implementer, whose claim prints the decision |
| The interface can't express what a task needs | `escalated`, `CONTRACT-CHANGE` | `dt ready` holds every half whose task reads the escalated type, and the escalating task's dependents; the rest runs on. After the drain: `architecture-design` Revise, then `build-planning` Replan adds a re-freeze interface task (run by an `implementer` agent, its `Writes:` naming the frozen folders); the user approves both, each committed on the build branch, then the loop resumes |
| A dependency isn't declared | `escalated`, `NEEDS-DEP` | Drain everything in flight. `build-setup` Extend adds it on the build branch (`pyproject.toml`, `uv.lock`) with the user's yes; new worktrees start from the new head |
| High risk or irreversible | a `**Risk:** external` task `dt ready` never lists | At the go or when it is next, ask; on a yes, `dt build resolve <task>` |
| Critical finding | a `REVIEW` line with Critical above 0 | `dt ready` stops releasing. After the drain, show the Critical lines (`dt build status`) and ask: a fix task through `build-planning` Replan, or the user's override, recorded with `dt build resolve <finding>` |
| Harness failure | `reject` `harness` three times in a row on one half | Blocked: report it as a harness problem (permissions, API), not the task's |

Important findings wait for the next user gate (a stop or Exit), where `build-planning` Replan
turns them into fix tasks, committed on the build branch before dispatch. Suggestions and Nits get
one only if the user asks.

## Reporting a stop

One message, then end the turn:

```
Build M1 stopped: nothing else can start until you decide.
Landed 12/19 halves. Running: none.
Blocked: M1-T17 implementer: TEST-WRONG (details: .git/dt-build/escalations/M1-T17.json).
  Held back: M1-T18, M1-T23.
Decide: rewrite the intent test (a fresh tester), or keep it and retry the implementer?
```

The user's answer is recorded first (`dt build resolve`), then the skills it calls for run, each
through its own gate, and the loop resumes with `dt ready`. The go covers one plan version: after a
Replan, `dt ready` holds everything (`go:`) until the user's new go, recorded with
`dt build go --note "<their words>"`. Never resume on a hedge.

## Never

- Edit a test, a fixture, the bar or the contract to get past a stop.
- Re-dispatch a blocked half without a recorded decision.
- Read a gate log, a diff or a findings file to decide for the user: show the `detail_file` path
  and the status lines, and let `dt build status` summarise.
