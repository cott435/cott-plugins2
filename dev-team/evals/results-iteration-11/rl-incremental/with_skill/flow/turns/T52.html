# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`), a routed change (`routed_changes`) or the user's words the spec doesn't honour yet (`requests_open`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Stage | `Stage:` line of each new feature: the stage the idea added, or the one it joins |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

# The spec: template, writing rules, hygiene check

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown
# [Project Name] — Spec

**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [brief.md](brief.md)

## Summary
[2-3 sentences: what is being built. Link to the brief for why — don't repeat it.]

## Users
| User | What they need to do |
|---|---|
| [Primary user] | [...] |

## Scope
**In scope:** [features, by name]
**Out of scope:** [what we're not building — include everything on the brief's Not Doing list, plus anything decided during clarification]

## Features

### [Feature name] (`CODE`)
**Serves:** Goal 1, Goal 3
**Stage:** S2
**Source:** [ideas/<slug>.md](ideas/<slug>.md) *(extend mode only — omit for features from the original brief)*
**Behavior:** [2-4 sentences or a short numbered flow describing what the user experiences.]

**Requirements**
- **CODE-01** [One testable statement of what the system does.]
  - Given [context], when [action], then [observable result].
  - Given [...], when [...], then [...].
- **CODE-02** [...]
  - Given [...], when [...], then [...].

**Edge cases & errors**
- [Situation] → [expected behavior]

## Data requirements
*(Data and ML projects only — omit otherwise.)*
- **DATA-01** [What data the system needs: content, coverage, history, frequency, freshness — not which vendor.]
  - Given [...], when [...], then [...].

## Quality requirements
- **QR-01** [Measurable non-functional requirement: speed, reliability, accessibility, privacy, security, cost, licence.]
  - [How it's checked.]

## Assumptions
- [Assumptions the user confirmed]

## Open questions
- [Unresolved items, each with who can answer it. Omit if none. A question about what an external source really returns is "answered by a probe during architecture".]

## Changelog
| Date | Change | Source | IDs |
|---|---|---|---|
| YYYY-MM-DD | Initial spec | brief.md | all |
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Every feature names one stage.** Its `**Stage:**` line holds only the ID of the roadmap stage that first builds it. `dt lint` fails a feature with no stage, or one naming no stage row.
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence, budget and run-time limits are `QR-` items, each with how it is measured ("data costs ≤ $50 a month"; "the full study runs in ≤ 1 hour", timed on the user's machine), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads it in `docs/requests.md`.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea", "UR-03") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git; which requirement honours which request goes in `docs/requests.md` (`dt request trace`).
- **The user's words win over the brief's.** Where a `spec` request is more specific than the brief or idea file ("circular tank", "one predator"), the requirement says what the request says, or the user approves the change.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **The user's words.** `dt request --open --owner spec` is empty, or each one left is a change you ask the user about.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of torchvision's ResNet-18" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.
# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

1. *Taking turns* (optional first rung): one side trains while the other is frozen, then they swap. The world is still for each learner, so S2's PPO works unchanged.
2. *Simultaneous learners*: both sides learn at once. This is the broken version, kept on purpose: it shows the moving target and the cycling.
3. *Self-play against past versions*: each side saves a copy of itself as a new generation every so often, and trains against a mix of its opponent's current and past generations. This is the fix.

**Judging it.** Each side's reward alone can't show learning, because the opponent improves too. Two fixed bars do: each side is scored against a random and a scripted opponent on the same seeded games. And a cross-play table pits every saved generation of one side against every generation of the other, so later generations beating earlier ones shows real progress rather than circling.

**Time.** The brief's limit of about an hour of training covers the whole self-play run, every generation of both sides, not each generation.

**The core grows again.** The shared core learns to run two learners with their own policies in one game. Snake and the tank keep running as before.

## Alternatives considered
- Evolutionary methods (a population, keep the fittest) — a different lesson from the policy gradients the lab has built up to.
- Simultaneous learners only — shows the problem without the fix.
- Pellets only as a bonus reward — prey can win by hiding forever, so there is no trade-off to learn.
- Several predators — a second multi-agent problem (teamwork) on top of the first.

## What success looks like
- Each side's learning curve beats a random and a scripted opponent on the same seeded games.
- In the cross-play table, later generations beat earlier ones, for both sides.
- Simultaneous learners visibly cycle or stall where self-play does not, or the notes record that they didn't.
- A replay shows prey foraging and dodging while the predator hunts.
- Snake's and the tank's results are unchanged after the core grows.

## What we're betting on
- S2's rays and PPO carry over to both sides with small changes.
- Simultaneous learners show the moving-target failure clearly in a small tank.
- A whole self-play run, over a handful of generations, fits in about an hour on a laptop CPU.

## Not doing
- Evolutionary methods — a different lesson.
- More than one predator — teamwork is a separate problem.
- Learned communication or teaming among prey — the prey share a policy, nothing more.

## Open questions
- Prey competing for the same pellets is an interaction between prey; is that allowed, given S2 kept fish independent?
- What the scripted predator and scripted prey do.
- How many generations are saved, and how a side picks which past opponents to train against.
- Whether the predator also has energy, or only the prey.

102	**Stage:** S1
103	**Behavior:** Every environment offers the same small set of behaviors: start a game from a seed, take one move for each of its acting agents and report what happened to each, say how big an observation is and what moves are allowed, and draw one frame for the replay viewer. The training loop, logging, learning curves and replay viewer use only these behaviors, so a new environment plugs in without changing them, whether its moves are a few choices or continuous controls, and whether it has one agent or several. Growing the core leaves Snake running exactly as before.
104	
105	**Requirements**
106	- **CORE-01** Every environment can start a new game from a given seed and returns the first observation.
107	  - Given any environment and seed 3, when a game is started twice, then both first observations are identical.
108	- **CORE-02** Every environment takes one move for each of its acting agents (Snake: the snake; the tank: each living fish) and reports, for each, its next observation and reward, plus whether the game has ended.
109	  - Given a running Snake game, when a move is taken, then one next observation, one reward and the game-over flag are reported.
110	  - Given a tank game with 3 living fish, when 3 moves are taken, then 3 next observations, 3 rewards and the game-over flag are reported.
111	- **CORE-03** Every environment reports its observation size and its allowed moves: either a number of choices, or a number of continuous controls with each control's limits.
112	  - Given Snake, when asked, then it reports 11 facts and 3 choices.
113	  - Given the tank, when asked, then it reports 25 numbers and 2 controls: turn −15° to +15°, speed 0 to 0.3.
114	- **CORE-04** Every environment draws a frame of its current state for the replay viewer.
115	  - Given a running Snake game, when a frame is requested, then it shows the grid, the snake, the food, the score and the step number.
116	  - Given a running tank game, when a frame is requested, then it shows the tank, the ball, each living fish with its heading, the number of fish left and the step number.
117	- **CORE-05** The training loop trains any agent on any environment that offers CORE-01 to CORE-04, for a set number of games, with a given seed.
118	  - Given a tiny test environment (a 1 × 5 corridor where reaching the right end gives +1), when the training loop runs on it with no changes to the core, then training completes and the agent reaches the right end in ≥ 9 of 10 evaluation games.
119	- **CORE-06** Logging, learning curves and the replay viewer work on any environment that offers CORE-01 to CORE-04.
120	  - Given the tiny test environment, when a run is logged, its learning curve drawn and a game replayed, then each works with no changes to the core.
121	- **CORE-07** The training loop, logging, learning curves and replay viewer work on an environment with continuous controls and several agents at once.
122	  - Given a tiny continuous test environment (2 points on a line from 0 to 5, each pushing itself −1 to +1 per step, +1 for reaching 5), when a policy-gradient agent trains on it with no changes to the core, then training completes, both points reach 5 in ≥ 9 of 10 evaluation games, and the run is logged, drawn and replayed.
123	- **CORE-08** When an environment removes one of its agents mid-game, the training loop stops asking that agent for moves and the game continues for the rest.
124	  - Given the continuous test environment where one point reaches 5 first, when the next step is taken, then only the other point is asked for a move.
125	- **CORE-09** Growing the core leaves Snake's results unchanged.
126	  - Given a 200-game Snake run with seed 1 recorded before the core grew, when it is repeated after, then every logged evaluation score is identical.
127	
128	**Edge cases & errors**
129	- An environment is missing one of the 4 behaviors → the core refuses it at start-up and names the missing behavior.
130	- An agent returns a move outside the environment's allowed choices or limits → the run stops with an error naming the move and the game step.
131	- An agent built for choices is given an environment with continuous controls, or the other way round → refused at start-up, naming both kinds.

133	### Value-learning agent (`AGENT`)
134	**Serves:** Goal 1, Goal 2
135	**Stage:** S1
136	**Behavior:** The agent learns an estimate of each move's long-run value from the 11 facts, using a small learned function. It picks moves by mostly taking the best-valued move and sometimes a random one, with the random share shrinking over training. It learns from random batches of remembered past steps, and builds its targets from a periodically refreshed frozen copy of its value estimate. Every part is written by hand.
137	
138	**Requirements**
139	- **AGENT-01** The agent estimates, for each observation, a value for every allowed move.
140	  - Given an observation of 11 facts, when the agent is asked, then it returns 3 values, one per move.
141	- **AGENT-02** During training the agent takes a random move with a probability that starts at 1.0 and decays to 0.01 over the first half of the training games, and otherwise takes its best-valued move.
142	  - Given training game 0, when the agent picks moves, then every move is random; given a game in the second half, then about 1% of moves are random.
143	- **AGENT-03** During evaluation the agent always takes its best-valued move.
144	  - Given an evaluation game, when the agent picks a move, then it is the move with the highest value, and the same observation always gives the same move.
145	- **AGENT-04** The agent remembers its most recent 100,000 steps and learns from random batches of them.
146	  - Given more than 100,000 steps taken, when the agent learns, then its batches come only from the latest 100,000 steps, drawn at random.
147	- **AGENT-05** The agent's learning targets are the step's reward plus the discounted best value of the next observation (discount 0.9), taken from a frozen copy of its value estimate that is refreshed every 1,000 steps; a game-ending step's target is its reward alone.
148	  - Given a non-final step with reward 0, when its target is built, then it equals 0.9 × the frozen copy's best value for the next observation.
149	  - Given a game-ending step with reward −10, when its target is built, then it is −10.
150	  - Given 1,000 learning steps since the last refresh, when the next one happens, then the frozen copy is replaced by the current estimate.
151	- **AGENT-06** A trained agent can be saved and loaded back, and the loaded agent picks the same moves.
152	  - Given a saved agent, when it is loaded and plays an evaluation game with seed 11, then it makes exactly the same moves as before saving.
153	
154	**Edge cases & errors**
155	- Fewer remembered steps than one batch → the agent keeps playing and does not learn until it has a full batch.
156	- A saved agent is loaded for an environment with a different observation size or move count → loading is refused with an error naming both sizes.
157	- Learning produces a non-number value → the run stops with an error naming the game and step, and the log so far is kept.

159	### Policy-gradient ladder (`PG`)
160	**Serves:** Goal 1, Goal 2
161	**Stage:** S2
162	**Source:** [ideas/fish-tank.md](ideas/fish-tank.md)
163	**Behavior:** Three hand-written agents learn the fish's steering policy directly, each one built on the one before and each fixing a failure of the rung below. Rung 1, plain policy gradient, makes moves that were followed by high returns more likely. Rung 2, actor-critic, also learns a value estimate and credits each move only with how much better it did than expected, which cuts the noise. Rung 3, the limited-update agent, reuses each game's steps several times but caps how far each update can move the policy, so reuse doesn't wreck it. All fish in a game share one policy, each acting on its own observation. Each rung is compared with the rung below it.
164	
165	**Requirements**
166	- **PG-01** Every rung's policy gives, for each observation, a spread of likely moves for each control (a centre and a width), and during training each move is drawn from it.
167	  - Given the same observation twice during training, when moves are drawn, then they can differ, and over 1,000 draws their average is within 0.05 of the policy's centre for each control.
168	- **PG-02** During evaluation every rung takes the centre of its policy for each control.
169	  - Given an evaluation game, when the agent picks a move, then the same observation always gives the same move.
170	- **PG-03** Every move a rung sends lies within the environment's limits, even when the drawn move falls outside them.
171	  - Given a drawn turn of +20°, when it is sent to the tank, then the tank receives +15°.
172	- **PG-04** All fish in a game share one policy: each fish acts on its own observation, and every fish's steps feed the same updates.
173	  - Given a game with 5 fish, when the agent learns from it, then one policy is updated, from the steps of all 5 fish.
174	- **PG-05** Every rung learns once after each training game, from all the steps of all its fish, with discount 0.99.
175	  - Given a training game of 3 fish surviving 40, 70 and 120 steps, when the game ends, then the agent makes one learning update from those 230 fish-steps.
176	- **PG-06** Rung 1, plain policy gradient, makes each move more or less likely in proportion to the discounted return that followed it, up to that fish's end.
177	  - Given a fish whose rewards were +1, +1, 0 before it was removed, when its steps are weighted, then the weights are 1.99, 1 and 0.
178	- **PG-07** Rung 2, actor-critic, learns a value estimate of each observation and weights each move by its advantage: how much better things went than the estimate expected, blending one-step and longer look-aheads with a blend factor of 0.95.
179	  - Given a fish's last step before removal with reward 0 and a value estimate of 2, when its advantage is built, then it is −2.
180	  - Given the value estimate after learning from many games, when it is checked on 100 held-out games, then it predicts the discounted return better than predicting the average return for every step.
181	- **PG-08** Rung 3, the limited-update agent, learns like rung 2 but reuses each game's steps for 10 passes in random batches of 64, and stops rewarding any move whose probability has already moved more than 20% up or down from the policy that played the game.
182	  - Given a move whose probability under the current policy is 1.3 × its probability when played, with a positive advantage, when the next pass updates, then that move gains nothing from becoming more likely.
183	- **PG-09** Rungs 2 and 3 rescale each game's advantages to an average of 0 and a spread of 1 before learning.
184	  - Given a game's advantages, when they are rescaled, then their mean is 0 and their standard deviation is 1, to within 0.001.
185	- **PG-10** Each rung's final evaluation scores are compared with the rung below it with the `null-hypothesis-testing` skill, given 5 training seeds × the same 100 held-out games for each rung; a rung counts as better only if its scores are higher at a 5% significance level after correcting for the 2 comparisons. The report also gives each rung's spread across its 5 seeds.
186	  - Given finished runs of all 3 rungs, when the ladder comparison runs, then the report says, for rung 2 against rung 1 and rung 3 against rung 2, "better" or "no detectable difference", with the test result and each rung's spread.
187	- **PG-11** A rung that is not better than the one below it is recorded as a finding in the notes, and S2 doesn't count as failed.
188	  - Given a ladder report where rung 3 shows "no detectable difference", when the stage is checked, then it passes, and the notes page records it as a finding (EXPL-04).
189	- **PG-12** A trained rung can be saved and loaded back, and the loaded agent picks the same moves.
190	  - Given a saved rung, when it is loaded and plays an evaluation game with seed 11, then it makes exactly the same moves as before saving.
191	
192	**Edge cases & errors**
193	- A game ends by the time limit → returns and advantages for the surviving fish stop at step 1,000; nothing is counted beyond it.
194	- A game where every fish is removed on the first step → the agent learns from those steps alone; it does not stop.
195	- A saved rung is loaded for an environment with a different observation size or controls → loading is refused with an error naming both.
196	- Learning produces a non-number value → the run stops with an error naming the game and step, and the log so far is kept.

198	### Ablation switches (`ABL`)
199	**Serves:** Goal 1
200	**Stage:** S1
201	**Behavior:** Each environment has three switches, each turning off one part of its top agent, so the learner can train the agent without it and compare. On Snake they turn off the value-learning agent's memory, frozen copy and exploration decay; on the tank they turn off the limited-update agent's value estimate, update cap and advantage rescaling. Each switch is set per run and recorded in the run's log. The comparison of each ablated agent with the full agent is judged by a hypothesis test.
202	
203	**Requirements**
204	- **ABL-01** With the memory switch off, the agent learns from only the step it just took, with no remembered steps.
205	  - Given memory off, when the agent learns, then each update uses exactly the latest step.
206	- **ABL-02** With the frozen-copy switch off, the agent builds its targets from its current value estimate.
207	  - Given frozen copy off, when a target is built, then it uses the current estimate's best next value, which changes after every update.
208	- **ABL-03** With the exploration-decay switch off, the agent's random-move probability stays fixed at 0.1 for the whole run.
209	  - Given decay off, when the agent picks moves at any point in training, then about 10% are random.
210	- **ABL-04** Each ablated agent is compared with the full agent of its environment (Snake: the value-learning agent; the tank: the limited-update agent) with the `null-hypothesis-testing` skill, given the final evaluation scores of both (5 training seeds each, on the same 100 held-out games); the ablation counts as hurting learning only if the full agent's scores are higher at a 5% significance level after correcting for the 3 comparisons in that environment.
211	  - Given finished runs of the full agent and the 3 ablated agents of one environment, when the study is run, then each ablation is reported as "hurts learning" or "no detectable difference", with its test result.
212	- **ABL-05** When no switch hurts learning, the study is still complete: the result is recorded as a finding in the notes, and S1 doesn't count as failed (nor S2, for the tank's switches).
213	  - Given a study report where all 3 ablations show "no detectable difference", when the stage is checked, then it passes, and the notes page records that no switch hurt learning as a finding (EXPL-02).
214	- **ABL-06** With the value-estimate switch off, the limited-update agent weights each move by the discounted return that followed it, as rung 1 does, and learns no value estimate.
215	  - Given value estimate off, when a fish's rewards were +1, +1, 0, then its moves are weighted 1.99, 1 and 0 before rescaling.
216	- **ABL-07** With the update-cap switch off, the limited-update agent still makes its 10 passes over each game's steps, with no limit on how far a move's probability can move.
217	  - Given cap off and a move already 1.3 × as likely as when played, with a positive advantage, when the next pass updates, then that move still becomes more likely.
218	- **ABL-08** With the rescaling switch off, the limited-update agent uses each game's advantages as built, without rescaling.
219	  - Given rescaling off, when a game's advantages are used, then they equal the advantages as built.
220	
221	**Edge cases & errors**
222	- Several switches are off in one run → allowed; the run's log records every switch's state.
223	- An ablated run fails before finishing → the study reports that ablation as missing, never as "no detectable difference".
224	- A switch is set on an agent that doesn't have that part (the tank's switches on rungs 1 or 2's missing pieces, Snake's switches on a tank rung) → the run is refused at start-up, naming the switch and the agent.

226	### Baselines (`BASE`)
227	**Serves:** Goal 2
228	**Stage:** S1
229	**Behavior:** Two non-learning agents play the same seeded games as the learning agents in each environment: a random agent and a simple scripted agent. Their scores set the bars every learning agent's curve must clear.
230	
231	**Requirements**
232	- **BASE-01** The random agent picks each move uniformly at random from the allowed moves: one of the choices, or each control anywhere within its limits.
233	  - Given 10,000 moves by the random agent on Snake, when counted, then each of the 3 moves is picked 30–37% of the time.
234	  - Given 10,000 moves by the random agent in the tank, when counted, then turns are spread evenly over −15° to +15° and speeds over 0 to 0.3, each tenth of either range holding 9–11% of moves.
235	- **BASE-02** On Snake, the scripted agent moves toward the food along the axis with the larger gap, and when that move is immediately fatal it takes any non-fatal move, preferring straight.
236	  - Given food straight ahead and no danger ahead, when the scripted agent moves, then it goes straight.
237	  - Given food straight ahead and a wall ahead, when it moves, then it turns to a side that is free.
238	- **BASE-03** Both baselines are scored on the same 100 held-out games as the learning agent.
239	  - Given the 100 held-out seeds, when each baseline plays them, then each records one score per seed, and its mean and spread are logged.
240	- **BASE-04** In the tank, the scripted fish swims at full speed, turning as far as it can away from the ray that sees the ball closest; with no ball in reach it swims straight, and when the wall is within 1 unit straight ahead it turns as far as it can toward the side whose rays see more room.
241	  - Given the ball seen only on the front-left ray and no wall within 1 unit ahead, when the scripted fish moves, then it turns −15° (to the right) at speed 0.3.
242	  - Given no ball in reach and the wall 0.5 units straight ahead with more room on the left, when it moves, then it turns +15° at speed 0.3.
243	
244	**Edge cases & errors**
245	- Every move is fatal → the scripted agent goes straight and the game ends.
246	- The scripted fish sees the ball equally close on two rays → it turns away from the one further left.
247	- The scripted fish sees the ball and the wall ahead at once → it avoids the wall.

249	### Evaluation (`EVAL`)
250	**Serves:** Goal 2
251	**Stage:** S1
252	**Behavior:** Every training run is checked at regular points on a fixed set of held-out games it never trains on, with exploration off, and ends with a final check on all 100 held-out games. Each learning agent's final check is compared with both baselines of its environment on those same games.
253	
254	**Requirements**
255	- **EVAL-01** Training games and evaluation games come from separate seed sets that never overlap.
256	  - Given any training run, when its training and evaluation seeds are listed, then no seed appears in both.
257	- **EVAL-02** During training the agent plays held-out games at regular points with exploration off and its mean score is logged: on Snake every 50 training games over all 100 held-out games; in the tank at every tenth of training over the same 20 of its 100 held-out games. Every run ends with a final check over all 100.
258	  - Given a Snake run of 1,000 training games, when it ends, then 20 evaluation results are logged, each over the same 100 seeds.
259	  - Given a tank run, when it ends, then 10 evaluation results over the same 20 seeds and one final result over all 100 seeds are logged.
260	- **EVAL-03** Each learning agent's final evaluation scores are compared with each baseline's scores of its environment with the `null-hypothesis-testing` skill, given 5 training seeds × the 100 held-out games for the agent and the same 100 games for each baseline; the agent beats a baseline only if its scores are higher at a 5% significance level after correcting for every comparison in that environment (2 on Snake: the full agent against 2 baselines; 6 in the tank: 3 rungs against 2 baselines).
261	  - Given finished runs of the full agent and both baselines, when the comparison is run, then the report says, for the random agent and for the scripted agent, whether the agent beats it, with the test result.
262	  - Given finished runs of all 3 rungs and both tank baselines, when the comparison is run, then the report says, for each of the 6 pairs, whether the rung beats the baseline, with the test result.
263	- **EVAL-04** On Snake the full agent's learning curve beats both the random baseline and the scripted baseline; in the tank every rung's learning curve beats both the random fish and the scripted fish.
264	  - Given the EVAL-03 report for Snake, when it is read, then the agent beats both baselines.
265	  - Given the EVAL-03 report for the tank, when it is read, then each of the 3 rungs beats both baselines.
266	
267	**Edge cases & errors**
268	- A run stops early → its completed evaluation points are kept and shown; it is left out of the final comparison, which names it as incomplete.

271	**Serves:** Goal 2, Goal 4
272	**Stage:** S1
273	**Behavior:** Every run, whether training or baseline, keeps a record of its settings and results, so curves can be redrawn and agents replayed without training again.
274	
275	**Requirements**
276	- **LOG-01** Each run records its environment, agent, every setting including the ablation switches, and its seed.
277	  - Given a finished run, when its record is opened, then the environment, the agent, every setting and the seed are listed.
278	- **LOG-02** Each run records the score and length of every training game.
279	  - Given a run of 1,000 games, when its record is read, then it holds 1,000 scores and game lengths.
280	- **LOG-03** Each run records every evaluation result and the training loss every 50 games.
281	  - Given a finished run, when its record is read, then each evaluation point has its mean score and spread, and each 50-game point has its average loss.
282	- **LOG-04** Each training run saves its final trained agent next to its record.
283	  - Given a finished training run, when its record is opened, then the saved agent can be loaded (AGENT-06).
284	- **LOG-05** A run's record is kept on disk while the run is in progress, at least after every evaluation point.
285	  - Given a run stopped at game 430, when its record is opened, then results up to game 400 are present.
286	
287	**Edge cases & errors**
288	- Starting a run with the same name as an existing one → refused, naming the existing run; nothing is overwritten.

290	### Learning curves (`CURVE`)
291	**Serves:** Goal 2, Goal 1
292	**Stage:** S1
293	**Behavior:** From saved run records, the learner draws learning curves: evaluation score against training games, with the environment's baselines as flat reference lines. Curves for several runs can share one chart, so the full agent and its ablations, or the three rungs of the ladder, can be compared at a glance.
294	
295	**Requirements**
296	- **CURVE-01** A learning curve shows the mean evaluation score against training games for one or more runs.
297	  - Given one run's record, when its curve is drawn, then the chart shows one line of mean evaluation score at each evaluation point.
298	- **CURVE-02** Runs of the same agent and settings with different seeds are drawn as one line of their mean, with a band showing their spread.
299	  - Given 5 seeds of the full agent, when drawn, then the chart shows one mean line and one band.
300	- **CURVE-03** The random and scripted baselines' mean scores of the chart's environment appear on every chart as labelled flat lines.
301	  - Given any Snake chart, when drawn, then two labelled flat lines show the random and scripted baselines' mean scores.
302	  - Given any tank chart, when drawn, then two labelled flat lines show the random and scripted fish's mean scores.
303	- **CURVE-04** The full agent and each ablated agent can be drawn together on one chart, each labelled by its switches.
304	  - Given the full agent and 3 ablation runs, when drawn together, then 4 labelled lines appear.
305	- **CURVE-05** Curves are drawn from saved records only, never by training again.
306	  - Given saved records and no training running, when a chart is drawn, then it appears in ≤ 10 seconds.
307	- **CURVE-06** The 3 rungs of the ladder can be drawn together on one chart, each labelled by its rung.
308	  - Given 5 seeds of each rung, when drawn together, then 3 labelled mean lines with bands appear.
309	
310	**Edge cases & errors**
311	- A record has no evaluation points yet → it is skipped with a note naming it; the other curves are drawn.
312	- Records from different environments are drawn together → refused, naming the environments.

314	### Replay viewer (`REPLAY`)
315	**Serves:** Goal 3
316	**Stage:** S1
317	**Behavior:** The learner picks any saved agent, or a baseline, and a seed, and watches it play that game frame by frame in a simple view of the environment, with pause, single-step and speed controls.
318	
319	**Requirements**
320	- **REPLAY-01** The learner can watch any saved trained agent, the random agent or the scripted agent play a game from a chosen seed.
321	  - Given a saved agent and seed 42, when a replay is requested, then the agent's game on seed 42 is shown from the first frame to game over.
322	- **REPLAY-02** Each frame shows the environment's drawing (CORE-04) plus the step number and score.
323	  - Given a Snake replay, when any frame is shown, then the grid, snake, food, step number and score are visible.
324	  - Given a tank replay, when any frame is shown, then the tank, the ball, each living fish with its heading, the number of fish left and the step number are visible.
325	- **REPLAY-03** The learner can pause, step one frame forward and change the playback speed between 1 and 30 frames per second.
326	  - Given a playing replay, when paused and stepped, then exactly one frame advances; when the speed is set to 30, then 30 frames show per second.
327	- **REPLAY-04** Replaying the same agent on the same seed shows the identical game every time.
328	  - Given a saved agent and seed 42, when replayed twice, then every frame and the final score match.
329	- **REPLAY-05** The final score of a replayed game matches that game's score in the agent's evaluation.
330	  - Given a held-out seed scored in evaluation, when it is replayed with the same saved agent, then the replay's final score equals the logged score.

332	**Edge cases & errors**
333	- The saved agent doesn't exist or can't be loaded → an error names it; no window opens.
334	- The game never ends → it ends by the environment's limit (SNAKE-05, TANK-06), so every replay has a last frame.

## 3. Assumptions I'm making (correct any of these now, or I'll go ahead with them)

1. **Tank and prey:** the tank is S2's (radius 10). Prey are S2's fish (radius 0.3, turn ±15°, speed 0–0.3), 5 by default. The game ends when every prey is gone, or after 1,000 steps.
2. **Predator:** one predator, radius 0.5, turn ±10°, speed 0–0.35. That makes it faster but less agile than prey. It catches a prey when their centres are < 0.8 apart. **The predator has no energy.**
3. **Prey energy:** each prey starts at 1.0 and loses 0.002 per step, so it starves after 500 steps without eating. A pellet restores +0.3, capped at 1.0. A prey at 0 is removed.
4. **Pellets:** 10 pellets (radius 0.2) are always present. An eaten pellet reappears at a random spot. If two prey reach the same pellet on the same step, the closer one eats it.
5. **Prey senses:** each prey has 8 rays of reach 4 reporting wall, predator, nearest other prey and nearest pellet, plus its own speed and energy: **34 numbers**.
6. **Predator senses:** the predator has 8 rays of reach 4 reporting wall and nearest prey, plus its own speed: **17 numbers**.
7. **Rewards and scores:**
   - Prey earn +1 per step alive and 0 on the step they're removed. The prey score is the average number of steps survived.
   - The predator earns +1 per catch. Its score is prey caught per game (0–5).
8. **Scripted baselines:**
   - **Scripted predator:** full speed, turning hardest toward the ray that sees the nearest prey. With no prey in sight it swims straight and avoids the wall the way the scripted fish does.
   - **Scripted prey:** flees the predator the way BASE-04 does. With no predator in sight it turns toward the nearest pellet it can see, and otherwise swims straight with wall avoidance.
   - **Random baselines:** uniform over each side's limits.
9. **Taking turns (optional rung, like TWIN):** training is split into 10 equal blocks, alternating sides, prey first. A generation is saved at every switch.
10. **Replay:** you pick any saved predator generation or baseline, and any prey generation or baseline. Frames show the tank, the predator, each prey with its heading and energy, the pellets, the number of prey left and the step number.

## 4. Questions

**Q1. What does "each side beats random and scripted opponents" (UR-76) measure?**
- **(A), recommended.** This mirrors Goal 2. The learned predator plays the scripted prey on the 100 held-out games and must catch more than the random predator and the scripted predator do against that same prey. The learned prey is judged the same way against the scripted predator. That's 4 comparisons for self-play, tested with the `null-hypothesis-testing` skill at 5% after correction.
- **(B)** A head-to-head win rate: for example, the learned predator catches ≥ 3 of the 5 prey against random prey and against scripted prey. That needs win thresholds I'd have to invent.

**Q2. Should the bar and the ablations work like this?**
- Only the self-play rung must pass the bar: each side beats both baselines, and later generations beat earlier ones.
- Taking turns and simultaneous learning are scored and shown but not required to pass. A stalled simultaneous rung is the expected finding.
- S3 has no ablation switches. OK?

**Q3. Are these self-play numbers right?**
- **Generations:** each side saves **10 generations** per run, one at every tenth of training.
- **Opponent mix:**
  - 50% of training games are current against current, with both sides learning.
  - 25% are the current predator against a past prey generation, where only the predator learns.
  - 25% are a past predator generation against the current prey, where only the prey learns.
  - Each past generation is drawn uniformly.

**Q4. How should the cross-play table and the study work?**
- **Table:** every predator generation plays every prey generation on the same **20 held-out games**, so the table is 10 × 10.
- **"Later beats earlier":** a side's last generation scores higher than its first, against the same opponent generations and games, tested at 5%.
- **Study:**
  - The full study (3 rungs × 5 seeds, baselines and tables) finishes unattended in **≤ 16 hours**.
  - Without the optional taking-turns rung, it finishes in ≤ 11 hours.
