# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Quote the words and the traced text side by side, so the user sees whether one does the other.

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted.   - Given the several-fish version, when the scripted fish observes, then a ball beyond 0.5 is hidden from it as in TANK-07.

**Edge cases & errors**
- The scripted snake has no safe move → it goes straight.
- The scripted fish has no ball in view (several-fish version) → it stays still.

### Evaluation (`EVAL`)
**Serves:** Goal 2
**Stage:** S1
**Behavior:** Each trained agent and each baseline plays the same fixed set of evaluation episodes it never trained on. Its scores are compared statistically, and the learning curve is drawn against the baselines.

**Requirements**
- **EVAL-01** Each agent is evaluated on 100 episodes, every agent in a world on the same 100 seeds.

- **EVAL-02** The learning curve is drawn with the `dataviz` skill: score against training progress, with the random and scripted agents' mean scores as reference lines.
  - Given a finished training run and its baselines' evaluations, when the chart is drawn, then it shows the curve and both reference lines on one axis.
- **EVAL-03** "Beats a baseline" is tested with the `null-hypothesis-testing` skill on the 100 evaluation scores of each; it passes only if the trained agent's mean is higher, significant at 5% after correction for the number of comparisons made in that world.
  - Given the trained and random agents' 100 scores each, when tested, then the result states the test, the corrected p-value and pass or fail.
- **EVAL-04** The trained snake beats both the random and the scripted snake under EVAL-03.
  - Given the Snake evaluations, when tested, then both comparisons pass.
- **EVAL-05** In each fish version, the trained fish beats the random fish under EVAL-03.
  - Given the single-fish evaluations, when tested, then the comparison with the random fish passes; the same for the several-fish version.
- **EVAL-06** In each fish version, the trained fish at least matches the scripted fish: tested with the `null-hypothesis-testing` skill, it passes only if the trained fish's mean survival is shown, at 5%, to be no worse than 95% of the scripted fish's.
  - Given the trained fish's mean is 480 steps and the scripted fish's 490, when tested, then it passes if the test rejects "trained mean ≤ 0.95 × 490".
- **EVAL-07** In predator and prey, each trained side is compared under EVAL-03 with the random and scripted versions of that side, all playing against the scripted opponent.
  - Given a trained predator, when evaluated against the scripted prey, then its catches are tested against the random and scripted predators' catches against the same scripted prey.

**Edge cases & errors**
- Every score of two agents is identical (e.g. all 1,000) → the comparison is reported as "no difference", not a pass.
- A baseline outscores the trained agent → the result is reported as a fail; the environment is not signed off (except predator and prey, see DONE-03).

### Replay (`REPLAY`)
**Serves:** Goal 3
**Stage:** S1
**Behavior:** Any saved agent, trained or baseline, can be watched playing an episode of its world as a 2D animation, including the mistakes it makes.

**Requirements**
- **REPLAY-01** The replay plays any saved agent on a chosen seed as a 2D animation of the world.
  - Given a saved trained snake and seed 42, when the replay is started, then the episode plays from its first step to its last.
- **REPLAY-02** The replay shows the step number and the current score.
  - Given a replay at step 150, when it is on screen, then "step 150" and the score so far are visible.
- **REPLAY-03** The replay can be paused, stepped one frame at a time, and run at speeds from 0.5× to 4×.
  - Given a paused replay, when "step" is pressed, then exactly one world step advances.
- **REPLAY-04** For agents that see only what is nearby, the replay draws each agent's sight circle.
  - Given the several-fish version, when replayed, then each fish has a 0.5-radius circle drawn around it.
- **REPLAY-05** A recorded episode can be watched again later exactly as it happened, without the agent or retraining.
  - Given a recorded episode, when reopened in a new session, then every frame matches the original.

**Edge cases & errors**
- The saved agent belongs to a different world than requested → the replay refuses with a message naming both worlds.
- A fish or prey goes out mid-episode → it is shown as out (greyed) for the rest of the replay.

### Notes (`NOTE`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** Each world has a short note, written by the learner, explaining why its method works, with the evidence beside it.

**Requirements**
- **NOTE-01** Each world has one note of 1,000 words or fewer explaining why its learning method works.
  - Given a finished world, when its note is opened, then it explains the method's idea in ≤ 1,000 words.
- **NOTE-02** The note includes the learning curve chart and the evaluation results.
  - Given the Snake note, when read, then it shows the EVAL-02 chart and the EVAL-04 results.
- **NOTE-03** The note describes at least one behaviour seen in a replay, including a wrong or surprising one if seen.
  - Given the fish note, when read, then it names a behaviour and the seed of the replay where it shows.
- **NOTE-04** The note states the reference check result and explains any gap.
  - Given the reference check result, when the note is read, then it states both scores and a reason for any difference.

**Edge cases & errors**
- A note is missing a required part → the world is not signed off (DONE-01).

### Reference check (`CHECK`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** After a world's hand-written learner passes, an established reference implementation of the same kind of method is trained on the same world under the same limits, and the two are compared.

**Requirements**
- **CHECK-01** The reference implementation is trained on the same world, with the same observations, actions, rewards and time limit as the hand-written learner.
  - Given the Snake check, when the reference trains, then it plays SNAKE-01..07's rules and stops within QR-01's limit.
- **CHECK-02** The reference is evaluated on the same 100 seeds as EVAL-01.
  - Given the reference agent, when evaluated, then its 100 scores use the seeds of the hand-written agent's evaluation.
- **CHECK-03** The hand-written learner lands in the reference's range: tested with the `null-hypothesis-testing` skill, it passes only if its mean score is shown, at 5%, to be no worse than 80% of the reference's.
  - Given hand-written mean 18 and reference mean 20, when tested, then it passes if the test rejects "hand-written mean ≤ 0.8 × 20".

**Edge cases & errors**
- The hand-written learner beats the reference by a wide margin → still a pass; the note says why.
- The reference can't finish within the time limit → it is compared at whatever it reached at the limit, and the note says so.

### Co-evolution comparison (`COEVO`)
**Serves:** Goal 4, Goal 1
**Stage:** S3
**Behavior:** Predator and prey are trained two ways, each within the same time limit: both sides learning at once against each other's current version, and each side learning against past versions of its opponent (self-play). The two are compared side by side, and the result is explained whatever it is.

**Requirements**
- **COEVO-01** In the simultaneous regime, both sides learn at once, each always facing the other's current version.

- **COEVO-02** In the past-versions regime, a snapshot of each side is saved at least every 10% of the run, and each side trains against opponents drawn from all the other side's snapshots so far.
  - Given a past-versions run at 50% progress, when the predator plays a training episode, then its prey come from one of the prey's 5 or more saved snapshots.
- **COEVO-03** Both regimes are compared side by side: every regime's final predator plays every regime's final prey for 100 evaluation episodes.
  - Given both finished regimes, when compared, then a 2 × 2 table of predator and prey scores is produced.
- **COEVO-04** Both regimes' learning curves are drawn on one chart with the `dataviz` skill, predator and prey shown separately.
  - Given both finished regimes, when the chart is drawn, then it shows four curves: each regime's predator and prey.
- **COEVO-05** Each final agent plays the opponent's saved snapshots in order, showing whether later versions do better against it than earlier ones.

## Data
- **Worlds are generated, not downloaded.** Every episode is set by one integer seed (AD-10).
- **Seeds (DATA-01):** per world, evaluation seeds are 0–99, learning-curve seeds 100–119, training seeds 1,000,000 and up; `core.seeds` is the only source, and `learners` refuses a training seed below 1,000,000.
- **Observations** are float32 arrays per role, shape (agents, features): Snake per AD-04, fish and predator-prey per AD-06. Rewards per AD-07.
- **Run folder** `runs/<world>/<run-id>/` (AD-11): `record.json` (seed, settings, duration, curves, status: DATA-02), `policy.pt` only for a finished run (LEARN-03), `scores/<agent>.json`, `comparisons.json`, `curve.png`, `recordings/<agent>-<seed>.json.gz`. Notes live in `notes/<world>.md`, committed; `runs/` is git-ignored.

## Cross-cutting concerns
- **Speed (QR-01):** training steps 16 world copies and makes one batched policy call per step; the loop stops at `time_limit_s` (3,600 by default) and records the duration. Small MLPs run on CPU (AD-09).
- **Reproducibility (QR-03):** one `np.random.Generator` and one `torch.Generator` per run from the run seed, no global random state; `torch.use_deterministic_algorithms(True)` and a fixed thread count in the settings.
- **Errors:** a not-a-number loss or score stops the run with status `diverged` and the curve point where it happened; an interrupted run keeps its curve with status `stopped` and no `policy.pt`. A policy loaded into the wrong world raises `WorldMismatch` naming both worlds.
- **Skills:** `evaluate` runs every significance claim as the `null-hypothesis-testing` skill specifies and draws every chart as the `dataviz` skill specifies (AD-14).
- **Testing:** world rules are tested on hand-placed states (each spec Given/When/Then is a test); learners on tiny worlds for "loss falls"; the reference adapter with SB3's `check_env`.

## Decisions
### AD-01: One Python 3.12 package, `rllab`
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** A one-person learning lab on one laptop, with no separate install, deployment or owner (brief: Not doing, a framework). PyTorch, SB3 and pygame-ce all ship 3.12 wheels for Apple Silicon.
- **Decision:** One package `rllab` with one folder per component. The `reference` component is the seam that carries Stable-Baselines3; it is the only importer of `stable_baselines3` and `gymnasium`, so it could move out if that stack ever gets in the way.
- **Alternatives:** A package per world — no real boundary; the worlds share every protocol. Python 3.13 — wheel coverage lags for some of the stack.
- **Consequences:** `requires-python = ">=3.12,<3.13"`. The import rule (only `reference` imports SB3) is checked by import-linter.

### AD-02: Learners written by hand on PyTorch autograd; worlds in NumPy
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-15: the user wants every method "From scratch in NumPy/PyTorch". LEARN-01 allows array operations and automatic gradients, but no ready-made RL algorithm in training.
- **Decision:** Networks are `torch.nn` layers trained with `torch.optim` and autograd; every RL piece (replay buffer, targets, advantage estimation, clipped loss, exploration) is our own code in `learners` and `coevo`. Worlds are plain NumPy. No module outside `reference` imports an RL library.
- **Alternatives:** NumPy only — writing backward passes by hand becomes the project, not the RL. JAX — less CPU tooling, and the user named PyTorch.
- **Consequences:** Optimizers like Adam are library code; the note may say so. Worlds return NumPy and learners convert at the boundary.

### AD-03: Double DQN for Snake
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** learners
- **Context:** UR-05: Snake is the "Good first env for DQN-style value learning." LEARN-04 needs the value of each of SNAKE-03's three moves learned from reward.
- **Decision:** DQN with a replay buffer, a target network synced every few thousand steps, the double-DQN target, epsilon-greedy exploration decaying over the first part of the run, and an MLP from the AD-04 observation to three move values. Evaluation plays greedily.
- **Alternatives:** Tabular Q-learning — the state space of a 10 × 10 snake is too large. Plain DQN without double targets — overestimates values; adding it is a few lines and a note topic.
- **Consequences:** The reference check compares against SB3's DQN, which also supports only discrete actions (AD-08).

### AD-04: Snake sees the whole grid plus a few direct features
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** The spec rules out pixels but leaves the observation open. EVAL-04 requires beating the scripted snake (BASE-02), which already uses "food direction plus next-step danger"; an agent seeing only those 11 classic features has no more information than the script.
- **Decision:** A 311-value vector: three 10 × 10 planes (head, body cells weighted by how soon they clear, food), the heading one-hot (4), the next-step danger for each move (3) and the food's direction relative to the head (4).
- **Alternatives:** The 11 classic features — fast, but caps the agent near the script. A small CNN over the planes — more to write and slower on CPU; revisit if the MLP falls short.
- **Consequences:** The agent can learn to avoid trapping itself, which the script can't. The MLP's first layer is larger; still CPU-cheap.

### AD-05: PPO with a squashed Gaussian movement action, shared within a role
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** learners
- **Context:** UR-11: the fish tank is "Good for policy-gradient / PPO and continuous control." LEARN-05 needs continuous heading and speed (TANK-03, PREY-04). TANK-06 and PREY-01 have several agents of a role at once.
- **Decision:** Clipped-objective PPO with generalised advantage estimation and separate actor and critic MLPs. The actor outputs a Gaussian over a 2D vector, squashed by tanh; the world reads its angle as heading and its length (capped at 1) times the role's top speed as speed. All fish, and all prey, share one policy, each acting on its own observation; the predator has its own.
- **Alternatives:** A Gaussian on (angle, speed) — the angle wraps at ±180°, which a Gaussian handles badly. Separate policies per fish — 5× the data for no gain; fish are interchangeable. REINFORCE — simpler, but much noisier; it is the note's comparison point, not the method.
- **Consequences:** The same PPO serves S2 and S3 (AD-13). Critic inputs are the acting agent's own observation, so the several-fish version is independent learners sharing parameters.

### AD-06: Nearby things fill fixed slots with a presence flag
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** TANK-07 and PREY-05 hide anything beyond 0.5; TANK-05's single fish sees everything. An MLP needs a fixed input size.
- **Decision:** Each observation starts with the agent's own position, velocity and distance to the wall, then fixed slots per kind of thing, nearest first, each holding relative position, relative velocity and a present flag; an empty slot is all zeros. Slots: single fish — 1 ball, always present; several fish — 1 ball, 4 other fish; prey — 1 predator, 4 other prey, 3 pellets; predator — 5 prey, 3 pellets. `worlds.decode` names the fields so scripted agents read the same array (BASE-06).
- **Alternatives:** Attention over a variable-length list — more expressive, more to build and explain. A coarse sensor ring (distances in N directions) — loses velocities.
- **Consequences:** Pellets beyond the 3 nearest in sight are dropped; recorded as an assumption.

### AD-07: Rewards follow each world's score
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** CHECK-01 needs the same rewards for both learners, so rewards belong to the world, not the learner. Scores are SNAKE-07, TANK-09 and PREY-07.
- **Decision:** Snake: +1 per food, −1 on death, 0 otherwise. Fish: +0.01 per step alive, −1 when the ball touches it. Prey: +1 per pellet, −1 when caught. Predator: +1 per catch.
- **Alternatives:** Shaping (distance to food or ball) — faster learning, but teaches the shaping and muddies the note.
- **Consequences:** Sparse Snake rewards may slow early learning; the risk below covers it.

### AD-08: Stable-Baselines3 is the reference
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** reference
- **Context:** CHECK-01–CHECK-03 need an established implementation of the same kind of method on the same world. SB3's DQN supports Discrete actions only and PPO supports Discrete and Box ("Can I use?" tables, https://stable-baselines3.readthedocs.io/en/master/modules/dqn.html and https://stable-baselines3.readthedocs.io/en/master/modules/ppo.html, read 2026-10-18). A custom environment subclasses `gymnasium.Env` with `reset(seed, options) → (obs, info)` and `step → (obs, reward, terminated, truncated, info)`, checked by `check_env` (https://stable-baselines3.readthedocs.io/en/master/guide/custom_env.html, read 2026-10-18). A custom `VecEnv` implements `reset`, `step_async`, `step_wait` and five attribute methods, and must put `terminal_observation` in the info dicts (https://stable-baselines3.readthedocs.io/en/master/guide/vec_envs.html, read 2026-10-18).
- **Decision:** `reference` wraps a world as a `gymnasium.Env` for single-agent worlds (Snake: SB3 DQN; single fish: SB3 PPO with a Box action) and as a custom `VecEnv` with one slot per fish for the several-fish version, so SB3's PPO shares one policy across the fish as AD-05 does. Same observations, rewards, seeds and time limit, stopped by a wall-clock callback. The trained SB3 model is wrapped as a `Policy`. Predator and prey has no reference check (DONE-03 doesn't require one).
- **Alternatives:** CleanRL — single-file scripts to copy, not a library to call. RLlib — handles multi-agent natively but is heavy for a laptop and a bigger stack.
- **Consequences:** SB3 and Gymnasium enter the dependencies, only for `reference`. The multi-fish `VecEnv` resets the whole world when the last fish is out; a fish that is out sends zero reward until then.
- **Probe:** none — the cited pages settle the action spaces and both environment interfaces; nothing depends on the user's accounts or a paid plan.

### AD-09: CPU training, a rented GPU only as fallback
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-20: "MacBook Pro, Apple Silicon, CPU only." UR-21: "I can rent a cloud GPU for a few dollars if needed." QR-01: ≤ 60 minutes per run; QR-02: a GPU only when a run can't meet QR-01, ≤ $5 per world.
- **Decision:** Every run trains on the CPU (`device="cpu"`, Apple's MPS unused), stepping 16 world copies with one batched policy call. `device` is a training setting, so a run that misses QR-01 can rerun unchanged on a rented CUDA machine; the bill is recorded in the run's settings.
- **Alternatives:** MPS on Apple Silicon — the user said CPU only, and small MLPs gain little from it. GPU-first — costs money for networks this small.
- **Consequences:** Worlds must step fast in NumPy; per-step Python overhead is the budget to watch. Reproducibility holds per machine (QR-03), not across CPU and GPU.

### AD-10: Fixed seed ranges keep evaluation seeds out of training
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** DATA-01 forbids training on evaluation seeds; EVAL-01 and CHECK-02 reuse the same 100; LEARN-02's curve needs scores during training.
- **Decision:** Per world: evaluation seeds 0–99, curve seeds 100–119, training seeds from 1,000,000 up, spawned from the run seed. `core.seeds` is the one source; the training loop rejects any episode seed below 1,000,000.
- **Alternatives:** Random evaluation seeds stored per world — needs a file to agree on; a range is checkable by reading it.
- **Consequences:** Curve points use curve seeds, so the curve never peeks at evaluation.

### AD-11: Plain files per run
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** store
- **Context:** DATA-02 needs seed, settings and duration per run; LEARN-03 a reloadable agent; REPLAY-05 recordings that outlive the agent; one user, a few dozen runs.
- **Decision:** `runs/<world>/<run-id>/` with JSON records and results, `policy.pt` holding the state dict plus world, role and architecture, and gzip JSON recordings. Run ids are UTC timestamps plus the method.
- **Alternatives:** MLflow or Weights & Biases — tracking servers for a one-person lab. SQLite — harder to read by eye.
- **Consequences:** Listing and comparing runs is a glob. Nothing is shared or backed up beyond the laptop.

### AD-12: Replays are recorded frames played in a pygame window
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** replay
- **Context:** REPLAY-05 needs a replay without the agent; REPLAY-03 needs pause, single-step and 0.5×–4×; QR-04 ≥ 30 frames per second; the brief rules out a polished app.
- **Decision:** `replay.record` plays a policy once and stores every `core.Frame`; `replay.view` draws frames in a pygame-ce window: space pauses, → steps one frame, ↑/↓ change speed through 0.5×, 1×, 2×, 4×. Out agents are grey; sight circles are drawn when the world has them.
- **Alternatives:** Matplotlib animation — fine for export but sluggish for interactive stepping. A browser viewer — a web interface the brief rules out.
- **Consequences:** Replays need a display; a headless run can still record. Exporting to video is not built.

### AD-13: Two co-evolution regimes on the same PPO
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** coevo
- **Context:** COEVO-01 (both learn at once against the current opponent) and COEVO-02 (snapshots at least every 10%, opponents drawn from all past snapshots); QR-01 gives each regime up to an hour.
- **Decision:** Both regimes use AD-05's PPO for both sides. Simultaneous: each iteration collects rollouts of current against current and updates both. Past-versions: a snapshot of each side every 5% of the time budget; each training episode draws the opponent uniformly from the other side's snapshots so far, and the two sides alternate updates. Snapshots are saved, so COEVO-05's sweep replays them.
- **Alternatives:** Training against the latest snapshot only — that is the simultaneous regime with lag, not past versions. Prioritised opponent sampling — a tuning knob the brief keeps out.
- **Consequences:** 20 snapshots per side per run in the store. Cycling or collapse is reported, not rerun (spec edge cases).

### AD-14: Statistics and charts follow the installed skills
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** evaluate
- **Context:** EVAL-03, EVAL-06, CHECK-03 and COEVO-06 name the `null-hypothesis-testing` skill; EVAL-02 and COEVO-04 name `dataviz`. Corrections are for the comparisons in one world.
- **Decision:** Every module that makes a significance claim calls `evaluate.compare`, which runs the test the `null-hypothesis-testing` skill specifies for superiority or a ratio margin, and corrects across one family per world (or per fish version). Every chart goes through `evaluate`'s chart functions, built as the `dataviz` skill specifies.
- **Alternatives:** A t-test chosen here — that replaces the skill's procedure.
- **Consequences:** The family for a world is fixed before its comparisons run; adding a comparison later reruns the correction.

## Risks and open questions
- Beating the scripted snake (EVAL-04) may be hard within an hour; the script is strong on a 10 × 10 grid. Mitigation: AD-04's full-grid observation; the fallback is a small CNN, then a longer run on a rented machine within QR-02.
- Sparse rewards (AD-07) may slow early Snake and predator learning. If the curve is flat after 20% of the budget, the learner chooses between shaping and more steps, and the note records it.
- Python per-step overhead could break QR-01 for 1,000-step fish episodes; a speed test on the tank world comes early in S2.
- Reference check for the several-fish version depends on our `VecEnv` adapter (AD-08); `check_env` covers single-agent worlds only, so the adapter gets its own tests.
- Assumption: AD-06 keeps the 3 nearest visible pellets, and the predator sees up to 5 prey slots.

**Assumptions**
- The package is named `rllab`. The world names are `snake`, `tank1` (one fish), `tank5` (five fish) and `prey`.
- Seeds: 0–99 for evaluation, 100–119 for learning-curve points, and 1,000,000 and up for training.
- Each run uses 16 copies of the world, 4 CPU threads, and deterministic PyTorch settings.
- With limited sight, each agent tracks a fixed number of nearby things: the 3 nearest pellets, the 4 nearest other fish or prey, and up to 5 prey for the predator. Anything further down the list is dropped.
- Using a ready-made optimizer like Adam still counts as written by hand, because the RL pieces themselves are your code.
- The replay viewer is a pygame window: space pauses, → steps one frame, ↑/↓ change speed. Runs save as plain files under `runs/` (left out of git), and notes go in `notes/<world>.md`.
- Sign-off checks return a list of what's missing, which is empty when a world is signed off.
