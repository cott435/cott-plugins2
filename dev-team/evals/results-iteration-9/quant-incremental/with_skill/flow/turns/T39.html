I've drafted the S3 architecture, and it's back to **Draft** for your review. Every S3 requirement has a home, and lint shows 0 errors; the one warning is the `qdata` contract size AD-12 already accepted. There are no probes, because no external service or dataset is involved.

## The design

**New package `qfeat`** holds the whole feature study (AD-18). It has nine modules:
- `target`: residual targets.
- `features`: the 7 candidate and 2 calibration features.
- `panel`: builds every date's window, features and targets, and joins them. It's the only module that reads data.
- `model`: the walk-forward model and each feature's gain.
- `claims`: rank correlations, the 19-claim family tested with `null-hypothesis-testing`, and the power statement.
- `explore`: inputs for the `data-analysis` characterisation.
- `synthetic`: the procedure check on planted data.
- `registry`: registered feature lists and the holdout ledger.
- `run`: development and holdout runs end to end.

`qfeat` writes only under `$QDATA_HOME/features/` and is run from the command line. No app pages.

**The dependency rule changes.** A research stage may now import an earlier stage's contract, never a later one's. So `qfeat` uses `qrisk`'s window, eligibility and factor-count functions rather than copying them. The new import order is `qfeat → qrisk → qdata`.

**New system pipeline PL-24, run the feature study:** `qfeat` opens the version, gets each date's window and factor count from `qrisk`, reads features as of each rebalance date and targets as of the next, then writes the run.

**Changes to existing docs:**
- `qrisk` and `qdata` contracts: only their "used by" lines change, to list `qfeat`. Both are back to Draft.
- AD-13 revised in place: its context now refers to "the point-in-time reader" rather than `qdata.query` alone.

## Decisions, all Proposed
| ID | Choice |
|---|---|
| AD-18 | `qfeat` is its own package and reuses `qrisk`'s windows; the import rule is widened as above |
| AD-19 | **LightGBM** gradient-boosted trees: deterministic, one thread per fit, fixed seed. Missing values are handled natively, never filled. Settings are tuned on development dates only and recorded at registration |
| AD-20 | Loadings are the top k principal components of each window's correlation, rescaled by each name's volatility, as RF-01 but refitted per window. The month's factor returns come from a cross-sectional regression on those loadings. Beta is the first loading, signed so the market factor's mean loading is positive |
| AD-21 | The feature panel is cached per data version and built one date per worker. Registered lists are write-once files whose ID is a hash of their contents. The holdout ledger is append-only: a holdout run is recorded under a file lock before it reads any holdout target, and a list already in it is refused |

## Assumptions I made
- **Names:** the package is `qfeat`. The module is `claims` rather than `tests`, to avoid confusion with the tests folder.
- **Commands:** `qfeat run --development` and `qfeat run --holdout <list_id>`.
- **Parameters:** they live in `config/features.toml`.
- **Reproducibility:** each run's manifest records the LightGBM version, because results only repeat on the same version.

## Open risks
- **Holdout power:** about 69 months can only detect a mean monthly rank correlation of roughly 0.025 or more.
- **The holdout ledger** stops accidental reruns, not someone deleting the file; the report says so.

**One question: is LightGBM right for the model?** The idea left the model family to this step, and it's the costliest choice to change later.
- **My recommendation and the default:** LightGBM. It handles interactions, routes missing values without filling them, and can be made exactly reproducible.
- **Alternatives:** a random forest (slower here, and it doesn't route missing values natively), or a ridge regression (no interactions, so the model would add little over the single-feature baseline).

Do you approve the architecture, with or without LightGBM? Once you do, the decisions become Accepted, and the next step is designing `qfeat`'s pipelines.
