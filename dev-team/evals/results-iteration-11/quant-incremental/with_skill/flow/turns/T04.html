# The spec: template, writing rules, hygiene check

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown
**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [brief.md](brief.md)

## Summary
[2-3 sentences: what is being built. Link to the brief for why — don't repeat it.]

## Users
| User | What they need to do |
|---|---|

## Scope
**In scope:** [features, by name]
**Out of scope:** [what we're not building — include everything on the brief's Not Doing list, plus anything decided during clarification]

### [Feature name] (`CODE`)

**Stage:** S2
**Source:** [ideas/<slug>.md](ideas/<slug>.md) *(extend mode only — omit for features from the original brief)*
**Behavior:** [2-4 sentences or a short numbered flow describing what the user experiences.]

**Requirements**
- **CODE-01** [One testable statement of what the system does.]

  - Given [...], when [...], then [...].
- **CODE-02** [...]
  - Given [...], when [...], then [...].

**Edge cases & errors**
- [Situation] → [expected behavior]

## Data requirements
*(Data and ML projects only — omit otherwise.)*
- **DATA-01** [What data the system needs: content, coverage, history, frequency, freshness — not which vendor.]
  - Given [...], when [...], then [...].

## Quality requirements
- **QR-01** [Measurable non-functional requirement: speed, reliability, accessibility, privacy, security, cost, licence.]
  - [How it's checked.]

## Assumptions
- [Assumptions the user confirmed]

## Open questions
- [Unresolved items, each with who can answer it. Omit if none. A question about what an external source really returns is "answered by a probe during architecture".]

## Changelog
| Date | Change | Source | IDs |
|---|---|---|---|
| YYYY-MM-DD | Initial spec | brief.md | all |
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Every feature names one stage.** Its `**Stage:**` line holds only the ID of the roadmap stage that first builds it. `dt lint` fails a feature with no stage, or one naming no stage row.
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence, budget and run-time limits are `QR-` items, each with how it is measured ("data costs ≤ $50 a month"; "the full study runs in ≤ 1 hour", timed on the user's machine), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads it in `docs/requests.md`.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea", "UR-03") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git; which requirement honours which request goes in `docs/requests.md` (`dt request trace`).
- **The user's words win over the brief's.** Where a `spec` request is more specific than the brief or idea file ("circular tank", "one predator"), the requirement says what the request says, or the user approves the change.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **The user's words.** `dt request --open --owner spec` is empty, or each one left is a change you ask the user about.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of torchvision's ResNet-18" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.
# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

# Quant Research Platform — Spec

**Status:** Draft · **Last updated:** 2026-10-18 · **Brief:** [brief.md](brief.md)

## Summary
A local data foundation for honest quant research on US stocks: it builds dated, validated snapshots of a point-in-time S&P 500 daily dataset (prices, returns, splits, dividends, delisted members included), reports every check and cross-source disagreement, loads any slice in one step, and lets the user explore it in a local app. See the [brief](brief.md) for why.

## Users
| User | What they need to do |
|---|---|
| Researcher (the owner, sole user) | Build and refresh the dataset, read its health, load slices for research, and explore prices, universe and problems by eye |

## Scope
**In scope:** Dataset build, As-of snapshots, Point-in-time universe, Prices and returns, Data health report, Research loader, Exploratory analysis, Data explorer.
**Out of scope:**
- Company fundamentals; Stage 1 holds prices and corporate actions only.
- Real money, order placement or any brokerage link; research and paper trading only.
- Intraday bars, live market feeds, non-US markets.
- Stocks that were never S&P 500 members.
- Using the cross-check source to fill gaps in the primary source; it only cross-checks.
- Sharing, hosting or multi-user access to the app.
- Signal research and backtesting (later stages, not yet decided).

## Features

### Dataset build (`BUILD`)
**Serves:** Goal 1, Goal 2
**Stage:** S1
**Behavior:** The user starts a build, from the command line or the app. It downloads everything the dataset needs from the primary source, cleans it, validates it, cross-checks surviving stocks against the second source, and stores the result as a new dated snapshot with its health report.

**Requirements**
- **BUILD-01** One command builds a complete new snapshot, with no other manual steps.
  - Given valid credentials and no existing snapshots, when the user runs the build command, then a new snapshot holding every dataset in Data requirements exists when it finishes.
- **BUILD-02** An interrupted build resumes without downloading again what it already has.
  - Given a build stopped halfway through the download, when the user runs it again the same day, then already downloaded stocks are not requested again and the finished snapshot equals one built without interruption.
- **BUILD-03** Cleaning never changes a value without recording it.
  - Given a raw price the cleaning step corrects or removes, when the build finishes, then the health report lists that stock, date, field, value before, value after and the rule that made the change.
- **BUILD-04** A build whose blocking checks fail is stored but marked failed.
  - Given a build where a blocking check (HLTH-02) fails, when it finishes, then the snapshot is listed with status "failed" and the loader refuses it unless the user asks for it by name.
- **BUILD-05** The app shows a running build's progress live.
  - Given a build in progress, when the user has the app open, then it shows the current phase (download, clean, validate, cross-check, store), the share of stocks done and the elapsed time, updated at least every 2 seconds.
- **BUILD-06** A build can be started from the app.
  - Given no build is running, when the user starts one in the app, then it runs exactly as the command does and its progress appears (BUILD-05).

**Edge cases & errors**
- Credentials missing or rejected → the build stops before downloading, with a message naming the problem; no snapshot is created.
- Primary source unreachable or rate-limited mid-build → the build retries, then stops resumably (BUILD-02) with a message; no partial snapshot is listed as usable.
- Cross-check source unreachable → the build finishes; the report marks the cross-check "incomplete" with the stocks not checked, never "passed".
- A second build started while one runs → refused, naming the running build.

### As-of snapshots (`SNAP`)
**Serves:** Goal 3
**Stage:** S1
**Behavior:** Each build is a snapshot named by the date its data was retrieved. Snapshots never change once finished, so any result can be reproduced by naming the snapshot it used, even after the vendor revises its history.

**Requirements**
- **SNAP-01** A finished snapshot is never modified.
  - Given a finished snapshot, when later builds run, then every value in it is unchanged.
- **SNAP-02** Rebuilding the derived data from a snapshot's saved raw data gives identical numbers.
  - Given a snapshot, when its returns, adjusted prices, universe and health report are rebuilt from its raw data, then every number equals the original exactly.
- **SNAP-03** The same load from the same snapshot always returns the same result.
  - Given a load request naming a snapshot, when it is repeated after newer snapshots exist, then the result is identical value for value.
- **SNAP-04** The user can list snapshots.
  - Given several snapshots, when the user lists them, then each shows its date, status (healthy or failed), date range covered, number of stocks and number of unexplained cross-check differences.
- **SNAP-05** The user can compare two snapshots to see what the vendor revised.
  - Given two snapshots, when the user compares them, then every price, split, dividend and membership date that differs on dates both cover is listed with both values, plus counts per field.

**Edge cases & errors**
- Two builds on the same day → the second gets a distinct name (date plus sequence number); neither overwrites the other.
- A snapshot whose files were altered or damaged → loading it fails with a message that it no longer matches its record, never returns altered data.
- Disk space runs out mid-build → the build stops resumably; earlier snapshots are untouched.

### Point-in-time universe (`UNIV`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** For any trading day in the covered history, the universe is the S&P 500 as it stood that day: stocks that later left the index or were delisted are in it, stocks that joined later are not.

**Requirements**
- **UNIV-01** The universe on a day is exactly the stocks that were index members that day.
  - Given a stock added to the index on 2015-03-20, when the universe is asked for 2015-03-19, then the stock is absent; for 2015-03-20, it is present.
  - Given a stock removed on 2012-06-01, when the universe is asked for 2010-01-04, then the stock is present.
- **UNIV-02** The user's ten delisted former S&P 500 members all appear.
  - Given the user's list of 10 delisted former members, when a snapshot is built, then each has its index entry and exit dates and daily prices up to its last trading day, and the health report shows this check passing for all 10.
- **UNIV-03** A stock keeps one identity through ticker changes.
  - Given a member that changed ticker, when its history is loaded, then prices before and after the change form one continuous series under one permanent identifier.
- **UNIV-04** A reused ticker never merges two companies.
  - Given a ticker held by one company until 2008 and by another from 2012, when either is loaded, then each company's history is separate and neither includes the other's prices.
- **UNIV-05** Daily member counts are checked.
  - Given a snapshot, when validated, then every trading day with fewer than 495 or more than 510 members is listed in the health report.

**Edge cases & errors**
- Companies with two share classes in the index at once → both classes are members, each with its own identifier.
- A member with no price on a day it was a member → listed in the health report (HLTH-02), not dropped from the universe.
- A day before the membership history begins → the universe request fails with a message naming the first covered day.

### Prices and returns (`PRICE`)
**Serves:** Goal 1, Goal 4
**Stage:** S1
**Behavior:** Every member has raw daily prices, split-adjusted prices, and daily returns with and without dividends, all derived from the same snapshot's raw prices and corporate actions.

**Requirements**
- **PRICE-01** Split-adjusted prices are continuous across splits.
  - Given a 2-for-1 split effective day D, when split-adjusted closes are loaded, then the raw close before D is divided by 2 and the day-D return reflects only the market move.
- **PRICE-02** Daily price return is the change in split-adjusted close.
  - Given split-adjusted closes 100 then 102, when the price return is loaded, then it is 0.02.
- **PRICE-03** Daily total return adds the cash dividend on its ex-date.
  - Given a close of 100, a $1 dividend with ex-date the next day and a next-day close of 100, when the total return is loaded, then it is 0.01 for the ex-date.
- **PRICE-04** Adjustments come from the snapshot's own recorded corporate actions.
  - Given a split or dividend corrected by cleaning (BUILD-03), when the snapshot is built, then adjusted prices and returns use the corrected value.
- **PRICE-05** No values are invented after a stock's last trading day.
  - Given a stock delisted on day D, when its data is loaded for a range past D, then rows end at D with no filled-forward prices or returns.

**Edge cases & errors**
- A missing trading day mid-series → no return is computed across the gap silently; the day's return is empty and the gap is listed in the health report.
- A split with no matching price jump, or a jump with no split → flagged by HLTH-02, never auto-adjusted.

### Data health report (`HLTH`)
**Serves:** Goal 2
**Stage:** S1
**Behavior:** Every snapshot carries a report of every check run, every disagreement with the cross-check source and every fix cleaning applied. Nothing found is hidden: each problem is either explained or shown as unexplained.

**Requirements**
- **HLTH-01** The report lists every check run, not only failures.
  - Given a build, when its report is opened, then every check appears with its result, its severity (blocking or warning) and the number of records affected, including checks with zero.
- **HLTH-02** The build runs at least these checks: missing trading days for a member, non-positive prices, high below low, close outside the day's high–low range, duplicate dates, daily moves beyond ±50% with no corporate action, splits with no matching price move, member days with no price, daily member counts (UNIV-05) and the ten-delisted check (UNIV-02).
  - Given a snapshot seeded with one example of each problem, when validated, then each check reports exactly that example.
- **HLTH-03** Surviving stocks' closes are cross-checked against the second source.
  - Given a surviving stock, when cross-checked, then every day its split-adjusted close differs from the second source by more than 0.5% is listed with both values.
- **HLTH-04** Splits are cross-checked against the second source.
  - Given a surviving stock, when cross-checked, then every split that is missing from either source, or differs in ratio or date, is listed.
- **HLTH-05** Dividends are cross-checked against the second source.
  - Given a surviving stock, when cross-checked, then every dividend missing from either source, or differing by more than $0.01 or in ex-date, is listed.
- **HLTH-06** Stocks the second source cannot check are counted, not skipped silently.
  - Given delisted members, when cross-checked, then the report shows them as "not cross-checkable" with their count.
- **HLTH-07** The user can attach an explanation to a difference.
  - Given a listed difference, when the user records an explanation, then the difference shows as explained with that note, and the snapshot's unexplained count drops by one.
- **HLTH-08** Explanations carry to later snapshots.
  - Given an explained difference, when a later snapshot finds the same difference (same stock, date, field and values), then it is shown as explained with the same note.

**Edge cases & errors**
- The second source returns nothing for a surviving stock → listed as "no cross-check data", counted separately from differences.
- A difference that changes between snapshots → shown as unexplained again, with the earlier note visible for reference.

### Research loader (`LOAD`)
**Serves:** Goal 4
**Stage:** S1
**Behavior:** From a research session, one call returns the requested slice of a snapshot as a table: which stocks (a list, or the point-in-time universe), which dates, which fields.

**Requirements**
- **LOAD-01** One call returns any slice.
  - Given stocks, a date range and fields, when the user makes one loader call, then it returns a table with one row per stock per trading day and one column per field.
- **LOAD-02** The loader offers raw open, high, low, close and volume, split-adjusted prices, price return, total return, and dividend and split amounts.
  - Given a request for each field, when loaded, then each column matches its definition in PRICE.
- **LOAD-03** Asking for the universe returns each stock only on its member days.
  - Given a request for the point-in-time universe over 2008–2010, when loaded, then a stock removed in 2009 has rows only up to its exit date.
- **LOAD-04** Without a named snapshot, the loader uses the latest healthy one.
  - Given a healthy snapshot and a newer failed one, when the user loads without naming one, then the healthy one is used.
- **LOAD-05** Every result says which snapshot it came from.
  - Given any load, when it returns, then the result carries the snapshot's name.

**Edge cases & errors**
- An unknown ticker or identifier → error naming it; no partial result.
- Dates outside the snapshot's coverage → error naming the covered range.
- No healthy snapshot exists → error saying so and naming the failed ones.

### Exploratory analysis (`EDA`)
**Serves:** Goal 1, Goal 2
**Stage:** S1
**Behavior:** For any snapshot, the user can produce a basic exploratory analysis of the dataset and read it as a report with plots.

**Requirements**
- **EDA-01** The dataset is characterised with the `data-analysis` skill, given a snapshot's point-in-time universe returns and coverage; it passes when the report shows coverage and missingness by year, the cross-sectional distribution of daily returns with its tails, the largest moves with their dates, and the member count over time, each with its plot.
  - Given a snapshot, when the analysis is run, then the report contains each listed item with a plot.
- **EDA-02** The analysis shows the size of survivorship bias.
  - Given a snapshot, when the analysis is run, then it plots the equal-weighted total return of the point-in-time universe against the same for only today's members, over the full history, with the annualised difference.
- **EDA-03** Rerunning the analysis on the same snapshot gives the same numbers.
  - Given a snapshot, when the analysis runs twice, then every number in both reports is identical.

**Edge cases & errors**
- A failed snapshot → the analysis runs only when named explicitly, and the report states the snapshot failed.

### Data explorer (`EXPL`)
**Serves:** Goal 5, Goal 2
**Stage:** S1
**Behavior:** A local app in the browser for looking at the data by eye: a stock's prices with its corporate actions and index membership, the universe on any day, the health report, the cross-check overlay, and running builds. Every view reads from one chosen snapshot.

**Requirements**
- **EXPL-01** Every view shows data from the chosen snapshot, named on screen.
  - Given two snapshots, when the user switches between them, then all views reload from the chosen one and its name and status stay visible.
- **EXPL-02** A stock view charts its full price history with its events.
  - Given any member, when opened, then raw and split-adjusted closes are charted with splits, dividends and index entry and exit marked on their dates.
- **EXPL-03** A universe view shows the members on any day.
  - Given a date, when chosen, then the members and their count are shown, and stepping to the next trading day highlights who joined and who left.
- **EXPL-04** A health view lists the report's findings, filterable.
  - Given a snapshot's report, when opened, then findings can be filtered by check, stock, severity and explained or unexplained.
- **EXPL-05** A finding opens the stock view at its date.
  - Given a finding for stock S on day D, when the user selects it, then the stock view opens for S centred on D.
- **EXPL-06** A cross-check view overlays both sources for a surviving stock.
  - Given a surviving stock, when opened, then both sources' split-adjusted closes are drawn together and days beyond the 0.5% tolerance are highlighted.
- **EXPL-07** The user records difference explanations in the app.
  - Given an unexplained difference, when the user writes a note in the health view, then it is saved as in HLTH-07.
- **EXPL-08** The interface is designed with the `frontend-design` skill to a deliberate visual direction, not a default dashboard; it passes when the user approves that direction from mock-ups of the stock and health views before the views are built.
  - Given the mock-ups, when the user reviews them, then the user approves the direction or the views are not built.

**Edge cases & errors**
- No snapshots yet → the app opens on an empty state offering to start a build.
- A stock with no cross-check data → the cross-check view says so instead of drawing one line.
- The app is open while a build finishes → the new snapshot appears in the picker without restarting the app; the open view does not switch on its own.

## Data requirements
- **DATA-01** Daily open, high, low, close and volume for every stock that was an S&P 500 member at any time in the covered history, including those since delisted, from the earliest date the primary source provides.
  - Given a snapshot, when coverage is checked, then every stock in the membership history has prices for every trading day of its membership on or after the first covered day.
- **DATA-02** S&P 500 membership history: each member's entry and exit dates, including members since delisted.
  - Given a snapshot, when membership is read, then every member has an entry date and, if it left, an exit date.
- **DATA-03** Splits with effective date and ratio, and cash dividends with ex-date and amount, for every member.
  - Given a member that split or paid a dividend, when its corporate actions are read, then each event appears with its date and value.
- **DATA-04** A permanent identifier per company, with its ticker history.
  - Given a company that changed ticker, when its record is read, then it has one identifier and each ticker with the dates it held it.
- **DATA-05** For surviving members: daily closes, splits and dividends from a second, independent source, used only for cross-checking.
  - Given a surviving member, when the cross-check data is read, then it holds that stock's closes, splits and dividends over the dates the second source provides.
- **DATA-06** US exchange trading days only.
  - Given a weekend or market holiday, when any data is loaded for it, then no row exists for that day.

## Quality requirements
- **QR-01** Data costs stay at or under $50 a month in total.
  - Checked against the monthly subscription charges of every data source used.
- **QR-02** Everything runs on the user's MacBook Pro (Apple Silicon) with no remote servers.
  - Checked by running a full build, a load and the app with no services other than the data sources.
- **QR-03** A full build from scratch finishes in ≤ 2 hours; a refresh that reuses unchanged history in ≤ 15 minutes.
  - Timed on the user's machine.
- **QR-04** Loading one year of daily closes for the whole point-in-time universe takes ≤ 2 seconds; the full history, ≤ 15 seconds.
  - Timed on the user's machine after the snapshot is first opened.
- **QR-05** In the app, a stock's full-history chart appears ≤ 1 second after it is selected.
  - Timed on the user's machine.
- **QR-06** The app accepts connections only from the same machine.
  - Checked by trying to open it from another device on the same network: the connection is refused.
- **QR-07** Credentials never appear in full in logs, reports, progress messages or the app.
  - Checked by searching every output of a build for the credential values.
- **QR-08** One snapshot takes ≤ 5 GB of disk.
  - Measured on the first full build.

## Assumptions
- One user, on one laptop; no logins or access control beyond QR-06.
- The S&P 500 is the whole universe for Stage 1; never-members are not stored.
- A build is started by the user; nothing runs on a schedule.
- Blocking checks: non-positive prices, high below low, duplicate dates, and the ten-delisted check; all others warn.

## Open questions
- Does the primary source include S&P 500 membership history and corporate actions in the current plan, and how far back? Answered by a probe during architecture.
- Can the second source return splits and dividends as well as prices for surviving stocks? Answered by a probe during architecture.
- Proposed numbers to confirm with the user: 0.5% close tolerance, $0.01 dividend tolerance, 495–510 daily members, ±50% move threshold, QR-03/04/05/08 limits, and which checks block.
