# Interface tasks: types, then contract tests

Read when writing a milestone's interface tasks (`phase0.md` a). Example: `examples-phase0.md`.

Interface tasks (`**Kind:** interface`, `**Step:** contract`, solo) freeze, as code, every boundary in the milestone whose two sides belong to different tasks:
- each contract `type` section named in a milestone step's `In → Out`, every one, since the step's signature needs it, written into its owner's `types.py`, with a schema (pandera for a frame, JSON Schema across runtimes) and one sample per case in `tests/contracts/<component>.<Type>/`. A case naming a probe sample (`PB-01 samples/sync_added.json#0`) puts `PB-01:samples` in `Read:`; the task derives the type's sample from it, never copies it
- each new step's signature in its owner module, its body `raise NotImplementedError("<task id>")` naming the task that replaces it (Fakes and stubs); where the layout splits a step's module by concern (`agent/dqn/memory.py`, `targets.py`), each concern file's seam too, so its thicken's packet shows it (a `Read:` path no task the reader waits on writes fails `read-unwritten`)
- for each function another pipeline or package calls (its `**Boundary:**` line names that consumer): a fixture-backed fake serving its fixtures, where the caller's tests load it, and its contract's cases as one test that takes the provider
- for each object with behavior a step passes (a Protocol or class: `core.Dataset`, `runstore.RunWriter`) and each call to a function another task builds in the caller's own pipeline and package (a `**Boundary:**` line naming a component too): the Protocol or signature plus a fixture-backed replay double in `tests/contracts/<component>.<Type>/`. The double is that type's sample, not a fake: the system task never swaps it. It stands in for the class's constructor and methods too (the caller's test hands it in or patches it where the step calls it), so a step that builds or calls one (`new_run` constructing `FileRunDir`) waits on no spine
- each component's `__init__.py` exports, and the package's `__main__.py`: the dispatch from each pipeline's trigger to its entry function, whose signature it stubs naming the wiring task, in that pipeline's own entry module

Not frozen: helpers, private functions, anything one task owns end to end, and boundaries an earlier milestone froze. `Read:` the type and boundary symbols.

**Types first, then one contract task per component**, so samples and contract tests, the slow part, run side by side, and a contract change redoes one part, not the whole freeze:
- **Types** (`**Depends on:** —`): every component's `types.py`, Protocols, step signatures and stubs, concern seams, exports and `__main__.py`; no samples or contract tests. Acceptance: every signature imports and matches the contract; the gate's type check passes. `Writes:` each component folder as one glob (`src/gridload/profile/**`) and `tests/support/**` for the helpers tests share (a golden-case store builder; `tests/conftest.py` is protected); `task-size` doesn't count them.
- **Contract**, one per component with contract types, each depending only on the types task: its samples, fakes, replay doubles and contract tests. Acceptance: every sample validates against its type; each fake passes its contract's cases, and each replay double serves its fixtures. `Writes:` its `tests/contracts/<component>.<Type>/` folders.

When the milestone's contract types sit in one component, one interface task does both. A task whose tests load a component's samples, fakes or doubles depends on its contract task. A milestone across packages has one types task per provider, all first, never depending on each other. When one runtime's types are generated from another's schema, the provider's types task runs the generator and writes the generated file too (its `Writes:` claims it). A human approval a requirement places before several steps (a design direction) is asked during planning, never written as a task's acceptance (a background agent can't get it); the types task writes the chosen direction's sample, and those steps build on it, with no edge to the step that sets it.

**Fakes and stubs.** A fake is allowed only where a pipeline calls another pipeline or package. Shared fixtures don't stop it drifting: whatever it does beyond echoing one (filtering, ordering, an error) is one of its contract's cases, and the system task runs those cases on the real provider (`dt context`'s Conformance block). Each case is also named in the acceptance of a task that builds that behavior in the real provider (its spine, a thicken or the wiring, or Deferred with it), so a drift fails there first; a case with no such task is a plan gap, like an uncovered ID. Mocking a step is forbidden: a step's spine is the real baseline, and its consumer builds against the type's sample (for a Protocol or class, its replay double). The interface stubs are the floor's one stub carve-out (`build-setup`'s CR-02): allowed while the task they name is open; the gate fails on one naming a done task, the milestone exit on any. No test checks a stub (`stub-pinned`): it would fail once its task lands, so an acceptance names the signature, never the body.

**Frozen means frozen.** Changing a frozen type, sample, signature or fake is a `contract-change`: `architecture-design` Revise, then a new interface task naming the symbol in `Read:`, never an edit to make a test pass. The bar enforces it (CR-09): once a contract folder exists at a task's base the implementer can't write it, and `dt guard` asks before any edit no open interface task covers. The re-freeze is that interface task, run by an implementer agent, never the main session: its `Writes:` names the frozen folders it changes, which opens them to it alone.
