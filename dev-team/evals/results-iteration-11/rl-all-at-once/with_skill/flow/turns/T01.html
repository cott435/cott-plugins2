No `docs/brief.md` yet. Examples: `examples-new.md` (all phases), `examples-process.md` (a non-product idea), `examples-data.md` (a data-dependent brief).

## The brief

Write `docs/brief.md` (create `docs/` if needed) from this template. The brief answers **why**, not **how** or **what exactly** — no requirements lists, no tech choices, no screens.

```markdown
# [Project Name]

**Status:** Draft · **Last updated:** YYYY-MM-DD

## The problem
[2-4 sentences. Who has the problem, what it costs them today, and why it matters now.]

## Who it's for
[The specific people this serves. Name a primary user; mention a secondary one only if it matters.]

## Goals
1. [An outcome for the user, not a feature — "Regulars can reorder in under 30 seconds"]
2. [...]
3. [...]

## Constraints
- [Real limits: deadline, budget, team, existing systems, rules or regulations]

## What success looks like
- [Observable signs it worked — numbers where you have them]

## What we're betting on
- [The 2-3 assumptions that must be true, in plain words]

## Not doing
- [Tempting thing we're deliberately leaving out] — [one-line reason]

## Open questions
- [Only questions that could change the direction. Omit the section if none.]
```

**Writing rules — the brief must pass all of these:**

- **One page or less.** Aim for 250-450 words. If it's longer, cut — don't shrink the font.
- **Plain English.** Write for a smart person outside the team. No acronyms without a definition, no jargon, no code, no file paths.
- **Short sentences, short bullets.** One idea per bullet. No bullet longer than two lines.
- **Data needs, not data vendors.** For ML and data projects, say what data the project depends on in plain terms ("10 years of hourly meter readings, including meters since decommissioned") as a constraint or a bet. Name a specific source only if it's fixed (our own data, a required benchmark). Choosing APIs and datasets happens in the architecture, after the spec.
- **Goals are numbered** so `spec-writing` can trace requirements back to them ("serves Goal 2").
- **3-5 goals, project-level and stage-neutral.** A goal is an outcome of the whole project ("Forecast errors we can trust"), never a stage ("Stage 2: the seasonal fit works"). If the user describes the project in stages, the stages become roadmap stage rows (`roadmap.md`), and every goal stays true whichever stage is being built. More than five goals means the project isn't focused yet — go back to Phase 2.
- **The Not Doing list is mandatory.** It is the most valuable part: it makes trade-offs explicit.
# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

## ML Feature in an Existing Product (Extend Mode)

**User invokes:** `/ideate use ML to flag bad assay plates automatically in our lab results app`

The app already has `docs/brief.md` (Goal 2: *Bad data is caught before it reaches analysis*) and `docs/spec.md`, so this is **extend mode**. The skill reads both, plus the `qc` module in the codebase.

### Phase 1: Understand & Expand

> **How might we** catch failed plates before they reach analysis, without scientists reviewing every plate by hand?

Questions:

1. **How are plates checked today, and how long does it take?**
2. **What history exists?** How many plates, and is there a record of which ones were failed and why?
3. **What's worse: a bad plate getting through, or a good plate being re-run?**

**User responds:** "Scientists eyeball every plate — about 6 hours a week. We have 3 years of plate reads, roughly 40,000 plates, and about 2% were marked failed in the app. Missing a bad plate is much worse; a re-run costs a day."

**Skill continues:**

Before any ML: assay QC already has a standard rule, the **Z′-factor** (plates under 0.5 are suspect). Your `qc` module computes it but nobody acts on it. That's the baseline any model has to beat. If the rule alone catches most failures, you may not need ML at all.

Variations:

1. **Simplification — Just Use the Rule:** Auto-flag plates with Z′ < 0.5 and stop there. Zero ML.
2. **Ranked Review Queue:** A model scores every plate. Scientists review the riskiest first and stop when the scores get low. Humans still decide.
3. **Inversion — Auto-Pass the Obvious:** Instead of finding bad plates, confidently clear the clearly-good ones, and scientists review the rest.
4. **Anomaly Detection:** No labels needed. Flag plates that look unlike typical ones. Useful if past "failed" labels turn out to be unreliable.
5. **Expert Lens — Layout Patterns:** Many failures show up as spatial patterns (edge effects, a dead column). Features built from plate layout may beat a generic model.

### Phase 2: Evaluate & Converge (summary)

**Data check:** 40,000 plates with 800 failures is enough to try a supervised model, *if* the labels are consistent. That's the biggest bet. Different scientists may fail plates for different reasons. **Baseline:** the Z′ rule. **Cost asymmetry:** missing a bad plate is far worse, so measure recall at a fixed review budget, not accuracy (98% accuracy is free by passing everything).

The user picks **2 (ranked queue), with 1 as the baseline it must beat**. **Fit check:** it serves existing Goal 2 and the same users, so **the brief does not change.**

### Phase 3: Write the Idea File

`docs/ideas/plate-qc-ranking.md`:

```markdown
# Idea: Plate QC Ranking

**Status:** Draft · **Last updated:** 2026-10-14 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This ranks every new assay plate by how likely it is to fail QC, so scientists review the riskiest plates first instead of checking all of them.

## The problem
Scientists check every plate by eye, about 6 hours a week. Failures are rare (about 2%) but costly: a bad plate that slips through corrupts downstream analysis. A good plate failed by mistake costs a day to re-run. The app already computes a standard quality score (Z′) but nothing acts on it.

## Who it's for
Lab scientists doing plate QC, during their weekly review.

## How it fits
- **Serves:** Goal 2 (bad data caught before analysis)
- **Touches:** QC-01 (Z′ is calculated per plate), QC-03 (scientist marks pass/fail)
- **Brief changes:** None
- **Stage:** New S3 (roadmap stage on acceptance)

## Recommended direction
Each new plate gets a risk score from a model trained on three years of past pass/fail decisions. The review screen sorts plates riskiest first. Scientists still make every pass/fail call; the model only sets the order.

The Z′ rule is the baseline. If the model doesn't clearly beat "sort by Z′", we ship the rule alone and stop.

## Data
- About 40,000 plates over 3 years, with raw reads, Z′, and the scientist's pass/fail decision (about 800 failures).
- All in our own database. No outside data needed.
- Evaluate on the most recent 6 months, never trained on, to mimic real use.

## Alternatives considered
- Rule only (Z′ < 0.5) — kept as the baseline, and the fallback if the model doesn't beat it.
- Anomaly detection — only if past labels turn out to be unreliable.
- Auto-passing obvious plates — revisit once the ranking has earned trust.

## What success looks like
- Reviewing the top 20% of plates catches at least 90% of the plates scientists would fail.
- Clearly better than sorting by Z′ alone on the same 6 months.
- Weekly review time drops from about 6 hours to under 2.

## What we're betting on
- Past pass/fail decisions are consistent enough to learn from.
- New plates look like past plates (same instruments and assays).

## Not doing
- Automatically failing or passing plates — a scientist always decides.
- Image-based models of the plate.
- Plates from other sites or instruments.

## Open questions
- How often do two scientists agree on the same plate? Measure before training.
- How often should the model be retrained, and who signs off?
```

# Ideation: understand, expand, converge

Phases 1 and 2 of every run, New and Extend alike. The mode file says what to read before Phase 1 and what Phase 2 must also settle. Throughout, record the user's words as `requests.md` says: their first message, each answer, each direction they pick.

## Phase 1: Understand & expand

1. **Restate the idea** as a "How Might We" problem statement.
2. **Ask 3-5 sharpening questions**, no more, with `AskUserQuestion`: who it's for, what success looks like, real constraints, what's been tried, why now. Don't proceed until you know who it's for and what success looks like.
3. **Generate 5-8 variations**, each with a one-line reason it exists. Lenses: inversion, constraint removal, audience shift, combination, simplification, 10x version, expert lens. `frameworks.md` has more; pick what fits.

In a codebase, ground variations in what exists and cite files. Read `docs/references.md` too; an idea cites a reference as prior art by `RF-NN`, never its path.

## Phase 2: Evaluate & converge

1. **Cluster** what resonated into 2-3 meaningfully different directions.
2. **Stress-test** each: user value (painkiller or vitamin?), feasibility (cost, hardest part), differentiation (would someone switch?), and for ML and data projects, data: does usable data exist, can we use it, what's the non-ML baseline? "No usable data" is a feasibility failure, not an open question. Rubric: `refinement-criteria.md`.
3. **Surface hidden assumptions:** what you're betting is true, what could kill it, what you're ignoring for now.
4. **Get a decision** on a direction before writing anything.
# Refinement & Evaluation Criteria

Use this rubric during Phase 2 (Evaluate & Converge) to stress-test idea directions. Not every criterion applies to every idea — use judgment about which dimensions matter most for the specific context.

## Core Evaluation Dimensions

### 1. User Value

The most important dimension. If the value isn't clear, nothing else matters.

**Painkiller vs. Vitamin:**
- **Painkiller:** Solves an acute, frequent problem. Users will actively seek this out. They'll switch from their current solution. Signs: people describe the problem with emotion, they've built workarounds, they'll pay for a solution.
- **Vitamin:** Nice to have. Makes something marginally better. Users won't go out of their way. Signs: people nod politely, say "that's cool," then don't change behavior.

**Questions to ask:**
- Can you name 3 specific people who have this problem right now?
- What are they doing today instead? (The real competitor is always the current workaround.)
- Would they switch from their current approach? What would make them switch?
- How often do they encounter this problem? (Daily problems > monthly problems)
- Is this a "pull" problem (users are asking for this) or a "push" problem (you think they should want this)?

**Red flags:**
- "Everyone could use this" — if you can't name a specific user, the value isn't clear
- "It's like X but better" — marginal improvements rarely drive adoption
- The problem is real but rare — high intensity but low frequency rarely justifies a product

### 2. Feasibility

Can you actually build this? Not just technically, but practically.

**Technical feasibility:**
- Does the core technology exist and work reliably?
- What's the hardest technical problem? Is it a known-hard problem or a novel one?
- Are there dependencies on third parties, APIs, or data sources you don't control?
- What's the minimum technical stack needed? (If the answer is "a lot," that's a signal.)

**Resource feasibility:**
- What's the minimum team/effort to build an MVP?
- Does it require specialized expertise you don't have?
- Are there regulatory, legal, or compliance requirements?

**Time-to-value:**
- How quickly can you get something in front of users?
- Is there a version that delivers value in days/weeks, not months?
- What's the critical path? What has to happen first?

**Red flags:**
- "We just need to solve [very hard research problem] first"
- Multiple dependencies that all need to work simultaneously
- MVP still requires months of work — likely not minimal enough

### 3. Differentiation

What makes this genuinely different? Not better — *different*.

**Questions to ask:**
- If a user described this to a friend, what would they say? Is that description compelling?
- What's the one thing this does that nothing else does? (If you can't name one, that's a problem.)
- Is this differentiation durable? Can a competitor copy it in a week?
- Is the difference something users actually care about, or just something builders find interesting?

**Types of differentiation (strongest to weakest):**
1. **New capability:** Does something that was previously impossible
2. **10x improvement:** So much better on a key dimension that it changes behavior
3. **New audience:** Brings an existing capability to people who were excluded
4. **New context:** Works in a situation where existing solutions fail
5. **Better UX:** Same capability, dramatically simpler experience
6. **Cheaper:** Same thing, lower cost (weakest — easily competed away)

**Red flags:**
- Differentiation is entirely about technology, not user experience
- "We're faster/cheaper/prettier" without a structural reason why
- The feature that differentiates is not the feature users care most about

**Internal tools, research code, and personal projects:** "would someone switch?" becomes "is this better than the notebook/spreadsheet/script we use today?" For forecasting work, differentiation is the accuracy gain itself — and the question is whether it survives held-out data and inputs known at forecast time, not whether it's novel.

### 4. Data & ML Feasibility

Apply this when the idea depends on data or a learned model. For these projects it is often the dimension that decides everything — a great idea with no usable data is not feasible.

**Do we need ML at all?**
- What's the simplest non-ML baseline (a rule, a threshold, a heuristic, a linear model)? How good is it?
- How much better than the baseline does the model need to be to matter? If nobody can say, the value isn't clear.
- What does a wrong prediction cost, and who catches it?

**Does the data exist?**
- Where would the data come from — data we own, a public dataset, a paid API? (Name candidates to test feasibility, checked from their public docs and pricing pages only; the final choice is made in the architecture. When the user hasn't picked a source for a kind of data the idea needs ("no fundamentals source yet"), suggest two or three with their cost and licence and ask which; one still unpicked goes under Open questions with its candidates. A risk that could kill the idea and that the docs can't settle goes under Open questions, for the architecture to probe.)
- Is there enough history and coverage (time span, entities, classes, regions)?
- For supervised learning: are there labels? Who made them, and would two people agree?
- Can we legally use it for this purpose? Licensing, terms of service, personal or patient data?
- What does it cost, now and at the scale we'd need?

**Is the data trustworthy for this use?**
- **Leakage / look-ahead:** would the model or its evaluation see anything that wasn't known at decision time?
- **Selection bias:** does the data quietly drop the failures (decommissioned meters, churned users, failed runs)?
- **Drift:** is the past a good guide to the future here? How fast does it go stale?
- **Point-in-time:** for time series especially, can we reconstruct what was known *at each time*, including later corrections?

**Can we tell if it works?**
- What metric, on what held-out data, compared to what baseline?
- Can it be tested before it's trusted — offline evaluation, replay on history, shadow mode, human review?

**Red flags:**
- "We'll figure out the data later" — for ML, the data *is* the project
- No baseline, so any result looks like success
- Labels that nobody has checked for consistency
- Offline results that look too good (usually leakage, look-ahead, or unrealistic costs)
- Data you can't legally use for this purpose, or that costs more than the project's budget

## Assumption Audit

For every idea direction, explicitly list assumptions in three categories:

### Must Be True (Dealbreakers)
Assumptions that, if wrong, kill the idea entirely. These need validation before building.

Example: "Users will share their data with us" — if they won't, the entire product doesn't work.

### Should Be True (Important)
Assumptions that significantly impact success but don't kill the idea. You can adjust the approach if these are wrong.

Example: "Users prefer self-serve over talking to a person" — if wrong, you need a different go-to-market, but the core product can still work.

### Might Be True (Nice to Have)
Assumptions about secondary features or optimizations. Don't validate these until the core is proven.

Example: "Users will want to share their results with teammates" — a growth feature, not a core value proposition.

## Decision Framework

When choosing between directions, rank on this matrix:

|                    | High Feasibility | Low Feasibility |
|--------------------|-------------------|-----------------|
| **High Value**     | Do this first     | Worth the risk   |
| **Low Value**      | Only if trivial   | Don't do this    |

Then use differentiation as the tiebreaker between options in the same quadrant.

## MVP Scoping Principles

When defining MVP scope for the chosen direction:

1. **One job, done well.** The MVP should nail exactly one user job. Not three jobs done partially.
2. **The riskiest assumption first.** The MVP's primary purpose is to test the assumption most likely to be wrong.
3. **Time-box, not feature-list.** "What can we build and test in [timeframe]?" is better than "What features do we need?"
4. **The 'Not Doing' list is mandatory.** Explicitly name what you're cutting and why. This prevents scope creep and forces honest prioritization.
5. **If it's not embarrassing, you waited too long.** The first version should feel incomplete to the builder. If it doesn't, you over-built.

## Restating it

> **How might we** build a small set of 2D environments where each one teaches one reinforcement learning (RL) idea (value learning, then continuous control, then two sides learning against each other) so that you understand each idea by building it and watching it learn?

## Four things to push back on now

1. **Environment 2 teaches two new things at once.** Continuous movement plus several fish that each see only what's nearby is both continuous control and multi-agent learning with limited vision. If it doesn't learn, you won't know which part is the problem. I'd start with one fish that sees everything, then add the other fish and the limited vision.
2. **"Both sides learn at once" and "self-play" are different methods.** Two learners updating together is co-evolution. Self-play means training against frozen copies of your opponent's *past* versions. Predator and prey are different kinds of agent, so self-play here would mean a pool of old predators and old prey. Two learners updating together often cycles or collapses. That failure can teach you a lot, but it can also look like "nothing works."
3. **Without baselines, you can't tell whether anything learned.** A snake that scores 4 might be impressive or might be worse than a ten-line rule. Each environment needs a random agent and a simple scripted agent to beat.
4. **Environment 3 is a research-grade problem.** It's fine as the last stage, but it shouldn't decide whether the project counts as a success.

## Variations

1. **As described:** three environments, each with the method you named. It's simple and follows a clear path.
2. **One fish first:** Environment 2 starts with a single fish that sees the whole tank, then grows to several fish with limited vision. This teaches one idea at a time.
3. **Baselines everywhere:** every environment comes with a random agent and a scripted one (a snake that heads straight for the food, a fish that flees the ball, a predator that chases the nearest prey). Learning has to beat both, so "it learned" becomes a fact rather than a feeling.
4. **One tank, two environments:** Environment 3 is Environment 2 plus food and a predator. You build the tank physics once and switch features on per environment. That's less code, and the jump from 2 to 3 becomes small.
5. **Write the algorithms yourself, check against a library:** you implement the value-learning and policy-gradient methods by hand, then compare your learning curves with a standard library's on the same environment. This is the deepest way to learn, and the slowest.
6. **Library methods, your own environments:** use ready-made algorithms and put your effort into environment design, rewards and experiments. This is faster, and you learn more about why agents learn the wrong thing.
7. **Experiments as the output:** each environment comes with a few "break it on purpose" runs, such as removing the target network or making vision shorter, plus a short note on what changed. What you take away is understanding, not only a trained agent.
8. **Swap the methods:** run value learning on a fish that can only move in a few set directions, and policy gradient on Snake. You see why each method suits its environment, not just that it does.

My early leaning is **2 + 3 + 4 + 7**, with 5 or 6 depending on your answer to question 1.
