# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. ## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.

189	### AD-03: Sharadar stocks, actions and tickers as the primary source
190	**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
191	- **Context:** UR-07: the data is "from my Sharadar subscription". UR-26: "use prices, actions and tickers in Stage 1". Checked against DATA-01–DATA-04 and UNIV-01–UNIV-03. Sharadar's site states "Active and delisted coverage extends back to the 90s" and calls the price data "nearly completely free of survivorship bias" ([sharadar.com](https://www.sharadar.com/), read 2026-10-18). The [stocks table docs](https://www.sharadar.com/docs/stocks) (read 2026-10-18) list `close` and `volume` (split adjusted), `closeadj` (adjusted for splits, dividends and spinoffs), `closeunadj` and `lastupdated`. Authentication is an `api_key` query parameter, and paging uses `limit` (default 10000) and `skip`. The [tickers docs](https://www.sharadar.com/docs/tickers) (read 2026-10-18) give `permaticker`, "a unique and unchanging identifier for a security (share class)", plus `category`, `isdelisted`, `firstpricedate` and `lastpricedate`. The [actions docs](https://www.sharadar.com/docs/actions) (read 2026-10-18) cover ticker changes, splits, cash dividends, spinoffs, listings, delistings and acquisitions, but list no action codes.

Stocks are keyed by `permaticker`, never by ticker, so reused and changed tickers stay distinct (BUILD edge cases). Eligibility (UNIV-05) comes from `category` common-stock values. Dollar volume is `close × volume`, both split-adjusted, which equals the unadjusted traded value. Total return is the day-on-day ratio of `closeadj` minus one (AD-07). An update requests rows with `lastupdated` after the previous build's date (BUILD-02). No fundamentals table is read: UR-27, the user hasn't picked a fundamentals source.
193	- **Alternatives:** Nasdaq Data Link's `SHARADAR/SEP` route to the same data: kept as a second adapter behind `PrimarySource` if the user's subscription is served there (PB-01 answers which). CRSP: the reference for delisting returns, but outside the budget (QR-04).
194	- **Consequences:** The vendor keeps only a row's latest value and its `lastupdated` date, with no version history. From the first build on, `qdata` records each correction itself (AD-06). Rows from before the first build are treated as known on their own trading date (Risks).
195	- **Probe:** PB-01 — With the user's subscription: which API route serves it, the exact `category` values for common stocks and the `action` codes, whether delisted common stocks from 2000-01-03 give at least 1,000 names with 63 days of dollar volume on most dates, how `lastupdated` behaves on a correction, and the request limits on a full download.

213	### AD-06: Bitemporal Parquet store with accepted builds
214	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `qdata`
215	- **Context:** DATA-04 (each value carries when it became known, and each correction), BUILD-02 (keep the replaced value), BUILD-04 and LOAD-06 (serve only accepted builds), LOAD-04 (as-of reads), BUILD-05 (resume), QR-02 (≤ 20 GB, 25-year load ≤ 30 s and ≤ 8 GB).
216	- **Decision:** Each stored table is Parquet partitioned by year under `data/store/`. Every row carries `known_from`, `known_to` (null while current) and the `build_id` that wrote it. A correction closes the old row's `known_to` and adds a new row, and nothing is overwritten. Each build stages its batches under `data/builds/<build_id>/`, with one checkpoint per completed batch. It commits by writing a manifest (status `passed`, `failed`, `accepted`, `not_run`) only after validation. A read as of A uses DuckDB over the Parquet files, filtered to `known_from ≤ A < known_to` and to rows from builds whose manifest is `passed` or `accepted`. The point-in-time universe is computed once per build and stored with it.
217	- **Alternatives:** SQLite or Postgres: row stores, slower on the 25-year column scans of QR-02, and Postgres means running a server. ArcticDB: built-in versioning, but snapshot granularity, not per-row known dates, and one more dependency.
218	- **Consequences:** As-of reads are a filter, not a replay. The store only grows. At about 1,000 universe names out of roughly 20,000 listings, the estimate is under 3 GB.
219	- **Probe:** none — no external service; the QR-02 limits are checked by a benchmark task in the build.

221	### AD-07: Returns, identity and missing data rules
222	**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
223	- **Context:** LOAD-01 (close, split-adjusted close, total return), LOAD-05 and BUILD-03 (missing stays missing), UNIV-03 and FCST-06 (final returns through delisting), DATA-03 (no split jumps).
224	- **Decision:** Total return on day t is `closeadj_t / closeadj_prev − 1`, where prev is the stock's previous trading day on the exchange calendar (`exchange_calendars` XNYS). A day with no trade is NaN, and the next return spans from the last traded close with `gap_days` recorded. The final return through delisting is the return to the last traded close. Identity is `permaticker`, and loaded frames carry the ticker as of each date as a column.
225	- **Alternatives:** Filling missing days with zero returns: forbidden by LOAD-05. Computing total returns from actions ourselves: duplicates the vendor's adjustment and is checked instead by XCHK-03.
226	- **Consequences:** Delisting returns after the last trade (a cash payout or a worthless delisting) aren't in Sharadar's prices, so they're missing (Risks).
227	- **Probe:** PB-01 — reused from AD-03: confirms the `closeadj` behaviour and whether the actions table carries delisting values.

244	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `research`
245	- **Context:** HARN-01–HARN-08, and every claim from S2 through S4 (COV-03, FTEST-03, FCST-04, FCST-05, FPORT-02, AGENT-04) runs through it. RESX-04 needs one record format for every stage.
246	- **Decision:** Every module that makes a claim registers a `research.Registration` before computing anything. The harness writes it to `data/runs/<run_id>/registration.json` with its SHA-256, and any later change makes a new run. Walk-forward windows default to 252 estimation days and 21-day holds. Learned models get train, validation and test splits in time order, with a purge of at least the label horizon between them. Strategies read data only through a guarded loader that ends at each period's start. A read inside the final test period before the verdict run raises `FinalPeriodLocked`, and a second run on that period is marked a repeat. Every finished or abandoned run writes its period results, verdict and conclusion. Verdicts come from `research.decide`, the step run with the `null-hypothesis-testing` skill, which gets per-period candidate and baseline results, the registered test, the level and the count of candidates tried under the claim.
247	- **Alternatives:** An experiment tracker (MLflow): it records runs, but doesn't lock registrations or guard reads, and adds a server.
248	- **Consequences:** Stages S3 and S4 add claims without new harness code. The run store is plain files that DuckDB queries for the results explorer.

251	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `research`
252	- **Context:** FACT-01–FACT-04 and DENO-01–DENO-04. UR-25: the user's reference code. RF-01 removes the market mode, but fits on the whole panel, fills gaps with zeros and has no denoising.
253	- **Decision:** `research.factors` adapts RF-01's `pca_factors`, `residualize` and `residual_correlation_check` to fit only inside each window. Stocks with under 80% of the window observed are excluded and listed, never zero-filled, and k ≥ N is an error. Out-of-sample residuals use the previous window's loadings. `research.denoise` fits the noise variance by matching the Marchenko–Pastur density to the window's eigenvalues (scipy `minimize_scalar`), replaces the eigenvalues at or below the edge with their mean, and rescales to a unit diagonal. k is a fixed number or the count above the edge, recorded with the run.
254	- **Alternatives:** scikit-learn `PCA`: it hides the per-window loadings needed for out-of-sample residuals. A shrinkage-only cleaning: not what DENO-01 asks for.
255	- **Consequences:** Synthetic factor panels are the known-answer tests for DENO-03 and FACT-04.

265	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `research`

278	### AD-15: PyTorch sequence forecasters built on the reference windowing
279	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `learn`
280	- **Context:** FCST-01–FCST-07. UR-25: the user's reference code. RF-02 builds static, known and observed inputs, but has no purge and drops rows silently. RF-03 builds forward return and volatility targets, but drops delisted names' final returns.
281	- **Decision:** `learn.windows` adapts RF-02's `WindowSpec` and `build_windows`, with gaps kept as masked steps, unknown categories mapped to a reserved index, and splits by the harness's purged schedule. `learn.targets` adapts RF-03's `make_targets`, counting trading days on the exchange calendar and keeping returns through delisting. Two model families (an LSTM encoder and a small temporal-fusion-transformer-style model) each output return and volatility for horizons 1, 5 and 21 days, with plain PyTorch training loops. Baselines are a zero return and the trailing mean for returns, and trailing 21-day and exponentially weighted volatility for volatility.

# research — Architecture

**Package:** research · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`research` holds the laptop-sized research methods and the harness every stage claims through. Stage S2 removes market factors per window, denoises correlation, estimates three covariances, builds three portfolios plus equal weight, and holds them walk-forward with costs. The verdicts are saved, and the best becomes the stage benchmark. Stage S3 builds features as of each close and tests each feature's information gain with LightGBM. Every claim is registered, run on guarded data views, decided by the `null-hypothesis-testing` skill and written to the run store (AD-10).

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `harness` | Registrations, locking, walk-forward and purged splits, guarded loader views, final-period lock, cost and turnover accounting, verdicts with the `null-hypothesis-testing` skill | HARN-01–HARN-06, HARN-08 | `records`, `qdata` |
| `records` | The run store: run folders, period results, verdicts, conclusions, abandoned runs, paper books; DuckDB queries across runs | HARN-07 | — |

| `compare` | The S2 comparison: estimator × method walk-forward runs, analysis with the `data-analysis` skill, tests, benchmark selection | COV-02, COV-03, PORT-06 | `harness`, `factors`, `covariance`, `portfolios` |

## Interfaces

## Data
- **Run store:** `data/runs/<run_id>/` holds `registration.json` (with `sha256`), `periods.parquet`, `verdict.json`, `conclusion.md`, `status.json` and the artefacts (weights, the denoising record per window). `data/runs/index.parquet` is rebuilt on write for listing.
- **Benchmark and survivors:** `data/runs/benchmarks/S2.json` points to the winning run, method and estimator. `data/runs/survivors/S3.json` lists the surviving feature ids (empty on a negative result).
- **Paper books:** `data/paper/<book_id>/` holds `snapshot.json` and `days.parquet`, written only through `RunStore.append_paper_day`.
- **Defaults:** 252-day estimation, 21-day hold, 10 bp per trade, 5% level after correction (spec Assumptions), with Holm–Bonferroni as the default correction, registered per claim.

## Cross-cutting concerns
- **Reproducibility (HARN-08):** a run records the build id, git revision, every seed and the package versions. Reruns compare periods bit for bit.
- **Point in time:** strategies get `GuardedLoader`, never a raw `qdata.Loader`.
- **Errors:** `FinalPeriodLocked`, `RegistrationLocked`, `Infeasible` (optimiser, handled by keeping previous weights), `ValueError` for k ≥ N.

## Data
- **Extracts:** `data/extracts/<build_id>-<sha>/` holds the universe panel, features and targets in Parquet. This is the only data copied to a rented machine.
