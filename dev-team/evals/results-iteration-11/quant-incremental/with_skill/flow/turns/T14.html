# Decisions

## Making a decision

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Ask about expensive-to-reverse ones. Record each as `AD-NN`, citing an informing reference by `RF-NN`, never its path. Small reversible choices go only in the tech stack table. - It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. A reversed decision collapses to its heading with the title struck, plus one status line: `**Status:** Superseded by AD-NN · date — reason`. Delete its Context, Decision, Alternatives and Consequences. The new decision's Context says what the old one chose and why that no longer holds. Then update every section that cited the old decision (tech stack, contracts, code comments, layout, risks) so that only the superseded line, the new decision and the Changelog mention it.
- **Accepted decisions stay true.** When a new decision changes only part of an Accepted one, revise the old one instead of superseding it. Rewrite the sentences that are no longer true, in its Context as well as its Decision and Consequences, and point to the new decision for the part it now owns. "Two holdouts, one per study" becomes "one holdout per study; AD-26 sets the ranges". The old decision stays Accepted. Supersede only when its choice is reversed as a whole. Readers take an Accepted decision as current, so a stale count in one is a defect.
- **Shared decisions state a rule, not a roster.** A decision that later stages build on (where claims go, which modules may import a library, where runs are stored) is worded to stay true as stages join: "every module that makes a significance claim writes a `Claim`", not "`eda` and `holdout` write claims". Its Context cites the requirements that set the rule, not each one that uses it. The members and their per-stage details (claim families, importers, run folders, time budgets) are listed once, where they live: a component's row and Covers, a contract section, the storage layout, or that stage's own decision. A new stage adds its members there and cites the shared decision. Revise the shared decision only when its rule changes. If one already lists members, move them out the next time a round touches it.

- **Context:** PRICE-01–PRICE-04 and LOAD-02 need raw OHLC, split-adjusted prices and returns derived from the snapshot's own (cleaned) actions. SNAP-05 needs vendor revisions to show as value changes. Sharadar serves OHLC split-adjusted and only `closeunadj` raw (AD-03), and its split-adjusted history is restated after every split.
- **Decision:** raw OHLC is the vendor's split-adjusted value × (`closeunadj` / `close`) for that day. Split-adjusted prices are recomputed from raw prices and the snapshot's cleaned splits. Price return is the change in split-adjusted close; total return adds the ex-date cash dividend, in split-adjusted terms. Vendor-adjusted columns are kept raw only, so the split-consistency check (HLTH-02) can compare them.
- **Alternatives:** Use Sharadar's adjusted columns directly: fails PRICE-04, since a cleaned split would never reach the prices.
- **Consequences:** Derivation is one pure function of raw tables, which makes SNAP-02 a rebuild-and-compare. A day where `close` is zero or missing has no raw OHLC; it becomes a finding, never a fill.

### AD-07: Sharadar `permaticker` is the permanent identity; membership comes from `sp500` changes
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UNIV-01, UNIV-03, UNIV-04 and DATA-02, DATA-04. The `sp500` table names members by ticker at the date of each change. `tickers` gives one `permaticker` per share class; `actions` records ticker changes.
- **Decision:** a security's id is its `permaticker`. A ticker history (ticker, start, end) is built from `tickers` and `actions` ticker changes. Each `sp500` event's ticker resolves to the permaticker holding that ticker on that date. Membership is a set of intervals `[entry, exit)` per permaticker, so a company that leaves and rejoins has two. An event whose ticker resolves to no security, or to two, is a blocking finding.
- **Alternatives:** Ticker as the key: merges reused tickers and splits renamed ones, failing UNIV-03 and UNIV-04. An outside identifier (CUSIP, FIGI): not in the subscription.
- **Consequences:** The first day the universe covers is the first `sp500` date whose full constituent list can be rebuilt. The `current` rows rebuild today's list; walking the changes backward gives every earlier day, and the earliest covered day is where that walk starts. The count check (UNIV-05) catches a walk that goes wrong.

### AD-08: Builds run in a staged run folder with checkpoints, a lock and a progress log
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** BUILD-01, BUILD-02 and BUILD-04–BUILD-06 need a build that resumes without re-downloading, refuses a second run, and reports progress to the app whoever started it. QR-03 needs a refresh in ≤ 15 minutes.
- **Decision:**
  - A build works in `data/runs/<run-id>/`. Each downloaded batch of securities is written there before the next is requested. A rerun on the same day resumes the newest unfinished run.
  - `data/build.lock` holds the running build's id and pid. A second build is refused, naming it; a lock whose pid is gone is reclaimed.
  - Progress events are appended to `data/runs/<run-id>/progress.jsonl` (`qdata.ProgressEvent`). The server tails that file, so builds started from the CLI and from the app look the same.
  - The app's Build button runs the same `qdata build` command as a subprocess (BUILD-06).
  - A refresh requests `stocks` rows with `lastupdated` after the previous snapshot's retrieval date. It replaces the whole history of every security with any changed row, and copies the rest from the previous snapshot.
- **Alternatives:** Build inside the server process: the CLI and app paths diverge, and a server restart kills the build. A job queue (Celery, RQ): a broker the laptop doesn't need.
- **Consequences:** Commit is the last step: an atomic rename of the run's output into `data/snapshots/`. A crash before commit never shows as a usable snapshot. The refresh's correctness rests on `lastupdated` moving on every restatement (PB-01); until that is confirmed, `--full` forces a full download.

### AD-09: FastAPI on 127.0.0.1; HTTP for queries, a WebSocket only for build progress
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-08, UR-20: "HTTP for data queries, WebSocket only for live progress of download/validation runs." This serves EXPL-01–EXPL-07, BUILD-05, BUILD-06, QR-05 and QR-06.
- **Decision:** `qdata serve` runs FastAPI 0.115 under uvicorn 0.30, bound to 127.0.0.1, with a Host and Origin allow-list of localhost. Data queries are JSON over HTTP under `/api/`. `/ws/builds` streams `qdata.ProgressEvent` messages only. The server serves `packages/explorer/dist/` when it exists; in development, Vite's dev server proxies `/api` and `/ws` to it.

- **Consequences:** One port and one command open the app. Every response is a pydantic model, which feeds AD-10.

### AD-10: Typed contract: pydantic models are the source; TypeScript types are generated
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-25: the frontend-backend interface comes "with typed contracts". Two runtimes share no types.
- **Decision:** every HTTP request, response and WebSocket message is a pydantic v2 model in `qdata`. `qdata openapi` writes the OpenAPI 3.1 document, with the WebSocket message schema under `components`, to `packages/qdata/openapi.json`. openapi-typescript 7 generates `packages/explorer/src/api/generated.ts` from it. ### AD-11: Charts drawn with D3 modules, styled to the frontend-design direction
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `explorer`
- **Context:** EXPL-08 asks for a deliberate visual direction, not a default dashboard; QR-05 needs a full-history chart (about 7,000 days, two series plus event marks) in ≤ 1 s.
- **Decision:** `d3-scale`, `d3-shape`, `d3-axis` and `d3-zoom` 7.x draw price lines on a canvas and event marks and axes in SVG, inside React components. The look comes from the mock-ups the user approves under the `frontend-design` skill.
- **Alternatives:** A chart library (ECharts, Recharts): faster to start, but its defaults are the "default dashboard" EXPL-08 rules out. uPlot: fast, and harder to bend to a custom design.
- **Consequences:** More chart code to own; the chart module is small and tested on its scales and marks.

### AD-12: Explanations live outside snapshots, keyed by a finding fingerprint
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** HLTH-07, HLTH-08 and EXPL-07: explanations attach to differences and carry forward, while snapshots never change (SNAP-01).
- **Decision:** explanations are appended to `data/explanations.jsonl`, one `qdata.Explanation` per line. Each is keyed by the finding's fingerprint: check, security, date, field and both values. A snapshot's report joins its findings to explanations when read, so the unexplained count is computed, not stored. A finding whose values changed matches no fingerprint and shows unexplained, with the earlier note found by check, security, date and field.
- **Alternatives:** Write explanations into the snapshot: breaks SNAP-01. SQLite: more than an append-only list of notes needs.
- **Consequences:** The latest line for a fingerprint wins, so a note can be rewritten without deleting history. Unexplained counts change over time while snapshot files do not.

### AD-13: NYSE trading calendar from exchange_calendars
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** DATA-06 allows only US exchange trading days; HLTH-02's missing-day check needs to know which days should exist.
- **Decision:** the `XNYS` calendar from exchange_calendars 4.x defines trading days. Rows on other days are a cleaning removal, recorded (BUILD-03).
- **Alternatives:** The union of dates in the price data: can't see a day the vendor dropped. pandas_market_calendars: similar, and it depends on exchange_calendars anyway.
- **Consequences:** Unscheduled closures (2001-09-11, 2012-10-29, national days of mourning) come from the library; a disagreement shows up as missing-day findings across every member at once.
