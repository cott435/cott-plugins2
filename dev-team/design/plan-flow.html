How a dev-team plan grows

Each planning skill adds one level to the plan and stops until you approve it. By the end, a stage has become pipeline steps, golden cases, a milestone and a task graph that many agents can build at once.

A general view of the process, illustrated with the quant fixture: 2 stages, 3 pipelines, and M1 planned interface-first as in interface-first-design.md §5.3. That design is a Draft; the task kinds, Writes: and the dependency graph table are proposed, not shipped.

What a task must carry

The task is the agent unit: one packet from dt context, one commit, one gate. Its fields are the whole contract with the builder.

Kind · Step
interface, spine, wiring, thicken or system; the step it builds (one step per task, except wiring)
Read
the IDs dt context prints: step, types, symbols, cases, RF-NN
Acceptance
checkboxes a test can decide; a spine passes the sample payload through and returns a schema-valid output
Verify
the exact commands, ending in check.sh gate
Depends on
only unmitigated edges; mitigated ones live in the graph table
Writes
exclusive paths; two tasks with no path between them never share one
Mode
solo, or split: a tester half that starts after the interface, then the implementer

What every other unit must carry

Stage S<n>

idea-refine · roadmap
  • An outcome you agreed, in your words
  • Outline, skills it routes to, references
  • Unsized; status Idea → Specced → Designed → Cut → Done

Requirement CODE-NN

spec-writing · spec.md
  • Observable behavior, no frameworks or files
  • Testable acceptance criteria and edge cases
  • Names the skill that owns a step, and its pass bar

Component and decision AD-NN

architecture-design
  • One responsibility; spec IDs covered; dependencies one way
  • Decision: 2–3 real options, a recommendation, Proposed → Accepted

Contract symbol comp.symbol

architecture-design · contract.md
  • Signature, Invariants, Errors, Used by
  • Owned by the provider
  • Cross-package: fixture cases and a fake under tests/contracts/

Type comp.Type new

architecture-design · contract.md
  • Fields and invariants, as a contract section
  • A sample payload path for each boundary it crosses
  • Written as code only by the milestone's interface task

Pipeline and step PL-NN.fn

pipeline-design · pipelines.md
  • Pipeline: entry, trigger, covers, smoke command
  • Step: one owner, one module, In → Out naming contract types
  • A real spine version, never a mock

Golden case TC-NN

test-planning · tests.md, fixtures
  • A source outside the agent
  • input.json, expected.json behind dt guard
  • A tolerance and its reason

Milestone M<n>

build-planning · roadmap, plan.md
  • Exit criteria; covers and deferred IDs
  • Depends names what it needs from the earlier one
  • Critical path ≤ about 15 tasks

Dependency edge new

build-planning · ## Dependency graph
  • From, To, Kind: data, call, file, code, contract-change, order
  • Mitigated by a named interface, or none: with a reason
  • Only unmitigated edges order tasks

Rule CR-NN

build-setup · CONSTRAINTS.md
  • The rule, how check.sh enforces it, any exception with an expiry
  • Tightening is routine; loosening needs your approval

How the waves get dispatched

  • dt ready lists every task whose Depends on are done, with its Writes:.
  • One worktree agent per ready task; Writes: becomes its allowed paths.
  • Branches merge in plan order. Writes are disjoint, so a conflict means a lint gap and is logged.
  • The check agent runs the gate after each merge; only the orchestrator ticks todo.md.
  • Checkpoints come after waves, not every two or three tasks.

What this does not prove yet

  • The critical path is no shorter in tasks; each task on it is smaller and each wave is wider.
  • Whether that wins wall-clock time after merge cost is what the build eval measures (arms A0–A4, design §9.2).
  • Two levers keep the count down: fold a step's spine into its thicken task, and fold trivial steps into wiring (open question §11.1).
