# Architecture Example: Grow

LeafLab's spec gains a collector that pulls new field photos from the site cameras every day. It's a long-running service deployed on its own, so the Extend round's Grow check fires ("a part runs or deploys on its own"). The skill proposes Grow, and after the user agrees writes `AD-06: split LeafLab into packages`, giving that reason. It proposes three packages:
- `core` — the `Dataset` seam named in the original design, now shared by the collector and the training loop
- `leaflab` — train, batches, augment, loss, and baselines; depends on `core`
- `collector` — the new service; depends on `core`, never on `leaflab`

Component ids become package ids, so existing Covers entries and contract IDs still resolve. Module detail moves to `docs/packages/<package>/architecture.md`. The `## core` group of the old contract moves to `docs/packages/core/contract.md` with its IDs (`core.Dataset`) unchanged; the rest stays in `docs/packages/leaflab/contract.md`. In the code, `src/leaflab/core/` moves out as a folder. The root becomes the system map, with a System pipeline `PL-NN: Collect a day's photos` (a new ID from `dt next-id PL`; `collector` → `core`: `core.write_images`, a new contract section), and the shape changes to `Multi-package`. No existing pipeline crosses the new boundary. Had one, it would keep its own ID as its owning package's segment, and `pipeline-design` Grow would mark it `**Part of:**` the new system pipeline. The seam named in the proof of concept is exactly where the split happens. After approval the skill points to `pipeline-design` Grow.
