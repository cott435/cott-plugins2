# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`), a routed change (`routed_changes`) or the user's words the spec doesn't honour yet (`requests_open`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Stage | `Stage:` line of each new feature: the stage the idea added, or the one it joins |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

## Steps

Run these for the idea only:

1. **Check for conflicts first.** Start with the IDs under *Touches*, then search the rest of the spec for anything else the idea contradicts. List conflicts for the user before writing — "Shared editing changes **EDIT-03** (only the owner can edit). Proposed: owner *or invited editors* can edit."
2. **Map the idea to features** and show the goal → feature mapping, with each feature's stage, before writing.
3. **Surface assumptions, then clarify** (SKILL.md's Asking section).
4. **Write the change** following `references/spec.md` and the rules below.
5. **Set the spec Status back to Draft** and run the Review Gate (SKILL.md, plus the gate steps below), highlighting the changed IDs so the user reviews only what's new.

## Writing rules

1. **Keep IDs stable, keep the text current.** IDs are never renumbered or reused. Old text does not stay in the spec once it stops being true; git keeps it.

   - New behavior in an existing feature → next unused number in that feature (if `SAVE-04` is the highest, add `SAVE-05`, even if `SAVE-02` was removed). `dt status` reports it under `prefixes`.
   - **Widen, don't bolt on.** If an existing requirement already covers this concern for an earlier part of the project, rewrite it to cover the new part too, instead of adding a near-duplicate. 2. **Link back to the idea.** Add `**Source:** [ideas/<slug>.md](ideas/<slug>.md)` under the `Stage:` line of each new feature section, so readers can find the full why.
3. **Update everything it touches, and consolidate.** Summary (rewritten for the whole spec, not appended to), Users, Serves lines. 4. **Add one Changelog row**, one line: the idea file as the source, a short description of the change, and the IDs as ranges in up to three `;`-separated groups: added, then changed, then removed (`FIELD-01–FIELD-12; CNN-03, CORE-04 (changed); CROP-04 (removed)`). - **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Every feature names one stage.** Its `**Stage:**` line holds only the ID of the roadmap stage that first builds it. `dt lint` fails a feature with no stage, or one naming no stage row.
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence and budget limits are `QR-` items ("data costs ≤ $50 a month"), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads it in `docs/requests.md`.

# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

# Idea: Forecasts and forecast-driven portfolios

## In one sentence
This adds neural forecasts of each S&P 500 member's next-month return and volatility, built on the features that passed Stage 3, and long-only portfolios driven by them, so that I find out whether prediction beats Stage 2's classical portfolios out of sample after costs.

## The problem
Stage 2 settles risk without any return forecast, and Stage 3 says which features carry information about residual returns. Neither says whether that information is worth anything once it drives a portfolio and pays for its trading. Sequence models are easy to overfit and easy to flatter: a network can beat a weak baseline while losing to EWMA volatility or to a plain minimum-variance portfolio. I want one honest comparison, on months nothing was tuned on, with costs charged to every portfolio alike.

## Who it's for
Me, with Stage 1's as-of members and returns, Stage 2's covariance estimates and portfolio rules, and Stage 3's verdicts, before anything learns to allocate.

## How it fits
- **Serves:** Goal 1 (as-of members and returns; nothing after each rebalance date is used); Goal 3 (its report opens in the app)
- **Touches:** PORT-02, PORT-03 (rebalance dates, eligible members); PORT-05–PORT-14 (the classical portfolios it must beat, and holding returns); INFO-07, INFO-13 (which features count as inputs); INFO-02, INFO-05 (the 2021-09-30 holdout); FEAT-05 (look-ahead); Out of scope (deep learning, forecasts fed into portfolios, backtests, costs). - **Brief changes:** Constraints (stages decided; compute); Not doing ("Strategy backtests" replaced by "Live or broker trading")
- **Stage:** New S4 (roadmap stage on acceptance)

## Recommended direction
One command runs the study and writes a report that the app opens, like the earlier studies. The study has three parts, all run through one shared simulated backtest.

**Forecasts.** At each Stage 2 month-end rebalance date, a neural sequence model, such as a temporal-fusion-transformer style model or an LSTM, reads each eligible member's recent daily history. It forecasts that member's return and realized volatility over the next month. Its inputs are the features that passed Stage 3's single-feature test on the development months only, plus returns and volume. Return forecasts are compared with simple baselines: a zero forecast, and a ridge model on the same features. Volatility forecasts are compared with EWMA and HAR. RF-02 and RF-03 are prior art for the windows and the labels, with their caveats: a purge gap of the forecast horizon between splits, windows that don't cross membership gaps, and no sector input.

**Portfolios.** The forecasts drive long-only, fully invested portfolios with no leverage, rebalanced monthly. Examples are a mean-variance portfolio using the return forecasts and forecast volatilities, and a risk parity portfolio using forecast volatilities. The best Stage 2 portfolio and 1/N run through the same backtest, with the same costs of 10 bps per side.

**The backtest.** The backtest is simulated only and places no orders anywhere. It charges costs on turnover, holds delisted names as Stage 2 does, and reports after-cost Sharpe ratio, volatility, drawdown and turnover for every portfolio. Stage 5's agents run through the same backtest.

Baselines: zero and ridge return forecasts; EWMA and HAR volatility; the best Stage 2 portfolio and 1/N. Requested models: neural sequence models (UR-113).

# Idea: Allocation agents

**Status:** Accepted · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This adds PPO agents that decide each month how to split money across a handful of portfolio sleeves, trained in Stage 4's simulated backtest, so that I find out whether a learned allocator beats Stage 2's classical portfolios out of sample after costs.

## The problem
Stage 4 tests fixed rules that turn forecasts into weights. A learned allocator could, in principle, learn when to lean on forecasts and when to fall back on minimum variance or cash. Reinforcement learning on market data overfits easily, though. There are only a few hundred monthly decisions, training is noisy from seed to seed, and an agent that trades for free will churn. I want to know whether an agent beats the simple choices, honestly, before I trust one.

## Who it's for
Me, once Stage 4's forecasts, forecast-driven portfolios and backtest exist.

## How it fits
- **Serves:** Goal 1 (as-of data; nothing after each rebalance date is used); Goal 3 (its report opens in the app)
- **Touches:** Stage 4's backtest, forecasts and forecast-driven portfolios; PORT-05–PORT-14 (the classical sleeves); INFO-02, INFO-05 (the 2021-09-30 holdout); Out of scope (backtests, ML in portfolios). Builds on [forecast-portfolios.md](forecast-portfolios.md).
- **Brief changes:** None beyond those in [forecast-portfolios.md](forecast-portfolios.md)
- **Stage:** New S5 (roadmap stage on acceptance)

## Recommended direction
One command trains the agents and writes a report that the app opens.

**What the agent decides.** At each month-end it chooses long-only weights, summing to 1, across about five sleeves: Stage 2 classical portfolios, Stage 4 forecast-driven portfolios, 1/N, and cash. It doesn't pick stocks. Its observations are what is known at that date: Stage 4's forecast summaries, forecast volatilities, and each sleeve's recent returns and drawdown. Its reward is after-cost return, adjusted for risk. It is trained with PPO in Stage 4's simulated backtest, with costs of 10 bps per side on the turnover its choices cause.

**Baselines.** Equal weights across the sleeves, the best single sleeve chosen on the development months, the best Stage 2 portfolio, and 1/N, all through the same backtest and the same costs.

**Verdict.** The agent beats the classical portfolios only if its after-cost Sharpe ratio is higher than both the best Stage 2 portfolio's and 1/N's, beyond chance. Results are reported across several training seeds, not the best seed alone. Training and tuning use months before 2021-09-30. The months from 2021-09-30 onward are scored once.

## Data
The same store and months as Stage 4, plus Stage 4's forecasts and sleeve returns. No outside data. Small networks that train on the laptop's CPU. Built and tested on synthetic sleeves first, including one with a planted, learnable regime and one with none. Agent-versus-baseline claims use the `null-hypothesis-testing` skill; training curves and seed spread use the `data-analysis` skill. Requested method: PPO (UR-117).

## Alternatives considered
- A stock-level agent across about 500 names: a huge action space and few decisions, the likeliest to overfit.
- An agent that only scales between one portfolio and cash: simpler, kept as a fallback if the sleeve agent can't learn.
- Other algorithms (DQN, SAC): PPO was asked for, and sleeve weights suit it.

## What success looks like
- One report compares the agent, across seeds, with every baseline after costs, with a verdict.
- The agent finds the planted regime on synthetic sleeves and gains nothing where none exists.
- The 2021-09-30-onward months are scored once.

## What we're betting on
- About 250 development months are enough for PPO to learn a sleeve allocation better than equal weights.
- The sleeves' returns differ enough over time for allocation to matter.
- Stage 4's holdout results don't steer which sleeves the agent gets. The sleeves are fixed before S5 is tuned.

## Not doing
- Stock-level agents.
- Live orders or a broker's paper account.
- Shorting or leverage across sleeves.
- Searches over settings that touch the 2021-09-30-onward months.

## Open questions
- The exact sleeves, and the observation set.
- The reward: after-cost return less a risk penalty, or a differential Sharpe ratio.
- How many seeds, and how the seed spread enters the test.
- Whether synthetic or bootstrapped histories may be used to give PPO more episodes, and how that is kept free of holdout data.

212	### Return structure (`STRUC`)
213	**Serves:** Goal 1
214	**Stage:** S2
215	**Source:** [ideas/return-structure-portfolios.md](ideas/return-structure-portfolios.md)
216	**Behavior:** At every month-end rebalance date of the portfolio study (PORT-02), the study looks at how that day's members moved together over the 252 trading days ending that day: how many eigenvalues of their correlation matrix stand above the level pure noise would reach, how much of the variance the market factor carries, and how much correlation is left once the dominant components are removed. 217	
218	**Requirements**
219	- **STRUC-01** The structure analysis is run with the `data-analysis` skill on every rebalance date's window: the eligible members of PORT-03 over the 252 trading days ending that day. 222	  - Given a synthetic window of 252 days and 400 stocks with independent returns, when analysed, then at most 1 eigenvalue is above the edge.
223	  - Given a synthetic window of 252 days and 400 stocks driven by one common factor that explains 40% of each stock's variance, when analysed, then exactly 1 eigenvalue is above the edge.
224	- **STRUC-03** For each window, the market factor's share of variance is the largest eigenvalue of the correlation matrix divided by the number of stocks, reported as a series over time.
225	  - Given the one-factor synthetic window of STRUC-02, when analysed, then the share is 0.40 ± 0.03.
226	- **STRUC-04** For each window, the principal components above the noise edge (at least 1) are removed from every stock's returns, and the mean absolute pairwise correlation of what remains is reported next to the raw value, with the number of components removed.
227	  - Given the one-factor synthetic window of STRUC-02, when analysed, then 1 component is removed, the raw mean absolute correlation is ≥ 0.35, and the residual one is ≤ 0.08.
228	- **STRUC-05** Each window's results use only the returns inside that window.
229	  - Given a return changed on a day after rebalance date R, when the study is run again, then every structure result for R and earlier windows is identical.
230	
231	**Edge cases & errors**
232	- A window with no eigenvalue above the edge → 1 component is still removed, and the window is marked as showing no structure above noise.

234	### Covariance and portfolio study (`PORT`)
235	**Serves:** Goal 1, Goal 3
236	**Stage:** S2
237	**Source:** [ideas/return-structure-portfolios.md](ideas/return-structure-portfolios.md)
238	**Behavior:** The researcher runs one command. At every month-end since 1998, it estimates the covariance of that day's members four ways, builds three long-only portfolios from each estimate plus an equal-weight portfolio, and holds them through the next month. It then ranks the estimates for each portfolio rule by the realized variance of the following months, reports turnover, and tests whether each rule's winner beats the sample estimate. The report, with the structure part (STRUC), opens in the app.
239	
240	**Requirements**
241	- **PORT-01** One command runs the whole study and writes one report with three parts: structure, league table and significance.
242	  - Given stored data from 1998-01-02, when the command is run, then one report is written that has all three parts.
243	- **PORT-02** Rebalance dates are the last trading day of each month, from the first month-end on which 252 trading days have passed since 1998-01-02 to the last month-end whose following month is complete.
244	  - Given data from 1998-01-02 to 2026-09-30, when the study runs, then every rebalance date is a month's last trading day, the first is the first month-end with 252 trading days behind it, and the last is 2026-08-31.
245	- **PORT-03** At each rebalance date, the portfolios hold that day's members (UNIV-01) that have 252 trading days of returns ending that day; members with fewer are left out that month, and the number left out is reported for every rebalance date.
246	  - Given a stock added to the index with 100 trading days of history on rebalance date R, when the study runs, then the stock is in no portfolio formed on R, and R's left-out count includes it.
247	- **PORT-04** Every estimate and every weight formed on rebalance date R uses no return from after R.
248	  - Given a return changed on a day after R, when the study is run again, then every estimate and weight formed on R or earlier is identical.
249	- **PORT-05** The sample estimate is the sample covariance of the window's daily returns.
250	  - Given a synthetic window, when estimated, then it equals the sample covariance of those returns.
251	- **PORT-06** The shrinkage estimate pulls the sample covariance toward a constant-correlation target (each stock's own sample variance, and one correlation shared by every pair equal to the window's average sample correlation), by an intensity estimated from the window and reported for every rebalance date.
252	  - Given any window, when estimated, then the result equals (1 − δ) × sample + δ × target with 0 ≤ δ ≤ 1, and δ is reported.
253	- **PORT-07** The denoised estimate replaces the correlation matrix's eigenvalues below the noise edge of STRUC-02 with their average, keeps those above it, and rescales to each stock's sample variance.
254	  - Given any window, when estimated, then the eigenvalues above the edge are unchanged, those below it are all equal, the matrix's trace is unchanged, and its diagonal equals the sample variances.
255	- **PORT-08** The factor-model estimate is built from the principal components above the noise edge (at least 1) plus each stock's own residual variance, and the number of components is reported for every rebalance date.
256	  - Given the one-factor synthetic window of STRUC-02, when estimated, then 1 component is used and the diagonal equals the sample variances.
257	- **PORT-09** Every portfolio is long-only and fully invested: no weight is negative and the weights sum to 1, with no cap on any one stock and no transaction costs.
258	  - Given any portfolio formed in the study, when its weights are read, then each is ≥ 0 and they sum to 1 within 1e-9.
259	- **PORT-10** The minimum-variance rule picks the weights with the lowest portfolio variance under the estimate.
260	  - Given 2 uncorrelated stocks with variances 1 and 4, when the rule runs, then the weights are 0.8 and 0.2.
261	- **PORT-11** The risk-parity rule picks the weights for which every stock contributes equally to the portfolio variance under the estimate.
262	  - Given 2 uncorrelated stocks with volatilities 10% and 20%, when the rule runs, then the weights are 2/3 and 1/3.
263	- **PORT-12** The hierarchical risk-parity rule clusters the stocks into a tree by correlation, then splits the weight down the tree, giving each branch of a split a share inversely proportional to its variance.
264	  - Given 2 uncorrelated stocks with variances 1 and 4, when the rule runs, then the weights are 0.8 and 0.2.
265	  - Given 4 stocks in 2 pairs, each pair correlated at 0.9 and the pairs uncorrelated, with equal variances, when the rule runs, then each pair gets 0.5 of the weight.
266	- **PORT-13** An equal-weight portfolio of each month's stocks is formed at every rebalance date and shown next to every rule's ranking as the floor.
267	  - Given 400 eligible stocks on R, when the study runs, then the equal-weight portfolio gives each 1/400.
268	- **PORT-14** Between rebalance dates, weights drift with prices. A stock that stops trading during the month counts its return through its last trading day, that day included, and its weight is then held as cash at 0% for the rest of the month.
269	  - Given a stock with 5% of the portfolio whose last trading day is the 10th trading day of the holding month, when the month's returns are computed, then its return counts through day 10, and from day 11 its drifted weight earns 0%.
270	- **PORT-15** A portfolio's realized variance for a holding month is the variance of its daily returns within that month, annualized ×252.
271	  - Given 20 daily portfolio returns alternating +1% and −1%, when realized variance is computed, then it is 0.0001 × 252 = 0.0252.
272	- **PORT-16** For each rule, the four estimates are ranked by mean realized variance over all holding months, lowest first, with the equal-weight portfolio shown alongside.
273	  - Given a completed study, when the league table is read, then each of the 3 rules lists 4 estimates in increasing mean realized variance, plus the equal-weight value.
274	- **PORT-17** Turnover is half the sum of absolute weight changes from the drifted weights to the new weights at each rebalance date, averaged over all rebalance dates, and reported as a number for every estimate and rule without affecting the ranking.
275	  - Given drifted weights (0.6, 0.4) and new weights (0.5, 0.5), when turnover is computed, then it is 0.1.
276	- **PORT-18** For each rule, the winner is tested against the sample estimate with the `null-hypothesis-testing` skill, on the paired monthly realized variances: the null is that the winner's realized variance is no lower. It passes only if the null is rejected one-sided at 5% after correction across the 3 rules. The report states, for each rule, whether the null is rejected and the corrected p-value.
277	  - Given a completed study, when the significance part is read, then each of the 3 rules shows its winner, the corrected p-value and whether the null is rejected.
278	  - Given a rule whose winner is the sample estimate, when the significance part is read, then that rule says no test is needed.
279	- **PORT-19** The study report can be opened in the app.
280	  - Given a completed study, when the researcher opens it in the app, then its three parts' tables and charts are shown.
281	- **PORT-20** The full study runs in ≤ 1 hour.
282	  - Timed on the researcher's machine on the full history since 1998-01-02.
283	
284	**Edge cases & errors**
285	- Study started with no stored data, or fewer than 252 trading days stored → refused with a message to run a refresh first.
286	- A member with a gap day (RET-07) in its 252-day window → counted as having fewer than 252 days of returns, so left out that month (PORT-03).
287	- A rule that finds no weights for an estimate in a month → the failure is reported, and that month is left out of every estimate's mean for that rule, so the comparison stays paired.
288	- Fewer than 2 eligible stocks on a rebalance date → no portfolios are formed that month, and the report says why.
