## Overview
`ingest` downloads S&P 500 history from Sharadar, cross-checks it against EODHD, and writes immutable numbered snapshots to a local data store. ### AD-01: Multi-package workspace with enforced import rules
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The app runs in a different runtime from the research code. S4 brings a heavy neural-network stack that the data and app layers shouldn't carry. Leakage (LOAD-05, HOLD-01–HOLD-05) is easier to prevent when research code can't reach the store writer.
- **Decision:** Five Python packages in one uv workspace plus a pnpm `web` package. The dependency rules above are checked by `import-linter` and ruff in the check script and pre-commit.
- **Alternatives:** One Python package plus `web` — less ceremony, but no tool can enforce the writer and model boundaries. A package per stage — splits the backtest away from the stages that share it.
- **Consequences:** Cross-package symbols need contract sections and frozen fixtures. One lockfile keeps versions aligned.

### AD-02: Python 3.12 backend, TypeScript and React frontend
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The brief fixes a TypeScript and React app over a Python backend. The research libraries are Python.
- **Decision:** Python 3.12 for all Python packages (`requires-python = ">=3.12,<3.13"`). TypeScript 5.6 with React 18 and Vite 5 for `web`.
- **Alternatives:** Python 3.13 — PyTorch, LightGBM and cvxpy wheels lag on new versions.
- **Consequences:** Types can't be shared directly across the two runtimes, so the boundary runs through JSON Schema (AD-07).

### AD-03: Immutable Parquet snapshots plus SQLite records
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`, `ingest`, `research`
- **Context:** INGST-04 needs numbered snapshots that later runs can name. INGST-06 keeps raw data. QR-02–QR-04 set speed targets on a laptop. Runs, unlocks and claims need small transactional records.
- **Decision:** Each snapshot is a folder of Parquet tables plus a manifest, written once and never modified; queries go through DuckDB. Records live in SQLite: `meta.sqlite` for runs, the lock and pre-registrations, and `results.sqlite` for scoreboard entries, claims and the feature catalogue. A new snapshot copies unchanged partitions by hard link.
- **Alternatives:** One DuckDB database for everything — single-writer locking clashes with a long ingest run while the app reads. Postgres — a server to run for one user.
- **Consequences:** Snapshots cost disk space (about 1 GB each, estimated). Old snapshots can be pruned only when no scoreboard entry names them.

  - `tickers` gives `permaticker`, a permanent per-security identifier. Reused tickers get a number appended for the delisted company (https://sharadar.com/docs/tickers, https://sharadar.com/docs/faqs).
  - `sp500` lists additions and removals from 1998 and is included in the Prices plan (https://sharadar.com/docs/sp500).
  - Full history comes as a bulk zip (https://sharadar.com/docs/getting-started).
  - Together these meet DATA-01–DATA-04.
- **Decision:** `ingest` fetches the four tables from api.sharadar.com: a bulk zip for full builds, date-filtered queries for updates. Records are keyed by `permaticker`. The ticker is display-only.
- **Alternatives:** Nasdaq Data Link — not the researcher's subscription, and a sharadar.com key doesn't work there.
- **Consequences:** No delisting return is provided, so AD-06 derives one. `sp500` rows carry tickers, which must be mapped to `permaticker` as of each event's date.
- **Probe:** PB-01 — on the researcher's key, do `sp500` (from 2005), delisted members' prices, delisting action types, acquisition values and the bulk export behave as documented? Does `sp500` store tickers as they were at the time or as renamed? Does a full bulk build fit QR-02?

### AD-05: EODHD as the cross-check source, Tiingo as fallback
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `ingest`
- **Context:** DATA-06 needs an independent daily source covering ≥ 50% of member-days since 2010. VALID-04 and VALID-05 compare returns (1 bp) and unadjusted closes (0.5%). QR-01 caps extra spend at $50/month. Docs read 2026-10-17:
  - EODHD Historian costs $19.99/month with 100,000 calls/day (https://eodhd.com/pricing).
  - Its `close` is as traded, and splits and dividends come from separate endpoints (https://eodhd.com/financial-apis/api-for-historical-data-and-volumes).
  - Delisted US tickers are listed, but those delisted before 2018 have prices without splits or dividends (https://eodhd.com/financial-apis/delisted-stock-companies-data-2).
- **Decision:**
  - EODHD Historian is the second source.
  - Each source's returns are rebuilt the same way (raw close, splits, dividends) before they are compared; vendor-adjusted closes are never compared directly.
  - Names whose splits or dividends are missing in EODHD are checked on unadjusted closes only and listed as "returns not cross-checkable".
  - Tiingo Power ($30/month; raw close, `divCash`, `splitFactor`: https://www.tiingo.com/documentation/end-of-day) replaces EODHD if PB-02 fails.
- **Alternatives:** Tiingo first — cleaner fields, but its docs don't state delisted coverage. Alpha Vantage at $49.99 — at the budget limit, and delisted price history isn't documented. Massive — 10 years of history costs $79. yfinance — unofficial, with no delisted names.
- **Consequences:** A symbol map from `permaticker` to EODHD codes is part of each snapshot. Cross-check coverage is reported per year (VALID-07).
- **Probe:** PB-02 — on the researcher's EODHD key, what share of S&P 500 member-days since 2010 can be matched, how are renamed and reused symbols handled, do 2010-17 delisted names have splits and dividends, and do the terms allow local storage for personal cross-checks?

### AD-06: Total returns built from unadjusted prices and actions
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`, `ingest`
- **Context:** LOAD-02 requires dividends on their ex-date and split-neutral returns. LOAD-03 requires that a later action never changes a past return. Sharadar's `closeadj` is adjusted backward from today (https://sharadar.com/docs/stocks), so it changes whenever a new action arrives. LOAD-04 needs delisting returns, which Sharadar doesn't report. RF-03's labels drop each ticker's last rows and lose them.
- **Decision:**
  - The daily return is r_t = (closeunadj_t × split_t + div_t) / closeunadj_{t−1} − 1, where split_t is the ratio ex-dated t and div_t the cash dividend ex-dated t.
  - On a delisting, the final return uses acquisition cash plus stock value when Sharadar reports them. Otherwise it uses `DelistingDefaults`: −30% for regulatory, bankruptcy or voluntary delistings and 0% for acquisitions and mergers, flagged as assumed.
  - As a check, `ingest` compares these returns with returns implied by `closeadj`.
- **Alternatives:** Use `closeadj` returns directly — simple, but breaks LOAD-03 and hides how dividends were applied.
- **Consequences:** Returns depend on the quality of `actions`, which VALID-03 and the cross-check guard. Mapping action types to the delisting defaults is a table in `data`.

### AD-07: Typed app contract: pydantic → JSON Schema → TypeScript
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `server`, `web`
- **Context:**
  - APP-06 needs one versioned contract, with bad messages rejected.
  - RUNS-02 and RUNS-03 need pushed updates every 2 seconds or faster.
  - RUNS-04 needs a run to outlive the app.
  - QR-06 needs local-only access.
- **Decision:**
  - `server` is FastAPI. Every request, response and WebSocket message is a pydantic model, exported to `schemas/` with a contract version.
  - `web` generates TypeScript types from those schemas and validates every incoming message with Ajv before rendering it.
  - Runs execute in a worker process started by `ingest`, which writes events to `meta.sqlite`. The `server` WebSocket tails those events, so closing the browser or restarting the server doesn't stop a run.
  - uvicorn binds to 127.0.0.1.
- **Alternatives:** OpenAPI client generators — they cover HTTP but not WebSocket messages. Server-sent events — simpler, but WebSocket is a fixed choice in the brief and also suits cancelling runs.
- **Consequences:** A CI check fails when the exported schemas differ from the committed ones. A schema change bumps the contract version.

### AD-08: Covariance and portfolio construction
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `research`
- **Context:**
  - COV-01–COV-03 need sample, shrinkage and denoised estimates on trailing windows.
  - FACT-01–FACT-03 fit components on trailing windows only. RF-01 fits on the full panel and mixes standardised and raw units.
  - PORT-01–PORT-03 need long-only, 5%-capped minimum-variance, risk parity and hierarchical risk parity portfolios.
- **Decision:**
  - Every estimator takes an explicit window end.
  - Shrinkage is Ledoit–Wolf (scikit-learn).
  - Denoising is written by hand: eigenvalue clipping at the Marchenko–Pastur edge, fitted on the correlation matrix and preserving the trace.
  - Factor removal is written by hand on the trailing window, with betas regressed in raw-return units.
  - Minimum-variance and capped risk parity are solved with cvxpy and Clarabel. Hierarchical risk parity is written by hand on SciPy clustering, with the cap applied by iterative redistribution.
- **Alternatives:** PyPortfolioOpt or riskfolio-lib — fast to start, but their window handling and caps are harder to audit against SCORE-01 and COV-02. A hand-written quadratic programming solver — not worth it.
- **Consequences:** The denoising and hierarchical risk parity code are ours to test, with planted-factor and two-block golden cases (COV-02, PORT-03).

### AD-09: Held-out lock enforced in the loader
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** HOLD-01–HOLD-05 and LOAD-05 need a lock that analysis code can't bypass by accident, plus pre-registration before any unlock.
- **Decision:**
  - The lock start is written once to `meta.sqlite` when the first validated snapshot is locked.
  - Every `data` load past it raises `HeldOutError` unless given a `data.Unlock`, which only `data.unlock` creates, after a pre-registration exists for that stage.
  - Unlocks, reasons and pre-registrations are append-only rows.
  - The scoreboard marks entries made under a second unlock "re-opened", and entries outside the pre-registration "exploratory".
- **Alternatives:** Hold the held-out years in a separate file — easy to load by mistake, and gives no audit trail.
- **Consequences:** Every research entry point takes an optional `Unlock` argument. Tests use a fake lock date on synthetic data.

### AD-10: Feature information gain measured with gradient boosting on purged walk-forward folds
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `research`
- **Context:**
  - SIG-01–SIG-05 need out-of-sample information gain on residual returns, with an embargo at least as long as the horizon and an FDR of 10% over the whole catalogue. RF-02's split has no embargo and fits encoders on all data.
  - The test procedure belongs to the `null-hypothesis-testing` skill.
- **Decision:**
  - For each feature, LightGBM is trained on purged walk-forward folds with a base feature set, then with the base set plus the feature.
  - Information gain is the per-date difference in out-of-sample rank correlation with the residual target.
  - The `null-hypothesis-testing` skill sets the null distribution and test. Its claims are recorded in the `features` claim family and corrected over the whole catalogue.
- **Alternatives:** Linear models only — fast, but they miss non-linear effects, which is the point of using ML. Mutual-information estimates without a model — noisy at daily cross-section sizes.
- **Consequences:** SIG runs are CPU-heavy. LightGBM runs single-threaded, with seeds, so results can be reproduced.

### AD-11: Neural forecasters in PyTorch
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `models`
- **Context:**
  - FCST-01–FCST-06 need return and volatility forecasts at 1, 5 and 21 days, compared with simple baselines across ≥ 5 seeds.
  - QR-09 allows a laptop or a rented GPU session costing ≤ $5.
  - RF-02 shows the static, known and observed split for a temporal-fusion-style model. Its caveats are: no embargo, vocabularies fitted on the full panel, alignment that only holds for 1-day targets, and windows that ignore date gaps.
- **Decision:**
  - PyTorch 2.5, with two forecaster families: an LSTM and a temporal-fusion-style model.
  - Both are built on windows indexed by trading day, with an embargo of at least the horizon, encoders fitted on training data only, and an "unknown" category slot.
  - Laptop CPU by default, with CUDA when available.
- **Alternatives:** Gradient boosting forecasters only — a strong baseline, but the brief asks for sequence models. JAX — less tooling for this.
- **Consequences:** A training run must fit in one ≤ $5 GPU session. The run record logs device, wall time and estimated cost.

### AD-12: PPO agents on a Gymnasium wrapper of the backtest simulator
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `models`, `research`
- **Context:** AGENT-01 needs the training environment to match the backtest to 1e-10. AGENT-02 needs observations that use only data through the previous close. SCORE-01 sets the portfolio rules.
- **Decision:**
  - `research.Simulator` is the single implementation of rebalancing, costs, drift and delistings. `research.run_backtest` and the agent environment both call it.
  - Agents are Stable-Baselines3 PPO on a Gymnasium environment.
  - Actions are scores mapped to long-only weights that are projected under the 5% cap before reaching the simulator.
- **Alternatives:** A separate vectorised environment — faster, but two implementations would drift apart. Hand-written PPO — more code to get wrong, for no research gain.
- **Consequences:** Simulator speed limits training. The simulator works on weekly steps over about 500 names, which keeps training cheap.

  - (b) Train on the laptop only.

# data — Architecture

**Package:** data · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
The bottom of the stack. `data` defines the shared identifiers and calendar, and reads immutable snapshots from the store. It serves point-in-time universes, prices and total returns, and owns the held-out lock and pre-registrations. Its only writer API, `SnapshotWriter`, is reserved for `ingest` by import rules (AD-01).

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `types` | `SecurityId`, `SnapshotRef`, `Provenance`, `DelistingDefaults`, frame schemas | DATA-04, LOAD-06 | — |
| `calendar` | XNYS trading days, holidays and early closes from 2005 | DATA-05 | `types` |
| `store` | Snapshot folders, manifests, `SnapshotWriter`, validation-status lookup | QR-05 | `types` |
| `loader` | Point-in-time universe, prices, total returns and delisting returns | LOAD-01–LOAD-04, LOAD-06, DATA-02 | `store`, `calendar`, `lock` |
| `lock` | Lock start, pre-registrations, unlocks, append-only log | HOLD-01–HOLD-05, LOAD-05 | `store` |

## Interfaces
See [contract.md](contract.md).

## Data
- Reads `snapshots/<n>/` (Parquet tables: `securities`, `prices`, `actions`, `membership`, `returns`, `manifest.json`) and the `lock`, `preregistrations` and `unlocks` tables in `meta.sqlite` (AD-03).
- `returns` is computed once per snapshot by `SnapshotWriter.finalize` (AD-06) and is never recomputed when read.
- A snapshot whose validation report has unexplained items loads only with `allow_unvalidated=True`, which only `ingest`'s validation and the app's report views pass (VALID-06).

## Cross-cutting concerns
- **Look-ahead:** every loader call takes an explicit date range. The lock check runs before any file is read.
- **Errors:** `SnapshotNotFound`, `SnapshotNotValidated`, `HeldOutError`, `PreregistrationMissing`.

packages/data/tests/

# ingest — Architecture

**Package:** ingest · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`ingest` turns vendor data into validated snapshots. A run (full build, update, or validation) executes in its own worker process. It fetches from Sharadar (AD-04) and EODHD (AD-05), keeps raw files, cleans and maps them to `SecurityId`, and writes a snapshot through `data.SnapshotWriter`. It then validates and cross-checks the snapshot. Progress and log events are appended to `meta.sqlite` for `server` to stream.

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `sources` | `Source` protocol; Sharadar and EODHD clients (Tiingo later behind the same protocol); retry with back-off; credential checks | DATA-01, DATA-03, DATA-06, QR-01, QR-07 | — |
| `raw` | Stores fetched files unchanged under `raw/<source>/<fetch-id>/`; resume checkpoints | INGST-05, INGST-06 | `sources` |
| `clean` | Maps rows to `SecurityId` and as-of tickers; builds the security, price, action and membership tables; detects source revisions | INGST-01–INGST-03 | `raw`, `data` |
| `snapshot` | Writes snapshots through `data.SnapshotWriter`; sets the lock on the first validated snapshot | INGST-04 | `clean`, `data` |
| `validate` | Consistency, coverage, ±40% flags, cross-check of returns and closes, item statuses, report | VALID-01–VALID-07 | `data`, `sources` |
| `runs` | Worker processes, single-active-run guard, cancel, event log, resume | RUNS-04–RUNS-06, QR-02, QR-03 | all above |

## Interfaces
See [contract.md](contract.md).

## Data
- **Full build:** the Sharadar bulk zip for `tickers`, `actions`, `sp500` and `stocks`, filtered to the securities that were ever members since 2005. Then EODHD per symbol, for the cross-check.
- **Update:** Sharadar queries filtered to `lastupdated` after the previous fetch, which catches revisions (INGST-03). Then EODHD for the new days.
- **Explanations:** item statuses and explanations live in `meta.sqlite`, keyed by item fingerprint, so an explanation carries over to the next snapshot when the item recurs.

## Cross-cutting concerns
- **Credentials:** `SHARADAR_API_KEY` and `EODHD_API_KEY` come from the environment. A missing or rejected key stops the run before any fetch, with `CredentialError`. Keys are redacted from every log line.
- **Speed:** bulk download plus vectorised cleaning, with a QR-02 budget of 2 h. An update touches only new days, with a QR-03 budget of 5 min.

## Project layout

packages/ingest/src/qrp_ingest/   → sources/ raw/ clean/ snapshot/ validate/ runs/
packages/ingest/tests/

# research — Architecture

**Package:** research · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
Everything between the loader and the neural models. `eda` characterises each snapshot. `backtest` is the single implementation of the portfolio rules and costs, and its scoreboard records every result. `claims` records every significance claim and its correction. `risk` holds return structure and classical portfolios (S2). `features` holds the catalogue, feature values, targets and information-gain tests (S3). Each component may be split into its own package later. The seams are the contract groups below.

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|

# models — Architecture

**Package:** models · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
S4's package, and the only one with PyTorch, Stable-Baselines3 and Gymnasium. It trains forecasters on residual targets and the features that passed S3, and compares them with simple baselines. It builds forecast-driven portfolios and PPO agents as `research.Strategy` objects running on `research.Simulator`. Finally it produces the pre-registered held-out verdict against the S2 portfolios. Nothing imports `models`.

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `windows` | Trading-day-indexed encoder/decoder windows; purged splits with an embargo of at least the horizon; encoders fitted on training only, with an unknown slot | FCST-01, FCST-04 | `research`, `data` |
| `forecast` | LSTM and temporal-fusion-style forecasters for returns and volatility at 1, 5 and 21 days; ≥ 5 seeds; device and cost logged | FCST-06, QR-09 | `windows` |
| `baselines` | Zero and trailing-mean return forecasts; trailing and exponentially weighted volatility forecasts | FCST-02, FCST-03 | `research` |
| `evaluate` | Forecast losses and rank correlations against baselines; claims in the `forecasters` family via the `null-hypothesis-testing` skill | FCST-02, FCST-03, FCST-05 | `forecast`, `baselines`, `research` |
| `fport` | Forecast-driven strategies: forecasts from passing forecasters plus a `research` covariance estimate, solved under the shared rules | FPORT-01, FPORT-02 | `evaluate`, `research` |
| `agents` | Gymnasium environment over `research.Simulator`; PPO training on development data only; ≥ 5 seeds; agent strategies | AGENT-01–AGENT-05 | `research`, `data` |
| `verdict` | S4 pre-registration, unlock, held-out entries, `verdict` claims via the `null-hypothesis-testing` skill, verdict report | VERD-01–VERD-03 | `fport`, `agents`, `research`, `data` |

## Interfaces
See [contract.md](contract.md).

## Data
- **Inputs:** `data.load_returns`, then `research.residual_returns`, `research.make_targets`, and `research.compute_features` for `research.surviving_features()` only.
- **Training windows (RF-02):** the static, known and observed split, with three fixes:
  - purged splits with an embargo,
  - vocabularies fitted on the training period only,
  - targets aligned by trading day for every horizon.
- **Labels (RF-03):** forward return and volatility definitions, with delisting returns kept and the cross-section taken from the point-in-time universe.
- **Run outputs:** checkpoints and run records go under `results/runs/<run-id>/`.

## Cross-cutting concerns
- **Reproducibility:** seeds for torch, NumPy and the environment, plus deterministic torch algorithms. Medians and ranges are reported over ≥ 5 seeds.
- **GPU (QR-09):** one training job is sized to fit a ≤ $5 rented session; the run record logs device, wall time and estimated cost. What may leave the laptop is open (see the system Risks).

# web — Architecture

**Package:** web · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
A React 18 single-page app, built with Vite and served locally, that talks only to `server`. TypeScript types are generated from `schemas/`, and every response and WebSocket message is validated with Ajv before rendering (AD-07). Visual direction follows the `frontend-design` skill; charts follow the `dataviz` skill.

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `api` | Generated types, fetch and WebSocket clients, Ajv validation, contract-error surface, backend-down retry | APP-06 | `server` schemas |
| `security` | Security search and chart, with corporate actions, memberships and delisting marked | APP-01 | `api` |
| `universe` | Date picker and that day's members with returns | APP-02 | `api` |
| `validation` | Validation report with a status filter | APP-03 | `api` |
| `eda` | Exploratory analysis charts per snapshot | APP-04 | `api` |
| `scoreboard` | Scoreboard table and side-by-side comparison | APP-05 | `api` |
| `runs` | Start and cancel runs; live progress, ETA, error count and log; reconnect with replay | RUNS-01–RUNS-06 | `api` |

## Interfaces
See [contract.md](contract.md).

## Cross-cutting concerns
- **State:** server state goes through TanStack Query. There is no client-side data store, and nothing is written to `localStorage` except UI preferences.
- **Held-out:** held-out days are never shown; views label the gap "held out".
- **Testing:** Vitest for components against the frozen `tests/contracts/server.*` fixtures; one Playwright smoke run against a server on a synthetic snapshot.

## Project layout

packages/web/src/   → api/ security/ universe/ validation/ eda/ scoreboard/ runs/
packages/web/tests/

The architecture is drafted. `dt status` shows every one of the 103 spec requirements has a home. The lint is clean apart from the `dataviz` warning you chose to leave.

Before you approve, one thing needs your decision: **rented GPUs conflict with the spec's no-data-leaves-the-laptop rule (QR-08).** Training on a rented GPU means sending data derived from Sharadar off your laptop, which QR-08 forbids. Your options:
- **(a)** Amend QR-08 to allow anonymised training arrays on a rented GPU that is wiped after each session. The arrays would hold features and targets only, with no prices or tickers. This is my recommendation.
- **(b)** Train on the laptop only.

Either way it's a spec change, made in its own round.

- **Per-package docs:** `docs/packages/{data,ingest,research,models,server,web}/` each have an `architecture.md` and a `contract.md`. Every type that crosses a package boundary names the test fixture cases it needs.

## The 12 decisions
| ID | Decision |
|---|---|
| AD-01 | 6 packages in a uv workspace, with dependency rules enforced by `import-linter` |
| AD-02 | Python 3.12; TypeScript 5.6, React 18 and Vite |
| AD-03 | Snapshots are immutable Parquet folders queried with DuckDB; run and lock records in `meta.sqlite`, research results in `results.sqlite` |
| AD-04 | Sharadar's own API: `stocks`, `actions`, `tickers`, `sp500`. Bulk zip for full builds; stocks keyed by Sharadar's permanent ID (`permaticker`) |
| AD-05 | EODHD Historian ($19.99/month) for the cross-check, Tiingo Power as fallback. Returns are rebuilt from raw prices on both sides, never from vendor-adjusted closes |
| AD-06 | Total returns built from unadjusted closes, splits and dividends. Sharadar's `closeadj` is not used, because it changes history. Delisting returns come from acquisition values when reported, otherwise the −30%/0% defaults |
| AD-07 | Typed app contract: pydantic models → JSON Schema → generated TypeScript types, with Ajv validating every message. Runs execute in a separate process that keeps going if the app closes |
| AD-08 | Ledoit–Wolf shrinkage. Denoising, factor removal and hierarchical risk parity written by hand. cvxpy for minimum-variance and risk parity |
| AD-09 | The held-out lock is enforced inside the data loader. Unlocking requires a pre-registration, and the log is append-only |
| AD-10 | Feature information gain measured with LightGBM, with and without the feature, on purged walk-forward folds |
| AD-11 | PyTorch LSTM and temporal-fusion-style forecasters, with RF-02's leakage caveats fixed |
| AD-12 | PPO (Stable-Baselines3) agents on a Gymnasium wrapper of the same backtest simulator, so the agent environment and the backtest can't drift apart |

## Assumptions I made
- **Results storage:** a single `record_claim` call records every significance claim and applies the correction for its family. There are five families: features at a 10% false discovery rate, and strategies, estimators, forecasters and verdict at 5%.
- **Validation explanations** are marked from the command line, not the app, which stays read-only over data. An explanation carries over to later snapshots when the same item recurs.
- **Precision and speed details:**
  - Factor refits happen at least weekly and are reused in between.
  - Chart series over 5,000 points are thinned, keeping corporate-action days.
  - The WebSocket checks for new run events every 0.5 seconds.
- **Missing cross-check data:** stocks whose EODHD split and dividend history is missing (pre-2018 delistings) are cross-checked on closes only and listed as "returns not cross-checkable".
- **Disk:** about 1 GB per snapshot, not yet measured.

- **Statistical power:** a 3-year held-out period makes "no significant difference" the likely verdict. You've already accepted this.
