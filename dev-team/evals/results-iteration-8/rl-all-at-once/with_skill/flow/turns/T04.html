# New mode: writing the spec from the brief

Read when `dt status` reports `mode: new`: there is no `docs/spec.md`, and the accepted brief is the input.

```
READ BRIEF ─→ SURFACE ASSUMPTIONS ─→ CLARIFY ─→ WRITE SPEC ─→ [user approves] ─→ architecture-design
```

## Step 1: Map goals to features

From the brief's numbered goals, propose features and show the mapping before writing:

```
Goal 1 (regulars reorder in < 30s)     → Saved orders, Text reorder
Goal 2 (no extra daily work for owner) → Regulars setup, Order notifications
```

Every goal has a feature. **Every stage the brief and roadmap list is specced in full**: features, requirements, criteria and edge cases for all of them, never "S1 in full, the rest outlined". Later skills design only what the spec holds.

# The spec: template, writing rules, hygiene check

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown
# [Project Name] — Spec

**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [brief.md](brief.md)

## Summary
[2-3 sentences: what is being built. Link to the brief for why — don't repeat it.]

## Users
| User | What they need to do |
|---|---|
| [Primary user] | [...] |

## Scope
**In scope:** [features, by name]
**Out of scope:** [what we're not building — include everything on the brief's Not Doing list, plus anything decided during clarification]

## Features

### [Feature name] (`CODE`)
**Serves:** Goal 1, Goal 3
**Source:** [ideas/<slug>.md](ideas/<slug>.md) *(extend mode only — omit for features from the original brief)*
**Behavior:** [2-4 sentences or a short numbered flow describing what the user experiences.]

**Requirements**
- **CODE-01** [One testable statement of what the system does.]
  - Given [context], when [action], then [observable result].
  - Given [...], when [...], then [...].
- **CODE-02** [...]
  - Given [...], when [...], then [...].

**Edge cases & errors**
- [Situation] → [expected behavior]

## Data requirements
*(Data and ML projects only — omit otherwise.)*
- **DATA-01** [What data the system needs: content, coverage, history, frequency, freshness — not which vendor.]
  - Given [...], when [...], then [...].

## Quality requirements
- **QR-01** [Measurable non-functional requirement: speed, reliability, accessibility, privacy, security, cost, licence.]
  - [How it's checked.]

## Assumptions
- [Assumptions the user confirmed]

## Open questions
- [Unresolved items, each with who can answer it. Omit if none. A question about what an external source really returns is "answered by a probe during architecture".]

## Changelog
| Date | Change | Source | IDs |
|---|---|---|---|
| YYYY-MM-DD | Initial spec | brief.md | all |
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence and budget limits are `QR-` items ("data costs ≤ $50 a month"), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads the idea file and the conversation.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of torchvision's ResNet-18" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.

**Assumptions I'm making** (correct any of these now, or I'll go with them):
1. Agents see short lists of numbers, never pixels. Every world runs without a display, and drawing is only for replays.
2. **Evaluation:** each trained agent plays 100 episodes on fixed seeds it never trained on. "Beats" means its mean score is higher than the baseline's and the `null-hypothesis-testing` skill confirms the gap at 5% significance.
3. **One hour:** each world's headline training run takes ≤ 60 minutes on the laptop's CPU, and the same seed gives the same result.
4. **Snake:** a 10×10 grid. The score is food eaten per episode, and an episode also ends after 100 moves without food, so a looping snake can't run forever. The lookup-table learner sees a compact summary (danger ahead, left and right, plus the direction to the food). Its lab note includes the run where the table approach breaks down on a richer view, which is why the neural network is needed.
5. **Tank:** the ball moves at a constant speed and bounces perfectly off the round wall. Fish can overlap each other. One fish first, with full sight. Then a school of 8 fish that all share one learned policy, each seeing only things within ¼ of the tank's width. The score is survival time, capped at 60 simulated seconds.
6. **Scripted baselines:**
   - Snake: head for the food, but avoid moves that kill it on the spot.
   - Tank: swim directly away from the ball. This tends to get fish pinned against the wall, so a learned agent should beat it by circling.
   - Predator-prey: the predator chases the nearest prey, and prey flee the predator when it's close and otherwise head for the nearest food.
7. **Break-it runs:** each world's lab note has ≥ 2 runs, each with one part of the learning method removed, plotted against the intact run.

**Questions** (each has my proposed default):
1. **Snake baseline strength:** "head for food and avoid moves that kill it on the spot" is a fairly strong opponent, and the network learner beating it in under an hour isn't guaranteed. Keep it as the bar, or use a weaker baseline that ignores its own body? *Default: keep it strong.*
2. **Caught fish in the tank:** they leave the tank, and the episode ends when all are caught or at 60 s. Or should they respawn? *Default: they leave.*
3. **Proof of co-evolution (S3, both sides learning):** I'd make it checkable with a round-robin tournament. Snapshots of each side, saved during training, play against each other's snapshots. It passes if later predators catch more of earlier prey than those earlier predators did, and later prey survive later predators better than earlier prey did. Or is visible back-and-forth in the curves enough? *Default: the tournament.*
4. **Library comparison:** your hand-written learner must reach ≥ 80% of an established library's evaluation score, on the same world and the same number of training steps. *Default: 80%.*
5. **Replay:** a live window on the Mac with play, pause and step controls, showing the 0 / 25 / 50 / 100% snapshots side by side. Also saving a video file? *Default: live window plus an optional saved video.*
