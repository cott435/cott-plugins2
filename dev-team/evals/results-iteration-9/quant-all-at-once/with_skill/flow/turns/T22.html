### AD-06: Bitemporal Parquet store with immutable snapshot manifests
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** INGST-03–INGST-05, DATA-04, PANEL-01 and PANEL-05 need immutable snapshots, both values of a revision with the date each was known, safe resume, and reproducible pinned reads; QR-03 and QR-08 need fast reads on a laptop.
- **Decision:** Every record row carries `ref_date`, `known_date`, `known_basis` (`observed` when first seen by a run; `assumed_ref_date` for backfilled history, known at the close of its reference date) and `run_id`. Runs append new Parquet part files and never modify one. A snapshot is a manifest (`store/snapshots/<id>/manifest.json`) listing the part files it includes plus vendor watermarks; `store/CURRENT` names the promoted snapshot and is replaced by atomic rename. Promotion builds a derived, rebuildable read view per snapshot (latest version per key, sorted by stock and date). DuckDB queries the parts and views.
- **Alternatives:** A database (Postgres, DuckDB file) with update-in-place — revisions and immutability need hand-built versioning, and a failed run can corrupt the current state. Full copy per snapshot — simple, but ~1–2 GB per daily update.
- **Consequences:** Snapshots share part files, so daily updates add MBs. An as-of-T read takes, per key, the newest version with `known_date ≤ T`. Garbage collection of unreferenced parts is a later manual command.
