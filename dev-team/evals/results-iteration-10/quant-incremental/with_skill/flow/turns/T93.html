# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Changing a step table

Revise, and Sync when the doc changes, edit an existing table this way:

- Keep step names where the function survives; a split step gets new rows with new function names. Keep the pipeline's ID: a rebuilt package keeps its PL IDs where it can, so its golden cases still apply.
- If the entry sketch is gone (the spine was built), don't recreate it. The step table is the contract the code must match; the code change becomes a task.

### AD-17: One eigendecomposition per window drives the structure and the estimators, on NumPy
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `study`
- **Context:** STRUC-02–STRUC-04 and PORT-05–PORT-08. UR-60 points to the user's reference code, RF-01, for removing the market mode. RF-01's caveats rule out using it as is: it fits on the whole panel (look-ahead), fills gaps with 0, hard-codes k, and has a sign fix that zeroes a vector whose loadings sum to 0. UR-72 keeps the components above the noise edge, at least 1. UR-73 picks the constant-correlation target.
- **Decision:** For each window: standardise each stock with the window's own mean and standard deviation, form the correlation matrix C, and decompose it with `numpy.linalg.eigh`. The noise edge is λ₊ = (1 + √(N/T))² for N stocks and T = 252 days; k = max(1, the count of eigenvalues above it). **Structure:** the market share is λ₁/N. As in RF-01's `pca_factors` and `residualize`, the k leading components are projected out of the standardised returns, but fit on the window alone, with no gap filling (windows have none, AD-16) and each vector's sign fixed by its largest loading. Raw and residual mean absolute off-diagonal correlations are reported. **Estimators:** sample is the covariance with ddof = 1. Shrinkage uses Ledoit and Wolf's (2004) constant-correlation intensity, clipped to [0, 1]. Denoised replaces the eigenvalues ≤ λ₊ with their mean (C′) and resets C′'s diagonal to 1. The factor model is V_k Λ_k V_kᵀ plus a diagonal that brings C's diagonal to 1. Denoised and factor are both rescaled by the sample standard deviations.
- **Alternatives:** scikit-learn's `LedoitWolf`: it shrinks toward a scaled identity, not UR-73's target. RF-01 as written: look-ahead and zero-filled gaps. The edge from a fitted MP distribution with an estimated variance: a second fit per window, for a cut the spec defines at unit variance.
- **Consequences:** STRUC-02's edge and k are shared by STRUC-04, PORT-07 and PORT-08, from one decomposition. PORT-07's eigenvalue and trace checks hold on C′, before its diagonal is reset, and its diagonal check on the final estimate (UR-80).

### AD-18: Portfolio rules on cvxpy with Clarabel, HRP on SciPy's hierarchy
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `study`
- **Context:** PORT-09–PORT-13 and the spec's edge case for a rule that finds no weights. UR-75 has a singular sample covariance used as is. PORT-20 allows 1 hour for about 340 dates × 4 estimates × 2 solved rules, so ~2,700 solves at N ≈ 500.
- **Decision:** **Minimum variance:** minimise wᵀΣw with w ≥ 0 and Σw = 1, through cvxpy's `quad_form` on `psd_wrap(Σ)`, solved by Clarabel. **Risk parity:** Spinu's convex form, minimise ½yᵀΣy − (1/N)Σ log yᵢ, then w = y/Σy, so contributions are equal and weights positive by construction; same solver. **HRP:** distance √(½(1 − ρ)), single linkage (`scipy.cluster.hierarchy.linkage`). Then walk the tree top-down: each node splits its weight between its two child clusters in inverse proportion to each child's inverse-variance-portfolio variance. **Equal weight:** 1/N. Weights within 1e-9 below 0 are set to 0 and renormalised. A solver status other than optimal, or weights still failing PORT-09, is a failure for that month and rule, reported, not raised.
- **Alternatives:** SciPy's SLSQP: no new dependency, but slow and unreliable with 500 bounded variables. Inverse-volatility weights for risk parity: exact only for uncorrelated stocks. HRP's original bisection of the sorted list: it can cut through a cluster, and PORT-12 splits down the tree.

# eqdata — Architecture

**Package:** eqdata · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`sources` fetches from Sharadar and Yahoo. `sync` cleans what Sharadar returns, stages it and commits it to `store` in one transaction, then calls `check`. `universe` and `returns` answer as-of queries from `store`. `check` and `eda` raise findings through `findings`. Every long job runs inside `runs`, which holds the lock and writes progress events. `cli` is the front door. The separate `server` package calls only the public API in [contract.md](contract.md): the query functions, `launch_run`, which spawns the CLI (AD-09), and `run_snapshot` and `events_after` for live progress (AD-13). The separate `study` package reads the as-of loader through the same API and saves its report through `reports`, which also holds the EDA report and serves both to `server` (AD-14, AD-15).

```mermaid

  cli --> runs & sync & check & eda
  runs --> store
  sync --> sources & store & check
  sync & check & eda -.Progress.-> runs
  check --> sources & universe & returns & findings & calendar & store
  eda --> universe & returns & findings & reports
  views --> returns & universe & findings
  universe --> store & calendar
  returns --> store & calendar
  findings --> store
```

## Data
- **Sources:** Sharadar SEP, ACTIONS, TICKERS and SP500 (AD-03). Yahoo via `yahooquery` for the sample only (AD-05). Researcher CSVs under `reference/` (AD-10).
- **Tables** (all keyed by `company_id`, AD-04): `companies`, `tickers` (company, ticker, from, to), `membership` (company, effective_from, effective_to), `prices` (unadjusted OHLCV), `actions` (splits, dividends, ticker changes, mergers, acquisitions, delistings). Each has `known_from` and `replaced_on` (AD-06). Also `findings`, `runs`, `run_events`, `source_diffs` (run, company, date, return and close differences; AD-12), and staging copies of the market tables.
- **Cleaning (SYNC-03):** duplicate (company, date) rows keep one, and the count goes to the summary. A changed past value closes the old row (`replaced_on`) and inserts the new one, listed as a revision.
- **Known-on queries (DATA-05):** as-of functions take `as_of` (market date: events after it are ignored) and an optional `known_on` (system date: rows not yet known, or already replaced, then are ignored).
- **Sampling (CHECK-01):** at least 2 companies per calendar year from 1998, drawn from members Yahoo still carries, then filled at random to 100. The seed is recorded in the run summary.
- **Reports:** one `report.json` (an `eqdata.Report`: sections of tables and chart series) per report in `EQDATA_HOME/reports/<kind>/<id>/`, for the `eda` and `study` kinds, rendered by `web` (AD-15).

## Cross-cutting concerns
- **Lock and atomicity:** `runs` holds the lock and `store.commit` is one transaction, so a killed refresh leaves only staging rows, which are cleared at the next start.
- **Credentials:** read in `sources` only, and redacted in logs and events (QR-05).

```python
def run_study(*, known_on: date | None = None) -> Report:
    panel = load_panel(known_on=known_on or date.today())
    structures, notes, holdings = run_rebalances(panel)
    league = rank(holdings)
    significance = test_winners(holdings, league)
    sections = report_sections(structures, notes, league, significance)
    return save_report("study", sections, params=report_params(panel))
```
