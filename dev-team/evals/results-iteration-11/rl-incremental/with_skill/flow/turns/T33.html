# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`), a routed change (`routed_changes`) or the user's words the spec doesn't honour yet (`requests_open`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Stage | `Stage:` line of each new feature: the stage the idea added, or the one it joins |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

## Steps

Run these for the idea only:

1. **Check for conflicts first.** Start with the IDs under *Touches*, then search the rest of the spec for anything else the idea contradicts. List conflicts for the user before writing — "Shared editing changes **EDIT-03** (only the owner can edit). Proposed: owner *or invited editors* can edit."
2. **Map the idea to features** and show the goal → feature mapping, with each feature's stage, before writing.
3. **Surface assumptions, then clarify** (SKILL.md's Asking section).
4. **Write the change** following `references/spec.md` and the rules below.
5. **Set the spec Status back to Draft** and run the Review Gate (SKILL.md, plus the gate steps below), highlighting the changed IDs so the user reviews only what's new.

## Writing rules

1. **Keep IDs stable, keep the text current.** IDs are never renumbered or reused. Old text does not stay in the spec once it stops being true; git keeps it.
   - New feature → new `### Feature (CODE)` section with a new code and IDs starting at `-01`.
   - New behavior in an existing feature → next unused number in that feature (if `SAVE-04` is the highest, add `SAVE-05`, even if `SAVE-02` was removed). `dt status` reports it under `prefixes`.
   - **Widen, don't bolt on.** If an existing requirement already covers this concern for an earlier part of the project, rewrite it to cover the new part too, instead of adding a near-duplicate. A training-time limit written for the first dataset becomes a limit for every dataset. A summary that says "the first milestone" is rewritten.
   - Changed requirement → rewrite it in place and keep its ID. Put no marker on it. Instead, list it as `(changed)` in this round's Changelog row, with the reason in the row's Change text. `architecture-design` reads those Changelog marks (through `dt status`) to find what the architecture must revisit, so list every changed ID.
   - Removed requirement → collapse it to one struck line and delete its criteria and edge cases: `- **CODE-03** ~~[short name]~~ *Removed YYYY-MM-DD: [reason, or "replaced by CODE-07"].*` Never delete the ID line; the ID stays retired.
2. **Link back to the idea.** Add `**Source:** [ideas/<slug>.md](ideas/<slug>.md)` under the `Stage:` line of each new feature section, so readers can find the full why.
3. **Update everything it touches, and consolidate.** Summary (rewritten for the whole spec, not appended to), Users, Serves lines. Scope stays one deduplicated list per side: merge new out-of-scope items into it, and drop or narrow anything the new features bring into scope (the gate's *Out of scope* step). Remove assumptions and open questions that are answered or no longer apply.
4. **Add one Changelog row**, one line: the idea file as the source, a short description of the change, and the IDs as ranges in up to three `;`-separated groups: added, then changed, then removed (`FIELD-01–FIELD-12; CNN-03, CORE-04 (changed); CROP-04 (removed)`). A `(changed)` or `(removed)` mark covers every ID in its group.

## Gate steps

Run the hygiene check on the whole spec, not just the new section, and add:

- **Out of scope.** Read every out-of-scope line against the features this round added. Drop a line the new features bring into scope. Narrow a line that is now only partly true to the part still excluded, and name the stage it applies to. Once a neural-network stage exists, "deep learning" is no longer out of scope. Once a reserve-planning stage uses demand forecasts, "no demand forecasts — the reserve stage is an equal split" becomes "the equal-split reserves use no demand forecasts". Then merge duplicates.
- **Leftovers.** The Summary describes the whole spec as it now stands. No requirement is still worded for one stage when it now covers several. Removed requirements are one line each. No `(changed …)` marker or other change note appears above the Changelog.

## On approval: close and freeze the idea

A `Specced` idea is the record of why the feature was added, as it stood that day. The spec is the current description.

1. Set its Status to `Specced` and add two lines under the header: `**Spec:** CODE-01–CODE-04, EDIT-03 (changed)` and the banner `> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)`.
2. Delete the open questions the spec answered. If none are left, the section becomes one line: `Resolved in the spec.`
3. Delete wording that only served the review: notes to the user ("my proposed limit, for you to check") and instructions to this skill ("this line must be removed from the spec").

After that, don't edit the file again, even when a later round changes what it describes, such as a narrowed holdout or a merged stage. That change goes in the spec, and the later idea file names this one under *Touches*.

# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

# RL Lab

**Status:** Accepted · **Last updated:** 2026-10-18

## The problem
Reinforcement learning (RL) is how an agent learns by trial and error from rewards. It is easy to read about and hard to really understand. Library code hides the parts that matter, and tutorials stop once the agent "works". The fastest way to learn it is to build small agents from scratch, in small 2D game environments, where each one teaches one idea and you can see it learn.

## Who it's for
Me: a solid Python programmer with some NumPy and PyTorch, who knows the basics of Q-learning (learning the value of each action in each state) and wants to learn RL by building it.

## Goals
1. For each environment, I can explain in my own words why the agent learns, and why each part of the algorithm matters.
2. Every agent is shown to learn: its learning curve beats a random agent and a simple scripted agent on the same games.
3. I can watch a replay of any trained agent playing.
4. A new environment reuses a shared core (environment interface, training loop, logging, replay viewer, learning curves) instead of starting over.

## Constraints
- Laptop CPU only, and under about an hour of training per environment.
- Free tools only.
- Evenings and weekends, a few weeks per environment, no deadline.
- Learning algorithms are written from scratch, not taken from a library.

## What success looks like
- The first environment, Snake, has an agent whose learning curve clearly beats both baselines, plus a replay of it playing.
- Turning off a key part of the agent visibly hurts its learning, and I can say why.
- The second environment, whatever it is, plugs into the shared core with small changes.

## What we're betting on
- Small, hand-picked descriptions of the game state ("danger ahead", "food to the left") are enough for an agent to learn well within an hour on a CPU.
- A shared core designed while Snake is the only example will still fit the next environment without a rewrite.
- Writing the algorithms myself teaches more than tuning a library would.

## Not doing
- Learning from raw pixels or the full grid image: much slower, and not the lesson I'm after.
- Comparing against library implementations, for now: a later step, once my own version works.
- Fancy views such as heatmaps of the agent's values: learning curves and replays are enough.
- Planning environments beyond Snake: the next one is chosen once Snake is done.
- Mastering Snake: agents that see only nearby danger tend to trap themselves, and that limit is fine.

## ML Feature in an Existing Product (Extend Mode)

**User invokes:** `/ideate use ML to flag bad assay plates automatically in our lab results app`

The app already has `docs/brief.md` (Goal 2: *Bad data is caught before it reaches analysis*) and `docs/spec.md`, so this is **extend mode**. The skill reads both, plus the `qc` module in the codebase.

### Phase 1: Understand & Expand

> **How might we** catch failed plates before they reach analysis, without scientists reviewing every plate by hand?

Questions:

1. **How are plates checked today, and how long does it take?**
2. **What history exists?** How many plates, and is there a record of which ones were failed and why?
3. **What's worse: a bad plate getting through, or a good plate being re-run?**

**User responds:** "Scientists eyeball every plate — about 6 hours a week. We have 3 years of plate reads, roughly 40,000 plates, and about 2% were marked failed in the app. Missing a bad plate is much worse; a re-run costs a day."

**Skill continues:**

Before any ML: assay QC already has a standard rule, the **Z′-factor** (plates under 0.5 are suspect). Your `qc` module computes it but nobody acts on it. That's the baseline any model has to beat. If the rule alone catches most failures, you may not need ML at all.

Variations:

1. **Simplification — Just Use the Rule:** Auto-flag plates with Z′ < 0.5 and stop there. Zero ML.
2. **Ranked Review Queue:** A model scores every plate. Scientists review the riskiest first and stop when the scores get low. Humans still decide.
3. **Inversion — Auto-Pass the Obvious:** Instead of finding bad plates, confidently clear the clearly-good ones, and scientists review the rest.
4. **Anomaly Detection:** No labels needed. Flag plates that look unlike typical ones. Useful if past "failed" labels turn out to be unreliable.
5. **Expert Lens — Layout Patterns:** Many failures show up as spatial patterns (edge effects, a dead column). Features built from plate layout may beat a generic model.

### Phase 2: Evaluate & Converge (summary)

**Data check:** 40,000 plates with 800 failures is enough to try a supervised model, *if* the labels are consistent. That's the biggest bet. Different scientists may fail plates for different reasons. **Baseline:** the Z′ rule. **Cost asymmetry:** missing a bad plate is far worse, so measure recall at a fixed review budget, not accuracy (98% accuracy is free by passing everything).

The user picks **2 (ranked queue), with 1 as the baseline it must beat**. **Fit check:** it serves existing Goal 2 and the same users, so **the brief does not change.**

# Idea: Fish Tank

**Status:** Draft · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This adds a second environment, a circular tank where several fish learn to steer away from a bouncing ball, so the learner can build policy-gradient methods up to PPO, with continuous control, on the shared core Snake built.

## The problem
Snake teaches value learning: a few discrete moves, each with a learned value. It can't teach the other half of modern RL. When moves are continuous (how hard to turn, how fast to swim), there is no list of moves to score, and the agent has to learn the policy directly. Policy gradients are where that starts, and PPO is where it usually ends up. Each step on the way fixes a specific failure of the one before. Building them in order, in a game where you can watch the result, is how to see why PPO exists.

## Who it's for
The same learner as the brief, once Snake (S1) is done and they move on from value learning to policy learning.

## How it fits
- **Serves:** Goal 1 (explain why each part matters), Goal 2 (beats random and scripted agents), Goal 3 (replay), Goal 4 (reuses the shared core)
- **Touches:** CORE-01–CORE-06 (environments must allow several agents at once and continuous moves; CORE-03 reports a "number of allowed moves"); BASE, EVAL, ABL, CURVE-03, REPLAY, EXPL, LOG-01 (written for Snake and its DQN); QR-01, QR-02, QR-03, QR-05 (Snake-only limits and the hand-written rule, which now covers a second family of algorithms). SNAKE and AGENT must keep working as they are.
- **Brief changes:** Not doing narrowed: the fish tank is planned now; only environments after it wait.
- **Stage:** New S2 (roadmap stage on acceptance), built after S1 is done.

## Recommended direction
**The tank.** A circular tank with one ball bouncing off its wall. Several fish swim in it with continuous movement: each step every fish chooses how to steer and how fast to swim. When the ball touches a fish, that fish is removed. The game ends when every fish is gone. Fish are rewarded for staying alive, so a good fish survives as long as possible.

**What a fish sees.** Only nearby things, through about 8 sensor rays spread evenly around it. Each ray reports how far away the wall, the ball and other fish are along that direction, up to a short range. Nothing beyond the rays' reach is visible.

**One brain, many bodies.** All fish share one policy, and each acts on its own observation. The fish don't block or crowd each other, so to the learner each fish is an independent copy of the same single-agent problem. This keeps the stage about policy gradients, not game theory. The build starts with one fish and adds more once a single fish learns.

**The ladder.** The learner writes three agents by hand, each one built on the previous one: REINFORCE (plain policy gradient), then actor-critic (a learned value estimate cuts the noise), then PPO (a limit on how far each update moves the policy). Each added piece has an off switch, as in S1, so turning it off shows what it was fixing.

**The core grows.** The shared core learns to handle continuous moves and several agents at once. Snake keeps running exactly as before.

**Optional extra.** A discrete twin of the tank, with 8 compass moves, run by S1's unchanged DQN. It shows what continuous control adds and checks that the core still serves value learning. The stage is done without it.

## Alternatives considered
- PPO only — skips the failures that explain each piece, which is the point of the lab.
- Fish that interact (crowding, blocking) — a genuinely multi-agent problem: richer, but a different lesson.
- A curriculum (the ball speeds up, more balls appear) — adds tuning without a new idea; revisit if the tank is too easy.
- A list of the nearest few objects as the observation — rays are fixed-size and closer to "sees only nearby things".

## What success looks like
- Each rung's learning curve beats a random fish and a scripted fish on the same seeded games.
- PPO learns better or more steadily than the rung below it, and turning off each piece visibly hurts, or the notes record that it didn't.
- A replay shows trained fish dodging the ball.
- Snake's results are unchanged after the core grows.

## What we're betting on
- About 8 short rays carry enough information to dodge one ball.
- A shared policy learns well from several independent fish, and the extra fish speed learning up rather than confusing it.
- The full ladder trains within the brief's hour per run on a laptop CPU.
- The S1 core stretches to continuous moves and several agents without a rewrite.

## Not doing
- Fish that affect each other — a multi-agent problem; out of scope.
- A curriculum of harder tanks — not needed to learn the lesson.
- Library implementations of PPO — the brief keeps algorithms hand-written.
- Learning from pixels — the brief rules it out.

## Open questions
- How many fish, how big the tank, how fast the ball, and how long a game may last before it's cut off (a perfect fish would never die).
- The exact steering choice: turn rate plus speed, or a push in x and y, and their limits.
- Ray range, and whether a fish also senses its own speed or heading.
- The reward: +1 per step per living fish, or a penalty when hit as well.
- The scripted fish: swim straight away from the ball, or also steer clear of the wall.
- Which switches the ladder has (for example the critic, the update limit, advantage normalisation), and how ablations are compared with the `null-hypothesis-testing` skill, as in S1.
- Whether the discrete twin is written into the spec now, or left for after the stage.
