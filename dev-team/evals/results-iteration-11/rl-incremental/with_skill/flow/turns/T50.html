# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## Overview
One Python package, `rllab`. Every environment and every agent sits behind the protocols in `core`. An environment takes one move per living agent and reports a result for each. Its moves are a set of choices or continuous controls with limits (AD-11). Snake and the corridor are one-agent environments with choices. The fish tank and the line test environment have several agents, and agents can be removed mid-game. The training loop, evaluation, run records, curves and replay viewer use only those protocols, so they never name an environment. A training run plays seeded games with a hand-written learner: the DQN learns after every step, and the three policy-gradient rungs learn once after every game (AD-12). The run scores the learner greedily on held-out seeds at regular points and once more at the end, and rewrites its JSON record after each check. The study command trains every variant of an environment's study plan, 5 seeds each, and scores both baselines. It then runs the `null-hypothesis-testing` comparisons (against the baselines, up the ladder, and for each ablation) and writes a report and charts for the learner's notes page. The notes command reads that page and reports missing sections and broken links; no code ever writes it (AD-10). Charts are drawn only from saved records. A replay re-plays a saved agent on a seed, so it never depends on frames saved during training.

## Data
- **Seeds (AD-04):** training game seeds are drawn from `[0, 1_000_000)` by a generator built from the run seed. The 100 held-out seeds are fixed at `1_000_000–1_000_099`. The two ranges can't overlap (EVAL-01), and every agent and baseline of an environment is scored on the same held-out games (BASE-03, EVAL-03).
- **Run folder (AD-05, AD-15):** `runs/<env>/<name>/record.json` holds the config, one score and length per training game, the evaluation points (mean, spread and per-seed scores), the final check over all 100 held-out seeds, the average loss per evaluation window, the status and the elapsed time. Next to it, `agent.pt` holds the state dict, sizes and config. Baselines get `runs/<env>/baseline-random/` and `runs/<env>/baseline-scripted/`, each with one evaluation point and its final check. Study runs are named `<variant>-s<seed>`, for example `runs/snake/no-memory-s3` or `runs/tank/no-cap-s2`.
- **Study output:** `runs/<env>/study/report.md` (every comparison with its test result, each learner's spread across seeds, missing or incomplete runs, and the finding lines ABL-05 and PG-11 ask for), `runs/<env>/study/curves.png` (the full agent, its ablations and the baselines) and, in the tank, `runs/<env>/study/ladder.png` (the 3 rungs and the baselines). The learner's own `notes/<env>.md` (EXPL-01–EXPL-04) links them. The code reads the notes page (`study.check_notes`) but never writes it, so the learner's words are never overwritten (AD-10).

## Cross-cutting concerns
- **Errors:** the domain errors are in `core`: `InvalidMoveError`, `WrongAgentsError` and `GameOverError` (ValueErrors), `EnvCheckError` and `MoveKindError` (TypeErrors), and `NonFiniteLossError`; `runs.RunExistsError` and `pg.PGConfig`'s switch refusal join them. `train` catches failures during the run, marks the record `failed` with the game and step, flushes it and re-raises, so the log so far survives.
- **Speed (QR-01, QR-02):** each run uses one CPU thread (`torch.set_num_threads(1)`). The study runs up to `os.cpu_count() - 1` runs at once in separate processes (AD-03). The default of 1,000 training games per run, in Snake and in the 5-fish tank, is checked against the 60-minute limit by a timing test on the learner's laptop.
- **Reproducibility (QR-05, SNAKE-08, TANK-10, REPLAY-04):** no global random state anywhere. Each environment, agent and run owns a `np.random.Generator` or `torch.Generator` built from its seed. Living agents are always asked, and learn, in id order. Deterministic torch algorithms and a single thread give identical logged results on the same machine (AD-04).
- **Hand-written learning (QR-03):** `agent` and `pg` may import `torch` and `numpy` only. No gymnasium, stable-baselines or other RL library is a dependency, and a dependency check enforces it (`build-setup`).
- **Testing:** the corridor proves the core is environment-agnostic (CORE-05, CORE-06), and the line proves it with continuous controls, several agents and removals (CORE-07, CORE-08). The Snake and tank rules are tested from seeded fixed-move games. CORE-09 is a golden case (`test-planning`): S1's exit records a 200-game Snake run with seed 1, and every later milestone that touches `core`, `evaluate`, `runs` or `train` repeats it and compares every logged evaluation score.

### AD-12: Learners learn per agent-step, per game, or both
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** AGENT-04 has the DQN learn from remembered steps as it plays; PG-05 has every rung learn once after each game from all its fish's steps. CORE-05 and CORE-07 need one training loop for both, and TWIN-02 has the DQN treat each fish's steps as its own.
- **Decision:** `core.LearningAgent` has `learn(t)`, called with each living agent's `Transition`, in id order, after every step, and `end_game()`, called once after every training game; each returns its update's loss or `None`. The DQN updates in `learn` and returns `None` from `end_game`; a rung only stores the step in `learn` and updates in `end_game`. `Transition.agent` names the fish, so a rung computes each fish's returns up to that fish's end. `train` logs the mean of every loss returned in each evaluation window.
- **Alternatives:** A per-game learner handed the whole game's trajectories by the loop: `train` would keep two code paths and buffer the steps itself. Separate training loops for value and policy learners: breaks CORE-07's "no changes to the core".
- **Consequences:** The loop is the same for every learner, and the DQN's calls on Snake are exactly the single-agent loop's. A rung holds one game's steps in memory, at most 10 fish × 1,000 steps.

### AD-13: The policy-gradient ladder: one hand-written `PGAgent` with a rung number and 3 switches
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** The user wants "policy-gradient/PPO and continuous control" (UR-48) and chose "The full ladder with off switches." (UR-55). PG-01–PG-09 fix the mechanics: a centre and width per control, clipping to the limits, one update per game from every fish's steps at discount 0.99, an advantage blend of 0.95, rescaled advantages on rungs 2 and 3, and on rung 3 10 passes in batches of 64 with a 20% cap. ABL-06–ABL-08 switch off rung 3's value estimate, cap and rescaling. QR-03 rules out RL libraries.
- **Decision:** `pg.PGAgent` takes `PGConfig.rung`. The policy is an MLP of observation size → 64 → 64 → one centre per control (tanh hidden layers) with a learned, observation-independent log width per control. Moves are drawn from a normal distribution and clipped to the limits, and log-probabilities are taken on the clipped move. Rung 1 weights each move's log-probability by the discounted return to that fish's end and makes one Adam step per game. Rung 2 adds a value MLP of the same size, trained by mean-squared error on the returns, and weights moves by the 0.95-blended advantage, rescaled. Rung 3 adds 10 passes over the game's steps in shuffled batches of 64, with the probability ratio clipped to 0.8–1.2. With `value` off, rung 3 uses the returns in place of advantages; with `cap` off, the ratio isn't clipped; with `rescale` off, advantages are used as built. Adam lr 3e-4. A game ended by the time limit stops returns at step 1,000 with no value carried past it.
- **Alternatives:** Three separate agent classes: the switches would cut across class lines, and the "switch on a rung without that part" check would be scattered. A tanh-squashed policy instead of clipping: an exact log-probability, but PG-03 describes clipping a draw that falls outside, and squashing changes what "centre" means in PG-01 and PG-02. Width predicted from the observation: more expressive, but less stable for a first policy-gradient build.
- **Consequences:** The module code can still read rung by rung (one file per rung's addition, laid out by `pipeline-design`). Hidden sizes, lr, the log-width start and clipping before the log-probability are choices the spec doesn't fix, kept in `PGConfig`. Taking log-probabilities on the clipped move biases the gradient when the policy pushes past a limit (see Risks).

### AD-14: The tank is simulated in NumPy, in continuous tank units
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** TANK-01–TANK-10 fix the geometry, motion, sight, rewards and limits: radius 10, a ball of radius 1 at 0.25 per step with mirror bounces, fish of radius 0.3 steering −15° to +15° and swimming 0 to 0.3, removal when centres are closer than 1.3, 8 rays of reach 4, and a 1,000-step limit. QR-01 needs a 5-fish run of 1,000 games in under an hour, so each step must be cheap. TWIN-01 adds a compass twin.
- **Decision:** `tank.TankEnv` keeps positions in float64 tank units around the centre. Each step: turn and swim every living fish (stopping at the wall), move the ball and reflect its velocity about the wall's normal on contact, then remove every fish within 1.3 of the ball. ## Risks and open questions
- **Training time (QR-01, QR-02):** neither default of 1,000 games has been timed. In Snake, a greedy agent that circles until the step limit makes evaluation games long; in the tank, a good policy plays up to 1,000 steps × 5 fish per game, each fish asking the policy network once per step, plus 10 evaluation points of 20 games and a final check of 100. Mitigation: the first milestone of each stage times one run alone and 3 in parallel. If too slow, lower the default game count; the spec doesn't fix it.
- **Settings the spec leaves open:** the DQN's 11 → 256 → 3 network, Adam lr 1e-3, batch 64, Huber loss and linear ε decay (AD-02), and the ladder's 64-unit networks, lr 3e-4 and log-width start (AD-13), are tutorial defaults, not tested here. If a learner doesn't beat the scripted baseline (EVAL-04), tune these before questioning the design.
- **Clipped log-probabilities (AD-13):** a policy whose centre sits past a limit (a fish always turning 15°) gets biased gradients. If curves stall with the centre outside the limits, take the log-probability of the unclipped draw instead and record it in `Transition`.
- **8 rays and one ball (brief bet):** the idea bets 8 short rays carry enough to dodge the ball, and that fish don't sense its motion (UR-58). If no rung beats the scripted fish, that is a finding for the notes (PG-11), not a design failure.
- **Comparison method:** the test statistic, how the seeds × 100 games are paired and the multiple-comparison correction are left to the `null-hypothesis-testing` skill when `study.compare_scores` is built. The contract passes it the raw per-seed, per-game scores so the skill can pair by game seed; each side may have fewer than 5 seeds (AD-09).
- **M1 rework:** the grown core (AD-11, AD-12, AD-15) changes signatures M1's approved plan, PL-01–PL-06 and the S1 golden cases were written against. Nothing is built, so the cost is docs; the build waits for pipeline-design, test-planning and build-planning's replan.
