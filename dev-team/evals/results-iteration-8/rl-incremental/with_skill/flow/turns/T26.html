73	## Decisions
74	### AD-01: Python 3.13 with uv
75	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
76	- **Context:** The laptop has Python 3.13 and uv already. PyTorch ships CPU wheels for 3.13 on macOS.
77	- **Decision:** Python 3.13. uv manages the virtual environment and the lock file.
78	- **Alternatives:** 3.12 — no library here needs it, and it would mean a second interpreter. Conda — heavier, and nothing needs it.
79	- **Consequences:** `requires-python = ">=3.13,<3.14"`. One `uv sync` sets up the project.
80	
81	### AD-02: PyTorch only for the network's arithmetic and gradients
82	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
83	- **Context:** NET-08 allows a general numerical library for the network's arithmetic and gradients only. The learner is new to PyTorch and wants to learn it (brief).
84	- **Decision:** `net` builds its network from `torch.nn.Linear` layers and uses `torch.optim.Adam`. Memory, sampling, targets, target copy, exploration and the update rule are written in the project. No PyTorch import outside `net`, and no reinforcement learning library anywhere.
85	- **Alternatives:** NumPy with a hand-written backward pass — teaches gradients, but adds a second hard problem to the rung, against Goal 2. JAX — less familiar CPU tooling, and the brief names PyTorch.
86	- **Consequences:** Only `net` carries the PyTorch dependency, and import-linter enforces that (AD-05). The table rung (L1, L2) runs before any PyTorch code exists.
87	
88	### AD-03: NumPy for everything outside the network
89	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
90	- **Context:** TAB-05 requires the table learner to be built from basic array operations. Views, evaluation scores and frames are small arrays.
91	- **Decision:** Views, frames, scores and the table's values are NumPy arrays. The table is a `dict[bytes, np.ndarray]` with three values per situation.
92	- **Alternatives:** Pure Python lists — slower and clumsier for views. PyTorch tensors everywhere — drags PyTorch into the table rung.
93	- **Consequences:** `net` converts views to tensors at its own boundary.
94	
95	### AD-04: One fully connected network for both views
96	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** net
97	- **Context:** NET-07 requires the same learner for both views, with only the input size changing. QR-02 caps a run at 60 minutes on a laptop CPU. The raw grid is at most 3×6×6 + 4 = 112 values.
98	- **Decision:** Input → 128 → 128 → 3 with ReLU, the input size taken from the view's length. Each view is flattened.
99	- **Alternatives:** A small convolutional network for the grid — a better fit for images, but it breaks NET-07 and adds a new concept to L4. A single hidden layer — may be too weak for L4's bar.
100	- **Consequences:** L4 tests whether a plain network can read a 6×6 board, which is the brief's bet. If L4 misses its bar, a convolutional network is the first change to try, through a new decision.
101	
102	### AD-05: Shared pieces depend only on `core`
103	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
104	- **Context:** CORE-01 says the shared pieces never use Snake directly. Goal 5 wants them reused, and the brief rules out a framework designed ahead of time.
105	- **Decision:** Every shared component (training, evaluation, replay, plots) imports only `core`. Every environment and agent implements `core.Env` or `core.Agent`. Only `lab` imports concrete environments and agents. import-linter checks these rules in the check script, along with "only `net` imports torch".
106	- **Alternatives:** A registry inside `train` — makes `train` import Snake. Gymnasium's interface — a reasonable standard, but it brings the library's conventions in before they're needed. The `Env` protocol stays close to it, so a later adapter is small.
107	- **Consequences:** A second environment needs a new `Env` class and a line in `lab`, nothing else. The protocols must stay tiny, or they become the framework.
108	
109	### AD-06: Plain files in one folder per run
110	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
111	- **Context:** EVAL-01, EVAL-02 and EVAL-10 need settings, logs and agents saved and reloaded. There's one user and no concurrency beyond the seed processes, each of which writes its own folder.
112	- **Decision:** The layout is as listed under Data: JSON for settings and evaluation, CSV for the training log, NPZ for the table, and a PyTorch weights file for the network.
113	- **Alternatives:** SQLite — queries aren't needed. An experiment tracker — an extra service for one person.
114	- **Consequences:** Runs are easy to inspect by hand and to delete. Comparing rungs means reading several `eval.json` files, which `lab` does for the closing note.
115	
116	### AD-07: A replay holds the seed, moves, frames and values
117	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** replay
118	- **Context:** WATCH-04 needs per-step move values, and WATCH-07 needs a game rebuilt from its seed and moves to match the saved one. Games are at most a few thousand steps on ≤ 10×10 boards.
119	- **Decision:** One JSON file per replay containing the environment settings, seed, moves, a frame per step (a small integer grid), rewards, the ending, and either per-step values or `null` for bots.
120	- **Alternatives:** Seed and moves only — smaller, but there's nothing to check WATCH-07 against, and the viewer would have to rebuild the environment. Frames as images — large, and no use to tests.
121	- **Consequences:** Replays are a few hundred kilobytes at most. `replay.rebuild` replays the moves on a fresh environment and compares the frames.
122	
123	### AD-08: matplotlib for curves and the viewer
124	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
125	- **Context:** EVAL-03 needs learning-curve figures. WATCH-02, WATCH-03 and WATCH-06 need a viewer with step, back, play and speed controls on the laptop screen. Nothing needs a game-quality window (spec Out of scope: a polished game).
126	- **Decision:** matplotlib for both. The viewer is a figure with keyboard controls (← → step, space play/pause, + − speed from 1 to 20 steps per second), with the board drawn from frames and a bar chart of the three move values.
127	- **Alternatives:** pygame — smoother playback, but a second graphics library. A terminal viewer — no value bars worth reading.
128	- **Consequences:** One plotting library to learn. matplotlib timers are fine at ≤ 20 frames per second on a 10×10 board.
129	
130	### AD-09: Reproducibility through explicit generators
131	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
132	- **Context:** QR-03 needs an identical learning curve for the same settings and seed. GAME-09 needs an identical game for the same seed and moves.
133	- **Decision:** Each run creates one `np.random.Generator` from its seed, and splits it into child generators for the environment, exploration and memory sampling. `net` also calls `torch.manual_seed`, `torch.use_deterministic_algorithms(True)` and `torch.set_num_threads(1)`. Nothing uses global random state.
134	- **Alternatives:** Global seeding — fragile, since any extra random draw shifts every later one.
135	- **Consequences:** A single thread costs a little network speed, which is acceptable at this network size (AD-04). Speed tests run with the same settings.
136	
137	### AD-10: Bar tests run through the `null-hypothesis-testing` skill
138	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** evaluate
139	- **Context:** EVAL-05–EVAL-07 name the `null-hypothesis-testing` skill as the judge. It defines the test statistic, null distribution and correction. The project must not write its own version of that procedure.
140	- **Decision:** `evaluate.compare` takes two score arrays, the bar (beats or matches, with the 10% margin) and α = 0.05, and returns a `BarResult`. The test inside it is designed and verified with the `null-hypothesis-testing` skill when `evaluate` is built. Each rung's bar results are saved in `eval.json` along with the test used.
141	- **Alternatives:** Choose a t-test by hand — that is exactly the procedure the skill owns.
142	- **Consequences:** The skill's design (for example a permutation or bootstrap test, and whether L1–L4 need a multiple-testing correction) is recorded in `evaluate`'s code and in each `eval.json`.
143	
144	### AD-11: Every pipeline step hands on a contract type
145	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
146	- **Context:** While the pipelines were being designed, three steps ended in a plain path, Markdown text or nothing: drawing curves, writing a note, and viewing a replay. Each pipeline step's output must be a frozen contract type, so tests can start on samples before the producing step exists.
147	- **Decision:** A step that writes something to disk returns a small type naming what it wrote (`plots.Figure`, `lab.Note`). A step that only shows something returns its input (`replay.view` returns the `Replay`, with `show=False` for tests).
148	- **Alternatives:** Bare `Path` and `None` returns — simpler, but they leave those steps with nothing to freeze or test against.
149	- **Consequences:** Two small types in the contract. The viewer can be tested without opening a window.
150	
151	### AD-12: Environments can start from a given state
152	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** snake
153	- **Context:** The golden cases for Snake's rules and views (TC-01–TC-10, TC-16) start from hand-built boards whose correct outcome follows from the spec. Reaching those boards through `reset` and random food isn't possible.
154	- **Decision:** `SnakeEnv.from_state` starts a game from a given `SnakeState`, validating it first. The rng is used only for food placed after that.
155	- **Alternatives:** Scripted move sequences from a seeded reset — they depend on random food placement, so their outcomes aren't closed-form. Setting private fields in tests — this breaks whenever the internals change.
156	- **Consequences:** Rule tests are short and exact. `from_state` is part of the public contract, so later environments may offer the same thing for their own golden cases.
157	
158	### AD-13: Stay a single package through Snake
159	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
160	- **Context:** `rllab` passes the Grow guidelines: 5 pipelines (more than 3) and a contract of about 230 lines (more than 200). But there's one user, one install and nothing deployed separately. The one dependency worth isolating, PyTorch, is confined to `net` by AD-05's import-linter rule. All five pipelines are short command-line workflows in `lab`.
161	- **Decision:** `rllab` stays one package for the whole Snake stage.
162	- **Alternatives:** Split now into shared core, environments and agents — extra packaging and documentation before any code exists, which is the framework-first approach the brief rules out.
163	- **Consequences:** Package docs grow past the guidelines, which is accepted. Revisit when the second environment's stage is planned. The seam is the shared core (`core`, `train`, `evaluate`, `replay`, `plots`) vs. environments and agents.
