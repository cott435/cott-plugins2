**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
`data` downloads Sharadar bulk files, computes returns, validates and writes a local point-in-time store. Every other package reads that store only through `data.Loader`, which refuses anything after the as-of date and anything in the locked holdout. `eval` is the shared walk-forward engine: strategies from `research` (classical portfolios) and `ml` (forecast portfolios, PPO agent) plug into its `Strategy` protocol and are scored under one cost model, one run log and one claims register. `paper` runs frozen strategies forward day by day. `server` exposes the store, run progress and results over HTTP and WebSocket to the `web` browser app.

- **Alternatives:** A single Python package with module folders — simpler, but the torch stack sits in every install and the layering relies on discipline. Separate repositories — versioning overhead for one person.
- **Consequences:** Cross-package hand-offs go through frozen contracts with fixtures. A package can only see what its dependencies export.

### AD-02: Market data from Sharadar Prices – Full History
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** DATA-01–DATA-06: daily OHLCV from about 2002, S&P 500 membership with effective dates including former members, delisted prices, splits, dividends and ticker changes, ≤ $50/month, personal research use with local storage, accessible from Python on macOS.
- **Decision:** Sharadar's personal plan, $299/year (about $25/month): the price, `sp500`, `actions` and `tickers` tables, fetched as bulk files over REST with `requests`. It sits behind a `data.Source` protocol. Our identity is Sharadar's `permaticker` (UNIV-03). ### AD-03: Local store in Parquet and DuckDB, run metadata in SQLite
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** QR-03 (full panel in ≤ 10 s), QR-07 (≤ 20 GB), ING-05/06 (incremental and resumable), APP-07 (progress from command-line runs visible in the app).
- **Decision:** Under a configurable data root: the raw vendor bulk files as downloaded; a Parquet store (prices partitioned by year; membership, actions, tickers, flags, returns) queried with DuckDB; a `meta.sqlite` file for data run records, progress events and the holdout lock; and a `results/` tree with the append-only `runlog.sqlite` (AD-06) and per-run Parquet artifacts.
- **Alternatives:** A single SQLite or Postgres database — slower wide-panel scans, and Postgres needs a server. HDF5 — weaker tooling and concurrency.
- **Consequences:** Writes go through `data` only. Readers open DuckDB read-only. SQLite carries the cross-process progress feed, so the server needs no in-process link to a run.

### AD-04: Returns computed in-house from unadjusted prices and corporate actions
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** ING-03 (price and total returns), ING-04 (final return before delisting), VAL-03 (jumps explained by splits).
- **Decision:** Compute price returns from unadjusted closes and split ratios, and total returns by adding cash dividends on their ex-dates. Cross-check every stock against Sharadar's dividend-adjusted close. A mismatch above 1e-4 on any day is flagged `adjustment_mismatch` (a VAL flag type).
- **Alternatives:** Use the vendor's adjusted closes directly — opaque, and they get restated on every new action, which breaks reproducibility. Adjusted data only, with no unadjusted prices — can't explain jumps.
- **Consequences:** Returns are reproducible from stored inputs, at the cost of one more module and its known-answer tests (the ING-03 split and dividend cases).

### AD-05: As-of gate and holdout lock live in `data.Loader`
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** LOAD-01, LOAD-05, EVAL-01, EVAL-06. The references show what happens otherwise: RF-01 fits its decomposition on the full sample, and RF-02 splits with no embargo.
- **Decision:** Every read goes through a `Loader` bound to an as-of date. A read past it raises `AsOfViolation`. The holdout start date is written to `meta.sqlite` the first time a holdout evaluation is asked for, and stays fixed after that. Normal loaders refuse holdout dates with `HoldoutLockedError`. `Loader.final_evaluation(strategy_id, version)` returns a holdout-capable loader once per strategy version, and records the grant.
- **Alternatives:** Enforce in `eval` only — research scripts and features could still read the future. A convention with no lock — the brief's whole problem.
- **Consequences:** Truncation tests have a single point to target. Research code cannot load "everything" for convenience; it asks for windows.

### AD-06: Append-only logs in SQLite with triggers and a hash chain
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** EVAL-08 (every run logged and uneditable), PAPER-06 (append-only ledger), FTEST-04 (an all-time count of tests for correction).
- **Decision:** One `eval.AppendLog` mechanism: SQLite tables whose UPDATE and DELETE are blocked by triggers. Each row carries the hash of the row before it, and `verify()` re-checks the chain. It backs the evaluation run log, the claims register and the paper ledger.
- **Alternatives:** JSONL files — easy to edit by accident, with no concurrent writers. A hosted experiment tracker — more than one person needs, and it lives off the laptop.
- **Consequences:** Mistakes are corrected by appending a superseding row, never by editing. The log grows forever, which is small at this scale.

### AD-07: Every significance verdict is a recorded `eval.Claim`
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** Goal 1 and the spec's rule that every "beats" or "survives" claim is tested with the `null-hypothesis-testing` skill, corrected within its comparison family (COV-06, PORT-07, FTEST-04, FCST-07, FPORT-03, AGENT-08, PAPER-05).
- **Decision:** Every module that makes a significance claim builds its test with the `null-hypothesis-testing` skill and records it with `eval.record_claim`: the family, hypothesis, statistic, null method, p-value, the corrected verdict over the whole family so far, effect size, and run ID. Each family is declared where its claims are made. A family's size counts every claim ever recorded in it, not just the latest run's.
- **Alternatives:** Each stage writes its own report format — verdicts can't be audited, and corrections silently reset between runs.
- **Consequences:** The app lists every claim, failures included (APP-10). A directional check, like the paper test's, records its p-value with `informational=True`, and that p-value never changes the verdict.

### AD-08: Estimators and optimizers built on NumPy, SciPy and cvxpy
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `research`
- **Context:** FACT-02, COV-01–COV-04, PORT-01–PORT-04, QR-06 (all 10 S2 runs in ≤ 1 hour), with N ≈ 500 and T = 756.
- **Decision:** PCA by eigendecomposition of the window's correlation matrix, with k set by the Marchenko–Pastur edge λ₊ = σ²(1+√(N/T))² and σ² fitted to the bulk. Shrinkage is Ledoit–Wolf toward a constant-correlation target, implemented in-house and checked against scikit-learn's identity-target `LedoitWolf` on synthetic data. Denoising replaces the noise eigenvalues with their mean, keeping the trace. Long-only minimum variance is a cvxpy QP solved with Clarabel. Risk parity uses cyclical coordinate descent. HRP uses single-linkage SciPy clustering, quasi-diagonal ordering and recursive bisection.
- **Alternatives:** A ready-made portfolio library such as PyPortfolioOpt or Riskfolio — hides the steps, and its look-ahead behavior would need auditing. SciPy SLSQP for minimum variance — slow and fragile at N = 500.
- **Consequences:** Each estimator has a known-answer test (FACT-04, COV-03, PORT-02, PORT-04). The RF-01 decomposition is a starting point only: refit per window, missing values never filled with 0, one consistent scale.

### AD-09: Feature-test learner is LightGBM, measured as per-fold error reduction
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `research`
- **Context:** FTEST-03 and FTEST-04: information gain from a learned model with and without each feature, on purged walk-forward folds. The panel is about 2.5 million stock-days.
- **Decision:** LightGBM regression on cross-sectionally rank-normalized residual targets. The gain is the per-fold drop in out-of-sample MSE when a feature is added to a base set of past residual returns. The null is built per the `null-hypothesis-testing` skill by block-permuting the feature in time while keeping each cross-section intact. The model's settings are fixed before testing, with no tuning per feature.
- **Alternatives:** Ridge — misses non-linear effects. Random forests — slower at this size. Mutual information without a model — doesn't measure gain on top of the other inputs.
- **Consequences:** Gains are comparable across features. Runtime is about (features × horizons × folds × permutations) fits, so permutation counts are set by the skill's power analysis and run on all CPU cores.

### AD-10: Forecaster is a hand-built LSTM in PyTorch tensor operations
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `ml`
- **Context:** FCST-01–FCST-04 and FCST-08. The model must be built from basic array and autodiff operations, checked against an established reference within 5% validation loss, and trainable on a laptop or a cheap rented GPU. RF-02 shows the window structure (separate static, known and observed inputs); RF-03 shows the target construction.
- **Decision:** A multi-horizon LSTM encoder with linear heads for return and log-volatility, written with `torch` tensor operations and autograd only. Optimizer (Adam), initialization and loss are hand-written. The reference is `torch.nn.LSTM` with `torch.optim.Adam`, run in `ml.reference` from the same initial weights: a forward-pass match within 1e-6, then the validation-loss check from FCST-04. Windows follow RF-02's layout, but scalers are fitted only on trailing data, splits are purged and embargoed (`eval.purged_splits`), and windows break at gaps. Targets follow RF-03's forward windows, but delisted stocks keep their final returns, and incomplete horizons are dropped per horizon, not per row.
- **Alternatives:** A Temporal Fusion Transformer — hand-building one is large, and its reference library (pytorch-forecasting) is heavy; it's left as a later addition on the same windows. A temporal CNN — fine, but the LSTM has an exact reference in core PyTorch.
- **Consequences:** The FCST-03 gradient check and the reference check are cheap and exact. Model capacity is modest, which suits a laptop.

### AD-11: Forecast baselines
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `ml`
- **Context:** FCST-05 and FCST-06 name zero, trailing-mean and linear baselines for returns, and trailing, exponentially weighted and autoregressive baselines for volatility.
- **Decision:** For returns: zero, a 252-day trailing mean, and ridge regression (scikit-learn) on the same inputs. For volatility: 21-day trailing realized volatility, an EWMA with λ = 0.94, and GARCH(1,1) per stock from `arch`, refit on each training window.
- **Alternatives:** HAR-RV for volatility — needs intraday data for its best form. No linear baseline — then any neural gain could be a linear effect.
- **Consequences:** The best baseline per horizon becomes the FCST-07 comparison target.

### AD-12: PPO allocation agent over portfolio sleeves, checked against Stable-Baselines3
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `ml`
- **Context:** AGENT-01–AGENT-07. A 500-stock action space is too wide for PPO given about 4,000 training days. AGENT-04 and AGENT-05 require a hand-built PPO checked against an established implementation.
- **Decision:** The agent allocates across sleeves: the 10 S2 portfolios and one forecast portfolio per return horizon. Its action is Gaussian logits passed through a softmax, so the mixed stock weights always meet PORT-01. The environment implements the Gymnasium API with daily steps and monthly rebalances, with reward and costs as in AGENT-03 and EVAL-02. The PPO is hand-built (clipped objective, GAE, value loss, entropy bonus) from torch tensor operations. The reference is Stable-Baselines3 PPO on Pendulum-v1 and on this environment, with the same budget over 5 seeds.
- **Alternatives:** Direct per-stock weights through a Dirichlet policy — far too many action dimensions for the data. Picking the top K stocks — discontinuous, and turnover is hard to control.
- **Consequences:** The agent can only beat the forecast portfolios (AGENT-08) by timing sleeves, which is a fair and interpretable test. The sleeves must be computed before training.

### AD-13: FastAPI backend that tails the run store for live progress
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `server`
- **Context:** APP-06–APP-08 and QR-05: start runs, a single-run lock, progress within 2 s, progress from runs started on the command line, and recovery after a page reload. The brief fixes a Python HTTP + WebSocket backend.
- **Decision:** A FastAPI app on uvicorn, bound to 127.0.0.1. Runs execute in a child process through `data.start_run`, which takes the lock in `meta.sqlite`. The server polls `data.tail_progress` every 250 ms and broadcasts over `/ws/progress`. On connect it sends a snapshot of the current state first. JSON payloads are Pydantic models exported as JSON Schema.
- **Alternatives:** Flask with Socket.IO — weaker typing and schema export. Server-sent events — would work, but the brief names WebSocket.
- **Consequences:** Runs started from either the command line or the app look the same. A server restart doesn't kill a run.

### AD-14: React + Vite + ECharts frontend with types generated from the server's schema
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `web`
- **Context:** APP-01–APP-11 and QR-04 (views in ≤ 2 s; a stock chart in ≤ 1 s with about 5,000 daily points and markers). The brief fixes TypeScript + React.
- **Decision:** A Vite + React 18 single-page app. ECharts for time series, heatmaps and the spectrum plot. TypeScript types generated from the server's OpenAPI and JSON Schema (`openapi-typescript`), with contract fixtures shared from `tests/contracts/`. Visual design follows the `frontend-design` and `dataviz` skills.
- **Alternatives:** Plotly — heavier bundle and slower redraws for large series. D3 by hand — too much custom code for one person.
- **Consequences:** A schema change breaks the TypeScript build. That is intended.

### AD-15: Exchange calendar from pandas_market_calendars
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `data`
- **Context:** VAL-01, the VAL edge case on closure days, and the trading-day definitions behind EVAL-02, COV-04 and PAPER-05. RF-02 counted days while ignoring holidays.
- **Decision:** The XNYS calendar from `pandas_market_calendars` is the single source of trading days, wrapped by `data.trading_days`.
- **Alternatives:** Inferring trading days from price rows — circular, because it hides missing days. NumPy business days — ignore holidays.
- **Consequences:** One calendar for every package.

### AD-16: Compute and reproducibility for neural training
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `ml`
- **Context:** FCST-08, QR-08 (≤ $10 per rented-GPU run) and EVAL-09.
- **Decision:** Training picks a device in the order CUDA, then MPS (Apple GPU), then CPU. It sets `torch.use_deterministic_algorithms(True)` and records the device, seed, commit and settings hash. A rented-GPU run is the same CLI command on a cloud machine with a copy of the derived training arrays only (not the raw vendor data). Its cost is entered into the run record.
- **Alternatives:** CPU only — slow for the reference checks across 5 seeds.
- **Consequences:** FCST-08 reproducibility is promised per device type, not across devices.

### AD-17: Paper trading is a manual daily step with sealed orders
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `paper`
- **Context:** PAPER-01–PAPER-06. Updates are run by hand (spec Assumptions), and nothing connects to a broker.
- **Decision:** `qrp paper step` runs after `qrp data update`. It fills the orders sealed for the latest day at that day's close, then seals the next day's orders. Sealed orders are written to the ledger with the ID and timestamp of the data run they used, before any later data run exists. Frozen strategies are referenced by version hash. Missed days are recorded as gaps.
- **Alternatives:** A long-running scheduled service — the user chose manual updates. Placing orders against a broker's paper account — out of scope.
- **Consequences:** PAPER-02 is checked by comparing the ledger timestamps with `meta.sqlite` run timestamps.

## Risks and open questions
- **DATA-03 coverage is the vendor's claim, unverified.** `data.check_former_member_coverage` is the first validation task; if it fails, fall back to EODHD behind `data.Source` and expect the gaps listed in AD-02.
- **Sharadar licence:** local copies must be deleted within 30 days of cancelling. The rented-GPU copy holds only derived arrays, and is deleted after the run (AD-16).
- **FTEST runtime:** permutation counts × folds × features could exceed a laptop evening. Mitigation: the skill's power analysis sets the counts, and fits run in parallel.
- **S4 may well fail its verdict.** That is an honest outcome; the design records it rather than tuning until it passes (AD-06, AD-07).

# data — Architecture

**Package:** data · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`data` is the only package that writes the dataset. A data run (full, update or validate) downloads Sharadar bulk tables through `Source`, normalizes them into the Parquet store, computes returns, then validates and flags them. Each step emits progress events into `meta.sqlite`. Readers get a `Loader` bound to an as-of date, which enforces the holdout lock (AD-05). The first validation step is the former-member coverage check (DATA-03, AD-02).

## Data
- **Source tables:** Sharadar price (unadjusted and split-adjusted OHLCV, `closeadj`), `sp500` (added/removed events and snapshots), `actions` (splits, dividends, ticker changes, delistings) and `tickers` (`permaticker`, names, listing dates).
- **Store layout under the data root:** `raw/<table>/<download-date>.zip` · `store/prices/year=YYYY/*.parquet` · `store/{membership,changes,actions,securities,returns,flags}.parquet` · `meta.sqlite` (run records, progress events, run lock, holdout lock and grants).
- **Identity:** `SecurityId` = `permaticker`. Tickers are attributes with date ranges.
- **History window:** for each security, from 3 years before its first entry (but not before the data starts, 1997-12-31) to its last trading day.
- **Missing values:** never filled. A missing member-day is a row-less day plus a `missing` flag.

## Cross-cutting concerns
- **Retries (ING edge cases):** exponential backoff, at most 5 attempts per request, then the item is recorded as failed and the run continues.
- **Resume (ING-06):** per-security completion markers in `meta.sqlite`. Writes are atomic (temp file, then rename), so an interrupted run never leaves a half-written partition.
- **Corrections:** an update that changes stored values writes (security, date, field, old, new) rows into the run record.
- **Timing (QR-01–QR-03):** the CLI records the duration of each run, with time waiting on the source counted separately. The loader benchmark is a test with a marker.

# eval — Architecture

**Package:** eval · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`eval` scores every strategy the same way. At each rebalance date D it hands the strategy a `data.Loader` bound to D. It takes the target weights the strategy returns, fills the trades at the close of D+1 under the cost model, and holds the positions until the next rebalance. A stock that stops trading is handled per EVAL-04. Results are reported at 1× and 2× costs. Training-split helpers purge and embargo. Every run goes into the append-only run log (AD-06), and every significance verdict into the claims register (AD-07). Holdout runs go through `run_holdout`, which takes the single final-evaluation grant from `data`.

- **Sub-periods:** 2005–2009, 2010–2014, 2015–2019, and 2020 to the holdout start (COV-05). The same sub-periods are used for EVAL-07 reporting.

## Cross-cutting concerns

# research — Architecture

**Package:** research · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`research` holds the classical and statistical work. In S1 it runs the exploratory analysis with the `data-analysis` skill. In S2 it fits factors and covariance estimates per window and wraps each portfolio method × estimator as an `eval.Strategy`. It then compares the estimators with `data-analysis` and tests every comparison with `null-hypothesis-testing`, recorded as `eval.Claim`s. In S3 it computes point-in-time features and tests their information gain over out-of-sample residual returns. The result is stored as the `S3Verdict`, which gates S4. No PyTorch.

## Components
| Module | Responsibility | Covers | Depends on |
|---|---|---|---|
| `eda` | Dataset analysis report, built with the `data-analysis` skill | EDA-01–EDA-03 | `data` |
| `factors` | Per-window PCA, Marchenko–Pastur factor count, residuals, out-of-sample residual series (AD-08; RF-01 as a starting point) | FACT-01–FACT-05 | `data`, `windows` |
| `windows` | Estimation windows ending at D, with the ≥ 90%-present eligibility rule | COV-04, FACT edge cases | `data` |
| `cov` | Sample, shrinkage and denoised estimators; singular-window detection | COV-01–COV-04 | `windows` |
| `portfolios` | Minimum variance, risk parity, HRP and equal weight; the `classical_strategy` factory | PORT-01–PORT-06 | `cov`, `eval` |
| `s2` | S2 run: all 10 walk-forwards, the estimator comparison report (`data-analysis`), claims (`null-hypothesis-testing`), holdout benchmarks | COV-05, COV-06, PORT-07, PORT-08, QR-06 | `portfolios`, `cov`, `factors`, `eval` |
| `features` | Feature registry and point-in-time feature computation, on raw or residual returns | FEAT-01–FEAT-04 | `data`, `factors` |
| `ftest` | Residual forward targets, the LightGBM information-gain test (AD-09), claims, the S3 verdict | FTEST-01–FTEST-06 | `features`, `factors`, `eval` |

## Interfaces
See [contract.md](contract.md).

## Data
- **Outputs:** `results/eda/<run_id>/` (report and figures), `results/s2/<run_id>/` (spectra, comparison tables), `results/s2/benchmarks.json` (`S2Benchmarks`), `results/s3/<run_id>/` and `results/s3/verdict.json` (`S3Verdict`).
- **Claim families:** `cov-estimators`, `classical-portfolios`, `s3-features`. The `s3-features` family is all-time: every feature × horizon ever tested.
- **Residuals for later stages:** exposures fitted on the window ending at each rebalance D apply to returns from D+1 until the next rebalance (FACT-05). The series is stored once per window setting and reused by `ftest` and `ml`.

## Cross-cutting concerns
- **Truncation tests:** FACT-01 and FEAT-01 are checked by recomputing on data cut at D.
- **Known answers:** FACT-04 (planted 3 factors), COV-03 (pure noise is closer to the identity), PORT-02 (3-stock analytic solution), PORT-04 (2 blocks get 50/50).
- **Skills:** `data-analysis` runs inside `eda` and the `s2` comparison. `null-hypothesis-testing` designs every claim test in `s2` and `ftest`; this package never carries its own testing procedure.
- **Speed (QR-06):** the 10 S2 runs share one factor and covariance computation per window, cached by window end date.

# ml — Architecture

**Package:** ml · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`ml` only starts when `research.load_s3_verdict` finds at least one surviving feature. Windowed datasets are built from the survivors plus past returns and volatility, with targets at the surviving horizons. A hand-built LSTM (AD-10) is trained on purged walk-forward splits and compared with the AD-11 baselines. A reference check proves the hand-built version matches core PyTorch. The forecasts feed a forecast portfolio, which is an `eval.Strategy`. A hand-built PPO agent (AD-12) allocates across sleeves inside a Gymnasium backtest environment. Every verdict is an `eval.Claim`, compared against `research.S2Benchmarks`.

## Components
| Module | Responsibility | Covers | Depends on |
|---|---|---|---|
| `targets` | Forward residual return and volatility targets per horizon. Follows RF-03, but delisted stocks keep their final returns and incomplete horizons are dropped per horizon | FCST-01 | `research`, `data` |
| `windows` | Encoder windows (static / known / observed) with trailing-only scaling, break at gaps, purged splits (RF-02 layout, fixed) | FCST-02 | `targets`, `research`, `eval` |
| `nn` | Hand-built tensor layers (LSTM cell, linear, layer norm), Adam, initialization, losses, gradient checks | FCST-03, AGENT-04 | torch (tensors and autograd only) |
| `forecast` | Model definition, training loop, early stopping, divergence stop, device choice and seeding (AD-16) | FCST-01, FCST-02, FCST-08, QR-08 | `nn`, `windows` |
| `baselines` | Zero, trailing mean, ridge; trailing realized vol, EWMA, GARCH(1,1) | FCST-05, FCST-06 | `windows` |
| `compare` | Out-of-sample loss and rank correlation per horizon; FCST-07 claims | FCST-05–FCST-07 | `forecast`, `baselines`, `eval` |
| `fport` | Forecast portfolio strategy: forecasts + best S2 covariance → long-only weights, 50% turnover cap | FPORT-01, FPORT-02 | `forecast`, `research`, `eval` |
| `env` | Gymnasium allocation environment over sleeves: state, action, reward, costs | AGENT-01–AGENT-03 | `research`, `fport`, `eval`, `data` |

| `reference` | The only module allowed to use `torch.nn` layers, `torch.optim` and Stable-Baselines3: the FCST-04 and AGENT-05 checks | FCST-04, AGENT-05 | `forecast`, `ppo` |

## Interfaces
See [contract.md](contract.md).

## Data
- **Inputs:** surviving features (`research.compute_features`), out-of-sample residuals (`research.residual_returns`), the best S2 covariance (`research.estimate_cov` with `S2Benchmarks.best_estimator`).
- **Outputs:** `results/ml/forecast/<run_id>/` (forecasts, losses, model state), `results/ml/agent/<run_id>/seed=<k>/`, verdicts in the claims register.
- **Claim families:** `forecast-vs-baseline`, `fport-vs-s2`, `agent-vs-s2`, `agent-vs-fport`.
- **Rented GPU:** only the derived window arrays and model code are copied out, never raw vendor files (AD-16).

## Cross-cutting concerns
- **Forbidden imports:** outside `reference`, a lint check rejects `torch.nn.<Layer>`, `torch.nn.functional`, `torch.optim` and `stable_baselines3`. `torch.Tensor` operations, `torch.autograd` and `nn.Parameter` are allowed.
- **Policy collapse:** `ppo` flags any 20-day run with one stock above 50% weight (looking through sleeves to stock weights).
- **Divergence:** training stops when the loss is NaN or 10× its starting value. The run is logged as failed with the step it stopped at.

# paper — Architecture

**Package:** paper · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
A paper session holds frozen candidate strategies and all 10 S2 portfolios, each pinned to a version. `qrp paper step` runs by hand after each `qrp data update` (AD-17). It first fills the orders sealed for the latest close D at D's close, under the cost model. Then it asks each strategy for D+1 weights using a loader as of D, and seals those orders in the append-only ledger, stamped with the data run they used. Once a session has 63 or more days, the directional forward test (PAPER-05) is computed and recorded as an `eval.ForwardTestResult`, with informational p-values from the `null-hypothesis-testing` skill.

## Components
| Module | Responsibility | Covers | Depends on |
|---|---|---|---|
| `session` | Create a session from frozen strategy versions; any version change starts a new session | PAPER-01, PAPER-04 | `eval`, `research`, `ml` |
| `ledger` | Sealed orders, fills and gaps on `eval.AppendLog` | PAPER-02, PAPER-06 | `eval` |
| `step` | Daily step: fill the previous orders, seal the next, record gaps | PAPER-02, PAPER-03 | `session`, `ledger`, `data`, `eval` |
| `forward` | The 63-day directional test, informational claims, `record_forward_test` | PAPER-05 | `ledger`, `eval`, `research` |
| `cli` | `qrp paper start|step|status` | — | `session`, `step`, `forward` |

## Interfaces
See [contract.md](contract.md).

## Data
- **Ledger:** `results/paper/ledger.sqlite`, with append-only tables `orders`, `fills`, `gaps` and `sessions`. Each order row holds the session, strategy version, target date, weights, the `data.RunRecord.run_id` it was decided on, and a sealed timestamp.
- **Seal check (PAPER-02):** a fill is accepted only if its order's sealed timestamp is earlier than the start of the data run that loaded the fill-day prices.

## Cross-cutting concerns
- **Missed days:** a step whose latest close is more than one trading day after the last sealed order records a gap. It never makes orders after the fact.
- **No broker:** the package makes no network calls.

## Project layout

packages/paper/tests/
```

# server — Architecture

**Package:** server · **Status:** Draft · **Last updated:** 2026-10-17 · **System:** [../../architecture.md](../../architecture.md)

## Overview
A FastAPI app on uvicorn, bound to 127.0.0.1 (AD-13). HTTP routes serve dataset queries through `data.Loader` and stored results from `research`, `eval`, `ml` (stored records only) and `paper` (stored records only). Run control calls `data.start_run`, which runs in a child process. A background task polls `data.tail_progress` every 250 ms and broadcasts new events on `/ws/progress`. A new connection gets a snapshot of the current state first. Response models are Pydantic, and their JSON Schema is the contract with `web`.

## Components
| Module | Responsibility | Covers | Depends on |
|---|---|---|---|
| `app` | App factory, CORS for the local dev origin, error mapping (typed errors → 4xx with a message) | QR-04 (server side) | all below |
| `dataset` | Universe, stock history, flags, coverage and EDA routes | APP-01–APP-05 (backend) | `data`, `research` |
| `runs` | Start-run route, run list, run record and validation report routes | APP-06, APP-08 | `data` |
| `live` | WebSocket progress broadcast, snapshot on connect, heartbeat | APP-07, APP-08, QR-05 | `data` |
| `results` | Read-only results: S2 spectra and comparisons, S3 feature results, S4 forecasts, verdicts, paper ledger | APP-09–APP-11 (backend) | `research`, `eval`, `ml`, `paper` stored outputs |
| `schemas` | Pydantic response models; JSON Schema export for `web` and `tests/contracts/` | — | — |

`results` reads `ml` and `paper` outputs as stored files and log rows through `eval.claims` and `eval.forward_test`, so `server` never imports `ml` or `paper` code. The torch stack stays out of the server.

## Interfaces
See [contract.md](contract.md).

## Cross-cutting concerns
- **Latency (QR-05):** 250 ms polling + broadcast stays well under 2 s. A test compares each event's `ts` with its send time.
- **Payload size (QR-04):** stock history is served as columns of arrays, about 5,000 points; flags are paged 200 at a time.
- **Errors:** `RunInProgressError` → 409, `OutOfRangeError` → 400, a missing report → 404 with the command that produces it.

packages/server/src/server/{app,dataset,runs,live,results,schemas}/
packages/server/tests/
