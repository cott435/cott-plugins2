# Quant Research Platform — Spec

**Status:** Draft · **Last updated:** 2026-10-17 · **Brief:** [brief.md](brief.md)

## Summary
A personal, local research platform for daily S&P 500 equities, built in four stages: a trustworthy point-in-time dataset with a browser explorer; return-structure analysis and classical risk-based portfolios; candidate features tested against chance; and neural forecasts and trading agents that must beat the classical portfolios after costs on years that were never looked at. Why: see the [brief](brief.md).

## Users
| User | What they need to do |
|---|---|
| The researcher (sole user) | Build and update the dataset, check it, explore it in the browser, run each stage's experiments, and read one scoreboard of honest out-of-sample results |

## Scope
**In scope:** Data download & update, Validation & cross-check, Point-in-time loader, Exploratory analysis, Explorer app, Live run progress, Backtest & scoreboard, Held-out lock, Factor decomposition, Covariance estimation, Classical portfolios, Candidate features, Feature significance, Forecasting, Forecast-driven portfolios, Trading agents, Final verdict.

**Out of scope:**
- Real-money or live broker trading; only paper results from backtests.
- Small and mid caps, non-US stocks, other asset classes, intraday data.
- Short selling, leverage, or any position above 5% of the portfolio.
- Return prediction before covariance estimation and classical portfolios are scored (S2 precedes S3 and S4).
- Any use of the held-out years before a stage's final verdict.
- Hosting, logins, multiple users, remote access.
- Editing or correcting data from the app.
- Scheduled or automatic updates; updates run when the researcher starts them.

## Features

### Data download & update (`INGST`)
**Serves:** Goal 1
**Behavior:** The researcher starts a full build or an incremental update. The system fetches every security that was an S&P 500 member at any time since January 2005, delisted ones included, with prices, corporate actions and membership history, and stores it locally as one dated snapshot.

**Requirements**
- **INGST-01** A full build fetches the complete history for every security that was an index member at any time from 2005-01-03 to the latest trading day.
  - Given an empty local store, when a full build completes, then every security on the point-in-time membership list since 2005-01-03 has price history for each day it was a member.
  - Given a security delisted in 2009, when the full build completes, then its history up to its last trading day is present.
- **INGST-02** An incremental update fetches only trading days after the latest stored day.
  - Given a store complete to day D, when an incremental update runs on day D+3, then only days D+1 to D+3 are fetched and earlier stored values are unchanged unless the source revised them.
- **INGST-03** Revisions the source makes to already-stored history are detected and recorded.
  - Given the source changes a stored close, when an update runs, then the change is applied and recorded with old value, new value and the update date.
- **INGST-04** Every build or update produces a numbered snapshot that later steps can name.
  - Given two updates on different days, when a backtest names snapshot 1, then it sees exactly the data of snapshot 1.
- **INGST-05** An interrupted run can be resumed without refetching completed securities.
  - Given a full build stopped at security 300 of 1,000, when it is resumed, then securities 1-299 are not fetched again and the result equals an uninterrupted build.
- **INGST-06** Raw fetched data is kept unchanged alongside the cleaned data.
  - Given a cleaned value, when the researcher asks for its origin, then the raw value it came from is shown.

**Edge cases & errors**
- Source unreachable or rate-limited → the run retries with back-off, then stops with a clear error naming what was not fetched; the previous snapshot stays usable.
- Credentials missing or rejected → the run stops before fetching anything, with a message saying which credential failed.
- A ticker symbol reused by a different company → the two histories are kept separate under different permanent identifiers.

### Validation & cross-check (`VALID`)
**Serves:** Goal 1
**Behavior:** After each build or update the system checks the data for internal consistency and compares it against a second, independent source, then writes a validation report. A snapshot is usable for research only once its report has no unexplained failures.

**Requirements**
- **VALID-01** Each snapshot is checked for internal consistency: no duplicate (security, day) rows, no non-positive prices, high ≥ open, close ≥ low, and no price on a non-trading day.
  - Given a snapshot with a duplicated row, when validation runs, then the report lists it as a failure with the security and date.
- **VALID-02** Each snapshot is checked for coverage: on every trading day, the number of members with a price equals the number of members on the membership list.
  - Given a day where a member has no price, when validation runs, then the report lists the security and day as a coverage gap.
- **VALID-03** Daily returns beyond ±40% are flagged for review against corporate actions.
  - Given a −50% return on a split ex-date with no recorded split, when validation runs, then it is flagged as a likely missing corporate action.
- **VALID-04** Adjusted daily returns are compared with the second source on every overlapping (security, day); they must agree within 1 basis point.
  - Given an overlapping day where the two sources differ by 3 basis points, when cross-check runs, then the pair is listed as a mismatch with both values.
- **VALID-05** Unadjusted closes are compared with the second source; they must agree within 0.5%.
  - Given a close differing by 1%, when cross-check runs, then it is listed as a mismatch.
- **VALID-06** Every failure and mismatch carries a status: unexplained, explained (with a written reason), or corrected.
  - Given a snapshot with one unexplained mismatch, when a research run asks to use it, then the run is refused and names the open item.
- **VALID-07** The report states the overlap coverage with the second source as a share of member-days.
  - Given a cross-check, when the report is written, then it shows the share of member-days compared, per year.

**Edge cases & errors**
- Second source has no data for a security (e.g. long delisted) → listed as "not cross-checkable", not as a failure.
- The two sources disagree on a corporate action date → listed as a mismatch on the action, not on every affected day.

### Point-in-time loader (`LOAD`)
**Serves:** Goal 1, Goal 3
**Behavior:** Every later stage gets its data through one loader. Given a snapshot, a date range and an as-of rule, it returns prices, total returns and the index universe exactly as they were known on each day.

**Requirements**
- **LOAD-01** The universe on day t is the list of index members on day t, including securities later removed or delisted.
  - Given a security removed from the index in 2012, when the universe for 2010-06-01 is requested, then it is included; for 2013-06-01 it is not.
- **LOAD-02** Daily total returns include dividends on their ex-dates and are unaffected by splits.
  - Given a 2-for-1 split on day t, when returns are loaded, then the return on day t reflects only the real price change.
  - Given a cash dividend ex-dated day t, when returns are loaded, then the return on day t includes it.
- **LOAD-03** Returns for past days do not change when a later corporate action is recorded.
  - Given returns loaded from snapshot 1, when snapshot 2 adds a split dated after snapshot 1's last day, then returns for days in snapshot 1 are identical.
- **LOAD-04** A delisted security's final return is included: the reported delisting return, or, if none is reported, an assumed return (default −30% for performance-related delistings, 0% for mergers and acquisitions), flagged as assumed.
  - Given a delisting for bankruptcy with no reported delisting return, when returns are loaded, then the last return is −30% and flagged.
  - Given the researcher sets the performance default to −50%, when returns are loaded, then that value is used.
- **LOAD-05** A request for any day inside the locked held-out period is refused unless the stage holds an unlock (see `HOLD`).
  - Given the lock is active, when a load reaches into the held-out period, then it fails with an error naming the lock.
- **LOAD-06** Each loaded panel records which snapshot and settings produced it.
  - Given a loaded panel, when its origin is inspected, then snapshot number, date range and delisting defaults are shown.

**Edge cases & errors**
- A member with missing prices on some days → returns for those days are missing, never filled with zero; later steps decide how to treat them.
- A ticker change mid-membership → one continuous history under the permanent identifier.

### Exploratory analysis (`EDA`)
**Serves:** Goal 1
**Behavior:** A repeatable analysis of each validated snapshot, run with the `data-analysis` skill, characterising the dataset before any modelling.

**Requirements**
- **EDA-01** The `data-analysis` skill is run on the snapshot's daily returns and reports, per year: member count, missing share, return distribution and tail statistics, and largest absolute returns.
  - Given a validated snapshot, when the analysis runs, then a report with those statistics for every year from 2005 is produced.
- **EDA-02** The report shows how average pairwise correlation and the largest eigenvalue's share of variance move over time on trailing 252-day windows.
  - Given the 2008-09 crisis, when the report is read, then both series are shown through it.
- **EDA-03** The report shows universe turnover: additions, removals and delistings per year.
  - Given the snapshot, when the report is read, then those counts are shown for each year.

### Explorer app (`APP`)
**Serves:** Goal 5
**Behavior:** A browser app running on the researcher's own machine to explore the stored data and results. It reads only; it never changes data.

**Requirements**
- **APP-01** The researcher can search any security, current or delisted, and see its price and total-return history with corporate actions and membership periods marked.
  - Given a delisted security, when it is searched, then its chart appears with the delisting date marked.
- **APP-02** The researcher can pick any date and see that day's universe with each member's return.
  - Given 2008-09-15, when chosen, then the members on that day and their returns are listed.
- **APP-03** The researcher can browse the latest validation report and filter its items by status.
  - Given a report with unexplained items, when filtered to "unexplained", then only those are shown.
- **APP-04** The researcher can view the exploratory analysis charts for any snapshot.
  - Given snapshot 2, when chosen, then its EDA charts are shown.
- **APP-05** The researcher can view the scoreboard and compare any two entries side by side.
  - Given two scoreboard entries, when compared, then their metrics and cumulative after-cost returns are shown together on the same period.
- **APP-06** Every message between the app and the backend matches one shared, versioned contract; a message that does not is rejected and shown as an error.
  - Given the backend sends a field the contract does not define, when the app receives it, then the app shows a contract error and does not render the bad data.

**Edge cases & errors**
- Backend not running → the app says so and offers a retry, instead of an empty screen.
- A view reaches into the held-out period while it is locked → those days are hidden and labelled "held out".

### Live run progress (`RUNS`)
**Serves:** Goal 5
**Behavior:** While a download or validation run is working, the app shows its progress as it happens, without refreshing.

**Requirements**
- **RUNS-01** The researcher can start a full build, incremental update or validation from the app.
  - Given no run in progress, when "incremental update" is started, then a run begins and appears in the app.
- **RUNS-02** A running job shows securities done out of total, current step, elapsed time, estimated time left and error count, updated at least every 2 seconds.
  - Given a running full build, when the app is open, then the counts change at least every 2 seconds.
- **RUNS-03** Errors and warnings appear in a live log as they occur.
  - Given a security fails to fetch, when it fails, then a log line naming it appears within 2 seconds.
- **RUNS-04** Closing the app does not stop a run, and reopening it shows the run's current state.
  - Given a run at 40%, when the app is closed and reopened, then it shows the run at its current progress with the full log so far.
- **RUNS-05** Only one data-changing run can be active at a time.
  - Given a full build running, when an update is started, then it is refused with a message naming the running job.
- **RUNS-06** A run can be cancelled from the app, leaving the previous snapshot intact.
  - Given a running update, when cancelled, then it stops within 10 seconds and the previous snapshot is still the current one.

### Backtest & scoreboard (`SCORE`)
**Serves:** Goal 3, Goal 4
**Behavior:** Every strategy, from the equal-weight baseline to the trading agents, is run through the same backtest with the same rules and costs, and its results land as one entry on one scoreboard.

**Requirements**
- **SCORE-01** All strategies obey the same portfolio rules: long only, fully invested, no leverage, no position above 5%, holdings only from the point-in-time universe at each rebalance.
  - Given a strategy proposing a 7% weight, when the backtest applies it, then the run fails with a rule violation; it is never silently clipped.
- **SCORE-02** The headline rebalance is weekly, at the last trading day's close of each week; a monthly rebalance is reported as a sensitivity.
  - Given any strategy entry, when it is read, then weekly (headline) and monthly results are both shown.
- **SCORE-03** Weights for a rebalance use only data through the close of the day before the trade; trades execute at the rebalance day's close.
  - Given a strategy whose weights depend on the rebalance day's own return, when the backtest is checked by the look-ahead test (a strategy given tomorrow's return must not gain), then it is detected and fails.
- **SCORE-04** Trading costs are 5 basis points one way per unit of turnover; a 15-basis-point stress case is also reported.
  - Given a rebalance with 40% turnover, when costs are charged, then 0.4 × 5 bp = 2 bp is deducted at headline and 6 bp in the stress case.
- **SCORE-05** Between rebalances holdings drift with returns; a holding that leaves the index is kept until the next rebalance; a holding that delists takes its delisting return and its proceeds are held as cash at zero return until the next rebalance.
  - Given a holding delisted mid-week, when the week ends, then its delisting return is applied and the proceeds sit in cash.
- **SCORE-06** Each entry reports annualised Sharpe ratio after costs (headline), annualised realised volatility, average weekly turnover, maximum drawdown and the period covered.
  - Given a finished backtest, when its entry is read, then all five are shown for weekly/monthly × 5 bp/15 bp.
- **SCORE-07** The equal-weight portfolio over the point-in-time universe is always on the scoreboard as the baseline.
  - Given any comparison, when the scoreboard is shown, then the equal-weight entry for the same period is present.
- **SCORE-08** Each entry records the snapshot, strategy settings, random seed and code version that produced it, and rerunning with those gives identical numbers.
  - Given an entry, when rerun from its record, then all metrics match to the last reported digit.
- **SCORE-09** Development results use walk-forward evaluation on 2008-01-01 up to the held-out start: every estimate used at a date is fitted only on data before it.
  - Given a development backtest, when any fitted object used on date t is inspected, then its fitting window ends before t.
- **SCORE-10** Claims that one strategy beats another are tested with the `null-hypothesis-testing` skill on the after-cost return series; a claim passes only if significant at 5% after correction for the number of comparisons made.
  - Given two strategies whose Sharpe ratios differ by 0.1, when the test does not reject at 5% corrected, then the scoreboard marks the difference "not significant".

### Held-out lock (`HOLD`)
**Serves:** Goal 3, Goal 4
**Behavior:** The final 3 years of data are locked away at the start of the project. A stage can unlock them once, for its final verdict, after declaring what it will evaluate. Every unlock is logged.

**Requirements**
- **HOLD-01** The held-out period starts at a fixed date, three years before the last trading day of the first validated snapshot, and runs to the latest data; the start date never moves.
  - Given the first validated snapshot ends 2026-10-16, when the lock is set, then held-out starts 2023-10-17 and all later data, including future updates, is held out.
- **HOLD-02** A stage unlocks only after recording its pre-registration: the strategies or models to evaluate, the comparisons, metrics and significance bar.
  - Given no pre-registration for S2, when S2 requests unlock, then it is refused.
- **HOLD-03** Each stage can unlock once; a second unlock for the same stage needs a written reason and marks every result produced after it "re-opened".
  - Given S2 has unlocked once, when it requests again with a reason, then the unlock proceeds and later S2 held-out results carry the "re-opened" mark.
- **HOLD-04** Every unlock is logged with the date, stage, pre-registration and reason.
  - Given two unlocks, when the log is read, then both appear with their details.
- **HOLD-05** Held-out results report only the pre-registered comparisons; anything else run during an unlock is marked "exploratory".
  - Given an unregistered strategy run during an unlock, when it reaches the scoreboard, then it is marked exploratory.

### Factor decomposition (`FACT`)
**Serves:** Goal 4
**Behavior:** Returns are decomposed into their principal components on trailing windows; the market and other dominant components are removed, leaving residual returns used by later stages.

**Requirements**
- **FACT-01** On each date the principal components of the standardised returns are fitted on the trailing 252 trading days only (504 as a sensitivity).
  - Given residuals for day t, when the fit behind them is inspected, then it uses days t−252 to t−1 only.
- **FACT-02** The number of components removed is either fixed by the researcher or set to the count of eigenvalues above the noise edge predicted for pure-noise data of the same shape.
  - Given the automatic setting, when a window is fitted, then the chosen count and the noise edge are recorded for that date.
- **FACT-03** Residual returns for day t are the day-t returns minus their projection on the components fitted before day t.
  - Given a synthetic panel with one planted market factor and independent noise, when one component is removed, then the residuals' mean absolute pairwise correlation is within 0.02 of the noise-only value.
- **FACT-04** A report, run with the `data-analysis` skill, shows over time the variance share of each removed component and the mean absolute pairwise correlation before and after removal.
  - Given a development run, when the report is read, then both series are shown from 2008 to the held-out start.

**Edge cases & errors**
- A member with fewer than 200 of the trailing 252 days → excluded from that window's fit and residuals, and the exclusion counted.

### Covariance estimation (`COV`)
**Serves:** Goal 4
**Behavior:** Three covariance estimates are built on the same trailing windows — sample, shrinkage toward a structured target, and denoised (eigenvalues inside the pure-noise band replaced by their average, the rest kept) — and compared on how well they control variance out of sample.

**Requirements**
- **COV-01** Each estimator is fitted at each rebalance on the trailing 252 trading days only (504 as a sensitivity).
  - Given an estimate used on rebalance date t, when its window is inspected, then it ends at t−1.
- **COV-02** The denoised estimate keeps eigenvalues above the pure-noise edge and replaces those below it with their mean, preserving the trace.
  - Given a synthetic matrix with 3 planted factors plus noise, when denoised, then exactly 3 eigenvalues exceed the edge and the trace equals the sample trace.
- **COV-03** Every estimate is symmetric and positive definite.
  - Given any rebalance date, when an estimate is checked, then its smallest eigenvalue is above zero.
- **COV-04** Estimators are compared by the realised out-of-sample variance of the minimum-variance portfolio built from each, using the `data-analysis` skill for the comparison report and the `null-hypothesis-testing` skill for whether differences are significant at 5% corrected.
  - Given a development run, when the comparison finishes, then each estimator's realised variance, its ranking and the significance of each pairwise difference are reported.
- **COV-05** The comparison is also reported per sub-period (2008-09, 2010-19, 2020-held-out start).
  - Given the report, when read, then the ranking for each sub-period is shown.

### Classical portfolios (`PORT`)
**Serves:** Goal 3, Goal 4
**Behavior:** Minimum-variance, risk parity and hierarchical risk parity portfolios are built from each covariance estimate and scored on the scoreboard against the equal-weight baseline.

**Requirements**
- **PORT-01** Minimum-variance weights minimise predicted variance under the shared portfolio rules.
  - Given a known 3-asset covariance with a closed-form solution inside the constraints, when weights are computed, then they match it within 1e-6.
- **PORT-02** Risk-parity weights give each holding an equal contribution to predicted risk, within the 5% cap.
  - Given a diagonal covariance, when weights are computed, then each is proportional to inverse volatility.
- **PORT-03** Hierarchical risk-parity weights come from clustering assets by correlation and splitting risk down the cluster tree.
  - Given two uncorrelated blocks of identical assets, when weights are computed, then each block receives half the weight.
- **PORT-04** Every portfolio × estimator combination is a scoreboard entry on development data.
  - Given 3 portfolio methods and 3 estimators, when S2's development run completes, then 9 entries plus equal-weight are on the scoreboard.
- **PORT-05** S2's held-out verdict compares the pre-registered portfolios with equal weight on the held-out years under `HOLD`.
  - Given S2's pre-registration, when the unlock runs, then only those comparisons are reported as S2's verdict.

### Candidate features (`FEAT`)
**Serves:** Goal 2, Goal 4
**Behavior:** The researcher defines candidate features in a catalogue; each is computed per security and day from data known at that day's close.

**Requirements**
- **FEAT-01** Every feature tried is registered in the catalogue with its definition, lookback and the date it was added, before it is tested.
  - Given a feature tested without a catalogue entry, when the test starts, then it is refused.
- **FEAT-02** A feature value for day t uses only data through day t's close.
  - Given the look-ahead test (shifting all inputs after t changes nothing at t), when run on each feature, then every feature passes.
- **FEAT-03** Features are computed only for securities in the point-in-time universe on that day.
  - Given a security not yet a member on day t, when features are computed, then it has no value on day t.
- **FEAT-04** Feature scaling or encoding is fitted on training data only; categories unseen in training map to an "unknown" value.
  - Given a sector that first appears after the training window, when encoded, then it is "unknown" and no error occurs.

### Feature significance (`SIG`)
**Serves:** Goal 2
**Behavior:** Each candidate is tested for information gain over the market-removed residual return: does a learned model predict next-period residual returns better with the feature than without it, out of sample, beyond chance?

**Requirements**
- **SIG-01** The target is the residual return (from `FACT`) over the next 1, 5 and 21 trading days, including delisting returns.
  - Given a security that delists 3 days after t, when its 5-day target is built, then it includes the delisting return rather than being dropped.
- **SIG-02** Information gain is measured out of sample on walk-forward folds within the development period, with a gap between training and test at least as long as the target horizon.
  - Given a 21-day target, when folds are built, then no training label's window overlaps any test day.
- **SIG-03** Each feature's information gain is tested with the `null-hypothesis-testing` skill; it passes only if the false discovery rate across every feature in the catalogue is held at 10%.
  - Given 40 catalogued features, when tests finish, then the correction counts all 40, including ones abandoned early.
- **SIG-04** Every result, pass or fail, is recorded with its effect size, raw and corrected p-value, horizon and fold scheme.
  - Given a failed feature, when results are read, then it appears with its numbers.
- **SIG-05** A planted-signal check shows the procedure can find a real effect and rejects noise: a synthetic feature built from the future target passes, and pure-noise features pass no more often than the 10% rate allows.
  - Given 100 noise features and 1 planted one, when tested, then the planted one passes and the false-discovery share among passes is at most 10% on average across repeats.

### Forecasting (`FCST`)
**Serves:** Goal 4
**Behavior:** Neural-network forecasters predict residual returns and volatility at 1, 5 and 21 days from price history and the features that passed `SIG`, and are compared against simple baselines.

**Requirements**
- **FCST-01** Inputs are limited to price-derived history, calendar information known in advance, and features that passed `SIG`.
  - Given a feature that failed `SIG`, when a forecaster is configured with it, then configuration is refused.
- **FCST-02** Volatility forecasts are compared against trailing realised volatility and an exponentially weighted trailing volatility.
  - Given a development run, when results are reported, then each forecaster's volatility loss is shown next to both baselines.
- **FCST-03** Return forecasts are compared against a zero forecast and a trailing-mean forecast, by the rank correlation between forecast and realised residual return.
  - Given a development run, when results are reported, then each forecaster's rank correlation is shown next to both baselines.
- **FCST-04** Training, validation and test periods are split by forecast date with a gap at least as long as the horizon.
  - Given a 5-day horizon, when the split is checked, then no training target window reaches into validation.
- **FCST-05** A forecaster beats a baseline only if the `null-hypothesis-testing` skill finds the loss difference significant at 5%, corrected for the number of forecaster × baseline × horizon comparisons.
  - Given 2 forecasters, 4 baselines and 3 horizons, when tested, then the correction counts all those comparisons.
- **FCST-06** Results are reported as the median across at least 5 training seeds, with the spread.
  - Given a forecaster, when its result is reported, then the median and range over ≥ 5 seeds are shown.

### Forecast-driven portfolios (`FPORT`)
**Serves:** Goal 3, Goal 4
**Behavior:** Portfolios that use the return and volatility forecasts, combined with the best covariance estimate from S2, under the shared portfolio rules.

**Requirements**
- **FPORT-01** Each forecast-driven portfolio uses forecasts from forecasters that beat their baselines in `FCST`, plus a covariance estimate from `COV`.
  - Given a forecaster that did not beat its baselines, when a portfolio is configured with it, then configuration is refused.
- **FPORT-02** Each forecast-driven portfolio is a scoreboard entry under the shared rules and costs.
  - Given a finished development run, when the scoreboard is read, then the entry shows the same metrics as every other entry.

### Trading agents (`AGENT`)
**Serves:** Goal 3, Goal 4
**Behavior:** Reinforcement-learning agents learn to set portfolio weights in a backtest environment that applies the shared rules and costs, trained only on development data.

**Requirements**
- **AGENT-01** The training environment applies exactly the backtest's rules, costs and rebalance schedule.
  - Given the same weights, when applied in the environment and in the backtest, then after-cost returns match to 1e-10.
- **AGENT-02** The agent's observation at a rebalance contains only data through the previous close.
  - Given the look-ahead test, when run on the environment, then it passes.
- **AGENT-03** Agents are trained only on development data; held-out data is reachable only through `HOLD`.
  - Given the lock is active, when training reaches the held-out start, then the episode ends.
- **AGENT-04** Agent results are reported as the median across at least 5 training seeds, with the spread.
  - Given an agent, when scored, then median and range over ≥ 5 seeds are on its scoreboard entry.
- **AGENT-05** Each agent is a scoreboard entry under the shared rules and costs.
  - Given a trained agent, when evaluated, then its entry has all `SCORE-06` metrics.

### Final verdict (`VERD`)
**Serves:** Goal 3, Goal 4
**Behavior:** The project's closing comparison: pre-registered forecast-driven portfolios and agents against pre-registered classical portfolios, on the held-out years, after costs.

**Requirements**
- **VERD-01** Candidates on both sides are chosen on development data and pre-registered before the S4 unlock.

## Assumptions
- History starts 2005-01-03, giving three years of warm-up before 2008.
- Delisting returns not reported by the source default to −30% (performance-related) and 0% (mergers and acquisitions), configurable and flagged.
- Cross-check tolerances: 1 basis point on adjusted daily returns, 0.5% on unadjusted closes.
- Trailing estimation window of 252 trading days, 504 as a sensitivity.
- Updates run on demand only.
- The app is read-only over stored data, apart from starting and cancelling runs.
- A 3-year held-out period is accepted although it gives little statistical power; "no significant difference" is the likely and acceptable verdict.
- Weights are computed from data through the previous close and traded at the rebalance day's close.
