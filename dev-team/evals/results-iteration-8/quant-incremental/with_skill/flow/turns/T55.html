# Quant Research Platform — Architecture

**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
`qdata` is the read side: the Python library research code imports. It owns snapshot storage, derives identities, adjusted prices and returns, and serves everything through one `Loader`; it never touches the network. `qops` is the operations side and its command line: it downloads the S&P 500 dataset from Sharadar into snapshots through `qdata`, validates them into flags, runs the exploratory report, and owns run processes and their progress. `server` is a local-only Python backend that answers `cockpit`'s queries through that `Loader`, starts runs, and streams their progress. `cockpit` is the TypeScript and React browser app. `qrisk` is the variance research package: a walk-forward test bench that compares covariance estimators and portfolios out of sample, reading only through `qdata.Loader`. `qfeat` is the feature lab: it scores hand-written features against next-month residual returns on `qrisk`'s windows and factor structure, tests every claim against a null, and keeps its registrations and holdout record in the repository. Runs execute in their own processes and log progress to disk, so the command line and the app see the same runs.

## Dependency rules
- `qdata` imports nothing internal, and never `qops`, `server`, a network client or a web framework: research code that imports it can't reach a vendor.
- `qops` imports `qdata` only through names exported from `qdata` itself; never `server` or a web framework.
- `qrisk` imports `qdata` only through its top-level exports; never `qops`, `server`, `qfeat`, a network client, a web framework or a machine-learning library.
- `qfeat` imports `qdata` and `qrisk` only through their top-level exports; never `qops`, `server`, a network client or a web framework.
- `server` imports `qdata` and `qops` only through their top-level exports; only `qfeat` imports `qrisk`, and nothing imports `qfeat`.
- `cockpit` talks only to `server`, only through types generated from `server`'s JSON Schema.
- Only `qdata.snapshots` writes snapshot, derived and validation storage; only `qops.runs` writes run records; only `qfeat.registry` writes `registry/`.
- Enforced by `import-linter` contracts and a schema-drift check, both run by the project's check script (AD-01, AD-09).

## Cross-package contracts
### AD-26: `qrisk` and `qfeat` stay whole above the pipeline guideline
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `qrisk`, `qfeat`
- **Context:** The Grow guideline is about 3 pipelines per package. `qrisk` has 5 (PL-18–PL-21, PL-30) and `qfeat` has 6 (PL-24–PL-29). The user chose to keep both whole (2026-10-17). Each package's pipelines share one set of frozen types and one results store, and `qfeat`'s holdout guard depends on its registry sitting beside the pipelines that read it.
- **Decision:** Neither package splits on pipeline count. A split is reconsidered only if a contract passes 200 lines, a package passes ~12 modules per component group, or a part gains a dependency stack or a deployment of its own.
- **Alternatives:** Split `qfeat` into a registry package and a scoring package — the holdout guard becomes a cross-package call, and the six pipelines would still share every type. Split `qrisk` by bench versus walk-forward — both run PL-19, so the seam would cross its most-used pipeline.
- **Consequences:** `dt status` keeps reporting both triggers; this decision is the record that they were weighed. The contracts (82 + 14 and 105 lines) stay under the ceiling.

**Overview (S3 sentence)**
> `qfeat` is the feature lab: it scores hand-written features against next-month residual returns on `qrisk`'s windows and factor structure, tests every claim against a null, and keeps its registrations and holdout record in the repository.

The diagram adds `qfeat → qrisk` (`build_windows`, `analyse_structure`), `qfeat → qdata` (`Loader`) and `qfeat → registry`.

**Packages row**

| Package | Covers | Depends on |
|---|---|---|

**Dependency rules (new or changed)**
- `qrisk` never imports `qops`, `server`, `qfeat`, a network client, a web framework or a machine-learning library.
- `qfeat` imports `qdata` and `qrisk` only through their top-level exports. It never imports `qops`, `server`, a network client or a web framework.
- Only `qfeat` imports `qrisk`, and nothing imports `qfeat`.
- Only `qfeat.registry` writes `registry/`.

**Cross-package contract:** `qrisk.build_windows`, `qrisk.analyse_structure`, `RunConfig`, `Window` and `Spectrum` are provided by `qrisk` and used by `qfeat`.

**System pipelines**
- **PL-22, development run:** open the loader, clipped at the development end (AD-25). Then `qrisk.build_windows`, then `qrisk.analyse_structure`, then `Loader` reads, producing a `qfeat.LabResult`.
- **PL-23, holdout:** open the unclipped loader only after the seal check. Then windows and structure, then `Loader` reads, producing a `LabResult`, with the result written into the `HoldoutRecord`.

**Tech stack (new rows)**

| Area | Choice | Decision |
|---|---|---|
| Feature lab | `qfeat`; registry committed to the repo | AD-21, AD-24 |
| Model | scikit-learn `HistGradientBoostingRegressor` on per-month ranks, fixed settings | AD-22 |
| Feature null | within-date shuffles: shadow copies for gains, shuffled ranks for screens | AD-23 |
| Holdout isolation | development-clipped `Loader` wrapper | AD-25 |

The Significance row now cites AD-20 and AD-23. The layout adds `packages/qfeat/` and `registry/`. The privacy note says `registry/` holds no source data.

**Decisions (all Accepted)**
- **AD-21, separate `qfeat` package.** Keeps ML out of the variance package and reuses Stage 2's windows and residuals rather than a second copy.
- **AD-22, gradient-boosted trees on ranks.** Single-threaded with a fixed seed and no tuning on results; a changed setting gives a new fingerprint. Chosen over LightGBM, which needs a separate OpenMP install on macOS.
- **AD-23, shuffle nulls.**
  - Screens are compared with within-date shuffles.
  - Gains are compared with 5 shadow copies trained alongside each feature.
  - The null-hypothesis-testing skill tests the monthly series and handles dependence between months.
  - Benjamini–Hochberg counts the whole feature log; the holdout uses Holm.
- **AD-24, registry in the repo.** Sealing requires the work to be committed and records the commit. The holdout runs once. Git history is the audit trail.
- **AD-25, clipped loader.** Any development read past 2021-12-31 raises `DevelopmentOnlyError`.
- **AD-26, `qrisk` (5 pipelines) and `qfeat` (6) stay whole.** A split is reconsidered only on contract size, module count, or a new dependency stack or deployment.
- **AD-17 (revised in place):** "No data or app package imports it". Later research packages import `qrisk` through its top-level exports.

**Risks (S3 additions)**
- Bench runtime is about an hour on 8 cores.
- The shadow null is unproven until PLANT-02 passes; the fallback would need your agreement on run time.
- Effects near a rank correlation of 0.02 may be undetectable.
- QR-13 is estimated at about 15 minutes, not yet measured.

**Changelog (S3 rows)**
- Stage 3 (AD-21–AD-25)
- `PlantPanel` contract type (AD-15 rule)
- `qrisk` and `qfeat` stay whole (AD-26)
