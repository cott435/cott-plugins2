# Extend mode: an idea file

`docs/brief.md` exists, so the new idea gets its own file and must earn its place in the project. Examples: `examples-extend.md`, `examples-ml.md`, `examples-data.md` (stage skills and references).

**Read before asking anything:** `docs/brief.md`, `docs/spec.md`, `docs/roadmap.md` and open ideas in `docs/ideas/`. Their problem, goals, constraints, Not Doing list and requirements constrain the new idea. `Specced` ideas are frozen records; where one disagrees with the spec, the spec is current.

- A `Draft` brief: ask whether to finish reviewing it first.
- A `Draft`, `Accepted` or `Parked` idea covering the same ground: offer to refine it instead. A `Specced` one is frozen; a change starts a new file.

**Phases 1-2** per `ideation.md`. Before Phase 1, restate the new idea in terms of the existing project: "This adds [X] so that [existing user] can [outcome]." Note which existing features and requirement IDs it touches.

**Fit check (during Phase 2) — answer one of these out loud. It decides whether the brief changes:**

| Finding | Idea file | Brief |

| Needs a new goal: the project's outcome itself widens, same problem and user | Write it | Add the goal with the next number. If that makes more than five, merge before writing: propose which goals fold together, your merge as the default, and write the merged set. Never write a sixth goal. |

**Writing rules for idea files:**

- **Plain English, still no requirements.** Describe what the user experiences and why; `spec-writing` turns that into requirement IDs and acceptance criteria.
- **More room than the brief, not unlimited.** Aim for 300-700 words. The extra space goes to *How it fits*, *Alternatives considered*, and *Open questions* — the context the spec needs.
- **One idea per file.** If the conversation produced two separable ideas, write two files (ask the user which to do first).
- **Write it as a record, in the brief's voice.** The file outlives the review. Notes to the user ("my proposed limit, for you to check") belong in the conversation. Questions belong under *Open questions*.
- **Tool preferences live here, not in the spec.** If the user names a library, dataset or service ("hand-write the CNN, then compare with a torchvision model"), record it under *Recommended direction* or *Data*. `spec-writing` writes the behavior without the name, and `architecture-design` reads the name from here.
- **Never paste the idea into the brief.** Brief edits are limited to the fit-check table above, and leave `brief_words` within `new.md`'s budget: pay for each addition with a cut. A stage's content belongs in the roadmap, never in a brief line listing the stages. Goal numbers stay stable; new goals take the next number, and a merged goal keeps the lower one. If a goal is dropped or merged away, tell the user which spec requirements referenced it.

**Review Gate** (`../SKILL.md`): also say whether the brief changed and which sections.

**Stage** per `roadmap.md`: one stage for the idea, Source `ideas/<slug>.md`. Skip it only when the idea's *Stage* line says it joins a stage not yet being built.

**Idea status lifecycle:** `Draft` → `Accepted` (user approved here) → `Specced` (set by `spec-writing` once the spec is approved). Parked ideas get `Parked` with a one-line reason, so they aren't re-proposed blindly. **A `Specced` idea is frozen.** It records why the feature was added, as it stood that day. `spec-writing` adds a one-line banner saying so, and nobody edits the file afterwards. # The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.
# Roadmap stages

Read when proposing stages at the Review Gate and when adding them on acceptance; the mode file says which stages to propose. An example: `examples-data.md`.

Stages live in `docs/roadmap.md`. A stage is an outcome the user agreed: what they can do when it's done, such as "Data + stats" or "See my spending". It is coarse and unsized. **Don't size it:** no task estimates, no pipeline counts, no splitting a stage because it looks big. Two stages differ by outcome, never by size. Once a stage's pipelines are approved, `build-planning` cuts it into build-sized milestones (`M<n>`), each a vertical slice it can run end to end, and owns those rows.

**Add stages only when the user accepts** (Phase 4). Each stage takes its ID from `dt next-id S` (`dt` as defined in `../SKILL.md`), a short name, and its Source. Leave the Status* cell empty, then run `dt roadmap`, which fills it. Under the tables, add a `## S<n>: <Name>` section with one plain-English `**Outline:**` line (what the user can do when the stage is done) and one `**Skills:**` line.

**Stage skills and references.** The `**Skills:**` line is the one record of which skills serve a stage; later skills start from it and `build-planning` checks each one lands on a milestone and then a task. Propose the skills whose descriptions fit the stage (project `.claude/skills/*/SKILL.md` and the installed skills in your context), and ask once: "Route profile-report and significance-check to S2? [yes / edit]". None fit → `**Skills:** —`. Also offer each `references_unassigned` entry that serves the stage ("RF-02 and RF-03 (boosting) → S3? [yes / edit]"). # RL Lab

**Status:** Accepted · **Last updated:** 2026-10-18

## The problem
Reinforcement learning (RL) is how an agent learns by trial and error from rewards. It is easy to read about and hard to really understand. Library code hides the parts that matter, and tutorials stop once the agent "works". The fastest way to learn it is to build small agents from scratch, in small 2D game environments, where each one teaches one idea and you can see it learn.

## Who it's for
Me: a solid Python programmer with some NumPy and PyTorch, who knows the basics of Q-learning (learning the value of each action in each state) and wants to learn RL by building it.

## Goals
1. For each environment, I can explain in my own words why the agent learns, and why each part of the algorithm matters.
2. Every agent is shown to learn: its learning curve beats a random agent and a simple scripted agent on the same games.
3. I can watch a replay of any trained agent playing.
4. A new environment reuses a shared core (environment interface, training loop, logging, replay viewer, learning curves) instead of starting over.

## Constraints
- Laptop CPU only, and under about an hour of training per environment.
- Free tools only.
- Evenings and weekends, a few weeks per environment, no deadline.
- Learning algorithms are written from scratch, not taken from a library.

## What success looks like
- The first environment, Snake, has an agent whose learning curve clearly beats both baselines, plus a replay of it playing.
- Turning off a key part of the agent visibly hurts its learning, and I can say why.
- The second environment, whatever it is, plugs into the shared core with small changes.

## What we're betting on
- Small, hand-picked descriptions of the game state ("danger ahead", "food to the left") are enough for an agent to learn well within an hour on a CPU.
- A shared core designed while Snake is the only example will still fit the next environment without a rewrite.
- Writing the algorithms myself teaches more than tuning a library would.

## Not doing
- Learning from raw pixels or the full grid image: much slower, and not the lesson I'm after.
- Comparing against library implementations, for now: a later step, once my own version works.
- Fancy views such as heatmaps of the agent's values: learning curves and replays are enough.
- Planning environments beyond the second, the fish tank: each next one is chosen once the one before is built.
- Mastering Snake: agents that see only nearby danger tend to trap themselves, and that limit is fine.

# Idea: Fish Tank

**Status:** Specced · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)
**Spec:** TANK-01–TANK-10, PG-01–PG-12, TWIN-01–TWIN-02, CORE-07–CORE-09, BASE-04, ABL-06–ABL-08, CURVE-06, EXPL-04; CORE-02–CORE-04, BASE-01, EVAL-02–EVAL-04, ABL-04, ABL-05, CURVE-03, REPLAY-02, EXPL-03, QR-01–QR-03 (changed)
> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)

## In one sentence
This adds a second environment, a circular tank where several fish learn to steer away from a bouncing ball, so the learner can build policy-gradient methods up to PPO, with continuous control, on the shared core Snake built.

## The problem
Snake teaches value learning over a few discrete moves. With continuous moves (how hard to turn, how fast to swim) there is no list of moves to score, so the agent must learn its policy directly. Policy gradients start there and usually end at PPO, each step fixing a failure of the one before. Building them in order, in a game you can watch, shows why PPO exists.

## Who it's for
The same learner as the brief, once Snake (S1) is done and they move on from value learning to policy learning.

## How it fits
- **Serves:** Goal 1 (explain why each part matters), Goal 2 (beats random and scripted agents), Goal 3 (replay), Goal 4 (reuses the shared core)
- **Touches:** CORE-01–CORE-06 (several agents at once, continuous moves; CORE-03's "number of allowed moves"); BASE, EVAL, ABL, CURVE-03, REPLAY, EXPL, LOG-01 (worded for Snake and its DQN); QR-01–QR-03, QR-05 (Snake-only limits; the hand-written rule). SNAKE and AGENT stay as they are.
- **Brief changes:** Not doing narrowed: the fish tank is planned now; only environments after it wait.
- **Stage:** New S2 (roadmap stage on acceptance), built after S1 is done.

## Recommended direction
**The tank.** A circular tank with one ball bouncing off its wall. Several fish swim in it with continuous movement: each step every fish chooses how to steer and how fast to swim. When the ball touches a fish, that fish is removed. The game ends when every fish is gone. Fish are rewarded for staying alive, so a good fish survives as long as possible.

**What a fish sees.** Only nearby things, through about 8 sensor rays spread evenly around it. Each ray reports how far away the wall, the ball and other fish are along that direction, up to a short range. Nothing beyond the rays' reach is visible.

**One brain, many bodies.** All fish share one policy, each acting on its own observation. Fish don't block or crowd each other, so each is an independent copy of one single-agent problem: the stage stays about policy gradients, not game theory. The build starts with one fish and adds more once it learns.

**The ladder.** The learner writes three agents by hand, each one built on the previous one: REINFORCE (plain policy gradient), then actor-critic (a learned value estimate cuts the noise), then PPO (a limit on how far each update moves the policy). Each added piece has an off switch, as in S1, so turning it off shows what it was fixing.

**The core grows.** The shared core learns to handle continuous moves and several agents at once. Snake keeps running exactly as before.

**Optional extra.** A discrete twin of the tank with 8 compass moves, run by S1's unchanged DQN, to show what continuous control adds. The stage is done without it.

## Alternatives considered
- PPO only — skips the failures that explain each piece, which is the point of the lab.
- Fish that interact (crowding, blocking) — a genuinely multi-agent problem: richer, but a different lesson.
- A curriculum (the ball speeds up, more balls appear) — adds tuning without a new idea; revisit if the tank is too easy.
- A list of the nearest few objects as the observation — rays are fixed-size and closer to "sees only nearby things".

## What success looks like
- Each rung's learning curve beats a random fish and a scripted fish on the same seeded games.
- PPO learns better or more steadily than the rung below it, and turning off each piece visibly hurts, or the notes record that it didn't.
- A replay shows trained fish dodging the ball.
- Snake's results are unchanged after the core grows.

## What we're betting on
- About 8 short rays carry enough information to dodge one ball.
- A shared policy learns well from several independent fish, and the extra fish speed learning up rather than confusing it.
- The full ladder trains within the brief's hour per run on a laptop CPU.

## Not doing
- Fish that affect each other — a multi-agent problem; out of scope.
- A curriculum of harder tanks — not needed to learn the lesson.

# Idea: Predator-Prey Foraging

**Status:** Draft · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This adds a third environment, the fish tank with food pellets and a learning predator, so the learner can see co-evolution: two sides that learn against each other, why that breaks plain training, and how training against past versions fixes it.

## The problem
In Snake and the tank the world stands still while the agent learns. When the opponent also learns, the target keeps moving: each side's reward can stay flat while both improve, and the two can chase each other in circles, forgetting old tricks as they learn new ones. Self-play against past versions is the usual fix. Building the broken version first, then the fix, shows why the fix exists.

## Who it's for
The same learner as the brief, once the fish tank (S2) is built and they move on from one learner in a fixed world to two learners shaping each other's world.

## How it fits
- **Serves:** Goal 1 (explain why self-play works), Goal 2 (beats random and scripted opponents), Goal 3 (replay), Goal 4 (reuses the shared core and S2's tank and PPO)
- **Touches:** S2's tank (TANK: the ball becomes a predator, pellets are added, prey have energy); PG-08 (PPO, reused for both sides); CORE-02, CORE-05, CORE-07 and CORE-08 (one trained agent per run becomes two learners with their own policies in one game); BASE, EVAL, CURVE, REPLAY, EXPL (written for one learner against a fixed world). The spec's "Fish that affect each other" and "Real environments beyond the fish tank" Out of scope items narrow. The frozen [fish-tank.md](fish-tank.md) stays as it is.
- **Brief changes:** Not doing narrowed: predator-prey foraging is planned now; only environments after it wait.
- **Stage:** New S3 (roadmap stage on acceptance), built after S2 is done.

## Recommended direction
**The tank, with stakes.** S2's circular tank, with the bouncing ball replaced by one predator fish, and food pellets scattered around. Prey lose energy over time and must eat pellets to keep it up, so a prey that only hides starves. A prey caught by the predator, or out of energy, is removed. The predator is rewarded for catching prey; prey are rewarded for staying alive. Both sides see only nearby things through rays, as in S2.

**One brain per side.** All prey share one policy, as the fish do in S2. There is one predator with its own policy. Both are the learner's hand-written PPO from S2.

**The ladder.**
1. *Taking turns* (optional first rung): one side trains while the other is frozen, then they swap. The world is still for each learner, so S2's PPO works unchanged.
2. *Simultaneous learners*: both sides learn at once. This is the broken version, kept on purpose: it shows the moving target and the cycling.
3. *Self-play against past versions*: each side saves a copy of itself as a new generation every so often, and trains against a mix of its opponent's current and past generations. This is the fix.

**Judging it.** Each side's reward alone can't show learning, because the opponent improves too. Two fixed bars do: each side is scored against a random and a scripted opponent on the same seeded games. And a cross-play table pits every saved generation of one side against every generation of the other, so later generations beating earlier ones shows real progress rather than circling.

**The core grows again.** The shared core learns to run two learners with their own policies in one game. Snake and the tank keep running as before.

## Alternatives considered
- Evolutionary methods (a population, keep the fittest) — a different lesson from the policy gradients the lab has built up to.
- Simultaneous learners only — shows the problem without the fix.
- Pellets only as a bonus reward — prey can win by hiding forever, so there is no trade-off to learn.
- Several predators — a second multi-agent problem (teamwork) on top of the first.

## What success looks like
- Each side's learning curve beats a random and a scripted opponent on the same seeded games.
- In the cross-play table, later generations beat earlier ones, for both sides.
- Simultaneous learners visibly cycle or stall where self-play does not, or the notes record that they didn't.
- A replay shows prey foraging and dodging while the predator hunts.
- Snake's and the tank's results are unchanged after the core grows.

## What we're betting on
- S2's rays and PPO carry over to both sides with small changes.
- Simultaneous learners show the moving-target failure clearly in a small tank.
- Self-play over a handful of generations fits on a laptop CPU.

## Not doing
- Evolutionary methods — a different lesson.
- More than one predator — teamwork is a separate problem.
- Learned communication or teaming among prey — the prey share a policy, nothing more.

## Open questions
- Training time: does the brief's "under about an hour per environment" hold for one generation, or for the whole self-play run?
- Prey competing for the same pellets is an interaction between prey; is that allowed, given S2 kept fish independent?
- What the scripted predator and scripted prey do.
- How many generations are saved, and how a side picks which past opponents to train against.
- Whether the predator also has energy, or only the prey.
