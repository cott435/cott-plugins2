# Quant Research Platform — Architecture

**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
`qdata` downloads the Sharadar tables, cleans and validates them, cross-checks them against Yahoo Finance and stores them as an as-of (bitemporal) Parquet store. Every other Python package reads that store only through `qdata`'s loader. `research` holds the stage S2 and S3 methods and the shared testing harness, which registers every claim, runs it walk-forward and writes every run (win or loss) to the run store. `learn` holds the torch-based stage S4 work. It installs on its own on a rented graphics card and on the laptop, and records through the same harness. `server` is a local FastAPI process that serves data and records over HTTP, streams run progress over a WebSocket and starts long runs as subprocesses. `web` is the TypeScript + React app in the browser.

```mermaid
flowchart LR
  web -- HTTP / WebSocket --> server
  server --> research --> qdata
  learn --> research
  learn --> qdata
  server -. starts as subprocess .-> learn
  qdata -- Sharadar API, yahooquery --> ext[(vendors)]
```

## Dependency rules
- `qdata` imports nothing internal. It is the only package that talks to Sharadar or Yahoo, and the only one that writes the data store.
- `research` may import `qdata`. It is the only writer of the run store (`research.RunStore`), paper books included.
- `learn` may import `research` and `qdata`. Nothing imports `learn`.
- `server` may import `research` and `qdata`, never `learn`: it starts `learn` jobs as subprocesses by module name, so the app never loads torch.
- `web` imports no Python. It reaches `server` only through the HTTP and WebSocket contract in [server's contract](packages/server/contract.md).
- Enforced by `import-linter` contracts in CI and the pre-commit hook. `learn`'s torch extras are declared only in its own `pyproject.toml` (AD-01).

## Cross-package contracts
- `qdata.Loader` (as-of prices, total returns, actions, universe) and `qdata.open_loader`: provided by `qdata`, used by `research`, `learn`, `server`. [Contract](packages/qdata/contract.md)
- `qdata.run_build`, `qdata.accept_build`, `qdata.ProgressEvent`: provided by `qdata`, used by `server`'s job runner. [Contract](packages/qdata/contract.md)
- `research.register`, `research.RunHandle`, `research.decide`, `research.RunStore`: provided by `research`, used by `learn` and `server`. [Contract](packages/research/contract.md)
- `research.estimate_covariances`, `research.build_portfolio`, `research.hold_period`, `research.load_benchmark`, `research.load_survivors`: provided by `research`, used by `learn`. [Contract](packages/research/contract.md)
- `learn.Strategy` and `learn.run_paper_day`: provided by `learn`, used only inside `learn` and from the `learn` command line. [Contract](packages/learn/contract.md)
- HTTP and WebSocket API (`server.*`): provided by `server`, used by `web`. Contract types are JSON Schema generated from the server's models (AD-09). [Contract](packages/server/contract.md)

## System pipelines
### PL-01: Dataset build and acceptance
**Trigger:** the researcher clicks "Build" or "Update" in the app, or runs `qdata build` · **Covers:** BUILD-01–BUILD-05, XCHK-01–XCHK-04, UNIV-01–UNIV-05, APP-04
**Purpose:** a validated, cross-checked dataset that becomes the current one once accepted, with progress watched live.
1. `web` → `server`: `server.start_run` (kind `build_full` or `build_update`)
2. `server` → `qdata`: `qdata.run_build`, run in a job subprocess, emitting `qdata.ProgressEvent`
3. `server` → `web`: `server.ProgressMessage` over `server.run_progress` (WebSocket)
4. `web` → `server` → `qdata`: `server.accept_build` → `qdata.accept_build` (only for a build whose checks failed or did not run)

### PL-02: Browse the dataset and its analysis
**Trigger:** the researcher opens a stock, a date, a build report or the analysis in the app · **Covers:** APP-01–APP-03, APP-05, APP-06, EDA-03, LOAD-01–LOAD-06
**Purpose:** see any stock, any day's universe, any build's validation report and the exploratory analysis, all from the accepted build.
1. `web` → `server`: `server.stock_history`, `server.universe_on`, `server.build_report`, `server.eda_report`
2. `server` → `qdata`: `qdata.open_loader`, `qdata.load_report`, `qdata.load_eda`

### PL-03: Classical risk comparison (stage S2)
**Trigger:** called from a research notebook or `research compare` · **Covers:** FACT-01–FACT-04, DENO-01–DENO-04, COV-01–COV-04, PORT-01–PORT-06, HARN-01–HARN-08
**Purpose:** covariance estimators and classical portfolios ranked on out-of-sample variance after costs, and the stage benchmark saved.
1. `qdata` → `research`: `qdata.open_loader` (universe returns as of the accepted build)
2. `research` internal: `research.register` → `research.RunHandle` → `research.decide` → `research.RunStore`

### PL-04: Feature tests (stage S3)
**Trigger:** called from a research notebook or `research features` · **Covers:** FEAT-01–FEAT-04, FTEST-01–FTEST-05
**Purpose:** every candidate feature tested for information gain over market-removed returns, and the survivors saved.
1. `qdata` → `research`: `qdata.open_loader`

## Decisions
### AD-01: Five packages with enforced import directions
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-44: the user approved the five-package map. The real boundaries are a different runtime (UR-12: a TypeScript + React frontend over a Python backend) and a dependency stack, torch, that only stage S4 needs and that installs on rented hardware (FCST-07, QR-01).
- **Decision:** One uv workspace with Python packages `qdata`, `research`, `learn` and `server`, plus a pnpm package `web`. They follow the directions in Dependency rules, enforced by `import-linter` in CI and pre-commit. Each Python package has its own `pyproject.toml`, and only `learn` declares torch, Stable-Baselines3 and Gymnasium.
- **Alternatives:** One Python package with `web` as a folder: simpler, but torch would sit in every install, or be kept out by convention only. Splitting `qdata` further (ingest vs loader): no separate deployment or dependency stack justifies it.
- **Consequences:** The server never loads torch, and a GPU box installs `qdata`, `research` and `learn` only. Paper books must go through `research`'s run store so the server can read them without importing `learn`.

### AD-02: Python 3.12 and TypeScript + React
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-12: the user named a TypeScript + React browser frontend over a Python backend. The research stack (pandas, scipy, torch, Stable-Baselines3) is Python.
- **Decision:** Python 3.12 for `qdata`, `research`, `learn` and `server`, managed by uv. TypeScript 5.6, React 18.3 and Vite 5.4 for `web`, managed by pnpm. Dataframes crossing Python boundaries are pandas frames checked by pandera schemas.
- **Alternatives:** Polars for dataframes: faster, but every library downstream (scikit-learn, cvxpy, the references RF-01–RF-03) expects pandas or numpy. Python 3.13: some wheels (LightGBM, Stable-Baselines3 dependencies) lag behind it.
- **Consequences:** The interface between the two runtimes needs generated types (AD-09).

### AD-03: Sharadar stocks, actions and tickers as the primary source
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UR-07: the data is "from my Sharadar subscription". UR-26: "use prices, actions and tickers in Stage 1". Checked against DATA-01–DATA-04 and UNIV-01–UNIV-03. Sharadar's site states "Active and delisted coverage extends back to the 90s" and calls the price data "nearly completely free of survivorship bias" ([sharadar.com](https://www.sharadar.com/), read 2026-10-18). The [stocks table docs](https://www.sharadar.com/docs/stocks) (read 2026-10-18) list `close` and `volume` (split adjusted), `closeadj` (adjusted for splits, dividends and spinoffs), `closeunadj` and `lastupdated`. Authentication is an `api_key` query parameter, and paging uses `limit` (default 10000) and `skip`. The [tickers docs](https://www.sharadar.com/docs/tickers) (read 2026-10-18) give `permaticker`, "a unique and unchanging identifier for a security (share class)", plus `category`, `isdelisted`, `firstpricedate` and `lastpricedate`. The [actions docs](https://www.sharadar.com/docs/actions) (read 2026-10-18) cover ticker changes, splits, cash dividends, spinoffs, listings, delistings and acquisitions, but list no action codes.
- **Decision:** `qdata.source` reads the Sharadar stocks, actions and tickers tables through the subscription's API, behind a `PrimarySource` protocol. Stocks are keyed by `permaticker`, never by ticker, so reused and changed tickers stay distinct (BUILD edge cases). Eligibility (UNIV-05) comes from `category` common-stock values. Dollar volume is `close × volume`, both split-adjusted, which equals the unadjusted traded value. Total return is the day-on-day ratio of `closeadj` minus one (AD-07). An update requests rows with `lastupdated` after the previous build's date (BUILD-02).
- **Alternatives:** Nasdaq Data Link's `SHARADAR/SEP` route to the same data: kept as a second adapter behind `PrimarySource` if the user's subscription is served there (PB-01 answers which). CRSP: the reference for delisting returns, but outside the budget (QR-04).
- **Consequences:** The vendor keeps only a row's latest value and its `lastupdated` date, with no version history. From the first build on, `qdata` records each correction itself (AD-06). Rows from before the first build are treated as known on their own trading date (Risks).
- **Probe:** PB-01 — With the user's subscription: which API route serves it, the exact `category` values for common stocks and the `action` codes, whether delisted common stocks from 2000-01-03 give at least 1,000 names with 63 days of dollar volume on most dates, how `lastupdated` behaves on a correction, and the request limits on a full download.

### AD-04: Yahoo Finance through yahooquery as the second source
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UR-08: "cross-checked against Yahoo Finance through yahooquery". Checked against DATA-05 (an independent source), XCHK-01–XCHK-04 and QR-04 (free). The [yahooquery README](https://github.com/dpguthrie/yahooquery) (read 2026-10-18) describes "a python interface to unofficial Yahoo Finance API endpoints", MIT licensed. Its docs pages for `history` could not be read on 2026-10-18.
- **Decision:** `qdata.xcheck` fetches daily history with dividends and splits for each universe stock from yahooquery, maps it by ticker and date range (the ticker as of each date), and compares daily total returns and actions as XCHK-01–XCHK-03 define. Stocks Yahoo doesn't cover are counted as "not covered" (XCHK-04). An unreachable endpoint marks the check "not run". Responses are cached per build, so an update fetches only new days for each covered stock (QR-03).
- **Alternatives:** yfinance: the same unofficial endpoints, with no coverage advantage, and the user named yahooquery. Stooq: free daily data, but thin on delisted stocks and with no dividend history.
- **Consequences:** Yahoo drops most delisted tickers, so coverage will be partial and reported, never failed (XCHK-04). The unofficial endpoints can change without notice, so the adapter is one module behind `SecondSource`.
- **Probe:** PB-02 — For a sample of universe stocks (active, delisted, ticker-changed): what share of universe stock-days yahooquery covers, whether `history` returns dividends and splits on their dates, its rate limits on about 1,000 tickers, and whether a daily cross-check fits QR-03's 10 minutes.

### AD-05: Sharadar S&P 500 constituents for the fallback universe
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UNIV-04 and DATA-06 need S&P 500 membership by date, used only if PB-01 shows the dollar-volume universe can't be built. Sharadar lists an "S&P500 Constituents (sp500)" table ([sharadar.com](https://www.sharadar.com/), read 2026-10-18). UR-26 named only prices, actions and tickers, so whether the subscription includes it is open.
- **Decision:** If the fallback is needed, `qdata.universe` builds membership from the Sharadar sp500 table's additions and removals, keyed by `permaticker`. The choice of universe rule is recorded in each build's manifest.
- **Alternatives:** Membership rebuilt from the public record of S&P index changes: free, but needs ticker-to-`permaticker` mapping by hand and has gaps before 2010. Dropping the fallback: rejected, because UR-29 asked for it.
- **Consequences:** The fallback costs nothing extra only if the table is in the subscription. Otherwise QR-04 needs a decision from the user.
- **Probe:** PB-03 — Is the sp500 table in the user's subscription, and does it give point-in-time additions and removals back to 2000-01-03, including members later delisted?

### AD-06: Bitemporal Parquet store with accepted builds
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** DATA-04 (each value carries when it became known, and each correction), BUILD-02 (keep the replaced value), BUILD-04 and LOAD-06 (serve only accepted builds), LOAD-04 (as-of reads), BUILD-05 (resume), QR-02 (≤ 20 GB, 25-year load ≤ 30 s and ≤ 8 GB).
- **Decision:** Each stored table is Parquet partitioned by year under `data/store/`. Every row carries `known_from`, `known_to` (null while current) and the `build_id` that wrote it. A correction closes the old row's `known_to` and adds a new row, and nothing is overwritten. Each build stages its batches under `data/builds/<build_id>/`, with one checkpoint per completed batch. It commits by writing a manifest (status `passed`, `failed`, `accepted`, `not_run`) only after validation. A read as of A uses DuckDB over the Parquet files, filtered to `known_from ≤ A < known_to` and to rows from builds whose manifest is `passed` or `accepted`. The point-in-time universe is computed once per build and stored with it.
- **Alternatives:** SQLite or Postgres: row stores, slower on the 25-year column scans of QR-02, and Postgres means running a server. ArcticDB: built-in versioning, but snapshot granularity, not per-row known dates, and one more dependency.
- **Consequences:** As-of reads are a filter, not a replay. The store only grows. At about 1,000 universe names out of roughly 20,000 listings, the estimate is under 3 GB.
- **Probe:** none — no external service; the QR-02 limits are checked by a benchmark task in the build.

### AD-07: Returns, identity and missing data rules
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** LOAD-01 (close, split-adjusted close, total return), LOAD-05 and BUILD-03 (missing stays missing), UNIV-03 and FCST-06 (final returns through delisting), DATA-03 (no split jumps).
- **Decision:** Total return on day t is `closeadj_t / closeadj_prev − 1`, where prev is the stock's previous trading day on the exchange calendar (`exchange_calendars` XNYS). A day with no trade is NaN, and the next return spans from the last traded close with `gap_days` recorded. The final return through delisting is the return to the last traded close. Identity is `permaticker`, and loaded frames carry the ticker as of each date as a column.
- **Alternatives:** Filling missing days with zero returns: forbidden by LOAD-05. Computing total returns from actions ourselves: duplicates the vendor's adjustment and is checked instead by XCHK-03.
- **Consequences:** Delisting returns after the last trade (a cash payout or a worthless delisting) aren't in Sharadar's prices, so they're missing (Risks).
- **Probe:** none — follows from the AD-03 columns; PB-01 confirms them.

### AD-08: Local FastAPI server with a subprocess job runner
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `server`
- **Context:** UR-30: "HTTP for data, WebSocket for live progress of download/validation runs". APP-04 (progress at least every 2 seconds), QR-06 (local only), and the AD-01 rule that `server` never imports `learn`.
- **Decision:** FastAPI on uvicorn, bound to `127.0.0.1`, with a Host-header check. Data and records are JSON over HTTP. Each long run (build, update, acceptance check, `learn paper`) starts as a subprocess (`python -m qdata …`, `python -m learn …`) that writes `ProgressEvent` lines to a per-run JSONL file. The server tails that file and pushes `server.ProgressMessage` over the WebSocket every second, plus a final message. A crashed or stopped run keeps its file, so the app shows the failing step and offers resume.
- **Alternatives:** Running jobs in-process on threads: a crash takes down the server, and `learn` jobs would import torch. Celery or Redis: a broker to run for one user.
- **Consequences:** Progress survives a page reload and a server restart. Only one build runs at a time, enforced by a lock file in `data/builds/`.

### AD-09: Generated API types and JSON Schema fixtures between server and web
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `server`, `web`
- **Context:** The `server` → `web` boundary crosses runtimes that share no types (UR-12). APP-05 needs light and dark themes, and APP-06 needs a full-history chart within 1 second.
- **Decision:** The server's request and response models are pydantic. Their OpenAPI document is exported in CI, and `openapi-typescript` generates `web`'s types from it. The WebSocket messages are pydantic models exported as JSON Schema. Contract fixtures are JSON samples validated against those schemas on both sides. `web` charts with Apache ECharts (canvas renderer, light and dark themes) and fetches through TanStack Query. One stock's full history is sent as parallel arrays (dates, values), not an array of row objects.
- **Alternatives:** Hand-written TypeScript types: they drift from the server. tRPC: needs a TypeScript backend. Recharts: SVG, slow beyond a few thousand points.
- **Consequences:** A server model change fails `web`'s type check until types are regenerated.

### AD-10: One testing harness with locked registrations and guarded data views
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `research`
- **Context:** HARN-01–HARN-08, and every claim from S2 through S4 (COV-03, FTEST-03, FCST-04, FCST-05, FPORT-02, AGENT-04) runs through it. RESX-04 needs one record format for every stage.
- **Decision:** Every module that makes a claim registers a `research.Registration` before computing anything. The harness writes it to `data/runs/<run_id>/registration.json` with its SHA-256, and any later change makes a new run. Walk-forward windows default to 252 estimation days and 21-day holds. Learned models get train, validation and test splits in time order, with a purge of at least the label horizon between them. Strategies read data only through a guarded loader that ends at each period's start. A read inside the final test period before the verdict run raises `FinalPeriodLocked`, and a second run on that period is marked a repeat. Every finished or abandoned run writes its period results, verdict and conclusion. Verdicts come from `research.decide`, the step run with the `null-hypothesis-testing` skill, which gets per-period candidate and baseline results, the registered test, the level and the count of candidates tried under the claim.
- **Alternatives:** An experiment tracker (MLflow): it records runs, but doesn't lock registrations or guard reads, and adds a server.
- **Consequences:** Stages S3 and S4 add claims without new harness code. The run store is plain files that DuckDB queries for the results explorer.

### AD-11: Per-window PCA factor removal and Marchenko–Pastur denoising
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `research`
- **Context:** FACT-01–FACT-04 and DENO-01–DENO-04. UR-25: the user's reference code. RF-01 removes the market mode, but fits on the whole panel, fills gaps with zeros and has no denoising.
- **Decision:** `research.factors` adapts RF-01's `pca_factors`, `residualize` and `residual_correlation_check` to fit only inside each window. Stocks with under 80% of the window observed are excluded and listed, never zero-filled, and k ≥ N is an error. Out-of-sample residuals use the previous window's loadings. `research.denoise` fits the noise variance by matching the Marchenko–Pastur density to the window's eigenvalues (scipy `minimize_scalar`), replaces the eigenvalues at or below the edge with their mean, and rescales to a unit diagonal. k is a fixed number or the count above the edge, recorded with the run.
- **Alternatives:** scikit-learn `PCA`: it hides the per-window loadings needed for out-of-sample residuals. A shrinkage-only cleaning: not what DENO-01 asks for.
- **Consequences:** Synthetic factor panels are the known-answer tests for DENO-03 and FACT-04.

### AD-12: Ledoit–Wolf shrinkage toward constant correlation
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `research`
- **Context:** COV-01 asks for a covariance shrunk toward a structured target, with its intensity chosen from the window only.
- **Decision:** Ledoit–Wolf (2004) shrinkage toward the constant-correlation target, with the analytic optimal intensity from the window's returns, implemented in `research.covariance`. scikit-learn's `LedoitWolf` (scaled-identity target) serves as a test cross-check.
- **Alternatives:** scikit-learn `LedoitWolf` as the estimator: its scaled-identity target ignores correlation structure. Oracle-approximating shrinkage: the same identity target.
- **Consequences:** About 40 lines of numpy to own and test against the published formula.

### AD-13: cvxpy for minimum variance; own risk parity and HRP
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `research`
- **Context:** PORT-01 (long-only, fully invested, ≤ 5% each), PORT-02 (equal risk contributions within 1%), PORT-03 (HRP), and the PORT edge case (infeasible dates keep previous weights).
- **Decision:** Minimum variance is a cvxpy quadratic program solved with Clarabel. Risk parity solves Spinu's convex log-barrier problem with scipy L-BFGS-B and rescales to sum to 1. HRP uses scipy's single-linkage clustering on correlation distance, quasi-diagonal ordering and recursive bisection, written in `research.portfolios`. A solver failure or infeasibility returns `Infeasible`, and the caller keeps the previous weights.
- **Alternatives:** PyPortfolioOpt or Riskfolio-Lib: they cover all three, but bring heavy dependencies and hide the steps a test must check.
- **Consequences:** Three small optimisers with known-answer tests (two-asset risk parity, a block-diagonal HRP).

### AD-14: LightGBM for feature information gain
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `research`
- **Context:** FTEST-02 (a learned model with the feature against one without it, out of sample), QR-01 (on the laptop), and FTEST-03 (the `null-hypothesis-testing` skill decides).
- **Decision:** LightGBM regression on standardised features. Its hyperparameters are fixed in the registration, the same for both arms and every feature, with seeds recorded. The metric is the per-date Spearman rank correlation of predicted and realised residual returns, and the per-date gains go to `research.decide`. `research.ftest` runs its data characterisation with the `data-analysis` skill (FTEST-04).
- **Alternatives:** Ridge regression: cheap, but misses non-linear gain. A neural network: GPU cost that S3 doesn't need.
- **Consequences:** About 10 features × walk-forward refits fit on a laptop. Tuning per feature is forbidden, because it would grow the count of candidates tried.

### AD-15: PyTorch sequence forecasters built on the reference windowing
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `learn`
- **Context:** FCST-01–FCST-07. UR-25: the user's reference code. RF-02 builds static, known and observed inputs, but has no purge and drops rows silently. RF-03 builds forward return and volatility targets, but drops delisted names' final returns.
- **Decision:** `learn.windows` adapts RF-02's `WindowSpec` and `build_windows`, with gaps kept as masked steps, unknown categories mapped to a reserved index, and splits by the harness's purged schedule. `learn.targets` adapts RF-03's `make_targets`, counting trading days on the exchange calendar and keeping returns through delisting. Two model families (an LSTM encoder and a small temporal-fusion-transformer-style model) each output return and volatility for horizons 1, 5 and 21 days, with plain PyTorch training loops. Baselines are a zero return and the trailing mean for returns, and trailing 21-day and exponentially weighted volatility for volatility.
- **Alternatives:** pytorch-forecasting's TFT: brings Lightning and its own dataset class, which repeats RF-02's leaks. Gradient-boosted forecasts only: no sequence model, which UR-21 asked for.
- **Consequences:** Every model family and horizon counts toward the correction in FCST-04 and FCST-05.

### AD-16: Stable-Baselines3 PPO with a differential Sharpe reward
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `learn`
- **Context:** AGENT-01 (reward is next-day return after the 10 bp cost, less a risk penalty, so the episode's total tracks its Sharpe ratio after costs; UR-42, UR-43), AGENT-02 (portfolio limits), AGENT-03 (clipped PPO on the training period only), AGENT-05 (5 or more seeds).
- **Decision:** A Gymnasium environment in `learn.env` replays the guarded universe day by day. The policy's action passes through a softmax and a cap projection, giving long-only weights at most 5% each with a cash slot. Weights are applied through `research.hold_period`, so costs and delisting rules match every other portfolio. The reward is Moody and Saffell's differential Sharpe ratio of the net daily return: the return less a variance penalty, from exponential moving estimates, so the reward summed over an episode tracks its Sharpe ratio. Training uses Stable-Baselines3 PPO (clip range in the registration) on the training period, with seeds 0–4 at least.
- **Alternatives:** CleanRL's single-file PPO: more code to own. RLlib: cluster tooling for one machine.
- **Consequences:** The action space is fixed to the universe's maximum size of 1,000 slots, with masked slots for absent stocks.

### AD-17: Rented-GPU training runs with a cost guard and returned bundles
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `learn`
- **Context:** QR-05 (≤ $10 per run, expected hours and cost stated before start), FCST-07 (model, settings and seeds brought back), QR-01, UR-35 ("an occasional rented GPU").
- **Decision:** `learn train-*` commands take a `TrainSpec` with the hourly rate and expected hours. Before any training, `learn.estimate_cost` prints the expected hours and cost and refuses if the expected cost exceeds $10. Training stops at a wall-clock cap set to the budget. Inputs ship as a frozen Parquet extract of the accepted build's universe panel, with no Sharadar credentials on the rented machine. Outputs are a `ModelBundle` folder (weights, settings, seeds, build id, git revision, training curve), copied back to `data/models/`. The provider is any hourly GPU rental. The hourly rate is an input, not a dependency.
- **Alternatives:** Training on the laptop's CPU: too slow for the sequence models. A managed ML platform: costs beyond the budget and lock-in.
- **Consequences:** Evaluation, the harness record and paper trading all run on the laptop from the bundle.

### AD-18: Paper trading from frozen strategy snapshots
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `learn`
- **Context:** PAPER-01–PAPER-04 (orders from data known at close, filled at the next close at 10 bp; frozen settings; no broker; daily records shown in the app).
- **Decision:** `learn.paper` runs each paper book: the S2 benchmark (`research.load_benchmark`), plus every S4 strategy whose run passed, each a `learn.Strategy` built from a frozen snapshot (bundle hash and settings). Each accepted daily build produces next-day target weights from data as of that close. The fills at the next close go through `research.hold_period`, and the day is appended to the book through `research.RunStore`. A missing or failed day is recorded as a gap. A changed snapshot starts a new book. `learn` imports no network client, and the import-linter contract forbids `httpx`, `requests` and `urllib` in `learn.paper`.
- **Alternatives:** A broker paper account: out of scope (UR-34).
- **Consequences:** Books live in the run store, so `server` shows them without `learn`.

# qdata — Architecture

**Package:** qdata · **Status:** Draft · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`qdata` turns the Sharadar subscription into a local as-of store. A build downloads in resumable batches, cleans, computes the point-in-time universe, cross-checks against Yahoo Finance, writes a validation report and commits a manifest. Every reader goes through `qdata.open_loader`, which serves only passed or accepted builds and filters every row by its as-of date (AD-06). The exploratory analysis runs on the loader's output and is saved with its build.

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `source` | Primary (`PrimarySource`, Sharadar, AD-03) and second (`SecondSource`, yahooquery, AD-04) adapters, paging, retry, credential lookup and URL redaction | DATA-01, DATA-05, QR-07 | — |
| `clean` | Deduplicate (stock, date), flag non-positive prices and missing trading days inside a listed life, map tickers to `permaticker` | BUILD-03, DATA-03 | `calendar` |
| `calendar` | XNYS trading days, previous trading day, gap counts | LOAD-05 | — |

| `universe` | Daily top-1,000 by 63-day median dollar volume from the day before, common stocks only, tie-break on `permaticker`, S&P 500 fallback | UNIV-01–UNIV-05, DATA-02, DATA-06 | `store`, `calendar` |
| `xcheck` | Total-return and action comparison against the second source, disagreement reasons, coverage share | XCHK-01–XCHK-04 | `source`, `store` |

| `eda` | The exploratory analysis, run with the `data-analysis` skill on loader output; saves figures and tables per build | EDA-01, EDA-02 | `loader` |

## Interfaces
See [contract.md](contract.md).

## Data
- **Sources:** Sharadar stocks, actions and tickers (AD-03), and sp500 if the fallback applies (AD-05). Yahoo Finance via yahooquery for the cross-check (AD-04).
- **Layout:** `data/store/{prices,actions,tickers,universe,second_source}/year=YYYY/*.parquet`, each row with `known_from`, `known_to` and `build_id`. `data/builds/<build_id>/` holds `manifest.json`, `report.json`, `progress.jsonl`, `batches/` checkpoints and `eda/`.
- **Build ids** are `YYYYMMDD-HHMMSS-<full|update>`. The current dataset is the newest build with manifest status `passed` or `accepted`.
- **Universe:** one row per (date, permaticker) in the universe, with rank and median dollar volume. The count for dates with fewer than 1,000 eligible stocks is written to the report.

## Cross-cutting concerns
- **QR-02:** loading 25 years of universe returns reads only the universe and prices partitions for those years and pivots to a float32 dates × stocks frame, about 6,300 × 3,000 columns at most (well under 8 GB). A benchmark test asserts ≤ 30 s.
- **QR-03:** an update requests only `lastupdated` after the previous build and new days. The cross-check fetches only new days per covered stock, from a cached history.
- **QR-07:** `source` reads the key from `keyring` or `SHARADAR_API_KEY`. A logging filter replaces `api_key=…` in every message.
- **Errors:** `SourceAuthError`, `SourceQuotaError` (the build stops, nothing is committed as current, and it can resume), `BuildLocked`, `NoAcceptedBuild`.

# research — Architecture

**Package:** research · **Status:** Draft · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`research` holds the laptop-sized research methods and the harness every stage claims through. Stage S2 removes market factors per window, denoises correlation, estimates three covariances, builds three portfolios plus equal weight, and holds them walk-forward with costs. The verdicts are saved, and the best becomes the stage benchmark. Stage S3 builds features as of each close and tests each feature's information gain with LightGBM. Every claim is registered, run on guarded data views, decided by the `null-hypothesis-testing` skill and written to the run store (AD-10).

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `harness` | Registrations, locking, walk-forward and purged splits, guarded loader views, final-period lock, cost and turnover accounting, verdicts with the `null-hypothesis-testing` skill | HARN-01–HARN-06, HARN-08 | `records`, `qdata` |
| `records` | The run store: run folders, period results, verdicts, conclusions, abandoned runs, paper books; DuckDB queries across runs | HARN-07 | — |
| `factors` | Per-window PCA market-factor removal, k rule, correlation-drop check (adapts RF-01) | FACT-01–FACT-04 | `qdata` |
| `denoise` | Marchenko–Pastur noise fit, eigenvalue clipping, unit-diagonal rescale, per-window record | DENO-01–DENO-04 | — |
| `covariance` | Sample, Ledoit–Wolf constant-correlation and denoised covariances per window | COV-01, COV-04 | `denoise` |
| `portfolios` | Minimum variance, risk parity, HRP, equal weight under the limits; hold-period simulation shared with `learn` | PORT-01–PORT-05 | — |
| `compare` | The S2 comparison: estimator × method walk-forward runs, analysis with the `data-analysis` skill, tests, benchmark selection | COV-02, COV-03, PORT-06 | `harness`, `factors`, `covariance`, `portfolios` |
| `features` | Feature registry (definition, inputs, lookback), per-date computation as of close, cross-sectional standardisation | FEAT-01–FEAT-04 | `factors`, `qdata` |
| `ftest` | Residual-return targets, LightGBM with and without each feature, gains, data characterisation with the `data-analysis` skill, survivors | FTEST-01–FTEST-05 | `harness`, `features`, `factors` |

## Interfaces
See [contract.md](contract.md).

## Data
- **Run store:** `data/runs/<run_id>/` holds `registration.json` (with `sha256`), `periods.parquet`, `verdict.json`, `conclusion.md`, `status.json` and the artefacts (weights, the denoising record per window). `data/runs/index.parquet` is rebuilt on write for listing.
- **Benchmark and survivors:** `data/runs/benchmarks/S2.json` points to the winning run, method and estimator. `data/runs/survivors/S3.json` lists the surviving feature ids (empty on a negative result).
- **Paper books:** `data/paper/<book_id>/` holds `snapshot.json` and `days.parquet`, written only through `RunStore.append_paper_day`.
- **Defaults:** 252-day estimation, 21-day hold, 10 bp per trade, 5% level after correction (spec Assumptions), with Holm–Bonferroni as the default correction, registered per claim.

## Cross-cutting concerns
- **Reproducibility (HARN-08):** a run records the build id, git revision, every seed and the package versions. Reruns compare periods bit for bit.
- **Point in time:** strategies get `GuardedLoader`, never a raw `qdata.Loader`.
- **Errors:** `FinalPeriodLocked`, `RegistrationLocked`, `Infeasible` (optimiser, handled by keeping previous weights), `ValueError` for k ≥ N.

## Overview
`learn` is the only package with torch. Training runs on a rented graphics card from a frozen Parquet extract and returns a bundle (AD-17). Everything else runs on the laptop from that bundle: forecasts, scoring against baselines, forecast-driven portfolios, agent evaluation and daily paper trading. ## Cross-cutting concerns
- **QR-05:** each `learn train-*` prints `expected_hours × rate` before starting and refuses if the expected cost is over $10. Training stops at `10 / rate` hours.
- **Divergence:** NaN loss, collapsing reward or weights outside the limits stop the run, which is recorded through `RunHandle.fail` with the training curve.
- **Determinism:** seeds for torch, numpy and the environment are set and recorded. cuDNN deterministic mode is on for evaluation.
- **PAPER-03:** an import-linter contract forbids `httpx`, `requests`, `urllib` and `socket` in `learn.paper`.

# web — Architecture

**Package:** web · **Status:** Draft · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
A Vite + React 18 + TypeScript single-page app served by `server` on `127.0.0.1`. It fetches through TanStack Query using types generated from the server's OpenAPI, charts with Apache ECharts, and subscribes to `server.run_progress` for live runs (AD-09). Screens and charts are designed with the `frontend-design` and `dataviz` skills, in light and dark themes (APP-05).

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `api` | Generated types, fetch client, query hooks, WebSocket hook with reconnect | APP-04 | server (HTTP/WS) |
| `theme` | Design tokens and the ECharts light and dark themes, from the `dataviz` and `frontend-design` skills | APP-05 | — |
| `charts` | Price and return chart with action marks and a delisting end, side-by-side source chart, run series chart on shared axes | APP-01, APP-03, APP-06, RESX-03 | `theme` |
| `data-screens` | Stock search and history, universe by date, builds and validation reports, analysis viewer, the "no accepted build" state | APP-01–APP-03, EDA-03 | `api`, `charts` |
| `runs-screen` | Start build, update or analysis, watch live progress, failing step and resume | APP-04 | `api` |
| `results-screens` | Run list with stage and verdict filters, run detail against its baseline, compare 2–6 runs, one generic view for every stage | RESX-01–RESX-04 | `api`, `charts` |
| `paper-screen` | Paper books against the benchmark: positions, trades, daily return, turnover, gaps | PAPER-02 | `api`, `charts` |

See [contract.md](contract.md).

## Cross-cutting concerns
- **APP-06:** a chart of 6,300 points on the ECharts canvas renderer with `sampling: "lttb"` draws in under 200 ms. A Playwright check opens one stock and asserts the chart is drawn within 1 s.
- **Type safety:** `pnpm gen:api` regenerates types from the server's exported OpenAPI. CI fails if they're stale.

Everything is still Draft, and nothing is committed.

**Decisions that need your attention**
- **Three data-source decisions wait on probes** and stay Proposed until the probes are answered:
  - **AD-03, Sharadar (PB-01):** which route serves your subscription, the exact codes for common stocks and corporate actions, and whether 1,000 names with 63 days of dollar volume exist on most dates from 2000. It also covers how corrections show up, and the download limits.
  - **AD-04, Yahoo via yahooquery (PB-02):** how many delisted stock-days Yahoo covers, whether dividends and splits come back on their dates, rate limits, and whether the daily cross-check fits the 10-minute update limit.
  - **AD-05, S&P 500 fallback (PB-03):** whether the S&P 500 table is in your subscription and goes back to 2000.
- **Sharadar keeps only the latest value of each row.** It records the last-updated date but no history of past values. From the first build on, `qdata` keeps every replaced value itself (AD-06). Data from before the first build is treated as known on its own trading date, so as-of loads can't see corrections Sharadar made before then.
- **Delisting returns:** the last return is the one up to the last traded price (AD-07). A cash-out or a worthless delisting after that isn't in Sharadar's price data, so failed companies may look better than they were. PB-01 checks whether the actions table carries those values.
- **The agents' reward (AD-16)** is the differential Sharpe ratio: each day's return after costs, minus a variance penalty. Summed over an episode, it tracks the episode's Sharpe ratio. This is how AGENT-01's risk penalty gets built.

**ASSUMPTIONS** (choices I made; tell me to change any of them):
1. **Stock identity:** every stock is keyed by Sharadar's permanent id, never its ticker. Dollar volume is the split-adjusted close times the split-adjusted volume.
2. **Daily returns:** worked out from Sharadar's fully adjusted close, on the New York Stock Exchange trading calendar.
3. **Storage:** data goes in Parquet files under a git-ignored `data/` folder at the project root. Run records go in `data/runs/` and paper books in `data/paper/`.
4. **Libraries:**
   - The shrinkage estimator is Ledoit–Wolf, shrinking toward a constant-correlation target.
   - Minimum variance uses cvxpy with the Clarabel solver; risk parity and HRP are written in-house.
   - The feature tests use LightGBM, with settings fixed in advance.
   - The forecasters are an LSTM and a small temporal-fusion-transformer-style model, both in plain PyTorch.
   - The agents use Stable-Baselines3's PPO.
   - The app draws charts with Apache ECharts.
5. **Multiple-testing correction:** Holm–Bonferroni by default, registered with each claim.
6. **Rented graphics card:** any hourly rental provider will do; you enter the hourly rate when a run starts. Only a frozen data extract goes to the rented machine, never your Sharadar key.
7. **API key:** read from the OS keychain or an environment variable. Every logged web address has the key removed, because Sharadar sends it in the address.
8. **Paper trading:** runs as a separate process started after each accepted daily update. The server never imports `learn`.
9. **Function names and signatures:** as written in the five `contract.md` files.

**Open questions:** only the three probes above. A side note: `dt lint` warns that the roadmap names the `dataviz` skill but can't find it installed with the plugin. It is available in this session, so this changes nothing in the design.
