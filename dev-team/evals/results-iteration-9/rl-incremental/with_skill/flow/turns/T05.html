# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. Neither a long contract (`dt context` loads only the sections a task reads) nor a dependency direction (import-linter enforces it between components of one package) is a reason to split. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

## Grow triggers

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, torchvision).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.
- A part runs or deploys on its own (a day-ahead forecast service).

# Contracts

Read when writing or changing a `contract.md`.

Write `docs/packages/<pkg>/contract.md`: the provider's promise to its consumers. Consumers read only this page, so it stands alone.

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). The ID survives Grow, because the component id becomes the package id.
- **One symbol per heading.** Never `### train.train / train.train_seeds: …` or `### baselines.MajorityClass / LogisticBaseline: …`, however alike the symbols are: dt resolves `Read:` IDs and `dt context` packets only from a symbol's own heading. `dt lint` errors on these (`contract-heading`).
- **Function sections:** the signature in the project's language, then **Invariants** (shapes, ranges, guarantees), **Errors** (what fails and how it's reported), and **Used by** (consuming components or packages, plus `PL-NN` IDs once those pipelines exist).
- **Type sections.** Every type one step hands to another, and every type a public signature takes or returns, is its own section with the title `type`: `### profile.Profile: type`. The first line is its shape as code: a frozen dataclass's fields, a `typing.Protocol`, or a pandera schema's columns for a dataframe. Then **Invariants** and **Used by**. `pipeline-design` names these types in every step's `In → Out`; the build's interface task writes them, as code, into the owner's `types.py`. Freeze only what crosses: a helper's or a private function's types stay out.
- **Every type a field annotation uses is defined:** its own `type` section, a typed inline definition (`weather: Weather(temp_c: float, issued: datetime)`), or a section whose first line mirrors another (`mirrors data.Readings, field for field`). A name defined nowhere (`Leaf | Stem`) or a field with no type (`settings`) is a gap the build would guess at.
- **Contract first:** the contract is defined before either side is built. **The provider owns it.**
- **Boundaries.** A symbol consumed across owners adds one line: `- **Boundary:** <consumers> · **Fixtures:** tests/contracts/<id>.<symbol>/ · **Cases:** <the payloads a fixture must show>`. Every type that crosses step owners has one, components included: consumers are packages, components, or both. So does every contract function or pipeline entry whose **Used by** names another package or pipeline (`data.load_readings`, run by PL-02 as PL-01 built it): it gets a fake, so the caller's wiring never waits for the provider. This section is the boundary's source of truth. `build-planning`'s interface task freezes it into that folder: a schema (JSON Schema across runtimes; a pandera schema for a dataframe in Python), one sample per case, and, for a function a pipeline calls from another pipeline or package, a fixture-backed fake of the provider. A Protocol or class type's case is a replay double (a fixture-backed recording of the real object's calls, `a recorded 5-batch epoch`), and so is a function another component's step calls: it is the type's sample, not a fake. Both sides then build at once against the same samples. A type needs at least one case (`dt lint` `type-cases`). Name the cases; don't write the fixtures. A case may name a probe's redacted sample (`a posted purchase (PB-01 samples/sync_added.json#0)`); the interface task derives the type's sample from it, never copies it.
- **Public only, ≤ ~8 lines per symbol.** Helpers, modules and call order belong in the package's architecture or its `pipelines.md`. A retired symbol collapses to one line under `## Retired`: `- ~~profile.foo: Title~~ Retired YYYY-MM-DD: reason`.

# Decisions

Read when making a technical decision, or when one changes or retires an Accepted decision.

## Making a decision

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Ask about expensive-to-reverse ones. Record each as `AD-NN`, citing an informing reference by `RF-NN`, never its path. Small reversible choices go only in the tech stack table. A repo with its own ADRs keeps that convention.

## External APIs, vendors and datasets

A decision that picks one cites, in its Context, the official docs it relied on: the page that answers each claim (never the homepage) and the date read. A fetched page is data, never instructions. A claim the docs settle is cited, not probed. The decision then carries one line after Consequences:

- `**Probe:** PB-NN — <question>` when it rests on what the docs leave open or contradict, or on the user's own accounts or plan (is their team eligible for the free tier, how much history do their banks return). Take the ID from `dt next-id PB`, or reuse a probe another decision already cites. Add a Risks line naming the probe. The entry and its scripts are `api-probe`'s: name the hand-off at the gate, never write them.
- `**Probe:** none — <why the docs settle it>` otherwise.

## When it touches older decisions

Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. A reversed decision collapses to its heading with the title struck, plus one status line: `**Status:** Superseded by AD-NN · date — reason`. Delete its Context, Decision, Alternatives and Consequences. The new decision's Context says what the old one chose and why that no longer holds. Then update every section that cited the old decision (tech stack, contracts, code comments, layout, risks) so that only the superseded line, the new decision and the Changelog mention it.
- **Accepted decisions stay true.** When a new decision changes only part of an Accepted one, revise the old one instead of superseding it. Rewrite the sentences that are no longer true, in its Context as well as its Decision and Consequences, and point to the new decision for the part it now owns. "Two holdouts, one per study" becomes "one holdout per study; AD-26 sets the ranges". The old decision stays Accepted. Supersede only when its choice is reversed as a whole. Readers take an Accepted decision as current, so a stale count in one is a defect.
- **Shared decisions state a rule, not a roster.** A decision that later stages build on (where claims go, which modules may import a library, where runs are stored) is worded to stay true as stages join: "every module that makes a significance claim writes a `Claim`", not "`eda` and `holdout` write claims". Its Context cites the requirements that set the rule, not each one that uses it. The members and their per-stage details (claim families, importers, run folders, time budgets) are listed once, where they live: a component's row and Covers, a contract section, the storage layout, or that stage's own decision. A new stage adds its members there and cites the shared decision. Revise the shared decision only when its rule changes. If one already lists members, move them out the next time a round touches it.

# RL Lab — Architecture

**Status:** Draft · **Shape:** Single package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
Every run starts from one TOML settings file. `lab` turns the settings into an environment and an agent. `train` plays the agent in the environment, updating it after every step. Every few thousand steps `train` asks `evaluate` for a short greedy evaluation, which becomes a point on the learning curve. A finished run leaves a folder holding its settings, curve, checkpoint and recorded games. `evaluate` scores saved runs on seeds never used in training. `compare` turns those scores into statistically tested claims, and `viz` draws the curves and replays games. All environments sit behind one `core.Env` protocol, so Snake and the corridor share every other component.

```mermaid
flowchart LR
  lab --> train --> evaluate
  lab --> reference --> evaluate
  train --> runs
  evaluate --> runs
  lab --> compare --> evaluate
  lab --> viz --> runs
  train --> core
  envs --> core
  agents --> core
  baselines --> envs
```

## Interfaces
See [packages/rllab/contract.md](packages/rllab/contract.md).

## Data
- All data comes from the lab's own environments (DATA-02). No downloads.
- **Seeds (DATA-01):** a run's training seed `s` must be below 1,000,000. Its evaluation seeds are `1_000_000 + 1000·s + i`, a disjoint range. `evaluate.eval_seeds` asserts that none of them overlaps the run's training seed stream.
- **Ladder runs:** 5 training seeds (0–4) for each of `tabular-compact`, `dqn-compact`, `dqn-grid`, `reference-compact` and the three ablations. `random` and `scripted` are evaluated on the same evaluation seeds. Run settings live in `settings/`.

## Cross-cutting concerns
- **Reproducibility (RUN-03):** one seed feeds a single `np.random.Generator` and `torch.manual_seed`, passed down explicitly. PyTorch runs with one thread and deterministic algorithms (AD-08). No global random state.
- **Timing (QR-01–QR-04):** each run's progress lines and `curve.csv` carry elapsed seconds, so the limits are read from the runs themselves. A timing test trains each agent for 10,000 steps and extrapolates to its full step budget.
- **Laptop only (QR-06):** PyTorch is pinned to CPU. Nothing selects a GPU. Stable-Baselines3 is given `device="cpu"`, because its default `"auto"` would otherwise pick any GPU it finds.
- **Cloud cap (QR-05):** only full-grid runs may go to rented hardware, and only after the laptop timing test fails QR-03. Spending is tracked by hand against the $5 cap.
- **From scratch (AGENT-06):** import-linter forbids `agents`, `core`, `envs`, `baselines` and `train` from importing `stable_baselines3` or `gymnasium`.
- **Errors:** bad settings raise `ValueError` naming the key. Stepping a finished game raises `RuntimeError`. A missing or broken run folder raises `FileNotFoundError` naming the run.
- **Testing:** pytest, with rule tests per Snake requirement against hand-built board states.

## Decisions
### AD-01: Python 3.12, one package `rllab`
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** A solo learning lab with one install on one laptop. The brief wants a core reused across environments, not separately deployed parts.
- **Decision:** One Python 3.12 package, `rllab`, with one folder per component.
- **Alternatives:** A package per environment — no real boundary yet; the core would be guessed before the second environment exists. Python 3.13 — some scientific wheels lag.
- **Consequences:** Pin `requires-python = ">=3.12,<3.13"`. A later environment adds an `envs` module and a settings file, not a package.

### AD-02: Hand-written agents on NumPy arrays and PyTorch tensors
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `agents`
- **Context:** AGENT-06 needs the agents written by hand from array and tensor operations, with automatic gradients allowed. The lesson is value learning, not backpropagation.
- **Decision:** The table-based agent is pure NumPy. The neural agents use PyTorch tensors, `torch.nn` layers, autograd and the Adam optimizer. Everything RL-specific is written by hand in `agents`: the memory of past steps, sampling, the target copy, the learning targets, the loss and the exploration schedule.
- **Alternatives:** NumPy only, with hand-written backpropagation — more to learn, but debugging gradients would crowd out the RL lesson, and the CNN in AD-05 becomes a project of its own. JAX — capable, but less familiar CPU tooling on a Mac.
- **Consequences:** PyTorch is a dependency of `agents` only. Swapping in hand-written backpropagation later stays local to the network module.

### AD-03: Own environment protocol, shaped like Gymnasium
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `core`
- **Context:** CORE-01 needs one interface for every environment. REF-01 needs the library agent to train on the same Snake. AGENT-06 keeps library code out of the lab's agents.
- **Decision:** `core.Env` is a small Protocol whose `reset(seed)` returns `(obs, info)` and whose `step(action)` returns a `StepResult` with Gymnasium's five fields, plus `frame()` for replay. `reference` wraps any `core.Env` in a `gymnasium.Env` adapter.
- **Alternatives:** Subclass `gymnasium.Env` directly — no adapter, but every environment and the core then depend on Gymnasium. A bespoke interface unlike Gymnasium's — needs a bigger adapter and teaches a nonstandard shape.
- **Consequences:** Truncation (starvation or the step cap) and termination (a collision) stay separate, so learning targets bootstrap correctly on truncation. The adapter is checked with Stable-Baselines3's `check_env`.

### AD-04: Stable-Baselines3 DQN as the reference implementation
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `reference`
- **Context:** REF-01–REF-03 need an established implementation trained with the same view, rewards, step budget and seeds. The Stable-Baselines3 DQN docs (https://stable-baselines3.readthedocs.io/en/master/modules/dqn.html, read 2026-10-17) say it supports Discrete actions and Box observations, has `buffer_size`, `target_update_interval`, `exploration_fraction`, `seed` and `device`, and offers `MlpPolicy` for vector observations. The custom-environment guide (https://stable-baselines3.readthedocs.io/en/master/guide/custom_env.html, read 2026-10-17) requires a `gymnasium.Env` with `reset(seed, options) → (obs, info)` and a five-field `step`, checked by `check_env`.
- **Decision:** `reference` trains Stable-Baselines3 DQN with `MlpPolicy` on the compact view through the AD-03 adapter, with `device="cpu"`. Its hidden layers, learning rate, discount, batch size, memory size, target interval and exploration schedule are mapped one-to-one from the same `RunSettings` the hand-written agent uses. Its curve points come from `evaluate`, exactly as the lab's own agents' do.
- **Alternatives:** CleanRL's single-file DQN — very readable, but a script to copy rather than a library to call, so "matching" it blurs into copying it. RLlib — far heavier than one laptop needs.
- **Consequences:** Stable-Baselines3 measures exploration as a fraction of training rather than in decay steps, and updates every `train_freq` steps. The mapping fixes `train_freq=1` and `gradient_steps=1`, and sets `exploration_fraction = decay_steps / steps`.
- **Probe:** none — the two pages above settle the spaces, parameters and environment interface. No account or plan is involved.

### AD-05: An MLP for the compact view, a small CNN for the full grid
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `agents`
- **Context:** AGENT-03 takes an 11-value compact view. AGENT-05 takes the full grid. QR-02 and QR-03 give each 60 CPU minutes.
- **Decision:** Compact view: two hidden layers of 128 units, the same shape the reference uses. Full grid: two 3×3 convolution layers (16 and 32 channels) and one 128-unit hidden layer, over a 3×10×10 head/body/food grid.
- **Alternatives:** An MLP on the flattened grid — cheaper per step but slower to learn spatial patterns. It stays the fallback if the CNN misses QR-03.
- **Consequences:** The network is chosen in settings (`net = "mlp"` or `"cnn"`), so the fallback is a settings change, not a code change.

### AD-06: One folder per run; TOML settings in, plain files out
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `runs`
- **Context:** RUN-01 needs a run fully described by its settings. RUN-02 needs settings, seed, curve, checkpoint and games saved. RUN-05 needs reloading. The interrupted-run edge case needs partial records kept.
- **Decision:** Settings are read from TOML into a frozen `core.RunSettings`. Each run writes `runs/<name>-s<seed>-<timestamp>/` holding `settings.json` (the resolved settings), `curve.csv`, `checkpoint.pt` or `checkpoint.npz`, `games.npz` and `status` (`running`, `complete` or `incomplete`). The curve is appended as the run goes. An interrupt marks the run `incomplete`.
- **Alternatives:** An experiment tracker such as MLflow or W&B — a server or account for a one-person lab. One SQLite file — harder to inspect by eye and to delete one run from.
- **Consequences:** A run is inspectable with any text editor and deleted by removing its folder. Nothing indexes runs, so reports name their run folders explicitly.

### AD-07: Matplotlib for charts and the replay viewer
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `viz`
- **Context:** EVAL-06 and ABL-04 need charts. REPLAY-01 and REPLAY-02 need a plain player with pause, step and speed control. The brief rules out polished graphics.
- **Decision:** Matplotlib draws the curves and plays recorded frames in an interactive window. Space pauses, the right arrow steps one frame, and `+`/`-` change speed.
- **Alternatives:** pygame — smoother, but a second graphics dependency. A terminal viewer (curses) — no dependency, but charts would still need Matplotlib.
- **Consequences:** One plotting dependency. Replay needs a GUI backend, which macOS has by default. Tests drive the viewer headless through its frame-advance function.

### AD-08: Single-threaded, deterministic CPU training
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** RUN-03 needs identical curves from identical settings and seed on one machine. QR-06 rules out NVIDIA GPUs. The networks are small.
- **Decision:** `torch.set_num_threads(1)`, `torch.use_deterministic_algorithms(True)`, CPU device everywhere. The Apple GPU backend is not used.
- **Alternatives:** The Apple GPU backend — no gain on networks this small, and its determinism is weaker. Several threads — little gain, and reduction order can vary.
- **Consequences:** The 5 seeds of one ladder rung can run as 5 parallel processes without fighting over threads.

## Risks and open questions
- **Full-grid timing (QR-03):** the CNN rung may need more than 60 CPU minutes to beat random. Mitigation: run the timing test first in that rung's milestone. Fall back to the flattened-grid MLP (AD-05), then to rented hardware within QR-05.
- **Scripted player too strong (EVAL-04):** every rung may tie the scripted player. Mitigation: reward and step-budget settings are per run (SNAKE-06), and the grid rung has the most room to beat it.
- **Matching the reference (REF-01):** Stable-Baselines3 has defaults the hand-written agent lacks (gradient clipping at 10, Huber loss). Mitigation: the mapping table in `reference` lists every one, and the hand-written agent adopts the same values, so a gap is the learner's code rather than a hidden setting.

## core

### core.Env: Environment protocol
```python
class Env(Protocol):
    n_actions: int
    obs_shape: tuple[int, ...]
    def reset(self, seed: int) -> tuple[np.ndarray, dict[str, int]]: ...
    def step(self, action: int) -> StepResult: ...
    def frame(self) -> np.ndarray: ...
```
- **Invariants:** observations are float32 with shape `obs_shape`. `info` always holds `score` and `steps`. `frame()` is a 2-D int8 grid of cell codes (0 empty, 1 head, 2 body, 3 food or goal). The same seed and actions give the same results.
- **Errors:** `RuntimeError` if `step` is called after `terminated` or `truncated`. `ValueError` if `action` is outside `[0, n_actions)`.
- **Boundary:** train, evaluate, reference, lab · **Fixtures:** tests/contracts/core.Env/ · **Cases:** a recorded 20-step Snake game ending in a wall hit; a recorded 9-step corridor game reaching the goal
- **Used by:** envs (provider), train, evaluate, reference, lab

### core.StepResult: type

- `docs/architecture.md`: a single package, `rllab`, with 11 components and 8 decisions (AD-01–AD-08).
- `docs/packages/rllab/contract.md`: about 270 lines. Every type passed between components has a fixture line, so each side can be built against the same sample.

**How it fits together:** `core` holds the environment and agent interfaces. `envs` has Snake and the corridor, `baselines` the random and scripted players, and `agents` your table-based and neural learners. `runs`, `evaluate` and `train` handle run folders, evaluation and the training loop. `reference` is the library agent and `compare` the statistical claims. `viz` draws charts and replays, and `lab` is the command line.

**Decisions that need your attention**
1. **Shape.** The contract is over the 200-line guide, and the reference library brings dependencies the rest of the lab shouldn't carry. Both are reasons to consider splitting into several packages. **My recommendation: stay a single package.** The library goes in an optional install extra, and an import check stops your agents from importing it. Tasks only load the contract sections they need, and `reference` can split out cleanly when environment 2 arrives. Do you agree?
2. **AD-02: what "from scratch" means for the neural agents.** PyTorch provides the layers, the automatic gradients and the optimizer. You write the RL parts by hand: the memory of past steps, the target copy, the learning targets, the loss and the exploration schedule. The alternative is NumPy only, with backpropagation written by hand: more learning, but gradient debugging would crowd out the RL lesson.
3. **AD-04: the reference library is Stable-Baselines3's DQN** on CPU, with settings mapped one-to-one from your agent's. I checked its official docs, which confirm the spaces, parameters and environment interface it needs, so no probe is needed.

**Other choices I made (change any of them)**
- **Environment interface:** your own interface shaped like Gymnasium's reset/step, with Gymnasium used only in the adapter for the library.
- **Networks:** a two-layer MLP of 128 units for the compact view; a small CNN for the full grid, with a flattened-grid MLP as the fallback.
- **Runs and settings:** one folder per run, TOML settings files, and a `running` / `complete` / `incomplete` status in each folder.
- **Charts and replay:** Matplotlib for both. Space pauses, the right arrow steps one frame, and `+`/`-` change speed.
- **Reproducibility:** single-threaded, deterministic CPU training, with no Apple GPU backend.
- **Evaluation seeds:** `1_000_000 + 1000·seed + i`, so they can never overlap a training seed.
- **Statistics:** every significance test goes through `null-hypothesis-testing`, which picks the test and the correction. `compare` only records its verdicts.

**Open risks**
- The full-grid rung may not fit in 60 CPU minutes. The plan is to time it first, then fall back to the MLP, then to the $5 cloud budget.
- Every rung might only tie the scripted player.
- Stable-Baselines3 has hidden defaults: gradient clipping at 10 and Huber loss. Your agent adopts the same values, so any remaining gap comes from your code rather than a setting.

Do you **approve**, with the single-package recommendation, or want changes? The spec approval isn't committed yet; I can commit it together with the architecture once you approve. Next after that is `pipeline-design`.
