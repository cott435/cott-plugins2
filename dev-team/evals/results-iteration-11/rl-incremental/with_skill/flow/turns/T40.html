# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module naming its Layout file; a step with two owners is two steps), In → Out, Spine version (what the simplest real version does; a type's fields and rules stay in the contract, never restated here), Covers. Every `QR-` item in scope is on the Covers of the step that applies it, a cost or licence limit on the step that picks or calls the source ("no paid data beyond the subscription" on the source factory and each source row); a `QR-` on no step keeps its stage below Designed. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change, routed with the fields its steps need (`../SKILL.md`, Not for) and named in the cell as the contract will name it; never invent it here. `dt lint` checks it (`step-io-types`); a routed type's errors stand until that Revise adds it.
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. One module per step owner, at the Owner's path with dots as folders and the name unchanged (`profile.fit` → `profile/fit.py`, `stock.view` → `stock/view.tsx`, never `stock/StockView.tsx`; an owner given only as `profile` gets one module per related group of steps), never named like a generated file (`api.schema` beside a generated `api/schema.ts`: call it `api.schema_check`). A step whose module needs private helpers owns a folder instead (`core.train` → `core/train/`), holding them; no other step's code goes inside it. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. ## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).

96	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
97	- **Context:** The user called Snake a "Good first env for DQN-style value learning" (UR-06) and said "I want to write DQN from scratch" (UR-08). 102	### AD-03: CPU only; one thread per run, separate processes for the study
103	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
104	- **Context:** The user's words are "Laptop CPU only" (UR-13). QR-01 limits one run to ≤ 60 minutes, and QR-02 limits each environment's study: Snake's 20 runs plus baselines to ≤ 10 hours, the tank's 30 to ≤ 15 hours. 107	- **Consequences:** A run's time doesn't depend on the other runs, as long as there are enough cores. On a 4-core laptop, 3 runs go at once: Snake's study takes about 7 rounds and needs each run under about 80 minutes when 3 run in parallel; the tank's takes 10 rounds and needs each under about 90 minutes. 109	### AD-04: Seeds owned per object, fixed held-out range
110	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
111	- **Context:** SNAKE-08, TANK-10, CORE-01, AGENT-06, PG-12, REPLAY-04, REPLAY-05 and QR-05 need same seed → same game. EVAL-01 needs the training and held-out seeds never to overlap.

114	- **Consequences:** A replay of a saved agent on a held-out seed reproduces its logged evaluation score (REPLAY-05). Results are reproducible on one machine, not across machines (QR-05 asks only for the first).

166	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
167	- **Context:** AGENT-04 has the DQN learn from remembered steps as it plays; PG-05 has every rung learn once after each game from all its fish's steps. CORE-05 and CORE-07 need one training loop for both, and TWIN-02 has the DQN treat each fish's steps as its own.

172	### AD-13: The policy-gradient ladder: one hand-written `PGAgent` with a rung number and 3 switches
173	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
174	- **Context:** The user wants "policy-gradient/PPO and continuous control" (UR-48) and chose "The full ladder with off switches." (UR-55). PG-01–PG-09 fix the mechanics: a centre and width per control, clipping to the limits, one update per game from every fish's steps at discount 0.99, an advantage blend of 0.95, rescaled advantages on rungs 2 and 3, and on rung 3 10 passes in batches of 64 with a 20% cap. ABL-06–ABL-08 switch off rung 3's value estimate, cap and rescaling. QR-03 rules out RL libraries.
175	- **Decision:** `pg.PGAgent` takes `PGConfig.rung`. The policy is an MLP of observation size → 64 → 64 → one centre per control (tanh hidden layers) with a learned, observation-independent log width per control. Moves are drawn from a normal distribution and clipped to the limits, and log-probabilities are taken on the clipped move. Rung 1 weights each move's log-probability by the discounted return to that fish's end and makes one Adam step per game. Rung 2 adds a value MLP of the same size, trained by mean-squared error on the returns, and weights moves by the 0.95-blended advantage, rescaled. Rung 3 adds 10 passes over the game's steps in shuffled batches of 64, with the probability ratio clipped to 0.8–1.2. With `value` off, rung 3 uses the returns in place of advantages; with `cap` off, the ratio isn't clipped; with `rescale` off, advantages are used as built. Adam lr 3e-4. A game ended by the time limit stops returns at step 1,000 with no value carried past it.
176	- **Alternatives:** Three separate agent classes: the switches would cut across class lines, and the "switch on a rung without that part" check would be scattered. A tanh-squashed policy instead of clipping: an exact log-probability, but PG-03 describes clipping a draw that falls outside, and squashing changes what "centre" means in PG-01 and PG-02. Width predicted from the observation: more expressive, but less stable for a first policy-gradient build.
177	- **Consequences:** The module code can still read rung by rung (one file per rung's addition, laid out by `pipeline-design`). Hidden sizes, lr, the log-width start and clipping before the log-probability are choices the spec doesn't fix, kept in `PGConfig`. Taking log-probabilities on the clipped move biases the gradient when the policy pushes past a limit (see Risks).

207	## Risks and open questions
208	- **Training time (QR-01, QR-02):** neither default of 1,000 games has been timed. In Snake, a greedy agent that circles until the step limit makes evaluation games long; in the tank, a good policy plays up to 1,000 steps × 5 fish per game, each fish asking the policy network once per step, plus 10 evaluation points of 20 games and a final check of 100. Mitigation: the first milestone of each stage times one run alone and 3 in parallel. If too slow, lower the default game count; the spec doesn't fix it.
209	- **Settings the spec leaves open:** the DQN's 11 → 256 → 3 network, Adam lr 1e-3, batch 64, Huber loss and linear ε decay (AD-02), and the ladder's 64-unit networks, lr 3e-4 and log-width start (AD-13), are tutorial defaults, not tested here. If a learner doesn't beat the scripted baseline (EVAL-04), tune these before questioning the design.
210	- **Clipped log-probabilities (AD-13):** a policy whose centre sits past a limit (a fish always turning 15°) gets biased gradients. If curves stall with the centre outside the limits, take the log-probability of the unclipped draw instead and record it in `Transition`.
211	- **8 rays and one ball (brief bet):** the idea bets 8 short rays carry enough to dodge the ball, and that fish don't sense its motion (UR-58). If no rung beats the scripted fish, that is a finding for the notes (PG-11), not a design failure.
212	- **Comparison method:** the test statistic, how the seeds × 100 games are paired and the multiple-comparison correction are left to the `null-hypothesis-testing` skill when `study.compare_scores` is built. The contract passes it the raw per-seed, per-game scores so the skill can pair by game seed; each side may have fewer than 5 seeds (AD-09).
213	- **M1 rework:** the grown core (AD-11, AD-12, AD-15) changes signatures M1's approved plan, PL-01–PL-06 and the S1 golden cases were written against. Nothing is built, so the cost is docs; the build waits for pipeline-design, test-planning and build-planning's replan.

198	### Ablation switches (`ABL`)
199	**Serves:** Goal 1
200	**Stage:** S1
201	**Behavior:** Each environment has three switches, each turning off one part of its top agent, so the learner can train the agent without it and compare. On Snake they turn off the value-learning agent's memory, frozen copy and exploration decay; on the tank they turn off the limited-update agent's value estimate, update cap and advantage rescaling. Each switch is set per run and recorded in the run's log. The comparison of each ablated agent with the full agent is judged by a hypothesis test.
202	
203	**Requirements**
204	- **ABL-01** With the memory switch off, the agent learns from only the step it just took, with no remembered steps.
205	  - Given memory off, when the agent learns, then each update uses exactly the latest step.
206	- **ABL-02** With the frozen-copy switch off, the agent builds its targets from its current value estimate.
207	  - Given frozen copy off, when a target is built, then it uses the current estimate's best next value, which changes after every update.
208	- **ABL-03** With the exploration-decay switch off, the agent's random-move probability stays fixed at 0.1 for the whole run.
209	  - Given decay off, when the agent picks moves at any point in training, then about 10% are random.
210	- **ABL-04** Each ablated agent is compared with the full agent of its environment (Snake: the value-learning agent; the tank: the limited-update agent) with the `null-hypothesis-testing` skill, given the final evaluation scores of both (5 training seeds each, on the same 100 held-out games); the ablation counts as hurting learning only if the full agent's scores are higher at a 5% significance level after correcting for the 3 comparisons in that environment.
211	  - Given finished runs of the full agent and the 3 ablated agents of one environment, when the study is run, then each ablation is reported as "hurts learning" or "no detectable difference", with its test result.
212	- **ABL-05** When no switch hurts learning, the study is still complete: the result is recorded as a finding in the notes, and S1 doesn't count as failed (nor S2, for the tank's switches).
213	  - Given a study report where all 3 ablations show "no detectable difference", when the stage is checked, then it passes, and the notes page records that no switch hurt learning as a finding (EXPL-02).
214	- **ABL-06** With the value-estimate switch off, the limited-update agent weights each move by the discounted return that followed it, as rung 1 does, and learns no value estimate.
215	  - Given value estimate off, when a fish's rewards were +1, +1, 0, then its moves are weighted 1.99, 1 and 0 before rescaling.
216	- **ABL-07** With the update-cap switch off, the limited-update agent still makes its 10 passes over each game's steps, with no limit on how far a move's probability can move.
217	  - Given cap off and a move already 1.3 × as likely as when played, with a positive advantage, when the next pass updates, then that move still becomes more likely.
218	- **ABL-08** With the rescaling switch off, the limited-update agent uses each game's advantages as built, without rescaling.
219	  - Given rescaling off, when a game's advantages are used, then they equal the advantages as built.
220	
221	**Edge cases & errors**
222	- Several switches are off in one run → allowed; the run's log records every switch's state.
223	- An ablated run fails before finishing → the study reports that ablation as missing, never as "no detectable difference".
224	- A switch is set on an agent that doesn't have that part (the tank's switches on rungs 1 or 2's missing pieces, Snake's switches on a tank rung) → the run is refused at start-up, naming the switch and the agent.

227	**Serves:** Goal 2
228	**Stage:** S1
229	**Behavior:** Two non-learning agents play the same seeded games as the learning agents in each environment: a random agent and a simple scripted agent. Their scores set the bars every learning agent's curve must clear.
230	
231	**Requirements**
232	- **BASE-01** The random agent picks each move uniformly at random from the allowed moves: one of the choices, or each control anywhere within its limits.
233	  - Given 10,000 moves by the random agent on Snake, when counted, then each of the 3 moves is picked 30–37% of the time.
234	  - Given 10,000 moves by the random agent in the tank, when counted, then turns are spread evenly over −15° to +15° and speeds over 0 to 0.3, each tenth of either range holding 9–11% of moves.
235	- **BASE-02** On Snake, the scripted agent moves toward the food along the axis with the larger gap, and when that move is immediately fatal it takes any non-fatal move, preferring straight.
236	  - Given food straight ahead and no danger ahead, when the scripted agent moves, then it goes straight.
237	  - Given food straight ahead and a wall ahead, when it moves, then it turns to a side that is free.
238	- **BASE-03** Both baselines are scored on the same 100 held-out games as the learning agent.
239	  - Given the 100 held-out seeds, when each baseline plays them, then each records one score per seed, and its mean and spread are logged.
240	- **BASE-04** In the tank, the scripted fish swims at full speed, turning as far as it can away from the ray that sees the ball closest; with no ball in reach it swims straight, and when the wall is within 1 unit straight ahead it turns as far as it can toward the side whose rays see more room.
241	  - Given the ball seen only on the front-left ray and no wall within 1 unit ahead, when the scripted fish moves, then it turns −15° (to the right) at speed 0.3.
242	  - Given no ball in reach and the wall 0.5 units straight ahead with more room on the left, when it moves, then it turns +15° at speed 0.3.

244	**Edge cases & errors**
245	- Every move is fatal → the scripted agent goes straight and the game ends.
246	- The scripted fish sees the ball equally close on two rays → it turns away from the one further left.
247	- The scripted fish sees the ball and the wall ahead at once → it avoids the wall.

249	### Evaluation (`EVAL`)
250	**Serves:** Goal 2
251	**Stage:** S1
252	**Behavior:** Every training run is checked at regular points on a fixed set of held-out games it never trains on, with exploration off, and ends with a final check on all 100 held-out games. Each learning agent's final check is compared with both baselines of its environment on those same games.
253	
254	**Requirements**
255	- **EVAL-01** Training games and evaluation games come from separate seed sets that never overlap.
256	  - Given any training run, when its training and evaluation seeds are listed, then no seed appears in both.
257	- **EVAL-02** During training the agent plays held-out games at regular points with exploration off and its mean score is logged: on Snake every 50 training games over all 100 held-out games; in the tank at every tenth of training over the same 20 of its 100 held-out games. Every run ends with a final check over all 100.
258	  - Given a Snake run of 1,000 training games, when it ends, then 20 evaluation results are logged, each over the same 100 seeds.
259	  - Given a tank run, when it ends, then 10 evaluation results over the same 20 seeds and one final result over all 100 seeds are logged.
260	- **EVAL-03** Each learning agent's final evaluation scores are compared with each baseline's scores of its environment with the `null-hypothesis-testing` skill, given 5 training seeds × the 100 held-out games for the agent and the same 100 games for each baseline; the agent beats a baseline only if its scores are higher at a 5% significance level after correcting for every comparison in that environment (2 on Snake: the full agent against 2 baselines; 6 in the tank: 3 rungs against 2 baselines).
261	  - Given finished runs of the full agent and both baselines, when the comparison is run, then the report says, for the random agent and for the scripted agent, whether the agent beats it, with the test result.
262	  - Given finished runs of all 3 rungs and both tank baselines, when the comparison is run, then the report says, for each of the 6 pairs, whether the rung beats the baseline, with the test result.
263	- **EVAL-04** On Snake the full agent's learning curve beats both the random baseline and the scripted baseline; in the tank every rung's learning curve beats both the random fish and the scripted fish.
264	  - Given the EVAL-03 report for Snake, when it is read, then the agent beats both baselines.
265	  - Given the EVAL-03 report for the tank, when it is read, then each of the 3 rungs beats both baselines.
