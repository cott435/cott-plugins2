# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency direction worth enforcing with tooling. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

## Grow triggers

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, gym).
- A one-way dependency is worth enforcing (data must never import models, to prevent leakage).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.
- A part runs or deploys on its own (a paper-trading service).
# Components

Read when adding, changing or documenting components.

- **Each component:** one responsibility in a sentence, the spec IDs it covers, what it depends on.
- **Every live requirement is covered**, `QR-` and `DATA-` included; cross-cutting ones under Cross-cutting concerns.
- **Dependencies point one way.** Two components needing each other are one, or miss an interface.
- **Single package:** one subfolder per component, its `__init__` exporting its contract.
- **Route steps to installed skills.** Each skill on the stage's `**Skills:**` line, and any installed skill owning a step (a hypothesis test, a security review), is named on the component running the step, whose contract takes what the skill needs. Never design a replacement procedure.
# Contracts

Read when writing or changing a `contract.md`.

Write `docs/packages/<pkg>/contract.md`: the provider's promise to its consumers. Consumers read only this page, so it stands alone.

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). The ID survives Grow, because the component id becomes the package id.
- **One symbol per heading.** Never `### train.train / train.train_seeds: …` or `### baselines.RandomAgent / ScriptedSnake: …`, however alike the symbols are: dt resolves `Read:` IDs and `dt context` packets only from a symbol's own heading. `dt lint` errors on these (`contract-heading`).
- **Function sections:** the signature in the project's language, then **Invariants** (shapes, ranges, guarantees), **Errors** (what fails and how it's reported), and **Used by** (consuming components or packages, plus `PL-NN` IDs once those pipelines exist).
- **Type sections.** Every type one step hands to another, and every type a public signature takes or returns, is its own section with the title `type`: `### stats.Cov: type`. The first line is its shape as code: a frozen dataclass's fields, a `typing.Protocol`, or a pandera schema's columns for a dataframe. Then **Invariants** and **Used by**. `pipeline-design` names these types in every step's `In → Out`; the build's interface task writes them, as code, into the owner's `types.py`. Freeze only what crosses: a helper's or a private function's types stay out.
- **Contract first:** the contract is defined before either side is built. **The provider owns it.**
- **Boundaries.** A symbol consumed across owners adds one line: `- **Boundary:** <consumers> · **Fixtures:** tests/contracts/<id>.<symbol>/ · **Cases:** <the payloads a fixture must show>`. Consumers are packages in a multi-package repo, and components in a single package. This section is the boundary's source of truth. `build-planning`'s interface task freezes it into that folder: a schema (JSON Schema across runtimes; a pandera schema for a dataframe in Python), one sample per case, and, for a function a pipeline calls from another pipeline or package, a fixture-backed fake of the provider. Both sides then build at once against the same samples. A type needs at least one case. Name the cases; don't write the fixtures.
- **Public only, ≤ ~8 lines per symbol.** Helpers, modules and call order belong in the package's architecture or its `pipelines.md`. A retired symbol collapses to one line under `## Retired`: `- ~~stats.foo: Title~~ Retired YYYY-MM-DD: reason`.

# Decisions

Read when making a technical decision, or when one changes or retires an Accepted decision.

## Making a decision

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Ask about expensive-to-reverse ones. Record each as `AD-NN`, citing an informing reference by `RF-NN`, never its path. Small reversible choices go only in the tech stack table. A repo with its own ADRs keeps that convention.

## When it touches older decisions

Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. A reversed decision collapses to its heading with the title struck, plus one status line: `**Status:** Superseded by AD-NN · date — reason`. Delete its Context, Decision, Alternatives and Consequences. The new decision's Context says what the old one chose and why that no longer holds. Then update every section that cited the old decision (tech stack, contracts, code comments, layout, risks) so that only the superseded line, the new decision and the Changelog mention it.
- **Accepted decisions stay true.** When a new decision changes only part of an Accepted one, revise the old one instead of superseding it. Rewrite the sentences that are no longer true, in its Context as well as its Decision and Consequences, and point to the new decision for the part it now owns. "Two holdouts, one per study" becomes "one holdout per study; AD-26 sets the ranges". The old decision stays Accepted. Supersede only when its choice is reversed as a whole. Readers take an Accepted decision as current, so a stale count in one is a defect.
- **Shared decisions state a rule, not a roster.** A decision that later stages build on (where claims go, which modules may import a library, where runs are stored) is worded to stay true as stages join: "every module that makes a significance claim writes a `Claim`", not "`eda` and `backtest` write claims". Its Context cites the requirements that set the rule, not each one that uses it. The members and their per-stage details (claim families, importers, run folders, time budgets) are listed once, where they live: a component's row and Covers, a contract section, the storage layout, or that stage's own decision. A new stage adds its members there and cites the shared decision. Revise the shared decision only when its rule changes. If one already lists members, move them out the next time a round touches it.

# Writing rules

Read before writing or changing any architecture doc, every round. Decision rules are in `decisions.md`.

- **`PL-NN` IDs are permanent.** A retired system pipeline collapses to `- ~~PL-NN: title~~ Retired YYYY-MM-DD: reason`.
- **Describe the design as it is now, not how it got here.** No process notes ("no code was built before this change"), no struck-through risks, no per-stage blocks of risks or notes. Git keeps the rest.
- **The Changelog has one row per round, one line long.** IDs are the new decisions, as ranges (`AD-12–AD-15`). Don't repeat the spec row's ID list. The exception is a spec row with no source file: copy its IDs with their marks (`AD-16; QR-03 (changed)`). While that runs, the first decision is the project's shape.

**My recommendation: multi-package, with three packages:**

```
web (browser app)  ──calls──▶  server (backend: queries + live run progress)  ──imports──▶  data (library)
```

- **`data`** is the Python library: download, snapshots, cleaning, validation, storage, the as-of loader, exploratory reports, and the command line. Later stages (signals, backtests) will import only this package.
- **`server`** is the local Python backend over `data`. It handles queries over HTTP and pushes live run progress over WebSocket. It can't run builds itself; it starts them through `data`.
- **`web`** is the TypeScript + React app. It talks to `server` only through one shared contract. That contract is the source the TypeScript types are generated from, so a mismatch fails the checks (QR-06).

**Why three packages rather than one:**
- The boundaries are real. `web` runs on a different runtime from the rest, which alone makes it a separate package.
- `data` must never import `server` or `web`. Later research code should get the dataset without web-server dependencies, and the rule can be enforced by tooling.
- I considered two packages (Python and web). But that lets the backend and the research library tangle together, and it's harder to undo later.

**Dependency rules:** `web` → `server` (over the network contract only) → `data`. `data` imports nothing internal. Only `data` writes to the store.
