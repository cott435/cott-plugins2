7	## Overview
8	Every environment implements `core.Env`, and every agent implements `core.Agent`. `train` takes a `RunConfig` and builds the environment and agent by name through `experiments`. Environments render to a generic `core.Frame` grid of cell codes, so nothing downstream knows Snake from the corridor (CORE-07).

80	## Decisions
81	### AD-01: Python 3.12 managed with uv
82	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
83	- **Context:** The learner knows Python and PyTorch. The laptop has Python 3.13 and uv installed.
84	- **Decision:** Python 3.12, pinned in `pyproject.toml`, with the environment and lock file managed by uv.
85	- **Alternatives:** 3.13 — supported by current PyTorch, but 3.12 has the widest wheel coverage, and nothing here needs 3.13. Plain pip with a venv — works, but there's no lock file, so it's less reproducible.
86	- **Consequences:** `uv run` is the entry for every command; uv installs 3.12 itself.
87	
88	### AD-02: Own environment protocol, shaped like Gymnasium, with no Gymnasium dependency
89	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
90	- **Context:** CORE-01–CORE-04 need one interface for every environment. The brief wants everything built by hand now, and a comparison with library agents later.
91	- **Decision:** `core.Env` is a `typing.Protocol` with `reset(seed) -> obs` and `step(action) -> StepResult` (observation, reward, terminated, truncated, info), the same split Gymnasium uses, plus `render() -> Frame`. Actions are plain integers; there are no space objects.
92	- **Alternatives:** Subclass `gymnasium.Env` — library agents work immediately, but it adds spaces, wrappers and checker rules that teach the library rather than the concept. A free-form API — would make the later library comparison a rewrite.
93	- **Consequences:** The later library-comparison stage needs a thin adapter (about 30 lines). The terminated/truncated split is in the protocol from day one, so bootstrapping is right (TAB-02, DQN-06).
94	
95	### AD-03: Snake simulated in plain Python, observations as NumPy vectors
96	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `snake`
97	- **Context:** QR-03 requires ≥ 10,000 steps per second. On a ≤ 10×10 grid, the per-step work is a few set lookups.
98	- **Decision:** Body is a `deque` of cells plus a `set` for collision checks; the 11 features are computed directly, then packed into one `float32` array.
99	- **Alternatives:** A NumPy grid array per step — the overhead of creating arrays dominates at this size. Vectorized batches of environments — faster, but harder to read and not needed for the budget.
100	- **Consequences:** The code reads like the rules. Rendering builds a `Frame` only when asked, never in the training loop.
101	
102	### AD-04: DQN in PyTorch on one CPU thread
103	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `dqn`
104	- **Context:** DQN-09 needs a general neural-network toolkit with no RL library. QR-01 gives ≤ 15 minutes per L3 run on an M4 Pro, with no NVIDIA GPU. The network is tiny: 11 inputs, 3 outputs.
105	- **Decision:** PyTorch, with a two-hidden-layer MLP (128 units each by default) and Adam optimizer. Everything runs on the CPU, with `torch.set_num_threads(1)`. Replay buffer and target network are written by hand.
106	- **Alternatives:** Apple GPU (MPS) — the overhead of each GPU launch outweighs the work for batches of 64 on a network this small. JAX — less familiar to the learner. A network in NumPy by hand — possible, but backprop by hand is a different lesson.
107	- **Consequences:** A 200,000-step L3 run should take minutes, well inside QR-01; a timing test confirms it. PyTorch is the largest dependency, so only `dqn` may import it (`runstore` saves and loads agents through their own `save` and `load`). This is enforced by a lint rule, which keeps `dqn` a clean seam for a later split.
108	
109	### AD-05: Reproducibility by explicit seeded random sources
110	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
111	- **Context:** QR-04 and SNAKE-15 require identical results from the same seed and configuration.
112	- **Decision:** Every environment and agent owns an `np.random.Generator` created from its seed. DQN also seeds torch, uses one thread and turns on `torch.use_deterministic_algorithms(True)`. No code touches global random state.
113	- **Alternatives:** Global seeding at program start — brittle, since any extra random call shifts every later result.
114	- **Consequences:** Results are reproducible on one machine. Across PyTorch versions or machines they may differ slightly, which QR-04 allows.
115	
116	### AD-06: Plain files per run, never overwritten
117	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `runstore`
118	- **Context:** TRAIN-04 requires each run kept separately with its configuration, logs, agent and recordings; QR-05 requires offline use; the brief rules out tracking services.
119	- **Decision:** One folder per run, named with seed and timestamp (layout under Data), created exclusively so it can't overwrite. JSON for configuration and summaries, CSV for logs, `.npz` for recordings and the tabular table, `.pt` for the network's weights.
120	- **Alternatives:** SQLite — overkill for append-only logs, and harder to read by eye. An experiment-tracking service — ruled out by the brief.
121	- **Consequences:** Every artifact is readable with a text editor or one line of NumPy. Finding runs is a directory search, which is fine for tens of runs.
122	
123	### AD-07: Matplotlib for both plots and the interactive viewer
124	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `viewer`, `plots`
125	- **Context:** VIEW-01–VIEW-06 need an interactive replay with controls, an action-value panel and animation export. EVAL-03 and ABL-04 need static plots following the `dataviz` skill.
126	- **Decision:** Matplotlib for both. The viewer is one figure: a grid image, a bar panel for the action values, buttons and a speed slider (Matplotlib widgets), and keyboard shortcuts. Export uses Matplotlib's animation writer with Pillow to produce GIF.
127	- **Alternatives:** Pygame — a smoother game loop, but a second graphics stack and hand-built controls. A terminal viewer — no export, and too cramped for the value panel.
128	- **Consequences:** One plotting dependency. Playback tops out at around 30 frames per second, which matches VIEW-02's limit. It needs a GUI backend (macOS's native one) for the interactive window; export works without one.
129	
130	### AD-08: Significance tests are run by the null-hypothesis-testing skill, not by code
131	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `compare`
132	- **Context:** EVAL-02 and ABL-03 name the `null-hypothesis-testing` skill as the owner of the test, the correction and the decision.
133	- **Decision:** `compare.write_comparisons` writes `reports/<name>/inputs.json`: one `ComparisonInput` per pair, carrying per-seed mean scores and per-episode scores for both sides. The skill is run on that file and writes `verdicts.json` as `Verdict` records. `compare.results_table` joins the verdicts with the run summaries, and marks a report underpowered when there are fewer than 5 seeds.
134	- **Alternatives:** A t-test or permutation test hand-written in `compare` — a second, unreviewed version of the skill's procedure.
135	- **Consequences:** Producing a report takes two steps (write the inputs, run the skill). `results_table` refuses to build until verdicts exist for every input.
136	
137	### AD-09: Fixed, disjoint seed ranges for training and evaluation
138	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `evaluate`, `train`
139	- **Context:** EVAL-01 requires evaluation seeds that are the same for every agent and never used in training. TRAIN-05 needs a fixed set for the learning curve.
140	- **Decision:** These are constants in `evaluate`: final evaluation uses 10,000–10,099, and the curve uses 20,000–20,019. Training episodes draw seeds from 1,000,000 upward using the run's generator.
141	- **Alternatives:** Random evaluation seeds per run — the comparisons would no longer be paired.
142	- **Consequences:** Every agent and baseline is scored on identical games, so paired tests are possible. Changing the ranges invalidates old comparisons.
143	
144	### AD-10: Pipeline entries are the public workflows; every step hands over a contract type
145	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
146	- **Context:** Pipeline design (PL-01–PL-09) found that the first contract mixed entry-like functions (`train_run`, `train_seeds`, `play_live`) in with steps. It left the protocols and `RunWriter` without type sections, and returned bare paths, strings or None from file-writing and interactive steps, so the step hand-offs had no types to freeze.
147	- **Decision:** Each workflow's public function is its `run_<workflow>` entry in the owning component's `pipeline.py` (`train.run_train`, `train.run_preset`, `compare.run_compare`, `compare.run_report`, `plots.run_plot`, `viewer.run_view`, `viewer.run_play`, `viewer.run_export`, `cli.run_inspect_table`). `cli` only parses arguments into them. Protocols and `RunWriter` are type sections. Every written file is returned as a `core.Artifact`; the report as a `compare.ResultsTable`; the viewer's exit as a `viewer.ViewResult`. `core.Env` carries `obs_labels`, so feature labels never need a `snake` import. Running one configuration over seeds (TRAIN-02) goes through preset sets.
148	- **Alternatives:** Keep returning paths and None — those steps then have nothing to freeze or test against. Keep `train_seeds` beside the presets — two ways to run a seed sweep.
149	- **Consequences:** Nine extra small contract sections. `gridlab train` runs one seed; sweeps are presets. `ablation_curves` returns `Artifact | None` for sets without variants.
150	
151	### AD-11: Test hooks are part of the contract
152	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `snake`, `dqn`
153	- **Context:** The known-answer cases (TC-02–TC-11, TC-18) need exact Snake states and a checkable DQN target. Through `reset` alone, food lands wherever the seed puts it, which can't be known before the code exists.
154	- **Decision:** `snake.SnakeEnv.set_state` puts the environment in a given body, heading, food and counters. `dqn.td_targets` is a pure function that `DQNAgent` uses for every update.
155	- **Alternatives:** Search seeds for wanted food positions — brittle, and it breaks when placement changes. Test private internals — couples tests to code layout.
156	- **Consequences:** `set_state` is also handy for teaching (set up a trap, then watch the agent). The target formula lives in one place that's tested by hand.
157	
158	### AD-12: Stay single-package through S1
159	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
160	- **Context:** The package has 9 pipelines (the Grow trigger is > 3), a 404-line contract (ceiling 200), and PyTorch as a heavy dependency. It's a one-person learning project with one install and no separate deployments.
161	- **Decision:** Keep `gridlab` as one package for all of S1. The seams stay named for a later split: environments (`core`, `snake`, `corridor`, `baselines`), agents (`tabular`, `dqn`) and the lab (the rest). Only `dqn` imports PyTorch (AD-04).
162	- **Alternatives:** Split now into three packages — more install and versioning ceremony than one learner needs before a second environment exists.
163	- **Consequences:** Build agents read a large contract through `dt context` packets, which stay under 2,000 lines. Revisit when Env 2's stage is cut.

165	## Risks and open questions
166	- **The greedy baseline may be hard to beat.** It sees exactly what the agent sees (danger and food direction), and with 11 features neither can see the shape of its own body, so DQN-10 may fail against greedy. Mitigations: tune the discount and training length first. If it still fails, that's a finding, which may lead to a spec change (for example, a richer observation).
167	- **5 seeds is little statistical power.** A real but small edge may not reach significance. The skill reports what it can; more seeds fit the time budget if needed.
168	- **The interactive Matplotlib backend on macOS** can lag with keyboard handling. Fallback: drive everything from the buttons.
169	- **The contract is 392 lines, over the 200-line ceiling for one package (lint `grow-size`).** It stays single-package for this proof of concept. The seams for a later split are named: `core`+`snake`+`corridor`+`baselines` (environments, no PyTorch), `tabular`+`dqn` (agents), and the rest (the lab). Split when Env 2 lands, or if build agents struggle with the contract's size.

# Grid RL Lab — Architecture

**Status:** Draft · **Shape:** Single package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

Single package (`gridlab`): one learner, one laptop, one install (AD-12). Environments sit behind the `core.Env` protocol, so each new environment drops in as a new component folder.

## Overview
Every environment implements `core.Env` and every agent implements `core.Agent`. Both work on arrays with one row per agent: Snake and the corridor have one row, a fish school has five (AD-13). An environment declares its `ActionSpace`, either discrete choices or bounded continuous values, and renders a `Frame` of shapes.

`train` takes a `RunConfig` and builds the environment and agent by name through `experiments`. It runs the step loop, hands the agent each step's `Transition`, pauses on a schedule for greedy evaluation via `evaluate`, and writes everything through `runstore` into the run's own folder. Value agents (`tabular`, `dqn`) learn from each transition; policy agents (`pg`) collect rollouts and update when one fills. After a set of runs, `compare` writes comparison inputs that the `null-hypothesis-testing` skill tests, and its verdicts come back into a results table. `plots` draws learning curves, and `viewer` replays any recorded episode from its shapes and agent readouts, without knowing which environment made it (CORE-07).


## Data
No external data: every experience comes from the environments.
- **Seeds (AD-09):** training seeds 1–5, used for agent initialization and exploration; each run draws its training-episode seeds from 1,000,000 upward. Learning-curve evaluation uses seeds 20,000–20,019 (TRAIN-05). Final evaluation uses seeds 10,000–10,099 (EVAL-01). The three ranges never overlap.
- **Baselines** are "runs" with zero training steps: each is evaluated under the same 5 seeds (its random source) and the same evaluation seeds, so both sides of every comparison have the same shape (BASE-04).
- **Scores:** an episode's score is whatever its environment reports in `info["score"]`: food eaten in Snake, reaching the goal in the corridor, mean steps survived per fish in the tank (TANK-12).
- **Storage (AD-06):** `runs/<experiment>/<agent>-<env>[-<level>]/seed<N>-<YYYYmmdd-HHMMSS>/` holds `config.json` (with a `complete` flag), `episodes.csv`, `curve.csv`, `final_eval.json`, the agent (`agent.pt` or `table.npz`) and `recordings/{best,median,live-*}.npz`. Reports live in `reports/<name>/`: `inputs.json`, `verdicts.json`, `table.md`, and the plot PNGs. Both trees are git-ignored.

## Cross-cutting concerns
- **Reproducibility (QR-04):** AD-05. One seeded `np.random.Generator` per environment and per agent, and torch seeded with one thread in every torch-using agent; no global random state.
- **Speed (QR-01–QR-03):** Snake steps in plain Python (AD-03); the tank moves all fish and casts all rays as array operations (AD-14). The small networks run faster on one CPU thread than on the Apple GPU (AD-04). Budgets are checked by timing tests, marked slow.
- **Errors:** invalid discrete actions, steps after the episode ended, unknown names and corrupt files raise `ValueError`, `RuntimeError` or `FileNotFoundError` with the valid options in the message; continuous actions are clipped, not refused (CORE edge cases). `cli` turns errors into one-line messages and a non-zero exit code.
- **Interruption (TRAIN edge case):** `train` catches Ctrl-C, flushes the logs and leaves `complete: false` in `config.json`.
- **Offline (QR-05):** no network calls anywhere; dependencies are installed once by uv.
- **Testing:** pytest. Environment rules are tested from exact states set through test hooks (AD-11); learning updates are tested against hand-computed values through pure functions (TAB-01, TAB-02, DQN-06, PG-01–PG-03). The corridor is the end-to-end smoke test for every agent.

## Decisions
### AD-01: Python 3.12 managed with uv
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The learner knows Python and PyTorch. The laptop has Python 3.13 and uv installed.
- **Decision:** Python 3.12, pinned in `pyproject.toml`, with the environment and lock file managed by uv.
- **Alternatives:** 3.13 — supported by current PyTorch, but 3.12 has the widest wheel coverage, and nothing here needs 3.13. Plain pip with a venv — works, but there's no lock file, so it's less reproducible.
- **Consequences:** `uv run` is the entry for every command; uv installs 3.12 itself.

### AD-02: Own environment protocol, shaped like Gymnasium, with no Gymnasium dependency
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** CORE-01–CORE-04 need one interface for every environment. The brief wants everything built by hand now, and a comparison with library agents later.
- **Decision:** `core.Env` is a `typing.Protocol` with `reset(seed)` and `step(actions) -> StepResult` (observations, rewards, terminated, truncated, info), the same split Gymnasium uses, plus `render() -> Frame`. The only space object is the project's own `core.ActionSpace`; AD-13 sets the array shapes, the agent dimension and the frame.
- **Alternatives:** Subclass `gymnasium.Env` — library agents work immediately, but it adds spaces, wrappers and checker rules that teach the library rather than the concept. A free-form API — would make the later library comparison a rewrite.
- **Consequences:** The later library-comparison stage needs a thin adapter per environment (one-agent environments map directly; the school needs a per-fish wrapper). The terminated/truncated split is in the protocol from day one, so bootstrapping is right (TAB-02, DQN-06, PG-03).

### AD-03: Snake simulated in plain Python, observations as NumPy vectors
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `snake`
- **Context:** QR-03 requires ≥ 10,000 Snake steps per second. On a ≤ 10×10 grid, the per-step work is a few set lookups.
- **Decision:** Body is a `deque` of cells plus a `set` for collision checks; the 11 features are computed directly, then packed into one `float32` array.
- **Alternatives:** A NumPy grid array per step — the overhead of creating arrays dominates at this size. Vectorized batches of environments — faster, but harder to read and not needed for the budget.
- **Consequences:** The code reads like the rules. Rendering builds a `Frame` only when asked, never in the training loop.

### AD-04: Neural networks in PyTorch on one CPU thread
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `dqn`, `pg`
- **Context:** DQN-09 and PG-08 need a general neural-network toolkit with no RL library. QR-01 gives ≤ 15 minutes per main run on an M4 Pro, with no NVIDIA GPU. The networks are small (11 or 41 inputs, at most 8 outputs).
- **Decision:** PyTorch, with small MLPs and the Adam optimizer, all on the CPU with `torch.set_num_threads(1)`. Replay buffer, target network, rollouts and losses are written by hand. PyTorch is the largest dependency, so only the torch-using agents (`dqn`, `pg`) may import it; `runstore` saves and loads agents through their own `save` and `load`.
- **Alternatives:** Apple GPU (MPS) — the overhead of each GPU launch outweighs the work for batches this small. JAX — less familiar to the learner. A network in NumPy by hand — possible, but backprop by hand is a different lesson.
- **Consequences:** Main runs should take minutes, inside QR-01; timing tests confirm it. An import-linter contract enforces which components may import PyTorch, which keeps the agents a clean seam for a later split.

### AD-05: Reproducibility by explicit seeded random sources
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** QR-04, SNAKE-15 and TANK-14 require identical results from the same seed and configuration.
- **Decision:** Every environment and agent owns an `np.random.Generator` created from its seed. Torch-using agents also seed torch, use one thread and turn on `torch.use_deterministic_algorithms(True)`. No code touches global random state.
- **Alternatives:** Global seeding at program start — brittle, since any extra random call shifts every later result.
- **Consequences:** Results are reproducible on one machine. Across PyTorch versions or machines they may differ slightly, which QR-04 allows.

### AD-06: Plain files per run, never overwritten
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `runstore`
- **Context:** TRAIN-04 requires each run kept separately with its configuration, logs, agent and recordings; QR-05 requires offline use; the brief rules out tracking services.
- **Decision:** One folder per run, named with seed and timestamp (layout under Data), created exclusively so it can't overwrite. JSON for configuration and summaries, CSV for logs, `.npz` for recordings and the tabular table, `.pt` for network weights.
- **Alternatives:** SQLite — overkill for append-only logs, and harder to read by eye. An experiment-tracking service — ruled out by the brief.
- **Consequences:** Every artifact is readable with a text editor or one line of NumPy. Finding runs is a directory search, which is fine for tens of runs.

### AD-07: Matplotlib for both plots and the interactive viewer
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `viewer`, `plots`
- **Context:** VIEW-01–VIEW-07 need an interactive replay with controls, a readout panel, fish selection and animation export. EVAL-03 and ABL-04 need static plots following the `dataviz` skill.
- **Decision:** Matplotlib for both. The viewer is one figure: the frame's shapes drawn as patches (squares, circles, ray lines) coloured by role, a readout panel (bars for action values or probabilities, mean ± spread for continuous actions), buttons and a speed slider (Matplotlib widgets), a fish selector and a ray toggle, and keyboard shortcuts. Export uses Matplotlib's animation writer with Pillow to produce GIF.
- **Alternatives:** Pygame — a smoother game loop, but a second graphics stack and hand-built controls. A terminal viewer — no export, and can't draw a round tank.
- **Consequences:** One plotting dependency. Playback tops out at around 30 frames per second, which matches VIEW-02's limit. It needs a GUI backend (macOS's native one) for the interactive window; export works without one.

### AD-08: Significance tests are run by the null-hypothesis-testing skill, not by code
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `compare`
- **Context:** EVAL-02 and ABL-03 name the `null-hypothesis-testing` skill as the owner of the test, the correction and the decision.
- **Decision:** `compare.write_comparisons` writes `reports/<name>/inputs.json`: one `ComparisonInput` per pair, carrying per-seed mean scores and per-episode scores for both sides. The skill is run on that file and writes `verdicts.json` as `Verdict` records. `compare.results_table` joins the verdicts with the run summaries, and marks a report underpowered when there are fewer than 5 seeds.
- **Alternatives:** A t-test or permutation test hand-written in `compare` — a second, unreviewed version of the skill's procedure.
- **Consequences:** Producing a report takes two steps (write the inputs, run the skill). `results_table` refuses to build until verdicts exist for every input.

### AD-09: Fixed, disjoint seed ranges for training and evaluation
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `evaluate`, `train`
- **Context:** EVAL-01 requires evaluation seeds that are the same for every agent and never used in training. TRAIN-05 needs a fixed set for the learning curve.
- **Decision:** These are constants in `evaluate`: final evaluation uses 10,000–10,099, and the curve uses 20,000–20,019. Training episodes draw seeds from 1,000,000 upward using the run's generator.
- **Alternatives:** Random evaluation seeds per run — the comparisons would no longer be paired.
- **Consequences:** Every agent and baseline is scored on identical games, so paired tests are possible. Changing the ranges invalidates old comparisons.

### AD-10: Pipeline entries are the public workflows; every step hands over a contract type
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** Pipeline design (PL-01–PL-09) found that the first contract mixed entry-like functions (`train_run`, `train_seeds`, `play_live`) in with steps. It left the protocols and `RunWriter` without type sections, and returned bare paths, strings or None from file-writing and interactive steps, so the step hand-offs had no types to freeze.
- **Decision:** Each workflow's public function is its `run_<workflow>` entry in the owning component's `pipeline.py` (`train.run_train`, `train.run_preset`, `compare.run_compare`, `compare.run_report`, `plots.run_plot`, `viewer.run_view`, `viewer.run_play`, `viewer.run_export`, `cli.run_inspect_table`). `cli` only parses arguments into them. Protocols and `RunWriter` are type sections. Every written file is returned as a `core.Artifact`; the report as a `compare.ResultsTable`; the viewer's exit as a `viewer.ViewResult`. `core.Env` carries `obs_labels`, so feature labels never need an environment import. Running one configuration over seeds (TRAIN-02) goes through preset sets.
- **Alternatives:** Keep returning paths and None — those steps then have nothing to freeze or test against. Keep `train_seeds` beside the presets — two ways to run a seed sweep.
- **Consequences:** Nine extra small contract sections. `gridlab train` runs one seed; sweeps are presets. `ablation_curves` returns `Artifact | None` for sets without variants.

### AD-11: Test hooks are part of the contract
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** Known-answer cases need exact environment states and checkable learning arithmetic. Through `reset` alone, food and fish land wherever the seed puts them, which can't be known before the code exists.
- **Decision:** Every environment with seeded placement has a `set_state` that puts it in a given state (`snake.SnakeEnv.set_state`, `tank.TankEnv.set_state`). Every learning update's arithmetic is a pure function the agent uses for every update and tests check by hand (`dqn.td_targets`, `pg.discounted_returns`, `pg.gae`, `pg.clipped_objective`).
- **Alternatives:** Search seeds for wanted positions — brittle, and it breaks when placement changes. Test private internals — couples tests to code layout.
- **Consequences:** `set_state` is also handy for teaching (set up a trap, then watch the agent). Each formula lives in one place that's tested by hand.

### AD-12: Stay single-package through S1 and S2
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The package passes the Grow triggers: more than 3 pipelines, a contract over the 200-line ceiling, and PyTorch as a heavy dependency. It's a one-person learning project with one install and no separate deployments.
- **Decision:** Keep `gridlab` as one package through S2. The seams stay named for a later split: environments (`core`, `snake`, `corridor`, `tank`, `baselines`), agents (`tabular`, `dqn`, `pg`) and the lab (the rest). Import-linter contracts enforce the seams; only the torch-using agents import PyTorch (AD-04).
- **Alternatives:** Split now into three packages — workspace config, per-package bars and multi-package pipelines before any code exists, for one learner.
- **Consequences:** Build agents read the contract through `dt context` packets, which stay under 2,000 lines. Revisit when a third environment's stage is cut.

### AD-13: The core is array-based, one row per agent
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The fish tank (TANK, PG) brings several agents, continuous actions and a round world. The first core assumed one agent, an integer action, a scalar reward and a grid frame (CORE-01–CORE-05 as first written). M1 hadn't been built, so changing the core cost a contract revision, not code.
- **Decision:** `reset` returns observations of shape (agents × obs_size); `step` takes one action per agent and returns per-agent arrays of rewards, terminated and truncated flags. `core.ActionSpace` is either discrete (a count and names) or continuous (bounds and names). Agents act on all rows at once and return a `core.Readout` (action values, state value, probabilities, or means and spreads) for the viewer. A `core.Frame` is a tuple of `core.Shape`s (squares, circles, lines) in the environment's own coordinates. Snake and the corridor are one row with a discrete space and square shapes (CORE-08).
- **Alternatives:** Keep the single-agent core and wrap the tank behind an adapter — two training loops and two viewers, which defeats Goal 4. A dictionary per agent — readable, but slower and harder to batch for PPO.
- **Consequences:** Tabular and DQN read row 0 and refuse continuous spaces. Golden cases written for Snake keep their expected values and read agent 0. The viewer draws shapes, not cells. The M1 interface task freezes this core instead of the first one.

### AD-14: Tank simulated as NumPy arrays with analytic ray casting
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `tank`
- **Context:** QR-03 requires ≥ 2,000 tank steps per second with 5 fish, each casting 8 rays against the wall, the ball and 4 other fish (TANK-09).
- **Decision:** Fish positions, headings and alive flags are arrays; one step moves every fish at once, clamps them to the wall (TANK-05) and casts all 40 rays together. A ray's hit is solved in closed form: ray-circle intersection against the tank wall (from inside), the ball and each other fish, taking the nearest hit within 0.5.
- **Alternatives:** Plain Python per fish and ray — around 200 intersections a step in loops would miss the budget. A physics library — a dependency for bounces this simple.
- **Consequences:** The geometry lives in a few pure functions that are easy to test with hand-made states (AD-11). Ray results are what the frame draws when rays are shown.

### AD-15: Hand-built REINFORCE and PPO, sharing one policy across a school
**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `pg`
- **Context:** PG-01–PG-08 require REINFORCE, then PPO with clipping, GAE, categorical and Gaussian policies, switchable pieces, and one shared policy for a school, all within QR-01's 15 minutes on one CPU thread.
- **Decision:** Separate actor and critic MLPs (two hidden layers of 64, tanh). Discrete actions use a categorical head; continuous ones a Gaussian mean head with a learned, state-independent log-spread. The agent collects a rollout of 2,048 agent-steps (every fish's step counts, so a school fills it faster), then runs 10 epochs of minibatches of 64 with Adam at 3e-4. The defaults are γ = 0.99, λ = 0.95, clip 0.2, entropy weight 0.01 and value-loss weight 0.5. The switches (clipping, value baseline, advantage normalization) are config flags. REINFORCE reuses the actor with no critic, and updates from whole episodes. The pure functions of AD-11 compute returns, advantages and the objective.
- **Alternatives:** One shared actor-critic body — fewer parameters, but the value and policy losses interfere, which is harder to explain. Recurrent policies for partial observability — a different lesson; the rays' closing speed gives enough motion cue.
- **Consequences:** A school is just more rows in the same batch. Sampled continuous actions may fall outside [−1, 1]: the environment clips them, while the agent learns from the sampled value (PG edge case).

## Risks and open questions
- **The greedy baseline may be hard to beat.** It sees exactly what the agent sees (danger and food direction), and with 11 features neither can see the shape of its own body, so DQN-10 may fail against greedy. Mitigations: tune the discount and training length first. If it still fails, that's a finding, which may lead to a spec change (for example, a richer observation).
- **The flee fish may be hard to beat, and PPO may need tuning beyond 15 minutes.** The fish is slower than the ball, so the flee fish dies when cornered, and that's the margin PPO must find. Mitigations: T1 and T2 first; tune rollout length and entropy on T2 before the school.
- **5 seeds is little statistical power.** A real but small edge may not reach significance. The skill reports what it can; more seeds fit the time budget if needed.
- **The interactive Matplotlib backend on macOS** can lag with keyboard handling. Fallback: drive everything from the buttons.
- **The contract is about 500 lines, over the 200-line ceiling for one package (lint `grow-size`).** It stays single-package through S2 (AD-12). Split if build agents struggle with the contract's size.
- **The M1 plan predates AD-13.** Its interface task would freeze the first core; `build-planning` must replan M1 before `/build` runs.

**The new core** (what M1-T01 will freeze, AD-13)
- `Env.reset` and `Env.step` work on arrays with **one row per agent**. Rewards, `terminated` and `truncated` are per agent. `info["score"]` is now a float.
- **`core.ActionSpace`** is either discrete (a count plus names) or continuous (bounds plus names).
- **`core.Frame`** is a tuple of **`core.Shape`**s: squares, circles and lines, each with a role and an optional agent index. Snake draws unit squares, the tank draws circles, and rays are lines.
- **`Agent.readout()`** replaces `action_values()`, and returns a **`core.Readout`** (action values, state value, probabilities, or mean and spread).
- `LearningAgent.epsilon` becomes **`exploration`**: epsilon for value agents, entropy for policy agents.
- Tabular and DQN read row 0 and refuse continuous spaces.
