# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Changing a step table

Revise, and Sync when the doc changes, edit an existing table this way:

- Keep step names where the function survives; a split step gets new rows with new function names. Keep the pipeline's ID: a rebuilt package keeps its PL IDs where it can, so its golden cases still apply.
- If the entry sketch is gone (the spine was built), don't recreate it. The step table is the contract the code must match; the code change becomes a task.
- Keep `Used by:` lines true: add the PL ID to a symbol a new step calls, and remove it from one no step of that pipeline calls any more.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. One module per step owner (`profile.fit` → `profile/fit.py`; an owner given only as `profile` gets one module per related group of steps), never named like a generated file (`api.schema` beside a generated `api/schema.ts`: call it `api.schema_check`). A step whose module needs private helpers owns a folder instead (`core.train` → `core/train/`), holding them; no other step's code goes inside it. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. In a single package each component gets a subfolder whose `__init__.py` exports its contract only, so a later Grow is a folder move. Modules on no step: only `__init__.py`, the entry modules, `__main__.py` for a `python -m` trigger (dispatching each trigger to its entry), and `types.py`. Test folders sit at the repo root in every layout, multi-package included: `tests/intent/<pkg>/`, `tests/unit/<pkg>/`, never under the package's folder. Plan against `build-setup`'s size bar (500 lines per module, 60 per function, or `CONSTRAINTS.md`'s values): split a module expected to pass it now.

## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).

# Quant Research Platform — Architecture

**Status:** Approved · **Shape:** Multi-package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
`qdata` downloads the Sharadar tables, cleans and validates them, cross-checks them against Yahoo Finance and stores them as an as-of (bitemporal) Parquet store. Every other Python package reads that store only through `qdata`'s loader. `research` holds the stage S2 and S3 methods and the shared testing harness, which registers every claim, runs it walk-forward and writes every run (win or loss) to the run store. `learn` holds the torch-based stage S4 work. It installs on its own on a rented graphics card and on the laptop, and records through the same harness. `server` is a local FastAPI process that serves data and records over HTTP, streams run progress over a WebSocket and starts long runs as subprocesses. `web` is the TypeScript + React app in the browser.

```mermaid
flowchart LR
  web -- HTTP / WebSocket --> server
  server --> research --> qdata
  learn --> research
  learn --> qdata
  server -. starts as subprocess .-> learn
  qdata -- Sharadar API, yahooquery --> ext[(vendors)]
```

## Dependency rules
- `qdata` imports nothing internal. It is the only package that talks to Sharadar or Yahoo, and the only one that writes the data store.
- `research` may import `qdata`. It is the only writer of the run store (`research.RunStore`), paper books included.
- `learn` may import `research` and `qdata`. Nothing imports `learn`.
- `server` may import `research` and `qdata`, never `learn`: it starts `learn` jobs as subprocesses by module name, so the app never loads torch.
- `web` imports no Python. It reaches `server` only through the HTTP and WebSocket contract in [server's contract](packages/server/contract.md).
- Enforced by `import-linter` contracts in CI and the pre-commit hook. `learn`'s torch extras are declared only in its own `pyproject.toml` (AD-01).

## Cross-package contracts
- `qdata.Loader` (as-of prices, total returns, actions, universe) and `qdata.open_loader`: provided by `qdata`, used by `research`, `learn`, `server`. [Contract](packages/qdata/contract.md)
- `qdata.run_build`, `qdata.accept_build`, `qdata.ProgressEvent`: provided by `qdata`, used by `server`'s job runner. [Contract](packages/qdata/contract.md)
- `research.register`, `research.RunHandle`, `research.decide`, `research.RunStore`: provided by `research`, used by `learn` and `server`. [Contract](packages/research/contract.md)

**Outline:** Download, clean, validate and store the as-of daily universe, cross-check it against Yahoo Finance, run the exploratory analysis, and browse it in the app, with live progress for long runs.
**Skills:** data-analysis, dataviz, frontend-design
## S2: Return structure & classical portfolios
**Outline:** Remove the market factors, denoise and compare covariance estimators, and rank minimum-variance, risk parity and HRP on out-of-sample variance after costs; this builds the shared out-of-sample testing harness.
**Skills:** data-analysis, dataviz
## S3: Features & ML
**Outline:** Test candidate features for information gain over market-removed returns, each with a null-hypothesis test, a correction for how many features were tried, and a recorded verdict.
**Skills:** null-hypothesis-testing, data-analysis
## S4: Forecasting & trading agents
**Outline:** Compare neural return and volatility forecasts against simple baselines, then run forecast-driven portfolios and PPO agents in a backtest, held to the bar "beat the S2 portfolios after costs, or document the loss," then simulated paper trading.
**Skills:** null-hypothesis-testing, data-analysis
# learn — Architecture
**Package:** learn · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)
## Overview
`learn` is the only package with torch. Training runs on a rented graphics card from a frozen Parquet extract and returns a bundle (AD-17). Everything else runs on the laptop from that bundle: forecasts, scoring against baselines, forecast-driven portfolios, agent evaluation and daily paper trading. Every claim goes through `research.register` and `research.decide`, and every portfolio rule through `research.hold_period`, so S4 is judged exactly like S2.
## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `budget` | `TrainSpec`, expected hours and cost, the $10 refusal, wall-clock cap | QR-05 | — |
| `extract` | Freeze the accepted build's universe panel, features and targets to a Parquet extract for the rented machine | FCST-07 | `qdata`, `research` |
| `targets` | Forward return and realised volatility per horizon in trading days, through delisting (adapts RF-03) | FCST-02, FCST-06 | `qdata` |
| `windows` | Lookback windows with gaps masked, unknown categories mapped to a reserved index, purged splits from the harness schedule (adapts RF-02) | FCST-01, FCST-03 | `targets` |
| `forecast` | LSTM and TFT-style models, training loop, bundle save and load, forecasts, baselines, scoring with the `null-hypothesis-testing` skill through `research.decide` | FCST-01–FCST-05, FCST-07 | `windows`, `budget`, `research` |
| `fport` | Forecast-driven portfolios: forecasts plus the best covariance, held and compared with the S2 benchmark on Sharpe after costs | FPORT-01–FPORT-03 | `forecast`, `research` |
| `env` | Gymnasium backtest: guarded day-by-day replay, capped weights, differential Sharpe reward | AGENT-01, AGENT-02 | `research` |
| `agents` | Stable-Baselines3 PPO training over 5 or more seeds, divergence detection, evaluation against the benchmark | AGENT-03–AGENT-06 | `env`, `budget`, `research` |
| `paper` | Frozen strategy snapshots, daily orders and next-close fills, gap days, books in the run store; no network client | PAPER-01, PAPER-03, PAPER-04 | `forecast`, `agents`, `research`, `qdata` |
## Interfaces
See [contract.md](contract.md).
## Data
- **Extracts:** `data/extracts/<build_id>-<sha>/` holds the universe panel, features and targets in Parquet. This is the only data copied to a rented machine.
- **Bundles:** `data/models/<bundle_id>/` holds `weights.pt` (or `policy.zip`), `settings.json`, `seeds.json`, `build_id`, `git_rev`, `curve.parquet` and `sha256`.
- **Splits:** train, validation and test in time order, with purge ≥ 21 trading days (the longest horizon). The test period is the claim's registered final test period.
## Cross-cutting concerns
- **QR-05:** each `learn train-*` prints `expected_hours × rate` before starting and refuses if the expected cost is over $10. Training stops at `10 / rate` hours.
- **Divergence:** NaN loss, collapsing reward or weights outside the limits stop the run, which is recorded through `RunHandle.fail` with the training curve.
- **Determinism:** seeds for torch, numpy and the environment are set and recorded. cuDNN deterministic mode is on for evaluation.
- **PAPER-03:** an import-linter contract forbids `httpx`, `requests`, `urllib` and `socket` in `learn.paper`.
## Project layout
```
packages/learn/src/learn/<component>/   → one folder per component; __init__ exports its contract
packages/learn/tests/                   → folders only; files are planned in pipelines.md
```
# qdata — Architecture
**Package:** qdata · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)
## Overview
`qdata` turns the Sharadar subscription into a local as-of store. A build downloads in resumable batches, cleans, computes the point-in-time universe, cross-checks against Yahoo Finance, writes a validation report and commits a manifest. Every reader goes through `qdata.open_loader`, which serves only passed or accepted builds and filters every row by its as-of date (AD-06). The exploratory analysis runs on the loader's output and is saved with its build.
## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `source` | Primary (`PrimarySource`, Sharadar, AD-03) and second (`SecondSource`, yahooquery, AD-04) adapters, paging, retry, credential lookup and URL redaction | DATA-01, DATA-05, QR-07 | — |
| `clean` | Deduplicate (stock, date), flag non-positive prices and missing trading days inside a listed life, map tickers to `permaticker` | BUILD-03, DATA-03 | `calendar` |
| `calendar` | XNYS trading days, previous trading day, gap counts | LOAD-05 | — |
| `store` | Bitemporal Parquet tables, staged batches, checkpoints, manifests, as-of DuckDB reads | BUILD-02, BUILD-05, DATA-04, QR-02 | — |
| `universe` | Daily top-1,000 by 63-day median dollar volume from the day before, common stocks only, tie-break on `permaticker`, S&P 500 fallback | UNIV-01–UNIV-05, DATA-02, DATA-06 | `store`, `calendar` |
| `xcheck` | Total-return and action comparison against the second source, disagreement reasons, coverage share | XCHK-01–XCHK-04 | `source`, `store` |
| `build` | Full and incremental builds: batches, cleaning, universe, cross-check, validation report, manifest, acceptance, progress events | BUILD-01, BUILD-02, BUILD-04, BUILD-05, QR-03 | `source`, `clean`, `store`, `universe`, `xcheck` |
| `loader` | Prices, total returns, actions, universe and universe returns, as of a date, from the current accepted build | LOAD-01–LOAD-06 | `store`, `calendar` |
| `eda` | The exploratory analysis, run with the `data-analysis` skill on loader output; saves figures and tables per build | EDA-01, EDA-02 | `loader` |
## Interfaces
See [contract.md](contract.md).
## Data
- **Sources:** Sharadar stocks, actions and tickers (AD-03), and sp500 if the fallback applies (AD-05). Yahoo Finance via yahooquery for the cross-check (AD-04).
- **Layout:** `data/store/{prices,actions,tickers,universe,second_source}/year=YYYY/*.parquet`, each row with `known_from`, `known_to` and `build_id`. `data/builds/<build_id>/` holds `manifest.json`, `report.json`, `progress.jsonl`, `batches/` checkpoints and `eda/`.
- **Build ids** are `YYYYMMDD-HHMMSS-<full|update>`. The current dataset is the newest build with manifest status `passed` or `accepted`.
- **Universe:** one row per (date, permaticker) in the universe, with rank and median dollar volume. The count for dates with fewer than 1,000 eligible stocks is written to the report.
## Cross-cutting concerns
- **QR-02:** loading 25 years of universe returns reads only the universe and prices partitions for those years and pivots to a float32 dates × stocks frame, about 6,300 × 3,000 columns at most (well under 8 GB). A benchmark test asserts ≤ 30 s.
- **QR-03:** an update requests only `lastupdated` after the previous build and new days. The cross-check fetches only new days per covered stock, from a cached history.
- **QR-07:** `source` reads the key from `keyring` or `SHARADAR_API_KEY`. A logging filter replaces `api_key=…` in every message.
- **Errors:** `SourceAuthError`, `SourceQuotaError` (the build stops, nothing is committed as current, and it can resume), `BuildLocked`, `NoAcceptedBuild`.
## Project layout
```
packages/qdata/src/qdata/<component>/   → one folder per component; __init__ exports its contract
packages/qdata/tests/                   → folders only; files are planned in pipelines.md
```
# research — Architecture
**Package:** research · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)
## Overview
`research` holds the laptop-sized research methods and the harness every stage claims through. Stage S2 removes market factors per window, denoises correlation, estimates three covariances, builds three portfolios plus equal weight, and holds them walk-forward with costs. The verdicts are saved, and the best becomes the stage benchmark. Stage S3 builds features as of each close and tests each feature's information gain with LightGBM. Every claim is registered, run on guarded data views, decided by the `null-hypothesis-testing` skill and written to the run store (AD-10).
## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `harness` | Registrations, locking, walk-forward and purged splits, guarded loader views, final-period lock, cost and turnover accounting, verdicts with the `null-hypothesis-testing` skill | HARN-01–HARN-06, HARN-08 | `records`, `qdata` |
| `records` | The run store: run folders, period results, verdicts, conclusions, abandoned runs, paper books; DuckDB queries across runs | HARN-07 | — |
| `factors` | Per-window PCA market-factor removal, k rule, correlation-drop check (adapts RF-01) | FACT-01–FACT-04 | `qdata` |
| `denoise` | Marchenko–Pastur noise fit, eigenvalue clipping, unit-diagonal rescale, per-window record | DENO-01–DENO-04 | — |
| `covariance` | Sample, Ledoit–Wolf constant-correlation and denoised covariances per window | COV-01, COV-04 | `denoise` |
| `portfolios` | Minimum variance, risk parity, HRP, equal weight under the limits; hold-period simulation shared with `learn` | PORT-01–PORT-05 | — |
| `compare` | The S2 comparison: estimator × method walk-forward runs, analysis with the `data-analysis` skill, tests, benchmark selection | COV-02, COV-03, PORT-06 | `harness`, `factors`, `covariance`, `portfolios` |
| `features` | Feature registry (definition, inputs, lookback), per-date computation as of close, cross-sectional standardisation | FEAT-01–FEAT-04 | `factors`, `qdata` |
| `ftest` | Residual-return targets, LightGBM with and without each feature, gains, data characterisation with the `data-analysis` skill, survivors | FTEST-01–FTEST-05 | `harness`, `features`, `factors` |
## Interfaces
See [contract.md](contract.md).
## Data
- **Run store:** `data/runs/<run_id>/` holds `registration.json` (with `sha256`), `periods.parquet`, `verdict.json`, `conclusion.md`, `status.json` and the artefacts (weights, the denoising record per window). `data/runs/index.parquet` is rebuilt on write for listing.
- **Benchmark and survivors:** `data/runs/benchmarks/S2.json` points to the winning run, method and estimator. `data/runs/survivors/S3.json` lists the surviving feature ids (empty on a negative result).
- **Paper books:** `data/paper/<book_id>/` holds `snapshot.json` and `days.parquet`, written only through `RunStore.append_paper_day`.
- **Defaults:** 252-day estimation, 21-day hold, 10 bp per trade, 5% level after correction (spec Assumptions), with Holm–Bonferroni as the default correction, registered per claim.
## Cross-cutting concerns
- **Reproducibility (HARN-08):** a run records the build id, git revision, every seed and the package versions. Reruns compare periods bit for bit.
- **Point in time:** strategies get `GuardedLoader`, never a raw `qdata.Loader`.
- **Errors:** `FinalPeriodLocked`, `RegistrationLocked`, `Infeasible` (optimiser, handled by keeping previous weights), `ValueError` for k ≥ N.
## Project layout
```
packages/research/src/research/<component>/   → one folder per component; __init__ exports its contract
packages/research/tests/                      → folders only; files are planned in pipelines.md
```
# server — Architecture
**Package:** server · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)
## Overview
A FastAPI app on `127.0.0.1` (AD-08). Read endpoints wrap `qdata`'s loader and reports and `research`'s run store, and return pydantic models whose OpenAPI drives `web`'s types (AD-09). A job runner starts builds, acceptance checks and paper days as subprocesses. Each one writes progress lines that a WebSocket streams to the browser.
## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `app` | FastAPI factory, `127.0.0.1` bind, Host check, error mapping, static serving of the built `web` bundle | QR-06 | `api`, `jobs` |
| `api` | Data, report, analysis, results and paper endpoints; full-history responses as parallel arrays | PAPER-02, RESX-04 | `qdata`, `research` |
| `jobs` | Subprocess runner, one-build lock, progress tailing, WebSocket push every second, resume | APP-04 | `qdata` |
## Interfaces
See [contract.md](contract.md).
## Cross-cutting concerns
- **QR-06:** uvicorn `--host 127.0.0.1`, plus middleware that returns 403 unless `Host` is `localhost:<port>` or `127.0.0.1:<port>`. A test opens the port on the LAN address and expects a refused connection.
- **APP-06:** `stock_history` reads one `permaticker` through the loader (one DuckDB filter) and returns about 6,300 points as arrays. The target is under 300 ms server-side.
- **Errors:** `qdata.NoAcceptedBuild` → 409 with `code: "no_accepted_build"` (the app offers a build); an unknown id → 404.
## Project layout
```

# web — Architecture
**Package:** web · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)
## Overview
A Vite + React 18 + TypeScript single-page app served by `server` on `127.0.0.1`. It fetches through TanStack Query using types generated from the server's OpenAPI, charts with Apache ECharts, and subscribes to `server.run_progress` for live runs (AD-09). Screens and charts are designed with the `frontend-design` and `dataviz` skills, in light and dark themes (APP-05).
## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `api` | Generated types, fetch client, query hooks, WebSocket hook with reconnect | APP-04 | server (HTTP/WS) |
| `theme` | Design tokens and the ECharts light and dark themes, from the `dataviz` and `frontend-design` skills | APP-05 | — |
| `charts` | Price and return chart with action marks and a delisting end, side-by-side source chart, run series chart on shared axes | APP-01, APP-03, APP-06, RESX-03 | `theme` |
| `data-screens` | Stock search and history, universe by date, builds and validation reports, analysis viewer, the "no accepted build" state | APP-01–APP-03, EDA-03 | `api`, `charts` |
| `runs-screen` | Start build, update or analysis, watch live progress, failing step and resume | APP-04 | `api` |
| `results-screens` | Run list with stage and verdict filters, run detail against its baseline, compare 2–6 runs, one generic view for every stage | RESX-01–RESX-04 | `api`, `charts` |
| `paper-screen` | Paper books against the benchmark: positions, trades, daily return, turnover, gaps | PAPER-02 | `api`, `charts` |
## Interfaces
See [contract.md](contract.md).
## Cross-cutting concerns
- **APP-06:** a chart of 6,300 points on the ECharts canvas renderer with `sampling: "lttb"` draws in under 200 ms. A Playwright check opens one stock and asserts the chart is drawn within 1 s.
- **Type safety:** `pnpm gen:api` regenerates types from the server's exported OpenAPI. CI fails if they're stale.
## Project layout
```
packages/web/src/<component>/   → one folder per component
packages/web/tests/             → folders only; files are planned in pipelines.md
