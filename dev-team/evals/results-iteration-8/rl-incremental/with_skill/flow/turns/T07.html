# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency direction worth enforcing with tooling. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

## Grow triggers

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, torchvision).
- A one-way dependency is worth enforcing (data must never import models, to prevent leakage).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.

# Contracts

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). ## When it touches older decisions

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.

# RL Lab — Architecture

**Status:** Draft · **Shape:** Single package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
One Python package, `rllab`. Environments (`snake`, `corridor`) and agents (`bots`, `tabular`, `net`) implement two small protocols in `core`. The shared pieces (`train`, `evaluate`, `replay`, `plots`) see only those protocols. `lab` is the one place that knows every concrete class: it holds the ladder (L1–L4), builds an environment and agent from saved settings, and drives a rung through train → evaluate → plot → note skeleton. ## Decisions
### AD-01: Python 3.13 with uv
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The laptop has Python 3.13 and uv already. PyTorch ships CPU wheels for 3.13 on macOS.
- **Decision:** Python 3.13. uv manages the virtual environment and the lock file.
- **Alternatives:** 3.12 — no library here needs it, and it would mean a second interpreter. Conda — heavier, and nothing needs it.
- **Consequences:** `requires-python = ">=3.13,<3.14"`. One `uv sync` sets up the project.

### AD-02: PyTorch only for the network's arithmetic and gradients
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** NET-08 allows a general numerical library for the network's arithmetic and gradients only. The learner is new to PyTorch and wants to learn it (brief).
- **Decision:** `net` builds its network from `torch.nn.Linear` layers and uses `torch.optim.Adam`. Memory, sampling, targets, target copy, exploration and the update rule are written in the project. No PyTorch import outside `net`, and no reinforcement learning library anywhere.
- **Alternatives:** NumPy with a hand-written backward pass — teaches gradients, but adds a second hard problem to the rung, against Goal 2. JAX — less familiar CPU tooling, and the brief names PyTorch.
- **Consequences:** Only `net` carries the PyTorch dependency, and import-linter enforces that (AD-05). The table rung (L1, L2) runs before any PyTorch code exists.

### AD-03: NumPy for everything outside the network
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** TAB-05 requires the table learner to be built from basic array operations. Views, evaluation scores and frames are small arrays.
- **Decision:** Views, frames, scores and the table's values are NumPy arrays. The table is a `dict[bytes, np.ndarray]` with three values per situation.
- **Alternatives:** Pure Python lists — slower and clumsier for views. PyTorch tensors everywhere — drags PyTorch into the table rung.
- **Consequences:** `net` converts views to tensors at its own boundary.

### AD-04: One fully connected network for both views
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** net
- **Context:** NET-07 requires the same learner for both views, with only the input size changing. QR-02 caps a run at 60 minutes on a laptop CPU. The raw grid is at most 3×6×6 + 4 = 112 values.
- **Decision:** Input → 128 → 128 → 3 with ReLU, the input size taken from the view's length. Each view is flattened.
- **Alternatives:** A small convolutional network for the grid — a better fit for images, but it breaks NET-07 and adds a new concept to L4. A single hidden layer — may be too weak for L4's bar.
- **Consequences:** L4 tests whether a plain network can read a 6×6 board, which is the brief's bet. If L4 misses its bar, a convolutional network is the first change to try, through a new decision.

### AD-05: Shared pieces depend only on `core`
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** CORE-01 says the shared pieces never use Snake directly. Goal 5 wants them reused, and the brief rules out a framework designed ahead of time.
- **Decision:** Every shared component (training, evaluation, replay, plots) imports only `core`. Every environment and agent implements `core.Env` or `core.Agent`. Only `lab` imports concrete environments and agents. import-linter checks these rules in the check script, along with "only `net` imports torch".
- **Alternatives:** A registry inside `train` — makes `train` import Snake. Gymnasium's interface — a reasonable standard, but it brings the library's conventions in before they're needed. The `Env` protocol stays close to it, so a later adapter is small.
- **Consequences:** A second environment needs a new `Env` class and a line in `lab`, nothing else. The protocols must stay tiny, or they become the framework.

### AD-06: Plain files in one folder per run
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** EVAL-01, EVAL-02 and EVAL-10 need settings, logs and agents saved and reloaded. There's one user and no concurrency beyond the seed processes, each of which writes its own folder.
- **Decision:** The layout is as listed under Data: JSON for settings and evaluation, CSV for the training log, NPZ for the table, and a PyTorch weights file for the network.
- **Alternatives:** SQLite — queries aren't needed. An experiment tracker — an extra service for one person.
- **Consequences:** Runs are easy to inspect by hand and to delete. Comparing rungs means reading several `eval.json` files, which `lab` does for the closing note.

### AD-07: A replay holds the seed, moves, frames and values
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** replay
- **Context:** WATCH-04 needs per-step move values, and WATCH-07 needs a game rebuilt from its seed and moves to match the saved one. Games are at most a few thousand steps on ≤ 10×10 boards.
- **Decision:** One JSON file per replay containing the environment settings, seed, moves, a frame per step (a small integer grid), rewards, the ending, and either per-step values or `null` for bots.
- **Alternatives:** Seed and moves only — smaller, but there's nothing to check WATCH-07 against, and the viewer would have to rebuild the environment. Frames as images — large, and no use to tests.
- **Consequences:** Replays are a few hundred kilobytes at most. `replay.rebuild` replays the moves on a fresh environment and compares the frames.

### AD-08: matplotlib for curves and the viewer
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** EVAL-03 needs learning-curve figures. WATCH-02, WATCH-03 and WATCH-06 need a viewer with step, back, play and speed controls on the laptop screen. Nothing needs a game-quality window (spec Out of scope: a polished game).
- **Decision:** matplotlib for both. The viewer is a figure with keyboard controls (← → step, space play/pause, + − speed from 1 to 20 steps per second), with the board drawn from frames and a bar chart of the three move values.
- **Alternatives:** pygame — smoother playback, but a second graphics library. A terminal viewer — no value bars worth reading.
- **Consequences:** One plotting library to learn. matplotlib timers are fine at ≤ 20 frames per second on a 10×10 board.

### AD-09: Reproducibility through explicit generators
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** QR-03 needs an identical learning curve for the same settings and seed. GAME-09 needs an identical game for the same seed and moves.
- **Decision:** Each run creates one `np.random.Generator` from its seed, and splits it into child generators for the environment, exploration and memory sampling. `net` also calls `torch.manual_seed`, `torch.use_deterministic_algorithms(True)` and `torch.set_num_threads(1)`. Nothing uses global random state.
- **Alternatives:** Global seeding — fragile, since any extra random draw shifts every later one.
- **Consequences:** A single thread costs a little network speed, which is acceptable at this network size (AD-04). Speed tests run with the same settings.

### AD-10: Bar tests run through the `null-hypothesis-testing` skill
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** evaluate
- **Context:** EVAL-05–EVAL-07 name the `null-hypothesis-testing` skill as the judge. It defines the test statistic, null distribution and correction. The project must not write its own version of that procedure.
- **Decision:** `evaluate.compare` takes two score arrays, the bar (beats or matches, with the 10% margin) and α = 0.05, and returns a `BarResult`. The test inside it is designed and verified with the `null-hypothesis-testing` skill when `evaluate` is built. Each rung's bar results are saved in `eval.json` along with the test used.
- **Alternatives:** Choose a t-test by hand — that is exactly the procedure the skill owns.
- **Consequences:** The skill's design (for example a permutation or bootstrap test, and whether L1–L4 need a multiple-testing correction) is recorded in `evaluate`'s code and in each `eval.json`.

## Risks and open questions
- **L4 may miss "beats scripted".** A plain network reading a 6×6 board within an hour is the brief's bet. Mitigation: AD-04 names the first change to try. A miss is still a finding for the L4 note.
- **Five seeds × 60 minutes per network rung.** Mitigation: seeds run side by side as processes. On a laptop with 4 or more cores, a rung's wall time stays near one hour.
- **The protocols could grow into a framework.** Mitigation: `core` changes only when a second environment needs it (AD-05).

**Shape:** one package, `rllab`, with 11 components:
- **Shared base:** `core` defines what every environment and every agent must provide.
- **Environments:** `snake`, plus `corridor`, a tiny test environment that proves the shared pieces aren't tied to Snake.
- **Agents:** `bots`, `tabular`, `net`.
- **Shared pieces:** `train`, `evaluate`, `replay`, `plots`. These only know about `core`, never Snake.

**Decisions to check:**
- **AD-02:** PyTorch is used *only* for the network's arithmetic and gradients. The memory, targets, target copy and exploration are your own code, and a check fails if PyTorch is imported outside `net`.
- **AD-04:** the same small network (two hidden layers of 128) is used for both views. The spec requires the same learner for both, so this rules out a convolutional network for the grid. If L4 misses its bar, a convolutional network is the first thing to try.
- **AD-05:** the rule that shared pieces only see `core` is checked automatically with import-linter. That's how "reused, not rebuilt" is enforced.
- **AD-08:** matplotlib draws both the learning curves and the replay viewer, with keyboard controls (step with the arrows, space to play, +/− for speed).
- **AD-09:** to get identical reruns, each run uses one random-number source created from its seed, and PyTorch is set to deterministic, single-thread mode.
- **AD-10:** `evaluate.compare` is where the `null-hypothesis-testing` skill comes in. The skill chooses and checks the actual test while that part is being built.

**Size warning:** the contract is 219 lines, over the 200-line guideline. I think splitting into several packages isn't worth it for one user and one install, and I've recorded that under Risks.

**Assumptions:**
- Python 3.13 via uv (what's on your laptop), PyTorch ≥ 2.6 (CPU-only build), NumPy ≥ 2.1, matplotlib ≥ 3.9.
- Each run is a plain folder of files: `runs/<rung>/seed-<n>/`. Replays are JSON files that store the seed, moves, frames and move values.
- The scripted bot reads the game state directly, not the 11-fact view.
- The table learner looks situations up by the view's raw bytes.
- The network's default settings (memory of 50,000 steps, refresh every 500 updates, learn every 4 moves, batch of 64) are starting points. You'll tune them during the build.
- Notes live in `notes/`. `lab` creates each one with the curve and summary already in it; you write the explanation.

**Open questions:** none. The risks are listed in the doc:
- L4 might not beat the scripted bot.
- A network rung takes 5 seeds × up to an hour, but the seeds run side by side as separate processes.
- The shared base could grow into a framework.

The approved spec (`docs/spec.md`) isn't committed yet. I can commit it along with the architecture once you approve.
