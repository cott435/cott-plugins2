**1. Critical finding M1-R12** (mdata review after M1-T20), in `packages/mdata/src/mdata/calendar.py:25` (`align_calendar`):
- **Bug:** the calendar starts on the latest first date of any ticker. It should start on the first date every ticker has a close (DATA-03).
- **Effect:** if a ticker that began earlier has no close on that start date, the fill step crashes with an `IndexError`. Example: ticker A trades on 01-01 and 01-03, ticker B on 01-02 and 01-03. The calendar should be 01-03, but the code crashes instead.
- **Reviewer's fix:** start at the earliest date all tickers share, return empty prices when they share none, and add a unit test with this input.

**2. M1-T21 raised a `CONTRACT-CHANGE` on `mdata.load_prices`:**
- **Mismatch:** the real `validate_rows` doesn't filter by `tickers`. It only raises `KeyError` for a requested ticker that's missing, then returns every ticker's rows. The stand-in versions of `mdata.load_prices` and `risk.vol_series` (frozen at M1-T01) do keep only the requested tickers.
- **Effect:** M1-T21's test calls `risk_report(..., tickers=['Y'])` and gets both X and Y back.
- **Cause:** `contract.md` never says that `tickers` filters the result.
- **Agent's proposed fix:** state in the mdata contract that `tickers` restricts the rows, and so the calendar, to those tickers. Then make `validate_rows` keep only the requested tickers. M1-T21's tests already check this.
- The record is in `.git/dt-build/details/M1-T21.solo-1.txt`.
