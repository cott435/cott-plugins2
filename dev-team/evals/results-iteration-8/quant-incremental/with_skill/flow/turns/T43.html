# Extend mode: an idea file

`docs/brief.md` exists, so the new idea gets its own file and must earn its place in the project. Examples: `examples-extend.md`, `examples-ml.md`, `examples-data.md` (stage skills and references).

**Read before asking anything:** `docs/brief.md`, `docs/spec.md`, `docs/roadmap.md` and open ideas in `docs/ideas/`. Their problem, goals, constraints, Not Doing list and requirements constrain the new idea. `Specced` ideas are frozen records; where one disagrees with the spec, the spec is current.

- A `Draft` brief: ask whether to finish reviewing it first.
- A `Draft`, `Accepted` or `Parked` idea covering the same ground: offer to refine it instead. A `Specced` one is frozen; a change starts a new file.

**Phases 1-2** per `ideation.md`. Before Phase 1, restate the new idea in terms of the existing project: "This adds [X] so that [existing user] can [outcome]." Note which existing features and requirement IDs it touches.

**Fit check (during Phase 2) — answer one of these out loud. It decides whether the brief changes:**

| Finding | Idea file | Brief |
|---|---|---|
| Serves an existing goal (including the next stage of the same project) | Write it | **No change.** This is the common case. |
| Needs a new goal, same problem and user | Write it | Only if the project's outcome itself widens; a new stage is not a new goal. Add it with the next number. If that makes more than five, ask the user which to merge. |
| Changes a constraint (deadline, budget, a rule) | Write it | Update Constraints. |
| Contradicts the Not Doing list | Write it only if the user reverses that decision | Remove the item, with the user's agreement. Otherwise park the idea. |
| Different problem or different user | Don't write it | Push back: this may be a separate project with its own brief. |

**Phase 3: write `docs/ideas/<idea-slug>.md`** (kebab-case slug, e.g. `shared-editing.md`):


**Writing rules for idea files:**

- **Plain English, still no requirements.** Describe what the user experiences and why; `spec-writing` turns that into requirement IDs and acceptance criteria.
- **More room than the brief, not unlimited.** Aim for 300-700 words. The extra space goes to *How it fits*, *Alternatives considered*, and *Open questions* — the context the spec needs.
- **One idea per file.** If the conversation produced two separable ideas, write two files (ask the user which to do first).
- **Write it as a record, in the brief's voice.** The file outlives the review. Notes to the user ("my proposed limit, for you to check") belong in the conversation. Questions belong under *Open questions*.
- **Tool preferences live here, not in the spec.** If the user names a library, dataset or service ("hand-write the CNN, then compare with a torchvision model"), record it under *Recommended direction* or *Data*. `spec-writing` writes the behavior without the name, and `architecture-design` reads the name from here.
- **Never paste the idea into the brief.** Brief edits are limited to the fit-check table above. Goal numbers stay stable; new goals take the next number. If a goal is dropped, tell the user which spec requirements referenced it.

**Review Gate** (`../SKILL.md`): also say whether the brief changed and which sections.

**Stage** per `roadmap.md`: one stage for the idea, Source `ideas/<slug>.md`. Skip it only when the idea's *Stage* line says it joins a stage not yet being built.

**Idea status lifecycle:** `Draft` → `Accepted` (user approved here) → `Specced` (set by `spec-writing` once the spec is approved). Parked ideas get `Parked` with a one-line reason, so they aren't re-proposed blindly. **A `Specced` idea is frozen.** It records why the feature was added, as it stood that day. `spec-writing` adds a one-line banner saying so, and nobody edits the file afterwards. The spec is the current description. When a new idea changes what a `Specced` one describes, such as a narrowed holdout or a merged stage, the new idea gets its own file and names the old one under *Touches*. The old file is not edited.

# Ideation: understand, expand, converge

Phases 1 and 2 of every run, New and Extend alike. The mode file says what to read before Phase 1 and what Phase 2 must also settle.

## Phase 1: Understand & expand

1. **Restate the idea** as a "How Might We" problem statement.
2. **Ask 3-5 sharpening questions**, no more, with `AskUserQuestion`: who it's for, what success looks like, real constraints, what's been tried, why now. Don't proceed until you know who it's for and what success looks like.
3. **Generate 5-8 variations**, each with a one-line reason it exists. Lenses: inversion, constraint removal, audience shift, combination, simplification, 10x version, expert lens. `frameworks.md` has more; pick what fits.

In a codebase, ground variations in what exists and cite files. Read `docs/references.md` too; an idea cites a reference as prior art by `RF-NN`, never its path.

## Phase 2: Evaluate & converge

1. **Cluster** what resonated into 2-3 meaningfully different directions.
2. **Stress-test** each: user value (painkiller or vitamin?), feasibility (cost, hardest part), differentiation (would someone switch?), and for ML and data projects, data: does usable data exist, can we use it, what's the non-ML baseline? "No usable data" is a feasibility failure, not an open question. Rubric: `refinement-criteria.md`.
3. **Surface hidden assumptions:** what you're betting is true, what could kill it, what you're ignoring for now.
4. **Get a decision** on a direction before writing anything.
# Example: an ML feature in an existing product

Extend mode for an ML idea: the Data section and a baseline.

## ML Feature in an Existing Product (Extend Mode)

**User invokes:** `/ideate use ML to flag bad assay plates automatically in our lab results app`

The app already has `docs/brief.md` (Goal 2: *Bad data is caught before it reaches analysis*) and `docs/spec.md`, so this is **extend mode**. The skill reads both, plus the `qc` module in the codebase.

### Phase 1: Understand & Expand

> **How might we** catch failed plates before they reach analysis, without scientists reviewing every plate by hand?

Questions:

1. **How are plates checked today, and how long does it take?**
2. **What history exists?** How many plates, and is there a record of which ones were failed and why?
3. **What's worse: a bad plate getting through, or a good plate being re-run?**

**User responds:** "Scientists eyeball every plate — about 6 hours a week. We have 3 years of plate reads, roughly 40,000 plates, and about 2% were marked failed in the app. Missing a bad plate is much worse; a re-run costs a day."

**Skill continues:**

Before any ML: assay QC already has a standard rule, the **Z′-factor** (plates under 0.5 are suspect). Your `qc` module computes it but nobody acts on it. That's the baseline any model has to beat. If the rule alone catches most failures, you may not need ML at all.

Variations:

1. **Simplification — Just Use the Rule:** Auto-flag plates with Z′ < 0.5 and stop there. Zero ML.
2. **Ranked Review Queue:** A model scores every plate. Scientists review the riskiest first and stop when the scores get low. Humans still decide.
3. **Inversion — Auto-Pass the Obvious:** Instead of finding bad plates, confidently clear the clearly-good ones, and scientists review the rest.
4. **Anomaly Detection:** No labels needed. Flag plates that look unlike typical ones. Useful if past "failed" labels turn out to be unreliable.
5. **Expert Lens — Layout Patterns:** Many failures show up as spatial patterns (edge effects, a dead column). Features built from plate layout may beat a generic model.

### Phase 2: Evaluate & Converge (summary)

**Data check:** 40,000 plates with 800 failures is enough to try a supervised model, *if* the labels are consistent. That's the biggest bet. Different scientists may fail plates for different reasons. **Baseline:** the Z′ rule. **Cost asymmetry:** missing a bad plate is far worse, so measure recall at a fixed review budget, not accuracy (98% accuracy is free by passing everything).

The user picks **2 (ranked queue), with 1 as the baseline it must beat**. **Fit check:** it serves existing Goal 2 and the same users, so **the brief does not change.**

### Phase 3: Write the Idea File

`docs/ideas/plate-qc-ranking.md`:

```markdown
# Idea: Plate QC Ranking

**Status:** Draft · **Last updated:** 2026-10-14 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This ranks every new assay plate by how likely it is to fail QC, so scientists review the riskiest plates first instead of checking all of them.

## The problem
Scientists check every plate by eye, about 6 hours a week. Failures are rare (about 2%) but costly: a bad plate that slips through corrupts downstream analysis. A good plate failed by mistake costs a day to re-run. The app already computes a standard quality score (Z′) but nothing acts on it.

## Who it's for
Lab scientists doing plate QC, during their weekly review.

## How it fits
- **Serves:** Goal 2 (bad data caught before analysis)
- **Touches:** QC-01 (Z′ is calculated per plate), QC-03 (scientist marks pass/fail)
- **Brief changes:** None
- **Stage:** New S3 (roadmap stage on acceptance)

## Recommended direction
Each new plate gets a risk score from a model trained on three years of past pass/fail decisions. The review screen sorts plates riskiest first. Scientists still make every pass/fail call; the model only sets the order.

The Z′ rule is the baseline. If the model doesn't clearly beat "sort by Z′", we ship the rule alone and stop.

## Data
- About 40,000 plates over 3 years, with raw reads, Z′, and the scientist's pass/fail decision (about 800 failures).
- All in our own database. No outside data needed.
- Evaluate on the most recent 6 months, never trained on, to mimic real use.

## Alternatives considered
- Rule only (Z′ < 0.5) — kept as the baseline, and the fallback if the model doesn't beat it.
- Anomaly detection — only if past labels turn out to be unreliable.
- Auto-passing obvious plates — revisit once the ranking has earned trust.

## What success looks like
- Reviewing the top 20% of plates catches at least 90% of the plates scientists would fail.
- Clearly better than sorting by Z′ alone on the same 6 months.
- Weekly review time drops from about 6 hours to under 2.

## What we're betting on
- Past pass/fail decisions are consistent enough to learn from.
- New plates look like past plates (same instruments and assays).

## Not doing
- Automatically failing or passing plates — a scientist always decides.
- Image-based models of the plate.
- Plates from other sites or instruments.

## Open questions
- How often do two scientists agree on the same plate? Measure before training.
- How often should the model be retrained, and who signs off?
```

# Quant Research Platform

**Status:** Accepted · **Last updated:** 2026-10-17

## The problem
I want to learn quant research and find out whether any signal survives honest testing. Home-built research usually fails earlier, on quietly wrong data. Free prices usually cover only companies alive today, so failures and buyouts vanish and backtests look too good. Tickers get reused by unrelated companies, and split and dividend adjustments are hard to check.

## Who it's for
Me alone: one researcher on one laptop. Research and paper trading only.

## Goals
1. An honest universe: S&P 500 membership as it was on each past date, including companies that later failed, were bought or renamed. Each company keeps one identity across ticker changes, and its exit is recorded.
2. Trustworthy prices and returns: adjusted series I can check against raw prices at any split or dividend.
3. Visible data problems: gaps, stale prices, odd jumps and source disagreements are flagged and easy to inspect, never silently fixed.
4. Reproducible results: each names the data snapshot it used, and rebuilding gives the same answer.
5. Data sources can be added or swapped without rewriting research code.
6. Risk estimates and portfolios judged out of sample: every estimator and allocation must beat simple baselines on realized variance, by a significance test.

## Constraints
- One Apple Silicon MacBook Pro, local storage, no servers.
- Daily US equity prices, 10+ years, covering 2008.
- An existing Sharadar subscription (already paid) plus free sources; new data spending under $50 a month.
- Python throughout, except a TypeScript and React browser app with typed contracts to the backend.

## What success looks like
- All ten test companies (BUD, DNA, WB, LEH, BSC, CFC, MER, SGP, WYE, EK) show the right identity, last trading day, removal date and exit type.
- Reused tickers (BUD, DNA) are never spliced onto another company.
- Sampled current members match a second source, or differences are flagged.
- In the browser app I can open any ticker, see its flags, and compare raw and adjusted prices around a split, with live progress on long runs.

## What we're betting on
- My Sharadar plan includes delisted companies, membership history and corporate actions.
- Recording how each company exited is enough, without exact final-day returns.
- Ten hand-checked names plus a sampled cross-check catch the important errors.

## Not doing
- Real money or broker connections — research and paper trading only.
- Intraday data, fundamentals or live streaming — daily prices first.
- Stocks outside the S&P 500 — a universe I can verify beats a bigger one.
- Reconciling every price across two sources — free sources lack the delisted names.
- A database server or scheduler — one laptop, run by hand.

## Open questions
- Does my Sharadar plan include membership, corporate actions and delisted names, and how is it accessed? A probe settles this first.

Before I draft anything, here is how the idea fits what's already here, then five questions and the directions I see.

**Restated:** this adds a feature lab, so you, as the platform's only researcher, can find out whether any candidate feature predicts residual (market-removed) returns better than chance, using ML as a measuring tool rather than a trading engine.

**How might we** measure whether a feature carries information about future residual returns, in a way that reliably reports "nothing" when there is nothing?

**What it touches:**
- **Brief Problem:** "find out whether any signal survives honest testing". This idea serves it directly, but no current goal covers signals. Goal 6 covers risk estimates only.
- **Brief Not doing:** "fundamentals". Features would be built only from prices, volume, corporate actions and membership unless you reverse that.
- **Spec Out of scope** (added for S2): "Return prediction, signals… and any machine learning". This idea reverses that line, which only scoped Stage 2, so it's a clean reversal.
- **Existing parts it builds on:** the window-only residuals (STRUC-03, PL-19 `residualize`), the planted-answer bench pattern (SYNTH-01–04), and the null-hypothesis-testing skill.

**My honest prior:** price and volume features on S&P 500 large caps have been mined heavily, and most published ones decay. The likeliest honest result is "nothing survives". The design has to make that a clean, trustworthy outcome, not a failure.

### Questions
1. **What should a feature predict, and over what horizon?** My default is next-month residual return, which matches S2's monthly rebalance. The alternative is next-week as well, but overlapping horizons make the null harder to build.
2. **Should features use prices and volume only?** My default is yes, keeping the brief's Not doing. Sharadar fundamentals (SF1) would reverse it and may cost extra.
3. **What counts as "information"?** My default is a held-out improvement in a model's rank correlation with residual returns (IC) when the feature is added. It's tested against a null built by shuffling that feature within each date, with a false-discovery correction across every feature tried.
4. **Should the most recent years be locked away?** My default is yes: hold out 2022 onward, lock the feature list before it is opened, and open it once.
5. **Where do results go?** My default is a static research report only. Features don't feed back into the S2 portfolios, and there's no strategy or backtest Sharpe.

### Variations
1. **Simplification, single-feature screens:** each feature's rank IC against residual returns, with a permutation null and FDR correction, and no ML. This is the baseline any model must beat.
2. **Model-based information gain:** a gradient-boosted model on all features. Each feature's gain is the held-out loss when it is removed or shuffled within date, tested against the null. This catches interactions the screens miss.
3. **Inversion, prove the test lies to you first:** run the whole pipeline on panels with no signal (it must find nothing at the stated false-positive rate) and on panels with a planted signal (it must find it). This mirrors the S2 bench.
4. **Pre-registration:** write the feature list and test settings to a file, hash it before the holdout is touched, and record every feature ever tried, so the correction counts them all.
5. **Expert lens, beyond known factors:** require gain over momentum, reversal and low volatility too, not just over the market. Otherwise "discoveries" are textbook factors under new names.
6. **Economic check:** turn a surviving feature into a long-short portfolio on residual returns and test its return against a null. This bridges to S2 but brings costs and turnover back into scope.
7. **10x, automated feature search:** generate thousands of candidates. It's tempting, but it is the trap the null test exists to catch. I'd reject it, or allow it only with every candidate counted.

**Recommendation:** use 3, 1, 2 and 4 as the core, and keep 5 as a required control. Leave 6 and 7 out of this stage. Variation 3 comes first for the same reason the S2 bench did: if the null test can't stay quiet on pure noise, nothing else it says counts.

**Fit check (my read):**
- The brief's problem and user stay the same, but the outcome widens to signals, so I'd add **Goal 7**: "Every feature claim is judged on held-out data against a null, with every feature tried counted."
- That makes seven goals, above the guide's five. I can instead widen Goal 6 to cover "risk estimates, portfolios and feature claims". Which do you prefer?
- The spec's "no ML / no return prediction" line gets narrowed when this is specced.

Answer the five questions (or say "defaults"), pick variations, and choose Goal 7 or a widened Goal 6. Then I'll write `docs/ideas/feature-information-gain.md` as a Draft.
