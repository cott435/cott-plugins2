# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module naming its Layout file; a step with two owners is two steps), In → Out, Spine version (what the simplest real version does; a type's fields and rules stay in the contract, never restated here), Covers. Every `QR-` item in scope is on the Covers of the step that applies it, a cost or licence limit on the step that picks or calls the source ("no paid data beyond the subscription" on the source factory and each source row); a `QR-` on no step keeps its stage below Designed. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change, routed with the fields its steps need (`../SKILL.md`, Not for) and named in the cell as the contract will name it; never invent it here. `dt lint` checks it (`step-io-types`); a routed type's errors stand until that Revise adds it.
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Changing a step table

Revise, and Sync when the doc changes, edit an existing table this way:

- Keep step names where the function survives; a split step gets new rows with new function names. Keep the pipeline's ID: a rebuilt package keeps its PL IDs where it can, so its golden cases still apply.
- If the entry sketch is gone (the spine was built), don't recreate it. The step table is the contract the code must match; the code change becomes a task.
- Keep `Used by:` lines true: add the PL ID to a symbol a new step calls, and remove it from one no step of that pipeline calls any more.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. One module per step owner, at the Owner's path with dots as folders and the name unchanged (`profile.fit` → `profile/fit.py`, `stock.view` → `stock/view.tsx`, never `stock/StockView.tsx`; an owner given only as `profile` gets one module per related group of steps), never named like a generated file (`api.schema` beside a generated `api/schema.ts`: call it `api.schema_check`). A step whose module needs private helpers owns a folder instead (`core.train` → `core/train/`), holding them; no other step's code goes inside it. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. In a single package each component gets a subfolder whose `__init__.py` exports its contract only, so a later Grow is a folder move. Modules on no step: only `__init__.py`, the entry modules, `__main__.py` for a `python -m` trigger (dispatching each trigger to its entry), and `types.py`. Test folders sit at the repo root in every layout, multi-package included: `tests/intent/<pkg>/`, `tests/unit/<pkg>/`, never under the package's folder. Plan against `build-setup`'s size bar (500 lines per module, 60 per function, or `CONSTRAINTS.md`'s values): split a module expected to pass it now.

## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).

# RL Lab — Architecture

**Status:** Approved · **Shape:** Single package · **Last updated:** 2026-10-19 · **Spec:** [spec.md](spec.md)

## Overview
One Python package, `rllab`. Every environment and every agent sits behind the protocols in `core`. An environment lists its sides, each with its own observation size, its moves (a set of choices or continuous controls with limits) and its agent ids (AD-11, AD-19). It takes one move per living id and reports a result for each, with a score per side. Snake and the corridor have one side with one agent. The fish tank and the line have one side with several agents, which can be removed mid-game. The predator-prey tank and the chase test environment have two sides, each played by its own agent. 107	### AD-02: A hand-written DQN on the 11 facts; PyTorch only for the network and its gradients
108	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
109	- **Context:** The user called Snake a "Good first env for DQN-style value learning" (UR-06) and said "I want to write DQN from scratch" (UR-08). QR-03 rules out RL libraries but allows array math with automatic gradients. AGENT-01–AGENT-05 fix the algorithm: a learned value per move, ε-greedy decaying 1.0 → 0.01 over the first half of the games, 100,000 remembered steps, discount 0.9, and a frozen copy refreshed every 1,000 steps.
110	- **Decision:** `agent.DQNAgent` is written by hand: the replay memory (a NumPy ring buffer), the ε schedule, the target computation, the frozen-copy refresh, the Huber-loss update and the ablation switches. Only the value network uses PyTorch: an MLP of observation size → 256 → move count (11 → 256 → 3 on Snake) built from `torch.nn.Linear`, trained by autograd and `torch.optim.Adam` (lr 1e-3, batch 64). It makes one update per remembered step once a full batch is remembered: one per environment step on Snake, one per fish-step in the compass tank (TWIN-02). AD-17 sets the PyTorch version.
111	- **Alternatives:** NumPy only, with backprop written by hand: it teaches more about gradients, but that isn't the lesson the brief wants and it adds bug surface; it could come later as an exercise. A Q-table (2¹¹ × 3 entries): it would learn Snake well, but it isn't DQN, and with no frozen copy or replay memory to switch off, the ablations would mean nothing.
112	- **Consequences:** The networks are the only library-backed parts, so the "from scratch" check (QR-03) reduces to reading `agent/`, `pg/` and `selfplay/`. The network size, learning rate, batch size and Huber loss are choices the spec doesn't fix, and they live in `AgentConfig` with these defaults.

114	### AD-03: CPU only; one thread per run, separate processes for the study
115	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
116	- **Context:** The user's words are "Laptop CPU only" (UR-13). QR-01 limits one run to ≤ 60 minutes, and QR-02 limits each environment's study. Networks this small gain nothing from torch's thread pool, and extra threads hurt reproducibility (QR-05).

The held-out seeds are `evaluate.EVAL_SEEDS = range(1_000_000, 1_000_100)`, and training seeds come from `[0, 1_000_000)`. Deterministic torch algorithms are switched on in every run.

275	## Risks and open questions
276	- **Training time (QR-01, QR-02):** no default of 1,000 games has been timed. In Snake, a greedy agent that circles until the step limit makes evaluation games long; in the tank, a good policy plays up to 1,000 steps × 5 fish per game, each fish asking the policy network once per step, plus 10 evaluation points of 20 games and a final check of 100. A predator-prey run plays up to 6 fish per step, makes two rung-3 updates per learning game, evaluates both sides (twice the evaluation games), and saves 20 generations; its cross-play table then adds 2,000 greedy games per run inside the study's limit. Mitigation: the first milestone of each stage times one run alone and 3 in parallel, and S3's also times one cross-play table. If too slow, lower the default game count; the spec doesn't fix it.
277	- **Settings the spec leaves open:** the DQN's 11 → 256 → 3 network, Adam lr 1e-3, batch 64, Huber loss and linear ε decay (AD-02), and the ladder's 64-unit networks, lr 3e-4 and log-width start (AD-13), used for both predator-prey sides (AD-22), are tutorial defaults, not tested here. If a learner doesn't beat the scripted baseline (EVAL-04), tune these before questioning the design.
278	- **Frozen opponents draw moves (AD-20, AD-22):** a frozen side or past generation plays its policy's draws, not its centre. If self-play's later generations fail to beat earlier ones (CROSS-04) while the cross-play table, which is greedy, shows them close, try greedy opponents before questioning the ladder.
279	- **Clipped log-probabilities (AD-13):** a policy whose centre sits past a limit (a fish always turning 15°) gets biased gradients. If curves stall with the centre outside the limits, take the log-probability of the unclipped draw instead and record it in `Transition`.
280	- **Rays and one ball or one predator (brief bets):** the S2 idea bets 8 short rays carry enough to dodge the ball, and that fish don't sense its motion (UR-58); the S3 idea bets the same rays carry over to both predator-prey sides and that simultaneous learners show the moving-target failure in a small tank. If no rung beats the scripted fish, or the simultaneous learners don't cycle or stall, that is a finding for the notes (PG-11, SELF-08, EXPL-05), not a design failure; CROSS-04 is the one S3 bar on learning against past generations.
281	- **Comparison method:** the test statistics, how the seeds × games (or runs × opponent generations × games) are paired and the multiple-comparison corrections are left to the `null-hypothesis-testing` skill when `study.compare_scores` and `study.compare_generations` are built. # Idea: Predator-Prey Foraging

**Status:** Specced · **Last updated:** 2026-10-19 · **Brief:** [../brief.md](../brief.md)
**Spec:** HUNT-01–HUNT-12, SELF-01–SELF-08, CROSS-01–CROSS-04, CORE-10, BASE-05–BASE-06, CURVE-07, EXPL-05; CORE-02–CORE-04, CORE-09, PG-04, EVAL-02–EVAL-04, LOG-01, LOG-02, LOG-04, CURVE-03, REPLAY-01, REPLAY-02, EXPL-03, QR-01–QR-03 (changed)

> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)

## In one sentence
This adds a third environment, the fish tank with food pellets and a learning predator, so the learner can see co-evolution: two sides that learn against each other, why that breaks plain training, and how training against past versions fixes it.

## The problem
In Snake and the tank the world stands still while the agent learns. When the opponent also learns, the target keeps moving: each side's reward can stay flat while both improve, and the two can chase each other in circles, forgetting old tricks as they learn new ones. Self-play against past versions is the usual fix. Building the broken version first, then the fix, shows why the fix exists.

## Who it's for
The same learner as the brief, once the fish tank (S2) is built and they move on from one learner in a fixed world to two learners shaping each other's world.

## How it fits
- **Serves:** Goal 1 (explain why self-play works), Goal 2 (beats random and scripted opponents), Goal 3 (replay), Goal 4 (reuses the shared core and S2's tank and PPO)
- **Touches:** S2's tank (TANK: the ball becomes a predator, pellets are added, prey have energy); PG-08 (PPO, reused for both sides); CORE-02, CORE-05, CORE-07 and CORE-08 (one trained agent per run becomes two learners with their own policies in one game); BASE, EVAL, CURVE, REPLAY, EXPL (written for one learner against a fixed world). The spec's "Fish that affect each other" and "Real environments beyond the fish tank" Out of scope items narrow. The frozen [fish-tank.md](fish-tank.md) stays as it is.
- **Brief changes:** Not doing narrowed: predator-prey foraging is planned now; only environments after it wait.
- **Stage:** New S3 (roadmap stage on acceptance), built after S2 is done.

## Recommended direction
**The tank, with stakes.** S2's circular tank, with the bouncing ball replaced by one predator fish, and food pellets scattered around. Prey lose energy over time and must eat pellets to keep it up, so a prey that only hides starves. A prey caught by the predator, or out of energy, is removed. The predator is rewarded for catching prey; prey are rewarded for staying alive. Both sides see only nearby things through rays, as in S2.

**One brain per side.** All prey share one policy, as the fish do in S2. There is one predator with its own policy. Both are the learner's hand-written PPO from S2.

**The ladder.**
1. *Taking turns* (optional first rung): one side trains while the other is frozen, then they swap. The world is still for each learner, so S2's PPO works unchanged.
2. *Simultaneous learners*: both sides learn at once. This is the broken version, kept on purpose: it shows the moving target and the cycling.
3. *Self-play against past versions*: each side saves a copy of itself as a new generation every so often, and trains against a mix of its opponent's current and past generations. This is the fix.

**Judging it.** Each side's reward alone can't show learning, because the opponent improves too. Two fixed bars do: each side is scored against a random and a scripted opponent on the same seeded games. And a cross-play table pits every saved generation of one side against every generation of the other, so later generations beating earlier ones shows real progress rather than circling.

**Time.** The brief's limit of about an hour of training covers the whole self-play run, every generation of both sides, not each generation.

**The core grows again.** The shared core learns to run two learners with their own policies in one game. Snake and the tank keep running as before.

## Alternatives considered
- Evolutionary methods (a population, keep the fittest) — a different lesson from the policy gradients the lab has built up to.
- Simultaneous learners only — shows the problem without the fix.
- Pellets only as a bonus reward — prey can win by hiding forever, so there is no trade-off to learn.
- Several predators — a second multi-agent problem (teamwork) on top of the first.

## What success looks like
- Each side's learning curve beats a random and a scripted opponent on the same seeded games.
- In the cross-play table, later generations beat earlier ones, for both sides.
- Simultaneous learners visibly cycle or stall where self-play does not, or the notes record that they didn't.
- A replay shows prey foraging and dodging while the predator hunts.
- Snake's and the tank's results are unchanged after the core grows.

## What we're betting on
- S2's rays and PPO carry over to both sides with small changes.
- Simultaneous learners show the moving-target failure clearly in a small tank.
- A whole self-play run, over a handful of generations, fits in about an hour on a laptop CPU.

## Not doing
- Evolutionary methods — a different lesson.
- More than one predator — teamwork is a separate problem.
- Learned communication or teaming among prey — the prey share a policy, nothing more.
