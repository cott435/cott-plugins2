# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Changing a step table

Revise, and Sync when the doc changes, edit an existing table this way:

- Keep step names where the function survives; a split step gets new rows with new function names. Keep the pipeline's ID: a rebuilt package keeps its PL IDs where it can, so its golden cases still apply.
- If the entry sketch is gone (the spine was built), don't recreate it. The step table is the contract the code must match; the code change becomes a task.
- Keep `Used by:` lines true: add the PL ID to a symbol a new step calls, and remove it from one no step of that pipeline calls any more.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. One module per step owner (`profile.fit` → `profile/fit.py`; an owner given only as `profile` gets one module per related group of steps), never named like a generated file (`api.schema` beside a generated `api/schema.ts`: call it `api.schema_check`). A step whose module needs private helpers owns a folder instead (`core.train` → `core/train/`), holding them; no other step's code goes inside it. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. In a single package each component gets a subfolder whose `__init__.py` exports its contract only, so a later Grow is a folder move. Modules on no step: only `__init__.py`, the entry modules, `__main__.py` for a `python -m` trigger (dispatching each trigger to its entry), and `types.py`. Test folders sit at the repo root in every layout, multi-package included: `tests/intent/<pkg>/`, `tests/unit/<pkg>/`, never under the package's folder. Plan against `build-setup`'s size bar (500 lines per module, 60 per function, or `CONSTRAINTS.md`'s values): split a module expected to pass it now.

## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).
# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

- **Context:** One learner, one laptop, PyTorch basics already known (brief). S1 needs one install and no separate deployments.
- **Decision:** Python 3.12 managed with uv; a single package `rllab` with one folder per component and one `rllab` command.
- **Alternatives:** Python 3.13: PyTorch and pygame-ce wheels for Apple Silicon lag on new versions. Several packages (core, envs, agents): no separate install or deployment boundary yet (AD-04); UR-34: "Keep one package despite the contract length warning".
- **Consequences:** `requires-python = ">=3.12,<3.13"`. `core` is the seam that would become its own package if environments multiply.

### AD-02: Hand-written learners on PyTorch, CPU only
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-07: the user chose "(a) Write DQN myself in NumPy/PyTorch"; UR-32: "PyTorch is fine for AD-02", over NumPy with hand-written backpropagation. TAB-04 and DQN-07 forbid ready-made learning algorithms. QR-02: an Apple Silicon laptop, no NVIDIA card. The networks are tiny (11 inputs, 3 outputs).
- **Decision:** The table learner is NumPy. Each DQN rung is a small `torch.nn` MLP (11 → 64 → 64 → 3) whose targets, loss, batch sampling, target-network refresh and Double DQN selection are written in `dqn`. PyTorch supplies only tensors, autograd and the Adam optimizer. No RL library is imported anywhere. Everything runs on the CPU; the Apple GPU (MPS) is not used.
- **Alternatives:** NumPy with hand-written backpropagation: you'd learn the gradient maths too, but the backward pass, not the RL, becomes the work. Stable-Baselines3 or similar: ruled out by DQN-07 and UR-07. MPS: slower than the CPU for a 3-output network, and nondeterministic.
- **Consequences:** Autograd hides the gradients but not the learning rule. Import-linter forbids RL libraries.

### AD-03: One DQN learner, the rung a setting
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** dqn
- **Context:** UR-06: Snake is "Good first env for DQN-style value learning". DQN-01–DQN-04 build four rungs. DQN-05 and SHAPE-05 require neighbouring rungs to differ only by the added piece.
- **Decision:** `dqn.DQNAgent` takes a `DQNSettings` whose `rung` is `plain`, `replay`, `target` or `double`. Each rung turns on exactly one more piece: a replay store sampled in batches, a frozen copy refreshed every `target_every` updates, Double DQN target selection. The plain rung trains on each move as a batch of one. All other fields share defaults, and `compare.build_report` refuses a pair whose saved settings differ anywhere else.
- **Alternatives:** Four separate classes: duplicated code, so one rung's change can leak into another unseen. A single class with independent on/off flags: allows combinations the ladder never compares.
- **Consequences:** A rung's added piece is one code branch, easy to read and test against its hand-computed target. Later variants (prioritised replay, say) add a rung value.

### AD-04: A shared core shaped by Snake
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-16: "a shared core reused across environments: env interface, training loop, logging, replay viewer". UR-22: "build it through Snake, shaped by Snake's needs, and adjust it later". RUN-08 requires a second environment to need no changes to training, testing, saving or replay. The brief rules out a general framework built ahead of need.
- **Decision:** Environments implement `core.Env`; agents implement `core.Agent`, and learners `core.Learner`. `train`, `evaluate`, `store` and `replay` import only `core` (and each other), never `snake`; the environment comes from `registry`. `core` holds only what Snake uses: discrete actions, a fixed-length observation vector, a `points` count for test scores and a grid `Frame` for drawing. A test-only grid walk proves RUN-08.
- **Alternatives:** Snake-specific code first, extracted later: RUN-08 would fail in S1. A Gymnasium-style interface: adds spaces, wrappers and render modes that Snake doesn't need, and Gymnasium itself brings dependencies the lab doesn't use.
- **Consequences:** A new environment that needs continuous actions or image observations changes `core`, as UR-22 expects. Import-linter keeps `snake` out of the shared components.

### AD-05: Seeds, test-seed reservation and CPU determinism
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** RUN-03 needs identical curves on a rerun; SNAKE-08, TAB-03, DQN-06 and REPLAY-07 need repeatable games; EVAL-01 needs test seeds never used in training.
- **Decision:** A run seed builds a `np.random.SeedSequence`, spawned into separate generators for training game seeds, exploration, batch sampling and network initialisation (a `torch.Generator`). Test seeds are 0–99; training game seeds are drawn from `[1_000, 2^31)`. Torch runs with `torch.set_num_threads(1)` and `torch.use_deterministic_algorithms(True)`. Each Snake game owns its own generator from its game seed, so food placement depends only on the seed and the moves.
- **Alternatives:** A global seed (`np.random.seed`): any new random call shifts every later draw. Several threads: faster on big networks, but the reduction order varies between runs.
- **Consequences:** Results reproduce on the same laptop and library versions, not across machines; `settings.json` records the versions. One thread stays fast enough for these networks (Risks).

### AD-06: One folder per run, status written last
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** RUN-02 lists the evidence; RUN-05 forbids overwriting; RUN-06 and RUN-07 mark runs incomplete or over time and keep them out of comparisons; the disk-full edge case must name the missing evidence.
- **Decision:** `store.begin_run` creates a new folder whose name ends with a UTC timestamp and a short random id, and writes `status.json` as `running` first. Curve points are appended as they come. `finish` writes the agent and test games, then rewrites `status.json` with the final status and any missing files. Every file is written to a temporary name and renamed. `list_runs` treats `running` with no live process as incomplete.
- **Alternatives:** SQLite: queryable, but a run's evidence is no longer a folder you can open and read. MLflow or Weights & Biases: extra servers or accounts for one learner on one laptop.
- **Consequences:** Comparisons scan folders; for 30-odd runs that's instant. Evidence is plain JSON you can open; agents are `.npz` or `.pt`.

### AD-07: Replay in a pygame window, rebuilt from saved moves
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** replay
- **Context:** REPLAY-02–REPLAY-05 need a board, move scores, pause, step and 1–30 moves per second. REPLAY-06 needs the replay to match the scored game. Web deployment is out of scope.
- **Decision:** `replay` rebuilds each frame by resetting the environment to the saved seed and stepping through the saved moves. It raises `ReplayMismatch` if a food count or ending differs from the saved game. It then draws `core.Frame`s in a pygame-ce window: space pauses and resumes, the right arrow steps, the up and down arrows change speed. Move scores show as three bars with the chosen move marked, or "n/a" for baselines.
- **Alternatives:** A Matplotlib animation: its widgets can't reliably hold 30 frames a second with controls. A self-contained HTML player: needs a JS front end to maintain, closer to the web work the brief leaves out. A terminal (curses) view: no room for score bars on a 10×10 board.
- **Consequences:** Saved games are small (moves only). The viewer draws any grid `Frame`, so the second environment replays unchanged (RUN-08).

### AD-08: Comparisons through the null-hypothesis-testing skill; explanations are the learner's files
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** compare
- **Context:** EVAL-04 and EVAL-05 require the `null-hypothesis-testing` skill on 5 seeds × 100 test games, at 5% after correction for the number of comparisons in the report. EVAL-06 and EVAL-07 need a written explanation for each result.
- **Decision:** Every comparison step in `compare` hands the skill both sides' per-seed, per-game scores on the same test seeds (5 × 100 for a learner, 1 × 100 for a baseline), alpha 0.05 and the report's comparison count. The skill chooses the test, the correction and the null distribution; `compare` maps its verdict to beats/ties/loses or better/worse/no difference. Explanations are Markdown files the learner writes under `reports/explanations/`; an empty or missing file is unexplained.
- **Alternatives:** A fixed Welch t-test in code: replaces the procedure the skill owns. Explanations stored in run folders: they belong to comparisons, not runs.
- **Consequences:** The test can change without touching the report. A comparison waits until both sides have 5 complete runs (EVAL-04).

### AD-09: Learning curves as Matplotlib PNGs following the dataviz skill
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** compare
- **Context:** EVAL-03 asks for the `dataviz` skill on each chart; EVAL-05 puts two rungs' combined curves on one chart. The report is read locally.
- **Decision:** `compare.build_report` draws each chart with Matplotlib to PNG, palette and marks taken from the `dataviz` skill: mean across seeds as a line, the seed range as a band, the two baselines as horizontal reference lines.
- **Alternatives:** Plotly HTML: interactive, but a heavier dependency for static report charts.
- **Consequences:** The charts are images in `reports/`; the report links them.

## Risks and open questions
- One CPU thread might not fit a DQN run plus 20 × 100 test games inside 60 minutes (QR-01). Mitigation: the first DQN task times 10,000 moves and one round of test games, and the step budget is set from that. Test games can be batched per move if needed.
- The table learner sees at most 2^11 situations but only a few hundred occur; it may plateau well below the scripted bot. That is a result to explain (EVAL-06), not a defect.
- Determinism (RUN-03) holds only on the same laptop and library versions. `settings.json` records them, and the rerun check compares like with like.
