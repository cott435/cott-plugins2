# Quant Research Platform — Spec

**Status:** Draft · **Last updated:** 2026-10-17 · **Brief:** [brief.md](brief.md)

## Summary
A local, single-user platform that downloads daily US equity data for every company that was ever in the S&P 500 since at least 2005, stores each download as an immutable snapshot, validates it, and serves it to research code through one source-neutral loader. A browser app lets the user browse securities, inspect data-quality flags, compare raw and adjusted prices around corporate actions, and start and watch download and validation runs. See the [brief](brief.md) for why.

## Users
| User | What they need to do |
|---|---|
| The researcher (sole user) | Build and refresh the dataset, load point-in-time universes and prices into research code, find and inspect data problems, and confirm the data is honest before testing any signal. |

## Scope
**In scope:** Point-in-time universe (`UNIV`), Prices, actions & returns (`PRICE`), Snapshots & runs (`SNAP`), Validation & flags (`QUAL`), Research loader (`LOAD`), Exploratory analysis (`EXPL`), Data cockpit app (`APP`).

**Out of scope:**
- Real money, broker connections or order placement.
- Intraday data, fundamentals, or live market streaming.
- Securities that were never S&P 500 members.
- Reconciling every price across two sources; only a fixed sample is cross-checked.
- A database server, a scheduler, or automatic runs; every run is started by hand.
- Signals, backtests, portfolios, or any later research stage.
- Synthetic final-day returns for delisted securities.
- Automatic correction of flagged data.
- Access from any machine other than the user's laptop.

## Features

### Point-in-time universe (`UNIV`)
**Serves:** Goal 1
**Behavior:** Every security that was an S&P 500 member on any day in the window has a permanent identity, a dated ticker history, its membership spells and, if it stopped trading, a recorded exit. The user can ask which securities were members on any past date and get the answer as it stood on that date.

**Requirements**
- **UNIV-01** Each security has a permanent identity that never changes, whatever its ticker.
  - Given a security whose ticker changed, when its history is requested under either ticker for the matching dates, then the same identity is returned.
- **UNIV-02** A ticker is a dated label: resolving a ticker requires a date and returns the security that held that ticker on that date.
  - Given ticker BUD, when resolved for 2007-06-01 and for 2020-06-01, then two different identities are returned, and no price series contains data from both.
  - Given ticker DNA, when resolved for 2008-06-02 and for the latest date in the snapshot, then two different identities are returned.
- **UNIV-03** Resolving a ticker without a date, when more than one security has used it, is refused with a list of every candidate and the dates each held it.
  - Given ticker BUD and no date, when resolved, then an error lists each candidate's identity, name and ticker dates.
- **UNIV-04** Each listed share class is its own security, linked to its company.
  - Given a company with two listed share classes in the index on the same day, when membership for that day is requested, then both share classes appear, each with its own identity and the same company link.
- **UNIV-05** Membership as of a date returns exactly the securities that were members at that day's close.
  - Given any of the ten test companies and its user-verified removal date, when membership is requested for the trading day before removal and for the removal date, then it is a member on the first and not a member on the second.
- **UNIV-06** Each security's membership is stored as one or more spells, each with an entry date and an exit date (or open).
  - Given a security that left the index and later rejoined, when its membership spells are requested, then two spells are returned with their dates.
- **UNIV-07** Each security that stopped trading has an exit record: its last trading day and one exit type from: acquired for cash, acquired for stock, bankruptcy or failure, moved off the exchange, other.
  - Given each of the ten test companies, when its exit record is requested, then the last trading day and exit type match the user-verified expected facts.

**Edge cases & errors**
- Security removed from the index but still trading → keeps its full price history; it is simply not a member after removal.
- Company that went bankrupt and re-listed under a new ticker (EK) → the re-listed shares are a new security; a link to the predecessor is recorded when the source provides one.
- Exit type cannot be determined from the source → recorded as "other" and flagged.
- Membership requested for a date outside the window or a non-trading day → clear error naming the nearest valid trading days.

### Prices, actions & returns (`PRICE`)
**Serves:** Goal 2
**Behavior:** For every security, the platform keeps raw daily prices exactly as the source gave them, plus splits and dividends. It computes adjusted prices and daily returns from these itself, so every adjustment can be traced back to a raw price and an action.

**Requirements**
- **PRICE-01** Each security has raw daily open, high, low, close and volume for every trading day it was listed within the window, including days outside its index membership.
  - Given a security that joined the index in 2012 and was listed since 2005, when its raw prices are requested, then rows from 2005 onward are returned.
- **PRICE-02** Raw prices are stored exactly as received, never altered.
  - Given a snapshot, when raw prices for any security and day are compared with the downloaded source records, then they are identical.
- **PRICE-03** Each security has its splits (date, ratio) and cash dividends (ex-date, amount per share).
  - Given a security with a known split, when its corporate actions are requested, then the split appears with its date and ratio.
- **PRICE-04** Split-adjusted prices are computed from raw prices and splits.
  - Given a 2-for-1 split on day T, when split-adjusted closes for T−1 and T are requested, then the T−1 adjusted close equals the raw T−1 close divided by 2.
- **PRICE-05** Split-and-dividend-adjusted (total return) prices are computed from raw prices, splits and dividends.
  - Given a cash dividend with ex-date T, when total-return adjusted prices are requested, then prices before T are scaled down by the factor (1 − dividend ÷ raw close on T−1).
- **PRICE-06** Daily price return is the change in split-adjusted close from the previous trading day.
  - Given a 2-for-1 split day where the raw close goes from 100 to 51, when the price return for that day is requested, then it is +2%.
- **PRICE-07** Daily total return includes dividends paid on the ex-date.
  - Given a day with a 1.00 dividend, prior close 100, close 99, when total return is requested, then it is 0%.
- **PRICE-08** A security's first trading day in the window has no return, not a zero return.
  - Given a security's first day of data, when its return is requested, then the value is missing.

**Edge cases & errors**
- Missing trading day while listed → the next day's return is computed against the last available close and the gap is flagged (QUAL-04).
- Split or dividend dated on a non-trading day → applied on the next trading day and flagged.
- Last trading day of a delisted security → its return is computed normally; no further rows exist.
- Corporate action types other than splits and cash dividends (spin-offs, special distributions) → recorded as received, not used in adjustments, and flagged.

### Snapshots & runs (`SNAP`)
**Serves:** Goal 4, Goal 5
**Behavior:** A download run fetches the complete dataset and saves it as a new, dated, immutable snapshot. A validation run checks one snapshot. Both can be started from the command line or the app, and each leaves a run record.

**Requirements**
- **SNAP-01** A completed download run creates one new snapshot with a unique ID, the download time, the source, and its coverage (securities, first and last dates).
  - Given a download run that completes, when snapshots are listed, then the new snapshot appears with its ID, time, source and coverage.
- **SNAP-02** A snapshot is a complete download, never a patch on an earlier snapshot.
  - Given two snapshots, when the older one is deleted from the list of snapshots, then the newer one still loads in full.
- **SNAP-03** A snapshot cannot be changed after it is created.
  - Given an existing snapshot, when any run tries to write into it, then the write is refused and the snapshot is unchanged.
- **SNAP-04** Each snapshot has a content fingerprint that can be re-checked at any time.
  - Given a snapshot whose stored files have been altered outside the platform, when its fingerprint is checked, then the check fails and names the snapshot.
- **SNAP-05** Rebuilding all derived data (adjusted prices, returns, flags) from a snapshot gives identical results every time.
  - Given a snapshot, when derived data is rebuilt twice, then both results have the same fingerprint.
- **SNAP-06** A download run that fails or is interrupted leaves no snapshot behind.
  - Given a download run stopped part way, when snapshots are listed, then no new snapshot appears and the run record shows the failure.
- **SNAP-07** Each run (download or validation) has a record: kind, start and end time, status, the steps it went through, and any errors.
  - Given any finished run, when its record is opened, then all those fields are present.
- **SNAP-08** Only one run of each kind can be active at a time.
  - Given an active download run, when a second download run is started from the command line or the app, then it is refused with a message naming the active run.

**Edge cases & errors**
- Two downloads on the same day → two distinct snapshot IDs.
- Source unreachable or credentials rejected → the run fails within 60 seconds with a message naming the cause; no snapshot is created.
- Temporary source errors → retried up to 3 times per request before the run fails.
- Disk full during a download → the run fails cleanly, as in SNAP-06.

### Validation & flags (`QUAL`)
**Serves:** Goal 1, Goal 2, Goal 3
**Behavior:** A validation run checks one snapshot and records every problem it finds as a flag. Flags are never fixed automatically; they sit beside the data for the user to inspect.

**Requirements**
- **QUAL-01** Each flag records the snapshot, security, date, flag type, the measured value and the threshold it broke.
  - Given any flag, when it is opened, then all those fields are present.
- **QUAL-02** A jump flag is raised when a security's daily price return exceeds 40% in either direction on a day with no corporate action.
  - Given a raw close series 50, 75 with no action, when validated, then a jump flag is raised on the second day.
- **QUAL-03** A stale flag is raised when a security's raw close is unchanged for 5 or more consecutive trading days.
  - Given a close unchanged for 5 consecutive trading days, when validated, then one stale flag covers that run of days.
- **QUAL-04** A gap flag is raised for each exchange trading day missing while a security is listed.
  - Given a listed security with no row on an exchange trading day, when validated, then a gap flag is raised for that day.
- **QUAL-05** An adjustment flag is raised when the platform's adjusted close differs from the source's adjusted close by more than 0.1%.
  - Given a day where the two adjusted closes differ by 0.2%, when validated, then an adjustment flag is raised with both values.
- **QUAL-06** A cross-check compares raw closes of a fixed sample of 50 current members against a second, independent source over their full history; any day differing by more than 0.5% is flagged.
  - Given the same snapshot validated twice, when the cross-check sample is listed, then the same 50 securities are chosen both times.
  - Given a sampled day where the two closes differ by 0.6%, when validated, then a cross-check flag is raised with both values.
- **QUAL-07** A member-without-price flag is raised when a security is an index member on a trading day with no raw price.
  - Given a member with no price on a membership day, when validated, then the flag is raised.
- **QUAL-08** A test-company check compares each of the ten test companies (BUD, DNA, WB, LEH, BSC, CFC, MER, SGP, WYE, EK) against user-verified expected facts: identity, last trading day, index removal date and exit type, and reports pass or fail per fact.
  - Given a snapshot, when validated, then the report lists 40 results (10 companies × 4 facts), each pass or fail with the expected and found values.
- **QUAL-09** Validation never changes the data it checks.
  - Given a snapshot's fingerprint before validation, when validation finishes, then the fingerprint is unchanged.
- **QUAL-10** Validating the same snapshot twice produces identical flags.
  - Given a snapshot validated twice, when the two flag sets are compared, then they are identical.
- **QUAL-11** Each validation run produces a summary of flag counts by flag type and year.
  - Given a finished validation run, when its summary is opened, then counts appear for every flag type and every year in the window, including zeros.

**Edge cases & errors**
- A sampled security missing from the second source → recorded as "not covered", not as a mismatch.
- A day missing from the second source → skipped and counted in the summary.
- Expected facts for a test company missing → that company's results show "no expected value", never pass.

### Research loader (`LOAD`)
**Serves:** Goal 4, Goal 5
**Behavior:** Research code gets universes, prices, returns, actions and flags through one interface. Every result says which snapshot it came from, and nothing returned for a date uses information from after that date.

**Requirements**
- **LOAD-01** The loader opens a snapshot by ID, or the latest snapshot when none is named.
  - Given two snapshots, when the loader is opened with no ID, then it uses the newer one and reports its ID.
- **LOAD-02** Every result carries the ID of the snapshot it came from.
  - Given any loader result, when its snapshot ID is read, then it matches the opened snapshot.
- **LOAD-03** The loader returns the universe as of any trading day.
  - Given a trading day D, when the universe is requested, then the result equals UNIV-05's membership for D.
- **LOAD-04** A point-in-time universe never includes a security before its entry date, and always includes members that later delisted.
  - Given a day in September 2008, when the universe is requested, then members that were later acquired or failed are included, and securities that joined after that day are not.
- **LOAD-05** The loader returns a panel (securities × trading days) of raw prices, adjusted prices, price returns or total returns, as requested, for any list of securities and date range.
  - Given a universe and a date range, when total returns are requested, then one value (or missing) is returned per security per trading day.
- **LOAD-06** The loader returns corporate actions and flags for any list of securities and date range.
  - Given a security with a split and a flag in the range, when actions and flags are requested, then both are returned.
- **LOAD-07** Research code calls the loader the same way whatever source the snapshot came from.
  - Given a small synthetic test source, when the loader's full test suite runs against a snapshot built from it, then every test passes with unchanged calls.

**Edge cases & errors**
- Unknown snapshot ID → error listing available snapshots.
- No snapshots exist → error saying to run a download first.
- Date range partly outside the window → error naming the window.
- Unknown ticker or identity → error; an ambiguous ticker without a date behaves as UNIV-03.

### Exploratory analysis (`EXPL`)
**Serves:** Goal 2, Goal 3
**Behavior:** From any snapshot, the user produces a report that characterises the dataset, so problems the flags don't catch become visible.

**Requirements**
- **EXPL-01** The report is produced from one snapshot with the `data-analysis` skill and covers: members over time, missing data, return distributions and tails, the largest moves, and flag counts by year. It passes when every section is present, the snapshot ID is stated, and regenerating from the same snapshot gives identical numbers.
  - Given a snapshot, when the report is generated twice, then both contain all five sections, name the snapshot, and show identical numbers.
- **EXPL-02** The members-over-time section shows the daily member count and marks every day outside 495–510 securities.
  - Given a day with 490 members, when the report is generated, then that day is marked.
- **EXPL-03** The largest-moves section lists the 50 largest absolute daily returns, each with any corporate action or flag on that day.
  - Given a move on a split day, when listed, then the split appears next to it.

**Edge cases & errors**
- Snapshot without a completed validation run → the report is still produced; the flag sections say validation has not run.

### Data cockpit app (`APP`)
**Serves:** Goal 2, Goal 3
**Behavior:** A browser app on the user's laptop. The user picks a snapshot, finds a security by ticker or name, sees its identity, ticker history, membership and exit, and charts raw against adjusted prices with corporate actions and flags marked. A flag overview shows where problems cluster. The user can start a download or validation run and watch its progress live.

**Requirements**
- **APP-01** The user picks which snapshot the app shows; the chosen snapshot's ID is visible on every screen.
  - Given two snapshots, when the user switches between them, then every view reloads from the chosen snapshot and shows its ID.
- **APP-02** Searching by ticker or company name lists every matching security with the dates it held that ticker.
  - Given a search for BUD, when results show, then two securities are listed with their names and ticker dates.
- **APP-03** A security page shows its identity, company, ticker history, membership spells and exit record.
  - Given LEH, when its page opens, then its last trading day, removal date and exit type are shown.
- **APP-04** The security page charts raw and adjusted closes together, with splits and dividends marked on the dates they apply.
  - Given a security with a split, when its chart opens, then both series are drawn and the split is marked.
- **APP-05** The user can jump the chart to a window of 20 trading days either side of any corporate action.
  - Given a split, when the user selects it, then the chart shows the 20 trading days before and after it.
- **APP-06** The security page lists its flags, filterable by type; selecting a flag moves the chart to that date.
  - Given a security with a jump flag, when the flag is selected, then the chart centres on the flagged day with the flag marked.
- **APP-07** A flag overview shows counts by type and year for the chosen snapshot; selecting a cell lists those flags, and each opens its security page.
  - Given a validated snapshot, when the overview opens, then counts match the validation summary (QUAL-11).
- **APP-08** The user can start a download run or a validation run (on a chosen snapshot) from the app.
  - Given no active run, when the user starts a validation run, then a run record is created and the app shows it as active.
- **APP-09** An active run's progress (current step, items done of total, elapsed time, errors so far) updates live.
  - Given an active run, when it finishes a step, then the app shows the new step within 1 second.
- **APP-10** Reloading or reopening the app during a run reconnects to that run's live progress; closing the app never stops a run.
  - Given an active run, when the browser tab is closed and reopened, then the same run's current progress is shown.
- **APP-11** The interface follows a visual direction set with the `frontend-design` skill, and every chart follows the `dataviz` skill. It passes when the user approves the visual direction before screens are built, and charts are readable in light and dark themes.
  - Given the approved direction, when any screen is reviewed, then it matches that direction and its charts pass the `dataviz` skill's checks in both themes.

**Edge cases & errors**
- Backend not running or connection lost → a clear disconnected state; the app reconnects automatically when the backend returns.
- Starting a run while one of the same kind is active → refused with a message naming the active run (SNAP-08).
- A run fails → its status and error message are shown, and the run record stays viewable.
- No snapshots exist → the app offers to start a download run.
- Security with no price data in the chosen snapshot → its page shows identity and membership, and says no prices exist.

## Data requirements
- **DATA-01** S&P 500 membership history: entry and exit dates for every member, from 2005-01-01 or earlier, as far back as the source allows, to the latest available day.
  - Given the downloaded membership, when the earliest date is checked, then it is 2005-01-01 or earlier.
- **DATA-02** Daily raw open, high, low, close and volume for every security that was ever a member in the window, including securities that were delisted, acquired or failed, over their full listed life within the window.
  - Given the ten test companies, when their raw prices are checked, then each has data up to its last trading day.
- **DATA-03** Corporate actions for those securities: splits, cash dividends, ticker changes and delistings, with their dates.
  - Given a security with a known ticker change, when actions are checked, then the change appears with its date.
- **DATA-04** A permanent security identifier from the source that survives ticker changes and is never reused.
  - Given BUD and DNA, when their identifiers before and after the ticker reuse are compared, then they differ.
- **DATA-05** The source's own adjusted prices, used only for comparison (QUAL-05).
  - Given a snapshot, when the source's adjusted closes are checked, then they are present for every raw price row.
- **DATA-06** A second, independent source of daily raw closes covering at least 50 current members over the window.
  - Given the cross-check sample, when the second source is queried, then at least 50 current members have data.
- **DATA-07** The US exchange trading calendar for the window.
  - Given the window, when the calendar is checked, then every trading day and market holiday is listed.
- **DATA-08** User-verified expected facts for the ten test companies (identity, last trading day, index removal date, exit type), recorded independently of the platform's own code.
  - Given the expected facts, when their origin is checked, then each fact was confirmed by the user.
- **DATA-09** The primary source is the user's existing Sharadar subscription.
  - Given a download run, when its record is checked, then the source named is Sharadar.

## Quality requirements
- **QR-01** Loading the full total-return panel for every security in one snapshot takes ≤ 5 seconds on the user's laptop.
  - Timed test on the full dataset.
- **QR-02** Opening a security's chart in the app takes ≤ 1 second from selection to drawn chart.
  - Timed test on the security with the longest history.
- **QR-03** A full download run finishes in ≤ 30 minutes.
  - Timed on a full download.
- **QR-04** A validation run on one snapshot finishes in ≤ 10 minutes.
  - Timed on a full snapshot.
- **QR-05** Run progress reaches the app ≤ 1 second after each step completes.
  - Timestamp comparison between the run record and the app.
- **QR-06** New data spending stays at or below $50 a month; the existing Sharadar subscription is not counted.
  - The architecture lists every paid source and its monthly price.
- **QR-07** The app and its backend accept connections only from the user's own laptop.
  - A connection attempt from another machine on the same network is refused.
- **QR-08** Source data and credentials never leave the laptop and are never stored in the project's version history.
  - A check over the version history finds no data files or credentials.
- **QR-09** Credentials are never shown in the app, run records or logs.
  - A search of run records and logs after a full run finds no credential values.
- **QR-10** Every message between the app and its backend is checked against one shared contract definition; any mismatch fails the project's checks before the app is run.
  - Changing a field on one side only makes the checks fail.
- **QR-11** One snapshot uses ≤ 2 GB of disk.
  - Size measured after a full download.

## Assumptions
- The universe is every security that was an S&P 500 member on any day in the window, with its full listed history within the window.
- Each listed share class is its own security; tickers are dated labels.
- Exits are recorded by type and last trading day; no synthetic final-day return is added.
- Adjusted prices and returns are computed by the platform; the source's adjusted prices are a check.
- Snapshots are complete downloads, started by hand.
- Flag thresholds: jump > 40%, stale ≥ 5 days, adjustment difference > 0.1%, cross-check difference > 0.5%.
- The cross-check uses a fixed sample of 50 current members.

## Open questions
- Does the Sharadar subscription include membership history, corporate actions, delisted securities and a permanent identifier, how far back does it go, and how is it accessed? Answered by a probe during architecture.
- Which second source supplies the cross-check closes within budget? Answered during architecture, after a probe.
- The expected facts for the ten test companies: the user provides them, or verifies a draft, during test planning.
