# RL Lab — Architecture

**Status:** Approved · **Shape:** Single package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
Three NumPy worlds (Snake, fish tank, predator and prey) sit behind one `Env` protocol that hands each role a compact observation array, never pixels. Hand-written PyTorch learners (DQN for Snake, PPO for the fish and both predator-prey sides) train against batched world copies on the laptop CPU, record a learning curve on held-out curve seeds, and save the agent into a plain-file run folder. Every agent, trained, baseline or reference, is a `Policy`, so evaluation, replay and the statistics treat them alike. A world is signed off when its run folder holds every artefact DONE-01 names and the learner's note passes its checks.

```mermaid
flowchart LR
  worlds --> core
  baselines --> worlds
  learners --> evaluate
  coevo --> learners
  reference --> evaluate
  evaluate --> store
  replay --> store
  signoff --> store
  store --> core
```

## Data
- **Worlds are generated, not downloaded.** Every episode is set by one integer seed (AD-10).
- **Seeds (DATA-01):** per world, evaluation seeds are 0–99, learning-curve seeds 100–119, training seeds 1,000,000 and up; `core.seeds` is the only source, and `learners` refuses a training seed below 1,000,000.
- **Observations** are float32 arrays per role, shape (agents, features): Snake per AD-04, fish and predator-prey per AD-06. Rewards per AD-07.
- **Run folder** `runs/<world>/<run-id>/` (AD-11): `record.json` (seed, settings, duration, curves, status: DATA-02), `policy.pt` only for a finished run (LEARN-03), `scores/<agent>.json`, `comparisons.json`, `curve.png`, `recordings/<agent>-<seed>.json.gz`. Notes live in `notes/<world>.md`, committed; `runs/` is git-ignored.

## Cross-cutting concerns
- **Speed (QR-01):** training steps 16 world copies and makes one batched policy call per step; the loop stops at `time_limit_s` (3,600 by default) and records the duration. Small MLPs run on CPU (AD-09).
- **Reproducibility (QR-03):** one `np.random.Generator` and one `torch.Generator` per run from the run seed, no global random state; `torch.use_deterministic_algorithms(True)` and a fixed thread count in the settings.
- **Errors:** a not-a-number loss or score stops the run with status `diverged` and the curve point where it happened; an interrupted run keeps its curve with status `stopped` and no `policy.pt`. A policy loaded into the wrong world raises `WorldMismatch` naming both worlds.
- **Skills:** `evaluate` runs every significance claim as the `null-hypothesis-testing` skill specifies and draws every chart as the `dataviz` skill specifies (AD-14).
- **Testing:** world rules are tested on hand-placed states (each spec Given/When/Then is a test); learners on tiny worlds for "loss falls"; the reference adapter with SB3's `check_env`.

## Decisions
### AD-01: One Python 3.12 package, `rllab`
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** A one-person learning lab on one laptop, with no separate install, deployment or owner (brief: Not doing, a framework). PyTorch, SB3 and pygame-ce all ship 3.12 wheels for Apple Silicon.
- **Decision:** One package `rllab` with one folder per component. The `reference` component is the seam that carries Stable-Baselines3; it is the only importer of `stable_baselines3` and `gymnasium`, so it could move out if that stack ever gets in the way.
- **Alternatives:** A package per world — no real boundary; the worlds share every protocol. Python 3.13 — wheel coverage lags for some of the stack.
- **Consequences:** `requires-python = ">=3.12,<3.13"`. The import rule (only `reference` imports SB3) is checked by import-linter.

### AD-02: Learners written by hand on PyTorch autograd; worlds in NumPy
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-15: the user wants every method "From scratch in NumPy/PyTorch". LEARN-01 allows array operations and automatic gradients, but no ready-made RL algorithm in training.
- **Decision:** Networks are `torch.nn` layers trained with `torch.optim` and autograd; every RL piece (replay buffer, targets, advantage estimation, clipped loss, exploration) is our own code in `learners` and `coevo`. Worlds are plain NumPy. No module outside `reference` imports an RL library.
- **Alternatives:** NumPy only — writing backward passes by hand becomes the project, not the RL. JAX — less CPU tooling, and the user named PyTorch.
- **Consequences:** Optimizers like Adam are library code; the note may say so. Worlds return NumPy and learners convert at the boundary.

### AD-03: Double DQN for Snake
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** learners
- **Context:** UR-05: Snake is the "Good first env for DQN-style value learning." LEARN-04 needs the value of each of SNAKE-03's three moves learned from reward.
- **Decision:** DQN with a replay buffer, a target network synced every few thousand steps, the double-DQN target, epsilon-greedy exploration decaying over the first part of the run, and an MLP from the AD-04 observation to three move values. Evaluation plays greedily.
- **Alternatives:** Tabular Q-learning — the state space of a 10 × 10 snake is too large. Plain DQN without double targets — overestimates values; adding it is a few lines and a note topic.
- **Consequences:** The reference check compares against SB3's DQN, which also supports only discrete actions (AD-08).

### AD-04: Snake sees the whole grid plus a few direct features
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** The spec rules out pixels but leaves the observation open. EVAL-04 requires beating the scripted snake (BASE-02), which already uses "food direction plus next-step danger"; an agent seeing only those 11 classic features has no more information than the script.
- **Decision:** A 311-value vector: three 10 × 10 planes (head, body cells weighted by how soon they clear, food), the heading one-hot (4), the next-step danger for each move (3) and the food's direction relative to the head (4).
- **Alternatives:** The 11 classic features — fast, but caps the agent near the script. A small CNN over the planes — more to write and slower on CPU; revisit if the MLP falls short.
- **Consequences:** The agent can learn to avoid trapping itself, which the script can't. The MLP's first layer is larger; still CPU-cheap.

### AD-05: PPO with a squashed Gaussian movement action, shared within a role
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** learners
- **Context:** UR-11: the fish tank is "Good for policy-gradient / PPO and continuous control." LEARN-05 needs continuous heading and speed (TANK-03, PREY-04). TANK-06 and PREY-01 have several agents of a role at once.
- **Decision:** Clipped-objective PPO with generalised advantage estimation and separate actor and critic MLPs. The actor outputs a Gaussian over a 2D vector, squashed by tanh; the world reads its angle as heading and its length (capped at 1) times the role's top speed as speed. All fish, and all prey, share one policy, each acting on its own observation; the predator has its own.
- **Alternatives:** A Gaussian on (angle, speed) — the angle wraps at ±180°, which a Gaussian handles badly. Separate policies per fish — 5× the data for no gain; fish are interchangeable. REINFORCE — simpler, but much noisier; it is the note's comparison point, not the method.
- **Consequences:** The same PPO serves S2 and S3 (AD-13). Critic inputs are the acting agent's own observation, so the several-fish version is independent learners sharing parameters.

### AD-06: Nearby things fill fixed slots with a presence flag
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** TANK-07 and PREY-05 hide anything beyond 0.5; TANK-05's single fish sees everything. An MLP needs a fixed input size.
- **Decision:** Each observation starts with the agent's own position, velocity and distance to the wall, then fixed slots per kind of thing, nearest first, each holding relative position, relative velocity and a present flag; an empty slot is all zeros. Slots: single fish — 1 ball, always present; several fish — 1 ball, 4 other fish; prey — 1 predator, 4 other prey, 3 pellets; predator — 5 prey, 3 pellets. `worlds.decode` names the fields so scripted agents read the same array (BASE-06).
- **Alternatives:** Attention over a variable-length list — more expressive, more to build and explain. A coarse sensor ring (distances in N directions) — loses velocities.
- **Consequences:** Pellets beyond the 3 nearest in sight are dropped; recorded as an assumption.

### AD-07: Rewards follow each world's score
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** CHECK-01 needs the same rewards for both learners, so rewards belong to the world, not the learner. Scores are SNAKE-07, TANK-09 and PREY-07.
- **Decision:** Snake: +1 per food, −1 on death, 0 otherwise. Fish: +0.01 per step alive, −1 when the ball touches it. Prey: +1 per pellet, −1 when caught. Predator: +1 per catch.
- **Alternatives:** Shaping (distance to food or ball) — faster learning, but teaches the shaping and muddies the note.
- **Consequences:** Sparse Snake rewards may slow early learning; the risk below covers it.

I checked first, and there's nothing waiting for this approval. The architecture and the `rllab` contract were already approved and committed (`542c50c`), and the working tree is clean, so I made no edit and no commit.

What the pipeline step actually needs now is to create `docs/packages/rllab/pipelines.md`, which doesn't exist yet. No spec ID sits on a pipeline so far. I haven't written anything: I need you to confirm the workflows first.

**Candidate workflows** (every stage, since S1–S3 are all specced):

| # | Workflow | Trigger | What it does | Stage |
|---|---|---|---|---|
| 1 | **Train an agent** | `rllab train <world>` | Creates a run folder, trains the hand-written DQN (Snake) or PPO (fish, one or several) within the time limit on 16 world copies, records the learning curve on the curve seeds, and saves `policy.pt` | S1, S2 |
| 2 | **Evaluate and compare** | `rllab evaluate <world> <run>` | Plays the trained, random, scripted and reference agents on evaluation seeds 0–99, runs the corrected comparisons and draws `curve.png` | S1–S3 |
| 3 | **Reference check** | `rllab reference <world>` | Trains Stable-Baselines3's DQN or PPO on the same world and rewards, then scores it as a policy for workflow 2 to compare | S1, S2 |
| 4 | **Record and watch a replay** | `rllab replay <run> <agent> <seed>`, `rllab watch <file>` | Records one episode's frames to `recordings/`, then plays them in a pygame window with controls | S1–S3 |
| 5 | **Sign off a world** | `rllab note <world>`, `rllab signoff <world>` | Starts the note with the results filled in, checks the note and the run folder's files against DONE-01, and gates which world can start next | S1–S3 |
| 6 | **Co-evolution comparison** | `rllab coevo` | Trains predator and prey under both approaches (both learning at once, and each training against past versions of the other), then builds the 2×2 cross-play table and the snapshot sweep | S3 |

**I recommend all six.** S1 runs 1–5 end to end, S2 reuses them with PPO, and S3 adds 6. The alternative is a core set of 1, 2, 4 and 5. That would drop the reference check (CHECK) and co-evolution (COEVO) from pipelines, and both would be listed as uncovered.

Which do you want: **all of them**, or **the core set only**? Also tell me if any trigger or grouping looks wrong. For example, 4 could become separate record and watch pipelines.
