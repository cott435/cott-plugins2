# Extend mode: an idea file

`docs/brief.md` exists, so the new idea gets its own file and must earn its place in the project. Examples: `examples-extend.md`, `examples-ml.md`, `examples-data.md` (stage skills and references).

**Read before asking anything:** `docs/brief.md`, `docs/spec.md`, `docs/roadmap.md` and open ideas in `docs/ideas/`. Their problem, goals, constraints, Not Doing list and requirements constrain the new idea. `Specced` ideas are frozen records; where one disagrees with the spec, the spec is current.

- A `Draft` brief: ask whether to finish reviewing it first.
- A `Draft`, `Accepted` or `Parked` idea covering the same ground: offer to refine it instead. A `Specced` one is frozen; a change starts a new file.

**Phases 1-2** per `ideation.md`. Before Phase 1, restate the new idea in terms of the existing project: "This adds [X] so that [existing user] can [outcome]." Note which existing features and requirement IDs it touches.

**Fit check (during Phase 2) — answer one of these out loud. It decides whether the brief changes:**

| Finding | Idea file | Brief |
|---|---|---|
| Serves an existing goal. Every new stage of the same project does | Write it | **No change.** This is the common case. A new stage never adds a goal, even when the user asks for one: the stage is its roadmap row and the idea's *Serves* line. |
| Needs a new goal: the project's outcome itself widens, same problem and user | Write it | Add the goal with the next number. If that makes more than five, merge before writing: propose which goals fold together, your merge as the default, and write the merged set. Never write a sixth goal. |
| Changes a constraint (deadline, budget, a rule) | Write it | Update Constraints. |
| Contradicts the Not Doing list | Write it only if the user reverses that decision | Remove the item, with the user's agreement. Otherwise park the idea. |
| Different problem or different user | Don't write it | Push back: this may be a separate project with its own brief. |

**Writing rules for idea files:**

- **Plain English, still no requirements.** Describe what the user experiences and why; `spec-writing` turns that into requirement IDs and acceptance criteria.
- **More room than the brief, not unlimited.** Aim for 300-700 words. The extra space goes to *How it fits*, *Alternatives considered*, and *Open questions* — the context the spec needs.
- **One idea per file.** If the conversation produced two separable ideas, write two files (ask the user which to do first).
- **Write it as a record, in the brief's voice.** The file outlives the review. Notes to the user ("my proposed limit, for you to check") belong in the conversation. Questions belong under *Open questions*.
- **Tool preferences live here, not in the spec.** If the user names a library, dataset or service ("hand-write the CNN, then compare with a torchvision model"), record it under *Recommended direction* or *Data*. `spec-writing` writes the behavior without the name, and `architecture-design` reads the name from here.
- **Never paste the idea into the brief.** Brief edits are limited to the fit-check table above. Goal numbers stay stable; new goals take the next number, and a merged goal keeps the lower one. If a goal is dropped or merged away, tell the user which spec requirements referenced it.

**Review Gate** (`../SKILL.md`): also say whether the brief changed and which sections.

**Stage** per `roadmap.md`: one stage for the idea, Source `ideas/<slug>.md`. Skip it only when the idea's *Stage* line says it joins a stage not yet being built.

**Idea status lifecycle:** `Draft` → `Accepted` (user approved here) → `Specced` (set by `spec-writing` once the spec is approved). Parked ideas get `Parked` with a one-line reason, so they aren't re-proposed blindly. **A `Specced` idea is frozen.** It records why the feature was added, as it stood that day. `spec-writing` adds a one-line banner saying so, and nobody edits the file afterwards. The spec is the current description. When a new idea changes what a `Specced` one describes, such as a narrowed holdout or a merged stage, the new idea gets its own file and names the old one under *Touches*. The old file is not edited.

**Mode: Extend.** The brief exists, so this idea gets its own file, `docs/ideas/<slug>.md`, and has to fit the existing project. Nothing gets written until we've agreed on a direction.

**Restated in project terms:** this adds Environment 2 so that you can learn **policy-gradient methods for continuous control** by building them. It touches Goal 1 (one named concept per environment), Goal 2 (match a library version), Goal 3 (beat random and scripted players), Goal 4 (replay) and especially **Goal 5 (reuse the shared core)**.

### Honest pushback first
1. **It bundles four concepts.** Policy gradients/PPO, continuous actions, multiple agents and limited vision are each a whole lesson. Goal 1 says each environment teaches *one* named concept, and debugging PPO is hard enough without multi-agent effects muddying every curve. Pick the lesson; the other parts become the setting, or later rungs.
2. **It collides with the current scope.** The approved spec rules out "multi-agent or competitive games." Several fish at once either reverses that, or stays inside it if the fish are just independent copies sharing one policy, never competing or cooperating. That's a decision only you can make.
3. **It will change the shared core, and that's actually useful.** Today `core.Env` and `core.Agent` assume one agent with discrete actions (`n_actions: int`, `act → int`). Continuous movement and several fish break both. Goal 5 promised that environment 2 would "only need its own game code". That promise gets tested for real here, and the core interface will need a deliberate revision. Better to plan for that than to discover it.
4. **The library comparison gets harder with many fish.** Stable-Baselines3 PPO handles continuous actions fine, but not several agents sharing one tank. A single-fish rung keeps the library match clean.

### Sharpening questions
1. **What's the named concept?** My guess: "policy gradients for continuous control (REINFORCE → PPO)", with multiple fish and limited vision as the setting, not the lesson.
2. **How do the fish relate?** (a) independent copies sharing one policy, which don't collide and maybe don't even see each other; (b) they see and avoid each other; (c) they compete or cooperate. My guess is (a), possibly (b). Option (c) reverses the spec's multi-agent exclusion.
3. **What does "done" look like?** My guess: average survival time beats a random swimmer and a scripted "swim straight away from the ball" fish; PPO beats plain REINFORCE; your PPO comes within 90% of the library's on the single-fish rung; and you can watch a replay of the school.
4. **Do the same constraints apply?** Under an hour of laptop CPU training, a few weeks, and $5 of cloud at most?
5. **Is it acceptable that this revises the core interface** (continuous actions, several agents per step), with Snake and the corridor updated to match?

### Variations
1. **A ladder, like Snake:** one fish with REINFORCE, then one fish with PPO, then a school of N fish sharing one PPO policy. Each step adds one idea.
2. **Discrete first:** start with 8 swim directions so your S1 DQN can run as a baseline, then go continuous. That shows why policy gradients are needed for continuous actions.
3. **Limited vision as its own rung:** the fish sees the whole tank, then only its local "sensor rays". That teaches partial observability on purpose instead of by accident.
4. **Shared policy, no interaction:** many fish are just many samples of experience per step, which is cheap data for PPO. That's the simplest multi-fish setup that stays inside the scope.
5. **Inversion: a learned ball.** The ball learns to hunt the fish. That's competitive multi-agent, so I'd leave it out.
6. **Physics as the main constraint:** a ball reflecting off a circular wall at a constant speed, fish with a speed cap, and everything seeded. Easy to reproduce, easy to test against closed-form answers.
7. **The 10x version:** schooling emerges when fish see each other. It's fun, but it's a different lesson.

**My lean:** **1 + 3 + 4**, with variation 2 as an optional baseline rung. The concept is policy gradients for continuous control. Multiple fish means a shared policy with no competition, which keeps the spec's exclusion intact. Limited vision is the final rung. The core interface gets revised deliberately.

Answer the questions, Q1, Q2 and Q5 especially, and I'll converge on a direction.
