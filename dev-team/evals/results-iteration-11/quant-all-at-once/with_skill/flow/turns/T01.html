**Writing rules — the brief must pass all of these:**

# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

# Ideation: understand, expand, converge

Phases 1 and 2 of every run, New and Extend alike. The mode file says what to read before Phase 1 and what Phase 2 must also settle. Throughout, record the user's words as `requests.md` says: their first message, each answer, each direction they pick.

## Phase 1: Understand & expand

1. **Restate the idea** as a "How Might We" problem statement.
2. **Ask 3-5 sharpening questions**, no more, with `AskUserQuestion`: who it's for, what success looks like, real constraints, what's been tried, why now. Don't proceed until you know who it's for and what success looks like.
3. **Generate 5-8 variations**, each with a one-line reason it exists. Lenses: inversion, constraint removal, audience shift, combination, simplification, 10x version, expert lens. `frameworks.md` has more; pick what fits.

In a codebase, ground variations in what exists and cite files. Read `docs/references.md` too; an idea cites a reference as prior art by `RF-NN`, never its path.

## Phase 2: Evaluate & converge

1. **Cluster** what resonated into 2-3 meaningfully different directions.
2. **Stress-test** each: user value (painkiller or vitamin?), feasibility (cost, hardest part), differentiation (would someone switch?), and for ML and data projects, data: does usable data exist, can we use it, what's the non-ML baseline? "No usable data" is a feasibility failure, not an open question. Rubric: `refinement-criteria.md`.
3. **Surface hidden assumptions:** what you're betting is true, what could kill it, what you're ignoring for now.
4. **Get a decision** on a direction before writing anything.
# Example: a demand-forecasting package

A data-dependent New project with its first roadmap stages, then a later idea routing stage skills and references.

## GridLoad (New Project, Data-Dependent)

**User invokes:** `/ideate a Python package for forecasting our utility's electricity demand — I keep rewriting the same notebook code`

### Phase 1: Understand & Expand

**Skill response:**

> **How might we** get from a forecast idea to an evaluation we can actually trust, without rebuilding the data and scoring plumbing every time?

Before expanding:

1. **Who uses it?** Just you, or a small team that needs to compare each other's results?
2. **What horizon and resolution?** Day-ahead? Hourly? By region?
3. **What data do you have today, and what's the budget?** Free sources, an existing subscription, or room to pay?
4. **Research only, or does this end up feeding operations?**

**User responds:** "Me and two analysts. Hourly by region, day-ahead is what matters. We have the utility's meter export and pull weather from a free public weather API. Budget maybe $100/month. Research only for now."

**Skill continues:**

"Rewriting notebook code" is the symptom. The expensive problem is **not trusting the results**. One-off notebooks are where look-ahead and missing history creep in, and a forecast that only scores well because of a bug is worse than no forecast.

Here are 5 variations:

1. **Model Engine First:** A clean training and scoring loop. Forecasts plug in. Data is the user's problem.
2. **Data Layer First (Inversion):** Start from trustworthy data, not the engine: a local store of readings and weather as known at any time, with one interface. Any simple model is fine once the data is right.
3. **Simplification — Tabular Only:** No sequence models. A forecast is a function from a region-by-hour feature table to predictions. Fast and enough for day-ahead.
4. **Combination — Notebook Kit:** Keep notebooks, but ship the pieces as a library: data loader, scoring function, standard error report.
5. **10x — Full Platform:** Scheduled data pulls, experiment tracking, and a model registry. Clearly too much for three people.

### Phase 2: Evaluate & Converge

**Data feasibility decides this one.** Today's readings are easy: they are the utility's own export. **Meter history including decommissioned meters** is not: the export lists today's registry, so every regional total quietly drops removed meters and past load looks wrong. Scoring with weather actuals where only the forecast was known has the same effect on errors. That's the dealbreaker to check first: can both be had within $100/month?

**Direction (2 + 3): Trustworthy data layer + tabular forecasts.** It attacks the real problem (trust). It fits day-ahead hourly forecasts. Hiding the weather source behind one interface keeps the provider decision open.

**Direction (1): Model engine.** More flexible training, but none of your forecasts need it yet. Pushing back: this is where these projects usually sink months.

The user picks (2 + 3).

```markdown

## What we're betting on
```

# Example: an ML feature in an existing product

Extend mode for an ML idea: the Data section and a baseline.

## ML Feature in an Existing Product (Extend Mode)

**User invokes:** `/ideate use ML to flag bad assay plates automatically in our lab results app`

The app already has `docs/brief.md` (Goal 2: *Bad data is caught before it reaches analysis*) and `docs/spec.md`, so this is **extend mode**. The skill reads both, plus the `qc` module in the codebase.

### Phase 1: Understand & Expand

> **How might we** catch failed plates before they reach analysis, without scientists reviewing every plate by hand?

Questions:

1. **How are plates checked today, and how long does it take?**
2. **What history exists?** How many plates, and is there a record of which ones were failed and why?
3. **What's worse: a bad plate getting through, or a good plate being re-run?**

**User responds:** "Scientists eyeball every plate — about 6 hours a week. We have 3 years of plate reads, roughly 40,000 plates, and about 2% were marked failed in the app. Missing a bad plate is much worse; a re-run costs a day."

**Skill continues:**

Before any ML: assay QC already has a standard rule, the **Z′-factor** (plates under 0.5 are suspect). Your `qc` module computes it but nobody acts on it. That's the baseline any model has to beat. If the rule alone catches most failures, you may not need ML at all.

Variations:

1. **Simplification — Just Use the Rule:** Auto-flag plates with Z′ < 0.5 and stop there. Zero ML.
2. **Ranked Review Queue:** A model scores every plate. Scientists review the riskiest first and stop when the scores get low. Humans still decide.
3. **Inversion — Auto-Pass the Obvious:** Instead of finding bad plates, confidently clear the clearly-good ones, and scientists review the rest.
4. **Anomaly Detection:** No labels needed. Flag plates that look unlike typical ones. Useful if past "failed" labels turn out to be unreliable.
5. **Expert Lens — Layout Patterns:** Many failures show up as spatial patterns (edge effects, a dead column). Features built from plate layout may beat a generic model.

### Phase 2: Evaluate & Converge (summary)

**Data check:** 40,000 plates with 800 failures is enough to try a supervised model, *if* the labels are consistent. That's the biggest bet. Different scientists may fail plates for different reasons. **Baseline:** the Z′ rule. **Cost asymmetry:** missing a bad plate is far worse, so measure recall at a fixed review budget, not accuracy (98% accuracy is free by passing everything).

The user picks **2 (ranked queue), with 1 as the baseline it must beat**. **Fit check:** it serves existing Goal 2 and the same users, so **the brief does not change.**

"""Market-mode removal for a daily returns panel by PCA.

Written while working through the "remove the market, then look at what's left" exercise. Takes a T x N
panel of simple daily returns (dates x tickers), finds the dominant principal components of the
correlation structure and regresses them out, leaving residual (idiosyncratic) returns.

The decomposition is fit on the whole panel passed in: the eigenvectors, the standardisation and the
loadings all use every row, including the last one.
"""
from __future__ import annotations

import numpy as np
import pandas as pd


def demean_returns(returns: pd.DataFrame, min_obs: int = 60) -> pd.DataFrame:
    """Drop thin columns, fill the remaining gaps with 0 and subtract each column's mean.

    Columns with fewer than ``min_obs`` non-missing rows are dropped. Missing values left after that are
    treated as a zero return (no trade that day).
    """
    keep = returns.columns[returns.notna().sum() >= min_obs]
    r = returns[keep].fillna(0.0)
    return r - r.mean(axis=0)


def standardise(returns: pd.DataFrame) -> tuple[pd.DataFrame, pd.Series]:
    """Scale each column to unit variance; returns the scaled panel and the per-column std used."""
    sd = returns.std(axis=0, ddof=1).replace(0.0, np.nan)
    return returns.divide(sd, axis=1).fillna(0.0), sd


def pca_factors(returns: pd.DataFrame, k: int = 1) -> tuple[pd.DataFrame, pd.DataFrame, np.ndarray]:
    """Top-k principal components of the standardised returns.

    Returns:
        factors: T x k factor return series (projections of each day onto the eigenvectors).
        loadings: N x k eigenvectors, sign-fixed so each column has a positive sum (the market mode then
            loads positively on almost every stock).
        explained: the fraction of total variance explained by each of the k components.
    """
    z, _ = standardise(demean_returns(returns))
    corr = np.corrcoef(z.to_numpy(), rowvar=False)
    evals, evecs = np.linalg.eigh(corr)
    order = np.argsort(evals)[::-1]
    evals, evecs = evals[order], evecs[:, order]
    vecs = evecs[:, :k]
    vecs = vecs * np.sign(vecs.sum(axis=0, keepdims=True))
    cols = [f"pc{i + 1}" for i in range(k)]
    loadings = pd.DataFrame(vecs, index=z.columns, columns=cols)
    factors = pd.DataFrame(z.to_numpy() @ vecs, index=z.index, columns=cols)
    explained = evals[:k] / evals.sum()
    return factors, loadings, explained

volatility over one or more horizons, per ticker, from a long table of daily closes. Rows whose horizon
runs past the end of a ticker's history get NaN targets and are dropped by ``drop_incomplete``.

from __future__ import annotations

import numpy as np
import pandas as pd

TRADING_DAYS = 252


def log_returns(prices: pd.DataFrame, price_col: str = "adj_close") -> pd.Series:
    """Daily log return per ticker. ``prices`` is long: one row per (ticker, date), sorted or not."""
    p = prices.sort_values(["ticker", "date"])
    lr = np.log(p[price_col]).groupby(p["ticker"]).diff()
    return lr.rename("log_ret")

def normalise_observed(panel: pd.DataFrame, cols: list[str], window: int = 252) -> pd.DataFrame:
    """Per-ticker z-score of observed covariates using a trailing window (no future rows)."""
    p = panel.sort_values(["ticker", "date"]).copy()
    g = p.groupby("ticker")[cols]
    mu = g.transform(lambda s: s.rolling(window, min_periods=20).mean())
    sd = g.transform(lambda s: s.rolling(window, min_periods=20).std())
    p[cols] = ((p[cols] - mu) / sd.replace(0.0, np.nan)).fillna(0.0)
    return p


def build_windows(panel: pd.DataFrame, targets: pd.DataFrame, spec: WindowSpec) -> dict[str, np.ndarray]:
    """Slice every ticker's history into windows.

    Returns arrays keyed by name, with S samples:
        static   (S, n_static)              int64
        known    (S, lookback + horizon, n_known)
        observed (S, lookback, n_observed)
        target   (S, horizon, n_target)
        origin   (S,) the forecast-origin date of each sample (last encoder step)
        ticker   (S,)
    """
    df = panel.merge(targets, on=["ticker", "date"], how="inner").sort_values(["ticker", "date"])
    span = spec.lookback + spec.horizon
    out = {k: [] for k in ("static", "known", "observed", "target", "origin", "ticker")}
    for tk, g in df.groupby("ticker", sort=True):
        if len(g) < span:
            continue
        st = g[spec.static_cols].iloc[0].to_numpy(dtype=np.int64)
        kn = g[spec.known_cols].to_numpy(dtype=np.float32)
        ob = g[spec.observed_cols].to_numpy(dtype=np.float32)
        tg = g[spec.target_cols].to_numpy(dtype=np.float32)
        dates = g["date"].to_numpy()
        for start in range(0, len(g) - span + 1, spec.stride):
            enc_end = start + spec.lookback
            out["static"].append(st)
            out["known"].append(kn[start:start + span])
            out["observed"].append(ob[start:enc_end])
            out["target"].append(tg[enc_end - 1:enc_end - 1 + spec.horizon])
            out["origin"].append(dates[enc_end - 1])
            out["ticker"].append(tk)
    return {k: np.stack(v) if v else np.empty((0,)) for k, v in out.items()}

**How might we** build a US equity research setup where every result, from a covariance estimate to a trading agent, can be trusted to hold up out of sample, and each stage stands on the one before it?

Your plan is already well ordered. Proving variance first and requiring every feature to pass a null-hypothesis test is the right order. Three honest pushbacks before the questions:

- **The real risk is look-ahead, not modelling.** Your reference code shows it already. `market_decomposition.py` fits the PCA on the whole panel, last day included, and fills gaps with zero returns. `tft_dataset.py` splits by forecast date without a gap, so 21-day targets overlap across the train/test boundary. Neither matters for teaching. Both would quietly inflate every Stage 2–4 result. Reference intake will flag these as "don't trust" items.
- **The Yahoo cross-check only covers stocks that still exist.** Delisted names, which a point-in-time universe needs most, can't be checked against Yahoo. So the cross-check is a sanity test on survivors, not proof that the data is right.
- **The viz app is the biggest scope risk in Stage 1.** A React and WebSocket app over daily data can take longer than the dataset itself. It's worth knowing what the app must show you in Stage 1 and what the WebSocket carries.

**Questions** (each has my default):

0. **References.** Your 3 files aren't indexed yet. Shall I run reference-intake first, so each one gets an entry saying what to trust, and then come back here? *Default: yes.*
1. **Purpose and success.** Is this for learning and research only, or might it one day guide real money? What would make you say "this worked" after Stage 2? *My guess: research and learning. Success means a denoised or shrinkage estimate measurably lowers out-of-sample variance against the sample covariance.*
2. **Universe and history.** How big is the universe, and how far back? Which Sharadar tables do you have (prices and actions only, or fundamentals too)? *Default: about the top 1,000 by market cap, point in time, from 2000 on, delisted names included.*
3. **Fundamentals.** Should Stage 3 features use fundamentals (earnings, book value) or only price and volume? *Default: price and volume only. Fundamentals go under Not Doing for now.*
4. **The Stage 4 bar.** Stage 2 portfolios are judged on realized variance, but forecast-driven ones aim at return. What does "beat" mean: after-cost risk-adjusted return over the same held-out period? *Default: after-cost Sharpe ratio plus realized variance, same period, same costs.*

**Directions:**

1. **As you wrote it.** Four stages, with the full viz app in Stage 1. It's complete, but the app competes with the data for time.
2. **Trust first.** The same stages, plus one rule that applies to all of them: every estimate is refit only on past data. Stage 1 includes a "no look-ahead" check that every later stage reuses.
3. **Thin app first.** In Stage 1 the app only browses prices, actions, universe membership and data-check results. Each later stage adds its own views (eigenvalue spectra, portfolio variance, feature test results).
4. **No app until Stage 2 (simplification).** Notebooks and saved charts for Stage 1. The app comes once there's structure worth exploring.
5. **Stage 4 split in two.** Forecasting plus forecast-driven portfolios is one outcome. PPO agents are a second, optional stage. PPO is the most likely part to eat months without beating min-variance.
6. **A shared scoreboard.** One out-of-sample evaluation harness, built in Stage 2: same periods, same costs. Every later portfolio is ranked on it, which makes "must beat stage 2" checkable.

My lean is **2 + 3 + 6**, with **5** worth considering.

Answer the questions (or just say "defaults") and pick a direction. I'll stop here until you do.
