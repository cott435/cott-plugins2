# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. Neither a long contract (`dt context` loads only the sections a task reads) nor a dependency direction (import-linter enforces it between components of one package) is a reason to split. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

## Grow triggers

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, torchvision).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.
- A part runs or deploys on its own (a day-ahead forecast service).

# Contracts

Read when writing or changing a `contract.md`.

Write `docs/packages/<pkg>/contract.md`: the provider's promise to its consumers. Consumers read only this page, so it stands alone.

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). The ID survives Grow, because the component id becomes the package id.

# Writing rules

Read before writing or changing any architecture doc, every round. Decision rules are in `decisions.md`.

- **`PL-NN` IDs are permanent.** A retired system pipeline collapses to `- ~~PL-NN: title~~ Retired YYYY-MM-DD: reason`.

- **The Changelog has one row per round, one line long.** IDs are the new decisions, as ranges (`AD-12–AD-15`). Don't repeat the spec row's ID list. As you hear it, before you write any doc:

129	  - Given any training run or test game, when the board size is read, then it is 10×10.
130	- **SNAKE-02** On each move the agent chooses one of 3 moves relative to its heading: straight, turn left, turn right.
131	  - Given a snake heading right, when it turns left, then its head moves up one cell and its heading becomes up.
132	  - Given any heading, when any of the 3 moves is chosen, then the snake never reverses into its own neck.
133	- **SNAKE-03** Eating food makes the snake 1 cell longer, gives a reward of +1, and places a new food on an empty cell.
134	  - Given food directly ahead, when the snake moves straight, then its length goes up by 1, the move's plain reward is +1, and one new food appears on a cell not covered by the snake.
135	- **SNAKE-04** Moving into a wall or into the snake's own body ends the game with a reward of −1.
136	  - Given the head next to a wall, when the snake moves into the wall, then the game ends and the move's reward is −1.
137	  - Given the head next to a body cell that will still be occupied after the move, when the snake moves into it, then the game ends and the move's reward is −1.
138	- **SNAKE-05** Every move that neither eats nor kills has a plain reward of 0.
139	  - Given a move into an empty cell, when it is made, then its plain reward is 0.
140	- **SNAKE-06** At every move the agent sees exactly 11 yes/no facts: danger straight, danger left, danger right; heading up, down, left, right; food is up, down, left, right of the head.
141	  - Given the head next to the top wall while heading up, when the facts are read, then "danger straight" is yes and "heading up" is yes.
142	  - Given food above and to the left of the head, when the facts are read, then "food is up" and "food is left" are yes and "food is down" and "food is right" are no.
143	  - Given a cell occupied by the body or a wall next to the head on its left, when the facts are read, then "danger left" is yes.
144	- **SNAKE-07** A game ends after 100 moves in a row without eating.
145	  - Given a snake that has gone 100 moves since its last food (or since the start), when the 100th move is made without eating, then the game ends and that move's plain reward is 0.
146	- **SNAKE-08** The same game seed and the same moves always give the same game.
147	  - Given a game seed and a list of moves, when the game is played twice, then every board, food position, reward and ending is identical.
148	
149	**Edge cases & errors**
150	- The head moves into the cell the tail is leaving on that move → allowed; the game goes on.
151	- The snake fills every cell, so no food can be placed → the game ends as a full-board finish, with no −1.
152	- The food appears directly ahead of a turning snake → nothing special; food is only eaten when the head enters its cell.
153	
154	### Baselines (`BASE`)
155	**Serves:** Goal 2
156	**Stage:** S1
157	**Behavior:** Two non-learning players set the bar every learner must clear: one picks moves at random, the other follows a simple rule. Both play the same test games as the learners.
158	
159	**Requirements**
160	- **BASE-01** The random player picks each move uniformly at random from the 3 moves.
161	  - Given 30,000 random-player moves, when the share of each move is counted, then each is between 32% and 35%.
162	- **BASE-02** The scripted bot moves toward the food, never making a move that kills it immediately when a safe move exists.
163	  - Given food to the left and the left cell free, when the bot moves, then it turns left.
164	  - Given food straight ahead and a wall straight ahead with the right cell free, when the bot moves, then it turns right.
165	  - Given several safe moves equally close to the food, when the bot moves, then it prefers straight, then left, then right.
166	- **BASE-03** When every move kills it, the scripted bot goes straight.
167	  - Given danger straight, left and right, when the bot moves, then it goes straight and the game ends.
168	
169	**Edge cases & errors**
170	- No safe move gets closer to the food → the bot takes the safe move that leaves it closest to the food, using the same preference order on ties.
171	
172	### Table-based Q-learning (`TAB`)
173	**Serves:** Goal 1
174	**Stage:** S1
175	**Behavior:** The first learner keeps a table with a score for each of the 3 moves in every combination of the 11 facts, and improves the table after every move from the reward and the best score of the next situation.
176	
177	**Requirements**
178	- **TAB-01** The table learner updates the score of the move it just made from the reward plus the discounted best score of the situation it reached (a one-step Q-learning update), after every move.
179	  - Given a known table, situation, move, reward and next situation, when one update is applied, then the new score equals the hand-computed Q-learning update for the run's learning rate and discount.
180	  - Given a move that ended the game, when the update is applied, then the next situation contributes nothing.
181	- **TAB-02** While training, the table learner sometimes picks a random move instead of its best one, at a rate that falls over the run from a starting rate to a floor saved with the run's settings.
182	  - Given a run's exploration settings, when the rate is read at the start, the middle and the end of training, then it matches the saved schedule at each point.
183	- **TAB-03** During test games the table learner always picks its highest-scored move.
184	  - Given a trained table, when a test game is played twice from the same seed, then both games are identical.
185	- **TAB-04** The learning update is written in the project; no ready-made learning algorithm is used.
186	  - Given the trained table learner, when its learning steps are traced, then each one is code written in the project.
187	
188	**Edge cases & errors**
189	- A situation never seen in training comes up in a test game → all 3 moves score equal and the learner picks by the order straight, left, right.
190	
191	### DQN ladder (`DQN`)
192	**Serves:** Goal 1, Goal 3
193	**Stage:** S1
194	**Behavior:** The second learner replaces the table with a small learned function that scores the 3 moves from the 11 facts. It is built in four rungs, each adding one piece to the one before, so each piece's effect can be measured on its own:
195	1. Plain: learns from each move as it happens.
196	2. + Replay buffer: learns from random samples of stored past moves.
197	3. + Target network: its learning targets come from a frozen copy of itself, refreshed at a fixed interval.
198	4. + Double DQN: the learner picks the best next move, and the frozen copy scores it.
199	
200	**Requirements**
201	- **DQN-01** The plain rung learns from each move right after it is made, using that move's reward plus the discounted best score of the next situation as its target.
202	  - Given a known function, move, reward and next situation, when one update is applied, then the target equals the hand-computed value and the function's score for that move moves toward it.
203	- **DQN-02** The replay-buffer rung stores past moves and learns from batches drawn at random from that store.
204	  - Given a store of past moves and a seed, when a batch is drawn, then every move in it comes from the store and the same seed draws the same batch.
205	  - Given a store at its saved capacity, when a new move is added, then the oldest move is dropped.
206	- **DQN-03** The target-network rung computes its targets from a frozen copy of the learner, refreshed every fixed number of updates saved with the run's settings.
207	  - Given the refresh interval, when updates run between two refreshes, then the copy does not change; when the interval is reached, the copy equals the learner.
208	- **DQN-04** The Double DQN rung chooses the next situation's best move with the learner, and scores that move with the frozen copy.
209	  - Given a learner and a copy that disagree on the next situation's best move, when the target is computed, then it uses the copy's score for the learner's chosen move.
210	- **DQN-05** Each rung differs from the rung before only by the piece it adds; every other setting is the same.
211	  - Given the saved settings of two neighbouring rungs, when they are compared, then the only differences are the added piece and its own settings.
212	- **DQN-06** While training, each rung explores with the same falling random-move rate as TAB-02; during test games it always picks its highest-scored move.
213	  - Given a trained rung, when a test game is played twice from the same seed, then both games are identical.
214	- **DQN-07** The learning updates of every rung are written in the project; no ready-made learning algorithm is used.
215	  - Given any trained rung, when its learning steps are traced, then each one is code written in the project.
216	
217	**Edge cases & errors**
218	- A move that ended the game is learned from → the next situation contributes nothing to its target.
219	- The replay-buffer store holds fewer moves than one batch → learning waits until it holds a full batch.
220	- Scores grow without bound (training diverges) → the run keeps going and saves its curve; the comparison reports the result, and the divergence is visible in the curve.
221	
222	### Reward shaping (`SHAPE`)
223	**Serves:** Goal 1, Goal 3
224	**Stage:** S1
225	**Behavior:** A second reward adds a small nudge toward the food on top of the plain reward, so the learner can be trained on either and the two compared.
226	
227	**Requirements**
228	- **SHAPE-01** The shaped reward is the plain reward plus 0.1 for a move that brings the head closer to the food and minus 0.1 for a move that takes it further away, measured in grid steps to the food that was on the board before the move.
229	  - Given a move that cuts the distance to the food from 5 to 4, when it is made, then the shaped reward is +0.1.
230	  - Given a move that raises the distance from 4 to 5, when it is made, then the shaped reward is −0.1.
231	  - Given a move that eats the food, when it is made, then the shaped reward is +1.1.
232	- **SHAPE-02** A move that ends the game by collision has a shaped reward of −1, with no nudge.
233	  - Given a move into a wall, when it is made, then the shaped reward is −1.
234	- **SHAPE-03** Every run uses either the plain or the shaped reward for training, and saves which.
235	  - Given a finished run, when its saved settings are read, then they name its reward.
236	- **SHAPE-04** Test scores never use the shaped reward; they always count food eaten.
237	  - Given the same agent tested once after plain training and once after shaped training, when the scores are read, then both are food eaten per game.
238	- **SHAPE-05** The plain-versus-shaped comparison trains the Double DQN rung on each reward, with every other setting the same.
239	  - Given the plain and shaped runs of that comparison, when their saved settings are compared, then the only difference is the reward.
240	
241	### Training runs (`RUN`)
242	**Serves:** Goal 3, Goal 5
243	**Stage:** S1
244	**Behavior:** One training run trains one learner, with one reward, from one seed. The learner starts the run with one action, watches its progress, and afterwards finds everything the run produced saved together, enough to recreate it.
245	
246	**Requirements**
247	- **RUN-01** A training run trains one learner (the table learner or one DQN rung) with one reward from one training seed.
248	  - Given a learner, a reward and a seed, when a run is started with one action, then it trains that learner with that reward and seed and nothing else.
249	- **RUN-02** Each run saves its settings, seed, learning curve, final agent and test games.
250	  - Given a finished run, when its saved evidence is opened, then all five are there.
251	- **RUN-03** Rerunning from a run's saved settings and seed gives the same result.
252	  - Given a finished run, when it is run again on the same laptop from its saved settings and seed, then the test score at every curve point is identical.
253	- **RUN-04** While a run trains, it shows the moves trained so far, the latest test score and the time elapsed.
254	  - Given a run in progress, when a curve point is reached, then the display updates all three.
255	- **RUN-05** A run never overwrites another run's evidence.
256	  - Given two runs with the same learner, reward and seed, when both finish, then both sets of evidence are kept.
257	- **RUN-06** A run that stops before it finishes is marked incomplete and is left out of every comparison.
258	  - Given a run stopped by hand partway through, when comparisons are made, then it is listed as incomplete and its numbers are not used.
259	- **RUN-07** A run still training at 60 minutes stops, saves what it has, and is marked over the time limit.
260	  - Given a run that reaches 60 minutes, when the limit passes, then training stops, its evidence so far is saved, it is marked over the time limit, and it is left out of every comparison.
261	- **RUN-08** Training, testing, saving evidence and replay work for a second environment without changes to them.
262	  - Given a minimal second environment used only for this check, when it is trained, tested and replayed, then none of the training, testing, saving or replay behavior had to change.
263	
264	**Edge cases & errors**
265	- A run is started with a learner or reward that doesn't exist → it does not start, and the message lists the valid choices.
266	- The disk fills while saving → the run is marked incomplete and says which evidence is missing.

268	### Evaluation & comparison (`EVAL`)
269	**Serves:** Goal 2, Goal 3
270	**Stage:** S1
271	**Behavior:** Every learner and baseline is scored on the same 100 held-out test games. Learning curves show progress against the baselines. Comparison reports say, from 5 training seeds per learner, whether each learner beats the baselines, and what each added piece changed. Each result carries a written explanation, so a tie counts.
272	
273	**Requirements**
274	- **EVAL-01** Every agent is scored on the same 100 test games, each started from a fixed test seed that is never used in training.
275	  - Given any two agents, when they are tested, then they play games from the same 100 test seeds.
276	  - Given any training run, when its game seeds are compared with the test seeds, then none match.
277	- **EVAL-02** An agent's test score is the mean food eaten per game over the 100 test games.
278	  - Given 100 test games with known food eaten, when the score is computed, then it equals their mean.
279	- **EVAL-03** Each run's learning curve is its test score against moves trained, at 20 evenly spaced points, with the random player's and the scripted bot's scores drawn as lines on the same chart; the chart follows the `dataviz` skill.
280	  - Given a finished run, when its curve is opened, then it shows 20 test scores in order of moves trained, plus both baseline lines.
281	  - Given the 5 seeds of one learner, when their combined curve is opened, then it shows the mean across seeds at each point with the spread across seeds.
282	- **EVAL-04** Each learner's final agent is compared with each baseline using the `null-hypothesis-testing` skill. It is given the 100 test-game scores of each of the learner's 5 seed runs, and the baseline's scores on the same 100 games. The learner beats the baseline when its score is higher and the difference is significant at 5% after correcting for the number of comparisons in the report; it ties when the difference is not significant; otherwise it loses.
283	  - Given 5 complete seed runs of a learner, when the comparison is made, then the report states beats, ties or loses against each baseline, with the test's result.
284	  - Given fewer than 5 complete seed runs, when the comparison is requested, then it is not made, and the report lists the missing seeds.
285	- **EVAL-05** Each added piece gets a before-and-after comparison with the rung below it, made the same way as EVAL-04: table learner → plain DQN, plain → + replay buffer, + replay buffer → + target network, + target network → + Double DQN, and plain reward → shaped reward. Every outcome counts: better, worse, or no difference.
286	  - Given 5 complete seed runs of both rungs, when the comparison is made, then the report states better, worse or no difference, with the test's result and both rungs' combined curves on one chart.
287	- **EVAL-06** Every comparison result holds a written explanation; a result with no explanation is shown as unexplained.
288	  - Given a comparison result with an empty explanation, when the report is opened, then that result is marked unexplained.
289	  - Given a tie or a no-difference result with an explanation, when the report is opened, then it is marked explained.
290	- **EVAL-07** Snake is done when the Double DQN agent beats the random player, beats or ties the scripted bot, every comparison in EVAL-04 and EVAL-05 has a result, and every tie and no-difference result is explained.
291	  - Given a Double DQN agent that beats both baselines and all comparisons made and explained, when the done check runs, then it reports done.
292	  - Given a Double DQN agent that ties the scripted bot with the tie explained, when the done check runs, then it reports done.
293	  - Given a tie with the scripted bot left unexplained, when the done check runs, then it reports not done and names the missing explanation.
294	  - Given a Double DQN agent that ties or loses to the random player, when the done check runs, then it reports not done.
295	
296	**Edge cases & errors**
297	- Every seed of a learner scores exactly the same as a baseline → the result is a tie.
298	- A run marked incomplete or over the time limit is among a learner's runs → it is left out, and the comparison waits for 5 complete runs.

301	**Serves:** Goal 3, Goal 4, Goal 5
302	**Stage:** S1
303	**Behavior:** The learner picks a saved agent and one of its test games, or a fresh game seed, and watches it play move by move. Next to the board, the viewer shows how the agent scored each of its 3 moves, so its choices can be explained.

306	- **REPLAY-01** Any saved test game of any saved agent, the baselines included, can be watched as a replay.

316	  - Given a speed of 5 moves per second, when it plays for 10 seconds, then it advances 50 moves (±2).
317	- **REPLAY-06** A replay of a saved test game is identical to the game that was scored.
318	  - Given a saved test game, when it is replayed, then every board, move and food count matches the saved game.
319	- **REPLAY-07** A saved agent can play and be watched on a fresh game from any seed chosen at the time.
320	  - Given a saved agent and a new seed, when the game is watched twice, then both games are identical.

323	- The chosen agent or game can't be found or read → the viewer opens nothing and names the missing item.
324	- A game ends on its first move → the replay shows that one move and the ending.

# RL Lab — Architecture

**Status:** Draft · **Shape:** Single package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
One Python package, `rllab`, run from the command line. A training run builds a Snake environment and one learner (from the registry), plays games from seeds derived from the run seed, and feeds every move to the learner. At each of 20 curve points it pauses training to play the 100 reserved test games greedily, then writes the point to the run's folder. When the run finishes it saves the agent and its test games and marks the run's status last. Comparisons read only complete runs and hand the per-game scores to the `null-hypothesis-testing` skill. The replay viewer rebuilds any saved game by stepping the environment through its saved moves. Training, testing, storage and replay see only the `core` protocols, so a second environment plugs in through `Env` (AD-04).

```mermaid
flowchart LR
  cli --> train & compare & replay
  train --> registry & evaluate & store
  registry --> snake & baselines & tabular & dqn
  replay --> registry & evaluate & store
  compare --> store
  snake & baselines & tabular & dqn & evaluate & store --> core
```

## Data
- **Experience (DATA-01):** every game is a `snake.SnakeEnv` started from a seed. Seeds 0–99 are the test seeds (`evaluate.test_seeds`); training game seeds are drawn from the run seed's generator in `[1_000, 2^31)`, so they never meet a test seed (AD-05).
- **Run evidence (RUN-02):** `runs/<learner>/<reward>/seed-<n>/<UTC timestamp>-<short id>/` holds `settings.json`, `curve.json`, `agent.npz` (table) or `agent.pt` (DQN), `test_games.jsonl` (seed, moves, per-move scores, food count per move, ending) and `status.json`, written last (AD-06). Baselines are stored the same way under `runs/random/` and `runs/scripted/`, with no curve.
- **Explanations (EVAL-06):** the learner writes one Markdown file per comparison, `reports/explanations/<comparison id>.md`; `compare` reads them, never writes them.
- **Reports (EVAL-03–EVAL-05):** `reports/report.md` and its PNG charts, rebuilt from the runs on every `rllab compare`.

## Cross-cutting concerns
- **Reproducibility (RUN-03, SNAKE-08):** every random draw comes from a `np.random.Generator` or `torch.Generator` derived from the run seed; PyTorch runs on CPU with one thread and deterministic algorithms (AD-05).
- **Time (QR-01, RUN-07):** `train` checks the wall clock after every move and at every test game; at 60 minutes it stops and saves what it has. Elapsed seconds are saved with each curve point.
- **Errors:** an unknown learner, reward or environment raises `UnknownName` with the valid choices; a disk error while saving marks the run incomplete with the missing evidence listed; Ctrl-C marks it incomplete.
- **Testing:** pytest. RUN-08 is checked with a test-only second environment, a tiny grid walk in `tests/`, trained, tested, stored and replayed through the same code.

## Decisions
### AD-01: Python 3.12 in one package, `rllab`
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** One learner, one laptop, PyTorch basics already known (brief). S1 needs one install and no separate deployments.
- **Decision:** Python 3.12 managed with uv; a single package `rllab` with one folder per component and one `rllab` command.
- **Alternatives:** Python 3.13: PyTorch and pygame-ce wheels for Apple Silicon lag on new versions. Several packages (core, envs, agents): no separate install or deployment boundary yet (AD-04).
- **Consequences:** `requires-python = ">=3.12,<3.13"`. `core` is the seam that would become its own package if environments multiply.

### AD-02: Hand-written learners on PyTorch, CPU only
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-07: the user chose "(a) Write DQN myself in NumPy/PyTorch". TAB-04 and DQN-07 forbid ready-made learning algorithms. QR-02: an Apple Silicon laptop, no NVIDIA card. The networks are tiny (11 inputs, 3 outputs).
- **Decision:** The table learner is NumPy. Each DQN rung is a small `torch.nn` MLP (11 → 64 → 64 → 3) whose targets, loss, batch sampling, target-network refresh and Double DQN selection are written in `dqn`. PyTorch supplies only tensors, autograd and the Adam optimizer. No RL library is imported anywhere. Everything runs on the CPU; the Apple GPU (MPS) is not used.
- **Alternatives:** NumPy with hand-written backpropagation: you'd learn the gradient maths too, but the backward pass, not the RL, becomes the work. Stable-Baselines3 or similar: ruled out by DQN-07 and UR-07. MPS: slower than the CPU for a 3-output network, and nondeterministic.
- **Consequences:** Autograd hides the gradients but not the learning rule. Import-linter forbids RL libraries.

### AD-03: One DQN learner, the rung a setting
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** dqn
- **Context:** UR-06: Snake is "Good first env for DQN-style value learning". DQN-01–DQN-04 build four rungs. DQN-05 and SHAPE-05 require neighbouring rungs to differ only by the added piece.
- **Decision:** `dqn.DQNAgent` takes a `DQNSettings` whose `rung` is `plain`, `replay`, `target` or `double`. Each rung turns on exactly one more piece: a replay store sampled in batches, a frozen copy refreshed every `target_every` updates, Double DQN target selection. The plain rung trains on each move as a batch of one. All other fields share defaults, and `compare.settings_diff` checks that each pair differs only where it should.
- **Alternatives:** Four separate classes: duplicated code, so one rung's change can leak into another unseen. A single class with independent on/off flags: allows combinations the ladder never compares.
- **Consequences:** A rung's added piece is one code branch, easy to read and test against its hand-computed target. Later variants (prioritised replay, say) add a rung value.

### AD-04: A shared core shaped by Snake
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-16: "a shared core reused across environments: env interface, training loop, logging, replay viewer". UR-22: "build it through Snake, shaped by Snake's needs, and adjust it later". RUN-08 requires a second environment to need no changes to training, testing, saving or replay. The brief rules out a general framework built ahead of need.
- **Decision:** Environments implement `core.Env`; agents implement `core.Agent`, and learners `core.Learner`. `train`, `evaluate`, `store` and `replay` import only `core` (and each other), never `snake`; the environment comes from `registry`. `core` holds only what Snake uses: discrete actions, a fixed-length observation vector, a `points` count for test scores and a grid `Frame` for drawing. A test-only grid walk proves RUN-08.
- **Alternatives:** Snake-specific code first, extracted later: RUN-08 would fail in S1. A Gymnasium-style interface: adds spaces, wrappers and render modes that Snake doesn't need, and Gymnasium itself brings dependencies the lab doesn't use.
- **Consequences:** A new environment that needs continuous actions or image observations changes `core`, as UR-22 expects. Import-linter keeps `snake` out of the shared components.

### AD-05: Seeds, test-seed reservation and CPU determinism
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** RUN-03 needs identical curves on a rerun; SNAKE-08, TAB-03, DQN-06 and REPLAY-07 need repeatable games; EVAL-01 needs test seeds never used in training.
- **Decision:** A run seed builds a `np.random.SeedSequence`, spawned into separate generators for training game seeds, exploration, batch sampling and network initialisation (a `torch.Generator`). Test seeds are 0–99; training game seeds are drawn from `[1_000, 2^31)`. Torch runs with `torch.set_num_threads(1)` and `torch.use_deterministic_algorithms(True)`. Each Snake game owns its own generator from its game seed, so food placement depends only on the seed and the moves.
- **Alternatives:** A global seed (`np.random.seed`): any new random call shifts every later draw. Several threads: faster on big networks, but the reduction order varies between runs.
- **Consequences:** Results reproduce on the same laptop and library versions, not across machines; `settings.json` records the versions. One thread stays fast enough for these networks (Risks).

### AD-06: One folder per run, status written last
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** RUN-02 lists the evidence; RUN-05 forbids overwriting; RUN-06 and RUN-07 mark runs incomplete or over time and keep them out of comparisons; the disk-full edge case must name the missing evidence.
- **Decision:** `store.begin_run` creates a new folder whose name ends with a UTC timestamp and a short random id, and writes `status.json` as `running` first. Curve points are appended as they come. `finish` writes the agent and test games, then rewrites `status.json` with the final status and any missing files. Every file is written to a temporary name and renamed. `list_runs` treats `running` with no live process as incomplete.
- **Alternatives:** SQLite: queryable, but a run's evidence is no longer a folder you can open and read. MLflow or Weights & Biases: extra servers or accounts for one learner on one laptop.
- **Consequences:** Comparisons scan folders; for 30-odd runs that's instant. Evidence is plain JSON you can open; agents are `.npz` or `.pt`.

### AD-07: Replay in a pygame window, rebuilt from saved moves
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** replay
- **Context:** REPLAY-02–REPLAY-05 need a board, move scores, pause, step and 1–30 moves per second. REPLAY-06 needs the replay to match the scored game. Web deployment is out of scope.
- **Decision:** `replay` rebuilds each frame by resetting the environment to the saved seed and stepping through the saved moves. It raises `ReplayMismatch` if a food count or ending differs from the saved game. It then draws `core.Frame`s in a pygame-ce window: space pauses and resumes, the right arrow steps, the up and down arrows change speed. Move scores show as three bars with the chosen move marked, or "n/a" for baselines.
- **Alternatives:** A Matplotlib animation: its widgets can't reliably hold 30 frames a second with controls. A self-contained HTML player: needs a JS front end to maintain, closer to the web work the brief leaves out. A terminal (curses) view: no room for score bars on a 10×10 board.
- **Consequences:** Saved games are small (moves only). The viewer draws any grid `Frame`, so the second environment replays unchanged (RUN-08).

### AD-08: Comparisons through the null-hypothesis-testing skill; explanations are the learner's files
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** compare
- **Context:** EVAL-04 and EVAL-05 require the `null-hypothesis-testing` skill on 5 seeds × 100 test games, at 5% after correction for the number of comparisons in the report. EVAL-06 and EVAL-07 need a written explanation for each result.
- **Decision:** Every comparison step in `compare` hands the skill a `compare.ComparisonInput` (both sides' per-seed, per-game scores on the same test seeds, alpha 0.05 and the report's comparison count). The skill chooses the test, the correction and the null distribution; `compare` maps its verdict to beats/ties/loses or better/worse/no difference. Explanations are Markdown files the learner writes under `reports/explanations/`; an empty or missing file is unexplained.
- **Alternatives:** A fixed Welch t-test in code: replaces the procedure the skill owns. Explanations stored in run folders: they belong to comparisons, not runs.
- **Consequences:** The test can change without touching the report. A comparison waits until both sides have 5 complete runs (EVAL-04).

### AD-09: Learning curves as Matplotlib PNGs following the dataviz skill
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** compare
- **Context:** EVAL-03 asks for the `dataviz` skill on each chart; EVAL-05 puts two rungs' combined curves on one chart. The report is read locally.
- **Decision:** `compare.plot_curves` draws each chart with Matplotlib to PNG, palette and marks taken from the `dataviz` skill: mean across seeds as a line, the seed range as a band, the two baselines as horizontal reference lines.
- **Alternatives:** Plotly HTML: interactive, but a heavier dependency for static report charts.
- **Consequences:** The charts are images in `reports/`; the report links them.

## Risks and open questions
- **Your decision (AD-02):** PyTorch autograd for the DQN, or NumPy with hand-written backpropagation? I recommend PyTorch: it keeps your effort on the learning rule. Default: PyTorch.
- One CPU thread might not fit a DQN run plus 20 × 100 test games inside 60 minutes (QR-01). Mitigation: the first DQN task times 10,000 moves and one round of test games, and the step budget is set from that. Test games can be batched per move if needed.
- The table learner sees at most 2^11 situations but only a few hundred occur; it may plateau well below the scripted bot. That is a result to explain (EVAL-06), not a defect.
- Determinism (RUN-03) holds only on the same laptop and library versions. `settings.json` records them, and the rerun check compares like with like.
