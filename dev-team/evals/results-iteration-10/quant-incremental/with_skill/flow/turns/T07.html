# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

# Contracts

Read when writing or changing a `contract.md`.

Write `docs/packages/<pkg>/contract.md`: the provider's promise to its consumers. Consumers read only this page, so it stands alone.

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). The ID survives Grow, because the component id becomes the package id.
- **One symbol per heading.** Never `### train.train / train.train_seeds: …` or `### baselines.MajorityClass / LogisticBaseline: …`, however alike the symbols are: dt resolves `Read:` IDs and `dt context` packets only from a symbol's own heading. `dt lint` errors on these (`contract-heading`).
- **Function sections:** the signature in the project's language, then **Invariants** (shapes, ranges, guarantees), **Errors** (what fails and how it's reported), and **Used by** (consuming components or packages, plus `PL-NN` IDs once those pipelines exist).
- **Type sections.** Every type one step hands to another, and every type a public signature or method takes or returns, is its own section with the title `type`: `### profile.Profile: type`. An object one call returns and another takes back (`store.StagedRun`, from `begin` into `commit`) is a `typing.Protocol` of its methods with a replay double case, never a code comment. The first line is its shape as code: a frozen dataclass's fields, a `typing.Protocol`, or a pandera schema's columns for a dataframe. Then **Invariants** and **Used by**. `pipeline-design` names these types in every step's `In → Out`; the build's interface task writes them, as code, into the owner's `types.py`. Freeze only what crosses: a helper's or a private function's types stay out.
- **Every type a field annotation uses is defined:** its own `type` section, a typed inline definition (`weather: Weather(temp_c: float, issued: datetime)`), or a section whose first line mirrors another (`mirrors data.Readings, field for field`). Read when making a technical decision, or when one changes or retires an Accepted decision.

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. A reversed decision collapses to its heading with the title struck, plus one status line: `**Status:** Superseded by AD-NN · date — reason`. A daily US equity dataset of S&P 500 members since 1998 with an as-of loader. Given any past date, the loader returns the stocks that were members on that date and their total returns, using only what was known then. Every download, clean, validate and store step can be run on demand. A validation layer checks the data against an independent source and flags every disagreement, and a browser app shows prices, corporate actions, source differences, universe size and live run progress. See the [brief](brief.md) for why.

| User | What they need to do |
|---|---|
| Researcher (the owner, sole user) | Refresh the data, ask for the universe and total returns as of any date since 1998, run validation, review and resolve flagged differences, inspect any stock visually, watch runs progress |

## Scope
**In scope:** Universe as of a date, Total returns as of a date, Data refresh, Cross-check and findings, Exploratory analysis, Data-quality app, Live run progress.

**Out of scope:**

## Features

### Universe as of a date (`UNIV`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** The researcher gives a date from 1998-01-02 onward and gets the list of stocks that were S&P 500 members on that date, including companies that later left the index, were acquired or went bankrupt. Each stock is identified by the company, not by its current ticker, and carries the ticker it traded under on that date.

**Requirements**
- **UNIV-01** For a given date, the system returns every stock that was an S&P 500 member during that date, by the date each index change took effect.
  - Given an index addition announced on day A and effective on day E > A, when the universe is requested for any day from A to E − 1, then the stock is not in it; when requested for day E, then it is.
  - Given an index removal effective on day R, when the universe is requested for day R − 1, then the stock is in it; for day R, then it is not.
- **UNIV-02** The universe for a date includes members that later left the index or stopped trading.
  - Given 2008-06-02, when the universe is requested, then Lehman Brothers, Bear Stearns, Countrywide, Merrill Lynch, Wachovia and Anheuser-Busch are all in it.
- **UNIV-03** Each stock has a permanent identifier for the company, which is unchanged across ticker changes.
  - Given a company that changed ticker, when its membership is requested for dates before and after the change, then both carry the same identifier.
- **UNIV-04** Each returned member carries the ticker it traded under on the requested date.
  - Given 2005-06-01, when the universe is requested, then the entry for Anheuser-Busch shows ticker BUD and the company is Anheuser-Busch, not today's holder of that ticker.
- **UNIV-05** The system returns the number of members for every trading day in a date range.
  - Given 1998-01-02 to the latest loaded day, when universe sizes are requested, then every trading day has a count, and each count equals the length of that day's universe list.

**Edge cases & errors**
- Date before 1998-01-02 → an error that names the earliest supported date; no partial list.
- Date after the latest loaded trading day → an error that names the latest loaded day.
- Weekend or market holiday → the universe for the previous trading day, with that day stated in the result.
- A day's member count outside 490–510 → the count is still returned, and a finding is raised (CHECK).

### Total returns as of a date (`RET`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** The researcher gives an as-of date and a set of stocks (usually that date's universe) and gets daily total-return series, including dividends and adjusted for splits, through the as-of date. Nothing published after the as-of date affects the result.

**Requirements**
- **RET-01** For every stock that was investable on any date since 1998, the system returns its daily total-return series between two given dates.
  - Given any date D since 1998-01-02 and the universe for D, when total returns from D to D + 20 trading days are requested, then a series is returned for every member, including members that stopped trading in that window.
- **RET-02** A daily total return combines the price change and any cash dividend going ex on that day.
  - Given a stock with a $0.50 dividend going ex on day T, a close of $50.00 on T − 1 and a close of $49.75 on T, when returns are requested, then the return for T is (49.75 + 0.50) / 50.00 − 1 = +0.50%.
- **RET-03** Daily total returns are unaffected by stock splits.
  - Given a 2-for-1 split effective on day T with closes of $100.00 on T − 1 and $50.50 on T, when returns are requested, then the return for T is +1.00%.
- **RET-04** Results requested as of date D use no information published after D.
  - Given a split or dividend that goes ex after D, when returns or prices are requested as of D, then the values up to D are identical to those produced before that event was loaded.
- **RET-05** Price levels are available unadjusted, or adjusted only for splits and dividends that went ex on or before the as-of date.
  - Given a 2-for-1 split on day S > D, when adjusted prices are requested as of D, then they equal the unadjusted prices for every day up to D.
- **RET-06** A stock's return series runs through its last trading day, including the return on that last day.
  - Given Lehman Brothers, when returns through 2008-09-30 are requested, then the return for 2008-09-15 is present and below −90%.
  - Given a company acquired for cash, when returns are requested, then the return on its last trading day is present and the series ends that day.
- **RET-07** Every returned series states whether each day is a trading day with a price, or a gap.
  - Given a trading halt with no close on day T, when returns are requested, then day T is marked as a gap and has no invented return.

**Edge cases & errors**
- Stock not a member on the as-of date → its series is still returned if asked for by identifier, with a note that it was not a member then.
- Requested range starts before a stock's first trading day or ends after its last → the series covers only the trading days, and the result says where it starts and ends.
- A day's return below −95% or above +100% → the value is returned unchanged, and a finding is raised (CHECK) unless one is already explained.

### Data refresh (`SYNC`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** The researcher starts a refresh. The system downloads what is new from the primary source (the existing Sharadar subscription), cleans it, validates it and stores it, so the data runs through the last completed trading day. The first refresh builds the full history from 1998.

**Requirements**
- **SYNC-01** A refresh downloads data from the primary source.
  - Given an empty store, when a refresh is started, then afterwards prices, corporate actions, company identities and index membership are stored for every S&P 500 member from 1998-01-02 to the last completed trading day.
- **SYNC-02** A refresh fetches only data newer than what is already stored.
  - Given data stored through day T, when a refresh is started on day T + 1 after the close, then only day T + 1 and any corrections the source issued since the last refresh are downloaded.
- **SYNC-03** A refresh cleans the data before it is stored.
  - Given a downloaded row with a duplicate (stock, date), when the refresh runs, then one row is stored and the duplicate is reported in the run summary.
- **SYNC-04** A refresh ends with a validation run (CHECK-01), and its results go to the run summary.
  - Given a completed refresh, when its summary is viewed, then it lists the number of rows added, rows changed, and new findings.
- **SYNC-05** A refresh that fails leaves the stored data as it was before the refresh started.
  - Given a refresh interrupted after half its downloads, when the universe or returns are requested, then the results are identical to those before the refresh.
- **SYNC-06** A refresh started while another is running is refused.
  - Given a refresh in progress, when a second is started, then it is refused with a message naming the running one.
- **SYNC-07** Each run of a refresh or validation is started on demand, from the command line or from the app.
  - Given the app open, when the researcher starts a refresh there, then it runs exactly as one started from the command line.

**Edge cases & errors**
- Primary source unreachable or credentials rejected → the refresh stops, stores nothing, and states the reason.
- The source revises a past value → the revision is stored, the earlier value is kept with the date it was replaced, and the run summary lists it.
- No new trading day since the last refresh → the refresh completes with zero rows added.

**Serves:** Goal 2
**Stage:** S1
**Behavior:** A validation run compares the data with an independent source (Yahoo Finance) for a sample of members, and runs internal checks on stocks that source doesn't carry. Every disagreement becomes a finding. The researcher marks each finding explained (with a reason) or accepted; the data itself is never edited to hide a finding.

**Requirements**

  - Given a validation run, when it finishes, then it has compared exactly 100 stocks (or all available, if fewer), and every calendar year from 1998 to today has at least 2 stocks that were members in that year.
- **CHECK-02** For each sampled stock, the run also checks every split and special dividend that stock had.
  - Given a sampled stock with 3 splits and 1 special dividend since 1998, when the run finishes, then all 4 events have been compared.
- **CHECK-03** A full validation run, on demand, checks every member the independent source carries.
  - Given a full validation run, when it finishes, then every member the independent source carries has been compared.
- **CHECK-04** Splits agree only when the date and the ratio match exactly.
  - Given a 3-for-2 split on one source and a 2-for-1 split on the same date on the other, when compared, then a finding is raised.
- **CHECK-05** Dividends agree only when the ex-date matches and the amount is within $0.001.
  - Given amounts of $0.2500 and $0.2509 on the same ex-date, when compared, then they agree; given $0.2500 and $0.2515, then a finding is raised.
- **CHECK-06** Daily total returns agree when they are within 5 basis points (0.05 percentage points) of each other.
  - Given returns of +1.20% and +1.24% for the same stock and day, when compared, then they agree; given +1.20% and +1.26%, then a finding is raised.
- **CHECK-07** Unadjusted closes agree when they are within 0.5% of each other.
  - Given closes of $40.00 and $40.18, when compared, then they agree; given $40.00 and $40.25, then a finding is raised.
- **CHECK-08** A stock the independent source doesn't carry is checked for missing trading days before its last trading day.
  - Given a delisted stock with no price on a day when the exchange was open and the stock was not halted, when checked, then a finding is raised for that day.
- **CHECK-09** A stock acquired for a known cash price is checked for a last close consistent with the deal.
  - Given a cash acquisition at $70.00 a share and a last close of $69.95, when checked, then it passes; given a last close more than 2% from the deal price, then a finding is raised.
- **CHECK-10** A stock's index membership is checked to end no later than its last trading day.
  - Given a stock whose membership ends after its last trading day, when checked, then a finding is raised.
- **CHECK-11** Findings from internal checks are listed and resolved in the same way as disagreements with the independent source.
  - Given a CHECK-08 finding and a CHECK-06 finding, when findings are listed, then both appear in one list with the same fields and the same resolve actions.
- **CHECK-12** Each finding records the stock, the date(s), the check that raised it, both values, and the difference.
  - Given any finding, when viewed, then all five are shown.
- **CHECK-13** The researcher resolves a finding by marking it explained, with a written reason, or accepted.
  - Given an open finding, when marked explained with no reason, then it is refused; with a reason, then its status becomes explained and the reason and date are kept.
- **CHECK-14** A resolved finding stays resolved in later runs while both values are unchanged.
  - Given an explained finding, when the next run finds the same difference, then no new finding is raised; when either value has changed, then the finding is reopened.

### AD-01: Python 3.12
**Status:** Proposed · **Date:** 2026-10-14 · **Scope:** system
- **Context:** ML libraries and the user's existing tooling are Python.
- **Decision:** Python 3.12.
- **Alternatives:** 3.13 — some ML libraries lag on new versions.
- **Consequences:** Pin `requires-python = ">=3.12,<3.13"` until the libraries catch up.

### AD-02: PyTorch for models
**Status:** Proposed · **Date:** 2026-10-14 · **Scope:** system
- **Context:** Models start with logistic regression and move to a small CNN; we want standard layers and autograd without adapters.
- **Decision:** Every model is a `torch.nn.Module` behind `core.Model`.
- **Alternatives:** NumPy only — simpler, but the CNN's backward pass becomes the project. JAX — capable, less CPU tooling on a laptop.
- **Consequences:** Batches must be fixed-shape tensors. Multi-worker data loading comes for free.

### AD-03: Batched NumPy augmentation, not per-image PIL calls
**Status:** Proposed · **Date:** 2026-10-14 · **Scope:** system
- **Context:** QR-01 needs ≥ 500 images/second. Images are a fixed 128×128; no learned augmentation.
- **Decision:** Each batch is augmented as array math on a preallocated array.
- **Alternatives:** Per-image PIL transforms — richer, far too slow and partly out of scope (spec Out of scope: learned augmentation).
- **Consequences:** Augmentations are limited to what array math does well. Fine for a proof of concept; revisit if accuracy depends on it.

**Status:** Proposed · **Date:** 2026-10-14 · **Scope:** data

- **Alternatives:** Request the full set now — premature before the training loop proves useful.
- **Consequences:** Early results are on synthetic images; the brief's success measure needs real leaves, so `FolderSet` must land before evaluation.

# US Equity Research Platform — Architecture

**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
`eqdata` is one Python install: the data library, its command line, and an HTTP and WebSocket server. A refresh pulls Sharadar's prices, corporate actions, tickers and S&P 500 membership into one SQLite file. It cleans them, keeps every revised value, validates them, and commits everything in one transaction. As-of queries (universe, total returns, prices) read that file and compute adjustments and returns at query time, using only events on or before the as-of date. Validation runs compare a sample with Yahoo Finance and run internal checks, and every disagreement becomes a finding in the same file. Every run is the same CLI process, whoever started it. Runs write progress events to the store, and the server pushes them to `web`, a TypeScript + React app that reads everything else over plain HTTP.

  yahoo[(Yahoo via yahooquery)] -.spot-check.-> eqdata
  eqdata --- db[(SQLite store)]
  web -- HTTP queries --> eqdata
  eqdata -- WebSocket run events --> web

## Decisions
### AD-01: Two packages, Python `eqdata` and TypeScript `web`
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-09: the user wants "a TypeScript + React browser frontend over a Python backend (HTTP and WebSocket)". Two runtimes share no code or types, which is a real package boundary. The CLI, the loader and the server share the store, the run machinery and every query (SYNC-07, RUNS-03).
- **Decision:** Two packages in one repo. `eqdata` holds the library, the CLI and the server as components of one Python install. `web` is the browser app. Inside `eqdata`, component directions are enforced with import-linter.
- **Alternatives:** Three packages with the server split out: it would carry FastAPI separately, but it runs the same queries on the same machine for one user, so the split buys nothing. One package with the frontend inside it: it mixes two toolchains in one build.
- **Consequences:** `web` builds against frozen JSON samples of the API, so both sides can build at once. The seams that could become packages later are `sources` (vendor clients) and `server`.

### AD-02: Python 3.12 backend, TypeScript + React frontend
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-09 names TypeScript + React over Python. The data work (pandas, `yahooquery`, `exchange_calendars`) is Python.
- **Decision:** Python 3.12 with `uv`. Pandas and NumPy for frames, pandera schemas for every frame that crosses a component, Pydantic 2 models for every type the API serves. TypeScript 5, React 18 and Vite with `pnpm`, and TanStack Query for HTTP caching.
- **Alternatives:** Python 3.13: some data libraries lag on new versions. Next.js: server rendering is unneeded for a local single-user app.
- **Consequences:** Pin `requires-python = ">=3.12,<3.13"`.

### AD-03: Sharadar as the primary source: SEP, ACTIONS, TICKERS and SP500
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** UR-04 and UR-14: Sharadar is the user's subscription and the primary source. UR-15: "Use whichever of its tables cover prices, corporate actions, tickers and S&P 500 membership." Checked against DATA-01–DATA-03, DATA-05 and QR-03. Sharadar's prices page (sharadar.com/prices, read 2026-10-18) says the Prices product includes stock prices with "History back to December 1997", "active and delisted securities", split-adjusted OHLC with `closeunadj`, corporate actions ("splits, dividends, spinoffs, acquisitions, delist reasons and ticker changes"), a tickers table keyed by `permaticker`, and "Current and historical S&P500 index constituents" from January 1998. It names the Sharadar API (`api.sharadar.com/v1.0/data/...`) as the access route. Two things conflict or stay open. QuantRocket's Sharadar catalog (quantrocket.com/data, read 2026-10-18) says the S&P 500 constituents dataset "is bundled with Sharadar US Company Fundamentals". Nasdaq Data Link's SEP database page lists only SEP, ACTIONS, TICKERS, METRICS and INDICATORS. So whether this user's subscription returns SP500, and through which API, is a question about their own account.
- **Decision:** Four Sharadar tables: stock prices (SEP), corporate actions (ACTIONS), tickers (TICKERS) and S&P 500 constituents (SP500), behind `sources.PrimarySource`. Prices are stored unadjusted. Unadjusted open, high and low are derived as split-adjusted OHLC × (`closeunadj` / `close`) (AD-07). Incremental refreshes (SYNC-02) fetch rows whose `lastupdated` is after the last refresh. The universe is limited to companies that appear in SP500, which also leaves out ETFs, OTC listings and preferreds (DATA-03).
- **Alternatives:** Membership from a free list (Wikipedia's change history): unverifiable effective dates and no company identities, so it is a fallback only if PB-01 fails. Nasdaq Data Link's `nasdaqdatalink` client instead of Sharadar's API: used instead if PB-01 shows the user's key works only there.
- **Consequences:** Every Sharadar-specific field name lives in `sources.sharadar`, so a change of access route touches one module. Storing unadjusted values keeps Sharadar's re-adjustment of history after each split from looking like a revision.
- **Probe:** PB-01 — Does the user's Sharadar subscription return SP500 with effective-dated additions and removals back to 1998-01-02, including the ten DATA-04 names, and through which API? Do SEP rows carry `closeunadj` and `lastupdated`?

### AD-04: Company identity is Sharadar's `permaticker`, with a curated override table
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** UNIV-03 and UNIV-04 need one permanent identifier per company across ticker changes. BUD, DNA and WB now belong to other companies. Sharadar's tickers table has a `permaticker` primary key (sharadar.com/prices, read 2026-10-18). The docs don't say how a legal entity that survives a merger under another name is keyed. The spec (DATA-04, Open questions) ends Schering-Plough on 2009-11-03, although its legal entity continued as Merck & Co.
- **Decision:** `CompanyId` is the `permaticker`. A curated `reference/identity_overrides.csv` (AD-10) can split one `permaticker` into two companies at a date, or join two. `universe` applies it before anything else reads identities. Each override row cites its reason.
- **Alternatives:** Ticker plus date ranges: exactly the reused-ticker error the brief warns about. CUSIP or CIK: not available from the user's current sources.
- **Consequences:** Every table is keyed by `company_id`, never by ticker. If PB-02 finds SGP and today's MRK on one `permaticker`, one override row ends Schering-Plough on 2009-11-03 as the spec says.
- **Probe:** PB-02 — Does Sharadar keep Schering-Plough (SGP) on its own `permaticker` ending 2009-11-03, or carry it on as Merck (MRK), and which `permaticker` holds Merck's pre-2009 history?

### AD-05: Yahoo Finance through `yahooquery` as the spot-check source
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** UR-05: "cross-checked against Yahoo Finance through yahooquery". CHECK-01–CHECK-07, QR-03 (free access only) and QR-04 (at most 100 stocks per standard run). The spec's assumption says Yahoo adjusts dividends its own way, so the comparison uses each source's unadjusted prices, raw dividends and splits. yahooquery's official guide (yahooquery.dpguthrie.com) could not be reached on 2026-10-18 (404). It's not yet confirmed whether `Ticker.history` returns dividend and split events, or whether its `close` is split-adjusted.
- **Decision:** `sources.YahooSource` wraps `yahooquery.Ticker.history`. It looks a company up by its current Sharadar ticker in Yahoo's format (`BRK.B` → `BRK-B`), takes Yahoo's split and dividend events, and rebuilds Yahoo's unadjusted closes from them before comparison. Retries 3 times per stock, then marks it not checked (CHECK edge cases).
- **Alternatives:** `yfinance`: also free, but the user named yahooquery. Yahoo's `adjclose`: the method difference the spec says must not raise findings.
- **Consequences:** Delisted names are checked internally only (CHECK-08–CHECK-10, CHECK-15).
- **Probe:** PB-03 — For a stock with splits and dividends since 1998 (AAPL), does `yahooquery` `Ticker.history(start="1998-01-01", interval="1d")` return dividend and split events, is its `close` split-adjusted, and do 100 such calls in a row finish without throttling?

### AD-06: One SQLite file in WAL mode, with bitemporal rows
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** SYNC-05 (a failed refresh leaves the data as before), DATA-05 (every value keeps the date it was first known and replaced), RET-04 (as-of results), the VIEW edge case (the app keeps reading during a refresh), RUNS-03 (a CLI run visible in the app), QR-01 and QR-02. About 1,500 companies × up to 7,200 trading days of prices, so roughly 10 M rows.
- **Decision:** One SQLite file in WAL mode holds market data, findings, runs and run events. Every market-data row has `known_from` and a nullable `replaced_on`, and a revision closes the old row and inserts a new one. A refresh downloads and cleans into staging tables, then validates, then commits the merge in one transaction. Readers in other processes keep seeing the last committed state until then.
- **Alternatives:** A DuckDB file: faster scans, but one process can't read while another writes, so the app would block during every refresh. Parquet files with a swapped manifest: atomic, but findings and runs would need a second store, and revisions mean rewriting partitions.
- **Consequences:** Single-writer: SYNC-06's lock matches SQLite's model. The EDA reads through pandas or DuckDB's SQLite scanner. Query speed rests on indexes. If QR-02's benchmark fails, the fallback is a per-company price cache rebuilt on commit, not a store change.

### AD-07: Prices stored unadjusted; returns and adjusted levels computed at query time
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** RET-02–RET-05: total return includes dividends, ignores splits, and uses no event after the as-of date D. Back-adjusted vendor prices change whenever a later split lands, so they leak the future into earlier dates.
- **Decision:** For each day T, `r_T = (C_T × s_T + d_T × s_T) / C_{T−1} − 1`. Here `C` is the unadjusted close, `s_T` the split ratio effective on T (new shares per old, 1 otherwise), and `d_T` the cash dividend per post-split share going ex on T. Adjusted price levels as of D are back-adjusted using only events with ex-date ≤ D. A day with no close is a gap with no return (RET-07).
- **Alternatives:** Store Sharadar's `closeadj`: it embeds every future split and dividend, which breaks RET-04 and RET-05. Store pre-computed returns: fine for speed, but a revision would then need two rows changed in step.
- **Consequences:** RET-02 and RET-03's worked examples are the unit tests. The dividend convention on a split day is fixed here and checked by PB-01's samples.

### AD-08: REST JSON over HTTP for queries, one WebSocket for run events
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-09 (HTTP and WebSocket), UR-22 (the WebSocket is for live run progress), UR-23: "Queries go over plain HTTP." RUNS-01 and RUNS-02 need updates within 2 seconds. Two runtimes share no types.
- **Decision:** `eqdata.server` is a FastAPI app. Every query and action is a REST JSON endpoint, and `/ws/runs` carries only run events. Response types are Pydantic models, and `web`'s TypeScript types are generated from `/openapi.json` with `openapi-typescript`. Bulk series go out column-wise (`{dates: [...], close: [...]}`).
- **Alternatives:** GraphQL: one client, fixed views, no gain. Server-sent events for progress: would work, but the user named WebSocket.
- **Consequences:** A contract change shows up as a TypeScript compile error in `web`. The server binds to `127.0.0.1` only (single user, no sign-in).

### AD-09: Every run is an `eqdata` CLI process, reporting through the store
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** SYNC-06 (one refresh at a time, the refusal names the running one), SYNC-07 (an app-started run runs exactly as from the CLI), RUNS-01–RUNS-04 (live progress within 2 s, CLI runs visible, history kept, catch-up after reconnect).
- **Decision:** The server starts a run by spawning the same `eqdata refresh|validate|eda` command the researcher types. A run takes the lock (a `runs` row with status `running` and a PID, released on exit and broken if the PID is dead) and appends numbered `RunEvent`s to the store. The server polls new events every 250 ms and pushes them over `/ws/runs`, starting each connection with the current state of every running run. A reconnecting client sends its last `seq` and gets what it missed.
- **Alternatives:** Runs as server background tasks: CLI runs would be invisible and the two paths would differ. A message broker: one process too many for one user.
- **Consequences:** Run events are the only progress channel, so the CLI's own progress output reads them too.

### AD-10: Curated reference tables are CSV files in the repo
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** CHECK-15 compares with the DATA-04 table. UR-34 says the dates stay draft until the researcher verifies each one. CHECK-09 needs cash deal prices, which no chosen source carries reliably. AD-04 needs identity overrides.
- **Decision:** Researcher-edited CSV files under `reference/`: `former_members.csv` (the 20 DATA-04 dates, each with a `verified` flag), `deal_terms.csv` (company, cash price per share, source note) and `identity_overrides.csv`. Each row has a `source` column. Checks read only rows marked `verified`. An unverified row yields a "not checked" line in the run summary, not a pass or a finding.
- **Alternatives:** Tables in the SQLite store: versioning would need its own UI, and git already gives history and review.
- **Consequences:** The researcher's verification is a reviewed commit. The ten names' deal prices need adding by hand before CHECK-09 checks them.

### AD-11: Suggested fundamentals source for a later stage: Sharadar Core US Fundamentals
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** later stage
- **Context:** UR-21: "I haven't picked a fundamentals source, so I'd like your suggestion for one." Fundamentals are out of scope in S1, and QR-03 forbids buying data now. The as-of problem the brief names needs filing dates, not period-end dates.
- **Decision:** Suggest Sharadar's US Company Fundamentals (SF1). It uses the same `permaticker` identity as S1, covers delisted companies, and has as-reported dimensions stamped with their filing date (`datekey`). It's only a suggestion: S1 builds nothing for it, and that stage's architecture decides. If PB-01 shows SP500 comes only with the fundamentals bundle, that bundle settles both questions at once, but only with the user's yes on QR-03.
- **Alternatives:** SEC EDGAR XBRL (free): point-in-time by construction, but thin before 2009 and heavy to normalise. Compustat point-in-time: the reference standard, priced for institutions.
- **Consequences:** Keeping `company_id` = `permaticker` (AD-04) means a later fundamentals table joins without a mapping step.

# eqdata — Architecture

**Package:** eqdata · **Status:** Draft · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`sources` fetches from Sharadar and Yahoo. `sync` cleans what Sharadar returns, stages it and commits it to `store` in one transaction, then calls `check`. `universe` and `returns` answer as-of queries from `store`. `check` and `eda` raise findings through `findings`. Every long job runs inside `runs`, which holds the lock and writes progress events. `cli` and `server` are the two front doors, and the server starts runs by spawning the CLI (AD-09).

```mermaid
flowchart TD
  cli --> runs
  server --> runs
  server --> universe & returns & findings & views
  runs --> sync & check & eda
  sync --> sources & store
  check --> sources & universe & returns & findings
  eda --> universe & returns & findings
  views --> returns & universe & findings
  universe --> store & calendar
  returns --> store & calendar
  findings --> store
```

## Interfaces
See [contract.md](contract.md).

## Data
- **Sources:** Sharadar SEP, ACTIONS, TICKERS and SP500 (AD-03). Yahoo via `yahooquery` for the sample only (AD-05). Researcher CSVs under `reference/` (AD-10).
- **Tables** (all keyed by `company_id`, AD-04): `companies`, `tickers` (company, ticker, from, to), `membership` (company, effective_from, effective_to), `prices` (unadjusted OHLCV), `actions` (splits, dividends, ticker changes, mergers, acquisitions, delistings). Each has `known_from` and `replaced_on` (AD-06). Also `findings`, `runs`, `run_events`, and staging copies of the market tables.
- **Cleaning (SYNC-03):** duplicate (company, date) rows keep one, and the count goes to the summary. A changed past value closes the old row (`replaced_on`) and inserts the new one, listed as a revision.
- **Known-on queries (DATA-05):** as-of functions take `as_of` (market date: events after it are ignored) and an optional `known_on` (system date: rows not yet known, or already replaced, then are ignored).
- **Sampling (CHECK-01):** at least 2 companies per calendar year from 1998, drawn from members Yahoo still carries, then filled at random to 100. The seed is recorded in the run summary.
- **EDA report:** `report.json` (sections of tables and chart series) in `EQDATA_HOME/reports/<run_id>/`, rendered by `web`.

## Cross-cutting concerns
- **Lock and atomicity:** `runs` holds the lock and `store.commit` is one transaction, so a killed refresh leaves only staging rows, which are cleared at the next start.
- **Credentials:** read in `sources` only, and redacted in logs and events (QR-05).

# eqdata — Contract

**Package:** eqdata · **Status:** Draft · **Last updated:** 2026-10-18 · **Architecture:** [architecture.md](architecture.md)

Types the API serves are frozen Pydantic models (AD-08). Their JSON Schema comes from `/openapi.json`, and `web` generates its types from it. Frames that cross components are pandas DataFrames with pandera schemas.

## Identity and universe

### eqdata.CompanyId: type
`CompanyId = NewType("CompanyId", int)  # Sharadar permaticker, or an override id ≥ 10_000_000 (AD-04)`
- **Invariants:** one per company; unchanged across ticker changes; never reused
- **Boundary:** web, every component · **Fixtures:** tests/contracts/eqdata.CompanyId/ · **Cases:** Anheuser-Busch (BUD then), Schering-Plough after its override (PB-02)

### eqdata.Member: type
`class Member(BaseModel, frozen=True): company_id: CompanyId; ticker: str; name: str; member_from: date; member_to: date | None`
- **Invariants:** `ticker` is the ticker on the requested date, not today's; `member_to` is the first day not a member (None while a member)
