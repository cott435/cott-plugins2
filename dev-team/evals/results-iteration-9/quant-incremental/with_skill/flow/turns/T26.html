# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Stage | `Stage:` line of each new feature: the stage the idea added, or the one it joins |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

## Steps

Run these for the idea only:

1. **Check for conflicts first.** Start with the IDs under *Touches*, then search the rest of the spec for anything else the idea contradicts. List conflicts for the user before writing — "Shared editing changes **EDIT-03** (only the owner can edit). Proposed: owner *or invited editors* can edit."
2. **Map the idea to features** and show the goal → feature mapping, with each feature's stage, before writing.
3. **Surface assumptions, then clarify** (SKILL.md's Asking section).
4. **Write the change** following `references/spec.md` and the rules below.
5. **Set the spec Status back to Draft** and run the Review Gate (SKILL.md, plus the gate steps below), highlighting the changed IDs so the user reviews only what's new.

## Writing rules

1. **Keep IDs stable, keep the text current.** IDs are never renumbered or reused. Old text does not stay in the spec once it stops being true; git keeps it.
   - New feature → new `### Feature (CODE)` section with a new code and IDs starting at `-01`.
   - New behavior in an existing feature → next unused number in that feature (if `SAVE-04` is the highest, add `SAVE-05`, even if `SAVE-02` was removed). `dt status` reports it under `prefixes`.
   - **Widen, don't bolt on.** If an existing requirement already covers this concern for an earlier part of the project, rewrite it to cover the new part too, instead of adding a near-duplicate. A training-time limit written for the first dataset becomes a limit for every dataset. A summary that says "the first milestone" is rewritten.
   - Changed requirement → rewrite it in place and keep its ID. Put no marker on it. Instead, list it as `(changed)` in this round's Changelog row, with the reason in the row's Change text. `architecture-design` reads those Changelog marks (through `dt status`) to find what the architecture must revisit, so list every changed ID.
   - Removed requirement → collapse it to one struck line and delete its criteria and edge cases: `- **CODE-03** ~~[short name]~~ *Removed YYYY-MM-DD: [reason, or "replaced by CODE-07"].*` Never delete the ID line; the ID stays retired.
2. **Link back to the idea.** Add `**Source:** [ideas/<slug>.md](ideas/<slug>.md)` under the `Stage:` line of each new feature section, so readers can find the full why.
3. **Update everything it touches, and consolidate.** Summary (rewritten for the whole spec, not appended to), Users, Serves lines. Scope stays one deduplicated list per side: merge new out-of-scope items into it, and drop or narrow anything the new features bring into scope (the gate's *Out of scope* step). Remove assumptions and open questions that are answered or no longer apply.
4. **Add one Changelog row**, one line: the idea file as the source, a short description of the change, and the IDs as ranges in up to three `;`-separated groups: added, then changed, then removed (`FIELD-01–FIELD-12; CNN-03, CORE-04 (changed); CROP-04 (removed)`). A `(changed)` or `(removed)` mark covers every ID in its group.

## Gate steps

Run the hygiene check on the whole spec, not just the new section, and add:

- **Out of scope.** Read every out-of-scope line against the features this round added. Drop a line the new features bring into scope. Narrow a line that is now only partly true to the part still excluded, and name the stage it applies to. Once a neural-network stage exists, "deep learning" is no longer out of scope. Once a reserve-planning stage uses demand forecasts, "no demand forecasts — the reserve stage is an equal split" becomes "the equal-split reserves use no demand forecasts". Then merge duplicates.
- **Leftovers.** The Summary describes the whole spec as it now stands. No requirement is still worded for one stage when it now covers several. Removed requirements are one line each. No `(changed …)` marker or other change note appears above the Changelog.

## On approval: close and freeze the idea

A `Specced` idea is the record of why the feature was added, as it stood that day. The spec is the current description.

1. Set its Status to `Specced` and add two lines under the header: `**Spec:** CODE-01–CODE-04, EDIT-03 (changed)` and the banner `> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)`.
2. Delete the open questions the spec answered. If none are left, the section becomes one line: `Resolved in the spec.`
3. Delete wording that only served the review: notes to the user ("my proposed limit, for you to check") and instructions to this skill ("this line must be removed from the spec").

After that, don't edit the file again, even when a later round changes what it describes, such as a narrowed holdout or a merged stage. That change goes in the spec, and the later idea file names this one under *Touches*.

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown
# [Project Name] — Spec

**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [brief.md](brief.md)

## Summary
[2-3 sentences: what is being built. Link to the brief for why — don't repeat it.]

## Users
| User | What they need to do |
|---|---|

**In scope:** [features, by name]
**Out of scope:** [what we're not building — include everything on the brief's Not Doing list, plus anything decided during clarification]

## Features

### [Feature name] (`CODE`)
**Serves:** Goal 1, Goal 3
**Stage:** S2
**Source:** [ideas/<slug>.md](ideas/<slug>.md) *(extend mode only — omit for features from the original brief)*
**Behavior:** [2-4 sentences or a short numbered flow describing what the user experiences.]

**Requirements**
- **CODE-01** [One testable statement of what the system does.]
  - Given [context], when [action], then [observable result].
  - Given [...], when [...], then [...].
- **CODE-02** [...]
  - Given [...], when [...], then [...].

**Edge cases & errors**
- [Situation] → [expected behavior]

## Data requirements
*(Data and ML projects only — omit otherwise.)*
- **DATA-01** [What data the system needs: content, coverage, history, frequency, freshness — not which vendor.]
  - Given [...], when [...], then [...].

| Date | Change | Source | IDs |
|---|---|---|---|
| YYYY-MM-DD | Initial spec | brief.md | all |
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Every feature names one stage.** Its `**Stage:**` line holds only the ID of the roadmap stage that first builds it. `dt lint` fails a feature with no stage, or one naming no stage row.
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence and budget limits are `QR-` items ("data costs ≤ $50 a month"), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads the idea file and the conversation.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of torchvision's ResNet-18" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.

# Idea: Return structure and variance portfolios

**Status:** Accepted · **Last updated:** 2026-10-17 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This adds a study of the structure of S&P 500 returns and a set of classical, long-only variance portfolios, so that I can learn which covariance estimate really lowers out-of-sample variance before I try any return prediction.

## The problem
Every portfolio I build later rests on a covariance estimate. With about 500 names and two years of daily data, there are about as many names as days. The sample covariance is then badly conditioned: minimum-variance weights chase noise and look far better in sample than they turn out to be. Shrinkage, random-matrix denoising and factor models all claim to fix this. I don't yet know which one helps on my data, or whether any of them beats simply holding every name equally. If I skip this step, every later signal test inherits a risk model I've never checked.

## Who it's for
Me, as the researcher, now that trusted point-in-time data exists. I'm getting variance optimization right on real data before adding return forecasts.

## How it fits
- **Serves:** Goal 4. Built on the same trusted data, with no new data work.
- **Touches:** reads only through research data access (`QUERY-01`–`QUERY-05`), and uses the point-in-time universe (`UNIV-01`, `UNIV-03`) and daily total returns (`PRICE-02`, `PRICE-04`). It adds pages to the explorer app.
- **Brief changes:** None.
- **Stage:** New S2 (a roadmap stage on acceptance).

## Recommended direction
**Structure first.** At each monthly rebalance, take the S&P 500 members on that date and their trailing two years of daily total returns. PCA of the correlation matrix shows how dominant the market mode is and how many factors stand out. The eigenvalue spectrum is compared with the Marchenko–Pastur distribution for that ratio of names to days, and eigenvalues inside the noise band count as noise. This is a diagnostic. Market removal (prior art: RF-01, which must be fitted per window, not on the whole sample) is used to understand the structure. It is never a preprocessing step before the portfolios, because a portfolio's realized variance includes market risk.

**Estimators.** Four covariance estimates are built from the same window:
- the sample covariance;
- a shrinkage estimate;
- a Marchenko–Pastur denoised estimate: noise eigenvalues replaced, diagonal restored, then scaled back to a covariance;
- a PCA factor model with k factors plus diagonal residuals, with k set by the Marchenko–Pastur edge.

The sample estimate is used for minimum variance only on a subset of names small enough for it to be well defined.

**Portfolios.** Each estimator feeds long-only minimum variance, risk parity and hierarchical risk parity, rebalanced monthly and held for the next month. Equal weight across the month's members is the baseline every portfolio must beat. Names that stop trading during a holding month stay in the portfolio until their exit, and their returns count up to that day. The scorecard is realized out-of-sample variance; turnover is reported too, with no cost model.

**Known answer first.** Before any real-data comparison, each estimator and portfolio runs on a synthetic panel with planted factors and a known true covariance. On that panel the denoised and factor estimates must recover the planted structure, and minimum variance must come close to the true minimum.

**Is it more than chance?** A difference in realized variance between two portfolios counts only when a test shows it is more than chance, corrected for the many pairs compared. The `null-hypothesis-testing` skill owns those tests. The `data-analysis` skill owns the spectra, the estimator comparisons and their stability over time.

**Where results show.** Research code writes reports and plots. The explorer app gains a page for eigenvalue spectra on each rebalance date, with the Marchenko–Pastur band, and a page comparing the portfolios: realized variance, turnover and test results.

## Data
Everything comes from the S1 data version through as-of reads: daily total returns of point-in-time members, about 500 names, with monthly rebalances and two-year trailing windows from 2002 on. There are no new sources and no labels. Results are evaluated out of sample. Each month's portfolio is formed only from data known at the rebalance date, then scored on the following month. Equal weight is the baseline. `null-hypothesis-testing` owns the significance tests and `data-analysis` the exploratory analysis.

## Alternatives considered
- Removing the market with PCA before estimating covariance — it optimizes residual variance, not the variance the portfolio actually has.
- Estimators judged only by a covariance-fit loss — what matters is the variance of the portfolio built on the estimate.
- Minimum variance and equal weight only, with risk parity and HRP later — rejected; the three portfolio types share the same machinery and comparison.

## What success looks like
- On the synthetic panel, every estimator and portfolio recovers the known answer within agreed tolerances.
- A ranking of estimator and portfolio pairs by out-of-sample realized variance against equal weight, each difference marked as significant or not after correction.
- In the app, I can open any rebalance date's spectrum and see the noise band and the factors that stand out.

## What we're betting on
- Two-year windows of daily returns are long enough for the estimators to differ in a way I can measure, and short enough to track changing structure.
- Monthly realized variance across about 23 years of rebalances gives the tests enough power.
- Long-only constraints don't erase the differences between estimators.

## Not doing
- Return prediction, expected-return inputs or mean-variance optimization — variance comes first.
- Transaction costs and turnover limits — turnover is reported only.
- Short positions and leverage.
- ML estimators such as learned covariance or neural factor models.

## Open questions
- Names without a full two-year history at a rebalance (recent IPOs and new members): drop them, or estimate on shorter histories? Dropping them biases the universe.
- Which shrinkage target: constant correlation, single factor or identity?
- How big a subset makes sample minimum variance well defined, and how is it chosen without look-ahead?
- Which risk parity: inverse volatility or equal risk contribution?
- Which test fits a difference in realized variance between two portfolio return series, given autocorrelation and heavy tails?

## Constraints
- One person, running locally.
- Under $50 per month. Sharadar (already paid for) is the main source; Yahoo, via an unofficial free client, is the cross-check.
- Daily bars. The universe is the historical S&P 500, with membership as of each date.
- The exploration app ships in the first stage: a TypeScript and React browser interface over a Python backend, with typed contracts, a distinctive look, and live progress for download and check runs.

## What success looks like
- My list of 10 delisted former S&P 500 members appears with correct histories, membership dates and exits.
- Adjusted returns agree with the Yahoo cross-check within an agreed tolerance on the names Yahoo still covers.
- All validation checks pass, or each failure is explained and visible in the app.

## What we're betting on
- My Sharadar plan includes delisted companies and S&P 500 membership by date. If not, membership needs another source within budget.
- Yahoo covers enough of the same companies for a meaningful cross-check. It likely misses delisted names, which rely on the hand-checked list.
- The unofficial Yahoo client keeps working for occasional checks.

## Not doing
- Intraday data — daily bars are enough for this research.
- Real-money trading — paper trading only, and not in this first stage.
- Non-US markets, or the whole US market at first — the S&P 500 is small enough to check properly.
- Fundamentals and alternative data — not needed until a signal asks for them.
- Hosting, multiple users or scheduled cloud jobs — it runs locally for one person.

## Open questions
- Does my Sharadar plan include historical S&P 500 membership, or only prices? (To check before the architecture relies on it.)

# Quant Research Platform — Spec

**Status:** Approved · **Last updated:** 2026-10-17 · **Brief:** [brief.md](brief.md)

## Summary
A local research data platform for one researcher: it downloads daily prices, corporate actions and index membership for every company that has ever been in the S&P 500 (delisted names included), stores them so that any question can be asked "as of" a past date, validates them with automated checks and an independent cross-check, and offers a browser app to explore tickers, check results and live download and check runs. Later research stages read the same data through one point-in-time interface. Why it exists: see the [brief](brief.md).

## Users
| User | What they need to do |
|---|---|
| Researcher (sole user, local machine) | Load and refresh the data, see that it is correct, explore any ticker's history and corporate actions, review and explain failed checks, and read the data from research code without look-ahead or survivorship bias |

## Scope
**In scope:** Data download and refresh, Point-in-time universe, Adjusted prices and returns, Validation checks, Independent cross-check, Research data access, Run progress, Explorer app.

**Out of scope:**
- Intraday data; daily bars only.
- Real-money trading; paper trading is a later stage, not this one.
- Non-US markets; US stocks outside the historical S&P 500.
- Fundamentals and alternative data.
- Hosting, multiple users, accounts, or scheduled or cloud jobs; every run is started by the user on their own machine.
- Signal research, backtesting and paper trading (later stages, specced when their idea files are accepted).
- Editing or correcting vendor data by hand; failures are explained, not patched.

## Features

### Data download and refresh (`LOAD`)
**Serves:** Goal 1, Goal 4
**Stage:** S1
**Behavior:** The user starts a download run. The first run fetches the full history from the primary source for every company that was an S&P 500 member at any time in the covered period. Later runs fetch only what is new or changed since the last completed run. Each completed run becomes a numbered, read-only data version.

**Requirements**
- **LOAD-01** A full download run fetches daily bars, corporate actions and membership history for every company that was an S&P 500 member on any trading day from 2000-01-03 to the most recent completed trading day.
  - Given an empty local store, when the user starts a full download run and it completes, then every company with at least one day of membership in the covered period has daily bars, corporate actions and membership intervals stored.
  - Given the completed run, when the user looks up a company that was removed from the index and later delisted, then its full history up to its last trading day is present.
- **LOAD-02** A refresh run fetches only days and records added or revised since the last completed run.
  - Given a completed run as of day D, when the user starts a refresh on day D+5, then the new bars for the days after D are stored and earlier unchanged records are not downloaded again.
  - Given the primary source revised a past record (for example a late dividend), when a refresh runs, then the revision is stored as a new record with the date it was first seen, and the earlier value is kept.
- **LOAD-03** Each completed download or refresh run produces a new data version with an identifier, a completion time and the date range it covers.
  - Given two completed runs, when the user lists data versions, then both appear with identifier, completion time, covered range and record counts.
  - Given an existing data version, when a later run completes, then reading the earlier version returns exactly the same records as before.
- **LOAD-04** An interrupted or failed run leaves the latest completed data version unchanged.
  - Given a run that fails at 60%, when the user reads data, then they see the previous completed version with no partial records.
  - Given a failed run, when the user starts a new run, then it resumes without downloading records already fetched in the failed run.
- **LOAD-05** The raw response from each source is kept alongside the stored data, so any stored value can be traced to what the source returned.
  - Given any stored bar or corporate action, when the user asks for its origin, then the run, the source and the raw values it was derived from are shown.

**Edge cases & errors**
- Source unreachable, rate-limited or returns an authentication error → the run stops with that reason shown; the latest completed version is untouched.
- A company changes ticker → it is one company with a ticker history, not two companies.
- A ticker is reused by a different company after a delisting → the two are separate companies; a lookup by ticker on a date returns the company that held it on that date.
- A company has no bars for its whole membership period → the run completes, and a validation check reports it.
- The covered period's start precedes the source's history for a company → history starts at the source's first bar, and the gap is reported by checks.

### Point-in-time universe (`UNIV`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** For any trading day, the user (or research code) can ask which companies were in the S&P 500 that day, and gets the members as they were then, including companies that later left the index or stopped trading. Each company shows when it joined, when it left and why it stopped trading, if it did.

**Requirements**
- **UNIV-01** The members on a trading day are the companies whose membership interval covers that day, by the change's effective date.
  - Given 2008-06-30, when the user asks for the members, then Lehman Brothers is among them.
  - Given a company added effective day D, when the user asks for members on D−1 and on D, then it is absent on D−1 and present on D.
- **UNIV-02** Every company stores all of its membership intervals, so a company that left and rejoined the index has more than one.
  - Given a company removed in 2010 and re-added in 2015, when the user views it, then two intervals with their start and end dates are shown.
- **UNIV-03** Every company that stopped trading records its last trading date and its exit type: acquired, bankrupt or liquidated, moved to another exchange, or other.
  - Given a company acquired for cash, when the user views it, then its last trading date and the exit type "acquired" are shown.
  - Given a company still trading, when the user views it, then no exit is shown.
- **UNIV-04** The member count is available for every trading day in the covered period.
  - Given any trading day, when the user asks for the member count, then a number is returned, and days outside 498–505 are reported by checks (`CHECK-06`).

**Edge cases & errors**
- A company with two share classes in the index → each share class is a separate member on the same day.
- A membership change effective on a non-trading day → it takes effect from the next trading day.
- A member removed from the index that keeps trading → bars continue after the removal; it is simply no longer a member.
- Date before the covered period or after the latest data → the request is refused with the covered range stated, never answered with an empty list.

### Adjusted prices and returns (`PRICE`)
**Serves:** Goal 1, Goal 2
**Stage:** S1
**Behavior:** Every company has daily open, high, low, close and volume as traded, plus split- and dividend-adjusted prices and daily total returns that a researcher can use directly. Adjustments use only corporate actions known on each date.

**Requirements**
- **PRICE-01** Each company has unadjusted daily open, high, low, close and volume for every trading day it traded in the covered period.
  - Given a company and a trading day it traded, when the user asks for its bar, then the five values as traded that day are returned.
- **PRICE-02** Each company has a daily total return, computed from unadjusted closes, splits and cash dividends by their ex-dates.
  - Given a 2-for-1 split on day D with no price change, when the return for D is computed, then it is 0% (within 0.01 percentage points), not −50%.
  - Given a $1 cash dividend with ex-date D on a $100 stock that closes at $99 on D, when the return for D is computed, then it is 0% (within 0.01 percentage points).
- **PRICE-03** Adjusted prices are derived from the daily total returns, anchored to the unadjusted close on a reference date the caller chooses, defaulting to the latest day in the data version.
  - Given a split after date T, when adjusted prices are requested anchored at T, then prices up to T equal the unadjusted prices.
- **PRICE-04** The last bar of a company that stopped trading is its last trading date; no prices or returns exist after it.
  - Given a company with last trading date L, when bars after L are requested, then none are returned, and the exit type is reported with the response.

**Edge cases & errors**
- Corporate action with an ex-date on a day the company did not trade → applied on its next trading day, and reported by checks.
- Special or stock dividend → applied to returns by its value as reported; if its value is missing, a check fails for that action.
- Zero-volume or missing bar inside a company's trading life → no value is filled in; the gap is reported by `CHECK-01`.

### Validation checks (`CHECK`)
**Serves:** Goal 2, Goal 3
**Stage:** S1
**Behavior:** The user starts a check run against a data version. Every check runs over every company and day, and records each failure with what was expected and what was found. The user reviews failures in the app and can mark each one explained with a note; explanations carry over to later runs while the failure stays the same.

**Requirements**
- **CHECK-01** A completeness check fails for each trading day in a company's trading life (first bar to last trading date) with no bar.
  - Given a company missing its bar on one exchange trading day, when checks run, then exactly one failure names that company and day.
- **CHECK-02** A bar-consistency check fails for each bar where low > min(open, close), high < max(open, close), any price ≤ 0 or volume < 0.
  - Given a bar with high below close, when checks run, then a failure shows the bar's five values.
- **CHECK-03** An extreme-move check fails for each daily total return beyond ±50% on a day with no corporate action.
  - Given a −60% return on a day without a split or dividend, when checks run, then a failure is recorded; given the same move on a 1-for-2 reverse-split day explained by the split, then none is.
- **CHECK-04** A split-consistency check fails for each split where the ratio of the unadjusted close before and on the ex-date differs from the split ratio by more than 30%.
  - Given a 3-for-1 split where the unadjusted price did not change, when checks run, then a failure names the split.
- **CHECK-05** A member-coverage check fails for each trading day on which an index member has no bar.
  - Given a member with no bar on a day it was in the index, when checks run, then a failure names the member and day.
- **CHECK-06** A member-count check fails for each trading day with fewer than 498 or more than 505 members.
  - Given a day with 490 members, when checks run, then a failure shows the day and the count.
- **CHECK-07** A point-in-time check fails for each record whose first-known date is later than the date it is used for in any as-of read.
  - Given a dividend first seen on day K with ex-date before K, when checks run on as-of reads before K, then no read before K returns it; any that does is a failure.
- **CHECK-08** A uniqueness check fails for each company and day with more than one bar, and for each ticker held by two companies on the same day.
  - Given a duplicated bar, when checks run, then one failure names the company and day.
- **CHECK-09** A reference-list check compares the user's list of 10 delisted former S&P 500 members against the data, and fails for each field that differs: membership start and end dates, last trading date and exit type.
  - Given the user's list with expected values, when checks run, then each of the 10 companies shows pass, or a failure stating the expected and found value.
  - Given a company on the list that is missing from the data, when checks run, then a failure says it was not found.
- **CHECK-10** The user can mark a failure explained with a note; the explanation stays attached while a later run finds the same failure with the same found values.
  - Given an explained failure, when the next check run finds it unchanged, then it shows as explained with the original note.
  - Given an explained failure whose found values change in a new data version, when checks run, then it shows as failed again, with the old note visible.
- **CHECK-11** Each check run produces a summary per check: failures, explained failures and unexplained failures.
  - Given a completed run, when the user opens its summary, then every check is listed with its three counts; the run is "clean" only when unexplained failures are 0.
- **CHECK-12** Before the extreme-move and member-count thresholds (`CHECK-03`, `CHECK-06`) are fixed for use, the first full data version is characterised with the `data-analysis` skill, given: the question "are these thresholds tight enough to catch errors without flooding the list with real events?", all companies' daily total returns and daily member counts over the covered period, split by decade; producing the distribution and tails of daily returns, the count of days beyond each candidate threshold, the member-count series, and missing-bar rates by year. It passes when the thresholds are confirmed or replaced by values the user approves from that analysis.
  - Given the analysis output, when the user reviews it, then the thresholds in use are the ones they approved.

**Edge cases & errors**
- A check cannot run (for example, the data version is missing a dataset) → the check is reported as "not run" with the reason, never as passed.
- Thousands of failures from one check → the run completes; the app groups them by company and check.
- A failure explained in the past no longer occurs → it is shown as resolved in the run history and does not count as a failure.

### Independent cross-check (`XCHK`)
**Serves:** Goal 2
**Stage:** S1
**Behavior:** As part of a check run (or on its own), the system fetches daily adjusted prices for the same companies from the independent secondary source, compares daily total returns over every day both sources have, and reports agreement per company. Companies the secondary source doesn't cover are listed as not covered, never as passed.

**Requirements**
- **XCHK-01** For each company the secondary source covers, the cross-check compares daily total returns on every trading day both sources have.
  - Given a company covered by both sources from 2005 to today, when the cross-check runs, then the number of compared days equals the number of days both have.
- **XCHK-02** A company passes the cross-check when its daily total returns differ from the secondary source's by ≤ 0.10 percentage points on ≥ 99% of compared days, and its cumulative total return over the compared period differs by ≤ 1% (relative).
  - Given a company whose returns differ by 0.5 points on 3% of days, when the cross-check runs, then it fails, with the worst days listed.
- **XCHK-03** Each compared day with a difference > 1 percentage point is listed individually with both sources' values and any corporate action that day.
  - Given a dividend recorded on different ex-dates by the two sources, when the cross-check runs, then both days are listed with the dividend shown.
- **XCHK-04** The cross-check reports its coverage: how many current and how many former members were compared, and which were not covered.
  - Given a run, when the user opens the cross-check summary, then it shows covered counts for current and former members, and the list of not-covered companies.
  - Given fewer than 95% of current members are covered, when the cross-check runs, then the summary marks the cross-check as insufficient.
- **XCHK-05** Cross-check failures are failures of the check run, and can be explained like any other (`CHECK-10`).
  - Given a cross-check failure caused by a known source difference, when the user explains it, then it counts as explained in the run summary.

**Edge cases & errors**
- The secondary source is unavailable or its client stops working → the cross-check is reported as "not run" with the reason; the other checks still complete.
- The secondary source returns a ticker for a different company (ticker reuse) → the company is matched only on days the ticker belongs to it; otherwise not covered.
- The secondary source's history is shorter → only overlapping days are compared, and the overlap is shown.

### Research data access (`QUERY`)
**Serves:** Goal 1, Goal 4
**Stage:** S1
**Behavior:** Research code in later stages reads members, bars, returns and corporate actions through one interface that takes an as-of date and a data version. Whatever it returns is what was knowable on the as-of date in that version, so later stages never redo data work and can reproduce a result exactly.

**Requirements**
- **QUERY-01** Every read takes an as-of date and returns only records first known on or before it.
  - Given a dividend first seen on day K, when data is read as of K−1, then the dividend is absent; read as of K, it is present.
  - Given an as-of date T, when bars are read, then no bar dated after T is returned.
- **QUERY-02** Every read takes a data version, defaulting to the latest completed one, and names the version it used in its result.
  - Given the same as-of date, request and version, when the read is repeated after later refreshes, then the result is identical.
- **QUERY-03** A universe read returns, for a range of days, each day's members with their bars and total returns.
  - Given 2008-01-02 to 2008-12-31, when the universe is read, then companies that were members and later delisted (Lehman Brothers among them) appear on their member days.
- **QUERY-04** A read for a company by ticker resolves the ticker to the company that held it on the as-of date.
  - Given a reused ticker, when it is read as of a date before the reuse, then the original company's data is returned.
- **QUERY-05** A read for days outside the version's covered range is refused, with the covered range in the error.
  - Given a version covering 2000-01-03 to 2026-10-16, when 1999 is requested, then the read is refused naming that range.

**Edge cases & errors**
- No completed data version exists → every read is refused with "no data loaded".
- A read while a refresh is running → served from the latest completed version, unaffected by the run.

### Run progress (`RUN`)
**Serves:** Goal 3
**Stage:** S1
**Behavior:** The user starts download, refresh and check runs from the app and watches them advance live: the current phase, how much is done, what failed so far. Runs can be cancelled, and past runs remain viewable.

**Requirements**
- **RUN-01** The user can start a full download, a refresh or a check run from the app.
  - Given no run in progress, when the user starts a refresh, then it begins and appears as running within 2 seconds.
- **RUN-02** Only one download or refresh run can be in progress at a time.
  - Given a refresh running, when the user tries to start another download or refresh, then it is refused with the running run shown.
- **RUN-03** A running run shows its phase, the companies done out of the total, elapsed time and the errors so far, updated at least every 2 seconds.
  - Given a full download in progress, when the user watches the run page, then the done count rises without reloading the page.
- **RUN-04** The user can cancel a running run; a cancelled run behaves as a failed run (`LOAD-04`).
  - Given a running refresh, when the user cancels it, then it stops within 10 seconds and the latest completed version is unchanged.
- **RUN-05** Every run is kept in a run history with its type, start and end times, outcome and data version.
  - Given three past runs, when the user opens the run history, then all three are listed, newest first, each opening its detail.
- **RUN-06** Closing or reloading the app does not stop a run; reopening it shows the run's current progress.
  - Given a running download, when the user reloads the app, then the run page shows the same run still advancing.

**Edge cases & errors**
- The local backend stops during a run → on restart the run is shown as failed with "interrupted", and can be resumed (`LOAD-04`).
- The connection between app and backend drops → the app shows "reconnecting" and resumes live updates when it returns.

### Explorer app (`EXPL`)
**Serves:** Goal 3
**Stage:** S1
**Behavior:** A local browser app where the user searches any current or former ticker or company name, sees its price history with corporate actions and membership periods marked, inspects its corporate actions, compares it with the cross-check source, and browses check failures and the members on any date.

**Requirements**
- **EXPL-01** The user can search by current or former ticker or company name, including companies that stopped trading.
  - Given a delisted company's former ticker, when the user types it, then the company appears in the results with its exit type.
- **EXPL-02** A company page shows a daily price chart over the company's full history, switchable between unadjusted and adjusted prices.
  - Given a company with a 2-for-1 split, when the user switches to unadjusted, then the split shows as a halving of the price; adjusted, it doesn't.
- **EXPL-03** The company page chart marks splits, dividends and the last trading date, and shades membership periods.
  - Given a company with two membership intervals and a delisting, when the page opens, then both intervals are shaded and the last trading date is marked.
- **EXPL-04** The company page lists all corporate actions with type, ex-date, value and first-known date.
  - Given a company with 40 dividends and one split, when the user opens its actions, then 41 rows are listed in date order.
- **EXPL-05** The company page shows the company's ticker history and its check failures, each linking to the failure detail.
  - Given a company with two unexplained failures, when the page opens, then both are listed with their check and day.
- **EXPL-06** The company page shows the cross-check comparison: both sources' cumulative returns over the compared period, and the listed days of disagreement.
  - Given a covered company, when the user opens the comparison, then both series and the disagreement days from `XCHK-03` are shown; for a not-covered company, the page says "not covered by the cross-check".
- **EXPL-07** A checks page shows the latest run's summary and lets the user filter failures by check, company, status (failed, explained, resolved) and date range.
  - Given 120 failures, when the user filters by one check and "failed", then only unexplained failures of that check are shown, with the count.
- **EXPL-08** From a failure, the user can write or edit its explanation note.
  - Given an unexplained failure, when the user saves a note, then the failure shows as explained and the summary counts update.
- **EXPL-09** A universe page shows the members on a date the user picks, with the count, and the additions and removals effective that day.
  - Given 2008-09-22, when the user picks it, then the members, the count and that day's changes are shown.
- **EXPL-10** Every page states the data version it shows.
  - Given two data versions, when the user switches version, then every page shows data from the chosen one and names it.

**Edge cases & errors**
- No data loaded yet → the app opens on the runs page with a prompt to start a full download.
- Search with no match → "no company found", with a hint that the covered period starts 2000-01-03.
- Charts for companies with very long histories → the chart remains interactive (`QR-02`).

## Data requirements
- **DATA-01** The data covers every company that was an S&P 500 member on any trading day from 2000-01-03 to the latest completed trading day, including those later removed, acquired, bankrupt or otherwise delisted.
  - Given the user's 10 delisted former members, when the data is loaded, then all 10 are present (`CHECK-09`).
- **DATA-02** Each company has unadjusted daily open, high, low, close and volume over its full trading life within the covered period, not only its membership periods.
  - Given a company that left the index in 2012 and traded until 2015, when its bars are read, then bars through 2015 are present.
- **DATA-03** Corporate actions cover splits (with ratio), cash dividends (with amount and ex-date), ticker changes and delistings (with last trading date and exit type).
  - Given a company's history, when its corporate actions are read, then each action has its type, date and value.
- **DATA-04** Membership history gives, for each company, every interval it was in the S&P 500, by effective date.
  - Given any trading day, when membership is read, then exactly the companies whose intervals cover it are returned.
- **DATA-05** Every stored record carries the date it first became known to the system or the source, whichever is earlier and evidenced; records without an evidenced earlier date use the date first downloaded.
  - Given a record first downloaded on day K with no source-provided known date, when its first-known date is read, then it is K.
- **DATA-06** A company is identified by a permanent identifier independent of ticker, stable across ticker changes and across data versions.
  - Given a company that changed ticker twice, when it is read under any of its tickers, then the same identifier is returned.
- **DATA-07** The independent cross-check source provides daily split- and dividend-adjusted closes for the companies it covers, fetched independently of the primary source.
  - Given a cross-check run, when a company is compared, then its secondary values come only from the secondary source.

## Quality requirements
- **QR-01** Data costs stay under $50 a month in total, using the already-paid primary subscription and a free secondary source.
  - Checked at architecture: every source and plan used is listed with its monthly cost, summing to < $50.
- **QR-02** In the app, a company page with up to 26 years of daily history becomes interactive within 2 seconds, and the universe page for any date within 1 second.
  - Measured on the user's machine against the full data version.
- **QR-03** A refresh run covering up to 5 new trading days completes within 10 minutes; a full check run, excluding the cross-check fetch, within 10 minutes.
  - Timed on the user's machine with the full data version.
- **QR-04** Data and app stay on the user's machine: the app is reachable only from that machine, and nothing is sent anywhere except requests to the two data sources.
  - Checked by reviewing every outgoing connection the system makes, and by confirming the app refuses connections from another device on the network.
- **QR-05** Requests to the secondary source are rate-limited to at most 1 request per second, and a cross-check fetch never re-requests a company already fetched that day.
  - Checked from the run log of a cross-check run.
- **QR-06** The primary source's data is never redistributed: it is stored only locally and the app has no export beyond the user's own research code.
  - Checked by reviewing that no feature publishes or uploads stored data.
- **QR-07** The app's visual direction is set with the `frontend-design` skill, given: the single researcher exploring trusted market data, the views in `EXPL` and `RUN` with the data each shows, and the brief's ask for a distinctive look, local-only. It passes when the user approves the direction before the views are built.
  - Checked by the user's sign-off on the design direction.
- **QR-08** The app and its backend agree on the shape of every message between them, so a mismatch is caught before the app runs, not at runtime.
  - Checked by a change to a message shape on one side failing the build of the other.

## Assumptions
- Membership uses the effective date of each index change; announcement dates are not needed.
- The covered period starts 2000-01-03 (first trading day of 2000).
- The user provides the list of 10 delisted former members with expected membership dates, last trading date and exit type; those expected values come from the user, not from either data source.
- A company's bars cover its full trading life within the covered period, not just its membership periods.
- The secondary source is only for cross-checking; its values are never used in place of the primary source's.
- Explanations are notes; the user never edits data values to clear a failure.
- The thresholds, tolerances and timings in `XCHK-02`, `XCHK-04`, `CHECK-03`, `CHECK-06`, `QR-02` and `QR-03` are the user's targets.
- Exit types are acquired, bankrupt or liquidated, moved to another exchange, or other.

## Open questions
- Does the primary subscription include historical S&P 500 membership by date and delisted companies? Answered by a probe during architecture; if not, membership needs another source within `QR-01`.
- Does the primary source provide a first-known date for corporate actions and revisions, or must the system rely on its own download dates (`DATA-05`)? Answered by a probe during architecture.

The next planning step is adding the accepted variance-portfolios idea to the spec. Before I write anything, here are the conflicts, the feature mapping, my assumptions and four questions.

## 1. Conflicts with the approved spec

- **Out of scope:** the line "Signal research, backtesting and paper trading (later stages)" now partly conflicts, because S2 tests variance portfolios on past data. I propose: "Return prediction, signal research, return-seeking backtests and paper trading."
- **QR-07** (visual direction via `frontend-design`) only names the existing app views. I'd widen it to include the two new pages. *(changed)*
- **QR-02** (how fast app pages load) only names the company and universe pages. I'd widen it to the new pages: the spectrum page within 1 s, the comparison page within 2 s. *(changed)*
- **Summary and Users** get rewritten to describe both stages.
- No conflicts with QUERY, UNIV or PRICE. The study only reads through the existing as-of reads. Names that stop trading are already covered by PRICE-04, and EXPL-10 (every page names its data version) already applies to new pages.

## 2. Goal → feature mapping (all Stage S2, Source: the idea file)

| Feature | Code | Serves | What it covers |
|---|---|---|---|
| Return structure | `STRUCT` | Goal 4 | Eigenvalue spectrum at each rebalance date, the band that counts as noise for that window, how much the market factor explains, and market removal used only as a diagnostic, fitted per window |
| Covariance estimators | `COV` | Goal 4 | Four estimates (sample, shrinkage, denoised, factor model), all built from the same trailing window |
| Variance portfolios | `PORT` | Goal 4 | Minimum variance, risk parity and HRP for each estimate, plus the equal-weight baseline; monthly rebalancing, delisting handling, turnover |
| Known-answer check | `SYNTH` | Goal 4 | Synthetic data with planted factors and a known true covariance, which every estimator and portfolio must recover |
| Out-of-sample comparison | `EVAL` | Goal 4 | Realized-variance scorecard, significance via `null-hypothesis-testing`, stability over time via `data-analysis`, reproducible reports |
| Research pages | `RVIEW` | Goal 3, Goal 4 | Spectrum page and portfolio comparison page in the app |

I'm making `RVIEW` a new feature rather than adding to `EXPL`, because a feature can name only one stage and `EXPL` is S1. There are no new `DATA-` requirements, since the idea says no new data. I'd add QR-09: a full study run finishes within 60 minutes on your machine.

## 3. Assumptions (correct me or I'll proceed with these)

1. **Timing:** a portfolio is formed on the last trading day of each month. It uses the trailing 504 trading days (2 years) and is scored on the following month. The first rebalance is the end of January 2002, and the study uses one fixed data version.
2. **Weights:** long-only, fully invested, summing to 1, no leverage. Within a month, weights drift with prices (held, not rebalanced daily). Turnover is measured against the drifted weights.
3. **Names that stop trading mid-month:** they stay in the portfolio until their last trading day. From the next day their value is spread across the other holdings in proportion to their weights. Holding it as cash instead would make variance look artificially low.
4. **Gaps:** a missing day is never treated as a zero return.
5. **Scorecard:** realized variance of daily out-of-sample returns, annualized, over the whole period. The monthly series feeds the tests.
6. **Comparisons:** every portfolio is compared with equal weight, and the estimators are compared pairwise within each portfolio type. All comparisons are corrected together, with significance at 5%. The `null-hypothesis-testing` skill picks the test, which answers your open question about autocorrelation and heavy tails. The spec names the skill, its inputs and the pass bar, not the procedure.
7. **Stability:** the `data-analysis` skill compares estimators in 5-year blocks and in the 2008 and 2020 crisis windows.
8. **Known-answer targets:** the synthetic data has 500 names, 504 days and 3 planted factors. The two estimators that infer structure (denoised and factor model) must recover exactly 3 factors. Their error against the true covariance must be below the sample estimate's. On the true covariance, their minimum-variance portfolio's variance must be within 10% of the true long-only minimum. Are these the right targets?

## 4. Questions (from your idea's open list)

1. **Short histories.** My proposal: a member needs at least 252 of the 504 window days to enter optimized portfolios, and is estimated on the days it has. Excluded members are counted and reported for each rebalance. Equal weight uses the same eligible set, and an all-members equal weight is reported for reference. OK, or do you want full-history only?
2. **Shrinkage target.** My proposal is constant correlation only, with the shrinkage amount estimated from each window. Or do you want all three targets (constant correlation, single factor, identity) as separate estimators?
3. **Sample minimum-variance subset.** My proposal: the 100 members with the highest average daily dollar volume over the trailing window, which uses only price and volume known at the rebalance date. All four estimators also run on this subset, so the sample estimate is compared like for like. Is 100 the right size?
4. **Risk parity.** My proposal is equal risk contribution, which uses the full covariance, so the choice of estimator matters. Inverse volatility would be an extra reference portfolio only. Is that right?

Once you answer, I'll write the spec change as a Draft and bring it back for review.
