# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

## Overview
Three NumPy worlds (Snake, fish tank, predator and prey) sit behind one `Env` protocol that hands each role a compact observation array, never pixels. Hand-written PyTorch learners (DQN for Snake, PPO for the fish and both predator-prey sides) train against batched world copies on the laptop CPU for a fixed number of environment steps, record a learning curve on held-out curve seeds, and save the agent into a plain-file run folder. Every agent, trained, baseline or reference, is a `Policy`, so evaluation, replay and the statistics treat them alike. A world is signed off when its run folder holds every artefact DONE-01 names and the learner's note passes its checks. ## Data
- **Worlds are generated, not downloaded.** Every episode is set by one integer seed (AD-10), or starts from a planted state in tests (AD-16).
- **Seeds (DATA-01):** per world, evaluation seeds are 0–99, learning-curve seeds 100–119, training seeds 1,000,000 and up; `core.seeds` is the only source, and `learners` refuses a training seed below 1,000,000.
- **Observations** are float32 arrays per role, shape (agents, features): Snake per AD-04, fish and predator-prey per AD-06. Rewards per AD-07.
- **Run folder** `runs/<world>/<run-id>/` (AD-11): `record.json` (seed, settings, duration, curves, status: DATA-02), `policy.pt` only for a finished run (LEARN-03, AD-15), `scores/<agent>.json`, `comparisons.json`, `curve.png`, `recordings/<agent>-<seed>.json.gz`; a prey run adds `snapshots/<regime>/<role>/` (AD-13). Notes live in `notes/<world>.md`, committed; `runs/` is git-ignored.

## Cross-cutting concerns
- **Speed (QR-01):** training steps 16 world copies and makes one batched policy call per step; the loop ends at the run's `total_steps`, set per world from measured steps per second so the run fits the hour, and `time_limit_s` (3,600 by default) is the backstop (AD-18). The duration is recorded. Small MLPs run on CPU (AD-09).
- **Reproducibility (QR-03):** one `np.random.Generator` and one `torch.Generator` per run from the run seed, no global random state; `torch.use_deterministic_algorithms(True)` and a fixed thread count in the settings. The run length and curve points are counted in environment steps, never wall-clock time (AD-18); a run cut short by the time limit says so in its record and doesn't count as a repeat.
- **Errors:** a not-a-number loss or score stops the run with status `diverged` and the curve point where it happened; an interrupted run keeps its curve with status `stopped` and no `policy.pt`. A policy loaded into the wrong world raises `ValueError` naming both worlds.
- **Skills:** `evaluate` runs every significance claim as the `null-hypothesis-testing` skill specifies and draws every chart as the `dataviz` skill specifies (AD-14).
- **Testing:** world rules are tested on planted states from `worlds.from_state` (AD-16; each spec Given/When/Then is a test); learners on test worlds registered with `worlds.register` (AD-17); the reference adapter with SB3's `check_env`.

### AD-15: A saved policy is a plain network plus an output rule
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** store
- **Context:** PL-02 scores the SB3 reference from its run folder (CHECK-02), so `store.save_policy` and `store.load_policy` must round-trip `reference.train_reference`'s SB3-backed `Policy`. AD-11 saved a state dict plus our own architecture, which can't rebuild an SB3 model, and AD-01 lets only `reference` import SB3. SB3's deterministic action is the argmax of DQN's `q_net`, and PPO's action-network mean clipped to the Box bounds (https://stable-baselines3.readthedocs.io/en/master/modules/dqn.html and https://stable-baselines3.readthedocs.io/en/master/modules/ppo.html, read 2026-10-18).
- **Decision:** Every trained `Policy` hands over its greedy path as a `core.GreedyNet`: a `torch.nn.Sequential` of Linear and activation layers plus a head (`argmax`, `tanh` or `clip`). Our DQN gives its Q network with `argmax`, our PPO its actor mean with `tanh` (AD-05), and `reference` copies the SB3 model's layers into the same form with `argmax` or `clip`. `policy.pt` stores the GreedyNet, world and role; `load_policy` rebuilds one generic `Policy` from it.
- **Alternatives:** Save the SB3 zip and let `load_policy` call SB3 — breaks AD-01's import rule. A loader registry that `reference` fills in — a dynamic import that hides the dependency.
- **Consequences:** Reloaded agents don't need the library that trained them, and the reference copy is tested by matching `model.predict(deterministic=True)` on the curve seeds' observations. A learner whose greedy path isn't a plain layer stack (a CNN, per the EVAL-04 fallback) adds a layer type to `GreedyNet` first.
- **Probe:** none — the cited pages settle SB3's deterministic actions; the layer copy is checked by that test, not by a service.

### AD-16: Worlds start from a planted state
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** The golden cases TC-02–TC-06, TC-08–TC-12 and TC-14–TC-21 start from hand-placed states (a 99-cell snake, a ball 0.13 from a fish, a step-999 tank), and most of them can't be reached by playing from `reset(seed)`. `core.Env` has only `reset(seed)`.
- **Decision:** Each world has a frozen state type (`worlds.SnakeState`, `worlds.TankState`, `worlds.PreyState`) holding everything its rules read. `worlds.from_state(state, seed=0)` returns an `Env` already at that state, with `seed` driving later random draws (food, pellets); `worlds.state_of(env)` reads it back, and `from_state(state_of(env))` continues exactly as `env` would. `core.Env` doesn't change; no learner, baseline or pipeline step calls either function.
- **Alternatives:** A `set_state` method on `core.Env` — every `Env` (the SB3 adapter, the fakes, the replay doubles) would have to carry a test hook. Tests setting private attributes — ties every case to the worlds' internals.
- **Consequences:** The state types are the worlds' full rule state, so a rule that reads something new adds a field. Rule tests assert on `state_of` as well as on `StepResult`, which doesn't carry velocities or survival counts.

### AD-17: Test worlds are registered by name
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** worlds
- **Context:** TC-29 trains `learners.train_dqn` on a one-step 3-arm bandit and TC-30 runs `learners.ppo_learner` on a reach-target world, so each has a known answer. `train_dqn`, `evaluate.play` and the curve points all look a world up by name through `worlds.make`, and `EnvSpec.world` allowed only the four real worlds.
- **Decision:** `worlds.register(name, factory)` adds a test world that `worlds.make` then builds; its name must start with `test_`, and `EnvSpec.world` admits those names. Learners and evaluation run on a test world unchanged, by name.
- **Alternatives:** Passing an `Env` or a factory into `train_dqn` — it would also have to reach `evaluate.play` for the curve points, widening two public signatures and every call between them for tests only.
- **Consequences:** Real code never registers a world. `signoff` and the run folders know only the four real worlds, so test runs go to a temporary folder. Registration lasts for the process; tests clear it in a fixture.

### AD-18: A run's length is a step budget; the time limit is a backstop
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** learners
- **Context:** QR-03 needs a repeated run to give the same curve, but a run stopped at `time_limit_s` takes a different number of steps each time, and curve points spaced by time land on different steps. TC-31 and TC-32 need a run that ends on a fixed step. QR-01 still caps a run at an hour.
- **Decision:** `TrainSettings.total_steps` (environment steps summed over the world copies) sets a run's length. Curve point k is taken at the first batch step reaching k/`curve_points` of the budget, and `CurvePoint.progress` is steps over budget. `time_limit_s` stays as the backstop. A run that reaches it first ends `finished`, keeps the curve so far and says in its message how many steps it reached. The per-world budgets are set from a measured speed so a run fits the hour. Co-evolution snapshots and the SB3 reference use the same budget (AD-13, AD-08).
- **Alternatives:** A step budget in `hparams` — an untyped key that the reference and co-evolution would also have to read. Making the time limit deterministic by counting steps per second — the speed itself varies between runs.
- **Consequences:** `total_steps` is required, so every settings default names a budget. A budget set too low can cap EVAL-04; the risk below covers it.
