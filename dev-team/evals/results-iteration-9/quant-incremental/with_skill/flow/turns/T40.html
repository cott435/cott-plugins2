The S3 architecture is **Approved**, and AD-18 to AD-21 are now Accepted. Since you chose LightGBM, I removed the open model-choice risk. Lint shows 0 errors.

Pipeline design is in **New** mode for `qfeat`. Nothing is written until you confirm the workflows.

## Candidate workflows for `qfeat`
1. **PL-25 Run the procedure check**, with `qfeat check [--seed N]`. It builds the planted synthetic data and runs features, model and claims on it unchanged. It reports whether the planted feature passes and all 16 noise claims fail (FSYN-01 to FSYN-03). Both run pipelines also call it first.
2. **PL-26 Build the feature panel**, with `qfeat panel [--version N]`. It covers the rebalance schedule, a window, factor count, loadings, features and targets for every date, and the development/holdout split. The result is cached per data version, and both runs reuse it. A per-date segment, **PL-27 Build one date**, does each date's work in its own worker process. Like PL-19 in S2, it's how the panel pipeline splits its work, not a separate workflow.
3. **PL-28 Export the characterisation inputs**, with `qfeat explore`. It writes the development-only tables, tagged by 5-year block, for the `data-analysis` skill (FTEST-06).
4. **PL-29 Register a feature list**, with `qfeat register --review "…"`. It tunes the model settings on development dates only, picks the best single feature on development, and records the list with your review note (HOLD-03, FTEST-03, FMOD-03).
5. **PL-30 Development run**, with `qfeat run --development` (part of PL-24). In order: procedure check, panel, development rows only, walk-forward model, rank correlations, the 19 claims, then the report.
6. **PL-31 Holdout run**, with `qfeat run --holdout <list_id>` (part of PL-24). In order: procedure check, claim the holdout in the ledger (or refuse), panel, walk-forward model with the registered settings, claims on holdout dates, then the report listing every holdout run.

## Question
**Which will you actually run?** I recommend all six; each one covers requirements nothing else does. The smaller alternative is to fold PL-28 into PL-29, with registration exporting the characterisation inputs first. That fold doesn't fit well, though: your review of that analysis has to exist *before* you register, so it really is a separate step.

I'm assuming the model settings are tuned inside registration (PL-29), not in the development run. That way, development runs use either default settings or a registered list's.

The approval edits to the architecture and the two contracts aren't committed yet. Do you want them committed now?
