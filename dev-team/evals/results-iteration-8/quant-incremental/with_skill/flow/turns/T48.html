Before I write anything, here are the candidate workflows. Nothing goes into a `pipelines.md` until you confirm which ones you want.

**qfeat: candidate pipelines**

| # | Pipeline | Trigger | What it does | Likely milestone |
|---|---|---|---|---|
| 1 | Score features (inner) | called by 2, 3 and 5; also `qfeat score --synthetic` | Takes a feature frame and a target frame and runs the screens, the annual model fits with shadow copies, the shuffle gains and the null tests | bench |
| 2 | Planted-signal bench | `qfeat bench --seed 1..20` | Builds the no-signal, single-signal, joint-signal and copied-momentum panels, runs pipeline 1 on each, and produces the PLANT checks | bench |
| 3 | Development run (PL-22) | `qfeat develop <registration>` | Records the registration and logs new features, builds windows on the clipped loader, computes features and controls, builds targets, then runs pipeline 1 and stores the results | real data |
| 4 | Report | `qfeat report <run>` | Writes the static feature report: the number confirmed first, then the bench, development results and holdout | real data |
| 5 | Holdout (PL-23) | `qfeat holdout <registration>` | Checks the seal, opens the full loader once, retrains through the holdout months, then runs pipeline 1 on the carried features with Holm correction and writes the holdout record | holdout |
| 6 | Seal | `qfeat seal <registration>` | Confirms the registry and feature code are committed, then records the fingerprint, commit and time | holdout |

**qrisk (extend, no new workflow):** `build_windows` is already PL-18's step 2. `analyse_structure` gets a short entry function that runs PL-19's `spectrum` then `residualize`, so `qfeat` calls one public name. This only updates `qrisk/pipelines.md` and adds no pipeline.

**My recommendation:**
- **Take all six.** They match the six CLI verbs AD-21 names. Seal (6) is tiny, but it is the guard that makes the holdout honest, so it should have its own tested pipeline rather than be glue code.
- **The likely cut:** bench (1 and 2) comes first, mirroring S2's M4, so the null is proven calibrated before any real feature is scored. Then real data (3 and 4), then the holdout (5 and 6).

**One thing to know:** six pipelines in `qfeat` will trip the same Grow guideline that `qrisk` does (more than 3). I'd treat it the way you just did for `qrisk` and leave the package whole. The six pipelines share one set of types and one registry, and splitting the registry out would make the holdout guard a cross-package call.

Which do you want?
- **All six** (recommended)
- **The core set only (1, 2, 3, 5):** this folds sealing into the holdout command as a preceding check, and the report into develop and holdout as a final step.
