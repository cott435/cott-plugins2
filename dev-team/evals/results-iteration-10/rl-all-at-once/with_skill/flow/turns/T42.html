**3. ## Review

**Interface** (after Phase 0): the code is the contract, no more and no less.
1. Types match `contract.md`: fields, types, invariants. Nothing a step's In → Out needs is missing; no helper is frozen.
2. Signatures match the step tables, in their owner modules. Each stub names the open task that owns its step; no logic beyond types and validation.
3. One sample per case the contract names, valid and realistically shaped, never carrying a TC's expected value. Replay doubles replay an interaction the Protocol allows; fakes serve their fixtures.
4. `__init__.py` exports exactly the contract; each `Mitigated by` in the plan's dependency graph exists; each split task's tester can write its tests from the frozen interface and its `Read:`.

**Each phase**, per package, tests before code:
1. **Interfaces followed** (CR-09): no frozen type, signature or contract folder changed outside a Revise. Consumers use the declared types: no dict for a dataclass, no reaching into a provider's internals, no local redefinition. A stub is replaced only by the task it names; no cross-package import outside the contract; spine tests run on samples and doubles, not another step's code.
2. **Tests prove something:** each intent test asserts its TC case or acceptance bullet, loading expected values and tolerances from fixtures; none is assertion-free or weakened; Hypothesis runs the `ci` profile. Unit tests are specific, never computing the expected value with the code under test or testing only a mock. **Mutation check** (`.claude/agents/reviewer.md`): per acceptance bullet, the smallest change that should break it; a mutation no test catches is a finding.
3. **Correct to the spec:** each acceptance bullet truly met, not special-cased to the sample; the error paths the requirement names; seeding and determinism; numerical edge cases.
4. **Simple** (CR-11, CR-12, CR-42): no abstraction with one implementation outside the contract or an AD; no forwarding wrapper, one-method class, or class where a function does; no parameter, flag or config key every caller sets the same; no `try/except` that only re-raises or swallows, no checks the types already guarantee; no loop the library already provides. No near-copies within or across the phase's tasks: one concept is one function in its owner module (tests may repeat for readability). Each finding names the simpler form, with the same tests passing.
5. **Pipelines** (CR-10): entry functions read as their step tables (`dt layout`); step owners respected; spine baselines still selectable.
6. **The bar** (CR-07): diff this file, `pyproject.toml`, `scripts/` and `.claude/agents/` against the milestone's Base. Any loosening is Critical; new exceptions need an owner and expiry.
7. **Hidden and parallel risks:** where a real provider could act differently from its double (flagged for the system phase); fixed output paths, global state, test-order dependence.
8. **The rest:** readability, security, performance where a QR sets a number; reused reference or probe code has its Caveats handled and fits the contract; `dt lint` clean, pre-build sections replaced by `dt layout` pointers.

**Milestone exit**, over the whole diff, adds: the Scope's Exit holds; every Covers ID has a test; `check.sh full --exit` finds no stub; system tests use real providers; the same sample through a real provider and its double agrees; deferred requirements untouched; pip-audit ran.

**Severity:** Critical: a frozen interface changed, a weakened test, an intent test that misses a mutation changing its TC's expected output, a wrong answer, a loosened bar, a security hole, lost data; it stops the build. |---|---|
| **What it does** | Enforces which modules may import which, so layers and boundaries stay clean |
| **Speed** | Seconds on small repos, tens of seconds on large ones, because it builds the whole import graph |

## What it catches

```python
# yourpackage/core/engine.py
from yourpackage.cli import main     # violates "core must not import cli"
```
```text
Layers: cli > services > core
  yourpackage.core is not allowed to import yourpackage.cli
```
Why: low-level code that imports high-level code creates cycles, makes testing hard, and defeats the point of splitting into layers. Agents add the "quick" import that creates this.

root_package = "yourpackage"

## Generating contracts from the architecture

Contracts are generated, never hand-written (CONSTRAINTS.md Boundaries says "do not edit"):
- **Source:** single package: each component's `Depends on` column. Multi-package: the package dependency rules. Contracts sit between component subfolders (`pkg.data`) in a single package and between packages in multi.
- **Shape:** order the components so every dependency points down, then write one `layers` contract, top first. Components that don't depend on each other share a layer: `"pkg.a | pkg.b"` (independent siblings).
- **Narrower rules:** if a component may import only some of the layers below it (`reserve` → `profile`, never `data`), add a `forbidden` contract for that pair.
- **Not built yet:** wrap a module that doesn't exist in parentheses, `"(pkg.report)"`. The layer is optional while missing and enforced once it exists (verified). Without that, a fresh skeleton fails with `Missing layer`. `dt status` flags parentheses around a module that now exists; Extend removes them.
- **Grow:** when a component becomes a package, Extend rewrites its component contract as a package contract. The rule is the same, so code that passed keeps passing.

```toml
[[tool.importlinter.contracts]]
name = "Layers: report > profile > data"
type = "layers"
layers = ["(gridload.report)", "gridload.profile", "gridload.data"]

# Claude Code hooks: how the project's checks are wired

Loaded when build-setup writes or changes `.claude/agents/*.md` or `scripts/hooks/*`. Doc claims checked against the Claude Code docs on 2026-10-16 (`design/tooling-verification.md` §7); the scripts are tested by `skills/build-setup/tests/`.

## The contract

1. Claude Code runs the command with **JSON on stdin**: `tool_name`, `tool_input` (`file_path` is always absolute for Edit, Write and Read), `cwd`, and `agent_id` / `agent_type` inside a subagent. Stop and SubagentStop also get `stop_hook_active`.
2. **Exit 0** = fine. **Exit 2** = blocking: PreToolUse blocks the call; PostToolUse shows stderr to the agent (the tool already ran). Any other non-zero exit is a non-blocking error, and the action goes ahead.
3. **Stop blocks with JSON**, not exit 2: print `{"decision": "block", "reason": "…"}` and exit 0. An exit-2 Stop hook whose stderr mentions a missing file ("No such file or directory") is treated as non-blocking, and test output often does.
4. Exit-0 output is not shown to anyone unless it is a `{"systemMessage": "…"}`, and a SubagentStop `systemMessage` doesn't reach the main view either (checked live, Claude Code 2.1.292).
5. Matchers made of letters, digits, `_`, `-`, spaces, `,` and `|` are exact lists: `Edit|Write|MultiEdit|NotebookEdit`. Stop takes no matcher. The default timeout is 600 s; don't set a short one, because a timed-out hook doesn't block.

## Who owns which hook

| Source | Fires | Hooks |
|---|---|---|
| Plugin `hooks/hooks.json` (dev-team2) | every session, **including tool calls inside subagents** | SessionStart `dt status --summary` (doesn't reach subagents), PreToolUse `dt guard` (oracle files → ask), PostToolUse `dt lint` on docs |
| Project `.claude/agents/*.md` frontmatter | only while that agent runs, only in a trusted workspace | the role hooks below. A frontmatter `Stop` becomes `SubagentStop` |
| Project `.claude/settings.json` | main session | optional, on request: Stop → `stop_gate.sh gate` as a last safety net |

- **Plugin subagents ignore `hooks` frontmatter.** That is why the agents are copied into the project's `.claude/agents/`.
- **Workspace trust:** project frontmatter hooks need the trust dialog accepted. `claude -p` in a folder never trusted skips them silently (checked live: the implementer wrote `tests/intent/` unblocked); in a trusted folder they fire under `-p` too. Headless eval runs only exercise them with `--agents`, user-level agents, or a folder trusted beforehand.
- **Commands are absolute:** `bash "$CLAUDE_PROJECT_DIR"/scripts/hooks/<x>.sh`. A missing script is a non-blocking error, so a relative path that breaks after `cd` would silently turn the guard off.
- **The root comes from the input's `cwd`** (`project_root.sh`), walking up to the folder holding `scripts/check.sh`. `CLAUDE_PROJECT_DIR` stays on the main checkout in a worktree; `cwd` follows Claude into worktrees and after `cd`.

`--protected` reads the list from `scripts/check.sh protected`, so the guard and the Stop-time diff can't drift apart. ## Two layers

Every protection has two layers:
1. **PreToolUse guard** stops the normal route (Edit, Write).
2. **Stop-time diff** catches Bash writes (`sed -i`, `echo >`): `check.sh gate` diffs the whole protected list against `refs/checks/base` and lists untracked files; `check.sh collect` does the same for everything outside `tests/intent`.

The orchestrator sets the base with `git update-ref refs/checks/base HEAD` when it commits the tester's work and at each task start. Without it the diff falls back to HEAD, which misses changes the agent already committed. It can also write the task's package to `.claude/.check_pkg`, which `stop_gate.sh` passes on as `--pkg`, and, in each builder's worktree, the task's `Writes:` to `.claude/.task_writes`.

# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).
