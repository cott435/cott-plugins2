# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

One command runs the portfolio study at every month-end since 1998 and writes a report: the correlation structure of the members' returns, a ranking of four covariance estimates under three long-only portfolio rules by realized variance the following month, and a test of whether each rule's winner beats the sample estimate. A browser app shows prices, corporate actions, source differences, universe size, live run progress and the reports. See the [brief](brief.md) for why.

### Return structure (`STRUC`)
**Serves:** Goal 1
**Stage:** S2
**Source:** [ideas/return-structure-portfolios.md](ideas/return-structure-portfolios.md)
**Behavior:** At every month-end rebalance date of the portfolio study (PORT-02), the study looks at how that day's members moved together over the 252 trading days ending that day: how many eigenvalues of their correlation matrix stand above the level pure noise would reach, how much of the variance the market factor carries, and how much correlation is left once the dominant components are removed. The results form the structure part of the study report, as series over time.

**Requirements**
- **STRUC-01** The structure analysis is run with the `data-analysis` skill on every rebalance date's window: the eligible members of PORT-03 over the 252 trading days ending that day. It passes when the report has, for every window, the eigenvalue spectrum, the market factor's share of variance, and the raw and residual mean absolute correlation.
  - Given a completed study, when the structure part of its report is read, then each of the three is present for every rebalance date.
- **STRUC-02** For each window, the eigenvalues of the members' correlation matrix are compared with the random-matrix (Marchenko–Pastur) noise edge for that window's number of days and stocks, and the number of eigenvalues above the edge is reported.
  - Given a synthetic window of 252 days and 400 stocks with independent returns, when analysed, then at most 1 eigenvalue is above the edge.
  - Given a synthetic window of 252 days and 400 stocks driven by one common factor that explains 40% of each stock's variance, when analysed, then exactly 1 eigenvalue is above the edge.
- **STRUC-03** For each window, the market factor's share of variance is the largest eigenvalue of the correlation matrix divided by the number of stocks, reported as a series over time.
  - Given the one-factor synthetic window of STRUC-02, when analysed, then the share is 0.40 ± 0.03.
- **STRUC-04** For each window, the principal components above the noise edge (at least 1) are removed from every stock's returns, and the mean absolute pairwise correlation of what remains is reported next to the raw value, with the number of components removed.
  - Given the one-factor synthetic window of STRUC-02, when analysed, then 1 component is removed, the raw mean absolute correlation is ≥ 0.35, and the residual one is ≤ 0.08.
- **STRUC-05** Each window's results use only the returns inside that window.
  - Given a return changed on a day after rebalance date R, when the study is run again, then every structure result for R and earlier windows is identical.

**Edge cases & errors**
- A window with no eigenvalue above the edge → 1 component is still removed, and the window is marked as showing no structure above noise.

### Covariance and portfolio study (`PORT`)
**Serves:** Goal 1, Goal 3
**Stage:** S2
**Source:** [ideas/return-structure-portfolios.md](ideas/return-structure-portfolios.md)
**Behavior:** The researcher runs one command. At every month-end since 1998, it estimates the covariance of that day's members four ways, builds three long-only portfolios from each estimate plus an equal-weight portfolio, and holds them through the next month. It then ranks the estimates for each portfolio rule by the realized variance of the following months, reports turnover, and tests whether each rule's winner beats the sample estimate. The report, with the structure part (STRUC), opens in the app.

**Requirements**
- **PORT-01** One command runs the whole study and writes one report with three parts: structure, league table and significance.
  - Given stored data from 1998-01-02, when the command is run, then one report is written that has all three parts.
- **PORT-02** Rebalance dates are the last trading day of each month, from the first month-end on which 252 trading days have passed since 1998-01-02 to the last month-end whose following month is complete.
  - Given data from 1998-01-02 to 2026-09-30, when the study runs, then every rebalance date is a month's last trading day, the first is the first month-end with 252 trading days behind it, and the last is 2026-08-31.
- **PORT-03** At each rebalance date, the portfolios hold that day's members (UNIV-01) that have 252 trading days of returns ending that day; members with fewer are left out that month, and the number left out is reported for every rebalance date.
  - Given a stock added to the index with 100 trading days of history on rebalance date R, when the study runs, then the stock is in no portfolio formed on R, and R's left-out count includes it.
- **PORT-04** Every estimate and every weight formed on rebalance date R uses no return from after R.
  - Given a return changed on a day after R, when the study is run again, then every estimate and weight formed on R or earlier is identical.
- **PORT-05** The sample estimate is the sample covariance of the window's daily returns.
  - Given a synthetic window, when estimated, then it equals the sample covariance of those returns.
- **PORT-06** The shrinkage estimate pulls the sample covariance toward a constant-correlation target (each stock's own sample variance, and one correlation shared by every pair equal to the window's average sample correlation), by an intensity estimated from the window and reported for every rebalance date.
  - Given any window, when estimated, then the result equals (1 − δ) × sample + δ × target with 0 ≤ δ ≤ 1, and δ is reported.
- **PORT-07** The denoised estimate replaces the correlation matrix's eigenvalues below the noise edge of STRUC-02 with their average, keeps those above it, and rescales to each stock's sample variance.
  - Given any window, when estimated, then the eigenvalues above the edge are unchanged, those below it are all equal, the matrix's trace is unchanged, and its diagonal equals the sample variances.
- **PORT-08** The factor-model estimate is built from the principal components above the noise edge (at least 1) plus each stock's own residual variance, and the number of components is reported for every rebalance date.
  - Given the one-factor synthetic window of STRUC-02, when estimated, then 1 component is used and the diagonal equals the sample variances.
- **PORT-09** Every portfolio is long-only and fully invested: no weight is negative and the weights sum to 1, with no cap on any one stock and no transaction costs.
  - Given any portfolio formed in the study, when its weights are read, then each is ≥ 0 and they sum to 1 within 1e-9.
- **PORT-10** The minimum-variance rule picks the weights with the lowest portfolio variance under the estimate.
  - Given 2 uncorrelated stocks with variances 1 and 4, when the rule runs, then the weights are 0.8 and 0.2.
- **PORT-11** The risk-parity rule picks the weights for which every stock contributes equally to the portfolio variance under the estimate.
  - Given 2 uncorrelated stocks with volatilities 10% and 20%, when the rule runs, then the weights are 2/3 and 1/3.
- **PORT-12** The hierarchical risk-parity rule clusters the stocks into a tree by correlation, then splits the weight down the tree, giving each branch of a split a share inversely proportional to its variance.
  - Given 2 uncorrelated stocks with variances 1 and 4, when the rule runs, then the weights are 0.8 and 0.2.
  - Given 4 stocks in 2 pairs, each pair correlated at 0.9 and the pairs uncorrelated, with equal variances, when the rule runs, then each pair gets 0.5 of the weight.
- **PORT-13** An equal-weight portfolio of each month's stocks is formed at every rebalance date and shown next to every rule's ranking as the floor.
  - Given 400 eligible stocks on R, when the study runs, then the equal-weight portfolio gives each 1/400.
- **PORT-14** Between rebalance dates, weights drift with prices. A stock that stops trading during the month counts its return through its last trading day, that day included, and its weight is then held as cash at 0% for the rest of the month.
  - Given a stock with 5% of the portfolio whose last trading day is the 10th trading day of the holding month, when the month's returns are computed, then its return counts through day 10, and from day 11 its drifted weight earns 0%.
- **PORT-15** A portfolio's realized variance for a holding month is the variance of its daily returns within that month, annualized ×252.
  - Given 20 daily portfolio returns alternating +1% and −1%, when realized variance is computed, then it is 0.0001 × 252 = 0.0252.
- **PORT-16** For each rule, the four estimates are ranked by mean realized variance over all holding months, lowest first, with the equal-weight portfolio shown alongside.
  - Given a completed study, when the league table is read, then each of the 3 rules lists 4 estimates in increasing mean realized variance, plus the equal-weight value.
- **PORT-17** Turnover is half the sum of absolute weight changes from the drifted weights to the new weights at each rebalance date, averaged over all rebalance dates, and reported as a number for every estimate and rule without affecting the ranking.
  - Given drifted weights (0.6, 0.4) and new weights (0.5, 0.5), when turnover is computed, then it is 0.1.
- **PORT-18** For each rule, the winner is tested against the sample estimate with the `null-hypothesis-testing` skill, on the paired monthly realized variances: the null is that the winner's realized variance is no lower. It passes only if the null is rejected one-sided at 5% after correction across the 3 rules. The report states, for each rule, whether the null is rejected and the corrected p-value.
  - Given a completed study, when the significance part is read, then each of the 3 rules shows its winner, the corrected p-value and whether the null is rejected.
  - Given a rule whose winner is the sample estimate, when the significance part is read, then that rule says no test is needed.
- **PORT-19** The study report can be opened in the app.
  - Given a completed study, when the researcher opens it in the app, then its three parts' tables and charts are shown.
- **PORT-20** The full study runs in ≤ 1 hour.
  - Timed on the researcher's machine on the full history since 1998-01-02.

**Edge cases & errors**
- Study started with no stored data, or fewer than 252 trading days stored → refused with a message to run a refresh first.
- A member with a gap day (RET-07) in its 252-day window → counted as having fewer than 252 days of returns, so left out that month (PORT-03).
- A rule that finds no weights for an estimate in a month → the failure is reported, and that month is left out of every estimate's mean for that rule, so the comparison stays paired.
- Fewer than 2 eligible stocks on a rebalance date → no portfolios are formed that month, and the report says why.

`eqdata` is the Python data library and its command line. `server` is a separate Python install that serves `eqdata`'s public API over HTTP and one WebSocket (AD-13). ### AD-01: Python backend and TypeScript `web` in separate packages, one repo

### AD-04: Company identity is Sharadar's `permaticker`, with a curated override table

### AD-06: One SQLite file in WAL mode, with bitemporal rows
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** SYNC-05 (a failed refresh leaves the data as before), DATA-05 (every value keeps the date it was first known and replaced), RET-04 (as-of results), the VIEW edge case (the app keeps reading during a refresh), RUNS-03 (a CLI run visible in the app), QR-01 and QR-02. About 1,500 companies × up to 7,200 trading days of prices, so roughly 10 M rows.
- **Decision:** One SQLite file in WAL mode holds everything `eqdata` stores; the eqdata Data section lists the tables. Every market-data row has `known_from` and a nullable `replaced_on`, and a revision closes the old row and inserts a new one. A refresh downloads and cleans into staging tables, checks the staged rows against their pandera schemas, and commits the merge in one transaction. Readers in other processes keep seeing the last committed state until then. The validation run against the independent source (SYNC-04) follows the commit, so its findings describe committed data.
- **Alternatives:** A DuckDB file: faster scans, but one process can't read while another writes, so the app would block during every refresh. Parquet files with a swapped manifest: atomic, but findings and runs would need a second store, and revisions mean rewriting partitions.
- **Consequences:** Single-writer: SYNC-06's lock matches SQLite's model. The EDA reads through pandas or DuckDB's SQLite scanner. Query speed rests on indexes. If QR-02's benchmark fails, the fallback is a per-company price cache rebuilt on commit, not a store change.

### AD-07: Prices stored unadjusted; returns and adjusted levels computed at query time
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** RET-02–RET-05: total return includes dividends, ignores splits, and uses no event after the as-of date D. Back-adjusted vendor prices change whenever a later split lands, so they leak the future into earlier dates.
- **Decision:** For each day T, `r_T = (C_T × s_T + d_T × s_T) / C_{T−1} − 1`. Here `C` is the unadjusted close, `s_T` the split ratio effective on T (new shares per old, 1 otherwise), and `d_T` the cash dividend per post-split share going ex on T. Adjusted price levels as of D are back-adjusted using only events with ex-date ≤ D. A day with no close is a gap with no return (RET-07).
- **Alternatives:** Store Sharadar's `closeadj`: it embeds every future split and dividend, which breaks RET-04 and RET-05. Store pre-computed returns: fine for speed, but a revision would then need two rows changed in step.
- **Consequences:** RET-02 and RET-03's worked examples are the unit tests. The dividend convention on a split day is fixed here and checked by PB-01's samples.

### AD-08: REST JSON over HTTP for queries, one WebSocket for run events
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-09 (HTTP and WebSocket), UR-22 (the WebSocket is for live run progress), UR-23: "Queries go over plain HTTP." RUNS-01 and RUNS-02 need updates within 2 seconds. Two runtimes share no types.
- **Decision:** The `server` package is a FastAPI app (AD-13). Every query and action is a REST JSON endpoint, and `/ws/runs` carries only run events. Response types are Pydantic models, and `web`'s TypeScript types are generated from `/openapi.json` with `openapi-typescript`. Bulk series go out column-wise (`{dates: [...], close: [...]}`).
- **Alternatives:** GraphQL: one client, fixed views, no gain. Server-sent events for progress: would work, but the user named WebSocket.
- **Consequences:** A contract change shows up as a TypeScript compile error in `web`. The server binds to `127.0.0.1` only (single user, no sign-in).

### AD-09: Every run is an `eqdata` CLI process, reporting through the store
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `eqdata`
- **Context:** SYNC-06 (one refresh at a time, the refusal names the running one), SYNC-07 (an app-started run runs exactly as from the CLI), RUNS-01–RUNS-04 (live progress within 2 s, CLI runs visible, history kept, catch-up after reconnect).
- **Decision:** The server starts a run through `eqdata.launch_run`, which spawns the same `eqdata refresh|validate|eda` command the researcher types. A run takes the lock (a `runs` row with status `running` and a PID, released on exit and broken if the PID is dead) and appends numbered `RunEvent`s to the store. The server polls new events every 250 ms and pushes them over `/ws/runs`. A connection first gets the events after its `since`, then the current state of every running run, stamped with the latest `seq` already written, then each new event. A reconnecting client sends the highest `seq` it received and misses nothing.
- **Alternatives:** Runs as server background tasks: CLI runs would be invisible and the two paths would differ. A message broker: one process too many for one user.
- **Consequences:** Run events are the only progress channel, so the CLI's own progress output reads them too.

## Overview
A Vite + React single-page app served locally. It reads everything through the `server` package's REST endpoints, with types generated from its OpenAPI document (AD-08, AD-13). It subscribes to `/ws/runs` for live run progress. Every page is a data view or a quality tool. There are no screens that rank or filter stocks by return or signal (VIEW-08).

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `api` | Generated types, a typed REST client with TanStack Query hooks, the run-events socket with reconnect and catch-up by `seq` | RUNS-01, RUNS-02, edge cases (reconnect, new data available) | `server` HTTP/WebSocket contract |
| `charts` | Time-series, timeline and threshold-band charts on ECharts, built with the `dataviz` skill | VIEW-01–VIEW-04 | — |

| `universe` | Date page: that day's members and tickers; member count per trading day | VIEW-04, VIEW-07 | `api`, `charts` |

| `runs` | Start refresh, validation or analysis; live progress, warnings and errors; finished-run list | SYNC-07, RUNS-01–RUNS-04 | `api` |
| `report` | Renders the latest EDA `report.json` | EDA-03 | `api`, `charts` |
| `shell` | Layout, navigation, connection status, "new data available" banner | VIEW-08 | `api` |

**Skills:** `charts` follows the `dataviz` skill (not installed: UR-25, so the build agent works from its own guidance until it is). Visual design across `shell` and the pages follows the `frontend-design` skill.

## Interfaces
See [contract.md](contract.md). `web` consumes [server's contract](../server/contract.md), and the `eqdata` types it serves, and provides none.

## Cross-cutting concerns
- **Stale data during a refresh:** query results are cached until the socket reports a committed refresh. The banner then offers a reload, so the app keeps showing the previous data until then.
- **Testing:** Vitest for components against the frozen `tests/contracts/server.*` and `tests/contracts/eqdata.*` samples. Playwright for one end-to-end pass of each page against a seeded server.

# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. Neither a long contract (`dt context` loads only the sections a task reads) nor a dependency direction (import-linter enforces it between components of one package) is a reason to split. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

## Grow triggers

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, torchvision).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.
- A part runs or deploys on its own (a day-ahead forecast service).
