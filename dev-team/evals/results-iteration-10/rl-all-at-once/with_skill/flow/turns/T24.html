# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Changing a step table

Revise, and Sync when the doc changes, edit an existing table this way:

- Keep step names where the function survives; a split step gets new rows with new function names. Keep the pipeline's ID: a rebuilt package keeps its PL IDs where it can, so its golden cases still apply.
- If the entry sketch is gone (the spine was built), don't recreate it. The step table is the contract the code must match; the code change becomes a task.
- Keep `Used by:` lines true: add the PL ID to a symbol a new step calls, and remove it from one no step of that pipeline calls any more.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. One module per step owner (`profile.fit` → `profile/fit.py`; an owner given only as `profile` gets one module per related group of steps), never named like a generated file (`api.schema` beside a generated `api/schema.ts`: call it `api.schema_check`). A step whose module needs private helpers owns a folder instead (`core.train` → `core/train/`), holding them; no other step's code goes inside it. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. In a single package each component gets a subfolder whose `__init__.py` exports its contract only, so a later Grow is a folder move. Modules on no step: only `__init__.py`, the entry modules, `__main__.py` for a `python -m` trigger (dispatching each trigger to its entry), and `types.py`. Test folders sit at the repo root in every layout, multi-package included: `tests/intent/<pkg>/`, `tests/unit/<pkg>/`, never under the package's folder. Plan against `build-setup`'s size bar (500 lines per module, 60 per function, or `CONSTRAINTS.md`'s values): split a module expected to pass it now.

## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).

## System pipelines
### PL-09: Train a run
**Trigger:** `rllab train --world snake --learner dqn [--seed N] [--reference-of <run>] [--mode past] [--resume-from <run>]` · **Covers:** RUNS-01–RUNS-05, RUNS-09, VALUE-01, VALUE-02, POLICY-01, POLICY-02, TANK-09, PREY-08, COEVO-01, COEVO-02, COEVO-05, POOL-01–POOL-04, QR-01, QR-02
**Purpose:** one learner trains on one world within its time limit, and everything about the run lands in its folder.
1. `cli` → `lab`: `lab.train` (a `runs.RunSpec`)
2. `worlds` → `lab`: `core.World` (`worlds.make_snake`, `worlds.make_tank` or `worlds.make_prey`)
3. `runs` → `lab`: `runs.Recorder` (`runs.start_run`)
4. `lab` → `dqn`, `ppo`, `coevo` or `reference`: `core.World`, the learner's settings and `runs.Recorder` (`dqn.train_dqn`, `ppo.train_ppo`, `coevo.train_coevo`, `reference.train_reference`)
5. learner → `runs`: episodes, signals and saved agents through `runs.Recorder`; `coevo` also `runs.SwingReport` (`runs.save_swing`)
6. learner → `lab`: `core.Agent` (and from `reference`, its unmatched settings)
7. `lab` → `runs`: `runs.RunRecord` (`runs.finish_run`)

### PL-10: Evaluate a run
**Trigger:** `rllab eval <run> [--reference <run>] [--role predator|prey] [--n 200] [--eval-seed N]` · **Covers:** EVAL-01–EVAL-05, VALUE-03, VALUE-04, TANK-12, POLICY-03, PREY-11, PREY-12, DATA-02
**Purpose:** the run's agent, its hand-written player and its library twin play the same 200 unseen games, and the run keeps the report and its verdicts.
1. `cli` → `evaluate`: the run ids (`evaluate.evaluate` and the judges)
2. `runs` → `evaluate`: `runs.RunRecord` for the run and its twin (`runs.open_run`), and their training seeds (`runs.training_seeds`)

### PL-11: Watch an agent play
**Trigger:** `rllab watch <run> [--step N] [--seed N] [--speed 1]` or `rllab watch --player snake` · **Covers:** REPLAY-01–REPLAY-05, TANK-13, PREY-13
**Purpose:** any saved agent or hand-written player replays a game from its seed, next to its run's learning curve.
1. `cli` → `replay`: `replay.watch`
2. `runs` → `replay`: `runs.RunRecord` (`runs.open_run`)
3. `lab` → `replay`: `core.Agent` (`lab.load_agent` or `lab.make_player`) and `core.World` (`lab.make_world`)
4. `runs` → `charts`: `runs.Curve` (`runs.read_curve`) and `runs.Verdict` (`runs.read_verdicts`)
5. `charts` → `replay`: the curve panel, drawn into a `charts.Axes` of the viewer's `charts.Figure` (`charts.plot_curve`)

### PL-12: Cross-play a predator & prey run
**Trigger:** `rllab crossplay <run> [--episodes 20]` · **Covers:** COEVO-03, COEVO-04
**Purpose:** every saved predator plays every saved prey, the grid is drawn as a heat map, and the run keeps the grid and its circling verdict.
1. `cli` → `evaluate`: the run id (`evaluate.cross_play`)
2. `runs` → `evaluate`: the saved steps of each side (`runs.saved_steps`)
3. `lab` → `evaluate`: `core.Agent` per save (`lab.load_agent`) and `core.World` (`lab.make_world`)

### PL-13: Judge settling
**Trigger:** `rllab judge settled <past-run> <both-run>` · **Covers:** POOL-05
**Purpose:** a past-opponents run and a both-at-once run are compared, and the past run keeps the settled verdict.

## Data
No outside data (DATA-01). Every episode is generated by a world from an integer seed.

- **Seeds (AD-09):** a run's seed drives one `np.random.Generator` and `torch.manual_seed`. Training episodes draw their seeds from `[0, 2³¹)` and every seed used is saved with the run. Evaluation seeds come from `[2³¹, 2³²)`, so they can't overlap. `evaluate` still checks the saved training seeds and refuses on any overlap (DATA-02, EVAL edge case).
- **Run folders (AD-08):** written only by `runs`; the layout is in [packages/runs/architecture.md](packages/runs/architecture.md).
- **Training setup:** a run stops at its step cap or its wall-clock limit, whichever comes first (RUNS-09). A library run copies its hand-written twin's world settings, seed, step cap and time limit (AD-10).

## Cross-cutting concerns
- **Time limit (QR-01, RUNS-09):** `Recorder.should_stop` checks the wall clock after each episode and each update. At the limit the learner saves its current agent and returns, and the run is marked "time limit reached". The default limit is 60 minutes.
- **Rented computing (QR-02):** a run with `device="cuda"` is recorded as rented. Its spec carries the machine's hourly price, and `runs` writes the cost (duration × price) to `run.json`. `rllab list` totals the cost per world against the $5 cap (AD-05).
- **Reproducibility (RUNS-04, REPLAY-05, SNAKE-09):** CPU only by default, `torch.use_deterministic_algorithms(True)`, a fixed thread count saved in the spec, and no global random state: every package takes a `Generator` or a seed (AD-05, AD-09).
- **Failure states:** a non-finite loss or value raises `core.Diverged`, and the run is marked "diverged" at that step with its curve kept. A run whose `run.json` still says "running" with no live process is shown as "incomplete" (RUNS edge case).
- **Significance claims:** every one (EVAL-03, PREY-12, COEVO-04, POOL-05) goes through `evaluate`, which follows the `null-hypothesis-testing` skill: null and alternative, statistic, 5% level, null distribution. `evaluate` saves the inputs and the skill's result as a `runs.Verdict`. No other package makes a significance claim.
- **Charts:** every chart is drawn by `charts` following the `dataviz` skill, and `replay` reuses `charts.plot_curve` for its curve panel.
- **Speed:** worlds step all their agents at once with NumPy array math, with no per-fish Python loop. Cross-play and evaluation games run in a process pool, because each game is independent given its seed.
- **Testing:** pytest, one `tests/` folder per package. Worlds and players are tested against the spec's Given/When/Then cases, learners on tiny worlds for a few hundred steps, and `reference` only when it is installed. Contract fixtures live under the repo's `tests/contracts/<id>.<symbol>/`, shared by provider and consumers.

### AD-14: Every saved report is a `runs` type, read and written through `runs`
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `runs`, `evaluate`, `coevo`, `charts`
- **Context:** AD-08 says only `runs` writes the run folder, but the evaluation report, the cross-play grid and the swing report were `evaluate` and `coevo` types. `runs` depends only on `core`, so it could neither write nor read them, and `pipeline-design` found no contract way to save them or to read `swing.json` back for the settled verdict (POOL-05, UR-42). `Verdict` already lives in `runs` for the same reason.
- **Decision:** Every report type saved in a run folder is defined in `runs`, which writes and reads it. Its members are listed in the contract's `runs` section.
- **Alternatives:** Each owner writes its own file through a path `runs` hands out: it breaks AD-08's single writer, and readers would need the owner's code. `runs` depending on `evaluate` and `coevo`: a cycle, since both depend on `runs`.
- **Consequences:** `charts` needs only `runs` for every type it draws. A new saved report adds its type and its writer to `runs`.
- **Probe:** none — no external dependency.

### AD-15: One package per component in a uv workspace
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-46: "split the package before build planning". The single `rllab` package had grown to 8 pipelines (the limit is about 3) and a 505-line contract. It also carries three dependency stacks that not every part needs: NumPy alone for the worlds and run folders, PyTorch for the learners, and Stable-Baselines3 with Gymnasium for the reference runs only (AD-04), which was held apart by an import rule rather than an install. UR-47: "Yes, go with one package per component.", replacing the earlier single-package choice.
- **Decision:** Each of the twelve components becomes a workspace package under `packages/<id>/`, with the same id, so every contract ID, Covers entry and package pipeline ID carries over. Each ships `src/rllab/<id>/` in one `rllab` import namespace and is distributed as `rllab-<id>`; one uv lockfile pins all of them. Each `pyproject.toml` declares exactly the dependencies in Dependency rules, and import-linter checks the same graph in CI. `reference` is the only package with the library, and `lab` takes it as an optional extra. Flows that cross packages are System pipelines PL-09–PL-13.
- **Alternatives:** Fewer, larger packages (`core`, `worlds`, `learners`, `reference`, `lab`, `analysis`): fewer `pyproject.toml` files, but contract IDs in the merged packages change (`dqn.train_dqn` → `learners.train_dqn`) and `analysis` would hold 6 pipelines, over the limit again. Keep one package with import-linter layers: the pipeline count and contract size stay, and the library stays an import rule rather than an install boundary.
- **Consequences:** Twelve small `pyproject.toml` files to keep in step, but each package's docs fit a build agent's context, and the hand-written stack installs and tests with no library present. `evaluate` can no longer draw its own figures, so `cli` draws the cross-play heat map (PL-12). Moving a symbol between packages is now a contract change.
- **Probe:** none — no external service; uv workspaces are a packaging choice.

## Risks and open questions
- **PB-01 (AD-04):** C2 and C3 passed. C4 (does the library's PPO learn the tank in 60 minutes?) is still to run, so AD-04 stays Proposed. If it fails, POLICY-02 and POLICY-03 have no fair answer key. Fallback: wrap the tank as 8 independent single-fish tanks for the library run only, and bring that change back for a decision. Before C4 runs, `api-probe` must update the probe to the changed spec (AD-13): the stand-in tank's touch distance becomes the 0.2 ball radius, C1 is rerun, and C4's Pass becomes a significant win over swim-away fish at 5% instead of 1.5×.
- **The ball is seen one step before it touches (AD-13):** with sight a quarter-radius and the ball's radius a fifth, both measured to its centre, the ball comes into view only 0.05 tank-radii from contact. At ball speed 0.5 and a step of 0.1 s it covers that in one step, and a fish at top speed moves 0.04. So no fish can dodge what it sees: trained fish can win only by where they wait (away from the ball's paths, near fish that are still alive). The spec chose this (TANK-02, TANK-05, UR-37), and the rerun of PB-01 C1 will show whether trained fish have room to beat swim-away fish. If not, the fix is a spec change (measure sight to the ball's edge, or widen sight) through `spec-writing`.
- **Tank training speed (QR-01):** PPO on 8 fish × 600 steps per episode must reach its verdicts in 60 minutes in pure NumPy and PyTorch. Mitigation: vectorised world steps, and measure steps per second in the first S2 milestone before tuning anything else. AD-05's rented GPU is the last resort.
- **Cross-play cost (COEVO-03):** 20 × 20 cells × 20 episodes is 8,000 tank episodes. That doesn't count toward QR-01's training limit, but it may take tens of minutes. Mitigation: a process pool, run once per run.
- **Settling test (POOL-05):** each run gives one swing. The significance test must resample the episode-level outcomes saved at each save point. The `null-hypothesis-testing` skill chooses the procedure, and `swing.json` keeps what it needs.
- **Snake's limited view (AD-07):** with only nearby danger visible, long snakes may trap themselves. This is enough for 1.5× the head-toward-food player, but may cap the score. A richer observation would be a later decision.
