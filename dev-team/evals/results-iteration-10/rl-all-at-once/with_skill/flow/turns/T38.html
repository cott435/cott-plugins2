# Milestone shape: interface, step spines, wiring, system

Read when writing a milestone's tasks. Examples: `examples-phase0.md`.

A milestone is planned from its pipelines' steps: each step has one owner, one module and typed `In → Out`, so it is the unit of work. The plan freezes every boundary between steps first, so the work on both sides starts at once instead of queueing behind one spine. Every task carries `**Kind:**`:

```
## Phase 0: Interface              interface (solo, first)       types, signatures, samples, fakes, exports, __main__
## Phase 1: Step spines            spine, one per step           each writes its owner module only
## Phase 2: Wiring and thicken     wiring, one per pipeline      its entry module, smoke test
                                   thicken (tasks.md)            each after its step's spine
## Phase 3: System                 system (solo, last)           fakes swapped for real providers
```

Phases name the usual waves; the dependency graph (`tasks.md` step 9) decides what may start. Tester halves of split tasks start right after the interface.

**a. Interface task** (`**Kind:** interface`, `**Step:** contract`, solo, `**Depends on:** —`). It freezes, as code, every boundary in the milestone whose two sides belong to different tasks:
- each contract `type` section named in a milestone step's `In → Out`, every one, since the step's signature needs it, written into its owner's `types.py`, with a schema (pandera for a frame, JSON Schema across runtimes) and one sample per case in `tests/contracts/<component>.<Type>/`. A case naming a probe sample (`PB-01 samples/sync_added.json#0`) puts `PB-01:samples` in `Read:`; the task derives the type's sample from it, never copies it
- each new step's signature in its owner module, with the body `raise NotImplementedError("<task id>")` naming the task that replaces it
- for each function a pipeline calls from another pipeline or package (its `**Boundary:**` line): a fixture-backed fake serving its fixtures, where the caller's tests load it
- for each object with behavior a step passes (a Protocol or class: `core.Dataset`, `runstore.RunWriter`) and each call into another component's function: the Protocol or signature plus a fixture-backed replay double in `tests/contracts/<component>.<Type>/`. The double is that type's sample, not a fake: the system task never swaps it
- each component's `__init__.py` exports, and the package's `__main__.py`: the dispatch from each pipeline's trigger to its entry function, whose signature it stubs naming the wiring task, in that pipeline's own entry module

Not frozen: helpers, private functions, anything one task owns end to end, and boundaries an earlier milestone froze. `Read:` the type and boundary symbols. Acceptance: every sample validates against its type; every signature imports; each fake and replay double serves its fixtures. A human approval a requirement places before several steps (a design direction) is asked during planning or is this task's acceptance ("direction approved; `design.Theme` sample written"); those steps build on the sample, with no edge to the step that sets it. `Writes:` each component folder as one glob (`src/gridload/profile/**`) plus its contract folders; `task-size` doesn't count them. A milestone across packages may have one interface task per provider, all solo and first; interface tasks never depend on each other. When one runtime's types are generated from another's schema, the providing interface task runs the generator and writes the generated file too (its `Writes:` claims it).

**b. Step spines** (`**Kind:** spine`, `**Step:** PL-NN.<function>`, solo, XS or S). One per new step, library class rows included, each depending only on the interface task: it replaces the stub naming it with the step's spine version from the step table. `Writes:` its owner module, or its owner folder as one glob (`src/leaflab/core/train/**`), and its unit test, nothing else; steps sharing one module share one spine task. A provider waiting on a probe gets no spine: its stand-in row (`pipeline-design`'s `steps.md`) is built instead, and the real spine goes in the milestone the probe's Answer unblocks. Acceptance: the step's input sample gives a schema-valid output; the signature is unchanged. A step another pipeline provides (`PL-01 as built`) gets no spine.

**c. Wiring** (`**Kind:** wiring`, `**Step:** PL-NN`, solo). One per new pipeline: the entry function in the pipeline's own entry module (the layout's, never one module shared by several pipelines), so wiring tasks run side by side, and its smoke test. `__main__.py` is the interface task's. It depends on its pipeline's spines, since the smoke runs them (`order`, `none: integration: …`), never on their thicken tasks. A call to another pipeline or package runs against that boundary's fake, so wiring PL-02 never waits for PL-01. Acceptance: the smoke command runs end to end and is committed as the pipeline's smoke test; the pipeline's pre-build sections are replaced by a `dt layout` pointer (`dt tick` prompts `dt prebuild-clear`).

**d. System task** (`**Kind:** system`, solo, last). It swaps each fake for the real provider, in the entry its wiring wrote (a `file` edge), and runs every smoke command and the milestone's golden cases on the real chain; the boundary samples still validate against real output. Its row to the provider's wiring is `order` · `none: integration: swaps in the real <provider>`. System tasks never depend on each other: each builds its golden-case stores from fixtures, and a case that needs another system pipeline's real output joins that pipeline's system task. Multi-package: one per new system pipeline, `**Step:**` that pipeline, `**Package:**` the owner of its first step, `**Reason:** system task`; the root has no pre-build sections, so no `dt layout` bullet. Single package: `**Step:**` the calling pipeline. A golden case that needs real collaborators (a thickened step, a class's real upgrade) is the system task's acceptance, never the wiring's, so wiring depends only on its pipeline's spines and fold tasks. A milestone with no fake and no such case has no system task.

**Folds** keep the task count down. The pipeline's wiring depends on a fold task, so a fold is allowed only where that task is XS and the critical path doesn't grow. Record each on its task as `**Reason:** fold: <rule>`:
- A step with a golden case whose spine and thicken are both in the milestone, or whose spine version is its whole behavior, may be one task that replaces the stub itself, `**Kind:** thicken` and `**Mode:** split`, never a spine; with a thicken folded in, its acceptance keeps the baseline selectable.
- A trivial step (pass-through, print) is built by its pipeline's wiring task; its stub names the wiring task.

**Fakes and stubs.** A fake is allowed only where a pipeline calls another pipeline or package: both sides test against the same fixtures, so neither drifts from the contract unseen. Mocking a step is forbidden: a step's spine is the real baseline, and its consumer builds against the type's sample (for a Protocol or class, its replay double). The interface stubs are the floor's one stub carve-out (`build-setup`'s CR-02): allowed while the task they name is open; the gate fails on one naming a done task, the milestone exit on any.

**Frozen means frozen.** Changing a frozen type, sample, signature or fake is a `contract-change`: `architecture-design` Revise, then a new interface task naming the symbol in `Read:`, never an edit to make a test pass. The bar enforces it (CR-09): once a contract folder exists at a task's base the implementer can't write it, and `dt guard` asks before any edit no open interface task covers. The re-freeze runs in the main session, since the implementer's guard blocks a folder frozen at the base.

A probe's code goes to the step that calls the same API (`PB-01:probe.py:sync_all`); its redacted samples (`PB-01:samples`) go to the interface task (`phase0.md`) and, as raw-shaped test input, to that step's spine and thicken tasks. Over 300 lines, add a selector so the packet stays small: `RF-01:deseasonalize` (one function or class), `RF-01:outline`, or `RF-03:<heading>` for a doc. With no selector a long file prints as its outline and `dt lint` warns `ref-large`. Whether to reuse the code is the builder's call; don't write it into Acceptance. A decision whose Consequences adopt what a probe spent (Plaid Items it linked) gets its own task in the milestone that builds that step.

## 7. Build mode

- `split` (tester, then implementer) when the task adds or changes behavior with a checkable outcome: anything a TC case, Given/When/Then or model criterion covers.
- `solo` for interface, spine, wiring, system, refactor, glue and doc-sync tasks.

`mode_violations` flags a task that breaks the rule. An override needs `**Reason:** <one line>` on the task. **A split task tests symbols a frozen interface declares** (the interface task's types and signatures), so the tester never writes against a guess and starts right after the interface, beside the implementers. Its `Depends on` is the implementer half's; the tester half waits only on the interface.

## 8. Checkpoints

`### Checkpoint after M<n>-T<nn>` at the end of a wave, naming the wave's last task in plan order: usually once after the wiring and thicken wave, when every pipeline runs end to end. `### Checkpoint: milestone exit` last. Use the blocks in `../examples.md`. A separate read-only reviewer runs each one; the orchestrator records its findings with `dt finding`, not this skill.

## 9. Dependencies, Writes, the graph, Verify

- **`Depends on:`** resolves, points only backward (position counts, not ID number), is acyclic, and holds only edges nothing mitigates.
- **`Writes:`** is exact paths, or a folder glob the task owns, and is an exclusive claim: two tasks with no `Depends on` path between them never write the same path (`writes`). Shared files (`__init__.py`, `types.py`, `__main__.py`, and shared test helpers: `conftest.py`, a golden-case store builder) belong to the interface task; each pipeline's entry module to its wiring and system tasks (`phase0.md`). No `Writes:` under `tasks/`: builders never tick `todo.md` or record findings; the orchestrator does after each merge.
- **`## Dependency graph`**, after the last checkpoint: one row per edge between tasks, `| From | To | Kind | Mitigated by |`. From is the task that needs, To the one it needs; each cell starts with the task ID. Mitigated by names the interface and the task freezing it (`profile.Profile sample (M1-T01)`), or says `none: <reason>`.

| Kind | Meaning | Mitigation |
|---|---|---|
| `data` | One step's output feeds another's input | The type and its sample |
| `call` | A pipeline calls another pipeline or package | The fixture-backed fake |
| `file` | Two tasks must write one file | Move the shared part to the interface task; else serial. Two wiring tasks never share a file: each writes its own entry module. Two steps' thicken tasks on one module: the interface task's layout splits it (each step its own file, the old module re-exporting); never chain them |
| `code` | A task changes code another task wrote (a thicken after its step's spine or an earlier thicken of that step) | None: serial |
| `contract-change` | A task changes a frozen interface | None: serial, plus a new interface task |
| `order` | Integration (a wiring or system task runs the steps it wires: `none: integration: the smoke runs it`), or risk or learning ("do X first to learn Y"; never a human approval: `phase0.md` a) | None: reason required |

A spine never has an edge to another step's task: it builds against the interface's samples and doubles. A mitigated edge documents why two tasks run side by side and never appears in `Depends on`; an unmitigated one must (`edges`). Every `Depends on` has its row, except a dependency on the interface task, which every task has and needs none. The table is the reviewable argument for every serial step.
- **Width.** `dt status` gives `critical_path`, `waves`, `width` and `parallelism`; on the fresh plan `dt ready` lists only the interface task(s). Mostly width-1 waves mean an edge an interface could mitigate is ordering tasks.
- **`Verify:`** The interface task's runs the schema check over every sample; every other task's runs its focused tests and `scripts/check.sh gate` (`--pkg <pkg>` in multi-package), plus its pipeline's smoke command (tests.md Strategy, else the Trigger plus ` --smoke`) once its `Depends on` path reaches that pipeline's wiring task: wiring and system tasks always. A thicken task running beside the wiring is smoke-tested by the gate after each merge. Only the modes `fast`, `gate` and `full` exist.
- **`Read:`** lists the IDs (references as `RF-NN[:selector]`, probes as `PB-NN:<file>[:<symbol>]`, `PB-NN:outline` or `PB-NN:samples`) and paths a builder needs, and nothing else. A split task's names its step's function, so the tester knows the signature it tests. Check each packet with `dt context <task>`: it must resolve and stay under 2,000 lines.

138	## Cross-cutting concerns
139	- **Time limit (QR-01, RUNS-09):** `Recorder.should_stop` checks the wall clock after each episode and each update. At the limit the learner saves its current agent and returns, and the run is marked "time limit reached". The default limit is 60 minutes.
140	- **Rented computing (QR-02):** a run with `device="cuda"` is recorded as rented. Its spec carries the machine's hourly price, and `runs` writes the cost (duration × price) to `run.json`. `rllab list` totals the cost per world against the $5 cap (AD-05).
141	- **Reproducibility (RUNS-04, REPLAY-05, SNAKE-09):** CPU only by default, `torch.use_deterministic_algorithms(True)`, a fixed thread count saved in the spec, and no global random state: every package takes a `Generator` or a seed (AD-05, AD-09).
142	- **Failure states:** a non-finite loss or value raises `core.Diverged`, and the run is marked "diverged" at that step with its curve kept. A run whose `run.json` still says "running" with no live process is shown as "incomplete" (RUNS edge case).
143	- **Significance claims:** every one (EVAL-03, PREY-12, COEVO-04, POOL-05) goes through `evaluate`, which follows the `null-hypothesis-testing` skill: null and alternative, statistic, 5% level, null distribution. `evaluate` saves the inputs and the skill's result as a `runs.Verdict`. No other package makes a significance claim.
144	- **Charts:** every chart is drawn by `charts` following the `dataviz` skill, and `replay` reuses `charts.plot_curve` for its curve panel.
145	- **Speed:** worlds step all their agents at once with NumPy array math, with no per-fish Python loop. Cross-play and evaluation games run in a process pool, because each game is independent given its seed.
146	- **Testing:** pytest, from the repo root: each package's tests live in `tests/intent/<pkg>/` and `tests/unit/<pkg>/`. Worlds and players are tested against the spec's Given/When/Then cases, learners on tiny worlds for a few hundred steps, and `reference` only when it is installed. Contract fixtures live under the repo's `tests/contracts/<id>.<symbol>/`, shared by provider and consumers.

162	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
163	- **Context:** UR-11: the user writes the learners "myself in NumPy/PyTorch, then compare against a library". VALUE-01 and POLICY-01 ask for learners built from basic array and gradient operations. It is a one-person learning project.

The replay buffer, targets, advantages, clipping and update loop are written by hand. Nothing imports a reinforcement-learning library except `reference`.
165	- **Alternatives:** NumPy only, with hand-written backprop: it teaches backprop rather than reinforcement learning, and the library comparison would be against a different numeric stack. JAX: capable, but has less laptop tooling and isn't what the user named.
166	- **Consequences:** One numeric stack across every learner, so the hand-written and library runs are compared on the same tensors. Which package carries which part of it is AD-15's.
167	- **Probe:** none — no external service; the library versions are settled in AD-04.

169	### AD-02: DQN as the value learner
170	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `dqn`
171	- **Context:** UR-05: Snake is a "good first env for DQN-style value learning". VALUE-01–VALUE-04 need a value learner that beats the head-toward-food player by 1.5× and reaches 90% of a library version within the time limit.
172	- **Decision:** DQN: an MLP from observation to the value of each of the 3 moves, a replay buffer, a target network synced every N steps, ε-greedy exploration with a linear decay, Huber loss, and Adam. Its settings and defaults mirror Stable-Baselines3's DQN, so the library run copies them one-for-one (AD-10). It logs mean value estimate, loss and ε (RUNS-03).
173	- **Alternatives:** Tabular Q-learning: it would work on Snake's small observation, but it isn't the method the user asked for. Double or dueling DQN: these are steps on the Snake method ladder, which is out of scope. They can become a setting later.
174	- **Consequences:** DQN has a library twin with the same knobs. Divergence shows up as a non-finite loss or value and is caught at the update (VALUE edge case).
175	- **Probe:** none — the method is hand-written, with no external dependency.

177	### AD-03: PPO as the policy learner, one Gaussian policy over turn and speed
178	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `ppo`, `coevo`
179	- **Context:** UR-08: the fish tank is "good for policy-gradient / PPO and continuous control". POLICY-01 needs continuous turn and speed. TANK-09 and PREY-08 need one shared policy per side, trained on every member's experience.
180	- **Decision:** PPO with the clipped objective, generalised advantage estimates, a separate actor and critic MLP, and a diagonal Gaussian over (turn, speed) with a learned log-std. The world clips actions to its limits (TANK-04). Each fish is its own trajectory: a caught fish's trajectory ends there, and the others continue. `ppo.PPOLearner` exposes act, record and update separately, so `coevo` can drive two learners in one loop. It logs policy loss, value loss, entropy, log-std and clip fraction (RUNS-03). Defaults mirror Stable-Baselines3's PPO.
181	- **Alternatives:** REINFORCE: simpler, but too noisy for a 60-minute budget. SAC: strong on continuous control, but off-policy and not the method the user named.
182	- **Consequences:** The same learner serves S2 and both sides of S3. Policy collapse is visible in the entropy and log-std signals (POLICY edge case).
183	- **Probe:** none — the method is hand-written, with no external dependency.

185	### AD-04: Stable-Baselines3 as the reference, an optional extra behind one module
186	**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `reference`
187	- **Context:** UR-11: compare against a library. VALUE-01 and POLICY-01: the hand-written learners must run with the library not installed. VALUE-02 and POLICY-02: the library version trains on the same world. Stable-Baselines3 supports DQN on Discrete actions and PPO on Box actions ([RL algorithms](https://stable-baselines3.readthedocs.io/en/master/guide/algos.html), read 2026-10-18). It requires Python 3.10+ and PyTorch ≥ 2.8 ([installation](https://stable-baselines3.readthedocs.io/en/master/guide/install.html), read 2026-10-18). With a `seed` given at model creation it is deterministic on one platform, but not across platforms or between CPU and GPU (RL algorithms page, "Reproducibility"). Its vectorised environments reset each sub-environment automatically when that sub-environment is done, returning the last observation in `infos[i]["terminal_observation"]` ([vectorized environments](https://stable-baselines3.readthedocs.io/en/master/guide/vec_envs.html), read 2026-10-18). The docs say nothing about several agents sharing one episode. Its PPO `n_steps` is the number of steps run for each environment per update, so a rollout holds `n_steps × n_envs` steps, and `batch_size` is the minibatch size over that whole rollout ([PPO](https://stable-baselines3.readthedocs.io/en/master/modules/ppo.html), read 2026-10-18). PB-01 C2 and C3 (2026-10-18, SB3 2.9.0, torch 2.14.1): the dead-slot `VecEnv` ran 60 updates over 2 tank episodes with no slot-rule violation, at 9,838 agent-steps/s, and a seeded run repeated its curve and weights exactly.
188	- **Decision:** The `reference` package depends on `stable-baselines3` 2.x and `gymnasium`, both pinned in the lockfile; `lab` takes it as the optional extra `rllab-lab[reference]` (AD-15). Snake is wrapped as a Gymnasium `Env`. The tank is wrapped as a custom `VecEnv` with one slot per fish, sharing one tank. A caught fish's slot reports done once, with its terminal observation. After that it returns a zero observation flagged as dead with zero reward until the tank episode ends, and then every slot resets together. The adapter logs each finished tank episode through the run's `Recorder`, and a callback copies the library's loss and exploration values into the run's signals. Library agents are saved as `.zip` files and loaded back as a `core.Agent`. No other package depends on or imports the library.
189	  - **Step-count conversion:** `PPOSettings.n_steps` counts agent-steps across every agent of the role, while the library's `n_steps` is per environment, and each fish slot is one environment. The adapter passes `n_steps // n_slots`: the default 2048 across 8 fish becomes the library's `n_steps` 256, so both learners update after the same 2048 agent-steps. If `n_steps` isn't a multiple of the slot count, the adapter rounds down and lists `n_steps` as unmatched (AD-10). `batch_size` already means a minibatch of the whole rollout in both, so it passes through unchanged. Snake has one environment and DQN has no `n_steps`, so nothing converts there.
190	- **Alternatives:** CleanRL: single-file scripts that are good to read, but not an installable answer key with a stable API. RLlib: it handles multi-agent tanks natively, but is far heavier than a laptop project needs. Using PettingZoo and SuperSuit for the shared episode: the same dead-slot idea with two more dependencies, and our own world API would have to change to fit theirs.
191	- **Consequences:** The library's PPO trains on some dead-slot steps that our PPO doesn't see, so the 90% comparison (POLICY-03) is slightly in our learner's favour on data use. The probe below checks that this doesn't break the library's learning.
192	- **Probe:** PB-01 — does Stable-Baselines3 PPO learn the 8-fish tank through the shared-episode `VecEnv` (dead slots inert until all reset) within 60 minutes on the laptop CPU, and does a seeded run reproduce its learning curve?

194	### AD-05: Laptop CPU by default, rented GPU only as a measured fallback
195	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
196	- **Context:** UR-15: "Laptop CPU (Apple Silicon)". UR-16: "I can rent a cloud GPU for a few dollars if needed." QR-01: 60 minutes per world on the laptop CPU. QR-02: at most $5 rented per world. RUNS-04 asks for exact reproduction on the laptop. PyTorch doesn't guarantee reproducible results across platforms or between CPU and GPU, even with the same seed ([Reproducibility](https://docs.pytorch.org/docs/2.14/notes/randomness.html), read 2026-10-18).
197	- **Decision:** Every run uses `device="cpu"` with deterministic algorithms and a fixed thread count saved in the run spec. Apple's GPU backend (MPS) isn't used. A run may set `device="cuda"` on a rented GPU only after a laptop run of that world has hit its 60-minute limit short of its verdicts. That run is marked as rented: its spec carries the machine's hourly price, and its cost (duration × price) is noted in its run folder.
198	- **Alternatives:** MPS on the laptop: its ops are less deterministic, and small networks gain little. Rented GPU by default: it costs money and breaks laptop reproducibility for no gain on networks this small.
199	- **Consequences:** RUNS-04 holds for every laptop run. A rented run reproduces only on the same kind of machine. For networks this small, more CPU cores often help more than a GPU, so measure before renting.
200	- **Probe:** none — the hardware is the user's own, and the PyTorch notes settle determinism.

242	### AD-11: Two PPO learners for predator & prey, with pools of saved agents
243	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `coevo`
244	- **Context:** COEVO-01: both sides learn at once by default. POOL-01–POOL-04: in past-opponents mode, opponents are drawn from pools of up to 20 frozen copies, dropping the oldest, and a run can start from a finished both-at-once run. COEVO-02 and COEVO-05: at least 20 evenly spaced saves of each side, and a latest-vs-latest match at each save.
245	- **Decision:** One `ppo.PPOLearner` per side. In both-at-once mode, each rollout collects both sides' experience from the same episodes, then both update. In past-opponents mode, each episode plays one learning side against a frozen copy drawn uniformly from the other side's pool. The sides take turns rollout by rollout. A pool is the list of the other side's saved agents in the run folder, read through `lab.load_agent`'s loaders, so the pool is just the newest 20 saves. Saves happen every `max_steps / 20` steps, or more often if set. At each save, the latest predator plays the latest prey for 20 unseen episodes, and the results are saved to `swing.json`.

247	- **Consequences:** POOL-04 is a copy of the parent run's saved agents into the new run's folder. The swing test (POOL-05) needs the episode-level outcomes, which `swing.json` keeps.

290	## Risks and open questions
291	- **PB-01 (AD-04):** C2 and C3 passed. C4 (does the library's PPO learn the tank in 60 minutes?) is still to run, so AD-04 stays Proposed. If it fails, POLICY-02 and POLICY-03 have no fair answer key. Fallback: wrap the tank as 8 independent single-fish tanks for the library run only, and bring that change back for a decision. Before C4 runs, `api-probe` must update the probe to the changed spec (AD-13): the stand-in tank's touch distance becomes the 0.2 ball radius, C1 is rerun, and C4's Pass becomes a significant win over swim-away fish at 5% instead of 1.5×.
292	- **The ball is seen one step before it touches (AD-13):** with sight a quarter-radius and the ball's radius a fifth, both measured to its centre, the ball comes into view only 0.05 tank-radii from contact. At ball speed 0.5 and a step of 0.1 s it covers that in one step, and a fish at top speed moves 0.04. So no fish can dodge what it sees: trained fish can win only by where they wait (away from the ball's paths, near fish that are still alive). The spec chose this (TANK-02, TANK-05, UR-37), and the rerun of PB-01 C1 will show whether trained fish have room to beat swim-away fish. If not, the fix is a spec change (measure sight to the ball's edge, or widen sight) through `spec-writing`.
293	- **Tank training speed (QR-01):** PPO on 8 fish × 600 steps per episode must reach its verdicts in 60 minutes in pure NumPy and PyTorch. Mitigation: vectorised world steps, and measure steps per second in the first S2 milestone before tuning anything else. AD-05's rented GPU is the last resort.
294	- **Cross-play cost (COEVO-03):** 20 × 20 cells × 20 episodes is 8,000 tank episodes. That doesn't count toward QR-01's training limit, but it may take tens of minutes. Mitigation: a process pool, run once per run.
295	- **Settling test (POOL-05):** each run gives one swing. The significance test must resample the episode-level outcomes saved at each save point. The `null-hypothesis-testing` skill chooses the procedure, and `swing.json` keeps what it needs.
296	- **Snake's limited view (AD-07):** with only nearby danger visible, long snakes may trap themselves. This is enough for 1.5× the head-toward-food player, but may cap the score. A richer observation would be a later decision.
