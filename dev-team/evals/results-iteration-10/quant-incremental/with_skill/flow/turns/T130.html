# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. In a single package each component gets a subfolder whose `__init__.py` exports its contract only, so a later Grow is a folder move. Modules on no step: only `__init__.py`, the entry modules, `__main__.py` for a `python -m` trigger (dispatching each trigger to its entry), and `types.py`. Test folders sit at the repo root in every layout, multi-package included: `tests/intent/<pkg>/`, `tests/unit/<pkg>/`, never under the package's folder. ## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).

# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.

### AD-27: The forecaster is a small LSTM on PyTorch with a return head and a variance head
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `forecast`
- **Context:** UR-113: "with neural networks (e.g. sequence models)". FCST-04, FCST-05 (walk-forward, settings from development months only), FCST-06, FCST-08, FCST-15 (≤ 8 hours on the laptop, or a rented GPU) and QR-06 (≤ $10 of GPU a run). About 165,000 stock-months and ~23 refits. RF-02 shows the window layout of a temporal-fusion-transformer-style model. Its caveats rule it out as is: no purge gap, windows cut by row across membership gaps and ticker changes, zero fills, a full-sample vocabulary and a sector input. RF-03's targets count rows, not dates.
- **Decision:** PyTorch ≥ 2.4. A stock-month's input is its window's 252 days, each day's total return over the window's standard deviation and the log of its split-adjusted volume over the window's median. The window is the eligible one: no gaps (AD-16), keyed by `CompanyId`. The passed features on R, ranked within the month to [−0.5, 0.5] as in AD-22, join the final hidden state. A `layers`-deep LSTM of width `hidden`, with dropout, feeds two linear heads. The return head is trained by squared error on the raw target, and the log-variance head by QLIKE against realized variance (FCST-08's loss). Each loss is scaled by its first-epoch value, and the two are summed. Adam at `learning_rate`. The epoch count is found by early stopping on the refit's last 12 training months, then the model is refit on all of them. Refits follow `eqdata_features.refits`, whose training months' targets end by the refit, which is the purge. Seeds and deterministic kernels come from the settings. `device` is `cpu` by default.
- **Alternatives:** A temporal fusion transformer through pytorch-forecasting: the Lightning stack and several times the CPU time, for variable selection over inputs that are mostly two sequences. A 1-D temporal CNN: would also serve; an LSTM is the plainer sequence baseline. A feed-forward net on summary features: not the sequence model UR-113 asks for.
- **Consequences:** The network is the run's main cost: ~23 refits of up to `max_epochs` passes over ~135,000 sequences at the last refit. The levers are a rented GPU (QR-06), fewer epochs and a smaller `hidden`. A raw-scale return head keeps FCST-06's R² against zero meaningful.

### AD-28: Baselines on scikit-learn and NumPy, scored and tested as the feature study's models are
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `forecast`
- **Context:** FCST-06–FCST-12, UR-115 and UR-123 ("volatility forecasts scored against EWMA and HAR"). A refit that fails drops its months from every comparison that uses it (FCST edge case). AD-22 and AD-23 fix the feature study's equivalents.
- **Decision:** **Zero:** 0 for every stock; a constant forecast's monthly rank correlation counts as 0. **Ridge:** scikit-learn `Ridge` on the passed features and each stock's 21- and 252-day total returns, all ranked within the month as in AD-22. α is picked from `ridge_alphas` on the refit's last 12 training months, then the model is refit on all of them. **EWMA:** weights 0.94^(251 − t) over the 252 days, normalised to 1, on squared daily returns, × 252. **HAR:** least squares with an intercept of next-month realized variance on the 1-, 5- and 22-day mean squared daily returns × 252, pooled over the training stock-months (`numpy.linalg.lstsq`). Scores follow FCST-06 and FCST-08. Each test is one-sided on paired monthly series, Holm within its family of 2. Draws come from one generator seeded from the settings, a child stream per test (as in AD-23). The `null-hypothesis-testing` skill picks each statistic and p-value computation within those families.
- **Alternatives:** HAR on log variance: not FCST-10's definition. Ridge's α by generalised cross-validation: AD-22's inner block keeps the two studies alike.
- **Consequences:** The baselines take seconds. They see the same stock-months as the network, so every comparison is paired.

### AD-29: One backtest holds every portfolio; the forecast rules reuse the portfolio study's solvers
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `forecast`
- **Context:** BT-01–BT-07, PORT-09, PORT-14, FPORT-01–FPORT-08, UR-122 and UR-126 ("long-only, no leverage, monthly rebalance, 10 bps per side costs on every portfolio"). BT's edge cases: a rule with no weights keeps its drifted weights, and a date with no stocks holds cash. The 12 portfolio-study portfolios must hold exactly as that study holds them (BT-01). AD-18 fixes those solvers.
- **Decision:** Every portfolio is a `Formation` on each R, held by `hold_month`. Weights drift as in `eqdata_study.hold`, and a stopped stock is held as cash at 0%. The cost is 0.001 × Σ |new − drifted| over stocks, cash excluded, with a first formation counted from cash, deducted on R. The monthly after-cost return is (1 − cost) × Π(1 + r) − 1. A failed formation keeps the drifted weights with no trade, and no eligible stock means cash. BT-05's measures come from the monthly returns of each phase. The 12 come from `eqdata_study.estimate` and `eqdata_study.form` on each window, and 1/N is `equal`. The best of the 12 is the highest development Sharpe ratio, recomputed by every run from development months only, so it never changes (BT-06). The forecast covariance takes σ from the network's variance forecasts and ρ from the shrinkage estimate. **Mean-variance:** maximise wᵀμ − (γ/2) wᵀΣw with w ≥ 0 and Σw = 1, through cvxpy on `psd_wrap(Σ)` solved by Clarabel. μ is the monthly return forecast × 12, so it is annual like Σ and FPORT-02's example holds. γ is the value in `gammas` with the best development after-cost Sharpe ratio. **Risk parity:** `eqdata_study.risk_parity` on the forecast covariance. **Top fifth:** ⌊N/5⌋ stocks, at least 1, ties broken by `CompanyId`. The four non-cash sleeves' held months become the agent study's tape (AD-30). Nothing in the backtest touches a network (BT-02).
- **Alternatives:** `eqdata_study.hold` alone: its `Weights` can't hold kept drifted weights or a cash remainder. Store the best classical choice once: a second record to keep, for a choice the development months already fix. Charging ½ Σ |Δw|: BT-03's examples charge the full sum.
- **Consequences:** `study` exposes `risk_parity`, which its own `form` calls, and exports its estimate, rule and holding symbols (AD-14, AD-19). cvxpy and Clarabel join `forecast`. Each run makes ~2,700 classical solves, plus ~280 mean-variance solves per γ and ~280 risk-parity solves.

**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system

### AD-31: PPO from Stable-Baselines3 in an environment built from the sleeve tape
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `agents`
- **Context:** UR-117: "train PPO trading/allocation agents". UR-128: "agent allocates across sleeves". AGENT-03–AGENT-06 and AGENT-17: 8 hours on the CPU for the selection grid, 10 seeds and both controls. PPO's mechanism is a clipped-surrogate policy-gradient update with a learned value baseline, over rollouts collected with the current policy.
- **Decision:** Stable-Baselines3 ≥ 2.3 `PPO` with `MlpPolicy` (two hidden layers of 64, tanh), on gymnasium ≥ 1.0, with PyTorch on the CPU. One step is one rebalance date. The action's 5 values go through a softmax to give the sleeve weights. The observation is AGENT-04's 23 values, with the current sleeve weights taken as they drifted to R. Within the month, the allocation's value is Σ aₛVₛ(t) over the sleeves' pre-cost paths in the tape, with cash at 1. Its daily returns give the realized variance (PORT-15), and the reward is AGENT-05's. The cost is `eqdata_forecast.cost` between the drifted holdings (each sleeve's `end` weights, weighted by the sleeve's drifted share) and the new holdings Σ aₛ × `new`ₛ (AGENT-03). Episodes walk the development months, or blocks of `block_months` resampled from them (AGENT-06). The hyperparameters come from `AgentSettings`. One process per agent, `workers` at a time.
- **Alternatives:** A PPO of our own on PyTorch: ~300 lines to verify against a tested library. RLlib: a cluster framework for one laptop. SAC or DQN: not the method the user named.
- **Consequences:** Evaluation uses the policy's deterministic action. A softmax gives no weight exactly 0, which PORT-09 allows. An environment step is a few vector operations, so training time is mostly PPO's own updates.

### AD-32: Settings chosen on the last 36 development months, 10 seeds averaged, controls trained the same way
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `agents`
- **Context:** AGENT-07–AGENT-15, the failed-seed edge case, and UR-132's decisions (settings on the last 36 development months, AGENT-11's extra tests outside the verdict, controls scored on the last 60 synthetic months, no verdict under 5 seeds).
- **Decision:** For each `grid` entry, `select_seeds` agents are trained on the development months before the last 36. Their averaged allocation is scored on those 36 by after-cost Sharpe ratio, and the best entry, with its κ, is frozen. Then `seeds` = 10 agents are retrained on every development month. Each month the allocation is the mean of the trained agents' allocations, a failed seed left out. The development figures are in-sample for these agents, so the report labels them so, and the holdout is the test. The baselines are AGENT-09's, through the same environment. The tests are AGENT-10's and AGENT-11's, through the `null-hypothesis-testing` skill, from one `SeedSequence`. Each control is a 300-month synthetic tape (`planted`, `none`). On each, 10 agents with the frozen settings train on the first 240 months, and their average is tested against equal sleeves on the last 60.
- **Alternatives:** The best seed alone: what AGENT-08 rules out. Controls trained with fewer seeds: cheaper, but not "trained the same way".
- **Consequences:** A run trains |grid| × `select_seeds` + 30 agents. At ~3 minutes each, a 4-entry grid with 3 selection seeds is 42 agents, ~2 hours on one worker.

## Overview
The agent study, started with `eqdata-agents` (AD-25). `tape` reads the sleeves and forecast summaries the latest `forecast` report saved, through `eqdata_forecast.load_tape`, cut at the fixed holdout boundary unless the holdout is being scored (AD-30). It never reruns a forecast and reads nothing else from the store. `market` turns a tape into a monthly allocation environment: observations, sleeve weights, stock-level costs through `eqdata_forecast.cost`, and the risk-adjusted reward (AD-31). `train` trains PPO agents on episodes of development months, one process per seed (AD-31). `select` chooses the settings on the last 36 development months, and `evaluate` runs the 10-seed average and the baselines through the same environment (AD-32). `synthetic` builds the planted-regime and no-regime tapes the controls train on. `inference` tests the averaged agent and the controls. `report` keeps the holdout record and saves the five sections and the trust notice (AD-30, AD-32).

```mermaid
  market --> tape & forecast & settings

  train --> market & settings
  select --> train & evaluate & settings
  evaluate --> market & train & forecast
  inference --> evaluate & train & synthetic & forecast & settings
  report --> evaluate & inference & train & settings & eqdata
```

**Skills:** `report` runs the `data-analysis` skill for AGENT-12. It takes every seed's training curve and final rewards, and the skill decides the summaries and plots within the seeds section. `inference` runs the `null-hypothesis-testing` skill for AGENT-10, AGENT-11, AGENT-13 and AGENT-14. It takes the paired monthly after-cost returns, and the skill picks the Sharpe-ratio test and how its p-value is computed. The report's charts are drawn by `web`'s `charts`, which follows the `dataviz` skill.

## Interfaces
See [contract.md](contract.md). `agents` consumes [eqdata's contract](../eqdata/contract.md) (public API only) and the symbols `eqdata_forecast` exports ([forecast's contract](../forecast/contract.md)). It provides nothing to other packages.

## Cross-cutting concerns
- **No look-ahead (BT-07, INFO-03, AGENT-06):** only `tape` reads the forecast report, and a development tape ends before 2021-09-30. An observation for R reads only tape rows for R and earlier; the month after R reaches only the reward. Every training episode is made of development months, and the settings are chosen on agents that never saw the last 36 (AGENT-07). A test changes a tape value after R and checks that every allocation on R or earlier is identical.
- **Reproducibility:** every seed, the bootstrap and every shuffle come from one `SeedSequence` from `settings.toml`, a child per agent and per test. The `forecast` report used, the settings and their digest go into the report's params.
- **Speed (AGENT-17, QR-06):** CPU only. Each environment step is a few vector operations on precomputed sleeve paths. Agents train in `workers` processes: the selection grid, the 10 final seeds and 10 seeds per control. Timed by a benchmark test on the full history.
- **Data:** built and tested on synthetic tapes first; the real run needs a real forecast report.

## Environment and training

### agents.make_env: An environment over some months of a tape
`def make_env(tape: SleeveTape, months: Sequence[TradingDay], settings: AgentSettings, *, bootstrap: bool, seed: int) -> AllocationEnv`

# eqdata — Architecture

**Package:** eqdata · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`sources` fetches from Sharadar and Yahoo. `sync` cleans what Sharadar returns, stages it and commits it to `store` in one transaction, then calls `check`. `universe` and `returns` answer as-of queries from `store`. `check` and `eda` raise findings through `findings`. Every long job runs inside `runs`, which holds the lock and writes progress events. `cli` is the front door. The separate `server` package calls only the public API in [contract.md](contract.md): the query functions, `launch_run`, which spawns the CLI (AD-09), and `run_snapshot` and `events_after` for live progress (AD-13). The separate `study` and `features` packages read the as-of loader, and `features` also the daily bars, through the same API. Every study package saves its report through `reports`, which also holds the EDA report and serves every kind to `server` (AD-14, AD-15, AD-19). `forecast` saves frames beside its report, and `agents` reads them back through `report_frame` (AD-30).

## Data
- **Sources:** Sharadar SEP, ACTIONS, TICKERS and SP500 (AD-03). Yahoo via `yahooquery` for the sample only (AD-05). Researcher CSVs under `reference/` (AD-10).
- **Tables** (all keyed by `company_id`, AD-04): `companies`, `tickers` (company, ticker, from, to), `membership` (company, effective_from, effective_to), `prices` (unadjusted OHLCV), `actions` (splits, dividends, ticker changes, mergers, acquisitions, delistings). Each has `known_from` and `replaced_on` (AD-06). Also `findings`, `runs`, `run_events`, `source_diffs` (run, company, date, return and close differences; AD-12), and staging copies of the market tables.
- **Cleaning (SYNC-03):** duplicate (company, date) rows keep one, and the count goes to the summary. A changed past value closes the old row (`replaced_on`) and inserts the new one, listed as a revision.
- **Known-on queries (DATA-05):** as-of functions take `as_of` (market date: events after it are ignored) and an optional `known_on` (system date: rows not yet known, or already replaced, then are ignored).
- **Sampling (CHECK-01):** at least 2 companies per calendar year from 1998, drawn from members Yahoo still carries, then filled at random to 100. The seed is recorded in the run summary.
- **Reports:** one `report.json` (an `eqdata.Report`: sections of tables and chart series) per report in `EQDATA_HOME/reports/<kind>/<id>/`, for the `eda`, `study`, `features`, `forecast` and `agents` kinds, rendered by `web`, with any frames beside it as Parquet files (AD-15, AD-24, AD-30).

## Cross-cutting concerns
- **Lock and atomicity:** `runs` holds the lock and `store.commit` is one transaction, so a killed refresh leaves only staging rows, which are cleared at the next start.
- **Credentials:** read in `sources` only, and redacted in logs and events (QR-05).
