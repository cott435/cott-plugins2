# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`), a routed change (`routed_changes`) or the user's words the spec doesn't honour yet (`requests_open`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Stage | `Stage:` line of each new feature: the stage the idea added, or the one it joins |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

# The spec: template, writing rules, hygiene check

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown
# [Project Name] — Spec

**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [brief.md](brief.md)

## Summary
[2-3 sentences: what is being built. Link to the brief for why — don't repeat it.]

## Users
| User | What they need to do |
|---|---|
| [Primary user] | [...] |

## Scope
**In scope:** [features, by name]
**Out of scope:** [what we're not building — include everything on the brief's Not Doing list, plus anything decided during clarification]

## Features

### [Feature name] (`CODE`)
**Serves:** Goal 1, Goal 3
**Stage:** S2
**Source:** [ideas/<slug>.md](ideas/<slug>.md) *(extend mode only — omit for features from the original brief)*
**Behavior:** [2-4 sentences or a short numbered flow describing what the user experiences.]

**Requirements**
- **CODE-01** [One testable statement of what the system does.]
  - Given [context], when [action], then [observable result].
  - Given [...], when [...], then [...].
- **CODE-02** [...]
  - Given [...], when [...], then [...].

**Edge cases & errors**
- [Situation] → [expected behavior]

## Data requirements
*(Data and ML projects only — omit otherwise.)*
- **DATA-01** [What data the system needs: content, coverage, history, frequency, freshness — not which vendor.]
  - Given [...], when [...], then [...].

## Quality requirements
- **QR-01** [Measurable non-functional requirement: speed, reliability, accessibility, privacy, security, cost, licence.]
  - [How it's checked.]

## Assumptions
- [Assumptions the user confirmed]

## Open questions
- [Unresolved items, each with who can answer it. Omit if none. A question about what an external source really returns is "answered by a probe during architecture".]

## Changelog
| Date | Change | Source | IDs |
|---|---|---|---|
| YYYY-MM-DD | Initial spec | brief.md | all |
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Every feature names one stage.** Its `**Stage:**` line holds only the ID of the roadmap stage that first builds it. `dt lint` fails a feature with no stage, or one naming no stage row.
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence and budget limits are `QR-` items ("data costs ≤ $50 a month"), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads it in `docs/requests.md`.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea", "UR-03") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git; which requirement honours which request goes in `docs/requests.md` (`dt request trace`).
- **The user's words win over the brief's.** Where a `spec` request is more specific than the brief or idea file ("circular tank", "one predator"), the requirement says what the request says, or the user approves the change.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **The user's words.** `dt request --open --owner spec` is empty, or each one left is a change you ask the user about.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of torchvision's ResNet-18" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.
# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

Quote the words and the traced text side by side, so the user sees whether one does the other.

# RL Lab

**Status:** Accepted · **Last updated:** 2026-10-18

## The problem
Reading about reinforcement learning (agents that learn by trial, error and reward) doesn't teach you why it works or why it fails. Library algorithms hide the parts that matter. The fastest way to understand it is to build agents yourself, in small 2D worlds where every result can be watched and explained.

## Who it's for
One learner: comfortable with Python and PyTorch basics, knows some reinforcement learning theory (Q-learning, the Bellman equation), still learning.

## Goals
1. Learn reinforcement learning by writing the learning algorithms yourself, one piece at a time.
2. Every trained agent is measured against a random player and a simple scripted bot, so "it learned" means something.
3. Every result can be explained, with the saved evidence from each run to back it up.
4. Any trained agent can be watched playing, as a replay.
5. A shared core (environment interface, training loop, logging, replay viewer) makes each new environment cheaper than the last.

## Constraints
- One person, evenings and weekends; a few weeks per environment.
- A MacBook Pro with Apple Silicon and no NVIDIA GPU.
- A training run must finish in under about an hour on the laptop's processor.
- No outside data: agents create their own experience by playing.

## What success looks like
- For each environment, the agent's learning curve beats a random player and a simple scripted bot. If it only ties the bot, that still counts as long as the tie is explained.
- A replay of each trained agent can be watched.
- Each piece added to an algorithm comes with a before-and-after comparison that shows what it changed.
- The first environment is classic Snake, learned by table-based Q-learning first, then by a deep Q-network (a neural network that scores each move) built step by step.

## What we're betting on
- Small 2D worlds with compact, hand-made views are enough to learn the core ideas.
- Writing the algorithms yourself teaches more than tuning a library's.
- A core shaped by one environment can be adapted to the next one without a rewrite.

## Not doing
- 3D worlds.
- Learning from pixels, or Atari games — too slow on a laptop, and the lesson is mostly computing power.
- Reproducing research papers — the aim is understanding, not benchmark scores.
- Web deployment.
- Library algorithms, for now — a comparison against them comes later.
- A general framework built before any environment needs it — the core grows from real use.
- Growing the board size during training — one fixed board keeps results comparable.
# Idea: Predator and prey

**Status:** Accepted · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This adds a third environment where prey fish forage for food pellets while a learning predator hunts them, so that the learner can see and measure how each side's learning changes what the other has to learn.

## The problem
Snake and the fish tank each have one learner facing a world that never changes its rules. Once a second learner shares the world, the opponent changes while you learn. Old lessons stop working, the two sides can chase each other in circles, and "it learned" becomes hard to measure. None of this shows up with one learner, so it needs a world built to show it.

## Who it's for
The brief's one learner, once the fish tank is done, studying two learners that adapt to each other (co-evolution) and the self-play fix for the problems that causes.

## How it fits
- **Serves:** Goal 1 (each step of the ladder written by hand), Goal 2 (random and scripted baselines for both sides), Goal 3 (the tournament chart explains the arms race), Goal 4 (replays), Goal 5 (the third environment reuses the tank and PPO)
- **Touches:**
  - The S2 tank: circle, ball physics, swim-velocity moves and view (TANK-01–TANK-13), PPO and the shared brain (PG-04, PG-06).
  - The spec's out-of-scope line "a ball that learns to hunt", and the frozen [fish-tank](fish-tank.md) idea's "learning hunter", which this idea takes on as its own lesson.
  - The baselines and comparisons (BASE-*, EVAL-01–EVAL-07).
  - RUN-08 and RUN-09: saved Snake and tank runs still rerun, compare and replay unchanged.
- **Brief changes:** None
- **Stage:** New S3 (roadmap stage on acceptance)

## Recommended direction
**The world.** Same circular tank, swim-velocity moves and PPO as the fish tank. A learning predator fish replaces the ball. Five prey fish eat food pellets, and an eaten pellet appears again somewhere else. The predator touching a prey removes it. Everyone has the same short view radius as the S2 fish.

**Two learners.** The 5 prey share one brain, as in S2. The predator has its own. Prey are rewarded for pellets eaten, and being caught ends that prey's game. The predator is rewarded for catches. The pellets matter: they pull prey toward danger, so prey can't just learn to flee as the S2 fish did.

**The ladder.** Each rung adds one fix for a moving opponent, with a before-and-after comparison:
1. **Both learn at once:** plain co-evolution, expected to chase or cycle.
2. **Take turns:** one side is frozen while the other trains, swapping every N updates.
3. **Train against past versions:** each side trains against a pool of the other side's saved past versions (self-play).

**The control, run in both directions.** A learning predator against the scripted forager, and learning prey against the scripted chaser. Each measures what a moving opponent costs that side. Three rungs plus two controls make 5 setups × 5 seeds = 25 runs.

**Baselines.** For the predator: a random swimmer and a scripted chaser that swims at the nearest prey it sees. For the prey: a random swimmer and a scripted forager that flees the predator when it sees it, and otherwise swims to the nearest pellet.

**Done.** Two conditions:
- Tested against fixed opponents on held-out tanks, each side beats the random player and beats or ties its scripted bot. An explained tie counts.
- A tournament chart (predator version i against prey version j) shows a measured trend, or an explained cycle.

## Data
- No outside data. Both sides create their own experience in the tank, from seeds.
- Evaluated on fixed held-out test tanks against fixed opponents, never against the co-learning partner alone.
- Each comparison is tested with the `null-hypothesis-testing` skill across 5 training seeds. The learning curves and the tournament grid are drawn with `dataviz`.

## Alternatives considered
- Both learn at once only: shows the problem but not the fix.
- Past-versions self-play only: shows the fix without the problem it fixes.
- A new world instead of the tank: the lesson would mix physics changes with the two-learner effects.
- Predator sees further than prey: adds an imbalance to explain before the dynamics.

## What success looks like
- Each side beats random and beats or ties its scripted bot when tested against fixed opponents, with every result explained.
- Each rung and the control has a measured before-and-after comparison.
- The tournament chart shows whether later predators beat earlier prey (and the other way round), or why they cycle.
- Any game can be watched as a replay, predator and prey together.

## What we're betting on
- Two learners together still train in under an hour on the laptop.
- The tank and PPO take a second learner with changes, not a rewrite.
- A balanced predator speed exists, one where neither side wins trivially.
- Lower rungs may fail or cycle. That is part of the lesson, as long as it's explained.

## Not doing
- Two or more predators (cooperative hunting): a different lesson.
- Separate brains per prey: the shared brain keeps the S2 choice.
- Evolutionary or genetic algorithms: "co-evolution" here means two learners adapting to each other.
- Library multi-agent algorithms: written in the project, as before.
- Shaped rewards beyond pellets and catches.

## Open questions
- Predator top speed compared with prey (2.5 per second in S2), and whether the predator can only catch prey by cornering them against the wall.
- Pellet count, how fast eaten pellets reappear, the reward sizes, and the time cap.
- Turn length (N) for rung 2, and the pool size and sampling for rung 3.
- How often versions are saved for the tournament chart.
- The replay's view of the predator's move and of the pellets.

260	### Fish tank environment (`TANK`)
261	**Serves:** Goal 1, Goal 5
262	**Stage:** S2
263	**Source:** [ideas/fish-tank.md](ideas/fish-tank.md)
264	**Behavior:** A circular tank holds one ball, bouncing off the wall at constant speed, and 1 or 5 fish. Every tenth of a second each fish still swimming chooses how to swim. The ball touching a fish removes it; the wall and other fish are harmless. Each fish sees only what lies within its view radius, as a short list of numbers, and is rewarded for every step it survives.
265	
266	**Requirements**
267	- **TANK-01** The tank is a circle of radius 10 holding one ball and a fixed number of fish, 1 or 5, saved with the run.
268	  - Given any tank game, when it starts, then the tank's radius is 10, it holds exactly one ball, and the number of fish is the run's 1 or 5.
269	- **TANK-02** The ball, of radius 0.5, moves at a constant 2 units per second and bounces off the tank wall like a mirror.
270	  - Given the ball reaching the wall, when it bounces, then it leaves at the same angle to the wall's normal as it arrived, on the other side of the normal.
271	  - Given any step of any game, when the ball's speed is measured, then it is 2 units per second.
272	- **TANK-03** Each game starts with the ball at the centre heading in a direction set by the game seed, and each fish at a seed-chosen spot between 5 units from the centre and the wall.
273	  - Given any game, when it starts, then the ball is at the centre and every fish is between 5 and 9.75 units from the centre.
274	  - Given the same game seed twice, when both games start, then the ball's direction and every fish's spot are identical.
275	- **TANK-04** Every 0.1 seconds of tank time, each fish still swimming chooses a move: a swim velocity (x, y) in tank directions, capped at a speed of 2.5 units per second.
276	  - Given a fish that chooses velocity (1, 0), when the step runs, then it moves 0.1 units in the x direction.
277	  - Given a fish that chooses velocity (3, 4), when the step runs, then it swims at 2.5 units per second in direction (0.6, 0.8) and moves 0.25 units.
278	- **TANK-05** A fish, of radius 0.25, can't leave the tank: a move that would carry it past the wall stops it at the wall.
279	  - Given a fish touching the wall that swims straight outward, when the step runs, then it stays inside the tank, touching the wall.
280	- **TANK-06** Fish swim through each other unharmed.
281	  - Given two fish whose paths cross, when the step runs, then both finish their moves and both are still swimming.
282	- **TANK-07** At the end of each step, the ball removes every fish whose edge touches it (centres within 0.75 units); a removed fish takes no more moves and is no longer seen by other fish.
283	  - Given a fish whose centre ends a step 0.7 units from the ball's centre, when the step ends, then the fish is removed.
284	  - Given a fish whose centre ends a step 0.8 units from the ball's centre, when the step ends, then the fish is still swimming.
285	  - Given a removed fish, when the other fish's views are read, then none of them sees it.
286	- **TANK-08** A tank game ends when every fish is removed, or at 60 seconds of tank time (600 steps); until then it goes on for the fish still swimming.
287	  - Given 5 fish of which 4 are removed, when the steps continue, then the game goes on until the last fish is removed or 600 steps have run.
288	  - Given a fish still swimming after 600 steps, when the 600th step ends, then the game ends.
289	- **TANK-09** A fish's reward is +0.1 for each step it survives, and 0 for the step in which it is removed, which ends its experience; there is no other reward.
290	  - Given a fish that survives a step, when the step ends, then its reward is +0.1.
291	  - Given a fish removed during a step, when the step ends, then its reward is 0 and it has no further steps.
292	  - Given a fish that survives all 600 steps, when its rewards are summed, then the total is 60.
293	- **TANK-10** A fish's score is the seconds of tank time it survived, from 0 to 60, and a game's score is the mean over all its fish, removed ones included.
294	  - Given 5 fish that survive 10, 20, 30, 60 and 60 seconds, when the game is scored, then its score is 36.
295	  - Given 1 fish removed at 12.5 seconds, when the game is scored, then its score is 12.5.
296	  - Given a fish removed at the end of step k, when it is scored, then it survived 0.1·k seconds, while its TANK-09 rewards sum to 0.1·(k−1), since the removal step pays 0: removed at the end of step 125, it scores 12.5 and its rewards sum to 12.4.
297	- **TANK-11** At every step, each fish sees exactly 11 numbers about what lies within its view radius: for the ball, whether it is seen, its position relative to the fish (2 numbers) and its velocity relative to the fish (2); for the wall, whether it is seen and the offset from the fish to the wall's nearest point (2); for the nearest other fish, whether it is seen and its position relative to the fish (2). Anything beyond the radius is seen as no, and its numbers are 0.
298	  - Given the short view and the ball 3 units away, when the fish's view is read, then the ball is seen as yes and its relative position and velocity are the true ones.
299	  - Given the short view and the ball 5 units away, when the view is read, then the ball is seen as no and its 4 numbers are 0.
300	  - Given the short view and a fish at the centre of the tank, when the view is read, then the wall is seen as no and its 2 numbers are 0.
301	  - Given a 1-fish game, when the view is read, then the nearest other fish is seen as no and its 2 numbers are 0.
302	- **TANK-12** A fish's view radius is either 4 units (the short view) or 20 units (the wide view, which spans the whole tank), saved with the run.
303	  - Given the wide view, when any fish's view is read at any step, then the ball and the wall are seen as yes, and so is the nearest other fish if one is still swimming.
304	- **TANK-13** The same game seed and the same moves always give the same game.
305	  - Given a game seed and a list of moves for every fish, when the game is played twice, then every position, removal, reward and ending is identical.

309	- The ball touches several fish in the same step → all of them are removed in that step.
310	- A fish chooses velocity (0, 0) → it stays where it is.

313	### Policy-gradient ladder (`PG`)
314	**Serves:** Goal 1, Goal 3
315	**Stage:** S2
316	**Source:** [ideas/fish-tank.md](ideas/fish-tank.md)
317	**Behavior:** The tank's learners keep a policy: a learned function that turns a fish's 11 numbers into a spread of swim velocities to pick from. Learning makes the moves that led to longer survival more likely. The ladder is built in four rungs on one fish, each adding one piece to the one before, so each piece's effect can be measured on its own:
318	1. REINFORCE: after each game, each move is made more likely in proportion to the return (the discounted rewards) that followed it.
319	2. + Learned baseline: a learned estimate of each situation's return is subtracted first, so each move is pushed by how much better or worse it did than expected.
320	3. Actor-critic: the return is replaced by the reward plus the discounted estimate of the next situation, so learning happens every few steps instead of waiting for the game to end.
321	4. PPO: each batch of experience is learned from several times, with each update clipped so the policy can't move far from the one that collected it.
322	
323	Then PPO trains 5 fish sharing one policy, and then 5 fish with the wide view.
324	
325	**Requirements**
326	- **PG-01** The REINFORCE rung, after each game, raises the chance of each move a fish made in proportion to the discounted return that followed it.
327	  - Given a known policy, a finished game, the run's learning rate and discount, when one update is applied, then the change to the policy equals the hand-computed REINFORCE step.
328	- **PG-02** The learned-baseline rung weights each move by its return minus a learned estimate of the return from the situation it was made in, and trains that estimate toward the returns seen.
329	  - Given a move with return 4.0 from a situation estimated at 3.0, when its weight is computed, then the weight is 1.0.
330	  - Given a situation whose estimate is below the returns seen from it, when the estimate is trained, then the estimate rises toward them.
331	- **PG-03** The actor-critic rung weights each move by its reward plus the discounted estimate of the next situation, minus the estimate of the situation it was made in, and learns after every fixed number of steps saved with the run's settings.
332	  - Given a known reward, discount and two estimates, when a move's weight is computed, then it equals the hand-computed value.
333	  - Given the run's steps per update, when training runs, then an update happens after every that many steps, not only at the end of a game.
334	- **PG-04** The PPO rung learns from each batch of experience in a fixed number of passes, and caps each move's change in chance at a clip range, both saved with the run's settings.
335	  - Given a move whose chance has already risen past 1 + the clip range times its chance when collected, and a positive weight, when the update is computed, then that move pushes the policy no further.
336	  - Given the run's passes per batch, when one batch is learned from, then the number of passes equals it.
337	- **PG-05** Each tank setup differs from the one it is compared with only by the piece it adds: one rung from the rung below, 5-fish PPO from 1-fish PPO only by the fish count, and wide-view PPO from short-view PPO only by the view radius.
338	  - Given the saved settings of any two setups compared in EVAL-05, when they are compared, then the only differences are the added piece and its own settings.
339	- **PG-06** With several fish, every fish uses the same policy on its own view, and every fish's experience trains it.
340	  - Given a 5-fish run, when moves are chosen, then every fish's move comes from the one policy applied to that fish's own 11 numbers.
341	  - Given a 5-fish run, when an update is applied, then it learns from the experience of all 5 fish up to each one's removal.
342	- **PG-07** While training, each fish picks its move at random from the policy's spread; during test games it takes the policy's most likely move.
343	  - Given a trained policy, when a test game is played twice from the same seed, then both games are identical.
344	- **PG-08** The learning updates of every rung are written in the project; no ready-made learning algorithm is used.
345	  - Given any trained rung, when its learning steps are traced, then each one is code written in the project.
346	
347	**Edge cases & errors**
348	- A picked velocity is faster than 2.5 units per second → the fish swims at the cap (TANK-04), and the learner learns from the move it picked.
349	- A fish is removed partway through a stretch of steps → its experience ends there, and the situation after its removal contributes nothing.
350	- The policy's spread collapses or learning diverges → the run keeps going and saves its curve; the comparison reports the result, and the problem is visible in the curve.
