# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

## Steps

Run these for the idea only:

1. **Check for conflicts first.** Start with the IDs under *Touches*, then search the rest of the spec for anything else the idea contradicts. List conflicts for the user before writing — "Shared editing changes **EDIT-03** (only the owner can edit). Proposed: owner *or invited editors* can edit."
2. **Map the idea to features** and show the goal → feature mapping before writing.
3. **Surface assumptions, then clarify** (SKILL.md's Asking section).
4. **Write the change** following `references/spec.md` and the rules below.
5. **Set the spec Status back to Draft** and run the Review Gate (SKILL.md, plus the gate steps below), highlighting the changed IDs so the user reviews only what's new.

## Writing rules

1. **Keep IDs stable, keep the text current.** IDs are never renumbered or reused. Old text does not stay in the spec once it stops being true; git keeps it.
   - New feature → new `### Feature (CODE)` section with a new code and IDs starting at `-01`.
   - New behavior in an existing feature → next unused number in that feature (if `SAVE-04` is the highest, add `SAVE-05`, even if `SAVE-02` was removed). `dt status` reports it under `prefixes`.
   - **Widen, don't bolt on.** If an existing requirement already covers this concern for an earlier part of the project, rewrite it to cover the new part too, instead of adding a near-duplicate. A training-time limit written for the first dataset becomes a limit for every dataset. A summary that says "the first milestone" is rewritten.
   - Changed requirement → rewrite it in place and keep its ID. Put no marker on it. Instead, list it as `(changed)` in this round's Changelog row, with the reason in the row's Change text. `architecture-design` reads those Changelog marks (through `dt status`) to find what the architecture must revisit, so list every changed ID.
   - Removed requirement → collapse it to one struck line and delete its criteria and edge cases: `- **CODE-03** ~~[short name]~~ *Removed YYYY-MM-DD: [reason, or "replaced by CODE-07"].*` Never delete the ID line; the ID stays retired.
2. **Link back to the idea.** Add `**Source:** [ideas/<slug>.md](ideas/<slug>.md)` under the `Serves:` line of each new feature section, so readers can find the full why.
3. **Update everything it touches, and consolidate.** Summary (rewritten for the whole spec, not appended to), Users, Serves lines. Scope stays one deduplicated list per side: merge new out-of-scope items into it, and drop or narrow anything the new features bring into scope (the gate's *Out of scope* step). Remove assumptions and open questions that are answered or no longer apply.
4. **Add one Changelog row**, one line: the idea file as the source, a short description of the change, and the IDs as ranges in up to three `;`-separated groups: added, then changed, then removed (`FIELD-01–FIELD-12; CNN-03, CORE-04 (changed); CROP-04 (removed)`). A `(changed)` or `(removed)` mark covers every ID in its group.

## Gate steps

Run the hygiene check on the whole spec, not just the new section, and add:

- **Out of scope.** Read every out-of-scope line against the features this round added. Drop a line the new features bring into scope. Narrow a line that is now only partly true to the part still excluded, and name the stage it applies to. Once a neural-network stage exists, "deep learning" is no longer out of scope. Once a reserve-planning stage uses demand forecasts, "no demand forecasts — the reserve stage is an equal split" becomes "the equal-split reserves use no demand forecasts". Then merge duplicates.
- **Leftovers.** The Summary describes the whole spec as it now stands. No requirement is still worded for one stage when it now covers several. Removed requirements are one line each. No `(changed …)` marker or other change note appears above the Changelog.

## On approval: close and freeze the idea

A `Specced` idea is the record of why the feature was added, as it stood that day. The spec is the current description.

1. Set its Status to `Specced` and add two lines under the header: `**Spec:** CODE-01–CODE-04, EDIT-03 (changed)` and the banner `> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)`.
2. Delete the open questions the spec answered. If none are left, the section becomes one line: `Resolved in the spec.`
3. Delete wording that only served the review: notes to the user ("my proposed limit, for you to check") and instructions to this skill ("this line must be removed from the spec").

After that, don't edit the file again, even when a later round changes what it describes, such as a narrowed holdout or a merged stage. That change goes in the spec, and the later idea file names this one under *Touches*.

# Quant Research Platform — Spec

**Status:** Approved · **Last updated:** 2026-10-17 · **Brief:** [brief.md](brief.md)

## Summary
A local, single-user platform that downloads daily US equity data for every company that was ever in the S&P 500 since at least 2005, stores each download as an immutable snapshot, validates it, and serves it to research code through one source-neutral loader. A browser app lets the user browse securities, inspect data-quality flags, compare raw and adjusted prices around corporate actions, and start and watch download and validation runs. On top of that data, a walk-forward test bench compares covariance estimators and minimum-variance, risk-parity and hierarchical risk-parity portfolios out of sample on realised variance, against simple baselines with significance tests, and reports the results in a static report. See the [brief](brief.md) for why.

## Users
| User | What they need to do |
|---|---|
| The researcher (sole user) | Build and refresh the dataset, load point-in-time universes and prices into research code, find and inspect data problems, and confirm the data is honest before testing any signal; then find which risk estimates and allocations really lower out-of-sample variance. |

## Scope
**In scope:** Point-in-time universe (`UNIV`), Prices, actions & returns (`PRICE`), Snapshots & runs (`SNAP`), Validation & flags (`QUAL`), Research loader (`LOAD`), Exploratory analysis (`EXPL`), Data cockpit app (`APP`), Walk-forward engine (`WALK`), Return structure analysis (`STRUC`), Covariance estimators (`COV`), Portfolios (`PORT`), Out-of-sample evaluation (`EVAL`), Known-answer bench (`SYNTH`), Variance report (`VREP`).

**Out of scope:**
- Real money, broker connections or order placement.
- Intraday data, fundamentals, or live market streaming.
- Securities that were never S&P 500 members.
- Reconciling every price across two sources; only a fixed sample is cross-checked.
- A database server, a scheduler, or automatic runs; every run is started by hand.
- Return prediction, signals, expected-return or cost-aware optimisation, and any machine learning.
- Turnover limits and transaction costs in the portfolio comparison.

- Synthetic final-day returns for delisted securities.
- Automatic correction of flagged data.
- Access from any machine other than the user's laptop.

## Features

### Walk-forward engine (`WALK`)
**Serves:** Goal 6, Goal 4
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** On the first trading day of each month the engine takes that day's point-in-time S&P 500 members, estimates on the trading days before it only, builds every portfolio, and holds it through the month. Every estimator and portfolio runs inside this one loop, so every comparison is out of sample by construction.

**Requirements**
- **WALK-01** Rebalance dates are the first trading day of each month, from the first month with a full estimation window after the data window starts, through the last complete month in the snapshot.
  - Given a snapshot whose window starts 2005-01-03 and a 504-day window, when rebalance dates are listed, then the first is in January 2007 and each is the first trading day of its month.
- **WALK-02** The universe at a rebalance date is the S&P 500 membership at the previous trading day's close.
  - Given a security whose membership starts at the close of a rebalance date, when that date's universe is built, then the security is not in it.
- **WALK-03** Estimates at a rebalance date use only returns from the 504 trading days ending at the previous close.
  - Given any return on or after a rebalance date is changed, when that date's estimates are recomputed, then every estimate is identical.
- **WALK-04** A member is eligible only if it has a return on at least 499 of the window's 504 days; up to 5 missing days count as zero returns.
  - Given a member with 498 returns in the window, when the universe is built, then it is excluded, and the rebalance's excluded and zero-filled counts are recorded.
- **WALK-05** A one-year configuration runs the same loop with a 252-day window and an eligibility floor of 247 days.
  - Given the one-year configuration, when it runs, then every estimate uses exactly the 252 prior trading days.
- **WALK-06** Weights are held from the rebalance date's close-to-close returns through the month's last trading day and drift with returns; a member that stops trading mid-month earns zero from its last trading day to month end.
  - Given a member whose last trading day falls mid-month, when the month's portfolio returns are computed, then its weight earns its returns up to that day and zero afterwards, and no other weight changes.
- **WALK-07** A fallback configuration restricts each rebalance's universe to the 100 eligible members with the highest average daily traded value over the window.
  - Given the fallback configuration, when a universe is built, then it holds at most 100 members, ranked by window-average closing price × volume.

**Edge cases & errors**
- Fewer than 20 eligible members at a rebalance (the 5% cap can't be met) → that rebalance is skipped and listed in the report.
- The snapshot is too short for one full window plus one holding month → the run stops with a message naming the shortfall.

### Return structure analysis (`STRUC`)
**Serves:** Goal 6, Goal 2
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** At each rebalance the window's correlation spectrum is set against random-matrix noise, showing how many factors stand out and how much correlation is left once they are removed. The factor count and the residual correlation feed the estimators and the hierarchical clustering.

**Requirements**
- **STRUC-01** At each rebalance, the window's correlation eigenvalues are compared with the Marchenko–Pastur upper edge for its stock-to-day ratio, and the number of eigenvalues above the edge is recorded.
  - Given a window of pure independent noise with N = 500 and T = 504, when the spectrum is analysed, then no eigenvalue exceeds the edge by more than 5%.
- **STRUC-02** At each rebalance, the share of variance explained by each of the top components above the edge is recorded.
  - Given a rebalance, when its record is read, then the first component's share and the count above the edge are present.
- **STRUC-03** At each rebalance, the mean absolute off-diagonal correlation of residual returns after removing the components above the edge is recorded beside that of the raw returns, using the `data-analysis` skill for the spectrum and residual analysis.
  - Given a one-factor synthetic panel, when residuals are taken, then their mean absolute off-diagonal correlation is below a tenth of the raw returns'.

**Edge cases & errors**
- A member with zero variance in the window → excluded from that rebalance and counted; it never yields an undefined correlation.

### Covariance estimators (`COV`)
**Serves:** Goal 6
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** Five estimates are made from the same window at every rebalance, so they compete on identical data.

**Requirements**
- **COV-01** The sample covariance of the window's returns.
  - Given a window, when the sample estimate is made, then it equals the unbiased sample covariance of the eligible members' returns.
- **COV-02** A shrinkage estimate toward the constant-correlation target, with the shrinkage intensity chosen from the window's data and recorded.
  - Given a window, when the shrinkage estimate is made, then its intensity lies in [0, 1] and is recorded.
- **COV-03** A denoised estimate: correlation eigenvalues inside the Marchenko–Pastur noise band are replaced by their average, the trace is preserved, the diagonal is reset to 1, and the result is rescaled by the sample variances.
  - Given a window, when the denoised estimate is made, then its correlation has a unit diagonal, the same trace as the sample correlation, and the eigenvalues above the edge unchanged.
- **COV-04** A factor-model estimate with k equal to the number of eigenvalues above the edge (at most 20), plus diagonal residual variances; and a market-only variant with k = 1.
  - Given a rebalance with 4 eigenvalues above the edge, when factor estimates are made, then one uses 4 factors and one uses 1.
- **COV-05** Every estimate is symmetric, positive semi-definite and finite; one that is not is marked failed for that rebalance, never silently replaced.
  - Given an estimate with a negative eigenvalue, when it is checked, then that estimator is marked failed for that rebalance and the report counts it.

### Portfolios (`PORT`)
**Serves:** Goal 6
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** Minimum variance, risk parity and hierarchical risk parity are built on every estimator at every rebalance, beside two baselines, all under the same rules.

**Requirements**
- **PORT-01** Every portfolio is long-only, fully invested and holds at most 5% in any member.
  - Given any portfolio, when its weights are checked, then all are ≥ 0, all are ≤ 0.05, and they sum to 1 within 1e-8.
- **PORT-02** A minimum-variance portfolio is built on each estimator.
  - Given an estimate, when the minimum-variance portfolio is built, then no portfolio meeting PORT-01 has lower predicted variance under that estimate, within 1e-6 relative.
- **PORT-03** A risk-parity portfolio is built on each estimator: every member not held at the cap contributes equal risk.
  - Given an estimate where no weight reaches the cap, when risk parity is built, then every member's risk contribution is equal within 1e-6 relative.
- **PORT-04** A hierarchical risk-parity portfolio is built on each estimator, clustering members on the residual-return correlation from STRUC-03 and allocating with the estimator's covariance.
  - Given a synthetic panel of two uncorrelated blocks of equal size and variance, when HRP is built, then each block receives half the weight within 1e-6.
- **PORT-05** Two baselines are built at every rebalance: equal weight over the eligible members, and minimum variance on the sample covariance.
  - Given 400 eligible members, when the equal-weight baseline is built, then every weight is 1/400.
- **PORT-06** A portfolio whose construction fails is recorded as failed for that rebalance, never replaced by another portfolio.
  - Given a construction that does not converge, when the rebalance completes, then that portfolio is marked failed and the report counts it.

### Out-of-sample evaluation (`EVAL`)
**Serves:** Goal 6
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** Each portfolio is judged by the variance it actually had in the month after it was built; each estimator also by how close its correlations come to what followed; and every "beats the baseline" claim must pass a significance test.

**Requirements**
- **EVAL-01** Each portfolio's out-of-sample variance for a month is the annualised variance of its daily returns over that month, and the pooled figure is the mean across months.
  - Given a portfolio's daily returns over a month, when its variance is computed, then it equals 252 × their sample variance.
- **EVAL-02** Each estimator's correlation error is the Frobenius distance between its correlation matrix and the realised correlation of the next 126 trading days.
  - Given a rebalance with fewer than 126 trading days left in the snapshot, when errors are computed, then that rebalance has none and is excluded from the pooled error.
- **EVAL-03** Each estimator's bias ratio is the realised out-of-sample variance of its own minimum-variance portfolio divided by its predicted variance.
  - Given a portfolio whose realised variance equals its predicted variance, when the ratio is computed, then it is 1.0.
- **EVAL-04** Every claim that a portfolio beats a baseline is tested with the `null-hypothesis-testing` skill on the paired series of monthly out-of-sample variances; it passes only if significant at 5% after Holm correction across all comparisons.
  - Given the full set of comparisons, when the tests run, then each reports its statistic, p-value, corrected decision and the number of months.
- **EVAL-05** Every metric is reported pooled and split into crisis periods (2007-10-01 to 2009-06-30 and 2020-02-19 to 2020-06-30) and calm periods (all other months).
  - Given a month in March 2020, when results are split, then it counts as crisis.
- **EVAL-06** The one-year configuration's results are reported beside the two-year ones, with the same metrics and tests.
  - Given both configurations have run, when results are compared, then every metric appears for both.

### Known-answer bench (`SYNTH`)
**Serves:** Goal 6
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** Before any real data, every estimator and portfolio runs on synthetic return panels whose true covariance is known, so the code is shown right before the market says anything.

**Requirements**
- **SYNTH-01** Synthetic panels with a planted number of factors and known true covariance are generated from a seed, at the real setup's size (N = 500, T = 504).
  - Given the same seed, when a panel is generated twice, then both are identical.
- **SYNTH-02** On a panel with k strong planted factors, the count of eigenvalues above the Marchenko–Pastur edge equals k.
  - Given 3 planted factors each explaining at least 5% of variance, when the spectrum is analysed, then exactly 3 eigenvalues lie above the edge.
- **SYNTH-03** Shrinkage, denoised and factor-model estimates are closer to the true covariance than the sample estimate.
  - Given a planted 3-factor panel, when each estimate's Frobenius distance to the true covariance is measured, then all three are below the sample estimate's.
- **SYNTH-04** On a pure-noise panel, no eigenvalue exceeds the edge by more than 5% and the denoised correlation is the identity within 1e-6.
  - Given a pure-noise panel, when it is denoised, then every off-diagonal correlation is 0 within 1e-6.

### Variance report (`VREP`)
**Serves:** Goal 6, Goal 4
**Source:** [ideas/variance-first-portfolios.md](ideas/variance-first-portfolios.md)
**Behavior:** One static report per run, naming its snapshot and configuration, ranks estimators and portfolios by out-of-sample variance with the significance results, regimes and the one-year check.

**Requirements**
- **VREP-01** The report has sections for return structure, the estimator comparison, portfolios against baselines with significance, regimes, the one-year check, and eligibility and failure counts; its charts follow the `dataviz` skill.
  - Given a completed run, when the report is opened, then every section is present and the snapshot ID and configuration are stated.
- **VREP-02** Regenerating the report from the same snapshot and configuration gives identical numbers.
  - Given two runs on one snapshot, when their tables are compared, then they are identical.

## Assumptions
- The universe is every security that was an S&P 500 member on any day in the window, with its full listed history within the window.
- Each listed share class is its own security; tickers are dated labels.
- Exits are recorded by type and last trading day; no synthetic final-day return is added.
- Adjusted prices and returns are computed by the platform; the source's adjusted prices are a check.
- Snapshots are complete downloads, started by hand.
- Flag thresholds: jump > 40%, stale ≥ 5 days, adjustment difference > 0.1%, cross-check difference > 0.5%.
- The cross-check uses a fixed sample of 50 current members.
- Stage 2 uses daily total returns with no risk-free adjustment, since only variance is measured; portfolios are held buy-and-hold within each month.

# The spec: template, writing rules, hygiene check

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown

|---|---|

- **CODE-01** [One testable statement of what the system does.]
  - Given [context], when [action], then [observable result].
  - Given [...], when [...], then [...].

  - Given [...], when [...], then [...].
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence and budget limits are `QR-` items ("data costs ≤ $50 a month"), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads the idea file and the conversation.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of torchvision's ResNet-18" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.
