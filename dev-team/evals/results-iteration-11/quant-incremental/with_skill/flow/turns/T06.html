# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

# Quant Research Platform — Spec

**Status:** Approved · **Last updated:** 2026-10-18 · **Brief:** [brief.md](brief.md)

## Summary
A local data foundation for honest quant research on US stocks: it builds dated, validated snapshots of a point-in-time S&P 500 daily dataset (prices, returns, splits, dividends, delisted members included), reports every check and cross-source disagreement, loads any slice in one step, and lets the user explore it in a local app. See the [brief](brief.md) for why.

## Users
| User | What they need to do |
|---|---|
| Researcher (the owner, sole user) | Build and refresh the dataset, read its health, load slices for research, and explore prices, universe and problems by eye |

## Scope
**In scope:** Dataset build, As-of snapshots, Point-in-time universe, Prices and returns, Data health report, Research loader, Exploratory analysis, Data explorer.
**Out of scope:**
- Company fundamentals; Stage 1 holds prices and corporate actions only.
- Real money, order placement or any brokerage link; research and paper trading only.
- Intraday bars, live market feeds, non-US markets.
- Stocks that were never S&P 500 members.
- Using the cross-check source to fill gaps in the primary source; it only cross-checks.
- Sharing, hosting or multi-user access to the app.
- Signal research and backtesting (later stages, not yet decided).

## Features

### Dataset build (`BUILD`)
**Serves:** Goal 1, Goal 2
**Stage:** S1
**Behavior:** The user starts a build, from the command line or the app. It downloads everything the dataset needs from the primary source, cleans it, validates it, cross-checks surviving stocks against the second source, and stores the result as a new dated snapshot with its health report.

**Requirements**
- **BUILD-01** One command builds a complete new snapshot, with no other manual steps.
  - Given valid credentials and no existing snapshots, when the user runs the build command, then a new snapshot holding every dataset in Data requirements exists when it finishes.
- **BUILD-02** An interrupted build resumes without downloading again what it already has.
  - Given a build stopped halfway through the download, when the user runs it again the same day, then already downloaded stocks are not requested again and the finished snapshot equals one built without interruption.
- **BUILD-03** Cleaning never changes a value without recording it.
  - Given a raw price the cleaning step corrects or removes, when the build finishes, then the health report lists that stock, date, field, value before, value after and the rule that made the change.
- **BUILD-04** A build whose blocking checks fail is stored but marked failed.
  - Given a build where a blocking check (HLTH-02) fails, when it finishes, then the snapshot is listed with status "failed" and the loader refuses it unless the user asks for it by name.
- **BUILD-05** The app shows a running build's progress live.
  - Given a build in progress, when the user has the app open, then it shows the current phase (download, clean, validate, cross-check, store), the share of stocks done and the elapsed time, updated at least every 2 seconds.
- **BUILD-06** A build can be started from the app.
  - Given no build is running, when the user starts one in the app, then it runs exactly as the command does and its progress appears (BUILD-05).

**Edge cases & errors**
- Credentials missing or rejected → the build stops before downloading, with a message naming the problem; no snapshot is created.
- Primary source unreachable or rate-limited mid-build → the build retries, then stops resumably (BUILD-02) with a message; no partial snapshot is listed as usable.
- Cross-check source unreachable → the build finishes; the report marks the cross-check "incomplete" with the stocks not checked, never "passed".
- A second build started while one runs → refused, naming the running build.

### As-of snapshots (`SNAP`)
**Serves:** Goal 3
**Stage:** S1
**Behavior:** Each build is a snapshot named by the date its data was retrieved. Snapshots never change once finished, so any result can be reproduced by naming the snapshot it used, even after the vendor revises its history.

**Requirements**
- **SNAP-01** A finished snapshot is never modified.
  - Given a finished snapshot, when later builds run, then every value in it is unchanged.
- **SNAP-02** Rebuilding the derived data from a snapshot's saved raw data gives identical numbers.
  - Given a snapshot, when its returns, adjusted prices, universe and health report are rebuilt from its raw data, then every number equals the original exactly.
- **SNAP-03** The same load from the same snapshot always returns the same result.
  - Given a load request naming a snapshot, when it is repeated after newer snapshots exist, then the result is identical value for value.
- **SNAP-04** The user can list snapshots.
  - Given several snapshots, when the user lists them, then each shows its date, status (healthy or failed), date range covered, number of stocks and number of unexplained cross-check differences.
- **SNAP-05** The user can compare two snapshots to see what the vendor revised.
  - Given two snapshots, when the user compares them, then every price, split, dividend and membership date that differs on dates both cover is listed with both values, plus counts per field.

**Edge cases & errors**
- Two builds on the same day → the second gets a distinct name (date plus sequence number); neither overwrites the other.
- A snapshot whose files were altered or damaged → loading it fails with a message that it no longer matches its record, never returns altered data.
- Disk space runs out mid-build → the build stops resumably; earlier snapshots are untouched.

### Point-in-time universe (`UNIV`)
**Serves:** Goal 1
**Stage:** S1
**Behavior:** For any trading day in the covered history, the universe is the S&P 500 as it stood that day: stocks that later left the index or were delisted are in it, stocks that joined later are not.

**Requirements**
- **UNIV-01** The universe on a day is exactly the stocks that were index members that day.
  - Given a stock added to the index on 2015-03-20, when the universe is asked for 2015-03-19, then the stock is absent; for 2015-03-20, it is present.
  - Given a stock removed on 2012-06-01, when the universe is asked for 2010-01-04, then the stock is present.
- **UNIV-02** The user's ten delisted former S&P 500 members all appear.
  - Given the user's list of 10 delisted former members, when a snapshot is built, then each has its index entry and exit dates and daily prices up to its last trading day, and the health report shows this check passing for all 10.
- **UNIV-03** A stock keeps one identity through ticker changes.
  - Given a member that changed ticker, when its history is loaded, then prices before and after the change form one continuous series under one permanent identifier.
- **UNIV-04** A reused ticker never merges two companies.
  - Given a ticker held by one company until 2008 and by another from 2012, when either is loaded, then each company's history is separate and neither includes the other's prices.
- **UNIV-05** Daily member counts are checked.
  - Given a snapshot, when validated, then every trading day with fewer than 495 or more than 510 members is listed in the health report.

**Edge cases & errors**
- Companies with two share classes in the index at once → both classes are members, each with its own identifier.
- A member with no price on a day it was a member → listed in the health report (HLTH-02), not dropped from the universe.
- A day before the membership history begins → the universe request fails with a message naming the first covered day.

### Prices and returns (`PRICE`)
**Serves:** Goal 1, Goal 4
**Stage:** S1
**Behavior:** Every member has raw daily prices, split-adjusted prices, and daily returns with and without dividends, all derived from the same snapshot's raw prices and corporate actions.

**Requirements**
- **PRICE-01** Split-adjusted prices are continuous across splits.
  - Given a 2-for-1 split effective day D, when split-adjusted closes are loaded, then the raw close before D is divided by 2 and the day-D return reflects only the market move.
- **PRICE-02** Daily price return is the change in split-adjusted close.
  - Given split-adjusted closes 100 then 102, when the price return is loaded, then it is 0.02.
- **PRICE-03** Daily total return adds the cash dividend on its ex-date.
  - Given a close of 100, a $1 dividend with ex-date the next day and a next-day close of 100, when the total return is loaded, then it is 0.01 for the ex-date.
- **PRICE-04** Adjustments come from the snapshot's own recorded corporate actions.
  - Given a split or dividend corrected by cleaning (BUILD-03), when the snapshot is built, then adjusted prices and returns use the corrected value.
- **PRICE-05** No values are invented after a stock's last trading day.
  - Given a stock delisted on day D, when its data is loaded for a range past D, then rows end at D with no filled-forward prices or returns.

**Edge cases & errors**
- A missing trading day mid-series → no return is computed across the gap silently; the day's return is empty and the gap is listed in the health report.
- A split with no matching price jump, or a jump with no split → flagged by HLTH-02, never auto-adjusted.

### Data health report (`HLTH`)
**Serves:** Goal 2
**Stage:** S1
**Behavior:** Every snapshot carries a report of every check run, every disagreement with the cross-check source and every fix cleaning applied. Nothing found is hidden: each problem is either explained or shown as unexplained.

**Requirements**
- **HLTH-01** The report lists every check run, not only failures.
  - Given a build, when its report is opened, then every check appears with its result, its severity (blocking or warning) and the number of records affected, including checks with zero.
- **HLTH-02** The build runs at least these checks: missing trading days for a member, non-positive prices, high below low, close outside the day's high–low range, duplicate dates, daily moves beyond ±50% with no corporate action, splits with no matching price move, member days with no price, daily member counts (UNIV-05) and the ten-delisted check (UNIV-02).
  - Given a snapshot seeded with one example of each problem, when validated, then each check reports exactly that example.
- **HLTH-03** Surviving stocks' closes are cross-checked against the second source.
  - Given a surviving stock, when cross-checked, then every day its split-adjusted close differs from the second source by more than 0.5% is listed with both values.
- **HLTH-04** Splits are cross-checked against the second source.
  - Given a surviving stock, when cross-checked, then every split that is missing from either source, or differs in ratio or date, is listed.
- **HLTH-05** Dividends are cross-checked against the second source.
  - Given a surviving stock, when cross-checked, then every dividend missing from either source, or differing by more than $0.01 or in ex-date, is listed.
- **HLTH-06** Stocks the second source cannot check are counted, not skipped silently.
  - Given delisted members, when cross-checked, then the report shows them as "not cross-checkable" with their count.
- **HLTH-07** The user can attach an explanation to a difference.
  - Given a listed difference, when the user records an explanation, then the difference shows as explained with that note, and the snapshot's unexplained count drops by one.
- **HLTH-08** Explanations carry to later snapshots.
  - Given an explained difference, when a later snapshot finds the same difference (same stock, date, field and values), then it is shown as explained with the same note.

**Edge cases & errors**
- The second source returns nothing for a surviving stock → listed as "no cross-check data", counted separately from differences.
- A difference that changes between snapshots → shown as unexplained again, with the earlier note visible for reference.

### Research loader (`LOAD`)
**Serves:** Goal 4
**Stage:** S1
**Behavior:** From a research session, one call returns the requested slice of a snapshot as a table: which stocks (a list, or the point-in-time universe), which dates, which fields.

**Requirements**
- **LOAD-01** One call returns any slice.
  - Given stocks, a date range and fields, when the user makes one loader call, then it returns a table with one row per stock per trading day and one column per field.
- **LOAD-02** The loader offers raw open, high, low, close and volume, split-adjusted prices, price return, total return, and dividend and split amounts.
  - Given a request for each field, when loaded, then each column matches its definition in PRICE.
- **LOAD-03** Asking for the universe returns each stock only on its member days.
  - Given a request for the point-in-time universe over 2008–2010, when loaded, then a stock removed in 2009 has rows only up to its exit date.
- **LOAD-04** Without a named snapshot, the loader uses the latest healthy one.
  - Given a healthy snapshot and a newer failed one, when the user loads without naming one, then the healthy one is used.
- **LOAD-05** Every result says which snapshot it came from.
  - Given any load, when it returns, then the result carries the snapshot's name.

**Edge cases & errors**
- An unknown ticker or identifier → error naming it; no partial result.
- Dates outside the snapshot's coverage → error naming the covered range.
- No healthy snapshot exists → error saying so and naming the failed ones.

### Exploratory analysis (`EDA`)
**Serves:** Goal 1, Goal 2
**Stage:** S1
**Behavior:** For any snapshot, the user can produce a basic exploratory analysis of the dataset and read it as a report with plots.

**Requirements**
- **EDA-01** The dataset is characterised with the `data-analysis` skill, given a snapshot's point-in-time universe returns and coverage; it passes when the report shows coverage and missingness by year, the cross-sectional distribution of daily returns with its tails, the largest moves with their dates, and the member count over time, each with its plot.
  - Given a snapshot, when the analysis is run, then the report contains each listed item with a plot.
- **EDA-02** The analysis shows the size of survivorship bias.
  - Given a snapshot, when the analysis is run, then it plots the equal-weighted total return of the point-in-time universe against the same for only today's members, over the full history, with the annualised difference.
- **EDA-03** Rerunning the analysis on the same snapshot gives the same numbers.
  - Given a snapshot, when the analysis runs twice, then every number in both reports is identical.

**Edge cases & errors**
- A failed snapshot → the analysis runs only when named explicitly, and the report states the snapshot failed.

### Data explorer (`EXPL`)
**Serves:** Goal 5, Goal 2
**Stage:** S1
**Behavior:** A local app in the browser for looking at the data by eye: a stock's prices with its corporate actions and index membership, the universe on any day, the health report, the cross-check overlay, and running builds. Every view reads from one chosen snapshot.

**Requirements**
- **EXPL-01** Every view shows data from the chosen snapshot, named on screen.
  - Given two snapshots, when the user switches between them, then all views reload from the chosen one and its name and status stay visible.
- **EXPL-02** A stock view charts its full price history with its events.
  - Given any member, when opened, then raw and split-adjusted closes are charted with splits, dividends and index entry and exit marked on their dates.
- **EXPL-03** A universe view shows the members on any day.
  - Given a date, when chosen, then the members and their count are shown, and stepping to the next trading day highlights who joined and who left.
- **EXPL-04** A health view lists the report's findings, filterable.

# Quant Research Platform — Architecture

**Status:** Draft · **Shape:** Multi-package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
`qdata`, a Python package, builds each dated snapshot. It downloads Sharadar prices, corporate actions, tickers and S&P 500 changes, cleans and validates them, cross-checks surviving members against Yahoo through yahooquery, and writes an immutable folder of Parquet files with a hashed manifest. Research sessions load slices from a snapshot through `qdata.load`. `qdata serve` runs a local FastAPI server on 127.0.0.1. `explorer`, a TypeScript + React app, reads snapshots over HTTP and follows builds over a WebSocket. Every message between the two has a typed contract generated from one source.

```mermaid

  Sharadar[(Sharadar API)] --> qdata
  Yahoo[(Yahoo via yahooquery)] --> qdata
  qdata -->|snapshots: Parquet + manifest| disk[(data/)]
  notebook[research session] -->|qdata.load| qdata
  explorer -->|HTTP queries| qdata
  qdata -->|WebSocket: build progress| explorer
```

- `qdata` never imports or builds `explorer`. `qdata serve` serves `packages/explorer/dist/` as static files when that folder exists (AD-09).
- Inside `qdata`, layers are enforced by `import-linter` ([qdata architecture](packages/qdata/architecture.md#dependency-rules)).

## System pipelines
### PL-01: Explore a snapshot
**Trigger:** the user opens the app or picks a snapshot · **Covers:** EXPL-01–EXPL-06, SNAP-04, QR-05
**Purpose:** the user looks at one snapshot's prices, events, universe, health findings and cross-check overlay by eye.
1. `explorer` → `qdata`: `qdata.http_list_snapshots` (picker, with status and unexplained counts)
2. `explorer` → `qdata`: `qdata.http_securities` (stock search for the chosen snapshot)
3. `explorer` → `qdata`: `qdata.http_stock`, `qdata.http_universe`, `qdata.http_health`, `qdata.http_crosscheck` (one per view, each naming the snapshot)

### PL-02: Start and watch a build from the app
**Trigger:** the user presses Build in the app, or a build is already running when the app opens · **Covers:** BUILD-05, BUILD-06
**Purpose:** the user starts a build without the terminal and watches its phase, share of stocks done and elapsed time live.
1. `explorer` → `qdata`: `qdata.http_start_build` (refused while one runs, naming it)
2. `qdata` → `explorer`: `qdata.ws_builds` (progress events from any running build, started by the CLI or the app)
3. `explorer` → `qdata`: `qdata.http_list_snapshots` (on a `finished` event, so the new snapshot joins the picker)

### PL-03: Explain a difference
**Trigger:** the user writes a note on a finding in the health view · **Covers:** EXPL-07, HLTH-07
**Purpose:** a cross-check difference becomes explained, now and in later snapshots that find it again.
1. `explorer` → `qdata`: `qdata.http_explain`
2. `explorer` → `qdata`: `qdata.http_health` (refreshed: the finding shows as explained and the count drops)

## Cross-cutting concerns
- **Local only (QR-02, QR-06):** the server binds 127.0.0.1 and rejects any request whose `Host` or `Origin` header is not localhost. No other service runs.
- **Credentials (QR-07):** the Sharadar key comes from `SHARADAR_API_KEY` or a git-ignored `.env`. A logging filter and the progress writer mask it everywhere. The API client never logs request URLs, because the key travels in the query string.
- **Cost (QR-01):** Sharadar is the only paid source. Whether the user's plan covers every table within $50 a month is PB-01's question.

## Decisions
### AD-01: Two packages, one per runtime
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-08: the user named "a TypeScript + React browser frontend over a Python backend (HTTP and WebSocket)". The two halves run in different runtimes, with separate toolchains and installs. The research loader and build share data and types, so they stay together.
- **Decision:** two packages. `qdata` (Python) holds everything that touches data, including the HTTP and WebSocket server. `explorer` (TypeScript) is the app.
- **Alternatives:** One Python package with the frontend in a subfolder: the TypeScript build and its contract would have no home of their own. Three packages, with the server split from `qdata`: the server's stack (FastAPI, uvicorn) is light, and the server reads the same store as the loader. It can move out later, behind `qdata.create_app`.
- **Consequences:** The HTTP contract is the only seam between the packages, so it needs a schema and fixtures (AD-10). Two toolchains run in the build: uv and npm.

### AD-02: Python 3.12 with uv; TypeScript 5.6, Vite and React 18
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-08 fixes the languages. The data libraries (pandas, pyarrow, DuckDB, exchange_calendars) all ship arm64 macOS wheels for 3.12 (QR-02).
- **Decision:** Python `>=3.12,<3.13`, managed by uv with one lockfile. For the app: TypeScript 5.6, React 18.3 and Vite 5.4 on Node 22, with an npm lockfile.
- **Alternatives:** Python 3.13: newer, and some pinned libraries lag on new versions. A frontend framework such as Next.js: brings server rendering a local single-page app doesn't need.
- **Consequences:** Each package has its own lockfile and checks. A repo-level script runs both.

### AD-03: Sharadar REST API as the primary source
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UR-03, UR-13: the user's Sharadar subscription at api.sharadar.com is the primary source. These are checked against DATA-01–DATA-04, DATA-06 and QR-01. Docs read 2026-10-18:
  - <https://sharadar.com/docs/stocks>: daily OHLCV for "active and delisted US public stocks" from December 1997. `open`/`high`/`low`/`close`/`volume` are split-adjusted; `closeunadj` is raw; there is a `lastupdated` column.
  - <https://sharadar.com/docs/actions>: splits, cash dividends, ticker changes, listing and delisting dates.
  - <https://sharadar.com/docs/sp500>: S&P 500 additions and deletions with effective dates from January 1998, and current constituents.
  - <https://sharadar.com/docs/tickers>: `permaticker`, "a unique and unchanging identifier for a security (share class)", plus `isdelisted`, `firstpricedate` and `lastpricedate`.
  - Queries go to `https://api.sharadar.com/v1.0/data/<table>`.
- **Decision:** `qdata` reads four Sharadar tables (`stocks`, `actions`, `sp500`, `tickers`) through an `httpx` client behind `qdata.PrimarySource`. It keeps their raw rows in each snapshot. History starts from the first day both `stocks` and `sp500` cover (January 1998, unless PB-01 shows otherwise).
- **Alternatives:** Sharadar through Nasdaq Data Link: the same data, but the user subscribes at api.sharadar.com (UR-13). Free S&P 500 lists (Wikipedia) plus Yahoo prices: no delisted prices, so they fail DATA-01, and the brief rules out Yahoo as a source.
- **Consequences:** Every other module sees Sharadar only through `qdata.RawDataset`, so a later source change touches one module. The docs don't list `actions` codes or the split `value` format; the parser waits on PB-01 samples.
- **Probe:** PB-01: does the user's Sharadar plan return `actions`, `sp500` and `tickers` as well as `stocks`, with full history, within $50 a month? What are the `actions` codes and the split `value` format? Does `lastupdated` move when history is restated? What are the page and rate limits? Are the user's 10 delisted members present?

### AD-04: yahooquery as the cross-check source
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UR-04, UR-23: the user named yahooquery, "free, unofficial Yahoo client". Checked against DATA-05 and HLTH-03–HLTH-06. Docs read 2026-10-18:
  - <https://github.com/dpguthrie/yahooquery/blob/master/docs/docs/guide/ticker/historical.md>: `Ticker.history(period="max", interval="1d")` returns `open`, `high`, `low`, `close`, `volume`, `adjclose` and `dividends` per symbol and date.
  - The 2.4.1 source (`yahooquery/ticker.py`) adds a `splits` column when Yahoo reports splits.
  - <https://pypi.org/project/yahooquery/>: 2.4.1, released 2025-05-15.
- **Decision:** `qdata.CrossCheckSource` wraps yahooquery 2.4.1, pinned exactly. It fetches full daily history for surviving members only, in batches, keeping `close`, `dividends` and `splits`. A symbol that returns nothing is recorded as "no cross-check data" (spec HLTH edge case), never as a pass.
- **Alternatives:** yfinance: the same Yahoo data, and the user picked yahooquery. A paid second source: unnecessary under the budget, since this source only cross-checks.
- **Consequences:** The client is unofficial and can break or be throttled without notice. A failed cross-check marks the report "incomplete" (spec BUILD edge case) and never fails the build. The docs don't say whether `close` and `dividends` are split-adjusted; HLTH-03 and HLTH-05 compare like with like only once PB-02 settles it.
- **Probe:** PB-02: for current S&P 500 members, does `history(period="max")` return splits and dividends? Are `close` and `dividends` split-adjusted? How fast can ~500 symbols be fetched without throttling (QR-03)?

### AD-05: Immutable snapshot folders of Parquet, with a hashed manifest and DuckDB reads
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** SNAP-01–SNAP-03 need snapshots that never change, rebuild exactly, and refuse damaged files. QR-04 needs one universe-year in ≤ 2 s and full history in ≤ 15 s; QR-08 needs ≤ 5 GB per snapshot. Roughly 1,100 securities × 28 years of daily rows is about 8 M price rows.
- **Decision:** each snapshot is a folder `data/snapshots/<YYYY-MM-DD>[-N]/` with raw tables, derived tables and health tables as zstd Parquet. A `manifest.json` records each file's SHA-256, the status, coverage and counts. Files are read-only once committed. The loader checks the manifest hashes when it opens a snapshot, and reads through DuckDB into pandas.
- **Alternatives:** A database (DuckDB file or SQLite) per snapshot: one file is harder to hash and diff per table, and writes in place invite edits. A shared table with an `as_of` column: one damaged file breaks every snapshot, and SNAP-01 rests on code discipline alone.
- **Consequences:** Same-day builds get a sequence suffix. A refresh copies the previous snapshot's unchanged raw rows rather than linking them, so deleting one snapshot never damages another. Disk grows by about one snapshot per build.

### AD-06: Raw prices and actions are the record; every adjustment is recomputed
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** PRICE-01–PRICE-04 and LOAD-02 need raw OHLC, split-adjusted prices and returns derived from the snapshot's own (cleaned) actions. SNAP-05 needs vendor revisions to show as value changes. Sharadar serves OHLC split-adjusted and only `closeunadj` raw (AD-03), and its split-adjusted history is restated after every split.
- **Decision:** raw OHLC is the vendor's split-adjusted value × (`closeunadj` / `close`) for that day. Split-adjusted prices are recomputed from raw prices and the snapshot's cleaned splits. Price return is the change in split-adjusted close; total return adds the ex-date cash dividend, in split-adjusted terms. Vendor-adjusted columns are kept raw only, so the split-consistency check (HLTH-02) can compare them.
- **Alternatives:** Use Sharadar's adjusted columns directly: fails PRICE-04, since a cleaned split would never reach the prices.
- **Consequences:** Derivation is one pure function of raw tables, which makes SNAP-02 a rebuild-and-compare. A day where `close` is zero or missing has no raw OHLC; it becomes a finding, never a fill.

### AD-07: Sharadar `permaticker` is the permanent identity; membership comes from `sp500` changes
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** UNIV-01, UNIV-03, UNIV-04 and DATA-02, DATA-04. The `sp500` table names members by ticker at the date of each change. `tickers` gives one `permaticker` per share class; `actions` records ticker changes.
- **Decision:** a security's id is its `permaticker`. A ticker history (ticker, start, end) is built from `tickers` and `actions` ticker changes. Each `sp500` event's ticker resolves to the permaticker holding that ticker on that date. Membership is a set of intervals `[entry, exit)` per permaticker, so a company that leaves and rejoins has two. An event whose ticker resolves to no security, or to two, is a blocking finding.
- **Alternatives:** Ticker as the key: merges reused tickers and splits renamed ones, failing UNIV-03 and UNIV-04. An outside identifier (CUSIP, FIGI): not in the subscription.
- **Consequences:** The first day the universe covers is the first `sp500` date whose full constituent list can be rebuilt. The `current` rows rebuild today's list; walking the changes backward gives every earlier day, and the earliest covered day is where that walk starts. The count check (UNIV-05) catches a walk that goes wrong.

### AD-08: Builds run in a staged run folder with checkpoints, a lock and a progress log
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** BUILD-01, BUILD-02 and BUILD-04–BUILD-06 need a build that resumes without re-downloading, refuses a second run, and reports progress to the app whoever started it. QR-03 needs a refresh in ≤ 15 minutes.
- **Decision:**
  - A build works in `data/runs/<run-id>/`. Each downloaded batch of securities is written there before the next is requested. A rerun on the same day resumes the newest unfinished run.
  - `data/build.lock` holds the running build's id and pid. A second build is refused, naming it; a lock whose pid is gone is reclaimed.
  - Progress events are appended to `data/runs/<run-id>/progress.jsonl` (`qdata.ProgressEvent`). The server tails that file, so builds started from the CLI and from the app look the same.
  - The app's Build button runs the same `qdata build` command as a subprocess (BUILD-06).
  - A refresh requests `stocks` rows with `lastupdated` after the previous snapshot's retrieval date. It replaces the whole history of every security with any changed row, and copies the rest from the previous snapshot.
- **Alternatives:** Build inside the server process: the CLI and app paths diverge, and a server restart kills the build. A job queue (Celery, RQ): a broker the laptop doesn't need.
- **Consequences:** Commit is the last step: an atomic rename of the run's output into `data/snapshots/`. A crash before commit never shows as a usable snapshot. The refresh's correctness rests on `lastupdated` moving on every restatement (PB-01); until that is confirmed, `--full` forces a full download.

### AD-09: FastAPI on 127.0.0.1; HTTP for queries, a WebSocket only for build progress
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-08, UR-20: "HTTP for data queries, WebSocket only for live progress of download/validation runs." This serves EXPL-01–EXPL-07, BUILD-05, BUILD-06, QR-05 and QR-06.
- **Decision:** `qdata serve` runs FastAPI 0.115 under uvicorn 0.30, bound to 127.0.0.1, with a Host and Origin allow-list of localhost. Data queries are JSON over HTTP under `/api/`. `/ws/builds` streams `qdata.ProgressEvent` messages only. The server serves `packages/explorer/dist/` when it exists; in development, Vite's dev server proxies `/api` and `/ws` to it.
- **Alternatives:** Flask with flask-sock: no typed models or OpenAPI, so UR-25's typed contract would be hand-kept. Server-sent events for progress: the user named WebSocket.
- **Consequences:** One port and one command open the app. Every response is a pydantic model, which feeds AD-10.

### AD-10: Typed contract: pydantic models are the source; TypeScript types are generated
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** system
- **Context:** UR-25: the frontend-backend interface comes "with typed contracts". Two runtimes share no types.
- **Decision:** every HTTP request, response and WebSocket message is a pydantic v2 model in `qdata`. `qdata openapi` writes the OpenAPI 3.1 document, with the WebSocket message schema under `components`, to `packages/qdata/openapi.json`. openapi-typescript 7 generates `packages/explorer/src/api/generated.ts` from it. A check regenerates both and fails on any diff. Boundary fixtures are JSON payloads validated against the same schema on both sides.
- **Alternatives:** Hand-written TypeScript types: drift silently. tRPC or GraphQL: TypeScript-first or a second schema language, against a Python provider.
- **Consequences:** Changing a route means regenerating the types in the same change. `explorer` fails to compile against a removed field, which is the point.

### AD-11: Charts drawn with D3 modules, styled to the frontend-design direction
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `explorer`
- **Context:** EXPL-08 asks for a deliberate visual direction, not a default dashboard; QR-05 needs a full-history chart (about 7,000 days, two series plus event marks) in ≤ 1 s.
- **Decision:** `d3-scale`, `d3-shape`, `d3-axis` and `d3-zoom` 7.x draw price lines on a canvas and event marks and axes in SVG, inside React components. The look comes from the mock-ups the user approves under the `frontend-design` skill.
- **Alternatives:** A chart library (ECharts, Recharts): faster to start, but its defaults are the "default dashboard" EXPL-08 rules out. uPlot: fast, and harder to bend to a custom design.
- **Consequences:** More chart code to own; the chart module is small and tested on its scales and marks.

### AD-12: Explanations live outside snapshots, keyed by a finding fingerprint
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** HLTH-07, HLTH-08 and EXPL-07: explanations attach to differences and carry forward, while snapshots never change (SNAP-01).
- **Decision:** explanations are appended to `data/explanations.jsonl`, one `qdata.Explanation` per line. Each is keyed by the finding's fingerprint: check, security, date, field and both values. A snapshot's report joins its findings to explanations when read, so the unexplained count is computed, not stored. A finding whose values changed matches no fingerprint and shows unexplained, with the earlier note found by check, security, date and field.
- **Alternatives:** Write explanations into the snapshot: breaks SNAP-01. SQLite: more than an append-only list of notes needs.
- **Consequences:** The latest line for a fingerprint wins, so a note can be rewritten without deleting history. Unexplained counts change over time while snapshot files do not.

### AD-13: NYSE trading calendar from exchange_calendars
**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `qdata`
- **Context:** DATA-06 allows only US exchange trading days; HLTH-02's missing-day check needs to know which days should exist.
- **Decision:** the `XNYS` calendar from exchange_calendars 4.x defines trading days. Rows on other days are a cleaning removal, recorded (BUILD-03).
- **Alternatives:** The union of dates in the price data: can't see a day the vendor dropped. pandas_market_calendars: similar, and it depends on exchange_calendars anyway.
- **Consequences:** Unscheduled closures (2001-09-11, 2012-10-29, national days of mourning) come from the library; a disagreement shows up as missing-day findings across every member at once.

## Risks and open questions
- **The Sharadar plan may not include `actions`, `sp500` or `tickers`** (UR-13 says "Sharadar prices"). Without them DATA-02–DATA-04 fail and QR-01 may not hold. PB-01 answers this; AD-03 stays Proposed until it does.
- **Yahoo's adjustment conventions are undocumented**, and the unofficial client can be throttled. PB-02 answers this; AD-04 stays Proposed until it does.
- **Refresh in ≤ 15 minutes (QR-03) rests on `lastupdated`** (AD-08, PB-01). Until it's confirmed, every build is a full build.
- **Rebuilding the earliest universe from `sp500` changes** may break where the change list has gaps (AD-07). UNIV-05's count check is the guard; the first build's findings will show it.

# qdata — Architecture

**Package:** qdata · **Status:** Draft · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`qdata build` downloads raw tables (`sources`) into a run folder (`store`). It cleans them, recording every change (`clean`), resolves identities and membership (`universe`), derives prices and returns (`prices`), and validates and cross-checks the result (`health`). The run is committed as an immutable snapshot (`store`); `build` drives the sequence. Research code calls `loader`, `compare` and `eda`. `server` exposes the same reads to the app, plus build start and progress. `cli` is the command line for all of it.

## Dependency rules
- Layers, top to bottom: `cli` → `server`, `build`, `eda`, `compare` → `loader`, `health` → `clean`, `universe`, `prices`, `sources`, `store` → `core`. A module imports only from layers below it.
- `clean`, `universe` and `prices` are pure: frames in, frames out, with no file or network access.
- Only `store` writes under `data/`; `sources` is the only module with network access.
- Enforced by `import-linter` contracts in the package's checks.

## Interfaces
See [contract.md](contract.md).

## Data
- **Sources:** Sharadar `stocks`, `actions`, `sp500` and `tickers` (DATA-01–DATA-04, AD-03); Yahoo closes, splits and dividends for surviving members only (DATA-05, AD-04).
- **Layout:**
```
data/
  build.lock                      → running build id + pid (AD-08)
  runs/<run-id>/                  → staging batches, progress.jsonl; deleted after commit
  snapshots/<YYYY-MM-DD>[-N]/     → read-only once committed (AD-05)
    manifest.json                 → SHA-256 per file, status, coverage, counts
    raw/       tickers, sp500, actions, prices, yahoo_prices, yahoo_actions .parquet
    derived/   securities, tickers_history, membership, prices .parquet
    health/    checks, findings, changes .parquet
  explanations.jsonl              → append-only notes (AD-12)
  eda/<snapshot>/                 → report.html, numbers.json, plots/
```
- **Flow:** raw tables → `clean` (raw + changes) → `universe` + `prices` (derived) → `health` (checks, findings) → commit. `rebuild` reruns everything after raw from a committed snapshot's raw files and compares (SNAP-02).

## Cross-cutting concerns
- **Errors:** user-facing failures raise `qdata.QDataError` subclasses whose messages name the problem: missing credentials, an unknown security, a range out of coverage, no healthy snapshot, a damaged snapshot. The CLI prints the message, never a traceback.
- **Determinism (SNAP-02, SNAP-03, EDA-03):** every frame is sorted by (permaticker, date) before it is written; no randomness; Parquet written with fixed settings.
- **Speed (QR-03, QR-04):** downloads are batched by security, with concurrency capped below the vendor's rate limit. Loads push filters into DuckDB over the derived Parquet.
- **Disk (QR-08):** zstd Parquet; `build` reports the snapshot size and warns past 5 GB.

# explorer — Architecture

**Package:** explorer · **Status:** Draft · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
A single-page React app. It picks a snapshot from `qdata.http_list_snapshots` and keeps it in the URL, so every view reads from that one snapshot (EXPL-01). Each view fetches its own `qdata.http_*` route through TanStack Query. One WebSocket connection to `qdata.ws_builds` feeds the build panel. All request and response types come from the generated `api/generated.ts` (AD-10).

## Tech stack
| Area | Choice | Decision |
|---|---|---|
| Language and build | TypeScript 5.6, React 18.3, Vite 5.4, Node 22 | AD-02 |
| API types | openapi-typescript 7, generated from `qdata`'s OpenAPI | AD-10 |
| Data fetching | @tanstack/react-query 5 | — |
| Routing | react-router 6 | — |
| Charts | d3-scale, d3-shape, d3-axis, d3-zoom 7.x; canvas lines and SVG marks | AD-11 |
| Tests | vitest, @testing-library/react | — |

## Components
| Component | Responsibility | Covers | Depends on |
|---|---|---|---|
| `api` | Generated types, a typed fetch client for each route, and the progress socket with reconnect | EXPL-01, BUILD-05 | — |
| `shell` | Layout, snapshot picker with name and status always visible, URL state, empty state with a Build offer | EXPL-01, BUILD-06 | `api` |
| `charts` | Time-series chart: canvas lines, event marks, zoom, centring on a date, highlighted days | EXPL-02, EXPL-06, QR-05 | — |
| `stock` | Stock view: raw and split-adjusted closes, with splits, dividends and index entry and exit | EXPL-02, EXPL-05 | `api`, `charts` |
| `universe` | Universe view: members and count on a day, stepping a day, joined and left highlighted | EXPL-03 | `api` |
| `health` | Health view: checks, filterable findings, explanation notes, a link from each finding to the stock view | EXPL-04, EXPL-05, EXPL-07 | `api` |
| `crosscheck` | Overlay of both sources' closes, days beyond 0.5% highlighted, "no data" state | EXPL-06 | `api`, `charts` |
| `builds` | Build panel: start a build, phase, share of stocks done, elapsed time, refreshing the picker on `finished` | BUILD-05, BUILD-06 | `api`, `shell` |

**Skills:** the visual direction for `shell`, `charts`, `stock` and `health` comes from the `frontend-design` skill. The stock and health views are mocked up and approved by the user before they are built (EXPL-08).

## Dependency rules
- Views (`stock`, `universe`, `health`, `crosscheck`, `builds`) never import each other. They link by route: `/s/:snapshot/stock/:permaticker?at=YYYY-MM-DD`.
- Only `api` calls `fetch` or opens a WebSocket. `api/generated.ts` is generated, never edited.
- Enforced by an ESLint `no-restricted-imports` rule.

## Interfaces
See [contract.md](contract.md). Everything consumed is in [qdata's contract](../qdata/contract.md).

## Cross-cutting concerns
- **Speed (QR-05):** one request for a stock's full history, with columnar arrays drawn straight to canvas; a stock is not re-fetched within a session.
- **Local only (QR-06):** the app uses relative URLs only. In development, Vite serves on 127.0.0.1 and proxies `/api` and `/ws`.
- **Errors:** every `ApiError` shows its `message` in place; a lost WebSocket reconnects with backoff and shows that it is reconnecting.

## Project layout
```
packages/explorer/src/   → api/ shell/ charts/ stock/ universe/ health/ crosscheck/ builds/ — one folder per component; index.ts exports it
packages/explorer/tests/ → folders only; files are planned in pipelines.md
packages/explorer/dist/  → built bundle, served by `qdata serve` (git-ignored)
```
