# Extend mode: adding an idea to an existing spec

Read when `dt status` reports `mode: extend`: `docs/spec.md` exists and an accepted idea file (`ideas_ready`), a routed change (`routed_changes`) or the user's words the spec doesn't honour yet (`requests_open`) is the input. Read the spec fully, then `references/spec.md`.

- A brief the idea edited must be `Accepted` too, like the idea itself.
- **No idea file** (the user just describes a feature): route to `idea-refine`, unless the change is small and fully clear; then confirm and add it, noting "no idea file" in the Changelog row.

The idea file is the main input. Its sections map onto the spec like this:

| Idea file section | Used for |
|---|---|
| How it fits → Serves | `Serves:` line of each new feature |
| How it fits → Stage | `Stage:` line of each new feature: the stage the idea added, or the one it joins |
| How it fits → Touches | Which existing requirements to check, change, or extend |
| Recommended direction | Feature Behavior and the requirements |
| Not doing | Out of scope |
| What success looks like | Quality requirements, where measurable |
| Open questions | Questions to ask in Step 3 — resolve them, or carry them into the spec's Open questions |

## Steps

Run these for the idea only:

1. **Check for conflicts first.** Start with the IDs under *Touches*, then search the rest of the spec for anything else the idea contradicts. List conflicts for the user before writing — "Shared editing changes **EDIT-03** (only the owner can edit). Proposed: owner *or invited editors* can edit."
2. **Map the idea to features** and show the goal → feature mapping, with each feature's stage, before writing.
3. **Surface assumptions, then clarify** (SKILL.md's Asking section).
4. **Write the change** following `references/spec.md` and the rules below.
5. **Set the spec Status back to Draft** and run the Review Gate (SKILL.md, plus the gate steps below), highlighting the changed IDs so the user reviews only what's new.

## Writing rules

1. **Keep IDs stable, keep the text current.** IDs are never renumbered or reused. Old text does not stay in the spec once it stops being true; git keeps it.
   - New feature → new `### Feature (CODE)` section with a new code and IDs starting at `-01`.
   - New behavior in an existing feature → next unused number in that feature (if `SAVE-04` is the highest, add `SAVE-05`, even if `SAVE-02` was removed). `dt status` reports it under `prefixes`.
   - **Widen, don't bolt on.** If an existing requirement already covers this concern for an earlier part of the project, rewrite it to cover the new part too, instead of adding a near-duplicate.    - Changed requirement → rewrite it in place and keep its ID. Put no marker on it.    - Removed requirement → collapse it to one struck line and delete its criteria and edge cases: `- **CODE-03** ~~[short name]~~ *Removed YYYY-MM-DD: [reason, or "replaced by CODE-07"].*` Never delete the ID line; the ID stays retired.
2. **Link back to the idea.** Add `**Source:** [ideas/<slug>.md](ideas/<slug>.md)` under the `Stage:` line of each new feature section, so readers can find the full why.
3. **Update everything it touches, and consolidate.** Summary (rewritten for the whole spec, not appended to), Users, Serves lines. Scope stays one deduplicated list per side: merge new out-of-scope items into it, and drop or narrow anything the new features bring into scope (the gate's *Out of scope* step). Remove assumptions and open questions that are answered or no longer apply.
4. **Add one Changelog row**, one line: the idea file as the source, a short description of the change, and the IDs as ranges in up to three `;`-separated groups: added, then changed, then removed (`FIELD-01–FIELD-12; CNN-03, CORE-04 (changed); CROP-04 (removed)`). A `(changed)` or `(removed)` mark covers every ID in its group.

## Gate steps

Run the hygiene check on the whole spec, not just the new section, and add:

- **Out of scope.** Read every out-of-scope line against the features this round added. Drop a line the new features bring into scope. Narrow a line that is now only partly true to the part still excluded, and name the stage it applies to. Once a neural-network stage exists, "deep learning" is no longer out of scope. Once a reserve-planning stage uses demand forecasts, "no demand forecasts — the reserve stage is an equal split" becomes "the equal-split reserves use no demand forecasts". Then merge duplicates.
- **Leftovers.** The Summary describes the whole spec as it now stands. No requirement is still worded for one stage when it now covers several. Removed requirements are one line each. No `(changed …)` marker or other change note appears above the Changelog.

## On approval: close and freeze the idea

1. Set its Status to `Specced` and add two lines under the header: `**Spec:** CODE-01–CODE-04, EDIT-03 (changed)` and the banner `> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)`.

3. Delete wording that only served the review: notes to the user ("my proposed limit, for you to check") and instructions to this skill ("this line must be removed from the spec").

# Idea: Residual-return features

**Status:** Accepted · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)

## In one sentence
This adds candidate price and volume features, and a machine-learning study of whether they predict next month's market-removed returns of S&P 500 members, so that every claim that a feature carries information has passed a null-hypothesis test.

## The problem
Once Stage 2 removes the market, what is left of each stock's return is mostly noise. Many features look predictive in-sample and fail out of sample, through look-ahead, through trying many features and keeping the lucky ones, or by quietly repackaging momentum or beta. I want to know which features really carry information about residual returns on my own point-in-time data, and I don't want to believe one that hasn't beaten chance.

## Who it's for
Me, with Stage 1's as-of members and total returns and Stage 2's market removal, before any strategy is built on a signal.

## How it fits
- **Serves:** Goal 1 (as-of members and returns; nothing after each rebalance date is used); Goal 3 (its report opens in the app)
- **Touches:** STRUC-04, PORT-08 (removing the components above the noise edge gives the residuals); PORT-02 (month-end rebalance dates); PORT-03 (eligible members); PORT-04, STRUC-05 (no look-ahead); DATA-01 (OHLCV); PORT-01, VIEW-08 (the report pattern); Out of scope (return signals and prediction models). Builds on [return-structure-portfolios.md](return-structure-portfolios.md), which is not edited.
- **Brief changes:** Constraints (three stages decided); Not doing narrowed to strategy backtests
- **Stage:** New S3 (roadmap stage on acceptance)

## Recommended direction
One command runs the study and writes a report that the app opens, like the Stage 2 study.

**Target.** At each Stage 2 month-end rebalance date, each eligible member's residual return over the following month: its return with the components above the noise edge removed, those components being fitted only on the 252 days ending that date.

**Features.** Candidate features built only from prices and volume through the rebalance date: momentum, short-term reversal, volatility, beta, liquidity, extreme-return measures and similar. Each is also residualized against the market, so the study doesn't rediscover beta.

**Tests, in order.**
1. *Baseline, no ML:* each feature's monthly rank correlation with the next month's residual return. The null is that the feature carries no information, and its distribution comes from shuffling the feature within each month. The p-values are corrected across all features (Holm).
2. *Combined model against a null:* ridge regression as the linear baseline, then gradient boosting, both trained walk-forward. Each model's out-of-sample score is compared with the same model retrained on labels shuffled within each month.
3. *Each feature inside the model:* drop the feature, or shuffle it within each month, and test whether the out-of-sample score falls by more than chance.

**Controls are required.** A positive control (short-term reversal, or a planted signal) must be found, and pure-noise features must be rejected at about the nominal rate, about 5%. If either control fails, the report says that the test can't be trusted.

**Holdout.** Model selection is walk-forward on the earlier years. The final ~5 years are locked until every feature, model and setting is frozen, then scored once. The report records when that happened.

The report gives one verdict per feature (out-of-sample gain, corrected p-value, survives or not) and the combined models against the baseline. "Nothing survives" is a valid result.

## Data
Stage 1's store: as-of S&P 500 members with daily OHLCV and total returns from 1998, delisted names included. That is about 330 rebalance months × about 500 members, roughly 165,000 stock-months. No outside data. The residuals come from Stage 2's market removal (RF-01 is prior art, refitted per window). The work is built and tested on synthetic data with planted and absent signals, and the real analysis runs on the Stage 1 sources. Feature profiling (coverage, distributions, correlation between features) uses the `data-analysis` skill. Every feature claim and the model-versus-null comparisons use the `null-hypothesis-testing` skill. Baselines: per-feature rank correlation and ridge regression. Requested models: linear baseline (rank correlation plus ridge), then gradient boosting, walk-forward.

## Alternatives considered
- Predicting residual volatility — a stronger signal, but a different question.
- Explaining residual co-movement — that is structure, already in Stage 2.
- Adding fundamentals or sectors — brings its own as-of problems; kept out.
- A long-short backtest as the measure — mixes information with costs and portfolio construction.
- Walk-forward with no locked holdout — leaves room for selection on the test years.

## What success looks like
- One report gives every candidate feature a verdict with its out-of-sample gain and corrected p-value.
- Ridge and gradient boosting are each compared with the per-feature baseline and their shuffled-label nulls.
- The positive control is found and noise features are rejected at about 5%.
- The holdout is scored once, after everything is frozen.
- No feature, target or model fitted for month R uses data from after R.

## What we're betting on
- About 165,000 stock-months is enough to detect a rank correlation of a few hundredths.
- Residuals from components fitted per window are stable enough to be a meaningful target.
- At least one known effect still shows up in large US stocks since 1998, so a positive control exists in real data.

## Not doing
- Backtests, long-short portfolios or transaction costs — information first.
- Fundamentals, sectors or any data beyond the store's OHLCV.
- Feeding predictions into Stage 2's portfolios as expected returns.
- Deep learning, or hyperparameter searches that touch the holdout.

## Open questions
- Exact target: residual returns summed or compounded over the month, and which window's components are used.
- The candidate feature list and its lookbacks.
- Holdout start date, the family that multiple-testing correction covers, and α.
- The score for "information" in the models (rank correlation of predictions, or out-of-sample R²).
- If short-term reversal is absent in real large-cap data, is a planted synthetic signal enough as the positive control?
- Whether the real analysis waits on PB-01, as Stage 2's does.

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Every feature names one stage.** Its `**Stage:**` line holds only the ID of the roadmap stage that first builds it. `dt lint` fails a feature with no stage, or one naming no stage row.
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full"). Cost, licence and budget limits are `QR-` items ("data costs ≤ $50 a month"), never `DATA-` or feature requirements.
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads it in `docs/requests.md`.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the field-photo idea", "UR-03") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git; which requirement honours which request goes in `docs/requests.md` (`dt request trace`).
- **The user's words win over the brief's.** Where a `spec` request is more specific than the brief or idea file ("circular tank", "one predator"), the requirement says what the request says, or the user approves the change.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("hourly readings for every meter in the service area, including decommissioned ones, since 2015"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, selection bias, and coverage gaps are requirements, not hopes: "Given a forecast issued at time T, when the model requests weather, then no value published after T is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The hand-written CNN reaches ≥ 90% of the accuracy of an established reference implementation on the same dataset." "The logistic regression is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

   - α = 5% throughout. Holm correction is applied separately to each family:
     - test 1: all candidate features
     - test 2: the 2 models
     - test 3: all features within each model
4. **Score.** "Information" means the mean monthly rank correlation between predictions and the residual target, with out-of-sample R² reported next to it.
   - The baseline the models must beat is the single feature with the best training rank correlation, sign included, chosen again at each refit.
   - The test of each model against shuffled labels and against the baseline is run with the `null-hypothesis-testing` skill.
5. **Controls.**
   - **Positive control (required in every run):** a planted feature with a true rank correlation of 0.03 must survive test 1.
   - **Negative control:** 100 pure-noise features must be rejected at 1–10% before correction.
   - **Real data:** whether short-term reversal is found is reported, but its absence doesn't make the report untrustworthy.
   - If either required control fails, the report says the tests can't be trusted.
