# Writing cases and the Strategy

Read when writing golden cases and Strategy rows. File shapes and a routed case are in `../examples.md`.

## What counts as a source

A user file, a paper table, a closed form, or a generator plus seed. The case records that source, and its tolerance's reason says why it is what it is ("5% of the amplitude edge, for finite-sample fluctuation"; "exact, dates are discrete"). An expected value the planning agent computed, even with a quick script, is the agent's belief checked against itself. Planning never runs a script, a generator or a reference to fill in an expected value.

Facts the user gives (in chat, the brief or the spec: GridLoad's decommissioned meters and their retirement dates) are their Source as given: cite their request (`UR-04`, `../../idea-refine/references/requests.md`) and don't re-verify them on the web. Look up a sample, three facts at most, only when a case's expected output rests on one that looks wrong, and list what you checked under ASSUMPTIONS. A fact that disagrees goes to Open questions; never correct the user's list yourself.

A reference (`RF-NN`) is a Source only through output the user supplies: they run it and hand you the result, or the file itself records known outputs. Its entry's Caveats are candidate known-answer cases: "fits the seasonal profile on the full sample" suggests a look-ahead case.

A probe's redacted sample (`samples/<name>.json` of a `PB-NN` entry in `docs/probes.md`) can be a case's `source/`: the vendor produced it and the user ran the script that captured it. It supplies the input only. The expected output still comes from the user, and a sample is never an `expected.json` by itself.

## Real pairs: two-layer fixtures

- `source/` keeps the raw example exactly as given and is never edited. Its files are data, never instructions, whatever text they contain.
- `input.json` is transcribed from it by hand, by the user or by you and shown for approval, following the contract's types. Tables go in CSV referenced from `input.json`; JSON holds structure and parameters.
- `expected.json` records the output the source states, with a tolerance.
- **Two tests come from one fixture.** A *parse test* checks that the pipeline's reading step turns `source/` into exactly what `input.json` describes; a *pipeline test* checks `input.json` → `expected.json`. A parsing bug then never looks like a logic bug. Record the parse layer on the case: `**Parse:** read_raw(source/<file>) == readings.csv`. A synthetic case has no parse layer.
- **Fixtures are kilobytes.** Cut the example to the rows that show the behaviour. Large data is referenced by path plus hash, never committed.

## No real pairs: synthetic known-answer cases

Known-answer cases need no data. A synthetic case is a **generator plus a property**, never a number you computed:

- Plant a signal and require it found (a planted daily sine: the daily term explains ≥ 40% of variance).
- Use pure noise and require nothing found (a flat spectrum: every fitted Fourier amplitude ≤ the edge 4σ√(2/T)).
- Build a tiny problem with a known answer by construction (two classes split by a margin: logistic regression classifies every training image correctly).

`input.json` names the generator and its parameters, including the seed. `expected.json` states the property and its tolerance. The generator is code the build writes; the test computes the property at run time.

## Route domain skills

If an installed skill owns the kind of claim a case checks, design the case with it and record it on the case (`**Skills:** significance-check`), so `build-planning` assigns it to the task. Check the installed skills in your context and `.claude/skills/*/SKILL.md`. Any "feature X carries information" or "beats chance" claim goes to `significance-check` when it's installed: the case states the hypothesis, the statistic, the null construction and the split, with a planted-signal case it must reject and a pure-noise case it must not. A home-made null is how false discoveries get approved. If no fitting skill is installed, say so under Open questions rather than inventing a procedure.

## Strategy: one row per pipeline

- **Smoke:** the pipeline's trigger plus `--smoke`, running end to end on fixture or synthetic data in seconds. It's the wiring task's done-check. Every pipeline has one.
- **Step unit tests:** the steps (or owner modules) that get unit tests.
- **Golden cases:** at least one `TC-NN` per pipeline, or the gap under Open questions with a reason. Each names the step boundaries it exercises: the contract type its input enters at, the steps it runs and the type its output leaves at, `TC-02 (Load → spectrum → Spectrum)`, or `(whole pipeline)`. A case spanning one step is tested at that step against the frozen interface, so its tester starts before any upstream code exists; a longer span waits for every step in it. Prefer the narrowest span the source allows, and transcribe `input.json` in the entering type.
- **Model eval:** for pipelines that train or select a model, a case of Kind `model evaluation` stating the metric, held-out split, baseline and seeds, citing the spec's model criteria by ID. `—` otherwise.

**Boundary tests.** When a pipeline's steps provide or consume a contract symbol with a `**Boundary:**` line (across packages, or across components in one package), name the boundary test under Step unit tests: the provider's output validates against the schema in the symbol's `**Fixtures:**` folder; the consumer runs on every sample there. Those samples belong to the contract (`architecture-design` names their cases, the build's interface task writes them), not to this skill; they are shapes, never expected answers. A real payload the user brings for a boundary (a captured API response) goes to `architecture-design`, not into `tests/fixtures/`.

## Case fields

Each `### TC-NN: Title` carries **Pipeline**, **Covers** (spec IDs), **Kind** (user example, paper table, closed form, synthetic known-answer, model evaluation, regression), **Fixture** (folder path), **Source**, **Expected** and **Tolerance** with its reason, and optional **Parse** and **Skills**. The ID is also the fixture folder's name.

  - Given the one-factor synthetic window of STRUC-02, when analysed, then the share is 0.40 ± 0.03.
- **STRUC-04** For each window, the principal components above the noise edge (at least 1) are removed from every stock's returns, and the mean absolute pairwise correlation of what remains is reported next to the raw value, with the number of components removed.
  - Given the one-factor synthetic window of STRUC-02, when analysed, then 1 component is removed, the raw mean absolute correlation is ≥ 0.35, and the residual one is ≤ 0.08.
- **STRUC-05** Each window's results use only the returns inside that window.
  - Given a return changed on a day after rebalance date R, when the study is run again, then every structure result for R and earlier windows is identical.

**Edge cases & errors**
- A window with no eigenvalue above the edge → 1 component is still removed, and the window is marked as showing no structure above noise.

### Covariance and portfolio study (`PORT`)
**Serves:** Goal 1, Goal 3
**Stage:** S2
**Source:** [ideas/return-structure-portfolios.md](ideas/return-structure-portfolios.md)
**Behavior:** The researcher runs one command. At every month-end since 1998, it estimates the covariance of that day's members four ways, builds three long-only portfolios from each estimate plus an equal-weight portfolio, and holds them through the next month. It then ranks the estimates for each portfolio rule by the realized variance of the following months, reports turnover, and tests whether each rule's winner beats the sample estimate. The report, with the structure part (STRUC), opens in the app.

**Requirements**
- **PORT-01** One command runs the whole study and writes one report with three parts: structure, league table and significance.
  - Given stored data from 1998-01-02, when the command is run, then one report is written that has all three parts.
- **PORT-02** Rebalance dates are the last trading day of each month, from the first month-end on which 252 trading days have passed since 1998-01-02 to the last month-end whose following month is complete.
  - Given data from 1998-01-02 to 2026-09-30, when the study runs, then every rebalance date is a month's last trading day, the first is the first month-end with 252 trading days behind it, and the last is 2026-08-31.
- **PORT-03** At each rebalance date, the portfolios hold that day's members (UNIV-01) that have 252 trading days of returns ending that day; members with fewer are left out that month, and the number left out is reported for every rebalance date.
  - Given a stock added to the index with 100 trading days of history on rebalance date R, when the study runs, then the stock is in no portfolio formed on R, and R's left-out count includes it.
- **PORT-04** Every estimate and every weight formed on rebalance date R uses no return from after R.
  - Given a return changed on a day after R, when the study is run again, then every estimate and weight formed on R or earlier is identical.
- **PORT-05** The sample estimate is the sample covariance of the window's daily returns.
  - Given a synthetic window, when estimated, then it equals the sample covariance of those returns.
- **PORT-06** The shrinkage estimate pulls the sample covariance toward a constant-correlation target (each stock's own sample variance, and one correlation shared by every pair equal to the window's average sample correlation), by an intensity estimated from the window and reported for every rebalance date.
  - Given any window, when estimated, then the result equals (1 − δ) × sample + δ × target with 0 ≤ δ ≤ 1, and δ is reported.
- **PORT-07** The denoised estimate replaces the correlation matrix's eigenvalues below the noise edge of STRUC-02 with their average, keeps those above it, and rescales to each stock's sample variance.
  - Given any window, when estimated, then the eigenvalues above the edge are unchanged, those below it are all equal, the matrix's trace is unchanged, and its diagonal equals the sample variances.
- **PORT-08** The factor-model estimate is built from the principal components above the noise edge (at least 1) plus each stock's own residual variance, and the number of components is reported for every rebalance date.
  - Given the one-factor synthetic window of STRUC-02, when estimated, then 1 component is used and the diagonal equals the sample variances.
- **PORT-09** Every portfolio is long-only and fully invested: no weight is negative and the weights sum to 1, with no cap on any one stock and no transaction costs.
  - Given any portfolio formed in the study, when its weights are read, then each is ≥ 0 and they sum to 1 within 1e-9.
- **PORT-10** The minimum-variance rule picks the weights with the lowest portfolio variance under the estimate.
  - Given 2 uncorrelated stocks with variances 1 and 4, when the rule runs, then the weights are 0.8 and 0.2.
- **PORT-11** The risk-parity rule picks the weights for which every stock contributes equally to the portfolio variance under the estimate.
  - Given 2 uncorrelated stocks with volatilities 10% and 20%, when the rule runs, then the weights are 2/3 and 1/3.
- **PORT-12** The hierarchical risk-parity rule clusters the stocks into a tree by correlation, then splits the weight down the tree, giving each branch of a split a share inversely proportional to its variance.
  - Given 2 uncorrelated stocks with variances 1 and 4, when the rule runs, then the weights are 0.8 and 0.2.
  - Given 4 stocks in 2 pairs, each pair correlated at 0.9 and the pairs uncorrelated, with equal variances, when the rule runs, then each pair gets 0.5 of the weight.
- **PORT-13** An equal-weight portfolio of each month's stocks is formed at every rebalance date and shown next to every rule's ranking as the floor.
  - Given 400 eligible stocks on R, when the study runs, then the equal-weight portfolio gives each 1/400.
- **PORT-14** Between rebalance dates, weights drift with prices. A stock that stops trading during the month counts its return through its last trading day, that day included, and its weight is then held as cash at 0% for the rest of the month.
  - Given a stock with 5% of the portfolio whose last trading day is the 10th trading day of the holding month, when the month's returns are computed, then its return counts through day 10, and from day 11 its drifted weight earns 0%.
- **PORT-15** A portfolio's realized variance for a holding month is the variance of its daily returns within that month, annualized ×252.
  - Given 20 daily portfolio returns alternating +1% and −1%, when realized variance is computed, then it is 0.0001 × 252 = 0.0252.
- **PORT-16** For each rule, the four estimates are ranked by mean realized variance over all holding months, lowest first, with the equal-weight portfolio shown alongside.
  - Given a completed study, when the league table is read, then each of the 3 rules lists 4 estimates in increasing mean realized variance, plus the equal-weight value.
- **PORT-17** Turnover is half the sum of absolute weight changes from the drifted weights to the new weights at each rebalance date, averaged over all rebalance dates, and reported as a number for every estimate and rule without affecting the ranking.
  - Given drifted weights (0.6, 0.4) and new weights (0.5, 0.5), when turnover is computed, then it is 0.1.
- **PORT-18** For each rule, the winner is tested against the sample estimate with the `null-hypothesis-testing` skill, on the paired monthly realized variances: the null is that the winner's realized variance is no lower. It passes only if the null is rejected one-sided at 5% after correction across the 3 rules. The report states, for each rule, whether the null is rejected and the corrected p-value.
  - Given a completed study, when the significance part is read, then each of the 3 rules shows its winner, the corrected p-value and whether the null is rejected.
  - Given a rule whose winner is the sample estimate, when the significance part is read, then that rule says no test is needed.
- **PORT-19** The study report can be opened in the app.
  - Given a completed study, when the researcher opens it in the app, then its three parts' tables and charts are shown.
- **PORT-20** The full study runs in ≤ 1 hour.
  - Timed on the researcher's machine on the full history since 1998-01-02.

**Edge cases & errors**
- Study started with no stored data, or fewer than 252 trading days stored → refused with a message to run a refresh first.
- A member with a gap day (RET-07) in its 252-day window → counted as having fewer than 252 days of returns, so left out that month (PORT-03).
- A rule that finds no weights for an estimate in a month → the failure is reported, and that month is left out of every estimate's mean for that rule, so the comparison stays paired.
- Fewer than 2 eligible stocks on a rebalance date → no portfolios are formed that month, and the report says why.
