# The user's words: `docs/requests.md`

Every planning skill follows this. The brief and the spec compress, and the next skill often runs in a fresh session that sees only the docs. `docs/requests.md` keeps what the user actually said, word for word, so the skill whose doc must honour it can. `dt request` writes every line; never edit the file by hand.

## What goes in

One request (`UR-NN`) per concrete statement you could check a doc against:

- facts about the domain, the data or the world ("the tank is circular"), numbers, limits, deadlines, budgets
- tools, libraries, vendors, protocols and data sources the user names ("stream prices over a WebSocket", "use yahooquery")
- choices: an option picked from yours ("Go with A"), and the answer to any question a skill asked
- a block acceptance ("assumptions 1–7 are fine"): one request, its `--about` listing what was accepted
- scope: what must be in, or left out

Not: approval of a whole doc ("approved", "looks good"), wishes with nothing to check ("make it nice"), your own proposals the user hasn't picked, or words already recorded (`dt request` lists them).

## Recording

As you hear it, before you write any doc:

```
dt request add <owner> "<their words>" --skill <this skill> [--about "<what it answers>"] [--replaces UR-NN]
```

- **Verbatim.** Quote the shortest span of their message that carries the fact. Never paraphrase, translate, correct or merge. A message stating three facts is three requests.
- **`--about`** whenever the words don't stand alone: "Go with A" → `--about "AD-22 price source: A = Sharadar, B = yfinance"`; "yes, 3" → what was asked. A bare letter means nothing to the next session, and the same words can pick opposite options in two rounds.
- **Owner** is the doc that must honour it: `brief` (who the user is, their time, budget or experience: context no later doc carries), `spec` (behaviour, numbers, scope the user can observe), `architecture` (tools, libraries, vendors, protocols, data sources, an option for a decision), `pipelines`, `tests`, `plan`, or `constraints` (the quality bar, tooling rules).
- **The user changes their mind:** record the new words with `--replaces` the old UR. A line is never edited or deleted.
- The request that started the run is the user's first message: record it too.

## Honouring

Before you write your doc, read `docs/requests.md` whole; `requests_open` in `dt status` lists the open requests your doc owns. For each:

- **Honour it:** write the requirement, decision, step, case or rule that does what the words say, then `dt request trace UR-NN <ID>…` with the IDs that do it (spec: requirement IDs; architecture: `AD-NN` or a contract ID; the others: their IDs). Honoured by a section with no ID (Out of scope, Assumptions, Constraints): trace its heading, `§Out of scope`.
- **Does what the words say** means the same shape, count, number, tool and goal, and for a named method or concept its mechanism, not its name: "self-play" is training against the opponent's past versions, not two learners at once. A number the words state must appear in the traced text (`request-number` warns).
- **Or change it, with the user's yes:** when it conflicts with another request or can't be met, say so at your gate with your alternative. Only after the user agrees, write the change into every ID it touches, the ones that honoured the old words included (a test case restating the old value too), then `dt request change UR-NN "<what instead>" --approved "<their words>" --skill <this skill> --into <those IDs>`. A doc that cites the request from another ID gets `request-cite`: bring it in line and add it with `dt request change UR-NN --into <ID>`. Never override a request silently, and never record an approval the user didn't give. Headless: leave it open under Open questions and the doc Draft.
- **A value from the user's words** (a golden case's expected output, a limit) cites the request as its Source: `**Source:** UR-04`. A number worked out from their words is not theirs; its Source says how it was derived (`request-source` warns).
- A request another doc owns waits for that doc's skill. Don't copy it into yours (the spec names no tools, even when a request does).

## At the gate

Before asking for approval, `dt request --open --owner <yours>` is empty, except requests whose change you are asking the user about. The summary lists them in one line:

> **Your words:** "circular tank" UR-01 → TANK-02 "the tank is a circle"; "use yahooquery" UR-03 → AD-04 "yahooquery"; change proposed: UR-05 one predator → two (yes?); open: none.

Quote the words and the traced text side by side, so the user sees whether one does the other.

Once the spec or architecture is Approved, `dt lint` fails it for every open request it owns, and `dt next` sends the run back to its skill.

# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. Neither a long contract (`dt context` loads only the sections a task reads) nor a dependency direction (import-linter enforces it between components of one package) is a reason to split. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, torchvision).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.

Personal stock research usually fools itself: price histories quietly leave out companies that failed, models peek at future data, and results that beat nothing in particular pass as discoveries. A one-person researcher has no team to catch these mistakes, so the setup itself has to catch them.

One independent researcher studying the daily behaviour of US stocks, for learning and paper trading only.

- One person, on a laptop, with an occasional rented graphics card for training neural networks.

- Every feature claim has a recorded test, corrected for how many features were tried.

- The subscription's history includes delisted stocks and enough corporate actions to rebuild the stock universe as of each date.

25	### Dataset build (`BUILD`)
26	**Serves:** Goal 1
27	**Stage:** S1
28	**Behavior:** The researcher runs one command to download the daily prices, corporate actions and company listings from the subscription, clean them, validate them and store them locally. A later run fetches only what is new. Each run ends with a validation report; data that fails validation is never silently stored as good.
29	
30	**Requirements**
31	- **BUILD-01** A full build downloads daily prices, corporate actions and company listings for every US common stock in the subscription, including delisted ones, and stores them locally.
32	  - Given an empty local store, when the researcher runs a full build, then afterwards the store holds prices, corporate actions and listings for every common stock the subscription lists, active and delisted.
33	- **BUILD-02** An incremental build adds only trading days and corrections published since the last build.
34	  - Given a store built through date D, when the researcher runs an update after new data is published, then only data after D (and vendor corrections to earlier rows) is downloaded, and the earlier stored rows are unchanged except where corrected.
35	  - Given a vendor correction to an earlier row, when it is stored, then the earlier value is kept with the date it was replaced, so an as-of-D load still returns what was known on D.
36	- **BUILD-03** Cleaning resolves duplicate rows, non-positive prices and missing trading days before storage.
37	  - Given a raw batch with a duplicated (stock, date) row, when it is cleaned, then exactly one row is stored and the duplicate is listed in the run report.
38	  - Given a price ≤ 0 or a missing trading day inside a stock's listed life, when it is cleaned, then the row is flagged (not filled with a zero return) and listed in the run report.
39	- **BUILD-04** Every build ends with a validation report that passes or fails.
40	  - Given a completed build, when the report is produced, then it states counts of stocks, stock-days, delisted stocks and flagged rows, and the result of every check in `XCHK` and `UNIV`.
41	  - Given any check that fails, when the build finishes, then the run is marked failed and the loader refuses to treat it as the current dataset until the researcher accepts it.
42	- **BUILD-05** An interrupted build can be resumed without starting over.
43	  - Given a build stopped part-way (network loss, laptop sleep), when the researcher reruns it, then it continues from the last completed batch and the final store equals one built without interruption.
44	
45	**Edge cases & errors**
46	- Subscription rejects the credentials or the quota is hit → the run stops with that reason, stores nothing partial as current, and can be resumed later.
47	- A ticker is reused by a different company after a delisting → the two are stored as distinct stocks, never merged.
48	- A stock changes ticker → its history stays one stock under its permanent identity.

50	### Point-in-time universe (`UNIV`)
51	**Serves:** Goal 1
52	**Stage:** S1
53	**Behavior:** For every trading date the platform knows which stocks were in the research universe that day, using only what was knowable the day before: about 1,000 of the most-traded US common stocks, delisted names included.
54	
55	**Requirements**
56	- **UNIV-01** For each trading date, the universe is the 1,000 US common stocks with the highest trailing dollar volume, measured over the previous 63 trading days.
57	  - Given trading date D, when the universe for D is requested, then it holds the 1,000 common stocks with the highest median daily dollar volume (price × shares traded) over the 63 trading days ending the day before D.
58	  - Given a stock with fewer than 63 trading days of history before D, when the universe for D is built, then it is ranked only once it has at least 63 days.
59	- **UNIV-02** Universe membership on date D uses no data from D or later.
60	  - Given the universe for D, when any price, volume or listing published on or after D is changed, then the universe for D is unchanged.
61	- **UNIV-03** Stocks that later delist stay in the universe on every date they qualified.
62	  - Given a stock that qualified on D and delisted after D, when the universe for D is requested, then the stock is in it, and its final return through delisting is part of the data.
63	- **UNIV-04** If the data budget (or the data itself) can't support the dollar-volume universe, the universe falls back to S&P 500 membership as it was on each date.
64	  - Given the decision (made when the data source is checked) that the budget or data limits the dollar-volume universe, when the universe for D is requested, then it holds the stocks that were S&P 500 members on D, including those later removed or delisted.
65	- **UNIV-05** Only common stocks are eligible.
66	  - Given a listing that is an ETF, ADR, preferred share, warrant, unit or fund, when the universe is built, then it is never included.
67	
68	**Edge cases & errors**
69	- Fewer than 1,000 eligible stocks on an early date → the universe holds all eligible stocks, and the report states the count for that date.
70	- Ties at rank 1,000 → broken by the permanent stock identity so the result is reproducible.

72	### Second-source cross-check (`XCHK`)
73	**Serves:** Goal 1
74	**Stage:** S1
75	**Behavior:** Every build compares the stored prices against a second, independent price source and explains every disagreement that matters.
76	
77	**Requirements**
78	- **XCHK-01** Daily total returns are compared with a second independent source for every universe stock it covers.
79	  - Given a completed build, when the cross-check runs, then for each universe stock-day both sources cover, the two daily total returns (dividends and splits included) are compared, and the report states the share of stock-days within 0.5% of each other.
80	  - Given the share within 0.5% is below 99%, when the build finishes, then the cross-check fails.
81	- **XCHK-02** Every stock-day disagreeing by more than 2% is listed with a reason.
82	  - Given a stock-day whose returns differ by more than 2%, when the report is produced, then it appears with one reason: split, dividend, missing in one source, stale price, or unexplained.
83	- **XCHK-03** Corporate actions are checked against the second source.
84	  - Given a split or dividend in the stored data, when the cross-check runs, then the report states whether the second source shows the same action within 1 trading day, and lists each mismatch.
85	- **XCHK-04** Coverage gaps in the second source are reported, not treated as errors.
86	  - Given a stock the second source doesn't cover (often a delisted one), when the cross-check runs, then it is counted as "not covered", and the report states the share of universe stock-days covered.
87	
88	**Edge cases & errors**
89	- Second source unreachable → the cross-check is marked "not run" (not passed), and the build can still be accepted manually with that noted.

91	### Research loader (`LOAD`)
92	**Serves:** Goal 1
93	**Stage:** S1
94	**Behavior:** Every later stage gets its data through one loader: for a date range and an as-of date, it returns prices, total returns, corporate actions and the point-in-time universe exactly as they were knowable.
95	
96	**Requirements**
97	- **LOAD-01** The loader returns daily adjusted prices and total returns for a date range.
98	  - Given a date range, when the researcher loads prices, then each stock-day carries the close, the split-adjusted close and the total return including dividends.
99	- **LOAD-02** The loader returns corporate actions for a date range.
100	  - Given a date range, when the researcher loads corporate actions, then every split, dividend, ticker change and delisting in that range is returned with its effective date.
101	- **LOAD-03** A load can be restricted to the point-in-time universe.
102	  - Given a date range, when the researcher loads universe returns, then each date holds only the stocks in that date's universe, and stocks that later delisted are present on their qualifying dates.
103	- **LOAD-04** A load as of date A returns only what was known on A.
104	  - Given as-of date A, when anything is loaded, then no row, correction or adjustment published after A is returned.
105	- **LOAD-05** Missing data stays missing.
106	  - Given a stock-day with no trade, when it is loaded, then its return is marked missing, never filled with zero.
107	- **LOAD-06** The loader only serves accepted builds.
108	  - Given the latest build failed validation and wasn't accepted, when the researcher loads, then the last accepted build is served and a warning names the failed one.
109	
110	**Edge cases & errors**
111	- A date range before the data starts or after the latest build → the loader returns what exists and states the actual range covered.

149	### Market-factor removal (`FACT`)
150	**Serves:** Goal 3
151	**Stage:** S2
152	**Behavior:** Within each estimation window, the dominant factors of the returns (the market first) are found by principal component analysis and removed, leaving residual returns that later stages study.
153	
154	**Requirements**
155	- **FACT-01** Factor removal fits principal components of the window's universe returns and subtracts each stock's exposure to the top k components.
156	  - Given an estimation window and k, when factors are removed, then the residual returns for that window are the returns minus each stock's fitted exposure to the top k principal components of that window's returns.
157	- **FACT-02** Factor removal uses only data inside the estimation window.
158	  - Given a window ending on date E, when any return after E is changed, then the factors, exposures and residuals up to E are unchanged.
159	  - Given residuals for a later out-of-sample day, when they are produced, then they use the components and exposures fitted on the window before that day.
160	- **FACT-03** The number of components removed is chosen by a rule fixed before the run.
161	  - Given a run, when it starts, then k is either a fixed number or chosen per window by a stated rule (such as the count of eigenvalues above the random-matrix bound in `DENO`), and the choice is recorded with the run.
162	- **FACT-04** Removal reduces cross-stock correlation, and this is checked.
163	  - Given a window's raw and residual returns, when the check runs, then the mean absolute pairwise correlation of the residuals is lower than that of the raw returns, and both values are recorded.
164	
165	**Edge cases & errors**
166	- A stock with fewer than 80% of the window's days observed → excluded from that window's fit (not filled with zeros), and the exclusion is listed.
167	- k ≥ the number of stocks in the window → the run stops with that reason.

169	### Correlation denoising (`DENO`)
170	**Serves:** Goal 3
171	**Stage:** S2
172	**Behavior:** The window's correlation matrix is cleaned with random-matrix theory: eigenvalues inside the Marchenko–Pastur noise band for the window's shape are treated as noise and flattened, while those above it are kept.
173	
174	**Requirements**
175	- **DENO-01** Eigenvalues at or below the Marchenko–Pastur upper edge for the window's ratio of stocks to days are replaced by their average, and the ones above are kept.
176	  - Given a correlation matrix from T days and N stocks, when it is denoised, then every eigenvalue ≤ (1 + √(N/T))² (scaled by the fitted noise variance) is replaced by the mean of those eigenvalues, the eigenvalues above it are unchanged, and the result is rescaled to a unit diagonal.
177	- **DENO-02** The denoised matrix is a valid correlation matrix.
178	  - Given any denoised matrix, when it is checked, then it is symmetric, has a unit diagonal and has no negative eigenvalues.
179	- **DENO-03** Denoising recovers known structure on synthetic data.
180	  - Given a synthetic return panel with a known number of factors plus noise, when its correlation is denoised, then the count of kept eigenvalues equals the true factor count, and the denoised matrix is closer to the true correlation than the sample one.
181	- **DENO-04** The noise fit and the count of kept eigenvalues are recorded per window.
182	  - Given a denoising run, when it finishes, then each window's fitted noise variance, upper edge and number of kept eigenvalues are saved.
183	
184	### Covariance comparison (`COV`)
185	**Serves:** Goal 2, Goal 3
186	**Stage:** S2
187	**Behavior:** Three covariance estimators (sample, shrinkage and denoised) are estimated on each rolling window and ranked by the realized variance of the portfolios built from them on the following, unseen period.
188	
189	**Requirements**
190	- **COV-01** Each estimation window produces a sample, a shrinkage and a denoised covariance estimate of the universe returns.
191	  - Given an estimation window, when the estimates are made, then the sample covariance, a covariance shrunk toward a structured target with its intensity chosen from that window's data only, and a covariance rebuilt from the `DENO` correlation with the window's volatilities are all produced.
192	- **COV-02** Estimators are ranked by the out-of-sample realized variance of the portfolios built from them.
193	  - Given the walk-forward schedule of `HARN`, when each estimator's covariance drives each portfolio method of `PORT`, then the realized variance of each portfolio over the following unseen period is recorded, and estimators are ranked per portfolio method by average realized variance.
194	- **COV-03** The comparison of estimators is analysed with the `data-analysis` skill and tested with the `null-hypothesis-testing` skill.
195	  - Given the out-of-sample realized variances, when the comparison is made, then the `data-analysis` skill characterises them (by period and market regime), and the `null-hypothesis-testing` skill tests each estimator against the sample covariance on the paired per-period variances; an estimator counts as better only if the null of no difference is rejected at 5% after correction for the number of comparisons.
196	- **COV-04** Forecast accuracy of the risk estimate is reported alongside.
197	  - Given each portfolio and estimator, when results are recorded, then the predicted variance at rebalancing and the realized variance afterwards are both stored, with their ratio.
198	
199	### Classical portfolios (`PORT`)
200	**Serves:** Goal 2, Goal 3
201	**Stage:** S2
202	**Behavior:** Minimum-variance, risk parity and hierarchical risk parity portfolios are built from each covariance estimate, rebalanced on a fixed schedule, and compared out of sample on realized variance after trading costs, with turnover reported. These are the benchmarks every later stage must beat.
203	
204	**Requirements**
205	- **PORT-01** A minimum-variance portfolio is built from each covariance estimate.
206	  - Given a covariance estimate, when the portfolio is built, then its weights are fully invested, long-only, at most 5% per stock, and minimise predicted variance under those limits.
207	- **PORT-02** A risk parity portfolio is built from each covariance estimate.
208	  - Given a covariance estimate, when the portfolio is built, then each stock's contribution to predicted portfolio variance is equal to within 1%, and weights are fully invested and long-only.
209	- **PORT-03** A hierarchical risk parity portfolio is built from each covariance estimate.
210	  - Given a covariance estimate, when the portfolio is built, then stocks are clustered by correlation distance into a tree, ordered by it, and weights are split down the tree in inverse proportion to each branch's variance, fully invested and long-only.
211	- **PORT-04** Portfolios are compared out of sample on realized variance after costs, with turnover reported.
212	  - Given the walk-forward schedule of `HARN`, when each portfolio is held over its unseen period, then its realized variance, its return after the per-trade cost, and its turnover per rebalance are recorded.
213	- **PORT-05** An equal-weight portfolio of the universe is the simple baseline.
214	  - Given any comparison, when results are reported, then the equal-weight universe portfolio, under the same schedule and cost, is shown alongside.
215	- **PORT-06** The best classical portfolio is named as the benchmark for later stages.
216	  - Given the completed comparison, when it is recorded, then the portfolio (method and estimator) with the lowest out-of-sample realized variance after costs is saved as the stage benchmark, together with all the others.
217	
218	**Edge cases & errors**
219	- The optimiser can't meet the limits on a date → that date keeps the previous weights, and the event is recorded with the run.
220	- A held stock delists mid-period → its final return through delisting is realised and its weight sits in cash until the next rebalance.

222	### Testing harness (`HARN`)
223	**Serves:** Goal 2
224	**Stage:** S2
225	**Behavior:** One shared harness runs every comparison in the project. Before a run, the researcher registers the claim, its baseline, the metric, the test and its threshold; the harness then runs it walk-forward on unseen data, applies costs, and records the result whether it wins or loses.
226	
227	**Requirements**
228	- **HARN-01** Every run is pre-registered before it touches out-of-sample data.
229	  - Given a new comparison, when the researcher starts it, then the claim, the baseline, the metric, the test, the significance level and the final test period must be stated, and are saved and locked before any result is computed.
230	  - Given a registered run, when its settings are changed after results exist, then the harness records it as a new run, never as an edit of the old one.
231	- **HARN-02** Comparisons run walk-forward: estimate on a past window, then hold on the following unseen period.
232	  - Given a strategy, when it is run, then by default it is estimated on the previous 252 trading days and rebalanced every 21 trading days, and each period's result uses only data from before that period.
233	- **HARN-03** Learned models are trained, tuned and tested on separated periods with a gap.
234	  - Given a model whose labels look h trading days ahead, when data is split, then training, validation and test periods are in time order, and at least h trading days are removed between each pair so no label overlaps the next period.
235	- **HARN-04** A final test period is held back for each claim and used once.
236	  - Given a registered claim, when it is run on its final test period, then that run is the claim's verdict, and any later run on the same period is marked as a repeat.
237	- **HARN-05** Every comparison applies one per-trade cost and reports turnover.
238	  - Given any portfolio or agent, when its result is computed, then a cost of 10 basis points of traded value is charged on every trade, the cost is stated with the result, and turnover per rebalance and per year is reported.
239	- **HARN-06** Every claim is tested against chance with the `null-hypothesis-testing` skill.
240	  - Given a completed run, when its verdict is decided, then the `null-hypothesis-testing` skill is given the per-period results of the candidate and the baseline and the registered test; the claim passes only if the null of no improvement is rejected at the registered level, after correction for every candidate tried under that claim.
241	- **HARN-07** Every run's result is recorded, wins and losses alike.
242	  - Given any finished or abandoned run, when it ends, then its registration, results, test verdict and a written conclusion are saved, and a loss is recorded with the same detail as a win.
243	- **HARN-08** Every run can be reproduced.
244	  - Given a recorded run, when it is rerun on the same accepted build with its recorded settings and random seeds, then it gives the same results.
245	
246	**Edge cases & errors**
247	- A run is stopped before finishing → recorded as abandoned, with how far it got.
248	- A run would read data inside its final test period before its verdict run → the harness refuses and says why.

265	### Candidate features (`FEAT`)
266	**Serves:** Goal 2
267	**Stage:** S3
268	**Behavior:** Candidate features are built from the daily data for every universe stock-day, using only what was known by that day's close, so they can be tested against later residual returns.
269	
270	**Requirements**
271	- **FEAT-01** Each candidate feature is computed per universe stock-day from data up to that day's close.
272	  - Given a feature value for stock S on date D, when any data after D is changed, then the value is unchanged.
273	- **FEAT-02** Each feature is registered with a definition before it is tested.
274	  - Given a new feature, when it is added, then its definition, inputs and lookback are recorded, and it counts toward the number of features tried from that moment.
275	- **FEAT-03** Features are standardised across the stocks of each date's universe.
276	  - Given date D, when features are standardised, then each feature has mean 0 and standard deviation 1 across D's universe, using only D's universe members.
277	- **FEAT-04** The initial candidate set covers price, volume and corporate-action information.
278	  - Given the first feature run, when the candidates are listed, then they include at least: past residual returns over several lookbacks, residual volatility, dollar volume and its change, and recent corporate actions.
279	
280	**Edge cases & errors**
281	- A feature can't be computed for a stock-day (not enough history) → it is marked missing, never filled with zero, and the missing share is reported per feature.

283	### Feature tests (`FTEST`)
284	**Serves:** Goal 2
285	**Stage:** S3
286	**Behavior:** Each candidate feature is tested for information gain over future market-removed returns using learned models on real data. Only features that pass a pre-registered test against chance, corrected for how many features were tried, survive to stage S4.
287	
288	**Requirements**
289	- **FTEST-01** The target is the next-period residual return from `FACT`.
290	  - Given date D, when the target is built, then it is each universe stock's residual return over the registered horizon after D, with factors fitted only on data up to D.
291	- **FTEST-02** Information gain is measured as the out-of-sample improvement of a learned model with the feature over the same model without it.
292	  - Given a feature, when it is tested, then a model trained with it and one trained without it are compared on the `HARN` test period using a registered metric (such as the rank correlation of predicted and realised residual returns), and the difference is the feature's gain.
293	- **FTEST-03** Every feature claim is tested with the `null-hypothesis-testing` skill.
294	  - Given a feature's per-date gains on the held-out period, when it is tested, then the `null-hypothesis-testing` skill is given those gains and the count of every feature tried; the feature survives only if the null of zero gain is rejected at 5% after correction for that count.
295	- **FTEST-04** The data behind each test is characterised with the `data-analysis` skill on the real data.
296	  - Given a feature test, when it is run, then the `data-analysis` skill reports the feature's distribution, missing share, stability across years and its correlation with the other candidates, on the real universe data.
297	- **FTEST-05** Every feature's verdict is recorded, failed ones included.
298	  - Given a tested feature, when its verdict is decided, then the feature, its gain, the test result and the correction applied are recorded through `HARN`, and the list of survivors is saved as the stage S3 result.
299	
300	**Edge cases & errors**
301	- No feature survives → stage S3 records a documented negative result, and stage S4 forecasts are built on the baseline inputs only (past returns and volatility).

303	### Neural forecasts (`FCST`)
304	**Serves:** Goal 2
305	**Stage:** S4
306	**Behavior:** Neural networks that read each stock's recent history as a sequence forecast its future return and volatility from the features that survived stage S3, and are compared against simple forecasting baselines.
307	
308	**Requirements**
309	- **FCST-01** Sequence models forecast each stock's forward return over registered horizons.
310	  - Given date D and a stock in D's universe, when a forecast is made, then the model reads the stock's history of the features that survived stage 3 (`FTEST`) over a fixed lookback ending at D and outputs its forward return for each registered horizon (by default 1, 5 and 21 trading days).
311	- **FCST-02** Sequence models forecast each stock's forward realised volatility over the same horizons.
312	  - Given date D, when a volatility forecast is made, then it is the realised volatility of daily returns over the h trading days after D, for each registered horizon.
313	- **FCST-03** Forecast inputs never reach past the forecast date.
314	  - Given a forecast made on D, when any input dated after D is changed, then the forecast is unchanged.
315	- **FCST-04** Return forecasts are compared with simple baselines.
316	  - Given the test period, when return forecasts are scored, then their rank correlation with realised returns is compared with that of a zero forecast and of the stock's own trailing mean; the claim passes only if the `null-hypothesis-testing` skill rejects the null of no improvement over the better baseline at 5% after correction for the number of models and horizons tried.
317	- **FCST-05** Volatility forecasts are compared with simple baselines.
318	  - Given the test period, when volatility forecasts are scored, then their error against realised volatility is compared with that of the trailing 21-day volatility and an exponentially weighted volatility; the claim passes only if the `null-hypothesis-testing` skill rejects the null of no improvement at 5% after correction.
319	- **FCST-06** Delisted stocks' final periods stay in the test.
320	  - Given a stock that delists within a forecast horizon, when its target is computed, then its realised return through delisting is used, not dropped.
321	- **FCST-07** Training can run on a rented graphics card and the results are brought back to the laptop.
322	  - Given a training run, when it runs on rented hardware, then its trained model, settings and seeds are saved so that forecasts and the `HARN` record are produced on the laptop.
323	
324	**Edge cases & errors**
325	- A stock or category not seen in training appears at test time → it is handled as unknown, never causing a failure.
326	- Gaps in a stock's history inside the lookback → the gap is visible to the model as missing, never stitched across.

328	### Forecast-driven portfolios (`FPORT`)
329	**Serves:** Goal 2, Goal 3
330	**Stage:** S4
331	**Behavior:** Portfolios built from the forecasts are compared out of sample, after costs, with the stage S2 benchmark portfolio. Either they beat it, or the loss is documented.
332	
333	**Requirements**
334	- **FPORT-01** Forecast-driven portfolios use the return forecasts with a covariance estimate from stage S2.
