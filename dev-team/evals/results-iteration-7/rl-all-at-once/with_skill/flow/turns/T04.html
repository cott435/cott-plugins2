# New mode: writing the spec from the brief

Read when `dt status` reports `mode: new`: there is no `docs/spec.md`, and the accepted brief is the input.

```
READ BRIEF ─→ SURFACE ASSUMPTIONS ─→ CLARIFY ─→ WRITE SPEC ─→ [user approves] ─→ architecture-design
```

## Step 1: Map goals to features

From the brief's numbered goals, propose features and show the mapping before writing:

```
Goal 1 (regulars reorder in < 30s)     → Saved orders, Text reorder
Goal 2 (no extra daily work for owner) → Regulars setup, Order notifications
```

Every goal has a feature. **Every stage the brief and roadmap list is specced in full**: features, requirements, criteria and edge cases for all of them, never "S1 in full, the rest outlined". Later skills design only what the spec holds.

# The spec: template, writing rules, hygiene check

Read before writing or extending `docs/spec.md`, and again for the hygiene check at the Review Gate.

## Template

```markdown
# [Project Name] — Spec

**Status:** Draft · **Last updated:** YYYY-MM-DD · **Brief:** [brief.md](brief.md)

## Summary
[2-3 sentences: what is being built. Link to the brief for why — don't repeat it.]

## Users
| User | What they need to do |
|---|---|
| [Primary user] | [...] |

## Scope
**In scope:** [features, by name]
**Out of scope:** [what we're not building — include everything on the brief's Not Doing list, plus anything decided during clarification]

## Features

### [Feature name] (`CODE`)
**Serves:** Goal 1, Goal 3
**Source:** [ideas/<slug>.md](ideas/<slug>.md) *(extend mode only — omit for features from the original brief)*
**Behavior:** [2-4 sentences or a short numbered flow describing what the user experiences.]

**Requirements**
- **CODE-01** [One testable statement of what the system does.]
  - Given [context], when [action], then [observable result].
  - Given [...], when [...], then [...].
- **CODE-02** [...]
  - Given [...], when [...], then [...].

**Edge cases & errors**
- [Situation] → [expected behavior]

## Data requirements
*(Data and ML projects only — omit otherwise.)*
- **DATA-01** [What data the system needs: content, coverage, history, frequency, freshness — not which vendor.]
  - Given [...], when [...], then [...].

## Quality requirements
- **QR-01** [Measurable non-functional requirement: speed, reliability, accessibility, privacy, security.]
  - [How it's checked.]

## Assumptions
- [Assumptions the user confirmed]

## Open questions
- [Unresolved items, each with who can answer it. Omit if none.]

## Changelog
| Date | Change | Source | IDs |
|---|---|---|---|
| YYYY-MM-DD | Initial spec | brief.md | all |
```

**Writing rules:**

- **One requirement, one behavior.** If a requirement contains "and", it's probably two.
- **Every requirement has at least one acceptance criterion** in Given/When/Then form. If you can't write one, the requirement isn't clear yet.
- **Describe behavior, not implementation.** "The customer sees their usual order" — not "the app queries the orders table."
- **Use exact numbers.** "≤ 2 seconds", "up to 50 regulars", never "fast" or "many".
- **Requirement IDs are permanent.** `CODE-NN`, numbered within the feature, never reused or renumbered.
- **Quality requirements only when measurable.** Leave out generic wishes ("should be secure"); keep checkable ones ("passwords are never shown in full").
- **No tech stack, libraries, vendors, schemas, endpoints, or file structure, even when the user names them.** Write the behavior the name stands for. The name itself belongs to `architecture-design`, which reads the idea file and the conversation.
- **Describe the product as it is now, not how it got here.** Requirement text, scope lists and assumptions carry no change notes, provenance tags ("from the tank idea") or process notes ("numbers chosen for review"). History goes in one Changelog row per round, and in git.

**Data and ML projects — extra rules:**

- **Specify the data, not the source.** `DATA-NN` requirements say what the data must contain and guarantee ("daily prices for all US stocks, including delisted ones, since 2010"; "every record is stamped with the date it became known"). Which API, vendor, or dataset meets them is an architecture decision, made by checking candidates against these requirements. Name a source only when the brief makes it a fixed constraint (our own database, a required benchmark).
- **Write data guarantees as testable criteria.** Leakage, look-ahead, survivorship bias, and coverage gaps are requirements, not hopes: "Given a backtest date D, when the strategy requests data, then no value published after D is returned."
- **Model quality is a requirement with a baseline.** Acceptance criteria name the metric, the held-out data, the threshold, and the baseline to beat: "Given the most recent 6 months of plates (never trained on), when ranked, then reviewing the top 20% catches ≥ 90% of scientist-failed plates, and beats ranking by Z′ alone." Never "the model is accurate".
- **No model types or libraries.** "Gradient boosting" or "PyTorch" are architecture decisions; the spec says what the model must achieve.
- **Learning projects: "build it by hand, then compare with a library" is a valid requirement. Write it without the names.** "The learner's PPO reaches ≥ 90% of the mean return of an established reference implementation on the same task." "The allocator is written from basic array operations; a reference library is used only to check its output." The architecture picks the reference.

## Hygiene check

Run on everything above the Changelog before presenting a Draft.

- **Implementation names.** Search for library, framework, vendor, dataset, file-format, database and model-type names, file and function names (a reference's included), including names the user, the brief or the idea file used. Rewrite each one as the behavior or guarantee it stands for: "within 10% of Stable-Baselines3" becomes "within 10% of an established reference implementation", and "NumPy only" becomes "written from basic array operations". The only exception is a source the brief makes a fixed constraint.

## Spec: the plan, my assumptions, and questions

**How the brief's goals map to features:**
```
Goal 1 (each env teaches one idea, I can explain it) → Snake (SNAKE), Fish tank (TANK), Predator–prey (PREY), Lesson notes (NOTE)
Goal 2 (my algorithms beat baselines, land near a library) → Evaluation & baselines (EVAL)
Goal 3 (watch agents, early vs late side by side)       → Replay viewer (VIEW)
Goal 4 (each env trains in ≤ ~1 hour on laptop CPU)     → Training runs (TRAIN) + a time requirement
Goal 5 (shared pieces built once)                       → Environment format (CORE), TRAIN, EVAL, VIEW
```
All three stages will be specified in full.

The spec describes what each agent does, not which algorithm it uses. It will say "a learner that estimates the value of each action from replayed past experience", and the names DQN and PPO get chosen in the architecture step. Likewise, "a library" will be written as "an established reference implementation".

**My assumptions, with proposed numbers. Correct any of these, or I'll use them:**

1. **Repeatable results.** The same seed and settings give identical results on the CPU. Every comparison uses 5 training seeds per setup, and "beats the baseline" is tested with the `null-hypothesis-testing` skill at the 5% level.
2. **Snake:**
   - 10×10 grid.
   - Three moves: turn left, go straight, turn right.
   - Rewards: +1 for food, −1 for dying, 0 otherwise.
   - An episode ends on death, or after 100 steps without eating.
   - The score is the average food eaten over 100 test episodes.
3. **Fish tank:**
   - A circular tank and one ball bouncing at constant speed.
   - 8 fish that steer continuously, with a capped speed.
   - Each fish sees only the ball, the other fish and the wall within a set radius, about 30% of the tank's radius.
   - A fish touched by the ball is out for the rest of the episode.
   - Episodes last up to 1000 steps, and the reward is +1 for each step a fish stays alive.
   - The score is the average number of steps a fish survives.
   - All fish use one shared learned policy.
4. **Predator–prey:**
   - The same tank, with food pellets appearing over time.
   - Prey have an energy level that runs down, so they have to forage rather than hide. Prey are rewarded for eating and penalized for being caught.
   - The predator is rewarded for each catch.
   - **Phase A:** a scripted predator chases the nearest prey it can see.
   - **Phase B:** prey and predator learn at the same time. Progress is measured by playing current agents against saved earlier versions of each side. This shows whether training cycles instead of improving.
5. **Baselines** for every environment: random actions, plus one simple scripted strategy.
6. **Time limit:** under 60 minutes on your laptop's CPU per training run. For S3 the limit applies to each phase separately.
7. **Replay viewer:** saved episodes play back exactly as recorded, at 30 frames per second or more, with two checkpoints side by side.

**Questions that change the requirements:**

1. **What does the snake see?**
   - (a) A short list of facts: is there danger to the left, ahead or right; which way is the food; which way am I heading. This trains in minutes.
   - (b) The whole grid. This is closer to "learning the board", but much slower and riskier for the one-hour limit.
   - *I recommend (a) as required and (b) as an optional extra.*
2. **How strong should Snake's scripted baseline be?** A greedy snake that also avoids immediate collisions is surprisingly hard to beat on a 10×10 grid within an hour of training.
   - *I recommend the plain greedy snake (heads for the food with no safety check) as the bar to beat, with the safe greedy snake reported for reference only.*
3. **How close to the library counts as "near"?**
   - *I propose your version reaching at least 80% of the reference's average final score, with the same number of training steps.*
   - The comparison would apply to S1, S2 and S3 Phase A only. Off-the-shelf libraries don't handle two sides learning at once (Phase B) well.
4. **Should "I can explain why it works" be a requirement?**
   - *I propose a short lesson note per environment: the idea, the results compared with the baselines, and one failure you saw and fixed.*
   - It would come with the charts that make explaining possible: losses, value estimates, and how much the policy is still exploring (entropy).
5. **What happens to a caught fish in env 2:** removed for the rest of the episode (my assumption), or put back somewhere else?

Once you answer, I'll write `docs/spec.md` and bring it back to you for approval.
