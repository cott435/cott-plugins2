## 2. Cut the stage into milestones

When `stage_to_cut` names a stage, its pipelines are `pipelines_inferred`: the ones covering the stage's spec IDs. When the brief lists every stage, each stage's Source is `brief` and the spec's only Changelog row says IDs `all`, so `dt` can't tell which pipelines belong to which stage and `pipelines_inferred` comes back empty: assign each approved pipeline to the stage whose outcome it delivers, by its Covers.

- **Order by dependency.** Which pipeline needs another's outputs? A consumer needs its provider's *interface*, not its finished build: a boundary the interface task freezes lets both sides build in the same milestone.
- **The first milestone is a walking skeleton:** the thinnest end-to-end path through every package the stage touches, one pipeline per package at spine version, joined across each boundary, so the user can run it end to end.
- **Each later milestone is a vertical slice:** it adds a capability the user can run end to end (categories, transfers, the review screen), thickening the skeleton. Never a horizontal layer ("all of the relay", "every model"), which can't run on its own, and never a leftover of what didn't fit: viewers, reference checks and write-ups go in the milestone that builds what they show, and that milestone's exit holds the stage's quality bar (the snake beats both baselines).
- **Cut along dependency lines,** only where a later milestone needs an earlier one's outputs, and name them in the row's `Depends`: `M1 (profile.Profile, PL-01 output)`. Depends lists only the milestones whose outputs this one needs, never a build order or a note naming another milestone: `dt` reads every `M<n>` in the cell as an edge. Independent tracks stay in one milestone as parallel waves: one milestone is active at a time, so splitting them only serializes them.
- **Size each one** against the cap (step 3): a critical path of at most about 15 tasks. Cut until each fits; fewer, larger milestones beat many thin ones. A stage that fits one milestone gets one.
- **Every pipeline lands** in the milestone that first wires it; a later slice that thickens it lists it again. Every spec ID of the stage lands in a milestone or is Deferred later.

# Milestone shape: interface, step spines, wiring, system

Read when writing a milestone's tasks. Examples: `examples-phase0.md`.

A milestone is planned from its pipelines' steps: each step has one owner, one module and typed `In → Out`, so it is the unit of work. The plan freezes every boundary between steps first, so the work on both sides starts at once instead of queueing behind one spine. Every task carries `**Kind:**`:

```
## Phase 0: Interface              interface (solo, first)       types, signatures, samples, fakes, exports, __main__
## Phase 1: Step spines            spine, one per step           each writes its owner module only
## Phase 2: Wiring and thicken     wiring, one per pipeline      its entry module, smoke test
                                   thicken (tasks.md)            each after its step's spine
## Phase 3: System                 system (solo, last)           fakes swapped for real providers
```

Phases name the usual waves; the dependency graph (`tasks.md` step 9) decides what may start. Tester halves of split tasks start right after the interface.

**a. Interface task** (`**Kind:** interface`, `**Step:** contract`, solo, `**Depends on:** —`). It freezes, as code, every boundary in the milestone whose two sides belong to different tasks:
- each contract `type` section named in a milestone step's `In → Out`, every one, since the step's signature needs it, written into its owner's `types.py`, with a schema (pandera for a frame, JSON Schema across runtimes) and one sample per case in `tests/contracts/<component>.<Type>/`. A case naming a probe sample (`PB-01 samples/sync_added.json#0`) puts `PB-01:samples` in `Read:`; the task derives the type's sample from it, never copies it
- each new step's signature in its owner module, its body `raise NotImplementedError("<task id>")` naming the task that replaces it (Fakes and stubs)
- for each function another pipeline or package calls (its `**Boundary:**` line names that consumer): a fixture-backed fake serving its fixtures, where the caller's tests load it, and its contract's cases as one test that takes the provider
- for each object with behavior a step passes (a Protocol or class: `core.Dataset`, `runstore.RunWriter`) and each call to a function another task builds in the caller's own pipeline and package (a `**Boundary:**` line naming a component too): the Protocol or signature plus a fixture-backed replay double in `tests/contracts/<component>.<Type>/`. The double is that type's sample, not a fake: the system task never swaps it
- each component's `__init__.py` exports, and the package's `__main__.py`: the dispatch from each pipeline's trigger to its entry function, whose signature it stubs naming the wiring task, in that pipeline's own entry module

Not frozen: helpers, private functions, anything one task owns end to end, and boundaries an earlier milestone froze. `Read:` the type and boundary symbols. Acceptance: every sample validates against its type; every signature imports and matches the contract; each fake passes its contract's cases, and each replay double serves its fixtures. A human approval a requirement places before several steps (a design direction) is asked during planning or is this task's acceptance ("direction approved; `design.Theme` sample written"); those steps build on the sample, with no edge to the step that sets it. `Writes:` each component folder as one glob (`src/gridload/profile/**`) plus its contract folders; `task-size` doesn't count them. A milestone across packages may have one interface task per provider, all solo and first; interface tasks never depend on each other. When one runtime's types are generated from another's schema, the providing interface task runs the generator and writes the generated file too (its `Writes:` claims it).

**b. Step spines** (`**Kind:** spine`, `**Step:** PL-NN.<function>`, solo, XS or S). One per new step, library class rows included, each depending only on the interface task: it replaces the stub naming it with the step's spine version from the step table. `Writes:` its owner module, or its owner folder as one glob (`src/leaflab/core/train/**`), and its unit test, nothing else; steps sharing one module share one spine task. A provider waiting on a probe gets no spine: its stand-in row (`pipeline-design`'s `steps.md`) is built instead, and the real spine goes in the milestone the probe's Answer unblocks. Acceptance: the step's input sample gives a schema-valid output; the signature is unchanged. A step another pipeline provides (`PL-01 as built`) gets no spine.

**c. Wiring** (`**Kind:** wiring`, `**Step:** PL-NN`, solo). One per new pipeline: the entry function in the pipeline's own entry module (the layout's, never one module shared by several pipelines), so wiring tasks run side by side, and its smoke test. `__main__.py` is the interface task's. It depends on its pipeline's spines, since the smoke runs them (`order`, `none: integration: …`), never on their thicken tasks. A call to another pipeline or package runs against that boundary's fake, so wiring PL-02 never waits for PL-01. Acceptance: the smoke command runs end to end and is committed as the pipeline's smoke test, which checks that the pipeline runs and the shape of what it writes, never a value a thicken changes. `dt prebuild-clear` replaces the pipeline's pre-build sections once the wiring lands; that is dt's step, not an acceptance bullet.

**d. System task** (`**Kind:** system`, solo, last). It swaps each fake for the real provider, in the entry its wiring wrote (a `file` edge), and runs every smoke command and the milestone's golden cases on the real chain. Its `Writes:` name each fake's conformance test (`tests/unit/<pkg>/test_<symbol>_conformance.py`), and its acceptance reads "each fake's contract cases pass on the real provider". Its row to the provider's wiring is `order` · `none: integration: swaps in the real <provider>`. System tasks never depend on each other: each builds its golden-case stores from fixtures, and a case that needs another system pipeline's real output joins that pipeline's system task. Multi-package: one per new system pipeline, `**Step:**` that pipeline, `**Package:**` the owner of its first step, `**Reason:** system task`. Single package: `**Step:**` the calling pipeline. A golden case that needs real collaborators (a thickened step, a class's real upgrade) is the system task's acceptance, never the wiring's, so wiring depends only on its pipeline's spines and fold tasks. A milestone with no fake and no such case has no system task.

**Folds** keep the task count down. The pipeline's wiring depends on a fold task, so a fold is allowed only where that task is XS and the critical path doesn't grow. Record each on its task as `**Reason:** fold: <rule>`:
- A step with a golden case whose spine and thicken are both in the milestone, or whose spine version is its whole behavior, may be one task that replaces the stub itself, `**Kind:** thicken` and `**Mode:** split`, never a spine; with a thicken folded in, its acceptance keeps the baseline selectable.
- A trivial step (pass-through, print) is built by its pipeline's wiring task; its stub names the wiring task.

**Fakes and stubs.** A fake is allowed only where a pipeline calls another pipeline or package. Shared fixtures don't stop it drifting: whatever it does beyond echoing one (filtering, ordering, an error) is one of its contract's cases, and the system task runs those cases on the real provider (`dt context`'s Conformance block). Each case is also named in the acceptance of a task that builds that behavior in the real provider (its spine, a thicken or the wiring, or Deferred with it), so a drift fails there first; a case with no such task is a plan gap, like an uncovered ID. Mocking a step is forbidden: a step's spine is the real baseline, and its consumer builds against the type's sample (for a Protocol or class, its replay double). The interface stubs are the floor's one stub carve-out (`build-setup`'s CR-02): allowed while the task they name is open; the gate fails on one naming a done task, the milestone exit on any. No test checks a stub (`stub-pinned`): it would fail once its task lands, so an acceptance names the signature, never the body.

**Frozen means frozen.** Changing a frozen type, sample, signature or fake is a `contract-change`: `architecture-design` Revise, then a new interface task naming the symbol in `Read:`, never an edit to make a test pass. The bar enforces it (CR-09): once a contract folder exists at a task's base the implementer can't write it, and `dt guard` asks before any edit no open interface task covers. The re-freeze runs in the main session, since the implementer's guard blocks a folder frozen at the base.
# Thickening, routing, modes, checkpoints, the graph, writing

Read when writing thicken tasks, the dependency graph and the files. Templates: `../examples.md`; graph example: `examples-phase0.md`; routing example: `examples-routing.md`.

## 5. Thicken

`**Kind:** thicken`, under Phase 2: one task per step upgrade, depending on its step's spine. Order in the file sets nothing: every thicken task can start once its spine lands. Risk orders tasks only when a later one must learn from an earlier one, as an `order` edge with its reason (step 9). In data and ML work, data loading, leak checks and the evaluation get thicken tasks of their own, never left until after the model.

**Split a task** when it needs more than one session, has more than 3 acceptance bullets, touches two packages or two steps, or has "and" in its title. Sizes count `Writes:` entries outside `tests/` (`task-size`; a folder glob counts as one): XS = 1, S = 1–2, M = 3–5. Nothing larger. Spine and thicken tasks are XS or S.

**Acceptance is test-backed.** Each bullet is checkable: a `TC-NN` passes, a Given/When/Then, a model criterion by ID, the smoke command. With no `tests.md`, write the criterion so a tester can encode it. A TC that runs the whole pipeline is the wiring or system task's acceptance (`phase0.md`), never a thicken's. A thicken's golden case builds its store from its own fixture (`input.json`) through a shared test helper, never through a wiring task's run, so no thicken waits on wiring.

## 6. Route skills and references

**Skills.** Start from `milestone_skills` (the milestone's `**Skills:**` line, else its stage's): each goes on the `**Skills:**` of every task it fits, and at least one. Then add others whose descriptions fit a task (project `.claude/skills/*/SKILL.md`, `skills_available`). The plan's Scope lists the milestone's skills. A task that needs a skill that isn't installed names it anyway (`dt status` reports it under `skills_missing`) and goes under Open questions. Never quietly plan the step without it.

**References.** Each `RF-NN` or `PB-NN` in `milestone_references` goes in the `Read:` of the tasks whose step it informs; an RF entry's *Use for* and *Key parts* say which, a PB entry's *Informs* and *Caveats*. Cite the ID, never the `references/` or `probes/` path. A probe's code goes to the step that calls the same API (`PB-01:probe.py:sync_all`); its redacted samples (`PB-01:samples`) go to the interface task (`phase0.md`) and, as raw-shaped test input, to that step's spine and thicken tasks. Over 300 lines, add a selector so the packet stays small: `RF-01:deseasonalize` (one function or class), `RF-01:outline`, or `RF-03:<heading>` for a doc. With no selector a long file prints as its outline and `dt lint` warns `ref-large`. Whether to reuse the code is the builder's call; don't write it into Acceptance. A decision whose Consequences adopt what a probe spent (Plaid Items it linked) gets its own task in the milestone that builds that step.

## 7. Build mode

- `split` (tester, then implementer) when the task adds or changes behavior with a checkable outcome: anything a TC case, Given/When/Then or model criterion covers.
- `solo` for interface, spine, wiring, system, refactor, glue and doc-sync tasks.

`mode_violations` flags a task that breaks the rule. An override needs `**Reason:** <one line>` on the task. **A split task tests symbols a frozen interface declares** (the interface task's types and signatures), so the tester never writes against a guess and starts right after the interface, beside the implementers. Its `Depends on` is the implementer half's; the tester half waits only on the interface.

## 8. Checkpoints

`### Checkpoint after M<n>-T<nn>` at the end of a wave, naming the wave's last task in plan order: `### Checkpoint after M<n>-T<nn> (barrier)` after the interface task(s), so nothing builds on an unreviewed interface, and usually once after the wiring and thicken wave, when every pipeline runs end to end. A plan without the barrier still gets the review: `dt` adds the barrier. `### Checkpoint: milestone exit` last. Use the blocks in `../examples.md`. A separate read-only reviewer runs each one; the orchestrator records its findings with `dt finding`, not this skill.

## 9. Dependencies, Writes, the graph, Verify

- **`Depends on:`** resolves, points only backward (position counts, not ID number), is acyclic, and holds only edges nothing mitigates.
- **`Writes:`** is exact paths, or a folder glob the task owns, and is an exclusive claim: two tasks with no `Depends on` path between them never write the same path (`writes`). Shared files (`__init__.py`, `types.py`, `__main__.py`, and shared test helpers: `conftest.py`, a golden-case store builder) belong to the interface task; each pipeline's entry module to its wiring and system tasks (`phase0.md`). No `Writes:` under `tasks/`: builders never tick `todo.md` or record findings; the orchestrator does after each merge.
- **`## Dependency graph`**, after the last checkpoint: one row per edge between tasks, `| From | To | Kind | Mitigated by |`. From is the task that needs, To the one it needs; each cell starts with the task ID. Mitigated by names the interface and the task freezing it (`profile.Profile sample (M1-T01)`), or says `none: <reason>`.

| Kind | Meaning | Mitigation |
|---|---|---|
| `data` | One step's output feeds another's input | The type and its sample |
| `call` | A step calls a function another task builds | Across pipelines or packages, its fixture-backed fake; in the caller's own pipeline and package, its replay double (`phase0.md` a), never a fake |
| `file` | Two tasks must write one file | Move the shared part to the interface task; else serial. Two wiring tasks never share a file: each writes its own entry module. Two steps' thicken tasks on one module: the interface task's layout splits it (each step its own file, the old module re-exporting); never chain them |
| `code` | A task changes code another task wrote (a thicken after its step's spine or an earlier thicken of that step) | None: serial |
| `contract-change` | A task changes a frozen interface | None: serial, plus a new interface task |
| `order` | Integration (a wiring or system task runs the steps it wires: `none: integration: the smoke runs it`), or risk or learning ("do X first to learn Y"; never a human approval: `phase0.md` a) | None: reason required |

A spine never has an edge to another step's task: it builds against the interface's samples and doubles. A mitigated edge documents why two tasks run side by side and never appears in `Depends on`; an unmitigated one must (`edges`). Every `Depends on` has its row, except a dependency on the interface task, which every task has and needs none. The table is the reviewable argument for every serial step.
- **Width.** `dt status` gives `critical_path`, `waves`, `width` and `parallelism`; on the fresh plan `dt ready` lists only the interface task(s). Mostly width-1 waves mean an edge an interface could mitigate is ordering tasks.
- **`Verify:`** The interface task's runs the schema check over every sample and each fake's contract cases; every other task's runs its focused tests and `scripts/check.sh gate` (`--pkg <pkg>` in multi-package), plus its pipeline's smoke command (tests.md Strategy, else the Trigger plus ` --smoke`) once its `Depends on` path reaches that pipeline's wiring task: wiring and system tasks always. A thicken task running beside the wiring is smoke-tested by the gate after each merge. Only the modes `fast`, `gate` and `full` exist.
- **`Read:`** lists the IDs (references as `RF-NN[:selector]`, probes as `PB-NN:<file>[:<symbol>]`, `PB-NN:outline` or `PB-NN:samples`) and paths a builder needs, and nothing else. A split task's names its step's function, so the tester knows the signature it tests. Check each packet with `dt context <task>`: it must resolve and stay under 2,000 lines.
