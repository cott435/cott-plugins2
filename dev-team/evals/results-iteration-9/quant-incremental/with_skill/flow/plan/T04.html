requirementCHECK-01A completeness check fails for each trading day in a company's trading life (first bar to last trading date) with no bar.added

criteria

requirementCHECK-03An extreme-move check fails for each daily total return beyond ±50% on a day with no corporate action.added
criteria
  • Given a −60% return on a day without a split or dividend, when checks run, then a failure is recorded; given the same move on a 1-for-2 reverse-split day explained by the split, then none is.
requirementCHECK-04A split-consistency check fails for each split where the ratio of the unadjusted close before and on the ex-date differs from the split ratio by more than 30%.added
criteria

requirementCHECK-05A member-coverage check fails for each trading day on which an index member has no bar.added
criteria

requirementCHECK-06A member-count check fails for each trading day with fewer than 498 or more than 505 members.added

requirementCHECK-07A point-in-time check fails for each record whose first-known date is later than the date it is used for in any as-of read.added
criteria
  • Given a dividend first seen on day K with ex-date before K, when checks run on as-of reads before K, then no read before K returns it; any that does is a failure.
requirementCHECK-08A uniqueness check fails for each company and day with more than one bar, and for each ticker held by two companies on the same day.added
criteria

requirementCHECK-09A reference-list check compares the user's list of 10 delisted former S&P 500 members against the data, and fails for each field that differs: membership start and end dates, last trading date and exit type.added
criteria
  • Given the user's list with expected values, when checks run, then each of the 10 companies shows pass, or a failure stating the expected and found value.
  • Given a company on the list that is missing from the data, when checks run, then a failure says it was not found.
requirementCHECK-10The user can mark a failure explained with a note; the explanation stays attached while a later run finds the same failure with the same found values.added
criteria
  • Given an explained failure, when the next check run finds it unchanged, then it shows as explained with the original note.
  • Given an explained failure whose found values change in a new data version, when checks run, then it shows as failed again, with the old note visible.
requirementCHECK-11Each check run produces a summary per check: failures, explained failures and unexplained failures.added

requirementLOAD-01A full download run fetches daily bars, corporate actions and membership history for every company that was an S&P 500 member on any trading day from 2000-01-03 to the most recent completed trading day.added
criteria
  • Given an empty local store, when the user starts a full download run and it completes, then every company with at least one day of membership in the covered period has daily bars, corporate actions and membership intervals stored.
  • Given the completed run, when the user looks up a company that was removed from the index and later delisted, then its full history up to its last trading day is present.
requirementLOAD-02A refresh run fetches only days and records added or revised since the last completed run.added
criteria
  • Given a completed run as of day D, when the user starts a refresh on day D+5, then the new bars for the days after D are stored and earlier unchanged records are not downloaded again.
  • Given the primary source revised a past record (for example a late dividend), when a refresh runs, then the revision is stored as a new record with the date it was first seen, and the earlier value is kept.
requirementLOAD-03Each completed download or refresh run produces a new data version with an identifier, a completion time and the date range it covers.added
criteria
  • Given two completed runs, when the user lists data versions, then both appear with identifier, completion time, covered range and record counts.
  • Given an existing data version, when a later run completes, then reading the earlier version returns exactly the same records as before.
requirementLOAD-04An interrupted or failed run leaves the latest completed data version unchanged.added
criteria
  • Given a run that fails at 60%, when the user reads data, then they see the previous completed version with no partial records.
  • Given a failed run, when the user starts a new run, then it resumes without downloading records already fetched in the failed run.
requirementLOAD-05The raw response from each source is kept alongside the stored data, so any stored value can be traced to what the source returned.added
criteria
