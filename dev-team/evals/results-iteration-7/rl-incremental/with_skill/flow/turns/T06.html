# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. # Decisions

Read when making a technical decision, or when one changes or retires an Accepted decision.

## Making a decision

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Ask about expensive-to-reverse ones. Record each as `AD-NN`, citing an informing reference by `RF-NN`, never its path. Small reversible choices go only in the tech stack table. A repo with its own ADRs keeps that convention.

## When it touches older decisions

Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. A reversed decision collapses to its heading with the title struck, plus one status line: `**Status:** Superseded by AD-NN · date — reason`. Delete its Context, Decision, Alternatives and Consequences. The new decision's Context says what the old one chose and why that no longer holds. Then update every section that cited the old decision (tech stack, contracts, code comments, layout, risks) so that only the superseded line, the new decision and the Changelog mention it.
- **Accepted decisions stay true.** When a new decision changes only part of an Accepted one, revise the old one instead of superseding it. Rewrite the sentences that are no longer true, in its Context as well as its Decision and Consequences, and point to the new decision for the part it now owns. "Two holdouts, one per study" becomes "one holdout per study; AD-26 sets the ranges". The old decision stays Accepted. Supersede only when its choice is reversed as a whole. Readers take an Accepted decision as current, so a stale count in one is a defect.
- **Shared decisions state a rule, not a roster.** A decision that later stages build on (where claims go, which modules may import a library, where runs are stored) is worded to stay true as stages join: "every module that makes a significance claim writes a `Claim`", not "`eda` and `backtest` write claims". Its Context cites the requirements that set the rule, not each one that uses it. The members and their per-stage details (claim families, importers, run folders, time budgets) are listed once, where they live: a component's row and Covers, a contract section, the storage layout, or that stage's own decision. A new stage adds its members there and cites the shared decision. Revise the shared decision only when its rule changes. If one already lists members, move them out the next time a round touches it.

# Grid RL Lab — Architecture

**Status:** Draft · **Shape:** Single package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

Single package (`gridlab`): one learner, one laptop, one install. The environments are behind the `core.Env` protocol, so a later environment drops in as a new component folder.

## Overview
Every environment implements `core.Env`, and every agent implements `core.Agent`. `train` takes a `RunConfig` and builds the environment and agent by name through `experiments`. It runs the step loop, has the agent learn from each `Transition`, pauses on a schedule for greedy evaluation via `evaluate`, and writes everything through `runstore` into the run's own folder. After a set of runs, `compare` writes comparison inputs that the `null-hypothesis-testing` skill tests. The skill's verdicts come back into a results table. `plots` draws learning curves, and `viewer` replays recorded episodes. Environments render to a generic `core.Frame` grid of cell codes, so nothing downstream knows Snake from the corridor (CORE-07).

```mermaid
flowchart LR
  cli --> experiments & train & compare & plots & viewer
  train --> experiments & evaluate & runstore
  experiments --> snake & corridor & baselines & tabular & dqn
  snake & corridor & baselines & tabular & dqn --> core
  evaluate --> core
  runstore --> core & experiments & evaluate
  compare --> runstore
  plots --> runstore
  viewer --> evaluate & runstore & experiments
  compare -. inputs.json .-> skill[null-hypothesis-testing skill] -. verdicts.json .-> compare
```

## Data
No external data: every experience comes from the environments.
- **Seeds (AD-09):** training seeds 1–5, used for agent initialization and exploration; each run draws its training-episode seeds from 1,000,000 upward. Learning-curve evaluation uses seeds 20,000–20,019 (TRAIN-05). Final evaluation uses seeds 10,000–10,099 (EVAL-01). The three ranges never overlap.
- **Baselines** are "runs" with zero training steps: each is evaluated under the same 5 seeds (its tie-breaking random source) and the same evaluation seeds, so both sides of every comparison have the same shape (BASE-04).
- **Storage (AD-06):** `runs/<experiment>/<agent>-<env>[-<level>]/seed<N>-<YYYYmmdd-HHMMSS>/` holds `config.json` (with a `complete` flag), `episodes.csv`, `curve.csv`, `final_eval.json`, the agent (`agent.pt` or `table.npz`) and `recordings/{best,median,live-*}.npz`. Reports live in `reports/<name>/`: `inputs.json`, `verdicts.json`, `table.md`, and the plot PNGs. Both trees are git-ignored.

## Cross-cutting concerns
- **Reproducibility (QR-04):** AD-05. One seeded `np.random.Generator` per environment and per agent, and torch seeded with one thread; no global random state.
- **Speed (QR-01–QR-03):** Snake steps in plain Python on a deque plus a set of body cells, with no array math in the hot path (AD-03). DQN's tiny network runs faster on one CPU thread than on the Apple GPU (AD-04). Budgets are checked by timing tests, marked slow.
- **Errors:** invalid actions, steps after the episode ended, unknown names and corrupt files raise `ValueError`, `RuntimeError` or `FileNotFoundError` with the valid options in the message. `cli` turns them into one-line messages and a non-zero exit code.
- **Interruption (TRAIN edge case):** `train` catches Ctrl-C, flushes the logs and leaves `complete: false` in `config.json`.
- **Offline (QR-05):** no network calls anywhere; dependencies are installed once by uv.
- **Testing:** pytest. Environment rules are tested with scripted action sequences; agent updates are tested with hand-computed values (TAB-01, TAB-02). The corridor is the end-to-end smoke test.

## Decisions
### AD-01: Python 3.12 managed with uv
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** The learner knows Python and PyTorch. The laptop has Python 3.13 and uv installed.
- **Decision:** Python 3.12, pinned in `pyproject.toml`, with the environment and lock file managed by uv.
- **Alternatives:** 3.13 — supported by current PyTorch, but 3.12 has the widest wheel coverage, and nothing here needs 3.13. Plain pip with a venv — works, but there's no lock file, so it's less reproducible.
- **Consequences:** `uv run` is the entry for every command; uv installs 3.12 itself.

### AD-02: Own environment protocol, shaped like Gymnasium, with no Gymnasium dependency
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** CORE-01–CORE-04 need one interface for every environment. The brief wants everything built by hand now, and a comparison with library agents later.
- **Decision:** `core.Env` is a `typing.Protocol` with `reset(seed) -> obs` and `step(action) -> StepResult` (observation, reward, terminated, truncated, info), the same split Gymnasium uses, plus `render() -> Frame`. Actions are plain integers; there are no space objects.
- **Alternatives:** Subclass `gymnasium.Env` — library agents work immediately, but it adds spaces, wrappers and checker rules that teach the library rather than the concept. A free-form API — would make the later library comparison a rewrite.
- **Consequences:** The later library-comparison stage needs a thin adapter (about 30 lines). The terminated/truncated split is in the protocol from day one, so bootstrapping is right (TAB-02, DQN-06).

### AD-03: Snake simulated in plain Python, observations as NumPy vectors
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `snake`
- **Context:** QR-03 requires ≥ 10,000 steps per second. On a ≤ 10×10 grid, the per-step work is a few set lookups.
- **Decision:** Body is a `deque` of cells plus a `set` for collision checks; the 11 features are computed directly, then packed into one `float32` array.
- **Alternatives:** A NumPy grid array per step — the overhead of creating arrays dominates at this size. Vectorized batches of environments — faster, but harder to read and not needed for the budget.
- **Consequences:** The code reads like the rules. Rendering builds a `Frame` only when asked, never in the training loop.

### AD-04: DQN in PyTorch on one CPU thread
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `dqn`
- **Context:** DQN-09 needs a general neural-network toolkit with no RL library. QR-01 gives ≤ 15 minutes per L3 run on an M4 Pro, with no NVIDIA GPU. The network is tiny: 11 inputs, 3 outputs.
- **Decision:** PyTorch, with a two-hidden-layer MLP (128 units each by default) and Adam optimizer. Everything runs on the CPU, with `torch.set_num_threads(1)`. Replay buffer and target network are written by hand.
- **Alternatives:** Apple GPU (MPS) — the overhead of each GPU launch outweighs the work for batches of 64 on a network this small. JAX — less familiar to the learner. A network in NumPy by hand — possible, but backprop by hand is a different lesson.
- **Consequences:** A 200,000-step L3 run should take minutes, well inside QR-01; a timing test confirms it. PyTorch is the largest dependency.

### AD-05: Reproducibility by explicit seeded random sources
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** QR-04 and SNAKE-15 require identical results from the same seed and configuration.
- **Decision:** Every environment and agent owns an `np.random.Generator` created from its seed. DQN also seeds torch, uses one thread and turns on `torch.use_deterministic_algorithms(True)`. No code touches global random state.
- **Alternatives:** Global seeding at program start — brittle, since any extra random call shifts every later result.
- **Consequences:** Results are reproducible on one machine. Across PyTorch versions or machines they may differ slightly, which QR-04 allows.

### AD-06: Plain files per run, never overwritten
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `runstore`
- **Context:** TRAIN-04 requires each run kept separately with its configuration, logs, agent and recordings; QR-05 requires offline use; the brief rules out tracking services.
- **Decision:** One folder per run, named with seed and timestamp (layout under Data), created exclusively so it can't overwrite. JSON for configuration and summaries, CSV for logs, `.npz` for recordings and the tabular table, `.pt` for the network's weights.
- **Alternatives:** SQLite — overkill for append-only logs, and harder to read by eye. An experiment-tracking service — ruled out by the brief.
- **Consequences:** Every artifact is readable with a text editor or one line of NumPy. Finding runs is a directory search, which is fine for tens of runs.

### AD-07: Matplotlib for both plots and the interactive viewer
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `viewer`, `plots`
- **Context:** VIEW-01–VIEW-06 need an interactive replay with controls, an action-value panel and animation export. EVAL-03 and ABL-04 need static plots following the `dataviz` skill.
- **Decision:** Matplotlib for both. The viewer is one figure: a grid image, a bar panel for the action values, buttons and a speed slider (Matplotlib widgets), and keyboard shortcuts. Export uses Matplotlib's animation writer with Pillow to produce GIF.
- **Alternatives:** Pygame — a smoother game loop, but a second graphics stack and hand-built controls. A terminal viewer — no export, and too cramped for the value panel.
- **Consequences:** One plotting dependency. Playback tops out at around 30 frames per second, which matches VIEW-02's limit. It needs a GUI backend (macOS's native one) for the interactive window; export works without one.

### AD-08: Significance tests are run by the null-hypothesis-testing skill, not by code
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `compare`
- **Context:** EVAL-02 and ABL-03 name the `null-hypothesis-testing` skill as the owner of the test, the correction and the decision.
- **Decision:** `compare.write_comparisons` writes `reports/<name>/inputs.json`: one `ComparisonInput` per pair, carrying per-seed mean scores and per-episode scores for both sides. The skill is run on that file and writes `verdicts.json` as `Verdict` records. `compare.results_table` joins the verdicts with the run summaries, and marks a report underpowered when there are fewer than 5 seeds.
- **Alternatives:** A t-test or permutation test hand-written in `compare` — a second, unreviewed version of the skill's procedure.
- **Consequences:** Producing a report takes two steps (write the inputs, run the skill). `results_table` refuses to build until verdicts exist for every input.

### AD-09: Fixed, disjoint seed ranges for training and evaluation
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** `evaluate`, `train`
- **Context:** EVAL-01 requires evaluation seeds that are the same for every agent and never used in training. TRAIN-05 needs a fixed set for the learning curve.
- **Decision:** These are constants in `evaluate`: final evaluation uses 10,000–10,099, and the curve uses 20,000–20,019. Training episodes draw seeds from 1,000,000 upward using the run's generator.
- **Alternatives:** Random evaluation seeds per run — the comparisons would no longer be paired.
- **Consequences:** Every agent and baseline is scored on identical games, so paired tests are possible. Changing the ranges invalidates old comparisons.

## Risks and open questions
- **The greedy baseline may be hard to beat.** It sees exactly what the agent sees (danger and food direction), and with 11 features neither can see the shape of its own body, so DQN-10 may fail against greedy. Mitigations: tune the discount and training length first. If it still fails, that's a finding, which may lead to a spec change (for example, a richer observation).
- **5 seeds is little statistical power.** A real but small edge may not reach significance. The skill reports what it can; more seeds fit the time budget if needed.
- **The interactive Matplotlib backend on macOS** can lag with keyboard handling. Fallback: drive everything from the buttons.
- **Is the custom API right (AD-02)?** The main choice to confirm. Subclassing Gymnasium is the alternative if library comparisons should work out of the box.

I've written the draft architecture. The gate checks came back clean: every spec requirement has a home, nothing is stale, and lint shows 0 errors with 2 warnings, covered below.

**Files**
- `docs/architecture.md`: overview with a dependency diagram, tech stack, 14 components, the data and seed layout, cross-cutting concerns, 9 decisions (AD-01 to AD-09), and risks.
- `docs/packages/gridlab/contract.md`: 47 public symbols across the 14 components, with 9 types marked for fixed test samples.

**Shape:** a single package, `gridlab`.

**Components**
- `core`: shared protocols and types.
- Environments: `snake`, `corridor`.
- Agents: `baselines`, `tabular`, `dqn`.
- `experiments`: builds environments and agents by name, plus the preset experiment sets.
- `evaluate`, `runstore`, `train`.
- Analysis and display: `compare`, `plots`, `viewer`, `cli`.

**Decisions that need your attention**
1. **AD-02: our own environment interface, with no Gymnasium dependency.** It has the same reset/step shape, including the terminated/truncated split, so a roughly 30-line adapter covers the later library-comparison stage. The alternative is subclassing Gymnasium now: library agents would work immediately, but you'd learn its spaces and wrapper rules along the way. I recommend our own interface.
2. **AD-08: the `null-hypothesis-testing` skill runs every significance test; the code never does.** `compare` writes `inputs.json`, the skill writes `verdicts.json`, and then `results_table` builds the table. That makes a report two steps instead of one command, but it avoids a second, unchecked version of the test procedure.
3. **The contract is over the size limit.** It's 333 lines against a 200-line ceiling for one package. I recommend staying single-package for now. The seams for a later split are recorded in the risks: environments, agents, and the rest of the lab. Only `dqn` may import PyTorch, and a lint rule will enforce it. The split would happen when Env 2 lands.
4. **Greedy may be hard to beat.** The greedy baseline sees exactly what the agent sees, and neither can see the shape of the snake's body, so DQN-10 might fail against greedy. That's recorded as a risk, with tuning as the first response and a spec change as a possible outcome.

The other warning is the same one as before: the roadmap checker can't find `dataviz`, but it's still available to use.

**Assumptions** (choices I made; correct any)
- Python 3.12 via uv; PyTorch on one CPU thread, not the Apple GPU (MPS), because launch overhead makes the GPU slower for a network this small; Matplotlib for both the viewer and the plots, with GIF export.
- DQN defaults: two hidden layers of 128 units, discount 0.95, batch 64, replay capacity 50,000, target refresh every 1,000 steps, exploration decaying over 100,000 steps. Tabular defaults: learning rate 0.1, discount 0.9.
- Seed ranges:

  | Purpose | Seeds |
  |---|---|
  | Training (agent seeds) | 1–5 |
  | Learning-curve evaluation | 20,000–20,019 |
  | Final evaluation | 10,000–10,099 |
  | Training episodes | 1,000,000 and up |

- Baselines are treated as runs with zero training steps, evaluated under the same 5 seeds, so both sides of every comparison have the same shape.
- The greedy baseline decides from the 11 observed features alone, never from the environment's internal state.
- The corridor observation is a one-hot position vector.
- Environments render a generic grid of cell codes, which is how the viewer works for both Snake and the corridor.
- Runs are stored as plain files under `runs/<experiment>/<group>/seed<N>-<timestamp>/`, and reports under `reports/<name>/`. Both are git-ignored.
