# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Root 2-4 pages, each package 1-3.

Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency direction worth enforcing with tooling. **A proof of concept is almost always a single package.** Don't build the platform inside it: name the seams that would become packages ("the data loader is behind `DataSource` so it can move out") and stop there.

## Grow triggers

A single package grows into several when one of these fires. `grow_triggers` in `dt status` reports the measurable ones; judge the rest from the spec and idea file.

- New requirements bring a dependency stack the rest shouldn't carry (torch, gym).
- A one-way dependency is worth enforcing (data must never import models, to prevent leakage).
- A package exceeds ~3 pipelines or ~12 modules, or its docs no longer fit a 2,000-line agent context, or `dt lint` warns `grow-size` on one of them.

# Contracts

Read when writing or changing a `contract.md`.

Write `docs/packages/<pkg>/contract.md`: the provider's promise to its consumers. Consumers read only this page, so it stands alone.

- **One `###` section per public symbol** (function, class, or type), headed `### <id>.<symbol>: <title>`. `<id>` is the package id. In a single package it is the component id, with sections grouped under `## <component>` (multi-package contracts drop that level and link the `architecture.md` beside them). The ID survives Grow, because the component id becomes the package id.
- **One symbol per heading.** Never `### train.train / train.train_seeds: …` or `### baselines.RandomAgent / ScriptedSnake: …`, however alike the symbols are: dt resolves `Read:` IDs and `dt context` packets only from a symbol's own heading. `dt lint` errors on these (`contract-heading`).
- **Function sections:** the signature in the project's language, then **Invariants** (shapes, ranges, guarantees), **Errors** (what fails and how it's reported), and **Used by** (consuming components or packages, plus `PL-NN` IDs once those pipelines exist).

# Decisions

Read when making a technical decision, or when one changes or retires an Accepted decision.

## Making a decision

For each significant open choice (language, libraries, storage, deployment, data sources, model approach): 2-3 real options checked against the requirements that constrain them (`DATA-`; model criteria and baseline), and a recommendation. Ask about expensive-to-reverse ones. Record each as `AD-NN`, citing an informing reference by `RF-NN`, never its path. Small reversible choices go only in the tech stack table. A repo with its own ADRs keeps that convention.

## When it touches older decisions

Find every Accepted decision a new one touches: search the doc for the components, data, counts and names it changes.

- It reverses an old choice → supersede the old decision, which collapses to its superseded line.
- It changes part of an old choice → revise the old decision in place (*Accepted decisions stay true*). Examples: a third holdout added to a decision that set up two, or a new caller of an interface that a decision said only one study uses.
- It only adds a member to a set a shared decision governs (another claim family, another run folder) → add the member where the set is listed and cite the shared decision. Don't revise it (*Shared decisions state a rule*).

## Rules

- **Decision IDs are permanent; superseded decisions shrink.** `AD-NN` IDs are never reused or renumbered, and the heading is never deleted. A reversed decision collapses to its heading with the title struck, plus one status line: `**Status:** Superseded by AD-NN · date — reason`. Delete its Context, Decision, Alternatives and Consequences. The new decision's Context says what the old one chose and why that no longer holds. Then update every section that cited the old decision (tech stack, contracts, code comments, layout, risks) so that only the superseded line, the new decision and the Changelog mention it.
- **Accepted decisions stay true.** When a new decision changes only part of an Accepted one, revise the old one instead of superseding it. Rewrite the sentences that are no longer true, in its Context as well as its Decision and Consequences, and point to the new decision for the part it now owns. "Two holdouts, one per study" becomes "one holdout per study; AD-26 sets the ranges". The old decision stays Accepted. Supersede only when its choice is reversed as a whole. Readers take an Accepted decision as current, so a stale count in one is a defect.
- **Shared decisions state a rule, not a roster.** A decision that later stages build on (where claims go, which modules may import a library, where runs are stored) is worded to stay true as stages join: "every module that makes a significance claim writes a `Claim`", not "`eda` and `backtest` write claims". Its Context cites the requirements that set the rule, not each one that uses it. The members and their per-stage details (claim families, importers, run folders, time budgets) are listed once, where they live: a component's row and Covers, a contract section, the storage layout, or that stage's own decision. A new stage adds its members there and cites the shared decision. Revise the shared decision only when its rule changes. If one already lists members, move them out the next time a round touches it.

# RL Lab — Architecture

**Status:** Draft · **Shape:** Single package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
One Python package, `rllab`. Worlds (Snake, and one tank world that serves both Fish tank and Predator–prey) all speak one parallel multi-agent interface from `core`. A named TOML configuration picks a world, a learner per team, and a step budget. `train` runs it and writes a self-contained run folder: settings, metric logs, checkpoints and recorded episodes. `evaluate` scores checkpoints and baselines on held-out seeds and exports per-seed tables. Significance tests on those tables are run with the `null-hypothesis-testing` skill. `reference` trains an established library's learner on the same worlds, so the 80% check can run. `viewer` replays recorded episodes, and `report` draws charts (following the `dataviz` skill) and keeps each world's lesson note.

Single package because this is one user, one install, no deployment. The seam that could later split out is the `[reference]` optional dependency group: only `reference` imports the reference library.

```mermaid
  train --> catalog
  evaluate --> catalog
  reference --> catalog
  viewer --> catalog
  catalog --> worlds & learners & baselines
  worlds --> core
  learners --> core
  baselines --> core
  report -->|reads files| evaluate
```

## Cross-cutting concerns
- **Repeatability (TRAIN-07, CORE-03):** see AD-10. A test trains two short runs and compares their logs byte for byte.
- **Speed (QR-01):** worlds step all agents with array maths; `train` steps K world copies in lockstep and does one batched forward pass (AD-09). Every run logs its wall-clock time, and a benchmark test fails if the default configurations project beyond 60 minutes.
- **Offline (QR-02):** no network calls anywhere; no experiment trackers.
- **Errors:** invalid actions, unknown names and missing seeds raise `ValueError` or `KeyError` with the allowed values in the message (CORE-04, CORE-07, TRAIN edge cases). Nothing is caught silently.
- **No RL library in learners (EVAL-06):** an import rule allows `stable_baselines3` and `gymnasium` only under `rllab.reference`.

## Decisions
### AD-01: Python 3.12 in one package
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** One user, one machine, no deployment (brief Constraints). The learners and the reference library are Python.
- **Decision:** One installable package `rllab` on Python 3.12, managed with uv.
- **Alternatives:** Several packages (core / learners / reference): no separate install or owner to justify it. Python 3.13: fine for the core, but the reference stack has the longest support record on 3.12.
- **Consequences:** Boundaries are folders and an import rule, not packages. The `[reference]` extra is the first split point if one is ever needed.

### AD-02: NumPy for worlds, PyTorch on CPU for learners
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** EVAL-06 asks for learners written from basic array and tensor operations. QR-01 and QR-02 require CPU-only training within 60 minutes. The user already knows NumPy and PyTorch.
- **Decision:** Worlds use NumPy only. Learners use PyTorch tensors, autograd, `nn` layers and optimisers, but no RL library. Torch runs on CPU.
- **Alternatives:** Pure NumPy with hand-written backpropagation: teaches calculus, not RL, and is slow. JAX: a new tool on top of a new subject.
- **Consequences:** Gradients are free; the RL-specific parts (replay, targets, advantages, clipping) are written by hand. Apple GPU (MPS) is not used, which keeps determinism simple.

### AD-03: Own parallel multi-agent world interface
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** CORE-01–CORE-08 need per-agent dictionaries, agents leaving mid-episode, and two teams, through one interaction for all worlds.
- **Decision:** `core.ParallelEnv`: `reset(seed) → {agent: obs}`, `step({agent: action}) → StepResult` with per-agent obs, reward and done. Its shape follows PettingZoo's Parallel API, but there is no dependency. Snake is the one-agent case.
- **Alternatives:** Gymnasium single-agent: can't express several fish or two teams without wrappers. PettingZoo itself: a heavier dependency, and its wrappers would hide the parts the user wants to write.
- **Consequences:** The reference library needs adapters (AD-06). Moving to PettingZoo later is mostly renaming.

### AD-04: One tank world for Fish tank and Predator–prey
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** worlds
- **Context:** PREY-01 reuses TANK-01–TANK-05 and TANK-09. The brief bets that the two fish worlds can share one tank.
- **Decision:** One `worlds.TankEnv` driven by `worlds.TankConfig`, with switches for the ball, food and energy, and the predator, and team sizes. "tank" and "prey" are two presets.
- **Alternatives:** Two separate worlds: double the physics code and tests, and the two would drift apart.
- **Consequences:** Movement, wall and vision code is tested once. The prey observation is the fish observation plus extra entries, so both presets have fixed but different observation sizes.

### AD-05: DQN for Snake, PPO-clip for the tank worlds, independent learners per team
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** learners
- **Context:** SNAKE-09 describes value learning from replay with a slow target. TANK-10 describes a continuous policy with limited update size and a policy shared by all fish. PREY-12 needs both sides learning at once.
- **Decision:** Snake uses DQN: a multilayer network, uniform replay, a hard-updated target network, Huber loss, and ε-greedy exploration decayed linearly. Tank worlds use PPO with the clipped objective and GAE. The policy is Gaussian with a learned log-std that doesn't depend on the state, and there is a separate value network. Each team has one shared policy, and each agent's trajectory is its own sample stream. Phase B runs two independent PPO learners, one per team, updated in the same loop.
- **Alternatives:** Double or duelling DQN, or prioritised replay: worthwhile improvements to try later, but not the core idea. SAC for continuous control: off-policy, and a different lesson from "learning a policy directly". MAPPO, with a centralised critic: more machinery than PREY-12 needs. Alternating which side trains: that isn't "at once".
- **Consequences:** One PPO implementation serves S2, S3 Phase A and S3 Phase B. Independent learners can cycle; PREY-14 and PREY-16 exist to show that.

### AD-06: Stable-Baselines3 as the reference, behind adapters
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** reference
- **Context:** EVAL-04 needs an established reference implementation of the same kind of learner for Snake, Fish tank and Predator–prey Phase A, trained with the same step budget.
- **Decision:** Stable-Baselines3 DQN and PPO, installed only through the `[reference]` extra and imported only by `reference`. Snake is wrapped as a Gymnasium env. The multi-fish worlds are wrapped as a vector env with one slot per fish, so a shared policy matches AD-05. A caught fish's slot reports done once, then sends a constant "out" observation with zero reward until the shared episode resets. The budget counts environment steps of real agents only.
- **Alternatives:** CleanRL: single-file scripts that get copied, not a library, which blurs EVAL-06. RLlib: very heavy for a laptop.
- **Consequences:** The "out" padding adds easy zero-reward samples to the reference's training only (see Risks). Reference runs use the same run-folder format, so `evaluate` scores them unchanged.

### AD-07: pygame-ce for the replay viewer
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** viewer
- **Context:** VIEW-03 and VIEW-04 need side-by-side playback, pause, single-step and speed control. QR-03 needs at least 30 fps with 29 bodies.
- **Decision:** A pygame-ce window that draws recorded `core.Frame`s, with keyboard controls.
- **Alternatives:** matplotlib animation: struggles to reach 30 fps with two panels and controls. A browser canvas: a second language and a file server for a single-user tool.
- **Consequences:** It's a desktop window, with no headless playback. Charts stay in matplotlib (AD-11).

### AD-08: Named TOML configurations and file-based run folders
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** TRAIN-01–TRAIN-06 need named configurations, settings saved with each run, logs readable while a run is going, and checkpoints. QR-02 requires everything offline.
- **Decision:** `configs/<name>.toml` is parsed with `tomllib` into frozen dataclasses (`catalog.RunConfig`). Each run writes the folder layout in Data. Logs are JSONL, flushed per line. Checkpoints use `torch.save`, and recordings are `.npz`.
- **Alternatives:** Hydra: powerful, but more to learn than the problem needs. TensorBoard or W&B: an extra tool, and W&B wants the network.
- **Consequences:** Everything can be inspected with a text editor or pandas. Comparing runs means reading folders, which `evaluate` and `report` do.

### AD-09: Batched in-process world copies
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** train
- **Context:** QR-01 sets a 60-minute limit on CPU. The per-step cost is dominated by Python overhead and small forward passes.
- **Decision:** `train` steps K copies of a world (default 8) in lockstep in one process, and does one batched forward pass over all agents in all copies. Each copy is seeded from the run seed and its index.
- **Alternatives:** Subprocess vector envs: their startup and messaging cost beats the gain for worlds this small. One copy: wastes most of each forward pass.
- **Consequences:** K is a configuration setting, and the S1 build measures throughput first. If a world still projects past 60 minutes, budgets are cut before reaching for a rented GPU (QR-02 forbids depending on one).

### AD-10: Seeding and determinism
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** system
- **Context:** CORE-03 and TRAIN-07 need exact repeats. EVAL-01 requires test seeds that are never training seeds.
- **Decision:** Each world owns one `np.random.Generator`, built from its reset seed. A run sets `torch.manual_seed`, `torch.use_deterministic_algorithms(True)` and a fixed `torch.set_num_threads(1)`. Training seeds and world-copy seeds stay below 1,000,000. Test episode `i` uses seed `1,000,000 + i`.
- **Alternatives:** Using all CPU threads: faster, but floating-point summation order can vary between runs.
- **Consequences:** One thread per run, so several seeds run as separate processes in parallel (`train_seeds`). Runs on a rented GPU are not expected to match (spec Assumptions).

### AD-11: Significance tests through the skill, charts per the dataviz skill
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** evaluate, report
- **Context:** EVAL-03 and PREY-15 name the `null-hypothesis-testing` skill. EVAL-05, NOTE-02 and PREY-14 name the `dataviz` skill.
- **Decision:** Every significance claim goes through the same flow. `evaluate` writes a per-seed `ComparisonTable` CSV. The test is run with the `null-hypothesis-testing` skill on that table. Its outcome is saved as an `evaluate.TestResult` JSON, which `report` reads. The rllab code contains no test procedure of its own. Every chart is drawn with matplotlib, following the `dataviz` skill's palette and mark rules.
- **Alternatives:** Hard-coding a t-test or permutation test in `evaluate`: duplicates the skill and hides its choices.
- **Consequences:** Running a comparison takes two steps: an rllab command, then the skill. `report.world_status` treats a missing TestResult as "not done".

### AD-12: Lesson notes as Markdown with generated blocks
**Status:** Proposed · **Date:** 2026-10-17 · **Scope:** report
- **Context:** NOTE-01 needs a draft with results filled in. Its edge case says my own writing must survive when the note is made again. NOTE-03 counts a world as done only when the explanation sections are written.
- **Decision:** `notes/<world>.md`. The generated results and charts sit between `<!-- rllab:begin <block> -->` and `<!-- rllab:end <block> -->` markers, which are rewritten on each run. Everything outside the markers is kept. An explanation section counts as written once it has 30 or more words besides its placeholder.
- **Alternatives:** Notebooks: diffs are awkward, and regenerating clobbers prose. Separate generated and handwritten files: the explanation ends up far from the evidence.
- **Consequences:** Deleting a marker detaches that block. `report` warns and leaves it alone.

## Risks and open questions
- **The 60-minute limit for the tank worlds (QR-01).** PPO with 8 fish, or 9 agents, may need more steps than 60 minutes allows. Mitigation: measure throughput in the first S2 milestone; tune K, network size and budget before tuning physics.
- **Reference "out" padding (AD-06)** gives Stable-Baselines3 easy extra samples, which may skew the 80% comparison either way. Mitigation: the reference check also reports the reference's score with padded samples counted in its budget. Decide in S2 whether the bar uses the stricter one.
- **Phase B may never settle (PREY-15).** This is an accepted outcome (PREY-16). Cross-play snapshots are saved from the start, so the failure can be explained.
- **The physical constants are starting values (spec Assumptions).** A world that is trivial or impossible is fixed by a spec change, not silently in code.

I've written a draft architecture in two files:
- **`docs/architecture.md`:** the design, with 12 proposed decisions (AD-01 to AD-12).
- **`docs/packages/rllab/contract.md`:** the public interface of each component.

All 75 spec requirements are covered, and the doc checks report no errors.

**Shape:** one Python package, `rllab`. It's split into 11 components, each a folder: `core`, `worlds`, `baselines`, `learners`, `catalog`, `train`, `evaluate`, `reference`, `viewer`, `report` and `cli`. Dependencies only point one way. The world code uses NumPy and has no PyTorch.

**Decisions that are expensive to reverse:**
- **AD-03:** worlds use our own multi-agent interface (one observation and action per agent, keyed by name), shaped like PettingZoo's but without the dependency. One interface covers Snake, 8 fish, and prey plus predator. The cost is that the reference library needs adapters.
- **AD-04:** one tank world, configured with switches (ball, food, predator), serves both S2 and S3.
- **AD-05:** DQN for Snake and PPO-clip for both tank worlds. All agents on a team share one policy. In Phase B, prey and predator are two independent PPO learners trained in the same loop.
- **AD-06:** Stable-Baselines3 is the reference. It's an optional install, and an import rule means only the `reference` component can use it, which keeps EVAL-06 honest. For the fish worlds, each fish gets a slot, and a caught fish's slot is padded with an "out" observation until the episode ends.
- **AD-11:** rllab writes the per-seed comparison tables, the `null-hypothesis-testing` skill runs the tests, and the results are saved for the notes. rllab has no test procedure of its own. Charts are drawn with matplotlib, following the `dataviz` skill.

**Assumptions I made (names, types and directions):**
- PyTorch runs on CPU only and single-threaded for exact repeats. Several seeds run in parallel as separate processes (AD-10).
- Test episodes use seeds 1,000,000 and up, and training uses seeds below that.
- Each run gets a folder `runs/<config>/seed-<n>/` with its settings, logs, checkpoints and recordings. Configurations are `configs/<name>.toml`.
- Training steps 8 copies of a world at once in one process (AD-09).
- The viewer is a pygame-ce desktop window.
- Lesson notes live in `notes/<world>.md`. Generated blocks sit between marker comments, and anything outside them is yours. An explanation section counts as written at 30 words or more.
- The Phase B prey start from the Phase A checkpoint, set in the configuration.

**Open questions and risks:**
1. **The one-hour limit for the tank worlds.** This is the biggest unknown. The first S2 milestone measures throughput before anything else.
2. **Padding in the reference comparison.** The "out" padding gives the library's PPO easy extra training samples. The reference check reports two numbers (padded steps counted in its budget, and not). I'd pick which one is the bar during S2.
3. **Contract length.** At 280 lines it's over the 200-line guide for one contract. I recommend staying a single package anyway, since build agents read single sections, and reconsidering if S2 grows it.
4. **`dataviz` isn't installed in the project.** It's available in this session, but the checks flag it because it isn't installed in the project or the dev-team plugin. Later skills may not find it, so it may need installing there.

The spec's change to Approved isn't committed yet. Your setup seems to commit automatically after each turn, so I've left it alone.
