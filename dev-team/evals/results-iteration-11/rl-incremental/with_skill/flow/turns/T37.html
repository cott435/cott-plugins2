# RL Lab — Architecture

**Status:** Approved · **Shape:** Single package · **Last updated:** 2026-10-18 · **Spec:** [spec.md](spec.md)

## Overview
One Python package, `rllab`. Every environment and every agent sits behind the protocols in `core`. The training loop, evaluation, run records, curves and replay viewer use only those protocols, so they never import Snake. A training run plays seeded games with a hand-written DQN agent. Every 50 games it scores the agent greedily on 100 held-out seeds, and it rewrites its JSON record after each of those checks. The study command trains the full agent and its 3 ablations, 5 seeds each, scores both baselines, and runs the `null-hypothesis-testing` comparisons. It then writes a report and a chart for the learner's notes page. The notes command reads that page and reports missing sections and broken links; no code ever writes it (AD-10). Charts are drawn only from saved records. A replay re-plays a saved agent on a seed, so it never depends on frames saved during training.

## Data
- **Seeds (AD-04):** training game seeds are drawn from `[0, 1_000_000)` by a generator built from the run seed. The 100 held-out seeds are fixed at `1_000_000–1_000_099`. The two ranges can't overlap (EVAL-01), and every agent and baseline is scored on the same held-out games (BASE-03, EVAL-03).
- **Run folder (AD-05):** `runs/<name>/record.json` holds the config, one score and length per training game, the evaluation points (mean, spread and per-seed scores), the average loss per 50 games, the status and the elapsed time. Next to it, `runs/<name>/agent.pt` holds the state dict, sizes and config. Baselines get `runs/baseline-random/` and `runs/baseline-scripted/`, each with one evaluation point. Study runs are named `<variant>-s<seed>`, for example `no-memory-s3`.
- **Study output:** `runs/study-<env>/report.md` (every comparison with its test result, missing or incomplete runs, and the finding line ABL-05 asks for) and `runs/study-<env>/curves.png`. ## Cross-cutting concerns
- **Errors:** the domain errors are `core.InvalidMoveError` and `core.GameOverError` (ValueErrors), `core.EnvCheckError`, `runs.RunExistsError` and `agent.NonFiniteLossError`. `train` catches the last of these and other failures, marks the record `failed` with the game and step, flushes it and re-raises it, so the log so far survives.
- **Speed (QR-01, QR-02):** each run uses one CPU thread (`torch.set_num_threads(1)`). The study runs up to `os.cpu_count() - 1` runs at once in separate processes (AD-03). The default of 1,000 training games is checked against the 60-minute limit by a timing test on the learner's laptop.
- **Reproducibility (QR-05, SNAKE-08, REPLAY-04):** no global random state anywhere. Each environment, agent and run owns a `np.random.Generator` or `torch.Generator` built from its seed. Deterministic torch algorithms and a single thread give identical logged results on the same machine (AD-04).
- **Hand-written learning (QR-03):** `agent` may import `torch` and `numpy` only. No gymnasium, stable-baselines or other RL library is a dependency, and a dependency check enforces it (`build-setup`).

## Decisions
### AD-01: Python 3.12, one package `rllab`
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** The user said "Single package, go with your recommendation." (UR-28). This is research code with one user, one laptop and one install (brief Constraints). The user already knows Python, NumPy and PyTorch (UR-07).
- **Decision:** One package, `rllab`, on Python 3.12, with one folder per component.
- **Alternatives:** Several packages (core, envs, agents): no separate install, release or runtime justifies the split, and the core's seam is already named. Python 3.13: PyTorch CPU wheels and pygame-ce lag on new versions.
- **Consequences:** Set `requires-python = ">=3.12,<3.13"`. A later split moves the environment-agnostic folders as they are, with their contract sections.

### AD-02: A hand-written DQN on the 11 facts; PyTorch only for the network and its gradients
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** The user called Snake a "Good first env for DQN-style value learning" (UR-06) and said "I want to write DQN from scratch" (UR-08). QR-03 rules out RL libraries but allows array math with automatic gradients. AGENT-01–AGENT-05 fix the algorithm: a learned value per move, ε-greedy decaying 1.0 → 0.01 over the first half of the games, 100,000 remembered steps, discount 0.9, and a frozen copy refreshed every 1,000 steps.
- **Decision:** `agent.DQNAgent` is written by hand: the replay memory (a NumPy ring buffer), the ε schedule, the target computation, the frozen-copy refresh, the Huber-loss update and the ablation switches. Only the value network uses PyTorch: an MLP of 11 → 256 → 3 built from `torch.nn.Linear`, trained by autograd and `torch.optim.Adam` (lr 1e-3, batch 64). It takes one update per environment step once a full batch is remembered.
- **Alternatives:** NumPy only, with backprop written by hand: it teaches more about gradients, but that isn't the lesson the brief wants and it adds bug surface; it could come later as an exercise. A Q-table (2¹¹ × 3 entries): it would learn Snake well, but it isn't DQN, and with no frozen copy or replay memory to switch off, the ablations would mean nothing.
- **Consequences:** The network is the only library-backed part, so the "from scratch" check (QR-03) reduces to reading `agent/`. The network size, learning rate, batch size and Huber loss are choices the spec doesn't fix, and they live in `AgentConfig` with these defaults.

### AD-03: CPU only; one thread per run, separate processes for the study
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** The user's words are "Laptop CPU only" (UR-13). QR-01 limits one run to ≤ 60 minutes and QR-02 the 20-run study plus baselines to ≤ 10 hours. A network this small gains nothing from torch's thread pool, and extra threads hurt reproducibility (QR-05).
- **Decision:** Install PyTorch from the CPU wheel index; the code never calls CUDA or MPS. Each run calls `torch.set_num_threads(1)`. `study` spreads its runs over `ProcessPoolExecutor(max_workers=os.cpu_count() - 1)`, with each run in its own process and writing its own folder.
- **Alternatives:** Running the study serially: 20 runs at up to 60 minutes each could exceed 10 hours. Batching several agents into one process (vectorised): faster, but it tangles the hand-written agent and makes ablations harder to read.
- **Consequences:** A run's time doesn't depend on the other runs, as long as there are enough cores. On a 4-core laptop the study takes about 7 rounds of 3 runs. QR-02 holds only if one run takes under about 80 minutes when 3 run in parallel, so the timing test measures that case too.

### AD-04: Seeds owned per object, fixed held-out range
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** SNAKE-08, CORE-01, AGENT-06, REPLAY-04, REPLAY-05 and QR-05 need same seed → same game. EVAL-01 needs the training and held-out seeds never to overlap.
- **Decision:** `Env.reset(seed)` builds the environment's generator from the game seed. `Agent.reset(seed)` reseeds any randomness the agent uses while playing (the random baseline). `DQNAgent` builds its exploration, sampling and weight-initialisation generators from the run seed. The held-out seeds are `evaluate.EVAL_SEEDS = range(1_000_000, 1_000_100)`, and training seeds come from `[0, 1_000_000)`. Deterministic torch algorithms are switched on in every run.
- **Alternatives:** One global seed set at start-up: any extra random call anywhere would shift every later game. Hashing training seeds: overlap with the held-out seeds would become unlikely rather than impossible.
- **Consequences:** A replay of a saved agent on a held-out seed reproduces its logged evaluation score (REPLAY-05). Results are reproducible on one machine, not across machines (QR-05 asks only for the first).

### AD-05: Run records as one JSON file per run, rewritten atomically
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** LOG-01–LOG-04 decide what a record holds, and LOG-05 needs it on disk at least after every evaluation point. At 1,000 games with 20 evaluation points of 100 scores, a record stays well under 1 MB. CURVE-05 needs charts in ≤ 10 seconds from records alone.
- **Decision:** `runs.RunWriter` keeps the record in memory. After every evaluation point, and when the run finishes or fails, it rewrites `record.json` through a temporary file and `os.replace`. The agent is saved as `agent.pt` (state dict, observation size, move count, config). Creating a run whose folder already exists raises `RunExistsError` (LOG edge case).
- **Alternatives:** SQLite: queryable, but one file per run is simpler to read, diff and delete. CSV per game plus JSON settings: two formats to keep in sync. Parquet: adds pyarrow to read a few kB.
- **Consequences:** A crash loses at most the games since the last evaluation point, which LOG-05 allows. Reading a record means reading the whole file, which is fine at this size.

### AD-06: The environment draws a toolkit-free `Frame`; the viewer is pygame-ce
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** The user chose "Go with pygame-ce for the replay viewer." (UR-29). CORE-04 has every environment draw its own frame. REPLAY-03 needs pause, single step and 1–30 fps, and CORE-06 needs the viewer to work with any environment.
- **Decision:** `Env.render()` returns a `core.Frame`: a grid of cell codes, a colour for each code, the step number and the score. Environments never import a GUI toolkit. `replay.show` draws frames in a pygame-ce window: space pauses, → steps one frame, and ↑/↓ change the speed between 1 and 30 fps. Its clock limits the frame rate.
- **Alternatives:** A Matplotlib animation: no extra dependency, but timing at 30 fps and keyboard control are unreliable across backends. A Tkinter canvas: in the standard library, but the event loop and timing take more code. A terminal view: no colour grid on every terminal.
- **Consequences:** One extra dependency, used only by `replay`. Frames are plain data, so replay tests check frames without opening a window.

### AD-07: Learning curves with Matplotlib from saved records

### AD-09: The comparisons use each side's finished seeds; only an ablation with a failed seed is missing
**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
- **Context:** test-planning found that `study.compare_scores` required the full agent to be 5 × 100, while the spec's EVAL edge case leaves a stopped run out of the final comparison and names it incomplete, and `run_study` fails only when the full agent has no finished run. - **Consequences:** A study with a stopped full-agent run still compares, with less power, and the report says how many seeds were used. Pairing per game on seed means matches TC-08's test, so the `null-hypothesis-testing` design holds.

**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system

- **Consequences:** EXPL-01–EXPL-03 are covered by a check of the learner's page, not by generated text. The check judges structure (headings present and non-empty, links resolve), never what the learner wrote.

# Idea: Fish Tank

**Status:** Specced · **Last updated:** 2026-10-18 · **Brief:** [../brief.md](../brief.md)
**Spec:** TANK-01–TANK-10, PG-01–PG-12, TWIN-01–TWIN-02, CORE-07–CORE-09, BASE-04, ABL-06–ABL-08, CURVE-06, EXPL-04; CORE-02–CORE-04, BASE-01, EVAL-02–EVAL-04, ABL-04, ABL-05, CURVE-03, REPLAY-02, EXPL-03, QR-01–QR-03 (changed)
> Record of why, frozen when specced. The spec is current: [spec.md](../spec.md)

## In one sentence
This adds a second environment, a circular tank where several fish learn to steer away from a bouncing ball, so the learner can build policy-gradient methods up to PPO, with continuous control, on the shared core Snake built.

## The problem
Snake teaches value learning over a few discrete moves. With continuous moves (how hard to turn, how fast to swim) there is no list of moves to score, so the agent must learn its policy directly. Policy gradients start there and usually end at PPO, each step fixing a failure of the one before. Building them in order, in a game you can watch, shows why PPO exists.

## Who it's for
The same learner as the brief, once Snake (S1) is done and they move on from value learning to policy learning.

## How it fits
- **Serves:** Goal 1 (explain why each part matters), Goal 2 (beats random and scripted agents), Goal 3 (replay), Goal 4 (reuses the shared core)
- **Touches:** CORE-01–CORE-06 (several agents at once, continuous moves; CORE-03's "number of allowed moves"); BASE, EVAL, ABL, CURVE-03, REPLAY, EXPL, LOG-01 (worded for Snake and its DQN); QR-01–QR-03, QR-05 (Snake-only limits; the hand-written rule). SNAKE and AGENT stay as they are.
- **Brief changes:** Not doing narrowed: the fish tank is planned now; only environments after it wait.
- **Stage:** New S2 (roadmap stage on acceptance), built after S1 is done.

## Recommended direction
**The tank.** A circular tank with one ball bouncing off its wall. Several fish swim in it with continuous movement: each step every fish chooses how to steer and how fast to swim. When the ball touches a fish, that fish is removed. The game ends when every fish is gone. Fish are rewarded for staying alive, so a good fish survives as long as possible.

**What a fish sees.** Only nearby things, through about 8 sensor rays spread evenly around it. Each ray reports how far away the wall, the ball and other fish are along that direction, up to a short range. Nothing beyond the rays' reach is visible.

**One brain, many bodies.** All fish share one policy, each acting on its own observation. Fish don't block or crowd each other, so each is an independent copy of one single-agent problem: the stage stays about policy gradients, not game theory. The build starts with one fish and adds more once it learns.

**The ladder.** The learner writes three agents by hand, each one built on the previous one: REINFORCE (plain policy gradient), then actor-critic (a learned value estimate cuts the noise), then PPO (a limit on how far each update moves the policy). Each added piece has an off switch, as in S1, so turning it off shows what it was fixing.

**The core grows.** The shared core learns to handle continuous moves and several agents at once. Snake keeps running exactly as before.

**Optional extra.** A discrete twin of the tank with 8 compass moves, run by S1's unchanged DQN, to show what continuous control adds. The stage is done without it.

## Alternatives considered
- PPO only — skips the failures that explain each piece, which is the point of the lab.
- Fish that interact (crowding, blocking) — a genuinely multi-agent problem: richer, but a different lesson.
- A curriculum (the ball speeds up, more balls appear) — adds tuning without a new idea; revisit if the tank is too easy.
- A list of the nearest few objects as the observation — rays are fixed-size and closer to "sees only nearby things".

## What success looks like
- Each rung's learning curve beats a random fish and a scripted fish on the same seeded games.
- PPO learns better or more steadily than the rung below it, and turning off each piece visibly hurts, or the notes record that it didn't.
- A replay shows trained fish dodging the ball.
- Snake's results are unchanged after the core grows.

## What we're betting on
- About 8 short rays carry enough information to dodge one ball.
- A shared policy learns well from several independent fish, and the extra fish speed learning up rather than confusing it.
- The full ladder trains within the brief's hour per run on a laptop CPU.

## Not doing
- Fish that affect each other — a multi-agent problem; out of scope.
- A curriculum of harder tanks — not needed to learn the lesson.

## Open questions
Resolved in the spec.
# RL Lab

**Status:** Accepted · **Last updated:** 2026-10-18

## The problem
Reinforcement learning (RL) is how an agent learns by trial and error from rewards. It is easy to read about and hard to really understand. Library code hides the parts that matter, and tutorials stop once the agent "works". The fastest way to learn it is to build small agents from scratch, in small 2D game environments, where each one teaches one idea and you can see it learn.

## Who it's for
Me: a solid Python programmer with some NumPy and PyTorch, who knows the basics of Q-learning (learning the value of each action in each state) and wants to learn RL by building it.

## Goals
1. For each environment, I can explain in my own words why the agent learns, and why each part of the algorithm matters.
2. Every agent is shown to learn: its learning curve beats a random agent and a simple scripted agent on the same games.
3. I can watch a replay of any trained agent playing.
4. A new environment reuses a shared core (environment interface, training loop, logging, replay viewer, learning curves) instead of starting over.

## Constraints
- Laptop CPU only, and under about an hour of training per environment.
- Free tools only.
- Evenings and weekends, a few weeks per environment, no deadline.
- Learning algorithms are written from scratch, not taken from a library.

## What success looks like
- The first environment, Snake, has an agent whose learning curve clearly beats both baselines, plus a replay of it playing.
- Turning off a key part of the agent visibly hurts its learning, and I can say why.
- The second environment, whatever it is, plugs into the shared core with small changes.

## What we're betting on
- Small, hand-picked descriptions of the game state ("danger ahead", "food to the left") are enough for an agent to learn well within an hour on a CPU.
- A shared core designed while Snake is the only example will still fit the next environment without a rewrite.
- Writing the algorithms myself teaches more than tuning a library would.

## Not doing
- Learning from raw pixels or the full grid image: much slower, and not the lesson I'm after.
- Comparing against library implementations, for now: a later step, once my own version works.
- Fancy views such as heatmaps of the agent's values: learning curves and replays are enough.
- Planning environments beyond the second, the fish tank: each next one is chosen once the one before is built.
- Mastering Snake: agents that see only nearby danger tend to trap themselves, and that limit is fine.

# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. 186	  - Given finished runs of all 3 rungs, when the ladder comparison runs, then the report says, for rung 2 against rung 1 and rung 3 against rung 2, "better" or "no detectable difference", with the test result and each rung's spread.

188	  - Given a ladder report where rung 3 shows "no detectable difference", when the stage is checked, then it passes, and the notes page records it as a finding (EXPL-04).
189	- **PG-12** A trained rung can be saved and loaded back, and the loaded agent picks the same moves.
190	  - Given a saved rung, when it is loaded and plays an evaluation game with seed 11, then it makes exactly the same moves as before saving.

193	- A game ends by the time limit → returns and advantages for the surviving fish stop at step 1,000; nothing is counted beyond it.
194	- A game where every fish is removed on the first step → the agent learns from those steps alone; it does not stop.

198	### Ablation switches (`ABL`)
199	**Serves:** Goal 1
200	**Stage:** S1
201	**Behavior:** Each environment has three switches, each turning off one part of its top agent, so the learner can train the agent without it and compare. On Snake they turn off the value-learning agent's memory, frozen copy and exploration decay; on the tank they turn off the limited-update agent's value estimate, update cap and advantage rescaling. Each switch is set per run and recorded in the run's log. The comparison of each ablated agent with the full agent is judged by a hypothesis test.
202	
203	**Requirements**
204	- **ABL-01** With the memory switch off, the agent learns from only the step it just took, with no remembered steps.
205	  - Given memory off, when the agent learns, then each update uses exactly the latest step.
206	- **ABL-02** With the frozen-copy switch off, the agent builds its targets from its current value estimate.
207	  - Given frozen copy off, when a target is built, then it uses the current estimate's best next value, which changes after every update.
208	- **ABL-03** With the exploration-decay switch off, the agent's random-move probability stays fixed at 0.1 for the whole run.
209	  - Given decay off, when the agent picks moves at any point in training, then about 10% are random.
210	- **ABL-04** Each ablated agent is compared with the full agent of its environment (Snake: the value-learning agent; the tank: the limited-update agent) with the `null-hypothesis-testing` skill, given the final evaluation scores of both (5 training seeds each, on the same 100 held-out games); the ablation counts as hurting learning only if the full agent's scores are higher at a 5% significance level after correcting for the 3 comparisons in that environment.
211	  - Given finished runs of the full agent and the 3 ablated agents of one environment, when the study is run, then each ablation is reported as "hurts learning" or "no detectable difference", with its test result.
212	- **ABL-05** When no switch hurts learning, the study is still complete: the result is recorded as a finding in the notes, and S1 doesn't count as failed (nor S2, for the tank's switches).
213	  - Given a study report where all 3 ablations show "no detectable difference", when the stage is checked, then it passes, and the notes page records that no switch hurt learning as a finding (EXPL-02).
214	- **ABL-06** With the value-estimate switch off, the limited-update agent weights each move by the discounted return that followed it, as rung 1 does, and learns no value estimate.
215	  - Given value estimate off, when a fish's rewards were +1, +1, 0, then its moves are weighted 1.99, 1 and 0 before rescaling.
216	- **ABL-07** With the update-cap switch off, the limited-update agent still makes its 10 passes over each game's steps, with no limit on how far a move's probability can move.
217	  - Given cap off and a move already 1.3 × as likely as when played, with a positive advantage, when the next pass updates, then that move still becomes more likely.
218	- **ABL-08** With the rescaling switch off, the limited-update agent uses each game's advantages as built, without rescaling.
219	  - Given rescaling off, when a game's advantages are used, then they equal the advantages as built.
220	
221	**Edge cases & errors**
222	- Several switches are off in one run → allowed; the run's log records every switch's state.
223	- An ablated run fails before finishing → the study reports that ablation as missing, never as "no detectable difference".
224	- A switch is set on an agent that doesn't have that part (the tank's switches on rungs 1 or 2's missing pieces, Snake's switches on a tank rung) → the run is refused at start-up, naming the switch and the agent.

227	**Serves:** Goal 2
228	**Stage:** S1
229	**Behavior:** Two non-learning agents play the same seeded games as the learning agents in each environment: a random agent and a simple scripted agent. Their scores set the bars every learning agent's curve must clear.
230	
231	**Requirements**
232	- **BASE-01** The random agent picks each move uniformly at random from the allowed moves: one of the choices, or each control anywhere within its limits.
233	  - Given 10,000 moves by the random agent on Snake, when counted, then each of the 3 moves is picked 30–37% of the time.
234	  - Given 10,000 moves by the random agent in the tank, when counted, then turns are spread evenly over −15° to +15° and speeds over 0 to 0.3, each tenth of either range holding 9–11% of moves.
235	- **BASE-02** On Snake, the scripted agent moves toward the food along the axis with the larger gap, and when that move is immediately fatal it takes any non-fatal move, preferring straight.
236	  - Given food straight ahead and no danger ahead, when the scripted agent moves, then it goes straight.
237	  - Given food straight ahead and a wall ahead, when it moves, then it turns to a side that is free.
238	- **BASE-03** Both baselines are scored on the same 100 held-out games as the learning agent.
239	  - Given the 100 held-out seeds, when each baseline plays them, then each records one score per seed, and its mean and spread are logged.
240	- **BASE-04** In the tank, the scripted fish swims at full speed, turning as far as it can away from the ray that sees the ball closest; with no ball in reach it swims straight, and when the wall is within 1 unit straight ahead it turns as far as it can toward the side whose rays see more room.
241	  - Given the ball seen only on the front-left ray and no wall within 1 unit ahead, when the scripted fish moves, then it turns −15° (to the right) at speed 0.3.
242	  - Given no ball in reach and the wall 0.5 units straight ahead with more room on the left, when it moves, then it turns +15° at speed 0.3.

245	- Every move is fatal → the scripted agent goes straight and the game ends.
246	- The scripted fish sees the ball equally close on two rays → it turns away from the one further left.
247	- The scripted fish sees the ball and the wall ahead at once → it avoids the wall.

249	### Evaluation (`EVAL`)
250	**Serves:** Goal 2
251	**Stage:** S1
252	**Behavior:** Every training run is checked at regular points on a fixed set of held-out games it never trains on, with exploration off, and ends with a final check on all 100 held-out games. Each learning agent's final check is compared with both baselines of its environment on those same games.
253	
254	**Requirements**
255	- **EVAL-01** Training games and evaluation games come from separate seed sets that never overlap.
256	  - Given any training run, when its training and evaluation seeds are listed, then no seed appears in both.
257	- **EVAL-02** During training the agent plays held-out games at regular points with exploration off and its mean score is logged: on Snake every 50 training games over all 100 held-out games; in the tank at every tenth of training over the same 20 of its 100 held-out games. Every run ends with a final check over all 100.
258	  - Given a Snake run of 1,000 training games, when it ends, then 20 evaluation results are logged, each over the same 100 seeds.
259	  - Given a tank run, when it ends, then 10 evaluation results over the same 20 seeds and one final result over all 100 seeds are logged.
260	- **EVAL-03** Each learning agent's final evaluation scores are compared with each baseline's scores of its environment with the `null-hypothesis-testing` skill, given 5 training seeds × the 100 held-out games for the agent and the same 100 games for each baseline; the agent beats a baseline only if its scores are higher at a 5% significance level after correcting for every comparison in that environment (2 on Snake: the full agent against 2 baselines; 6 in the tank: 3 rungs against 2 baselines).
261	  - Given finished runs of the full agent and both baselines, when the comparison is run, then the report says, for the random agent and for the scripted agent, whether the agent beats it, with the test result.
262	  - Given finished runs of all 3 rungs and both tank baselines, when the comparison is run, then the report says, for each of the 6 pairs, whether the rung beats the baseline, with the test result.
263	- **EVAL-04** On Snake the full agent's learning curve beats both the random baseline and the scripted baseline; in the tank every rung's learning curve beats both the random fish and the scripted fish.
264	  - Given the EVAL-03 report for Snake, when it is read, then the agent beats both baselines.
265	  - Given the EVAL-03 report for the tank, when it is read, then each of the 3 rungs beats both baselines.

268	- A run stops early → its completed evaluation points are kept and shown; it is left out of the final comparison, which names it as incomplete.
