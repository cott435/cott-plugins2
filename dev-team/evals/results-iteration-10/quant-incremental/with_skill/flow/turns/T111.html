# Shape: single package or multi-package

Read before proposing the shape, and when weighing Grow.

- **Single package** (proof of concept, library, one service, research code): `docs/architecture.md` plus `docs/packages/<pkg>/contract.md`. Components are modules, one subfolder each; decisions live in the one doc. 1-3 pages.
- **Multi-package** (a platform or monorepo of separately installed or deployed packages): a root `docs/architecture.md` system map with dependency rules, System pipelines and every decision (each scoped `system` or a package id), plus `architecture.md` and `contract.md` per package. Choose multi-package only for a real boundary: separate install, versioning or deployment, different runtimes or owners, or a dependency stack the rest shouldn't carry. 107	### AD-01: Python backend and TypeScript `web` in separate packages, one repo
108	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
109	- **Context:** UR-09: the user wants "a TypeScript + React browser frontend over a Python backend (HTTP and WebSocket)". Two runtimes share no code or types, which is a real package boundary. The CLI, the loader and the server share the store, the run machinery and every query (SYNC-07, RUNS-03).
110	- **Decision:** The Python backend and the browser app `web` are separate packages in one repo. AD-13 and AD-14 set how the Python side splits. Inside each Python package, component directions are enforced with import-linter.
111	- **Alternatives:** One package with the frontend inside it: it mixes two toolchains in one build.
112	- **Consequences:** `web` builds against frozen JSON samples of the API, so both sides can build at once. The seam that could become a package later is `sources` (vendor clients).

115	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
116	- **Context:** UR-09 names TypeScript + React over Python. The data work (pandas, `yahooquery`, `exchange_calendars`) is Python.
117	- **Decision:** Python 3.12 with `uv`. Pandas and NumPy for frames, pandera schemas for every frame that crosses a component, Pydantic 2 models for every type the API serves. TypeScript 5, React 18 and Vite with `pnpm`, and TanStack Query for HTTP caching.

121	### AD-03: Sharadar as the primary source: SEP, ACTIONS, TICKERS and SP500
122	**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
123	- **Context:** UR-04 and UR-14: Sharadar is the user's subscription and the primary source. UR-15: "Use whichever of its tables cover prices, corporate actions, tickers and S&P 500 membership." Checked against DATA-01–DATA-03, DATA-05 and QR-03. Sharadar's prices page (sharadar.com/prices, read 2026-10-18) says the Prices product includes stock prices with "History back to December 1997", "active and delisted securities", split-adjusted OHLC with `closeunadj`, corporate actions ("splits, dividends, spinoffs, acquisitions, delist reasons and ticker changes"), a tickers table keyed by `permaticker`, and "Current and historical S&P500 index constituents" from January 1998. It names the Sharadar API (`api.sharadar.com/v1.0/data/...`) as the access route. Two things conflict or stay open. QuantRocket's Sharadar catalog (quantrocket.com/data, read 2026-10-18) says the S&P 500 constituents dataset "is bundled with Sharadar US Company Fundamentals". Nasdaq Data Link's SEP database page lists only SEP, ACTIONS, TICKERS, METRICS and INDICATORS. So whether this user's subscription returns SP500, and through which API, is a question about their own account.
124	- **Decision:** Four Sharadar tables: stock prices (SEP), corporate actions (ACTIONS), tickers (TICKERS) and S&P 500 constituents (SP500), behind `sources.PrimarySource`. Prices are stored unadjusted. Unadjusted open, high and low are derived as split-adjusted OHLC × (`closeunadj` / `close`) (AD-07). Incremental refreshes (SYNC-02) fetch rows whose `lastupdated` is after the last refresh. The universe is limited to companies that appear in SP500, which also leaves out ETFs, OTC listings and preferreds (DATA-03).
125	- **Alternatives:** Membership from a free list (Wikipedia's change history): unverifiable effective dates and no company identities, so it is a fallback only if PB-01 fails. Nasdaq Data Link's `nasdaqdatalink` client instead of Sharadar's API: used instead if PB-01 shows the user's key works only there.
126	- **Consequences:** Every Sharadar-specific field name lives in `sources.sharadar`, so a change of access route touches one module. Storing unadjusted values keeps Sharadar's re-adjustment of history after each split from looking like a revision.
127	- **Probe:** PB-01 — Does the user's Sharadar subscription return SP500 with effective-dated additions and removals back to 1998-01-02, including the ten DATA-04 names, and through which API? Do SEP rows carry `closeunadj` and `lastupdated`?

130	**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
131	- **Context:** UNIV-03 and UNIV-04 need one permanent identifier per company across ticker changes. BUD, DNA and WB now belong to other companies. Sharadar's tickers table has a `permaticker` primary key (sharadar.com/prices, read 2026-10-18). The docs don't say how a legal entity that survives a merger under another name is keyed. The spec (DATA-04, Open questions) ends Schering-Plough on 2009-11-03, although its legal entity continued as Merck & Co.

138	**Status:** Proposed · **Date:** 2026-10-18 · **Scope:** `eqdata`
139	- **Context:** UR-05: "cross-checked against Yahoo Finance through yahooquery". CHECK-01–CHECK-07, QR-03 (free access only) and QR-04 (at most 100 stocks per standard run). The spec's assumption says Yahoo adjusts dividends its own way, so the comparison uses each source's unadjusted prices, raw dividends and splits. yahooquery's official guide (yahooquery.dpguthrie.com) could not be reached on 2026-10-18 (404). 145	### AD-06: One SQLite file in WAL mode, with bitemporal rows
146	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `eqdata`
147	- **Context:** SYNC-05 (a failed refresh leaves the data as before), DATA-05 (every value keeps the date it was first known and replaced), RET-04 (as-of results), the VIEW edge case (the app keeps reading during a refresh), RUNS-03 (a CLI run visible in the app), QR-01 and QR-02. About 1,500 companies × up to 7,200 trading days of prices, so roughly 10 M rows.
148	- **Decision:** One SQLite file in WAL mode holds everything `eqdata` stores; the eqdata Data section lists the tables. Every market-data row has `known_from` and a nullable `replaced_on`, and a revision closes the old row and inserts a new one. A refresh downloads and cleans into staging tables, checks the staged rows against their pandera schemas, and commits the merge in one transaction. Readers in other processes keep seeing the last committed state until then. The validation run against the independent source (SYNC-04) follows the commit, so its findings describe committed data.
149	- **Alternatives:** A DuckDB file: faster scans, but one process can't read while another writes, so the app would block during every refresh. Parquet files with a swapped manifest: atomic, but findings and runs would need a second store, and revisions mean rewriting partitions.
150	- **Consequences:** Single-writer: SYNC-06's lock matches SQLite's model. The EDA reads through pandas or DuckDB's SQLite scanner. Query speed rests on indexes. If QR-02's benchmark fails, the fallback is a per-company price cache rebuilt on commit, not a store change.

152	### AD-07: Prices stored unadjusted; returns and adjusted levels computed at query time
153	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `eqdata`
154	- **Context:** RET-02–RET-05: total return includes dividends, ignores splits, and uses no event after the as-of date D. Back-adjusted vendor prices change whenever a later split lands, so they leak the future into earlier dates.
155	- **Decision:** For each day T, `r_T = (C_T × s_T + d_T × s_T) / C_{T−1} − 1`. Here `C` is the unadjusted close, `s_T` the split ratio effective on T (new shares per old, 1 otherwise), and `d_T` the cash dividend per post-split share going ex on T. Adjusted price levels as of D are back-adjusted using only events with ex-date ≤ D. A day with no close is a gap with no return (RET-07).
156	- **Alternatives:** Store Sharadar's `closeadj`: it embeds every future split and dividend, which breaks RET-04 and RET-05. Store pre-computed returns: fine for speed, but a revision would then need two rows changed in step.
157	- **Consequences:** RET-02 and RET-03's worked examples are the unit tests. The dividend convention on a split day is fixed here and checked by PB-01's samples.

167	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** `eqdata`
168	- **Context:** SYNC-06 (one refresh at a time, the refusal names the running one), SYNC-07 (an app-started run runs exactly as from the CLI), RUNS-01–RUNS-04 (live progress within 2 s, CLI runs visible, history kept, catch-up after reconnect).
169	- **Decision:** The server starts a run through `eqdata.launch_run`, which spawns the same `eqdata refresh|validate|eda` command the researcher types. A run takes the lock (a `runs` row with status `running` and a PID, released on exit and broken if the PID is dead) and appends numbered `RunEvent`s to the store. The server polls new events every 250 ms and pushes them over `/ws/runs`. A connection first gets the events after its `since`, then the current state of every running run, stamped with the latest `seq` already written, then each new event. A reconnecting client sends the highest `seq` it received and misses nothing.
170	- **Alternatives:** Runs as server background tasks: CLI runs would be invisible and the two paths would differ. A message broker: one process too many for one user.
171	- **Consequences:** Run events are the only progress channel, so the CLI's own progress output reads them too.

This adds candidate price and volume features, and a machine-learning study of whether they predict next month's market-removed returns of S&P 500 members, so that every claim that a feature carries information has passed a null-hypothesis test.

# eqdata — Architecture

**Package:** eqdata · **Status:** Approved · **Last updated:** 2026-10-18 · **System:** [../../architecture.md](../../architecture.md)

## Overview
`sources` fetches from Sharadar and Yahoo. `sync` cleans what Sharadar returns, stages it and commits it to `store` in one transaction, then calls `check`. `universe` and `returns` answer as-of queries from `store`. `check` and `eda` raise findings through `findings`. Every long job runs inside `runs`, which holds the lock and writes progress events. `cli` is the front door. The separate `server` package calls only the public API in [contract.md](contract.md): the query functions, `launch_run`, which spawns the CLI (AD-09), and `run_snapshot` and `events_after` for live progress (AD-13). The separate `study` package reads the as-of loader through the same API and saves its report through `reports`, which also holds the EDA report and serves both to `server` (AD-14, AD-15).

## Data
- **Sources:** Sharadar SEP, ACTIONS, TICKERS and SP500 (AD-03). Yahoo via `yahooquery` for the sample only (AD-05). Researcher CSVs under `reference/` (AD-10).
- **Tables** (all keyed by `company_id`, AD-04): `companies`, `tickers` (company, ticker, from, to), `membership` (company, effective_from, effective_to), `prices` (unadjusted OHLCV), `actions` (splits, dividends, ticker changes, mergers, acquisitions, delistings). Each has `known_from` and `replaced_on` (AD-06). Also `findings`, `runs`, `run_events`, `source_diffs` (run, company, date, return and close differences; AD-12), and staging copies of the market tables.
- **Cleaning (SYNC-03):** duplicate (company, date) rows keep one, and the count goes to the summary. A changed past value closes the old row (`replaced_on`) and inserts the new one, listed as a revision.
- **Known-on queries (DATA-05):** as-of functions take `as_of` (market date: events after it are ignored) and an optional `known_on` (system date: rows not yet known, or already replaced, then are ignored).
- **Sampling (CHECK-01):** at least 2 companies per calendar year from 1998, drawn from members Yahoo still carries, then filled at random to 100. The seed is recorded in the run summary.
- **Reports:** one `report.json` (an `eqdata.Report`: sections of tables and chart series) per report in `EQDATA_HOME/reports/<kind>/<id>/`, for the `eda` and `study` kinds, rendered by `web` (AD-15).

## Cross-cutting concerns
- **Lock and atomicity:** `runs` holds the lock and `store.commit` is one transaction, so a killed refresh leaves only staging rows, which are cleared at the next start.
- **Credentials:** read in `sources` only, and redacted in logs and events (QR-05).
