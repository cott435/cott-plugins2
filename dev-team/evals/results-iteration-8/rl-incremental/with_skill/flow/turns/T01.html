```markdown
## What we're betting on
- [The 2-3 assumptions that must be true, in plain words]

## Not doing
- [Tempting thing we're deliberately leaving out] — [one-line reason]

## Open questions
- [Only questions that could change the direction. Omit the section if none.]
```

**Writing rules — the brief must pass all of these:**

- **One page or less.** Aim for 250-450 words. If it's longer, cut — don't shrink the font.
- **Plain English.** Write for a smart person outside the team. No acronyms without a definition, no jargon, no code, no file paths.
- **Short sentences, short bullets.** One idea per bullet. No bullet longer than two lines.
- **Data needs, not data vendors.** For ML and data projects, say what data the project depends on in plain terms ("10 years of hourly meter readings, including meters since decommissioned") as a constraint or a bet. Name a specific source only if it's fixed (our own data, a required benchmark). Choosing APIs and datasets happens in the architecture, after the spec.
- **Goals are numbered** so `spec-writing` can trace requirements back to them ("serves Goal 2").
- **3-5 goals, project-level and stage-neutral.** A goal is an outcome of the whole project ("Forecast errors we can trust"), never a stage ("Stage 2: the seasonal fit works"). If the user describes the project in stages, the stages become roadmap stage rows (`roadmap.md`), and every goal stays true whichever stage is being built. More than five goals means the project isn't focused yet — go back to Phase 2.
- **The Not Doing list is mandatory.** It is the most valuable part: it makes trade-offs explicit.

# Ideation: understand, expand, converge

Phases 1 and 2 of every run, New and Extend alike. The mode file says what to read before Phase 1 and what Phase 2 must also settle.

## Phase 1: Understand & expand

1. **Restate the idea** as a "How Might We" problem statement.
2. **Ask 3-5 sharpening questions**, no more, with `AskUserQuestion`: who it's for, what success looks like, real constraints, what's been tried, why now. Don't proceed until you know who it's for and what success looks like.
3. **Generate 5-8 variations**, each with a one-line reason it exists. Lenses: inversion, constraint removal, audience shift, combination, simplification, 10x version, expert lens. `frameworks.md` has more; pick what fits.

In a codebase, ground variations in what exists and cite files. Read `docs/references.md` too; an idea cites a reference as prior art by `RF-NN`, never its path.

## Phase 2: Evaluate & converge

1. **Cluster** what resonated into 2-3 meaningfully different directions.
2. **Stress-test** each: user value (painkiller or vitamin?), feasibility (cost, hardest part), differentiation (would someone switch?), and for ML and data projects, data: does usable data exist, can we use it, what's the non-ML baseline? "No usable data" is a feasibility failure, not an open question. Rubric: `refinement-criteria.md`.
3. **Surface hidden assumptions:** what you're betting is true, what could kill it, what you're ignoring for now.
4. **Get a decision** on a direction before writing anything.
# Roadmap stages

Read when proposing stages at the Review Gate and when adding them on acceptance; the mode file says which stages to propose. An example: `examples-data.md`.

Stages live in `docs/roadmap.md`. A stage is an outcome the user agreed: what they can do when it's done, such as "Data + stats" or "See my spending". It is coarse and unsized. **Don't size it:** no task estimates, no pipeline counts, no splitting a stage because it looks big. Two stages differ by outcome, never by size. Once a stage's pipelines are approved, `build-planning` cuts it into build-sized milestones (`M<n>`), each a vertical slice it can run end to end, and owns those rows.

**Add stages only when the user accepts** (Phase 4). Each stage takes its ID from `dt next-id S` (`dt` as defined in `../SKILL.md`), a short name, and its Source. I'll run this through the idea-refine process. It ends with a one-page brief at `docs/brief.md` and the first roadmap stage. The project is empty right now, so this is the "new project" path. This turn covers step one: understand the idea and widen it out.

## How might we…

**…build a small set of 2D environments where I implement the learning algorithms myself, so that each environment teaches one RL concept that I can watch the agent learn and then explain?**

Snake as the first environment is a good choice, with two caveats:

- **How you describe the board to the agent matters more than the algorithm.**
  - With a compact description (about 11 yes/no facts like "danger ahead", "danger left", "food is up"), basic DQN learns Snake in minutes on a laptop.
  - With the raw grid as input, you need a convolutional network, hours of training, and a lot of tuning. Many first-timers get stuck here and conclude their DQN is broken.
- **"Lab" is a trap if it comes first.** Building a framework for environments you haven't designed yet is how learning projects stall. I'd let a shared structure emerge after environment 2, not before environment 1.

## Questions (these shape the brief)

1. **Background:** Have you used PyTorch, or something like it? Do you already know Q-learning and the Bellman equation, or should the project teach them?
2. **From scratch or a library:** Do you want to write DQN yourself (replay buffer, target network, epsilon-greedy exploration)? Or would you use a library's DQN and focus on designing environments? This choice decides what you actually learn.
3. **What does "it learned" mean to you?** For example: an average score above some number on a 10×10 board, beating a simple scripted bot, or being able to explain *why* it fails when it does?
4. **Constraints:** Is this on your Mac (CPU or Apple's GPU) only? Roughly how many hours a week will you put in?
5. **How much of the "lab" do you want in version 1?** Shared viewing and plotting across environments, or just Snake done well?

## Variations to react to

1. **Snake + DQN from scratch, as you described.** It's the baseline plan.
2. **Two-step ladder: a table first, then DQN.** Start with tabular Q-learning, where the agent stores a value for every situation in a lookup table, on a tiny board with the compact description. Then switch to DQN on the same environment. You'd see for yourself why a neural network is needed instead of a table.
3. **Two ways to see the board.** The same Snake, with a switch between the compact description and the full grid. It teaches what "representation" means in RL by letting you feel the difference.
4. **Reference checks.** Make the environment Gymnasium-compatible (Gymnasium is the standard Python interface for RL environments), and add a hand-written greedy bot and a random bot. Then you can ask "did my DQN beat a 20-line heuristic?" and check your results against a library's DQN when you suspect a bug.
5. **Watching first.** Replay games of any saved checkpoint, and show the agent's value estimate for each move live. This is the part that makes it a *lab* rather than a script.
6. **Snake with no tail.** Just chasing food on a grid, as a warm-up level. The agent learns to seek a reward before it has to learn to avoid itself.
7. **Curriculum.** Grow the board as the agent improves. This is interesting, but it's probably a later environment's concept, not Snake's.

My early view: **1 + 4 + 5 is the core**, and **2 and 3 are the strongest additions for learning**. I'd leave 7 out for now.
