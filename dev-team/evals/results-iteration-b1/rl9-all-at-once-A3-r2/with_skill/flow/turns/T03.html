87	## Decisions
88	### AD-01: Python 3.12 in one uv-managed package
89	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
90	- **Context:** One learner on an Apple Silicon laptop; PyTorch, pygame-ce and Stable-Baselines3 all ship arm64 macOS wheels for Python. QR-06 needs the whole install to work offline once set up.
91	- **Decision:** Python 3.12, one `rllab` package with a `uv.lock`. Stable-Baselines3 and Gymnasium go in an optional `check` extra.
92	- **Alternatives:** Python 3.13: wheels for some libraries lag. Separate `rllab-check` package: a real boundary only if the reference stack becomes a burden, so it is a named seam for now.
93	- **Consequences:** `requires-python = ">=3.12,<3.13"`. Training can run without the `check` extra installed, which proves CHECK-01 at install level too.
94	
95	### AD-02: PyTorch for networks and gradients, not for the learning algorithm
96	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
97	- **Context:** CHECK-01 allows automatic gradient computation but the learner writes action choice, learning targets and updates. Networks are small MLPs on observations of tens of numbers (WORLD-03). Training is CPU-only (QR-01).
98	- **Decision:** Learners use `torch.nn` layers, `torch.optim` optimisers and autograd. Replay buffers, exploration, targets, advantage estimation, clipping and update schedules are hand-written in `methods`.
99	- **Alternatives:** NumPy with hand-derived backprop: teaches backprop, which is not this project's subject, and is slower to debug. JAX: capable, but less familiar CPU tooling and a functional style that hides the update loop.
100	- **Consequences:** `torch.set_num_threads(1)` per run process (AD-05); small batches stay fast on CPU. The PyTorch install is about 200 MB.
101	
102	### AD-03: DQN for discrete actions, PPO for continuous ones, one learner per team
103	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
104	- **Context:** Snake has 3 discrete actions (SNAKE-02); fish and predator-prey push with two numbers in [−1, 1] (FISH-02, PREY-02). Many-fish has 8 agents (FISH-06), and predator-prey has two teams learning at once (TRAIN-07). The brief wants each world to teach one idea, and wants checking against a reference implementation (CHECK-02).
105	- **Decision:** `dqn` (replay buffer, target network, ε-greedy, Huber loss) for snake and the discrete check world. `ppo` (Gaussian policy, GAE, clipped objective) for fish, predator-prey and the continuous check world. All agents of a team share one learner (parameter sharing over a batch of agents). Teams have separate learners in the same run. Evaluation and replay act deterministically: greedy for DQN, the mean action for PPO.
106	- **Alternatives:** PPO everywhere: one method fewer, but snake would not teach value learning. SAC for fish: strong on continuous control, but a third method and harder to explain for many agents. Tabular Q-learning for snake: SNAKE-06 includes length, an unbounded number, so the table would need discretising.
107	- **Consequences:** Two methods to write, each with a check world (TRAIN-06) and a Stable-Baselines3 equivalent (AD-08). A prey that leaves the episode is masked out of its team's batch.
108	
109	### AD-04: Our own multi-agent World protocol, not Gymnasium or PettingZoo
110	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
111	- **Context:** WORLD-01–WORLD-07 need seeded resets, a declared spec, team-labelled agents, per-team scores with a direction, and a drawable state. The brief bets that one core serves a grid game, smooth movement and two teams.
112	- **Decision:** `core.World` is a small protocol. Observations, actions, rewards and active masks are NumPy arrays indexed by agent, teams map to agent indices in `WorldSpec`, and `draw()` returns a `DrawState`. "Not seen" entries are a 0/1 flag followed by zeros, so lengths stay fixed (WORLD-03, FISH-07, PREY-06).
113	- **Alternatives:** Gymnasium: single-agent, with no teams, score direction or drawable state, so all of those would be extras. PettingZoo parallel API: multi-agent, but dict-per-agent stepping is slow in Python and adds a dependency the learner didn't write.
114	- **Consequences:** `refcheck` writes the one Gymnasium/VecEnv adapter (AD-08). Every world implements all five methods, and `core.play_episode` is the only episode loop.
115	
116	### AD-05: Seeds from SeedSequence, disjoint held-out ranges, one process per run
117	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
118	- **Context:** WORLD-01, WORLD-02, TRAIN-02 and REPLAY-02 need exact repeats; TRAIN-04 and EVAL-03 need seeds never used in training; TRAIN-05 and QR-02 need runs in parallel, one per core.
119	- **Decision:** A run seed spawns the learner's, exploration and episode-seed generators through `np.random.SeedSequence`. An episode seed spawns the world's and the policies' generators inside `core.play_episode`. Training draws episode seeds from [0, 10⁶); evaluation seeds are the fixed `core.EVAL_SEEDS` and `core.FINAL_SEEDS` ranges (see Data). `train.run_batch` runs each config in its own `spawn` process with `torch.set_num_threads(1)` and `torch.use_deterministic_algorithms(True)`.
120	- **Alternatives:** Global `np.random.seed`/`torch.manual_seed`: order-dependent, breaks once evaluation interleaves with training. Threads: the GIL serialises the Python world loop.
121	- **Consequences:** Identical runs are promised on the same machine only (TRAIN-02). In-training evaluation never touches the training generators, so turning evaluation off for a test leaves training identical.
122	
123	### AD-06: Run folders of JSON, JSON Lines and torch checkpoints
124	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
125	- **Context:** LOG-01 and LOG-02 need a record and per-episode logs. LOG-06 needs them readable while the run writes, at most one evaluation point behind. A stopped run keeps its checkpoints and is marked incomplete. A run name that already exists is refused (TRAIN edge cases). REPLAY edge cases need a checkpoint to carry its world spec.
126	- **Decision:** One folder per run (see Data). Logs are append-only JSON Lines, flushed at every evaluation point; `run.json` is rewritten atomically (write, then rename) on each status change. A checkpoint is a `torch.save` dict of spec, method configs and state dicts, loaded with `weights_only=True`.
127	- **Alternatives:** Parquet: fast to read but not appendable while a run is live. SQLite: one file for everything, but concurrent writers from parallel runs need care and the files are no longer readable by eye.
128	- **Consequences:** Charts and evaluation read whole JSONL files; at ~10⁴ episodes per run that is instant. A crashed process leaves `run.json` at `running`; `runlog` reports any `running` run with no live process as incomplete.
129	
130	### AD-07: Replays re-simulate into a Trace, shown with pygame-ce and saved with imageio-ffmpeg
131	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
132	- **Context:** REPLAY-01–REPLAY-08 need any checkpoint or baseline from any seed, step back, 4 speeds, side by side, a sight overlay and video export. QR-04 needs ≥ 30 steps/s; QR-06 needs it offline. Worlds are deterministic (AD-05), so nothing needs recording during training.
133	- **Decision:** `replay.trace_sides` (or, for one side, `to_trace` over a traced `core.play_episode`) plays the whole episode headless through `core.play_episode` into a `Trace` of frames (at most the world's `max_steps`), then the viewer only draws frames. Stepping back is an index change. 1× is 30 steps/s. pygame-ce draws circles, cells and text; MP4 (H.264) export goes through imageio's ffmpeg writer.
134	- **Alternatives:** matplotlib animation: slow at 16× for 8 fish and clumsy keyboard control. A browser viewer: smooth, but a local web server and JavaScript stack for one user (spec: everything local).
135	- **Consequences:** The `Trace` is testable without a window, so REPLAY-02 is a frame comparison. Memory is one episode of `DrawState`s, under 1,000 frames of a few dozen objects.
136	
137	### AD-08: Stable-Baselines3 as the reference, isolated in `refcheck`
138	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
139	- **Context:** CHECK-02 needs an established implementation of the same kind of method (DQN, PPO; AD-03) trained on the same world, budget and seeds; CHECK-01 forbids it inside training runs. Worlds speak `core.World`, not Gymnasium (AD-04).
140	- **Decision:** `refcheck` wraps a world as a Gymnasium env (single agent) or as an SB3 `VecEnv` with one slot per agent of the learning team (many-fish: 8 slots stepping one world, matching parameter sharing). It trains SB3 `DQN` or `PPO` for 5 seeds and evaluates on `core.FINAL_SEEDS` through `core.play_episode`. In predator-prey, SB3 cannot co-train two models, so each team's reference trains against the rule-based opponent, the same opponent PREY-08 evaluates against.
141	- **Alternatives:** CleanRL single-file scripts: easy to read, but they would need editing to fit our worlds, which weakens them as a reference. RLlib: multi-agent native, but a heavy distributed stack for a laptop.
142	- **Consequences:** SB3's default hyperparameters differ from ours; `refcheck` starts from the hand-written method's settings where SB3 has the same knob. The predator-prey reference answers a narrower question than co-training, so CHECK-03's 80% bar compares a fixed-opponent reference with a co-trained team there; the learner accepted this (2026-10-17).
143	
144	### AD-09: Every batch first runs the method's check world
145	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
146	- **Context:** TRAIN-06 needs every learning method to learn a hand-derived best behaviour before it is used in a world. Bugs in RL are silent (brief), and methods change while a world is built.
147	- **Decision:** `train.run_check` trains each team method in a config on its check world: for DQN a 6-state corridor with two exits, left of state 0 (reward 0.8) and right of state 5 (reward 1.0), γ = 0.9, so the best action is left in states 0–1 and right in 2–5 and a learner biased to one action can't pass; for PPO a 1-D point that is rewarded for reaching a target, where the best push is the sign of the offset. It needs ≥ 95% agreement over every check-world state. `train.run_batch` runs the same check steps with the batch's method settings before starting any run and refuses the batch on failure. `rllab check <config>` runs it alone.
148	- **Alternatives:** A recorded pass per method version: saves seconds but goes stale silently when code changes. A test only: passes in CI but not for the settings actually used.
149	- **Consequences:** Each batch spends under a minute on the check. A check-world settings override exists because a world's tuned settings (e.g. buffer size) may be too large for a 6-state world.
150	
151	### AD-10: Pipeline entries are the public API; `cli` only dispatches
152	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
153	- **Context:** Pipeline design gave every workflow one entry function calling named steps (PL-01–PL-12). Entries import their steps' owners, so where an entry lives sets an import direction. PL-03 runs PL-02 in worker processes, so `train` can't depend on `cli`. A chart, a summary and a heatmap each need two or more components that the `cli` row already depends on.
154	- **Decision:** `train` hosts the PL-01–PL-03 entries (`run_check`, `run_train`, `run_batch`) and exports them as its contract. Every other entry lives in `cli/pipelines/`. Entries return contract types. `cli/__main__.py` parses arguments, loads configs through `train.load_run_configs`, calls the entry, prints its result and sets the exit code; `cli` owns no pipeline step.
155	- **Alternatives:** All entries in `cli`: the batch's worker processes would import `cli`, inverting the dependency. Each entry in its main component: `charts` and `evaluate` entries would need `runlog` and `baselines` steps, which they may do, but the replay and refcheck entries would need printing in their own components.
156	- **Consequences:** The contract carries the train entries, the config loader and every step function a `cli` entry calls. `cli` has no step tests; its intent tests drive `main` with arguments.

158	### AD-11: Stay a single package past the size triggers
159	**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** system
160	- **Context:** The contract passed its 200-line size ceiling and the package has 12 pipelines, past the ~3-pipeline Grow trigger. The learner chose to stay single (2026-10-17). Nothing runs or deploys on its own, and the one dependency stack the rest shouldn't carry (Stable-Baselines3, Gymnasium) is already isolated as the optional `check` extra in `refcheck` (AD-08).
161	- **Decision:** `rllab` stays one package. Size is handled by `dt context`, which loads only the contract sections and pipelines a task reads, and import-linter keeps the component directions.
162	- **Alternatives:** Split `refcheck` into its own package: a real boundary, but already met by the extra. Split the shared core from the worlds: every world needs the core, and the core has no other consumer.
163	- **Consequences:** The Grow triggers stay reported by `dt` and are answered by this decision. A new trigger (a part that runs on its own, a heavy new stack) reopens it.

Import-linter counts type-only imports, so an annotation can't get around this. LOG-01 and TRAIN-03 need the run record and each checkpoint to carry the full config.
- **Decision:** A type that a component stores or returns, but that a component above it defines, moves to the lowest component that every user can import, usually `core`. The component that consumes the type still validates it, so `train.load_run_configs` checks method settings keys. The types this applies to are listed in the contract: `core.RunConfig` and `core.MethodConfig`.

The frozen interface needs a re-freeze task to move their contract folders.
