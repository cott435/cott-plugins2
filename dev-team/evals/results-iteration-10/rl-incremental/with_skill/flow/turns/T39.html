# Steps, layout and readability rules

Read before writing or changing a step table or the planned layout. The file format is `template.md`.

## Steps

Per pipeline:
- **Entry** `src/<path>/<entry module>::run_<workflow>`, in the pipeline's own entry module (Layout), **Trigger** (a CLI command or a call from another pipeline), **Purpose** (one sentence a newcomer understands: what running it gives the user, not how; `dt explain` leads with it), **Covers** (spec IDs, including whole-run `QR-` IDs; a constraint a decision meets, such as a data source's licence under AD-02, goes on the Covers of the step that applies it).
- **Step table**, one row per call in order, plus a row per library class (below): Step (function name; `PL-NN.<function>` is its ID), Owner (one component, or component.module; a step with two owners is two steps), In → Out, Spine version, Covers. A step another pipeline provides says `PL-01 as built`; one following a reference cites it (`as RF-01, per-window fit`).
- **In → Out names contract types.** Every Out, and every In another step's Out feeds, is a contract `type` section (`Demand → Profile` resolves to `### profile.Profile: type`; qualify as `profile.Profile` only when two components define the name), and every CamelCase name in the cell must resolve to one. Entry arguments (dates, regions, a config field) and the last step's plain result (a path, frames) stay lower-case. The build freezes each of these types first, with a sample, so every step's spine and tests start at once against it. A type the contract lacks is a contract change: list it and route to `architecture-design` Revise; never invent it here. `dt lint` checks it (`step-io-types`).
- **Library classes are steps.** A class a factory or lookup step returns, which the pipeline then drives through a Protocol (`make_dataset` returning `SingleCropSet` as a `Dataset`), gets its own row right after its factory's: Step the class name, Owner its module, In → Out its constructor's input → the Protocol, Spine version a minimal real class (200 synthetic leaves, a model guessing at random). The entry sketch never calls it, but the build gives it a spine of its own, so wiring waits on that spine, never on the class's upgrade. Two classes behind one factory are two rows. The same holds for any contract function or class a step calls (`methods.make_learner`, `runlog.RunWriter`, `store.append_parts`): its own row, unless it lives in the calling step's owner folder (`train.loop` → `train/loop/`). No spine builds a contract symbol beyond its own step.
- **A provider waiting on a probe** (an external API whose probe isn't Answered or Waived) sits behind a Protocol, and the milestone gets a stand-in: a synthetic class row behind the same factory, in a sibling owner folder (`data.weather_synthetic` → `data/weather_synthetic/`), selected by settings. The real provider keeps its row; `build-planning` plans its spine once the probe is Answered.
- **References** (optional): `**References:** RF-01 (remove_seasonality)` after Covers. Never a `references/` path.
- **Entry sketch** (pre-build): calls to the steps in table order and a return, nothing else. A loop, branch or computation is a missing step.

**Contract `Used by:` lines** get the calling PL IDs after the consumer components; symbol IDs are component-qualified even in a single package (`### profile.fit_seasonality: …`).

**Multi-package:** cross-package *system pipelines* are `architecture-design`'s, in the root. A package-local pipeline that is one segment of one names it: `**Entry:** … · **Trigger:** … · **Part of:** PL-05`. Never edit the root.

Revise, and Sync when the doc changes, edit an existing table this way:

- Keep step names where the function survives; a split step gets new rows with new function names. Keep the pipeline's ID: a rebuilt package keeps its PL IDs where it can, so its golden cases still apply.
- If the entry sketch is gone (the spine was built), don't recreate it. The step table is the contract the code must match; the code change becomes a task.
- Keep `Used by:` lines true: add the PL ID to a symbol a new step calls, and remove it from one no step of that pipeline calls any more.

## Layout

One entry module per pipeline, never shared, so two pipelines' wiring never touches one file: `pipeline.py` in the component (single package) or package whose only pipeline it is; where a component runs several, `pipelines/pl<NN>_<workflow>.py` each, and an existing `pipeline.py` stays as it is. One module per step owner (`profile.fit` → `profile/fit.py`; an owner given only as `profile` gets one module per related group of steps), never named like a generated file (`api.schema` beside a generated `api/schema.ts`: call it `api.schema_check`). A step whose module needs private helpers owns a folder instead (`core.train` → `core/train/`), holding them; no other step's code goes inside it. A step with its own upgrade beyond the spine gets its own module (`validate/flags.py`, `validate/coverage.py`), so its thicken task never shares a file; only steps built and thickened together share one. In a single package each component gets a subfolder whose `__init__.py` exports its contract only, so a later Grow is a folder move. Modules on no step: only `__init__.py`, the entry modules, `__main__.py` for a `python -m` trigger (dispatching each trigger to its entry), and `types.py`. Test folders sit at the repo root in every layout, multi-package included: `tests/intent/<pkg>/`, `tests/unit/<pkg>/`, never under the package's folder. Plan against `build-setup`'s size bar (500 lines per module, 60 per function, or `CONSTRAINTS.md`'s values): split a module expected to pass it now.

## Readability rules

`build-setup` copies these into `CONSTRAINTS.md`; builders and reviewers enforce them.

- One entry function per pipeline, reading as calls to its named steps; each step owned by one component, its function living there.
- No registries, plugin dispatch or config-driven wiring unless an `AD-NN` says so. A new abstraction needs a second real implementation or a seam the architecture named.
- Every spine version is real and minimal, often the baseline, never a mock, stub or hard-coded return; it stays as what upgrades must beat. Only a step calling another pipeline or package may run against that boundary's fixture-backed fake, until the milestone's system task swaps in the real provider; a step consuming another step's output is built and tested on that type's frozen sample, never on a fake of the step. An object with behavior (a Protocol or class) or a call into another component's function is frozen as its Protocol or signature plus a fixture-backed replay double, which is that type's sample, not a fake.
- A decision-backed exception goes on the row or pipeline, citing it (`dataset lookup by name (AD-06)`).

## Overview
One Python package, `rllab`, run from the command line, holding two environments (Snake and the fish tank) on one shared core. A training run builds one environment setup (Snake with a reward, or the tank with a fish count and a view) and one learner from the registry. It plays games from seeds derived from the run seed, and hands every acting agent's move to the learner: Snake's one snake, or every fish in the tank sharing one policy. At each of 20 curve points it pauses training to play the setup's 100 reserved test games greedily, then writes the point to the run's folder. When the run finishes it saves the agent and its test games and marks the run's status last. The replay viewer rebuilds any saved game by stepping the environment through its saved moves, and draws Snake's move scores or each fish's swim arrow and spread. Training, testing, storage, comparison and replay see only the `core` protocols and the registry, never an environment or a learner (AD-04, AD-11).

65	## Data
66	- **Experience (DATA-01):** every game is an environment from `registry.make_env` started from a seed. In each environment, seeds 0–99 are the test seeds (`evaluate.test_agent`); training game seeds are drawn from the run seed's generator in `[1_000, 2^31)`, so they never meet a test seed (AD-05).
67	- **Run evidence (RUN-02):** `runs/<env>/<learner>/<setup>/seed-<n>/<UTC timestamp>-<short id>/` holds `settings.json`, `curve.json`, `agent.npz` (table) or `agent.pt` (DQN, policy gradient), `test_games.jsonl` (seed, each step's moves for every agent, per-agent move scores or spreads, game score after each step, ending) and `status.json`, written last (AD-06). `<setup>` is `plain` or `shaped` in Snake and `fish-<1|5>-<short|wide>` in the tank. Baselines are stored the same way, with no curve: Snake's under the setup `none`, the tank's under the fish count and view they were scored with (BASE-07).
68	- **Explanations (EVAL-06):** the learner writes one Markdown file per comparison, `reports/<env>/explanations/<comparison id>.md`; `compare` reads them, never writes them.
69	- **Reports (EVAL-03–EVAL-05):** `reports/<env>/report.md` and its PNG charts, one report per environment, rebuilt from the runs on every `rllab compare` (AD-14).

71	## Cross-cutting concerns
72	- **Reproducibility (RUN-03, RUN-09, SNAKE-08, TANK-13):** every random draw comes from a `np.random.Generator` or `torch.Generator` derived from the run seed; PyTorch runs on CPU with one thread and deterministic algorithms (AD-05). Adding the tank changes no Snake code path, seed stream, setup label or file format, so Snake runs saved before it rerun, compare (AD-14) and replay identically.
73	- **Time (QR-01, RUN-07):** `train` checks the wall clock after every step and at every test game; at 60 minutes it stops and saves what it has. Elapsed seconds are saved with each curve point. A step is one environment step, whatever the number of agents (AD-11).
74	- **Errors:** an unknown environment, setup value or learner, or a learner from the other environment, raises `UnknownName` with the valid choices; a disk error while saving marks the run incomplete with the missing evidence listed; Ctrl-C marks it incomplete.
75	- **Testing:** pytest. RUN-08 is checked with a test-only second environment, a tiny grid walk in `tests/`, trained, tested, stored and replayed through the same code. RUN-09 is checked against a Snake run saved before the tank lands.

85	## Decisions
86	### AD-01: Python 3.12 in one package, `rllab`
87	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
88	- **Context:** One learner, one laptop, PyTorch basics already known (brief). The lab needs one install and no separate deployments; both environments train, compare and replay through the same commands.
89	- **Decision:** Python 3.12 managed with uv; a single package `rllab` with one folder per component and one `rllab` command. The shared core is kept apart by the import layers (Components), not by a package boundary.
90	- **Alternatives:** Python 3.13: PyTorch and pygame-ce wheels for Apple Silicon lag on new versions. Several packages (core, envs, agents): no separate install or deployment boundary (AD-04); UR-34: "Keep one package despite the contract length warning"; UR-65: "Keeping it in the single package with a clearly separated shared-core component is fine".
91	- **Consequences:** `requires-python = ">=3.12,<3.13"`. `core` and the runners are the seam that would become their own package if environments multiply.
92	
93	### AD-02: Hand-written learners on PyTorch, CPU only
94	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
95	- **Context:** UR-07: the user chose "(a) Write DQN myself in NumPy/PyTorch"; UR-32: "PyTorch is fine for AD-02", over NumPy with hand-written backpropagation. TAB-04, DQN-07 and PG-08 forbid ready-made learning algorithms. QR-02: an Apple Silicon laptop, no NVIDIA card. The networks are tiny (11 inputs, a handful of outputs).
96	- **Decision:** The table learner is NumPy. Every network is a small `torch.nn` MLP whose learning rule (targets, returns, advantages, losses, batch sampling, target refresh, clipping) is written in the learner's own component; `dqn` (AD-03) and `pg` (AD-12) set their networks. PyTorch supplies only tensors, autograd and the Adam optimizer; `torch.distributions` is not used. No RL library is imported anywhere. Everything runs on the CPU; the Apple GPU (MPS) is not used.
97	- **Alternatives:** NumPy with hand-written backpropagation: you'd learn the gradient maths too, but the backward pass, not the RL, becomes the work. Stable-Baselines3 or similar: ruled out by DQN-07, PG-08 and UR-07. MPS: slower than the CPU for networks this small, and nondeterministic.
98	- **Consequences:** Autograd hides the gradients but not the learning rule. Import-linter forbids RL libraries and `torch.distributions`.

100	### AD-03: One DQN learner, the rung a setting
101	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** dqn
102	- **Context:** UR-06: Snake is "Good first env for DQN-style value learning". DQN-01–DQN-04 build four rungs. DQN-05 and SHAPE-05 require neighbouring rungs to differ only by the added piece.
103	- **Decision:** `dqn.DQNAgent` takes a `DQNSettings` whose `rung` is `plain`, `replay`, `target` or `double`, with a `torch.nn` MLP of 11 → 64 → 64 → 3. Each rung turns on exactly one more piece: a replay store sampled in batches, a frozen copy refreshed every `target_every` updates, Double DQN target selection. The plain rung trains on each move as a batch of one. All other fields share defaults, and `compare.build_report` refuses a pair whose saved settings differ anywhere else.
104	- **Alternatives:** Four separate classes: duplicated code, so one rung's change can leak into another unseen. A single class with independent on/off flags: allows combinations the ladder never compares.
105	- **Consequences:** A rung's added piece is one code branch, easy to read and test against its hand-computed target. Later variants (prioritised replay, say) add a rung value.
106	
107	### AD-04: A shared core reused across environments
108	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
109	- **Context:** UR-16: "a shared core reused across environments: env interface, training loop, logging, replay viewer". UR-22: "build it through Snake, shaped by Snake's needs, and adjust it later". UR-53: "reuse the shared core (env interface, training loop, logging, replay viewer) from Snake". RUN-08 requires a second environment to need no changes to training, testing, saving or replay. The brief rules out a general framework built ahead of need.
110	- **Decision:** Environments implement `core.Env`; agents implement `core.Agent`, and learners `core.Learner`. The runners (`train`, `evaluate`, `store`, `compare`, `replay`) import only `core`, `registry` and each other, never an environment or a learner; environments and agents come from `registry`. `core` holds only what the lab's environments use; AD-11 sets its shape for Snake and the tank. A test-only grid walk proves RUN-08.
111	- **Alternatives:** Environment-specific runners: RUN-08 would fail, and the tank would copy the loop. A Gymnasium-style interface: adds spaces, wrappers and render modes beyond what the two environments need, and Gymnasium itself brings dependencies the lab doesn't use.
112	- **Consequences:** A new environment that needs something `core` lacks (image observations, say) changes `core`, as UR-22 expects. Import-linter enforces the layers.

114	### AD-05: Seeds, test-seed reservation and CPU determinism
115	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
116	- **Context:** RUN-03 needs identical curves on a rerun; SNAKE-08, TANK-13, TAB-03, DQN-06, PG-07 and REPLAY-07 need repeatable games; EVAL-01 needs test seeds never used in training; RUN-09 needs Snake's draws untouched by the tank.
117	- **Decision:** A run seed builds a `np.random.SeedSequence`, spawned into separate generators for training game seeds, move choice (exploration or sampling from the policy), batch sampling and network initialisation (a `torch.Generator`), the same four for every learner and environment. Test seeds are 0–99; training game seeds are drawn from `[1_000, 2^31)`. Torch runs with `torch.set_num_threads(1)` and `torch.use_deterministic_algorithms(True)`. Each game owns its own generator from its game seed, so food placement, the ball's start direction and the fish's start spots depend only on the seed and the moves.
118	- **Alternatives:** A global seed (`np.random.seed`): any new random call shifts every later draw. Several threads: faster on big networks, but the reduction order varies between runs.
119	- **Consequences:** Results reproduce on the same laptop and library versions, not across machines; `settings.json` records the versions. One thread stays fast enough for these networks (Risks).

121	### AD-06: One folder per run, status written last
122	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
123	- **Context:** RUN-02 lists the evidence; RUN-05 forbids overwriting; RUN-06 and RUN-07 mark runs incomplete or over time and keep them out of comparisons; the disk-full edge case must name the missing evidence.
124	- **Decision:** `store.begin_run` creates a new folder `runs/<env>/<learner>/<setup>/seed-<n>/` whose name ends with a UTC timestamp and a short random id, and writes `status.json` as `running` first. Curve points are appended as they come. `finish` writes the agent and test games, then rewrites `status.json` with the final status and any missing files. Every file is written to a temporary name and renamed. Test-game moves are written as JSON numbers: integers for discrete moves, float32 values written as the exact float64 they convert to, so they read back bit for bit. `list_runs` treats `running` with no live process as incomplete.
125	- **Alternatives:** SQLite: queryable, but a run's evidence is no longer a folder you can open and read. MLflow or Weights & Biases: extra servers or accounts for one learner on one laptop.
126	- **Consequences:** Comparisons scan folders; for 60-odd runs that's instant. Evidence is plain JSON you can open; agents are `.npz` or `.pt`. A tank run's 100 saved test games are a few megabytes.

128	### AD-07: Replay in a pygame window, rebuilt from saved moves
129	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** replay
130	- **Context:** REPLAY-02–REPLAY-05 and REPLAY-08–REPLAY-09 need the board or tank, Snake's move scores or each fish's swim arrow and spread, pause, step and 1–30 steps per second. REPLAY-06 needs the replay to match the scored game. Web deployment is out of scope.
131	- **Decision:** `replay` rebuilds each frame by resetting the environment to the saved seed and stepping through the saved moves. It raises `ReplayMismatch` if a step's game score or the ending differs from the saved game. It then draws each `core.Frame`'s shapes (cells, circles, rings) in a pygame-ce window, scaled from the frame's bounds, with the frame's labels beside it: space pauses and resumes, the right arrow steps, the up and down arrows change speed. What the agent shows follows `core.ActionSpace`: for discrete moves, one bar per move score with the chosen move marked; for continuous moves, an arrow from each acting agent's shape along its chosen move and the agent's numbers (the tank: spread). Baselines show "n/a".
132	- **Alternatives:** A Matplotlib animation: its widgets can't reliably hold 30 frames a second with controls. A self-contained HTML player: needs a JS front end to maintain, closer to the web work the brief leaves out. A terminal (curses) view: can't draw a circular tank.
133	- **Consequences:** Saved games are small (moves only). The viewer draws any `Frame` and any `ActionSpace` kind, so a new environment replays unchanged (RUN-08).

135	### AD-08: Comparisons through the null-hypothesis-testing skill; explanations are the learner's files
136	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** compare
137	- **Context:** EVAL-04 and EVAL-05 require the `null-hypothesis-testing` skill on 5 seeds × 100 test games, at 5% after correction for the number of comparisons in the report. EVAL-06 and EVAL-07 need a written explanation for each result. BASE-07 scores a learner against baselines run on its own setup.
138	- **Decision:** Every comparison step in `compare` hands the skill both sides' per-seed, per-game scores on the same test seeds of the same environment setup (5 × 100 for a learner, 1 × 100 for a baseline), alpha 0.05 and the comparison count of that environment's report (AD-14). The skill chooses the test, the correction and the null distribution; `compare` maps its verdict to beats/ties/loses or better/worse/no difference. Explanations are Markdown files the learner writes under `reports/<env>/explanations/`; an empty or missing file is unexplained.
139	- **Alternatives:** A fixed Welch t-test in code: replaces the procedure the skill owns. Explanations stored in run folders: they belong to comparisons, not runs.
140	- **Consequences:** The test can change without touching the report. A comparison waits until both sides have their complete runs (5 seeds for a learner, one baseline run on the same setup) (EVAL-04).

150	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
151	- **Context:** RUN-03 reruns a run from its saved settings, and AD-03 and AD-12 refuse a ladder pair whose saved settings differ beyond the added piece (DQN-05, SHAPE-05, PG-05). Pipeline design found that nothing filled a learner's defaults before `store.begin_run` writes `settings.json`, so a run using defaults would save an incomplete `params`. UR-37: "Go ahead with the five contract changes."

157	### AD-11: The core speaks several agents and continuous moves, frozen before M1
158	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** system
159	- **Context:** UR-53: "reuse the shared core (env interface, training loop, logging, replay viewer) from Snake". UR-52: "a good fit for policy-gradient / PPO and continuous control". The tank has 1 or 5 fish moving at once (TANK-01, TANK-04), removed one by one (TANK-07), sharing one policy (PG-06), scored in seconds, drawn as circles, and shown with arrows (REPLAY-09). AD-04 sized `core` to Snake: one agent, 3 moves, an integer food count, a grid frame. No code exists yet; M1's interface task will freeze `core` (UR-65 keeps one package).
160	- **Decision:** Every environment is several agents stepped together; Snake is one. `Env` has `n_agents` and an `ActionSpace` (`discrete` with named moves, or `continuous` with a vector size and a speed cap, plus the names of the numbers an agent shows in a replay). `reset` returns one observation row per agent; `step` takes one move per agent and returns per-agent rewards, which agents still act, whose experience ended, and the game's score so far as a float. `Agent.act` maps rows to moves, each row on its own, so one policy plays every fish. `train` passes one `Transition` per acting agent per step, in agent order, to `Learner.observe`; a step is one environment step. A removal, a Snake ending and the tank's time cap all end that agent's experience with no next term. `Frame` is shapes in world units (cells, circles, rings) instead of grid cells. These shapes land in M1's interface task, so Snake is built on them from the start.
161	- **Alternatives:** Keep the Snake-shaped core for S1 and change it when the tank lands: every S1 module would change and saved Snake runs would need migrating, against RUN-09. A separate tank loop: copies training, logging and replay, against UR-53. Fish as separate single-agent games: the ball and the nearest-fish view need every fish in one world.
162	- **Consequences:** Snake's learners handle a one-row batch, and its saved moves are one-element lists; nothing Snake does changes. M1's approved plan and the pipelines must be rechecked against these contracts before the build starts. Treating the cap as an ending keeps every learner's rule simple, but the tank's critic must guess a return it can't see coming (Risks).
163	- **Probe:** none — no external API.

165	### AD-12: One policy-gradient learner, Gaussian swims, the rung a setting
166	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** pg
167	- **Context:** UR-52: "I want it to be a good fit for policy-gradient / PPO and continuous control". PG-01–PG-04 build four rungs; PG-05 requires each to differ only by the added piece; PG-06 shares one policy across fish; PG-07 samples in training and takes the most likely move in tests; REPLAY-09 shows each fish's spread; PG-08 forbids library algorithms.
168	- **Decision:** `pg.PGAgent` takes a `PGSettings` whose `rung` is `reinforce`, `baseline`, `actor_critic` or `ppo`. The policy is a diagonal Gaussian over the swim velocity (x, y): an MLP 11 → 64 → 64 → 4 gives the mean and the log spread of each axis for the fish's own view, the log spread clamped to [−5, 1]. Training samples a move from the move-choice generator; tests take the mean; the replay shows the mean of the two spreads. The fish learns from the move it sampled; the tank caps the speed. Log-probabilities, discounted returns, advantages, losses and the clipped ratio are written in `pg`. Each rung adds one piece: `baseline` subtracts a separate critic (11 → 64 → 64 → 1) trained toward the returns; `actor_critic` replaces the return with the one-step estimate, learning every `steps_per_update` steps; `ppo` makes `passes` clipped passes over each batch in minibatches. `reinforce` and `baseline` update once every agent's experience has ended.
169	- **Alternatives:** A spread that doesn't depend on the view: steadier, and usual for PPO, but every fish would show the same number at every step, so REPLAY-09 would say nothing. PPO with generalised advantage estimation: the textbook form, but it adds a second piece to the PPO rung, against PG-05. Discrete swim directions: fits value learning, not the continuous control UR-52 asks for.
170	- **Consequences:** The four rungs share one code path, each step testable against a hand-computed value. The PPO rung is weaker than the textbook one, which is a result to explain (EVAL-06), not a defect. Later variants (generalised advantages, say) add a rung value.
171	- **Probe:** none — no external API.

173	### AD-13: The tank simulated in NumPy, a fixed 0.1-second step
174	**Status:** Accepted · **Date:** 2026-10-18 · **Scope:** tank
175	- **Context:** TANK-02 needs a mirror bounce at a constant speed; TANK-04 a move every 0.1 s capped at 2.5 units per second; TANK-05 a wall stop; TANK-07 removal at the end of each step; TANK-13 identical games from a seed. QR-01 needs a 5-fish PPO run and its test games inside 60 minutes.
176	- **Decision:** `tank.TankEnv` holds positions as NumPy arrays and runs each step in a fixed order: cap each move's speed, move every acting fish and stop it at the wall (centre at most 9.75 from the centre), move the ball 0.2 units with any bounce taken at the exact point it meets the wall (centre 9.5 from the centre), then remove every fish within 0.75 of the ball. Views are computed for all fish at once.
177	- **Alternatives:** A physics library (pymunk, Box2D): collision solvers built for rigid bodies, with their own time steps and float paths, for one bouncing ball. A ball bounce found by clamping after the move: the speed changes at a bounce, against TANK-02.
178	- **Consequences:** One step is a few dozen array operations, cheap enough for 600-step games. The step order is part of the game: changing it changes saved tank games.
179	- **Probe:** none — no external API.

189	## Risks and open questions
190	- One CPU thread might not fit a run plus 20 × 100 test games inside 60 minutes (QR-01): a DQN run on Snake, and above all 5-fish PPO, whose test games are up to 600 steps each. Mitigation: the first DQN task and the first tank PPO task each time 10,000 steps and one round of test games, and the step budget is set from that. Test games can be stepped as a batch if needed.
191	- The table learner sees at most 2^11 situations but only a few hundred occur; it may plateau well below the scripted bot. That is a result to explain (EVAL-06), not a defect.
192	- Determinism (RUN-03, RUN-09) holds only on the same laptop and library versions. `settings.json` records them, and the rerun check compares like with like.
193	- The tank's time cap ends experience like a removal (AD-11), but a fish's view has no clock, so the critic of the upper rungs sees the same view end in very different returns. It may learn slower; a result to explain. Counting the cap as a cut-off would be a change to AD-11 and AD-12.
194	- A view-dependent spread (AD-12) can collapse or blow up; the clamp bounds it, and the curve shows it (the PG edge case).
195	- M1's plan was approved against the earlier contract. On approval, `pipeline-design` updates PL-01–PL-03 for these contracts and the tank, `test-planning` adds tank cases and a RUN-09 case, and `build-planning` rechecks M1's interface task before the build starts.
196	- Grow: 14 components and a contract well over 200 lines trip the size trigger; the lab stays one package (UR-34, UR-38, UR-65).

211	### core.ActionSpace: type
212	`@dataclass(frozen=True) class ActionSpace: kind: Literal["discrete", "continuous"]; size: int; names: tuple[str, ...]; max_norm: float | None; score_names: tuple[str, ...]`
213	- **Invariants:** `discrete`: `size` moves named by `names`, a move is an `int` in `[0, size)`, `max_norm` is `None`; `continuous`: a move is a float32 vector of length `size`, its components named by `names`, its length capped at `max_norm` by the environment; `score_names` names the numbers `Agent.scores` gives per agent (Snake: `straight, left, right`; the tank: `spread`) (AD-11)
214	- **Boundary:** snake, tank, registry, evaluate, replay · **Fixtures:** tests/contracts/core.ActionSpace/ · **Cases:** Snake's 3 moves; the tank's capped 2-vector
215	- **Used by:** snake, tank, registry, evaluate, replay
216	
217	### core.Step: type
218	`@dataclass(frozen=True) class Step: obs: np.ndarray; rewards: np.ndarray; acting: np.ndarray; ended: np.ndarray; done: bool; score: float; ending: str | None`
219	- **Invariants:** `obs` float32 `(n_agents, obs_size)`, rows of agents not acting all 0; `rewards` float `(n_agents,)`, 0 for agents that didn't act; `acting` bool, who moves next; `ended` bool, whose experience ended on this step (removed, killed, or the game ended); `done` exactly when no agent acts; `score` is the game score so far (Snake: food eaten; the tank: TANK-10's mean seconds survived); `ending` is `None` until `done`, then an environment-defined name (Snake: `wall`, `body`, `starved`, `full_board`; the tank: `all_removed`, `time_cap`)
220	- **Boundary:** snake, tank, evaluate, train, replay · **Fixtures:** tests/contracts/core.Step/ · **Cases:** an ordinary Snake move; a food move; a wall death; a tank step removing 1 of 5 fish; a tank step reaching the cap
221	- **Used by:** snake, tank, evaluate, train, replay
222	
223	### core.Transition: type
224	`@dataclass(frozen=True) class Transition: agent: int; obs: np.ndarray; action: int | np.ndarray; reward: float; next_obs: np.ndarray; done: bool`
225	- **Invariants:** one agent's step; `obs` and `next_obs` float32 `(obs_size,)`; `action` an `int` for discrete moves, the float32 vector the agent chose (before any cap) for continuous ones; `done` is that agent's `Step.ended`, and when `done` every learner ignores `next_obs`
226	- **Boundary:** train, tabular, dqn, pg · **Fixtures:** tests/contracts/core.Transition/ · **Cases:** a mid-game Snake move; a game-ending Snake move; a tank fish's move; a tank fish's removal
227	- **Used by:** train, tabular, dqn, pg
