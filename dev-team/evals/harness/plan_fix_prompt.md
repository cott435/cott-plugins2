You are fixing a finished set of planning documents before a solo developer starts building. A reviewer checked them against the developer's own messages and against each other, and listed the defects in `.review/review.json`. Apply them.

## What you have (paths relative to the folder you are in)
- `.review/review.json`: the defect list. Each defect has a `file`, an exact `quote`, `evidence` and a `fix`.
- `.review/user_messages.md`: every message the developer sent, in order. It is the ground truth when a fix is unclear; a later message overrides an earlier one.
- `docs/`, `tasks/`: the docs you edit. `tests/fixtures/<pkg>/TC-NN/expected.json`: a golden case's expected output, which you may change only as the fact rules below allow. Context packets are generated from these docs, so a packet defect is fixed in the doc the packet reads (a task's **Read:** or **Writes:** line in `tasks/plan.md`, a section in a `contract.md`).
- The plan tool: `{DT} lint` checks every doc's IDs, references and formats; `{DT} context <task>` prints a task's packet as the builder will see it; `{DT} route test-planning "<change>" --from plan-review` records a change for test-planning's Revise.

## Rules
- Edit only files under `docs/` and `tasks/`, and `expected.json` files as the fact rules allow. Never touch `.review/`, `references/`, any other file under `tests/` or any code. Don't create CONSTRAINTS.md or other build-setup files.
- Keep every ID, heading, table column and field format exactly as it is. Don't renumber or retire IDs; add new IDs only where a fix needs a new requirement, case or task, using the next free number (`{DT} next-id <prefix>`).
- One exception to not renumbering: when a fix adds a milestone inside a stage, milestones that have no plan yet (no tasks) may be renumbered so the IDs read in build order. Update every Depends cell and every mention of a renumbered milestone. Never renumber a milestone that has tasks.
- **Narrower is measured on the plan, not the wording.** When a fix offers options, or leaves the shape of the edit to you, take the one that freezes fewer contract symbols and adds fewer dependency edges, even if it takes more words. An interface task freezes only its own milestone's types, not later milestones'. Never add a dependency between two interface tasks or between two spines. When a task needs a symbol, fake or file that another task writes, move that symbol or fake into a task that already depends on both, or give the needing task the type on its **Read:** line, instead of adding an edge.
- When the brief and the spec disagree, `.review/user_messages.md` decides: keep the developer's own words and change the doc that departs from them. Never weaken a doc's wording of what the developer asked for to match the other doc.
- **No reordering.** Never move a task block, a requirement, a case or a table row within its file (the milestone exception above aside). A new ID goes after the last one of its kind in its section, with the next free number. A new dependency points only at a task earlier in the plan. If lint's order rule would need a block moved or an edge to a later task, skip that part of the fix and say why.
- **A changed fact reaches every doc and every test case.** When a fix changes a fact (above all one the developer stated), grep `docs/`, `tasks/` and `tests/fixtures/` for the old value: its own words, and the words a case would use for it (a count, a score's name and direction, a limit, a shape). Change every place that restates it, not only the file the defect names: brief, spec, architecture, contract, pipelines, roadmap, plan acceptance, and each case in a `tests.md`, including its title, **Source:**, **Expected:** and **Tolerance:** wording. After the fix, no doc may contradict another.
- **Expected values in a case.** An expected value that is the developer's fact itself (a count, a limit, a shape, a score's direction) changes to the developer's value, in the case's **Expected:** and in its `expected.json`. Quote the developer's turn in `oracle_edits`. A value that would have to be computed (a golden number, a score on a worked instance, a value derived from inputs) is never written by you. Delete the stale value from **Expected:** and from `expected.json`, and mark the case for test-planning to re-derive in the form test-planning uses for a headless oracle change:
  1. The `tests.md` header's **Status:** goes to Draft.
  2. An Open questions bullet names the case and what must be re-derived, and why.
  3. Record it with `{DT} route test-planning "TC-NN: re-derive <what> (<fact> changed)" --from plan-review`.
  Edit `expected.json` only with Edit, never through Bash. Never retire a case or delete a fixture.
- **Before you reply, re-grep every changed fact's old value** across `docs/`, `tasks/` and `tests/fixtures/`. Fix each hit that still restates it. Report each hit you leave, with why, in `leftovers`: for example, an **Alternatives:** line recording the rejected option, or a quote of the developer's earlier words.
- Prefer deleting stale or narrating text to rewording it. Don't add process notes ("fixed in review", "updated") anywhere.
- Each fix stays small and local. A fix that would need a redesign (a new package, a re-cut of milestones across the whole roadmap) is applied only as far as the docs can carry it now (the Outline, Exit, Depends, Skills, References lines), and otherwise skipped with the reason.
- If a defect is wrong (the quote isn't there, the developer's messages say otherwise, or the fix would break something), skip it and say why.
- When you're done, run `{DT} lint` and fix every error your edits introduced (warnings that were already there can stay). Then run `{DT} context` on two or three tasks you changed and check the packet now holds what the fix added.

## Output
When everything is applied, reply with ONLY a JSON object, no other text:
