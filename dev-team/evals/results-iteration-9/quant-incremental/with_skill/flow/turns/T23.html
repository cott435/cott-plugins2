# Extend mode: an idea file

`docs/brief.md` exists, so the new idea gets its own file and must earn its place in the project. Examples: `examples-extend.md`, `examples-ml.md`, `examples-data.md` (stage skills and references).

**Read before asking anything:** `docs/brief.md`, `docs/spec.md`, `docs/roadmap.md` and open ideas in `docs/ideas/`. Their problem, goals, constraints, Not Doing list and requirements constrain the new idea. `Specced` ideas are frozen records; where one disagrees with the spec, the spec is current.

- A `Draft` brief: ask whether to finish reviewing it first.
- A `Draft`, `Accepted` or `Parked` idea covering the same ground: offer to refine it instead. A `Specced` one is frozen; a change starts a new file.

**Phases 1-2** per `ideation.md`. Before Phase 1, restate the new idea in terms of the existing project: "This adds [X] so that [existing user] can [outcome]." Note which existing features and requirement IDs it touches.

**Fit check (during Phase 2) — answer one of these out loud. It decides whether the brief changes:**

| Finding | Idea file | Brief |
|---|---|---|
| Serves an existing goal. Every new stage of the same project does | Write it | **No change.** This is the common case. A new stage never adds a goal, even when the user asks for one: the stage is its roadmap row and the idea's *Serves* line. |
| Needs a new goal: the project's outcome itself widens, same problem and user | Write it | Add the goal with the next number. If that makes more than five, merge before writing: propose which goals fold together, your merge as the default, and write the merged set. Never write a sixth goal. |
| Changes a constraint (deadline, budget, a rule) | Write it | Update Constraints. |
| Contradicts the Not Doing list | Write it only if the user reverses that decision | Remove the item, with the user's agreement. Otherwise park the idea. |
| Different problem or different user | Don't write it | Push back: this may be a separate project with its own brief. |

**Writing rules for idea files:**

- **Plain English, still no requirements.** Describe what the user experiences and why; `spec-writing` turns that into requirement IDs and acceptance criteria.
- **More room than the brief, not unlimited.** Aim for 300-700 words. The extra space goes to *How it fits*, *Alternatives considered*, and *Open questions* — the context the spec needs.
- **One idea per file.** If the conversation produced two separable ideas, write two files (ask the user which to do first).
- **Write it as a record, in the brief's voice.** The file outlives the review. Notes to the user ("my proposed limit, for you to check") belong in the conversation. Questions belong under *Open questions*.
- **Tool preferences live here, not in the spec.** If the user names a library, dataset or service ("hand-write the CNN, then compare with a torchvision model"), record it under *Recommended direction* or *Data*. `spec-writing` writes the behavior without the name, and `architecture-design` reads the name from here.
- **Never paste the idea into the brief.** Brief edits are limited to the fit-check table above. Goal numbers stay stable; new goals take the next number, and a merged goal keeps the lower one. If a goal is dropped or merged away, tell the user which spec requirements referenced it.

**Review Gate** (`../SKILL.md`): also say whether the brief changed and which sections.

**Stage** per `roadmap.md`: one stage for the idea, Source `ideas/<slug>.md`. Skip it only when the idea's *Stage* line says it joins a stage not yet being built.

**Idea status lifecycle:** `Draft` → `Accepted` (user approved here) → `Specced` (set by `spec-writing` once the spec is approved). Parked ideas get `Parked` with a one-line reason, so they aren't re-proposed blindly. **A `Specced` idea is frozen.** It records why the feature was added, as it stood that day. `spec-writing` adds a one-line banner saying so, and nobody edits the file afterwards. The spec is the current description. When a new idea changes what a `Specced` one describes, such as a narrowed holdout or a merged stage, the new idea gets its own file and names the old one under *Touches*. The old file is not edited.

# Ideation: understand, expand, converge

Phases 1 and 2 of every run, New and Extend alike. The mode file says what to read before Phase 1 and what Phase 2 must also settle.

## Phase 1: Understand & expand

1. **Restate the idea** as a "How Might We" problem statement.
2. **Ask 3-5 sharpening questions**, no more, with `AskUserQuestion`: who it's for, what success looks like, real constraints, what's been tried, why now. Don't proceed until you know who it's for and what success looks like.
3. **Generate 5-8 variations**, each with a one-line reason it exists. Lenses: inversion, constraint removal, audience shift, combination, simplification, 10x version, expert lens. `frameworks.md` has more; pick what fits.

In a codebase, ground variations in what exists and cite files. Read `docs/references.md` too; an idea cites a reference as prior art by `RF-NN`, never its path.

## Phase 2: Evaluate & converge

1. **Cluster** what resonated into 2-3 meaningfully different directions.
2. **Stress-test** each: user value (painkiller or vitamin?), feasibility (cost, hardest part), differentiation (would someone switch?), and for ML and data projects, data: does usable data exist, can we use it, what's the non-ML baseline? "No usable data" is a feasibility failure, not an open question. Rubric: `refinement-criteria.md`.
3. **Surface hidden assumptions:** what you're betting is true, what could kill it, what you're ignoring for now.
4. **Get a decision** on a direction before writing anything.
# Roadmap stages

Read when proposing stages at the Review Gate and when adding them on acceptance; the mode file says which stages to propose. An example: `examples-data.md`.

Stages live in `docs/roadmap.md`. A stage is an outcome the user agreed: what they can do when it's done, such as "Data + stats" or "See my spending". It is coarse and unsized. **Don't size it:** no task estimates, no pipeline counts, no splitting a stage because it looks big. Two stages differ by outcome, never by size. Once a stage's pipelines are approved, `build-planning` cuts it into build-sized milestones (`M<n>`), each a vertical slice it can run end to end, and owns those rows.

**Add stages only when the user accepts** (Phase 4). Each stage takes its ID from `dt next-id S` (`dt` as defined in `../SKILL.md`), a short name, and its Source. Leave the Status* cell empty, then run `dt roadmap`, which fills it. Under the tables, add a `## S<n>: <Name>` section with one plain-English `**Outline:**` line (what the user can do when the stage is done) and one `**Skills:**` line.

**Stage skills and references.** The `**Skills:**` line is the one record of which skills serve a stage; later skills start from it and `build-planning` checks each one lands on a milestone and then a task. Propose the skills whose descriptions fit the stage (project `.claude/skills/*/SKILL.md` and the installed skills in your context), and ask once: "Route profile-report and significance-check to S2? [yes / edit]". None fit → `**Skills:** —`. Also offer each `references_unassigned` entry that serves the stage ("RF-02 and RF-03 (boosting) → S3? [yes / edit]"). On acceptance, write the line and set `**Milestones:**` on each RF entry the user assigned to the stage ID (`—` becomes `S3`; otherwise append). Those two fields are all you write in the roadmap sections and `docs/references.md`.

# Example: a demand-forecasting package

A data-dependent New project with its first roadmap stages, then a later idea routing stage skills and references.

## GridLoad (New Project, Data-Dependent)

**User invokes:** `/ideate a Python package for forecasting our utility's electricity demand — I keep rewriting the same notebook code`

### Phase 1: Understand & Expand

**Skill response:**

> **How might we** get from a forecast idea to an evaluation we can actually trust, without rebuilding the data and scoring plumbing every time?

Before expanding:

1. **Who uses it?** Just you, or a small team that needs to compare each other's results?
2. **What horizon and resolution?** Day-ahead? Hourly? By region?
3. **What data do you have today, and what's the budget?** Free sources, an existing subscription, or room to pay?
4. **Research only, or does this end up feeding operations?**

**User responds:** "Me and two analysts. Hourly by region, day-ahead is what matters. We have the utility's meter export and pull weather from a free public weather API. Budget maybe $100/month. Research only for now."

**Skill continues:**

"Rewriting notebook code" is the symptom. The expensive problem is **not trusting the results**. One-off notebooks are where look-ahead and missing history creep in, and a forecast that only scores well because of a bug is worse than no forecast.

Here are 5 variations:

1. **Model Engine First:** A clean training and scoring loop. Forecasts plug in. Data is the user's problem.
2. **Data Layer First (Inversion):** Start from trustworthy data, not the engine: a local store of readings and weather as known at any time, with one interface. Any simple model is fine once the data is right.
3. **Simplification — Tabular Only:** No sequence models. A forecast is a function from a region-by-hour feature table to predictions. Fast and enough for day-ahead.
4. **Combination — Notebook Kit:** Keep notebooks, but ship the pieces as a library: data loader, scoring function, standard error report.
5. **10x — Full Platform:** Scheduled data pulls, experiment tracking, and a model registry. Clearly too much for three people.

### Phase 2: Evaluate & Converge

**Data feasibility decides this one.** Today's readings are easy: they are the utility's own export. **Meter history including decommissioned meters** is not: the export lists today's registry, so every regional total quietly drops removed meters and past load looks wrong. Scoring with weather actuals where only the forecast was known has the same effect on errors. That's the dealbreaker to check first: can both be had within $100/month?

**Direction (2 + 3): Trustworthy data layer + tabular forecasts.** It attacks the real problem (trust). It fits day-ahead hourly forecasts. Hiding the weather source behind one interface keeps the provider decision open.

**Direction (1): Model engine.** More flexible training, but none of your forecasts need it yet. Pushing back: this is where these projects usually sink months.

The user picks (2 + 3).

```markdown

A small forecasting team (1-3 people) testing day-ahead hourly demand forecasts for one utility's service area.
```

The new stage idea is next. I've read the brief, spec and roadmap. Before I suggest directions I have a few questions for you, plus two points I'd push back on.

**The idea restated:** this adds a return-structure and portfolio stage so that you can work out which covariance estimate gives the lowest realized variance out of sample, using the trusted point-in-time S&P 500 data, before any return prediction. The question it answers: how might you tell whether a better covariance estimate actually lowers out-of-sample variance, rather than only looking better in sample?

**Fit:** it serves Goal 4 (each later stage builds on the same trusted data), so the brief doesn't change. It reads data through `QUERY-01`–`QUERY-05` (as-of reads, versions, universe reads) and depends on `UNIV` and `PRICE-02` total returns. It doesn't conflict with anything on the Not Doing list.

**Two points to push back on**
1. **PCA market removal and minimum variance pull in different directions.** A portfolio's realized variance includes market risk. If the market mode is removed before estimating covariance, minimum variance is optimizing the wrong thing. PCA works better here in one of two roles:
   - as a diagnostic: what the structure looks like and how dominant the market mode is;
   - as its own estimator: a k-factor model plus diagonal residuals, with k set by the Marchenko–Pastur edge. That joins your first two steps into one estimator rather than a preprocessing chain.

   RF-01 does the removal. Its caveats (fitting on the whole sample, zero-filling missing returns) are what this stage must avoid.
2. **Equal weight (1/N) should be the baseline.** Classical estimators often fail to beat it out of sample. If no estimator beats 1/N, that is a real result, not a failure.

**Questions**
1. **Where do results live?** Reports and plots from research code only, or pages in the explorer app too, such as eigenvalue spectra and portfolio comparisons?
2. **Universe and timing:** the full point-in-time S&P 500 at each rebalance (about 500 names, with names delisted mid-period kept through their exit)? How often do you rebalance, and how long is the trailing window? With about 500 names and a 1-year window there are more names than days, so the sample covariance is singular and plain minimum variance on it isn't defined.
3. **Constraints:** long-only, or are shorts allowed? Do turnover and transaction costs count, or only variance?
4. **What counts as "right":** a ranking by realized variance, or must the differences be shown to be more than chance? If they must, the `null-hypothesis-testing` skill would handle that, alongside `data-analysis` for the spectra and the estimator comparison.

**Directions I'd weigh once you answer**
- **A. Portfolio as the scorecard (your direction, tightened):** sample, shrinkage, denoised and PCA-factor estimators feed minimum variance, risk parity and HRP. Rolling out-of-sample tests rank them by realized variance against 1/N.
- **B. Known answer first:** run A first on a synthetic panel with planted factors and a known covariance, then on real data. Every estimator gets a correctness check before real numbers are trusted.
- **C. Narrower first cut:** estimators feed minimum variance and 1/N only. Risk parity and HRP follow once the estimator ranking is settled.

I lean towards **A with B's synthetic check built in**. Please answer the questions, then I'll draft `docs/ideas/` for your review.
