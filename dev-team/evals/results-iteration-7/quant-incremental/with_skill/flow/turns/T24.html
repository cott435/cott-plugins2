# Quant Lab — Architecture

**Status:** Approved · **Shape:** Multi-package · **Last updated:** 2026-10-17 · **Spec:** [spec.md](spec.md)

## Overview
`builder` is the write side: it downloads raw snapshots, builds and validates immutable dataset versions with their exploratory reports, and runs the `qlab` command line. `data` is the read side: the shared types, the data home's layout, version resolution and the point-in-time loader that `server` and research code use. `server` is a local Python backend over both: HTTP for queries, WebSocket for live run progress. `web` is the TypeScript + React browser app, which talks only to `server`, through one generated contract.

  builder -- "download" --> sources["Sharadar · EODHD"]
  builder -- "writes" --> home[("Data home: snapshots, dataset versions, run log")]
  data -- "reads" --> home
```

## Dependency rules
- `data` imports nothing internal. Research code in later stages depends on `data` alone.
- `builder` imports `data` only through [data's contract](packages/data/contract.md); `data` never imports `builder`.
- `server` imports `data` and `builder` only through their contracts; neither imports `server`.
- `web` reaches `server` only over HTTP and WebSocket, through the types generated from the server contract (AD-12). It imports no Python and no hand-written copies of server types.
- Only `builder` writes to the data home; `data` and `server` only read it. `server` starts and cancels runs through `builder`.
- Enforced by import-linter contracts in the project checks (Python) and an ESLint import boundary plus a contract drift check (web) (AD-01, AD-12, AD-15).

- `builder.start_run`, `builder.cancel_run`, `builder.read_events`, `builder.list_runs`, `builder.RunEvent`, `builder.RunRecord`: run control and progress, used by `server`. [Contract](packages/builder/contract.md)
- The HTTP endpoints and WebSocket messages (`server.StockView`, `server.RunEventMessage`, …): used by `web`. [Contract](packages/server/contract.md)

## System pipelines

### PL-01: Build or update the dataset

### PL-02: Live run progress
**Trigger:** any run is active, whoever started it · **Covers:** RUN-02, RUN-03, RUN-05, RUN-06, RUN-07, QR-03

3. `web` → `server`: `server.list_runs` / `server.get_run` for history and state after a reload

### PL-03: Explore the dataset
**Trigger:** the researcher opens or changes a view in the app · **Covers:** APP-01–APP-07, QR-02
1. `web` → `server`: a query endpoint (`server.get_stock`, `server.get_universe`, `server.get_validation`, `server.get_trace`, `server.get_eda`, `server.list_versions`, `server.diff_versions`, `server.search`)

The S2 architecture is written as a Draft. Every S2 requirement now has a home, nothing is stale, and `dt lint` has 0 errors.

## What changed
**New package `portfolio`** (`docs/packages/portfolio/architecture.md` and `contract.md`). It depends on `data` only and has 8 modules:

| Module | What it covers |
|---|---|
| `harness` | The rebalance calendar, eligibility, strict window slicing, the holding month (drift, delistings, cash), and equal weight |
| `structure` | PCA, the Marchenko–Pastur edge and signal count, and residuals |
| `estimators` | The 4 covariance estimators |
| `allocators` | Minimum variance with OSQP, risk parity, and HRP on market-removed correlations |
| `scoring` | The three estimator scores |
| `claims` | Every "lower variance" claim, tested via `null-hypothesis-testing` |
| `reports` | The reports, written with `data-analysis` and charted with `dataviz` |
| `cli` | `qlab-portfolio run` |

Its contract has 14 symbols: `RunSpec`, `run_walk_forward` and `RunResult`, plus the hand-off types (`Returns`, `Window`, `Structure`, `CovEstimate`, `Weights`, `HoldingMonth`, `EstimatorScore`, `ClaimTest`, and the estimator and allocator name types).

**Root architecture:**
- The overview and diagram now include `portfolio`.
- There's a new row in the package table, and new dependency rules: `portfolio` imports only `data`, and nothing imports `portfolio`.
- There's a new system pipeline, **PL-14: Walk-forward comparison**. It loads data from `data` once per run, then asks `data` for the universe at each rebalance.
- The tech stack gained NumPy 2, SciPy 1.14, OSQP 0.6 and matplotlib 3.9.
- A cross-cutting note covers determinism and speed.

**New decisions (Proposed):**
- **AD-18:** the `portfolio` package, and why it isn't inside `data` or `builder`.
- **AD-19:** the numerical stack. Shrinkage, denoising, the repair to a valid matrix, risk parity and HRP's splitting are written from basic array operations.
- **AD-20:** one returns load per run, sliced strictly per window.
  - Missing days stay missing (NaN), never zero.
  - Adjusted prices are never used, so no later split or dividend can leak in.
  - This slicing is the one place look-ahead could enter. The HARN-04 property test guards it.
- **AD-21:** reports go in `QLAB_HOME/research/portfolio/<run-id>/`.
  - `results.json` holds every number, rounded and with sorted keys, so CMP-06 can compare reruns exactly.
  - It sits beside `report.md` and static PNG charts.
  - The run ID is derived from the inputs.

**Accepted decisions revised in place:**
- **AD-15** now says *"Only `builder` writes dataset files; research packages write only their own report folders."*
- `data`'s architecture lists the new `research/portfolio/` folder in its description of the data folder.

## Assumptions
- **Names:** Python package `qlab_portfolio` and command `qlab-portfolio`. Strategy names look like `"denoised/hrp"`, plus `"equal"`.
- **Inputs:** `run_walk_forward` takes a `RunSpec` with defaults matching the spec: window 252, coverage 0.8, at least 20 stocks, at most 10 factors.
- **Missing data:** windows are T×N arrays with NaN for missing days. Only `harness` slices by date.
- **Speed:** each window's eigendecomposition is computed once and shared by the structure analysis, denoising and the factor model (QR-07).
- **Determinism:** single-threaded linear algebra, fixed solver settings and a seeded bootstrap.

## Risks
- **Solver precision:** OSQP's iterative tolerance could make weights differ in the last digits across machines. Mitigation: polishing is on, results are rounded, and CMP-06 is checked on one machine.
- **Honest null results:** with about 220 months, real differences between estimators may not survive the correction. The reports will say so, and that's a legitimate outcome.
